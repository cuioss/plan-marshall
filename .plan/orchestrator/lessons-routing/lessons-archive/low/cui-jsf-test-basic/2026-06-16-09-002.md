# Sonar HTTPS-required error when auth is configured against an http:// host

The `sonar-roundtrip` finalize step failed with `Unexpected error: HTTPS
required when authentication is configured` when the configured Sonar host
URL used the `http://` scheme while an authentication token was also
configured. SonarQube refuses to transmit credentials over plaintext HTTP;
the host URL must be `https://` (or authentication must be removed for a
local non-TLS instance). The step is advisory in finalize, so the run
proceeded — but the Sonar round-trip was silently skipped, losing the
issue-triage pass it exists to perform.

## Context

In `recipe-refactor-to-profile-standards-module-testing`, the
`sonar-roundtrip` step dispatched `plan-marshall:workflow-integration-sonar`,
which exited non-zero:

```
[ERROR] (plan-marshall:execute-script:1) script_failure
  notation=plan-marshall:workflow-integration-sonar:sonar
  exit_code=1 failure_kind=script_internal_failure
  detail=error: "Unexpected error: HTTPS required when authentication is configured"
```

The error originates from the Sonar client's pre-flight guard: when a token
or login credential is present in the provider configuration, the client
refuses any request whose base URL is not `https://`. The intent is to
prevent leaking the bearer token over the wire in plaintext.

## Root Cause

A configuration mismatch between two provider settings:

- An authentication credential (token / login) is configured for the Sonar
  provider, **and**
- The configured `sonar.host.url` (or the provider base URL) uses `http://`
  rather than `https://`.

The two settings are individually valid but mutually incompatible: auth
implies a secure transport. The client treats the combination as a hard
error rather than silently downgrading security or stripping the token.

## Solution

Reconcile the two settings so transport and auth agree:

- **Production / hosted SonarCloud / SonarQube**: set the host URL scheme to
  `https://`. This is the correct fix in nearly all cases — the server
  already terminates TLS.
- **Local / CI scratch instance with no TLS**: either front it with an HTTPS
  reverse proxy, or remove the configured token so the client makes
  anonymous requests over `http://` (only acceptable for a throwaway local
  instance with no sensitive data).

Verify via `manage-providers` (or the equivalent provider-config surface)
that the stored Sonar base URL and the auth token are consistent before the
finalize step runs, so the round-trip is not silently skipped.

## Impact

Any plan whose finalize manifest includes `sonar-roundtrip` against a
mis-configured provider (auth + `http://`) will lose its Sonar triage pass.
Because the step is advisory and never blocks finalize, the failure is easy
to miss — the plan ships green with no Sonar findings, which looks identical
to "Sonar found nothing". The signature to watch for is the exact string
`HTTPS required when authentication is configured` in the work log; treat it
as a provider-configuration defect to fix, not a transient to retry.
