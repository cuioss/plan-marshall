# weakened_test check flags assertions removed together with a declared dead-code deletion

## Problem

Q-Gate finding b3c230 (`weakened_test at ClaimValueTest`): 5 assertions were removed along with the dead method ClaimValue.isNotPresentForClaimValueType. The outline declared that deletion in deliverable 3. The operator accepted it.

## Solution

The weakened-test check should read the deletions the outline declares, and treat assertions that only exercised a declared-deleted production member as expected removals rather than findings.

## Provenance

Candidate lesson from plan plan-25-epic-leftover-sweep (epic quality-report), inbox message 005; source: qgate 6-finalize b3c230 (functional-review, round 1, accepted). Re-filed as 012, 021, 028 (same declared deletion, 2 rounds, 2 review steps).

## Recurrence: a declared behaviour reversal (plan-27-test-size-guideline-restore, PR #887)

The same gate failed the same way when the declared change is a behaviour reversal, not a dead-code deletion. PLAN-27's spec reverted the PLAN-25 explicit-null refusal and replaced its tests with `IdentifierClaimNullEquivalenceTest`. The check raised five blocking `weakened_test` errors (ClaimNameTest 4 assertions, StrictStringMapperTest 4, MapRepresentationTest 12, IdentifierClaimNullRejectionTest 15, TokenBuilderExplicitNullTest 7), each at functional-review and again at code-review at the same head, so the operator closed the identical five removals twice, and again at a second head (inbox messages 001-005, 007-011).

Three facets beyond the original:

1. The detector counts a deleted-and-replaced test class as a pure assertion loss; it does not credit the replacement class (a rename plus rewrite reads as a removal).
2. An operator acceptance at functional-review does not carry over to code-review: the code-review step re-raises the same removal and needs its own close.
3. The code-review author did not transcribe the mechanical weakened_test rows into its findings file, so the verifier refused the verdict ("the mechanical weakened_test rows are not in the findings file and 5 blocking findings remain"), the step looped back once, and only then could the operator close (inbox message 012; message 006 records the same loop at functional-review).

Candidate fix beyond reading declared deletions: let a spec declare expected test removals (class and reason) in a form the review can read, carry an accepted removal across the two review steps for one head, and credit a successor class named in the spec.
