# Prefer Jest's built-in --silent flag over a custom console-stubbing setup file (avoids hiding errors during local debugging)

The goal of this plan was to stop Jest's captured console output (`console.warn` /
`console.error` / `console.info` emitted via the `log` utility in `utils.js`)
from being printed by `npm run test` / `test:coverage` during the Maven build,
where each line is re-prefixed by Maven's `[INFO]` and reads like a nested
failure that can mask a real error.

## What was built first (the anti-pattern)

A bespoke console-silencing mechanism was implemented:

- a new global setup file `jest.setup-console.js` that overwrote
  `console.debug` / `console.info` / `console.warn` / `console.error` with
  `jest.fn()` no-op stubs,
- a `beforeEach` hook re-stubbing those `console` methods every test,
- a dedicated `console-silence.test.js` regression test asserting the stubs
  were in place.

This worked for the build, but the PR automated-review bot (Gemini) flagged it
as over-engineered and worse, harmful to local debugging.

## Why it was the wrong approach

1. **A built-in tool flag already solved the problem.** Jest ships a `--silent`
   CLI flag that suppresses all console output from the test run. The custom
   setup file, the regression test, and the `beforeEach` re-stubbing were all
   reinventing a one-flag built-in.

2. **Global no-op stubs degrade the local-debugging DX.** Overwriting the global
   `console` methods with `jest.fn()` swallows console output *everywhere*,
   including interactive local runs (`npm run test`, `npm run test:watch`).
   When a test fails locally, the developer needs the warning/error text and
   stack traces — the global stubs hid exactly that diagnostic output. Jest's
   `--silent` only suppresses printing to the terminal; it does NOT disable
   `jest.spyOn(console, ...)`, so tests that assert on console output still pass.

3. **The `beforeEach` re-stubbing was also redundant.** `restoreMocks: true`
   (and `jest.restoreAllMocks()`) only restores spies created via
   `jest.spyOn()`. Directly assigning `console.debug = jest.fn()` is a property
   overwrite Jest does not track, so it survives across tests without any
   `beforeEach` re-application — the hook added complexity for nothing.

## Fix applied

Reverted the bespoke mechanism entirely (commit d6faac6):

- removed `jest.setup-console.js` and `console-silence.test.js`,
- reverted the `package.json` `setupFilesAfterEach` change,
- added `--silent` to the build/CI scripts:

```json
"test:coverage": "NODE_ENV=test jest --coverage --silent",
"test:ci": "NODE_ENV=test jest --coverage --watchAll=false --passWithNoTests --silent"
```

Local-debugging scripts (`test`, `test:watch`) keep console output; only the
Maven/CI-facing scripts gain `--silent`, so the nested `[INFO]`-wrapped output
disappears from the build log without hiding anything from a developer running
tests interactively.

## How to apply (generalizable)

- **Reach for the tool's built-in flag/option before building a custom test-
  infra mechanism.** "Suppress console output during CI runs" is a solved
  problem in most test runners (Jest `--silent`, etc.). Adding a setup file +
  global mocks + a regression test to do what one CLI flag does is wasted
  surface area and a maintenance liability. Check the runner's own docs first.

- **Never globally stub/no-op `console` (or any diagnostic output) in shared
  test setup.** It hides errors and stack traces during interactive local
  debugging, which is the moment a developer most needs them. If output must be
  quieted, scope it to the CI invocation (a CLI flag on the CI script) so the
  default local run stays verbose.

- **Apply silencing per-invocation, not per-environment.** Differentiate the
  build/CI script (silent) from the local/watch script (verbose) at the
  `package.json` script level, rather than via a setup file that affects every
  run uniformly.

- **`restoreMocks` only restores `jest.spyOn` spies, not direct property
  assignments.** If you do overwrite `console.x = jest.fn()` directly, a
  `beforeEach` re-stub is redundant — but the better answer is not to overwrite
  at all (see above).
