title: "CodeRabbit's rate-limit ETA is unparseable and its window slides, so the claim clock is not the real window"
content: "## Context

`automatic-review`'s refusal-recovery arm claims a rate window through `manage-locks` and
waits it out. On plan `misconfigured-reviewer-name-reads-missing-review` (PR #1392) that arm
mis-modelled CodeRabbit's window twice, in two independent ways, and the two compounded into
the run's longest operational stall — roughly four hours between the first refusal and the
first real review.

**1. The stated ETA is never extracted.** CodeRabbit publishes its reset in prose:
`Next included review available in 59 minutes`, and later `in 40 minutes` and `in 51 minutes`.
The registry's `coderabbit` `rate_limit_eta_patterns` matched none of them, so the producer
returned `eta: \"\"` and the claim fell back to the verb's default window. The run recorded the
drift itself:

> `18:35:28Z WARNING` — \"The claim carries the verb DEFAULT 3600s window only because the
> registry rate_limit_eta_patterns failed to extract that stated eta (producer reported
> eta=''), so the claim clock is not the real window. REGISTRY DRIFT to file: add the
> 'Next included review available in N minutes' phrasing to coderabbit rate_limit_eta_patterns.\"

**2. That default collides with an unrelated budget.** The synthetic fallback is `3600.0s`
and this plan's `review_rate_window_timeout_seconds` is also `3600`. At the boundary,
*\"the window expired\"* and *\"the await budget was exhausted\"* are the same number, so the two
outcomes cannot be told apart from the claim alone. The collision is coincidental, which is
what makes it dangerous — nothing declares the two values are related and nothing would notice
if one moved.

**3. The window SLIDES; it does not reset on a fixed boundary.** At `20:07:25Z` the run read
the `18:48:30Z` notice's \"40 minutes\" and computed a reopening at `~19:28:30Z`, concluding the
window was open. It was not: a fresh notice now stated **51** minutes, and the
`trigger_comment` posted on that reading drew a third `Review rate limited` reply. That burned
recovery attempt 2 of 2 and produced the `blocked_user_review` return
(`escalate_ask{reason: rate_window_exhausted}`) at a cost of 187,858 tokens.

## Root cause

Two separate assumptions, both unstated: that a refusal notice's ETA is machine-extractable
by the current pattern set, and that the interval a notice states is anchored to when that
notice was posted. Neither holds for CodeRabbit. When the first fails the code substitutes a
default rather than recording that it could not measure; when the second fails a stale notice
is read as authoritative.

## Proposed action

1. Add the observed phrasings to `coderabbit` `rate_limit_eta_patterns`:
   `Next included review available in N minutes` and the bare `in N minutes` form.
2. **Do not silently substitute a default for an unextractable ETA.** Record
   `eta_source: stated | defaulted` on the claim so a consumer can tell a measured window from
   a guessed one, and make the defaulted case say so in its decision-log line rather than
   leaving the reader to discover it.
3. Break the `3600` collision: derive the fallback window from something other than the value
   `review_rate_window_timeout_seconds` happens to hold, or publish both numbers on the claim
   so an equal pair is legible as a coincidence rather than a cause.
4. Model the window as **sliding**: re-read the bot's newest refusal notice at claim-check
   time and treat a fresher notice's stated interval as authoritative over the claim clock. A
   claim whose backing notice has been superseded is stale by construction.

## Recurrence — 2026-09-05 (shipped-guards-assume-the-meta-projects-own-layout)

Both halves recurred on PR #1397, unfixed, and the run diagnosed each independently.

**Half 1 — the ETA is still unextractable.** At `18:30:42Z` the run recorded:

> \"registry ETA drift: `pr wait-for-comments` classified coderabbit's refusal correctly
> (`cause=quota`, `class=awaitable_window`) but returned `eta=\"\"` although the notice states
> 'Next included review available in 57 minutes'. coderabbit's `rate_limit_eta_patterns` in
> `automatic-review/standards/coderabbit.md` does not match that wording, so Branch 2 would
> omit `--window-seconds` and fall back to the default window instead of the stated 3420s.\"

This is the **same phrasing** proposed action 1 of this lesson asks to be added, observed
again with a third numeral. The pattern set was not updated between the two plans.

**Half 3 — the sliding window bit again, twice.** The run stated it plainly at `23:20:22Z`:

> \"the orchestrator's window arithmetic has now been WRONG TWICE (inferred 'long open' from an
> 08:09Z trigger, then inferred reset at ~22:43Z from a 21:43Z spend). CodeRabbit's stated
> reset is not reliably derivable from the last observed spend, so stop inferring it.\"

Each wrong inference cost a refused trigger plus roughly 900s of polling (903s / 28 polls,
then 931s / 29 polls). The run's conclusion — stop inferring, apply the operator's fixed
sleep-and-retry policy verbatim — is the operational form of this lesson's proposed action 4,
reached the expensive way.

**One thing this recurrence adds that the lesson does not cover.** After the second refusal
the run read the *full* refusal body rather than only its classification and found the real
blocker was not the window at all: \"This command is applicable only when automatic reviews
are paused.\" Automatic reviews were not paused, so `@coderabbitai review` was the wrong
instrument and no amount of correct window modelling would have made it succeed. Filed
separately as lesson `2026-09-05-07-003`; noted here because a reader arriving at this lesson
during a stall should check instrument applicability before tuning the window model.

Cost on this run: 3 of an operator ceiling of 10 waits spent, one of them a full 5400s.
