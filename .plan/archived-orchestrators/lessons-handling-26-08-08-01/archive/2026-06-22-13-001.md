# Local ruff select omits the RUF family, so RUF002 ambiguous EN DASH in Python docstrings slips past every in-house gate and only the PR bot catches it

The local quality-gate runs `ruff check` with `select = ["E", "W", "F", "I", "B", "C4", "UP"]` (see root `pyproject.toml` `[tool.ruff.lint]`). The `RUF` rule family is NOT in that select list, so `RUF002` (docstring contains ambiguous EN DASH `–`, "did you mean HYPHEN-MINUS `-`?") is never evaluated by any in-house gate — not `module-tests`, not `quality-gate`, not `verify`. CodeRabbit, by contrast, runs ruff with its full default rule set (which includes `RUF`), so it flags every ambiguous-unicode occurrence the project's own gate is structurally blind to.

During PR #751, three Python files shipped `R1–R4` written with a literal EN DASH (U+2013) inside their module docstrings — `claude_pretooluse_hook.py` (lines 12, 228), `pretooluse_gate.py` (line 29), and `test_claude_pretooluse_hook.py` (lines 8, 20). All in-house gates were clean; the PR review bot raised three RUF002 inline findings, all remediated in-run by replacing the EN DASH with an ASCII hyphen.

## Root cause

This is a gate-coverage gap, not an authoring mistake in isolation. The EN DASH is easy to introduce — many editors and paste sources auto-substitute `–` for `-`, and the glyphs are visually near-identical. Because the project gate omits `RUF`, the only thing standing between an ambiguous-unicode character and merge is an external review bot. That is the same slipped-then-caught defect class as lessons `2026-06-21-12-002` (MD040 not in the in-house markdown gate, only markdownlint-cli2 catches bare fences) and the `2026-06-21-21-001` / `2026-06-22-11-001` cluster (in-house gates clean, only adversarial PR bots caught it) — but the root cause here is specifically the ruff `select` list, which none of those cover.

## Corrective action

Do X instead of Y:

- **Y (avoid):** relying on the in-house `quality-gate`/`verify` ruff run to catch ambiguous-unicode characters in Python source or docstrings. It cannot — `RUF` is not selected.
- **X (do):** add the `RUF` family (or at minimum `RUF001`, `RUF002`, `RUF003`) to `select` in root `pyproject.toml` `[tool.ruff.lint]`, so ambiguous-unicode characters are caught at the local gate before push. When authoring or editing Python docstrings/comments, use only ASCII hyphen-minus `-` for ranges like `R1-R4`; never paste an EN DASH `–` or other ambiguous glyph.

Adding `RUF` to the select list closes the gap at the build-pyproject layer (the skill that owns the canonical ruff invocation) and converts this defect class from "PR-bot-only" to "fails the local gate", which is where it belongs.

## Impact

Affects every Python file in the marketplace. Any ambiguous-unicode character (EN DASH, EM DASH, fancy quotes, non-breaking space) introduced into Python source or docstrings will pass the local gate and reach the PR, costing a review-bot round-trip and an in-run remediation commit that the local gate should have prevented.

PR #808 (plan `plugin-doctor-framework-refactor`) confirmed the gap is not RUF002-specific — it is the whole `RUF` family. `test/pm-plugin-development/plan-marshall-plugin/test_discover.py:99` unpacked `has_fm, fm, _fields = extract_frontmatter(content)` in `test_unclosed_frontmatter`, but the test only asserts `has_fm is False`, leaving `fm` unused. This is the **second distinct RUF-family rule** (after RUF002) to slip past on the identical root cause — the omitted `RUF` family in the local ruff `select`. Two independent rules from the same omitted family now have a PR-bot-only catch on the record, which raises the priority of the corrective action above: adding `RUF` to `select` in root `pyproject.toml` would have caught both RUF002 and RUF059 at the local gate. Until that lands, expect further RUF-family findings (RUF001/002/003 ambiguous unicode, RUF059 unused unpack, etc.) to keep arriving as review-bot-only round-trips.
