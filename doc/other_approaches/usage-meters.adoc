**Verdict: not relevant as tooling.** One cross-check idea (see <<_what_to_learn>>).

== What they are

Meters that show remaining quota and the next reset, so an operator avoids starting a large task just
before a limit. They save no tokens.

[cols="2,5",options="header"]
|===
| Tool | Summary

| UsageScope
| Closed-source menu-bar app for macOS and Windows covering several providers. For Claude it signs in
  with OAuth and queries the provider for quota and reset windows; whether it also parses local
  session logs is not documented. https://www.usagescope.com/

| ccusage
| Open-source CLI that parses the local session logs under `~/.claude/projects/` into usage reports.
  https://github.com/ryoppippi/ccusage

| Others
| Several open-source menu-bar meters exist (ClaudeBar, Claude-Usage-Tracker, usage-menubar); their
  data sources were not inspected.
|===

== Assessment against plan-marshall

`manage-metrics` records per-phase and per-dispatch token composition (`input`, `output`,
`cache_read`, `cache_creation`), tool-use counts and exploration-share byte counters. That is the
instrument the token roadmap is built on; a quota meter adds operator convenience, not project
capability.

== What to learn

. **Cross-check the instrument against an independent enumeration.** `manage-metrics` totals and a
  log parser such as ccusage read the same underlying session records through different code. Agreement
  between the two over a window is evidence the instrument counts completely; disagreement is a
  defect in one of them. The project's own rule is that a total should be derived from an independent
  enumeration, not asserted.
