## G2 — Site 2 exempts a dirty tracked `.plan/` path whose porcelain rendering is quote-escaped

- **Kind:** bug
- **Severity:** high
- **Where:** `marketplace/bundles/plan-marshall/skills/plan-marshall/scripts/_git_helpers.py:53-100` — `git_dirty_files` (the un-`-z` `git status --porcelain` call at `:71-72`, the quote-strip-without-unescape at `:96-97`), consumed by `_invariants.py:676` `_capture_main_dirty_files` → `_filter_main_dirty_paths` (`:615-641`) → `_plan_state_exemption.partition_plan_state_exemption`
- **What is wrong:** The two sides of the trackedness comparison use different path encodings. `git_dirty_files` runs `git status --porcelain` **without `-z`**, so with git's default `core.quotePath=true` a path containing a non-ASCII byte (or a space/quote) comes back C-quoted and octal-escaped; the helper strips the surrounding quotes but leaves the escapes. `tracked_plan_paths` runs `git ls-files -z`, which emits raw bytes. The escaped string is therefore never found in the tracked set and falls into the **exempted** branch. **Re-reproduced during adversarial review** on a purpose-built repo at HEAD: with a committed-then-dirtied `.plan/ünï.json`, `git_dirty_files(repo)` returned `['.plan/\\303\\274n\\303\\257.json', '.plan/local/', '.plan/marshal.json']` and `partition_plan_state_exemption(...)` returned `retained=['.plan/marshal.json']`, `exempted=['.plan/\\303\\274n\\303\\257.json', '.plan/local/']` — a **tracked** `.plan/` file dropped as untracked. Site 1 is immune: `post_run_source_guard._observe_dirty_source` on the same repo returned `offenders=['.plan/marshal.json', '.plan/ünï.json']` because it observes with `-z` and decodes via `parse_porcelain_z`.
- **Why it matters:** It is a false-clean of precisely the defect class this plan exists to close: the layer-D drift capture silently drops a tracked `.plan/` leak, so `_check_main_dirty_drift` can never see it and the boundary reports no drift. Reachability is bounded — it fires only when a tracked `.plan/` path carries a character git quotes, and none of the repo's current 13 tracked `.plan/` paths do (`marshal.json`, `project-architecture/_project.json`, eleven `{module}/enriched.json`, where the variable segment is a build-map module id). The bound limits the blast radius, not the wrongness: the guard's verdict is decided by a string comparison between two observations that do not speak one encoding.
- **Fix:** Make the two observations speak one encoding. Either switch `git_dirty_files` to `git status --porcelain -z` and decode with the existing `phase-6-finalize/scripts/post_run_source_guard.py::parse_porcelain_z` logic (extract it to `script-shared` so both sites share it, matching D1's own "one predicate, not two copies" principle), or run both git calls with `-c core.quotePath=false`. Add a regression test alongside `test_capture_main_dirty_files_reports_tracked_plan_state` that commits a tracked `.plan/` file with a non-ASCII name, dirties it, and asserts it is retained.
- **Done when:** with a committed tracked `.plan/ünï.json` dirtied in a throwaway repo, `_capture_main_dirty_files` returns a list containing that path spelled as `git ls-files` spells it, and a test pinning it fails against today's `git_dirty_files`.
- **Module/topic:** `plan-marshall:plan-marshall` scripts — `_git_helpers` / layer-D drift capture / `script-shared:_plan_state_exemption`.

## G5 — A STAGED DELETION of a tracked `.plan/` file is exempted at BOTH guard sites

- **Kind:** bug
- **Severity:** high
- **Where:** `marketplace/bundles/plan-marshall/skills/script-shared/scripts/_plan_state_exemption.py:58-86` — `tracked_plan_paths` (the `git ls-files -z -- .plan/` observation at `:76`), consumed by `partition_plan_state_exemption:113`; reaches both confirmed sites (`post_run_source_guard.py:201`, `_invariants.py:640`)
- **What is wrong:** The trackedness oracle is `git ls-files`, which reads the **index**. `git status --porcelain` reports a *staged deletion* under the path's **pre-image** spelling, which by then is no longer in the index. The two disagree exactly for a removed tracked file, and the predicate resolves the disagreement by exempting. Reproduced by execution at HEAD on a throwaway repo (tracked `src.md` + tracked `.plan/marshal.json` committed, then `git rm .plan/marshal.json`):
  - `post_run_source_guard._observe_dirty_source(repo)` → `(True, [], ['.plan/marshal.json'], ['.plan/marshal.json'], None)` — **`clean: True`**, the removed tracked descriptor published as *exempted plan state*.
  - `partition_plan_state_exemption(git_dirty_files(repo), repo)` → `([], ['.plan/marshal.json'])` — site 2 retains nothing, so layer-D sees no drift.
  A *rename* (`git mv`) is NOT affected: both sites retain the destination path and report `clean: false` (verified on a third probe), so the defect is specifically the removal case, where there is no destination path to rescue the verdict.
- **Why it matters:** This is the plan's own defect surviving inside its fix, in the case that needs no exotic filename: an ordinary `git rm` of a tracked `.plan/` descriptor (the shape an architecture-refresh takes when a module disappears) is a tracked, post-merge, unpushable mutation, and both fixed guards report it clean. It also refutes a supporting claim the run and the original verification both made — that `exempted_paths` is *structurally* empty at site 1 because `--untracked-files=no` has already dropped untracked paths. It is not: a staged deletion enters `considered` and leaves through `exempted`, so the published population actively mislabels a tracked path as untracked plan state.
- **Fix:** Widen the oracle in `_plan_state_exemption.tracked_plan_paths` so "tracked" means *tracked in the index OR at HEAD*: union the existing `git ls-files -z -- .plan/` result with `git ls-tree -r -z --name-only HEAD -- .plan/` (verified to list `.plan/marshal.json` in the probe above), returning `None` only when the `ls-files` observation itself fails, so the fail-closed contract is unchanged and a repo with no commits (`ls-tree HEAD` fails) still falls back to the index answer. Add two controls beside `test_partition_retains_tracked_plan_file` in `test/plan-marshall/script-shared/test_plan_state_exemption.py`: a `git rm`'d tracked `.plan/` path is **retained**, and an untracked `.plan/` path in the same repo is still **exempted**.
- **Done when:** in a throwaway repo where a committed `.plan/marshal.json` has been `git rm`'d, `post_run_source_guard._observe_dirty_source` returns `clean=False` with `.plan/marshal.json` in `offending_paths` and absent from `exempted_paths`, `partition_plan_state_exemption` retains it, and the two new tests fail against today's `tracked_plan_paths`.
- **Module/topic:** `plan-marshall:script-shared` — `_plan_state_exemption` trackedness oracle (both confirmed guard sites).

## Refuted during adversarial review

removed or corrected above; they are recorded here rather than dropped.

- **G2's trailing clause about non-`.plan/` paths — REFUTED, removed.** The original G2 argued that "the
  same encoding mismatch applies to any tracked source path with a space or non-ASCII byte, since … the
  baseline/observed set comparison is done on a different spelling than `ls-files` uses". It is not a
  defect: `git_dirty_files` is consumed at exactly one site (`_invariants.py:676`; re-swept with
  `grep -rn git_dirty_files --include=*.py marketplace/ test/`), and `_main_dirty_drift_diff`
  (`_invariants.py:682-700`) compares a persisted baseline against a fresh observation — **both** produced
  by `git_dirty_files`, so both sides carry the same escaped spelling and the comparison is consistent.
  `ls-files` spelling enters the pipeline only inside `partition_plan_state_exemption`, which is the
  `.plan/`-only defect G2's main body already states. A non-`.plan/` escaped path is retained either way.
- **"`exempted_paths` is structurally empty at site 1" — REFUTED.** Asserted in report-01.md and accepted
  by the original verification's "No contradiction found in" list. A staged deletion of a tracked `.plan/`
  file puts a path into `exempted_paths` at site 1 (`(True, [], ['.plan/marshal.json'], …)`), and a `git mv`
  puts the rename pre-image there. The claim is now filed as part of **G5**.
