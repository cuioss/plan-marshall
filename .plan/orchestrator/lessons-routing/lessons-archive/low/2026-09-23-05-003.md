# Merge-lock release reports 'already free' for a lock the releasing plan had acquired

## What happened

During finalize of plan-17 (`jwks-egress-allowlist`, API Sheriff PR #345, merged via merge queue as
c1b09c7), the plan acquired the merge mutex and, on release, the release call reported the lock was
**already free**. The merge itself was unaffected.

## Why it matters

The release path did not observe its own claim. Two readings are possible and the report does not
distinguish them: the lock was released by something else (a stale-holder reaper, a concurrent session,
a liveness sweep), or the release resolved a different lock identity than the acquire did. Either way the
mutex's mutual exclusion is not established for the window between the two calls — which is exactly the
property a merge mutex exists to provide, and the failure is silent because "already free" reads as
success.

## Suggested corrective rule

A release whose holder token does not match the caller's acquire token is a DISCREPANCY, not an idempotent
no-op: report it distinctly (e.g. `released` vs `already_free_not_held_by_caller`) and name the observed
holder, so a lost lock is visible rather than indistinguishable from a clean double-release.
