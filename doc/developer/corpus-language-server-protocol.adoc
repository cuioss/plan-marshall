This page records *why the corpus reference intelligence is exposed as a language server*, so the choice is not re-litigated from scratch later. It is a decision record, not a how-to: the operator-facing page is xref:../user/corpus-language-server.adoc[User Guide › The Corpus Language Server], and the contract is the xref:../../marketplace/bundles/pm-plugin-development/skills/tools-corpus-language-server/SKILL.md[skill].

The full option analysis, with the measurements and the re-verified external research behind it, is the proposal at `doc/plans/code-intelligence-substrate/240-skill-lsp-server/proposal-protocol-surface.md`. This page records the decision that proposal was written to inform.

== The question

The skill corpus already carried real cross-file reference intelligence — five edge types over roughly 300 components, with line-level provenance — and nothing reached it. The question was not how to build that intelligence but *what surface should present it*, and specifically whether an editor protocol was appropriate at all when this repository's consumers are predominantly agents rather than humans in an editor.

== What decided it

=== Residency, which is a measurement and not a preference

[cols="2,1", options="header"]
|===
| Path | Cost

| One-shot CLI query, end to end
| ≈ 2.0 s

| Index construction alone
| ≈ 1.87 s

| Forward / reverse edges, warm index
| < 0.1 ms

| Transitive closure, depth 10, warm index
| ≈ 1.5 ms

| Whole-graph cycle detection, warm index
| ≈ 4.0 ms

| Provenance-verified `references`, warm index, per-component file lists cached
| < 5 ms (≈ 20 ms on the first call for the most-referenced component measured, at 443 inbound edges)
|===

Effectively the entire cost is index construction, and it is paid per process. This eliminates the one-shot shape outright rather than merely disfavouring it: a surface that forks per request is a two-second surface whichever protocol it speaks. Any acceptable answer had to be resident, and a language server is resident by construction.

=== An editor protocol is now also an agent protocol

The original framing assumed the two audiences were opposed — that an editor protocol serves humans while agents want tool calls. That is no longer true on this platform. Claude Code's plugin schema accepts an `lspServers` declaration (inline in `plugin.json`, or in a sibling `.lsp.json`), starts declared servers automatically when the plugin is enabled, and routes definition and reference lookups through them; `diagnostics` are pushed into the agent's context by default.

So a single language server serves both audiences, and the premise that would have ruled the protocol out no longer holds.

=== Nothing off the shelf covers the notation

The claim that no language server existed for this surface was re-verified rather than repeated, and it needed correction. Generic Markdown language servers now exist — `markmark` and the `mdbase` server both offer go-to-definition, find-references and link validation over Markdown link targets. What none of them understands is the corpus's own vocabulary: `bundle:skill:script` notation, `skills:` and `implements:` frontmatter, and the Python-import edges. That is four of the five edge types, so an off-the-shelf server is a complement rather than a substitute.

The converse claim held. The mature "language server for agents" projects run the *opposite* direction — bridging per-language code servers to agents, each requiring the language server binary installed separately, none offering documentation-corpus intelligence. Those are integrated, not rebuilt.

== What was rejected, and why

[cols="1,3", options="header"]
|===
| Option | Why not

| A tool-calling or MCP surface
| Solves nothing the language server does not, *unless* it is also resident — at which point the residency requirement, not the protocol name, is doing the work. It would also serve no editor, and risks repeating a pattern this epic has already paid for: a vocabulary shipped over verbs nothing calls.

| Extending the machine-local `language_servers` binding
| A direction error. That store binds a language to a *locally-installed third-party binary*, which is why it is machine-local and git-ignored. This server ships with the repository, so its command is a constant every developer would have to enter identically. Its key is also a *language*, which a corpus is not, and its `enabled` switch is already overloaded — enabling a language there also switches on a whole-workspace harvest at every crawl. Its hosting model is explicitly short-lived-subprocess-per-call, which is the two-second shape again.

| Doing nothing until a consumer exists
| A serious option, given that the dependency verbs had zero adoption and that this epic has already built and removed one zero-adoption surface. It was initially set aside because on Claude Code a plugin-declared language server is consumed automatically by the agent, so declaring it would create the first consumer rather than waiting for one. ⚠ **That reasoning did not survive implementation**, and the outcome sits closer to this option than the decision anticipated — see "The declaration is documented, not shipped" below.
|===

What *was* taken from the `language_servers` design is its degradation contract — `not_configured` / `ready` / `ok` with a `provider_count` discriminator, so a caller can always distinguish "nothing ran" from "ran and found nothing". That vocabulary is reused verbatim; the store is not.

== Where opt-in is enforced, and why it cannot be the manifest

A plugin-declared language server *starts automatically when its plugin is enabled*. Declaring the server would therefore itself constitute opting in, and "strictly opt-in" would be unachievable at the manifest layer.

The switch is consequently read by the server itself, from the project's version-controlled `.plan/marshal.json` under `code_intelligence.corpus_language_server.enabled`. When it is not enabled the server starts — the client expects it to — and then advertises *no capabilities*, answers every request emptily, and never builds the index. Every unreadable or ambiguous configuration fails closed to disabled, so a malformed config can never accidentally switch a surface on.

Version-controlled rather than machine-local is deliberate, and is the same argument that ruled out reusing the `language_servers` store: a repository-shipped server has one correct command for every developer.

== Two constraints the decision carries forward

*Extension collision.* `extensionToLanguage` binds by file extension, and the documented behaviour when several enabled servers claim one extension is that the first registered wins and the others never start. A `.md` registration could therefore shadow a user's own Markdown server. This is the concrete reason opt-in must be default-off rather than a flag consulted after the extension is already claimed — and, as the next section records, it is what decided that the declaration is not shipped at all.

== The declaration is documented, not shipped

⛔ The bundle manifest carries **no** `lspServers` declaration. The `SKILL.md` and the user page document the block; an operator adds it deliberately.

This reverses the reasoning that set Option D aside, and the reversal is the most important thing on this page. A client binds an extension when the **plugin** is enabled, which is strictly earlier than any configuration this surface reads — so the `marshal.json` switch governs whether the server *answers*, never whether it *binds*. A shipped declaration would therefore mean that enabling `pm-plugin-development` for any of its other skills could take `.md` from an operator's own Markdown server and, while this surface was unconfigured, answer nothing in its place. That is a change to an unconfigured project's behaviour, which the opt-in requirement forbids outright.

⚠ Both halves of that could not be had. The consequence is stated rather than softened: **the surface has no automatic consumer.** The `query` verb is reachable without a client, and the editor surface is one documented copy-paste away — a smaller adoption gap than shipping nothing, and a larger one than the decision assumed.

⭐ Two findings from implementation are worth carrying forward, because neither was visible from the analysis. First, the two defects masked each other: the multi-target generator was silently dropping `lspServers` from the built artifact, so the collision could not occur and the declaration did nothing — fixing the generator is what made the trade-off real and forced this decision. Second, a static manifest cannot express a conditional binding, so "declare it and let the server decide" is not available on this platform at all.

*Diagnostics stay withheld.* No diagnostic capability is advertised. The validator's unresolved set is presently about 97% false positives — documentation placeholders, foreign namespaces such as build-command and Maven coordinates, and notations whose third segment is a subcommand rather than a script. Advertising a diagnostic provider before that precision work lands would ship confidently wrong warnings at the substrate's most visible surface.
