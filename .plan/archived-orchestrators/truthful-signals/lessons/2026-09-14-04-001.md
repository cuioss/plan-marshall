# Three documented-set mirrors have no machine-readable registry to derive from

Three separate CodeRabbit findings on PR #1489 (plan
`architecture-store-query-truthfulness`) name the same structural gap: a
hand-maintained list that mirrors a set defined elsewhere, where **no
machine-readable registry exists to derive the list from**. Each was suppressed
on that PR because building the registry is a scope expansion well beyond a
bug-fix plan, not because the finding is wrong. A future plan should pick the
registry work up.

The distinguishing property — and the reason these three were suppressed while
two sibling findings from the same review were fixed in place — is that the
authoritative source is **not reachable in-process at the mirror site**. Where
it is reachable (a `vars(_mod)` walk, a table the test already parses row by
row) the fix is a few lines and was taken. Where it is not, the fix requires
inventing the registry first, and that is a design decision with its own
consumers.

## The three sites

### 1. Composer-filter inventory — `manage-execution-manifest`

Finding `d396e7`, Major. `manage-execution-manifest/SKILL.md` around line 416
carries a table that manually mirrors the complete filter set of the compose
pipeline (`scope_gated_finalize`, `canonical_verify_inactive`,
`execution_tier_routing`, `step_execution_tier`, `ceremony_finalize_selection`,
`lane_resolution`, `frontmatter_order_sort`, and the post-compose gates). A new
or renamed filter changes selection behaviour while the table goes on claiming
completeness. The remedy CodeRabbit named: move the filter metadata into one
machine-readable registry, and drive both composition and documentation
generation from it.

### 2. Worktree-linter literal detectors — `q-gate-validation`

Finding `0efb44`, Major.
`test/plan-marshall/q-gate-validation-agent/test_q_gate_validation_worktree_linter.py`
around line 519 defines `_WL_LITERAL_DETECTORS`, which manually mirrors the
literal-based patterns written in prose in Section 2.15 of
`plan-marshall/workflow/q-gate-validation.md`. Adding or renaming a
literal-based pattern in that section leaves the guard green while it never
scans the new pattern. The remedy: store the pattern definitions in one
machine-readable registry, render Section 2.15 from it, and build the detector
population from it.

### 3. Client command catalog — `manage-architecture`

Finding `1b9139`, Minor — the registry-requiring half only. The summary table in
`manage-architecture/standards/client-api.md` (around lines 1547-1565) is an
independently-maintained catalog of the client commands, and it had already
drifted: it omitted `derive-verification`, `profiles` and `siblings`. The remedy:
derive or validate that table from the command registry.

The *separately verified* half of `1b9139` — the disagreement between
`_cmd_client_handlers.py`'s hardcoded "all 20 CLI handlers" docstring roster and
`client-api.md`'s 17 verb sections / 17-row table, two mirrors that never compare
against each other — was NOT suppressed. It was allocated as a fix task on the
same plan, because making two existing mirrors cross-validate needs no new
registry.

## The shape of the work

All three want the same thing: **one registry, two renderings** — the
executable one and the documented one — so the document is generated from the
set rather than asserting it. That is one coherent piece of work with three
instances, which is why it is recorded as a single lesson rather than three.

Two constraints any such plan inherits from this repository's existing rules:

- A derived population that can come back empty is a vacuous guard. Every
  registry-derived detector or test MUST publish its population size and assert
  non-emptiness — this repository has re-introduced the vacuous-guard archetype
  repeatedly, including inside fixes for it.
- The terminating move for a stale restatement is to replace it with a pointer
  at its source. Correcting the restatement authors a new claim that drifts
  again; deleting it under-declares.
