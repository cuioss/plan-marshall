# TestFindSkillsRoot patches a module object the function under test may no longer read

## What was observed

Running the whole test tree with the top-level `test/` subtrees passed to pytest
in reverse order — same parallel regime as the canonical `module-tests` run
(`-n auto --dist=loadgroup`, in-repo `--basetemp`) — one test in
`test/plan-marshall/platform-runtime/test_platform_runtime_bootstrap.py`
`TestFindSkillsRoot` fails. Which one varies by run:

- `test_finds_root_from_script_inside_skills_tree`
- `test_finds_correct_root_with_deep_nesting`

The assertion shows the real repository's
`marketplace/bundles/plan-marshall/skills` where the fixture's synthetic
`{tmp_path}/bundle-a/skills` was expected. In the default (alphabetical) order
the same run is green, which is why the canonical gate never sees it.

## Why it happens

The tests do:

```python
from platform_runtime import _find_skills_root
...
with patch("platform_runtime.__file__", str(fake_file)):
    result = _find_skills_root()
```

`patch("platform_runtime.__file__", ...)` resolves the target through
`sys.modules['platform_runtime']`, while `_find_skills_root` reads `__file__`
out of `_find_skills_root.__globals__` — the namespace of the module object it
was defined in. Those are the same dict only while nothing has re-registered
`platform_runtime` in `sys.modules`. This tree loads skill scripts by path into
freshly-built module objects, so a sibling test that loads `platform_runtime.py`
that way replaces the entry; the patch then lands on the new module while the
already-imported function keeps reading the old one's real `__file__`, and the
ancestor walk finds the repository's own `skills/` directory.

That makes the outcome depend on whether such a sibling ran earlier on the same
xdist worker — i.e. on collection order, not on anything the test declares.

## What to do instead

Patch the namespace the function actually reads, so the patch cannot be
detached from the callee by `sys.modules` churn:

```python
with patch.dict(_find_skills_root.__globals__, {"__file__": str(fake_file)}):
    result = _find_skills_root()
```

The same reasoning applies to any test that patches a module attribute by
dotted string and then calls a function imported by value from that module.

## Scope of this finding

Pre-existing: it reproduces on an untouched `HEAD` worktree, so it is not a
regression from the suppression sweep that surfaced it. The file is outside
that deliverable's declared mutation scope, which is why the fix was recorded
here rather than folded into an unrelated commit.
