# Corroborating outputs of one extractor must share ONE input population: retaining the wider input behind a harmless no-op docstring claim keeps the false-fact channel the narrowing fix existed to close

## Context

The `repair-plan-retrospective-false-verdicts` plan existed to remove *false verdicts*
from `plan-retrospective` — confident findings the underlying data could not support.
One deliverable narrowed `analyze-logs.py`'s dispatch-inference extractor: instead of
admitting every line merely *containing* the substring `plan-marshall:phase-5-execute`
(which inflated `inferred_dispatches` roughly 6x-18x), only lines matching the two
literal execute-phase markers (`_STARTING_RE` / `_RE_ENTERING_RE`) may contribute a
timestamp.

The narrowing was applied to the *predicate* but not to the *population*. The function
returns three corroborating outputs — `inferred_dispatches`, `starting_markers`,
`re_entering_markers`. The two marker counts were computed over `work_log_lines` only,
but the timestamp-clustering loop that produces `inferred_dispatches` still iterated
`work_log_lines + script_log_lines`. The shipped docstring defended that asymmetry
explicitly:

> `script_log_lines` stays in the signature and in the scanned population: the marker
> lines occur only in `work.log`, so scanning the script-log lines for them is a
> harmless no-op and no caller or test signature changes.

CodeRabbit caught it on the PR. A single marker-shaped line landing in
`script-execution.log` would change `inferred_dispatches` while remaining invisible to
both marker counts — producing a dispatch fact that no marker count can corroborate.
That is precisely the uncorroborated-confident-fact class the plan was chartered to
eliminate, surviving inside the plan's own fix. Neither phase-3-outline nor the Q-Gate
caught it.

The fix iterates `work_log_lines` alone and states the invariant positively: scanning
one population for all three outputs makes the divergence **structurally impossible
rather than merely unlikely**.

## Root cause

Two distinct failures compound here, and both are design-time, not coding-time:

1. **The narrowing was applied at one derivation site, not all of them.** A fix framed
   as "stop admitting the wrong lines" naturally targets the *predicate* the finding
   named. But the same signal was derived at three sites in the same function, and only
   the sites the finding pointed at were narrowed. The remaining site kept the wide
   input.

2. **The retained wide input was defended by a claim about *data*, not an invariant of
   the *code*.** "The marker lines occur only in `work.log`" is an empirical statement
   about what producers currently emit — nothing in the extractor enforces it, and no
   test seeds the excluded population with a trigger-shaped line to prove it. Dressing
   that assumption up as a "harmless no-op" in a docstring converts an unenforced
   assumption into a false sense of coverage: the prose reads like a justification, so
   neither outline review nor Q-Gate re-derived it.

## Corrective action

**Y (avoid):** narrowing the predicate/filter at the site a finding names while leaving
the wider input in the scanned population at a sibling derivation site, justified in
prose as "a harmless no-op" because the wider input "cannot contain" the trigger.

**X (do):**

- **Derive corroborating outputs from ONE population.** When a function returns several
  values that are meant to cross-check each other (a count and an inference over the
  same event class; a total and its breakdown; a detected set and its cardinality),
  every one of them must be computed from the *same* input collection. A value derived
  from a wider population than the values that corroborate it is, by construction, an
  uncorroborable fact channel — which is the shape of a false verdict.
- **At outline time, enumerate every derivation site before prescribing the narrowing.**
  When a deliverable narrows what feeds a signal, grep the function/module for every
  other place the same input collection is iterated or summed, and scope the narrowing
  to all of them in the same deliverable. A narrowing scoped to one site is the same
  under-enumeration defect as an outline enumerating affected files from memory.
- **Treat a "harmless no-op" / "cannot happen" justification as a review tripwire, not
  as evidence.** If the wider input genuinely cannot carry the trigger, that is an
  assumption about upstream producers, not a property of this code. Either (a) drop the
  wider input from the scan so the property becomes structural, or (b) if it must stay,
  add a discriminating fixture that seeds the excluded population with a trigger-shaped
  line and asserts the output does not move. Prose is not a test.
- **State the invariant positively in the docstring.** "Scanning one population for all
  three outputs makes the divergence structurally impossible rather than merely
  unlikely" is a checkable claim a reviewer can verify against the loop. "This is a
  harmless no-op" is not.

## Impact

The defect class is generic to any extractor, classifier, or metrics collector that
returns a primary inference alongside corroborating counts — and it is invisible to
type-checking, lint, and to tests whose fixtures only ever populate the "real"
population. Its cost here was a PR-bot round-trip and an in-run remediation commit on a
plan whose entire purpose was removing exactly this failure mode, which is the sharpest
possible demonstration that a plan does not get immunity from its own defect archetype.
