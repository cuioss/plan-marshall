# Review-bot fix recipes can specify vacuous tests (pass both pre- and post-regression): the executing task must prove the test discriminates by mutation before accepting it done

Re-homed from the API-Sheriff consumer store 2026-07-16 ([[feedback_manage_lessons_cwd_store_resolution]]).

## Problem

A review bot's suggested fix is a *hypothesis*, not a specification. When the suggestion is "add a test that covers X", the concrete recipe it supplies can be subtly wrong in a way that produces a **vacuous test** — one that passes both before and after the regression it is nominally guarding, and therefore pins nothing.

`verification-feedback` triage validates that the finding's *premise* is real (cited code exists, claim holds). It does not, and cannot cheaply, validate that the finding's *proposed test design actually discriminates*. That check belongs to the executing task, before the test is written — otherwise the plan ships a green test that provides false assurance, worse than no test (a reader trusts it).

## Observed

Plan `fix-plan-02-landing-gaps`, PR #64, coderabbitai finding `5e9c0b`. The bot correctly identified a real coverage gap (`ConfigProducer` wires `tls.passthrough_sni` into `TopologyResolver.resolve(..., additionalAliases)` via `.map(Map::values)`, untested — a `values()`→`keySet()` swap would silently pass hosts as aliases). Its recipe: "boot with a `tls.passthrough_sni` block referencing an unresolvable alias and assert the boot aborts." That recipe is vacuous: `TopologyResolver.resolve` silently skips unresolved `additionalAliases`, so with an *unresolvable* alias `values()` and `keySet()` BOTH leave it absent and BOTH produce the same abort — the test passes green under the exact regression it targets.

The discriminating design is the inverse: a **resolvable** alias whose host key is *not* a valid alias. Correct `values()` wiring resolves it and boots clean; `keySet()` hands over the host, leaves the alias unresolved, and aborts. The executing agent found this by reading production code (not transcribing the recipe) and **proved** it by mutation — `values()`→`keySet()` turned the discriminating test red while the bot's literal test stayed green.

## Directive

When a review-bot finding's disposition is FIX and the fix is "add a test", the executing task MUST establish that the test discriminates before accepting it as done:

1. Read the production path the test pins and reason about whether the proposed inputs separate correct from incorrect behaviour. A recipe naming an input class where both correct and regressed code take the same branch is vacuous.
2. Prove non-vacuity empirically where cheap: temporarily introduce the exact regression, confirm the test goes red, revert, confirm green. Never commit the mutation.
3. When the bot's literal recipe is vacuous but the gap is real, implement the discriminating design and say so in the PR reply.
4. Record in the test's Javadoc *why* the discriminating input was chosen, so a later reader doesn't "simplify" it back to the vacuous variant.

Generalizes beyond review bots to any hand-specified test recipe, including one written into a task description by an earlier planning phase. Same run also caught a vacuous-by-construction test at another deliverable (a "disabled endpoint … does not fail boot" assertion that would also pass if the fixture never loaded) — non-vacuity proof deserves to be a standing expectation for any test whose assertion is "nothing bad happens".

## Recurrence — 2026-07-27 (finalize-dispatch-audit-integrity)

A second vacuity shape, with a **cheap static signature** the mutation proof above catches only after the fact: **a test that derives a population and then never consumes it in the assertion**.

`test/plan-marshall/phase-6-finalize/test_step_termination_contract.py::test_invariant_is_reachable_from_every_dispatched_roster_entry` parsed the DISPATCHED roster out of `dispatch-inline-split.md` at test time — deliberately derived, "never hardcoded", and documented as such in the module docstring. But the loop variable fed only `len(roster)` (inside an assertion *message*) and a non-empty guard. Both assertions were **global and identical regardless of what the roster contained**: they asserted the record-before-return invariant existed *centrally* in `agents.md`. Deriving the population was pure decoration.

The consequence was a real hole the green test covered for: the roster is partitioned, and only the **external** (`project:` / `bundle:skill`) partition had a reach-point to the invariant, via `external-step-contract.md`. The nine `default:`-prefixed **built-in** dispatched steps had no shared authoring contract and no reach-point at all — a built-in step body could ship a trailing `mark-step-done` that a leaf skips while still returning success. Adding or removing roster rows, or flipping every row to a partition with no reach-point, would not have moved the test. The fix asserts **per partition**, with an explicit `unpartitioned` check so a new row shape fails rather than silently escaping both branches.

### Added directive

5. **A derived population must be consumed by the assertion, not only by a length check or an error message.** When a test parses a roster / registry / config to build a population, at least one assertion must vary with the *contents* of that population. `assert population` (non-empty) and `len(population)` interpolated into a failure string are NOT consumption — they make the derivation read as population-driven while the verdict stays constant. Concretely: iterate the population, or partition it and assert each partition, and add a residual `unpartitioned`/`unmatched` assertion so an element shape nobody anticipated fails loudly. This is statically checkable at review time (does the loop variable reach an `assert`?), which makes it a cheaper first filter than the mutation proof in directive 2 — the two are complementary, not alternatives.

This is the same archetype the epic keeps surfacing under other names (`scope_creep_check`, saturated markers, `search-markers`, roster-count): a guard whose predicate cannot fire for the case it exists to catch. Here the guard was a *test* and the never-firing input was its own derived population.
