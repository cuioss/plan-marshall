# pre-commit-verify-freshness can return two different verdicts for one unchanged tree

## Problem

`manage-tasks pre-commit-verify-freshness` returned two different verdicts for one
unchanged worktree, minutes apart, during the phase-6-finalize push barrier of plan
`output-volume-standard` (PR #1387).

First call:

```text
status: stale
reason: build_scope_narrow
worktree_sha: 85368a1d24a69519f2bc7c1a945ba918c93d3bef...
notation_cross_check: corroborated
scope_cross_check: narrow
```

It scanned the change-ledger, found `kind=build` rows matching the current
`worktree_sha`, and refused because each matching row's canonical
(`quality-gate plan-marshall`, `quality-gate`, `test-compile`,
`module-tests plan-marshall`) recorded `canonical_performs_too_few_analyses` — none
covered the change on its own.

Second call, after running the covering canonical `verify` (green, 23951 tests, no
source edit in between):

```text
status: fresh
reason: plan footprint touches no build_map glob — only non-buildable files changed
message: build-decision ruled a build not_necessary for this footprint, so no
         kind=build entry can exist and none is required. Gate permitted without
         a ledger scan.
```

## Why this matters

The two calls took **different routes over the same footprint**. The second
short-circuits on a `build-decision` verdict *before* the ledger scan the first
performed. Both verdicts cannot be correct for one unchanged tree:

- If the build-decision short-circuit was right, no build was ever required and the
  first call's scope-narrow refusal was spurious — the gate blocked a push it had no
  grounds to block.
- If the ledger scan was right, a build *was* required, and the second call cleared
  the gate without checking whether one had happened.

The second shape is the dangerous one: a gate that permits *without scanning* reports
`fresh` in exactly the same field a genuine ledger-corroborated pass does. A caller
branching on `status` alone cannot tell "a build verified this tree" from "no build
was needed, so nothing was checked". That is the confident-signal-hides-a-caveat class
the gate itself exists to prevent.

## Directive

Reconcile the two routes in `pre-commit-verify-freshness` so one footprint yields one
verdict:

- Establish which route is authoritative when a `build-decision` says `not_necessary`
  but the ledger holds matching `kind=build` rows. The two answers disagreed here.
- If the short-circuit stays, make its `fresh` distinguishable from a
  ledger-corroborated `fresh` — a caller must be able to tell an affirmative
  verification from a vacuous permit, per ADR-009.
- Add a regression test pinning both routes against one fixture footprint, asserting
  they agree.

## Evidence

Recorded as finding `a03f17` on plan `output-volume-standard`, dispositioned
`taken_into_account` by operator decision (hold for a follow-up plan that owns
`manage-tasks`; fixing it in-plan would have converted a documentation-only PR into a
script change).

The plan was not compromised: its push rested on an independent whole-tree `verify`
green at that exact tree, not on the `fresh` verdict.
