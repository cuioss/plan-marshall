# build-maven run defaults to an adaptively-lowered subprocess timeout that silently kills long builds — the script-level --timeout binds, not the Bash timeout

Re-homed from the nifi consumer store 2026-07-16 ([[feedback_manage_lessons_cwd_store_resolution]]).

## Symptom

`verify -Pcoverage` returned `status: timeout, exit_code: -1, duration_seconds: 120, timeout_used_seconds: 120` — even though `architecture resolve --command coverage` reported `bash_timeout_seconds: 150`, `execution_tier: per_task`, and the Bash tool call itself passed `timeout: 300000`. The build was killed mid-run at 120s. Re-running the identical command with an explicit script-level `--timeout 480` completed in **57 seconds**, exit 0.

## Root cause

Two independent timeouts govern a build, and the one that kills it is NOT the one the Bash tool call sets:

1. **Bash tool `timeout`** — bounds how long the harness waits for the tool call.
2. **`maven.py run --timeout N`** — the *subprocess* timeout the script enforces internally. `--help` documents `default: 300`, but the observed `timeout_used_seconds: 120` shows the effective default is adaptively lowered below both the documented default and `bash_timeout_seconds`.

Raising only the Bash timeout does nothing: the script kills its own subprocess first and reports `status: timeout`. `architecture resolve`'s `bash_timeout_seconds` sizes the *Bash* call (per `persona-plan-marshall-agent` § "Bash: Timeout from architecture-resolved canonical command") — necessary but NOT sufficient, and that rule does not mention the script-level flag.

## Guidance

For any build expected to run beyond ~2 minutes, pass **both** timeouts, script-level set generously above expected duration:

```bash
python3 .plan/execute-script.py plan-marshall:build-maven:maven run \
  --command-args "verify -Pcoverage" --timeout 480 --plan-id {plan_id}
```

and set the Bash tool `timeout` above that. The script-level `--timeout` is the binding constraint; the Bash timeout must merely exceed it.

## Diagnostic tell

`status: timeout` with `timeout_used_seconds` LOWER than what you passed to the Bash call (and lower than resolved `bash_timeout_seconds`) means the script-level timeout fired, not the harness. Treat it as a tooling artifact — re-run with explicit `--timeout` before triaging as a real error.

## Primary cause is cross-project build contention → the build-server is the structural fix

The dominant trigger is **CPU contention from parallel builds across multiple projects**, not the build itself being slow. Diagnostic proof: the re-run completed in **57s**, well UNDER the 120s bound — a 57s build cannot hit a 120s timeout unless its wall-clock was stretched past 120s on the killed run. Three projects × `max_slots=5` = up to 15 uncoordinated concurrent heavy builds on one machine inflate a ~57s build past its learned 120s timeout. The `plan-marshall` **build-server (`marshalld`, plan-server epic goal 2: cross-project coordination)** is the structural fix: one machine-level owner serializes/limits build-class work across ALL projects, so a build runs at its true duration and the timeout never fires. **Re-evaluate this lesson when marshalld ships** — the timeout should stop firing for the contention case.

**One residual timeout-logic bug marshalld does NOT close** (keep tracked): the adaptive timeout learns from warm runs with only `SAFETY_MARGIN` 1.25× headroom, floored at `MINIMUM_TIMEOUT_SECONDS` 120 — so *within-project* variance (cold cache, GC pause, slow disk) can still kill a build learned from its fast runs, even with zero cross-project contention. marshalld removes the biggest variance source, not this residual headroom fragility. (The sibling concern — `--timeout` being discarded rather than honoured as a true override once a value is persisted — has since shipped as a genuine override with an unconditional floor; that half of the prior tension is closed.)
