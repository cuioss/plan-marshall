# keyword_drift Q-Gate check searches only task title/metadata, flagging terms legitimately grounded in the outline's analysis prose — expected false-positive, resolve taken_into_account

The phase-4-plan Q-Gate `keyword_drift` check compares the terminology used in
generated task titles/descriptions against a haystack built from the task's own
title and metadata plus the deliverable summary. That haystack is **narrower
than the outline itself**: a term that phase-3-outline legitimately introduced
and grounded in its analysis prose (e.g., a siting/trade-off section) does not
appear in the check's haystack, so a task that correctly carries the term
forward is flagged as drift. The result is a predictable false-positive on any
plan whose outline contains substantive analysis sections whose vocabulary
flows into task text.

This is the same genre of expected-Q-Gate-false-positive as lesson
`2026-06-28-17-001` (4-plan §2.2 assessment-coverage check fires when
phase-3-outline produced zero CERTAIN_INCLUDE assessments by design) and
`2026-06-21-11-001` (2-refine `narrative_vs_code_validator` fires on
lesson-conversion plans), but a different validator and a different root cause:
here the check's **haystack is too narrow**, not an absent baseline or a
stale-by-construction narrative.

## Root cause

The `keyword_drift` mechanical check treats "term absent from task
title/metadata + deliverable summary" as evidence the planner invented the
term. It never consults the full solution-outline body, so terminology that is
outline-grounded but lives in analysis prose (siting decisions, trade-off
discussion, constraint sections) is invisible to the check. The gap is in the
check's haystack construction, not in the plan.

## Recommended action

When a `keyword_drift` warning fires on a term that a read of the solution
outline shows is legitimately grounded there:

- Verify the grounding with a direct read of the outline (search the outline
  body for the flagged term and confirm the task's usage matches the outline's
  meaning), then resolve the finding `taken_into_account` with a reason naming
  the narrow-haystack false-positive cause. Do NOT rewrite the task to purge a
  correctly-grounded term — that would make the task text drift AWAY from the
  outline to appease the check.
- The durable fix is at the tool layer (we own the check): widen the
  `keyword_drift` haystack to include the solution-outline body (or at minimum
  the sections of the deliverable the task implements), so outline-grounded
  vocabulary never counts as drift. Until that lands, the disposition above is
  the standing answer.

## Evidence

Plan `whole-tree-gate-git-native` (premise-falsification outcome: the requested
git-native whole-tree gate already existed; the plan shipped ADR-006 recording
the consume-boundary decision instead of new code). The 4-plan Q-Gate raised a

term was legitimately grounded in the outline's CI-siting analysis; the check's
title/metadata haystack simply could not see that section. Resolved
`taken_into_account` as the expected false-positive.
