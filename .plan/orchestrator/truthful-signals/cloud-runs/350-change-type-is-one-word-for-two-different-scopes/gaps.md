## G1 — Guard the reconciliation against a settled classification outside `VALID_CHANGE_TYPES`

- **Kind:** bug
- **Severity:** high
- **Where:** `marketplace/bundles/plan-marshall/skills/manage-execution-manifest/scripts/manage-execution-manifest.py:1848-1867` — `cmd_compose`; read helper `marketplace/bundles/plan-marshall/skills/manage-execution-manifest/scripts/_manifest_decide.py:340` — `_read_settled_change_type`
- **What is wrong:** the *supplied* value is validated against `VALID_CHANGE_TYPES` (line 1812), but the *settled* value returned by `_read_settled_change_type` never is, and `VALID_CHANGE_TYPES` (`_manifest_core.py:65-72`) holds only the six canonical values. `status.metadata.change_type` is written through `manage-status metadata --set`, whose `_coerce_metadata_value` (`manage-status/scripts/_status_query.py:51-65`) coerces booleans only and stores every other string verbatim — there is no enum check on the write side, and the report's own D0 lists that manual `--set` as a producer. The repository asserts that a plan can carry `feature_breaking` at that key (`manage-status/scripts/_cmd_planning_lane.py:104` `_DEEP_CHANGE_TYPES`; `plan-retrospective/references/plan-efficiency.md:144` states it explicitly), and `feature_breaking` is not a member of `VALID_CHANGE_TYPES`. Re-executed independently during adversarial review against the real `cmd_compose` with `status.metadata.change_type = 'feature_breaking'`, iterating **all six** members of `VALID_CHANGE_TYPES` plus `feature_breaking` itself: `analysis`, `feature`, `enhancement`, `bug_fix`, `tech_debt`, `verification` → `change_type_scope_conflict` (6/6); `feature_breaking` → `invalid_change_type`. There is no accepting input — established over the whole input domain, not on a two-value sample.
- **Why it matters:** phase-4-plan Step 7b states compose "MUST run on every successful plan-phase invocation; the manifest is required by phase-5-execute on entry". A plan whose settled classification is `feature_breaking` — or carries any typo, legacy, or externally-set value — is therefore permanently unable to compose and cannot leave phase 4. The refusal message compounds it by instructing "Re-run compose with `--plan-change-type feature_breaking`", which the enum check at line 1812 then rejects; only the parenthetical "or correct `status.metadata.change_type`" offers a real way out. Before this plan, such a plan composed fine — the block is new.
- **Reachability (added during adversarial review — the half the original entry left unstated):** the repository's own **user-facing** documentation invites the value that hard-blocks compose. `manage-status/SKILL.md:957` documents the S3 planning-lane signal as `status.metadata.change_type` ∈ {`feature`, `feature_breaking`}, and the same statement is repeated in the `_cmd_planning_lane.py:16` module docstring — i.e. a reader is told `feature_breaking` is a live value at exactly that key. The write path (`manage-status metadata --set --field change_type`, a canonical invocation documented at `manage-status/scripts/manage-status.py:17`) accepts it verbatim. Counter-evidence, also established: **no automated in-tree producer can emit a non-canonical value** — the heuristic's `_KEYWORDS` (`_cmd_change_type_heuristic.py:37-60`) has exactly the six canonical keys, the LLM fallback's declared vocabulary (`phase-3-outline/workflow/detect-change-type.md:139`) is the same six, and every `default_change_type` in every in-tree `provides_recipes()` (swept: `plan-marshall-plugin/extension.py:143,151,159,167,175`, `pm-dev-java-cui`, `pm-documents`) is canonical, as is every derived value in `recipe-lesson-cleanup/standards/recipe-config.md`. The precondition is therefore reachable only by a manual or external write — but that write is a documented verb pointed at a value the documentation itself calls live, which is why `high` is upheld rather than reduced.
- **Fix:** in `cmd_compose`, treat a settled value that is not in `VALID_CHANGE_TYPES` as **not a usable classification** rather than as a conflicting one. Either (a) have `_read_settled_change_type` return `None` for a non-member value and emit a `decision.log` line naming the unusable value, so compose falls through to the existing `change_type_scope: supplied` path; or (b) keep the refusal but change its error to a distinct `settled_change_type_not_canonical` whose message says the settled value is outside the enum and names the only remedy (correcting `status.metadata.change_type`) instead of naming an impossible `--plan-change-type` re-run. Option (a) is preferred — it keeps the fail-toward-composing discipline the malformed-`status.json` path already follows. Independently, consider validating `change_type` on the `manage-status metadata --set` write side against the canonical vocabulary in `ref-workflow-architecture/standards/change-types.md`.
- **Done when:** a test in `test/plan-marshall/manage-execution-manifest/test_compose_change_type_reconciliation.py` seeds `status.metadata.change_type = 'feature_breaking'`, calls compose with each of the six canonical values, and asserts compose does not return `change_type_scope_conflict` for any of them (option a: `status == 'success'` with `change_type_scope == 'supplied'`; option b: a `settled_change_type_not_canonical` error whose message names correcting the status field and does not instruct a `--plan-change-type` re-run with a non-enum value).
- **Module/topic:** `plan-marshall:manage-execution-manifest` — compose change-type reconciliation

## G2 — Make the decision-log test able to tell the two scopes apart

- **Kind:** vacuous-test
- **Severity:** medium
- **Where:** `test/plan-marshall/manage-execution-manifest/test_compose_change_type_reconciliation.py:172-186` — `test_reconciliation_emits_auditable_decision_log_line` (the two vacuous assertions are at :185 and :186)
- **What is wrong:** the test asserts `'settled' in recon[0]` and `'bug_fix' in recon[0]`. The emitted line (`manage-execution-manifest.py:1875-1881`) always contains the literal `settled status.metadata.change_type=…` and, on this fixture, always contains `bug_fix` on both sides — so both assertions hold whichever scope actually drove the decision. Demonstrated by mutation, re-run independently during adversarial review: with **only** `change_type_scope` pinned to the constant `'supplied'` (line 1874, single-line edit, file restored from saved bytes; md5 `02171cf521815cb7565e74c00a22e1a7` before and after) the file went **2 failed / 7 passed** — `test_matching_change_type_composes_and_records_settled_scope` and `test_narrowing_decision_records_its_scope_and_input` red, this one **green**. With the fuller pre-fix shape (refusal disabled and `effective_change_type` pinned as well) the file went **3 failed / 6 passed**, this one still **green**. It is named for D4(d) ("the narrowing decision names its scope") but cannot detect the scope being wrong.
- **Why it matters:** the file is the plan's red-first evidence for D4(d). One of its four D4 guards passes against the very defect the plan exists to prevent, so the suite overstates its own coverage. The deliverable itself is still genuinely covered by `test_narrowing_decision_records_its_scope_and_input`, so no wrong behaviour ships today — but a future change that regressed only the log line would go unnoticed.
- **Fix:** assert on the scope-bearing clause rather than on a bare substring. Replace `assert 'settled' in recon[0]` with an assertion on the full phrase the code emits — `assert "from the settled scope" in recon[0]` — and add a paired case seeding no `status.json` that asserts `"from the supplied scope" in recon[0]`, so the two scopes are distinguished in both directions.
- **Done when:** mutating `change_type_scope` in `cmd_compose` to the constant `'supplied'` makes `test_reconciliation_emits_auditable_decision_log_line` fail.
- **Module/topic:** `plan-marshall:manage-execution-manifest` — compose reconciliation tests

## G3 — Name each scope at the surface that authors it

- **Severity:** low
- **Where:** `marketplace/bundles/plan-marshall/skills/phase-3-outline/SKILL.md:437`; `marketplace/bundles/plan-marshall/skills/manage-solution-outline/standards/solution-outline-standard.md` (deliverable **Metadata:** block) and `marketplace/bundles/plan-marshall/skills/manage-solution-outline/templates/deliverable-template.md`; `marketplace/bundles/plan-marshall/skills/manage-status/SKILL.md:73` and `marketplace/bundles/plan-marshall/skills/manage-status/standards/status-lifecycle.md:102`
- **What is wrong:** ⚠ **Reframed during adversarial review — this is residue BEYOND D2, not a shortfall against it.** D2's condition is "name the two scopes apart **wherever both appear** … *Done when:* the names differ". At every site where both scopes appear, they now differ: the compose flag (`--plan-change-type` vs a deliverable's `change_type`), `decision-rules.md:34-49` § "change_type scope reconciliation", `manage-execution-manifest/SKILL.md:111,167,537` and `phase-4-plan/SKILL.md:684`. All four were re-read at HEAD and each names both scopes explicitly. **D2's done-when is met.** What remains is a different, weaker property the deliverable did not ask for: at the surfaces where only **one** scope appears — the ones that *author* each value — the field is spelled bare, so a reader of that document alone cannot tell which of the two `change_type`s it describes. The outline deliverable metadata (`phase-3-outline/SKILL.md:437`, `deliverable-template.md:11,59`, `solution-outline-standard.md:297,462`) presents the deliverable-scoped field as plain `change_type`; `manage-status/SKILL.md:73` and `status-lifecycle.md:102` present the plan-scoped field the same way. - **Why it matters:** the compose guard now catches a wrong-scope forward at runtime, but the documents an author reads while *producing* each value still use one word for both — which is how a caller comes to believe the two are interchangeable in the first place. It causes no wrong behaviour today and no deliverable is unmet by it, which is why it is `low` and why the D2 row in verification.md now reads **Complete: yes**.

In `phase-3-outline/SKILL.md:437`, `solution-outline-standard.md` and `deliverable-template.md`, annotate the deliverable field as "the DELIVERABLE's local kind — distinct from the plan's settled classification at `status.metadata.change_type`; see `manage-execution-manifest/standards/decision-rules.md` § change_type scope reconciliation". In `manage-status/SKILL.md:73` and `status-lifecycle.md:102`, annotate `change_type` as "the PLAN's single settled classification — distinct from a deliverable's local `change_type` in the solution outline", with the same cross-reference.
- **Done when:** each of the five sites names its scope and links to `decision-rules.md` § "change_type scope reconciliation", and a reader of any one of them can identify which scope the field carries without opening another document.

## G4 — The `change_type_scope_conflict` refusal writes no decision-log line, contradicting the documented audit claim

- **Kind:** bug
- **Severity:** medium
- **Where:** `marketplace/bundles/plan-marshall/skills/manage-execution-manifest/scripts/manage-execution-manifest.py:1850-1867` — the refusal `return` inside `cmd_compose`, which precedes the `_emit_decision_log` call at :1875. Documented claim at `marketplace/bundles/plan-marshall/skills/manage-execution-manifest/standards/decision-rules.md:47`.
- **What is wrong:** `cmd_compose` emits its `change_type reconciliation` decision-log line at line 1875 — **after** the conflict `return` at 1851-1867. So the one event this plan exists to create, the refusal, leaves **no** entry in the plan's `logs/decision.log`. Only the accepting paths (`settled` and `supplied`) are logged. Executed, not inferred: with `status.metadata.change_type = 'bug_fix'` and `--plan-change-type verification`, `_emit_decision_log` was monkeypatched to capture every call — result `{"error": "change_type_scope_conflict", "log_lines": []}`. Zero lines. `decision-rules.md:47` nevertheless states "a `decision.log` line names the scope and value used — so the narrowing decision carries its input and **can be audited afterward**", with no carve-out for the refusal path; `manage-execution-manifest/SKILL.md:167` makes the same auditability claim. No test in `test_compose_change_type_reconciliation.py` asserts anything about the log on the refusal path — `test_reconciliation_emits_auditable_decision_log_line` exercises only a matching pair.
- **Why it matters:** the plan's D3 rationale is explicit that the defect went unseen because "the run's own logs disagreed with themselves and nothing noticed", and that "a decision that does not record its input cannot be audited afterwards". The refusal is the highest-value audit event of the whole feature — it is the moment a caller was caught forwarding the wrong scope — and it is invisible in the durable, plan-local artifact. `plan-retrospective/scripts/check-manifest-consistency.py::load_decision_log_entries` (lines 141-163) harvests exactly the composer-tagged `decision.log` lines for the retrospective report, so a refused compose is also invisible to the retrospective auditor. The compose result TOON does carry `settled_change_type` / `supplied_change_type`, but that is agent-transient stdout, not a persisted record. This is a shipped false signal in a documentation surface: a standard asserting auditability that the code does not provide on the path that most needs it.
- **Fix:** in `cmd_compose`, add an `_emit_decision_log(plan_id, …)` call immediately **before** the `change_type_scope_conflict` `return` at line 1851, carrying the same `(plan-marshall:manage-execution-manifest:compose) change_type reconciliation — ` prefix as the accepting path (so `check-manifest-consistency.py`'s `_DECISION_TAG` filter picks it up) and naming the refusal plus both values, e.g. `… REFUSED — supplied --plan-change-type={supplied!r} contradicts settled status.metadata.change_type={settled!r}; no manifest written`. Keep the existing accepting-path emission at :1875 unchanged.
- **Done when:** a test in `test/plan-marshall/manage-execution-manifest/test_compose_change_type_reconciliation.py` seeds `status.metadata.change_type = 'bug_fix'`, monkeypatches `_emit_decision_log` to capture calls, invokes compose with `--plan-change-type verification`, asserts the result is `change_type_scope_conflict` **and** that exactly one captured message contains `change_type reconciliation`, `bug_fix` and `verification`; and deleting the new emission call makes that test fail.
- **Module/topic:** `plan-marshall:manage-execution-manifest` — compose change-type reconciliation

## Refuted during adversarial review

**No gap was refuted.** G1, G2 and G3 were each re-derived from the tree by an agent that did not
write them, and all three survived — G1 and G2 by independent execution and mutation rather than by
re-reading the original evidence. The one substantive reconsideration is recorded in place rather
than here, because it changed a framing and not a verdict:

- **G3 was re-scoped, not refuted.** It was originally presented as D2 being incomplete. Re-reading
  D2's actual text — "name the two scopes apart **wherever both appear** … *Done when:* the names
  differ" — against the four sites where both scopes do appear shows the done-when is met, so G3 is
  residue beyond the deliverable rather than a shortfall against it. The finding itself (five
  authoring surfaces spell the field bare) re-derived exactly and stands at `low`; the verification's
  D2 **Complete** column was corrected from `partly` to `yes` as a result.
- **G1's severity was challenged and upheld.** The challenge was reachability: no automated in-tree
  producer can write a non-canonical value (heuristic keyword map, LLM-fallback vocabulary, and every
  recipe `default_change_type` were all swept and are all canonical), which argues for `medium`. It
  is upheld at `high` because `manage-status/SKILL.md:957` documents `feature_breaking` as a live
  value at exactly the blocked key, so the repository's own user-facing documentation invites the
  input that hard-blocks compose. The sweep is now recorded in G1 so a third reviewer can re-open the
  severity on new evidence rather than on re-argument.
