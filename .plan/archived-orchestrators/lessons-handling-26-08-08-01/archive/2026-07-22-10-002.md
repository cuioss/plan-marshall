# Files entering scope after the discovery sweep has already run bypass its assessment entirely

## What happened

During phase-3-outline on `consumer-upgrade-cache-freshness` (deep/complex
lane, full codebase discovery), the initial discovery sweep ran and produced
the plan's affected-files/design-notes corpus in the usual way. Two
operator-decision files then entered the plan's scope AFTER that sweep had
already completed, and neither received the assessment pass the sweep
performs on every file it discovers up front — an omission the phase-3-outline
Q-Gate flagged as two separate warning-severity findings, both resolved
in-run before phase-4-plan.

## Root cause

The deep-lane discovery sweep is structured as a single up-front pass: it
enumerates the codebase, classifies candidate files, and produces the
deliverable design notes from that one enumeration. Nothing re-runs the
sweep's classification/assessment step for a file that is added to scope
*after* the sweep has already executed — whether because an operator decision
recorded during clarification/outline widened scope, or because a later
deliverable's design notes reference a file the first pass never considered.
The sweep's completeness guarantee is a point-in-time guarantee: it covers
what existed in scope at the moment it ran, not what scope grows to include
afterward. A late-arriving file is *silently* exempt from the same
scrutiny every file discovered in the first pass received, unless the author
explicitly loops back and re-runs (or manually performs) the assessment for
it.

## The generalizable rule

Any file that enters a plan's scope after the discovery sweep has already
completed — an operator-decision artifact, a file surfaced by a later
deliverable's design notes, a file added in response to a Q-Gate finding on a
sibling deliverable — needs an explicit, deliberate assessment pass before
the outline is finalized. Do not treat "the sweep already ran" as license to
fold a late-arriving file into `affected_files` without also running the same
classification/consistency check the sweep would have applied had the file
been present from the start. Concretely: when scope grows after the
discovery sweep, either (a) re-run the sweep's assessment step scoped to just
the new file(s), or (b) explicitly document, in the deliverable's Design
notes, why the new file needs no assessment (e.g., it is purely additive with
no interaction with the swept corpus) — silence is not evidence the file was
considered.

## Why it slipped

The discovery sweep's mental model treats "ran the sweep" as a completed,
one-time gate rather than a standing invariant that must be re-satisfied
whenever scope changes. There is no structural trigger that fires the
assessment step again when a file is added to `affected_files` outside the
sweep's own enumeration — the phase-3-outline Q-Gate is currently the only
backstop, and it caught this instance only because it independently checks
scope-completeness rather than trusting the sweep's own report of what it
covered.

## Impact

Advisory-only cost this run (Q-Gate caught both omissions before
phase-4-plan, resolved in the same corrective pass). Left unfixed as a
process gap, a future plan could ship a late-scoped file — including one
carrying an operator decision that changes deliverable behavior — with zero
consistency check against the rest of the outline.
