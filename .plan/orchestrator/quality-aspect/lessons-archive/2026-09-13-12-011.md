# Do not say "yield" in a fixture docstring unless the fixture yields

The `handler_calls` fixture in `test_credentials_cli.py:65` documented itself as
yielding the call log, while its body ends in `return calls` with no `yield`
anywhere. "Yield" is a **term of art** in pytest fixtures — it selects the
setup/teardown form — so the docstring does not merely read loosely, it names the
wrong fixture kind.

Two readings follow, and they diverge in a way that costs real work:

- **Reading A** — a yield-fixture carrying teardown, which a maintainer extends by
  adding cleanup after a `yield` that does not exist.
- **Reading B** (the intended one) — a plain return fixture handing the list back.

The ambiguity was live rather than theoretical: a genuine yield-fixture sits in the
sibling `test_configure.py`, so both forms are in use in the same test package.

## Solution

Reserve "yield" in a fixture docstring for a fixture that actually yields. Say
"return" or "hand back" for the plain form. Where a file's other docstrings are
already precise about mechanics — this one's neighbours read "return the code
`safe_main` exits with", "returns that handler's value", "exits 1" — a loose
"yield" reads as *deliberate* against the file's own standard, which is what makes
it misleading rather than merely imprecise.

## Impact

Cheap to get right, and the cost of getting it wrong is paid by a future
maintainer at the moment they are adding teardown to a fixture that cannot carry
it. The general rule: in a docstring, a word that is a framework keyword is a
factual claim about which API shape the code uses.
