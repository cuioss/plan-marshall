# literal-count-drift counts per-bundle extension.py overrides, NOT the ext-point Current Implementations table — reconciling the two reintroduces the finding

The `literal-count-drift` plugin-doctor rule (added by PR #774) measures a
specific set: the number of per-bundle `discover_modules()` / `provides_recipes()`
overrides declared across the `plan-marshall-plugin/extension.py` files. It does
NOT measure the entries in the corresponding `ext-point-*.md` "Current
Implementations" table. The two sets have different cardinalities and are
counting different things — the count in `extension-api/SKILL.md`'s Extension
Points table mirrors the `extension.py` override count (3 bundles each for both
`discover_modules` and `provides_recipes`), while the `ext-point-build.md`
Current Implementations table lists 4 build tools (maven, gradle, npm, pyproject)
and the recipe table lists 6 recipe keys.

## Anti-pattern

During pre-submission self-review of the PR#774-findings fix, the
`touched_claim_unverified` self-review candidate flagged the surviving literal
`3` in `extension-api/SKILL.md` line 117 as wrong, reasoning that it should be
`4` to match `ext-point-build.md`'s Current Implementations table. Acting on that
"fix" would have changed 3 -> 4 (and 3 -> 6 for the recipe count) and
**reintroduced the exact `literal-count-drift` findings the plan existed to
eliminate** — the plugin-doctor gate confirmed 0 findings only at the value `3`.

The same trap applies to any reviewer (human or LLM) who sees two nearby tables
that "should" agree and reconciles them by editing the literal: the rule and the
Current Implementations table are deliberately decoupled because they count
different sets. They are not in conflict; they are orthogonal.

## Rule

When `literal-count-drift` reports (or a reviewer questions) a count in a
`plan-marshall-plugin` / `extension-api` SKILL.md Extension Points table:

1. Resolve the count against the **per-bundle `extension.py` override set** —
   grep the `discover_modules()` / `provides_recipes()` method overrides across
   the bundles' `plan-marshall-plugin/extension.py` files and count the bundles
   that actually override the method. That count is authoritative.
2. Do NOT reconcile it against the `ext-point-*.md` "Current Implementations"
   table — that table enumerates a different set (concrete build tools / recipe
   keys) and is not what the rule measures.
3. Treat the live `doctor-marketplace analyze` result at the current literal as
   ground truth: if the rule reports 0 findings at value N, N is correct by
   construction. Changing N to satisfy a separate table reintroduces the finding.

## Detection

A reviewer-side red flag: a `touched_claim_unverified` / count-mismatch finding
whose proposed correction would make a SKILL.md literal agree with a nearby
"Current Implementations" table. Before applying, run `doctor-marketplace analyze`
and confirm whether the rule actually flags the current value — only the rule's
own verdict, not table-agreement intuition, settles the count.

## Impact

Affects any plan that touches `extension-api` / `plan-marshall-plugin` SKILL.md
Extension Points tables, and any reviewer reasoning about plugin-doctor
count-drift findings. The failure is silent at review time (the "fix" looks like
an obvious table reconciliation) and only the plugin-doctor gate catches the
regression — by which point the build-failing finding is back.
