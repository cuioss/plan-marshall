# A freshness gate that accepts a --help invocation as evidence a verify observed the tree

## What happened

`pre-commit-verify-freshness` exists to confirm that a verify actually observed the current tree
before a commit is allowed. It accepted a **`--help` invocation** as that evidence.

`--help` parses arguments, prints usage, and exits. It reads no source, runs no test, and touches no
tree. It nonetheless satisfied the gate, because the gate's evidence test was "a verify command was
invoked and exited zero" rather than "a verify observed this tree."

A second instance from the same run, in the opposite direction: a compose-time
`execution_tier: per_task` stamp was recorded for `verify:module-tests`, while the live resolve
returns `orchestrator / 638s` — a stamped derived value asserting a tier the leaf **provably cannot
run**. And a third: a fixed warning string that outlived the gate it described, reporting the wrong
gate's reason.

## Why it matters

This is the vacuous-guard archetype in its evidence-accepting form. The more familiar shape is a
predicate that never fires; this one is a predicate that fires on **anything**, including a null
action. Both produce the same artifact: a green gate that certifies nothing.

An evidence gate is a load-bearing safety mechanism precisely because it is trusted downstream. A
gate that can be satisfied by an invocation which does no work is worse than no gate, because the
absence of a gate is visible and its vacuous presence is not.

⭐ The three instances differ in mechanism — an accept-anything evidence test, a stale derived stamp,
a message outliving its condition — but share one property: **the artifact asserting the fact was
produced without the fact being checked.**

## How to apply

- **Test the evidence, not the invocation.** A verify's evidence must be tied to the tree it
  observed: a content hash, a `worktree_sha`, a file list, a test count. "The command ran" is not
  evidence about the tree.
- **Ask what null action satisfies this gate.** If `--help`, an empty input, a zero-file run, or a
  no-op invocation passes, the gate is vacuous. Make that question part of authoring any guard, and
  add the null action as an explicit failing test.
- ⛔ **A derived value stamped at compose time is a snapshot, not an authority.** If the live resolver
  can disagree with the stamp, either re-resolve at consumption or record the stamp with the inputs it
  was derived from so the divergence is detectable.
- **A fixed message must name a condition it can still be wrong about.** When a gate's logic changes,
  its message is part of the change; a message that survives its gate reports a reason that is no
  longer computed.
- Every guard deserves a test that proves it **can fail**. A guard with only passing tests has never
  been shown to be a guard.
