# Test pollution guard misattributes a concurrent plan's merge.lock write to the running test

## What happened

A whole-tree `verify` failed with a pollution-guard ERROR from `test/conftest.py:1403`:

```
Pollution guard: test test/plan-marshall/tools-script-executor/test_executor_target_resolution.py::TestCmdGenerateTargetFlag::test_executor_target_in_toon_output leaked into the real .plan/local tree:
  New entries: ['merge.lock']
```

The named test did not write that file. `merge_lock check` showed the lock was held by a **different plan** — `always-on-is-not-a-resolve`, staleness `fresh` — running concurrently in a sibling worktree on the same machine. The tests themselves were green: 23951 passed, 0 failed, 11 skipped.

Re-running the identical verify once the lock already existed — so it sat in the guard's baseline snapshot instead of appearing mid-window — passed: exit 0, compile + lint + test green.

## Root cause

The guard snapshots the machine-global `.plan/local` directory before and after each test and attributes **any** new entry to whichever test was running. `.plan/local` is shared by every plan-marshall session on the machine, so a concurrent session's legitimate merge-mutex acquisition is indistinguishable from a leak by the test under observation.

The blamed test is simply the one with the widest window — at 52.33s it was the second-slowest in the run, which maximises its chance of straddling an unrelated concurrent write. The attribution is therefore not merely wrong but **randomly** wrong: which test gets blamed depends on timing, so the same defect surfaces under a different name each run and reads as flakiness scattered across the suite.

## Why it matters

A concurrent session can redden an unrelated plan's quality gate. The failure names a specific test as leaking, so the natural response is to investigate that test — which is clean. Worse, the signal is condition-dependent: it vanishes on re-run once the lock is already present, which invites classifying it as flaky and moving on, leaving the unsound attribution in place for the next plan to trip over.

## How to apply

Make the guard unable to blame a test for another session's write. Either:

- **Scope the snapshot to the sandbox** rather than the real shared tree, so only writes the test itself could have made are in view; or
- **Ignore entries attributable to another live plan.** `merge.lock` records its `holder_plan_id`, so the guard can check whether a new entry belongs to a different, live plan and exclude it rather than fail.

The second is the narrower fix and keeps the guard's real purpose — catching genuine sandbox escapes — intact.
