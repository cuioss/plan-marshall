# plan_logging.log_entry does not validate client-supplied plan_id (shared-logging hardening follow-up)

Surfaced during PLAN-03 (interaction audit logging) as a deferred, out-of-scope
finding (accepted, hash `5f7133`): the client's `_audit_log` passes the
caller-supplied `plan_id` straight to `plan_logging.log_entry`, which resolves the
log path via `get_store_dir`/`get_log_path` WITHOUT ever calling
`input_validation.is_valid_plan_id` — unlike `log_work` and `log_decision` in the
same module, which validate first. A crafted `plan_id` containing path segments
could in principle influence the resolved log path.

## Why deferred (not fixed in PLAN-03)

This is a **pre-existing, system-wide** gap in the shared `plan_logging` module,
not something PLAN-03 introduced. `log_entry` / `get_log_path` are shared by many
pre-existing callers (e.g. `log_script_execution` via `extract_plan_id`). A correct
fix means validating `plan_id` once at the shared-logging boundary and touching all
those call sites — well outside PLAN-03's live footprint. Patching only the
build-server-client call site would leave the other callers exposed.

## The fix that belongs to a dedicated plan

Add an `is_valid_plan_id` gate inside `plan_logging.log_entry` (and/or
`get_log_path`) so EVERY caller is protected at the boundary, matching what
`log_work` / `log_decision` already do — then remove any now-redundant per-caller
validation. Fix at the tool layer (the shared module), not at each call site
(see [[feedback_fix_at_tool_layer_we_own_it]]).

Scope note: this is path-traversal-adjacent; pair the fix with a containment test
(a `plan_id` with `../` / absolute-path segments must be rejected or safely
contained), mirroring the CWE-59 containment work done elsewhere in finalize.
