# Handing every task's module build back to the orchestrator was very expensive

## What happened

Plan plan-25-integration-test-evidence (PR #408). The module-tests command for `integration-tests` (`test -pl integration-tests -am`) resolves to the orchestrator tier on this project (about 1140 to 1160 s, above the per-task limit). Each task therefore ended its hand-off after compiling and yielded so the orchestrator could run the build. After TASK-1 and TASK-2 the second yield was reclassified as an error by the no-progress check (in_progress=1, completed_delta=0, 536031 tokens).

## Operator decision

One full module-tests build per deliverable, not per task. Tasks run test-compile and their targeted tests inline; the orchestrator runs the long build once at the end of each deliverable, before its commit. Accepted risk: a module-wide failure surfaces one or two tasks late.

## Observations for the pickup

- Where a module's test build always exceeds the per-task limit, a per-task verification command of that kind guarantees one hand-back per task. The planner could detect this at planning time and stamp the long build per deliverable from the start.
- A yield for an owed long build was counted as "no progress" although the task's code was written and compiled.
- Batching left uncommitted work of several deliverables in the tree while builds ran; the plan had to stage one deliverable's state of a shared file from a stored git blob.
