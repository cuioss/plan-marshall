# An argparse_rejection script_failure record must carry argparse's own message, and envelope docs and executor script must share one bundle version

The `script_failure` record for `failure_kind=argparse_rejection` must capture argparse's own stderr message (the unrecognized or missing argument), not only the argv, and the skill docs an envelope loads must come from the same installed bundle version as the script the executor runs.

## What happened

In plan client-refresh-verification-discovery-cache, during the first 6-finalize functional-review envelope (work-log 9d96b1, 2026-11-15T11:41:01Z), the reviewer ran `architecture.py --plan-id {plan} search --content --literal --pattern '...'`. The executor logged `exit_code=2 failure_kind=argparse_rejection` with a `detail` holding only the command line. Checked afterwards against the currently resolvable script the invocation looks valid (`--plan-id` is a top-level flag before the verb, and `search` declares `--content`, `--pattern` and `--literal`). Two causes remain open: the envelope ran against another installed bundle version in which `--literal` or `search` was not yet declared (two plan-marshall cache versions, 0.1.2119 and 0.1.2134, were installed on the machine), or the single quotes reached argparse literally. The reviewer re-dispatched and the step completed.

## Why it matters

- An argparse rejection whose logged detail is only the argv cannot be diagnosed after the fact; the signal-scan counts it as a script-failure cluster and nobody can tell what to fix.
- If the cause was version skew between the envelope's skill docs and the executor's script, a reviewer can follow the docs exactly and still be rejected.

## Rule

- Record argparse's stderr in the `script_failure` detail for every `argparse_rejection`.
- Check at dispatch that the docs an envelope loads and the script the executor runs come from the same installed bundle version.
