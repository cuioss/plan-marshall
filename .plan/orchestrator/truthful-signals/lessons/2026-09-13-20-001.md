# manage-tasks commit-add rejects deliverable:0 that triage.md's FIX allocation instructs writing

Observed while running plan architecture-store-query-truthfulness (PLAN-CIS-049), verification-feedback triage round 6. workflow/triage.md Step 3c explicitly instructs the FIX allocation body to write deliverable: 0 for a fix task with no natural deliverable owner. manage-tasks commit-add rejected this with "Missing required field: deliverable" -- a falsy-value check (likely `if not data.get("deliverable")`) misreports a PRESENT field (0) as absent, and manage-tasks/SKILL.md documents deliverable as a single positive integer, directly contradicting the 0 the triage workflow instructs. The error message additionally misattributes the cause as missing rather than invalid-value, which costs real diagnosis time.

## Directive
Before authoring or reviewing a FIX-task allocation that follows workflow/triage.md Step 3c literally, verify whether manage-tasks commit-add still rejects deliverable: 0 -- if so, map the fix task to the most relevant existing deliverable instead (the one whose declared files the fix targets) and note the substitution, rather than retrying deliverable: 0. Separately, this is a real doc/validator divergence worth fixing at the source: either commit-add should accept 0 as the documented origin=fix sentinel (fixing the falsy-check bug and correcting SKILL.md to allow 0 for that origin), or triage.md Step 3c should stop instructing a value the validator has never accepted -- pick one arm and update both surfaces together so a future FIX allocation does not rediscover the same rejection.
