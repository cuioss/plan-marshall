# A worktree-relative --tasks-file staging path can silently read a stale prior-attempt file instead of a freshly Write-tooled one

## Context

During phase-4-plan for plan-170-make-the-attribution-usable, the agent staged the
multi-task batch JSON via the `Write` tool at an **absolute** path anchored under the
main checkout (`/home/oliver/git/plan-marshall/.plan/local/plans/{plan_id}/work/tasks-batch.json`),
then invoked `manage-tasks batch-add --tasks-file .plan/local/plans/{plan_id}/work/tasks-batch.json`
(a **relative** path) from Bash. The plan uses a worktree, and the Bash tool's actual cwd for
this session was the worktree root
(`/home/oliver/git/plan-marshall/.plan/local/worktrees/{plan_id}`), which itself contains its
OWN nested `.plan/local/plans/{plan_id}/work/` tree (per the ADR-002 cwd walk-up resolution
contract that `manage-*` scripts use).

The relative `--tasks-file` path therefore resolved against the WORKTREE's nested `.plan`
tree, not the main checkout's tree the `Write` call had targeted. A stale `tasks-batch.json`
already present at that worktree-relative path — left over from an earlier, abandoned
phase-4-plan attempt against a since-revised solution outline (4 deliverables vs. the
current 3) — was silently picked up and persisted as 7 wrong tasks, none of which matched
the current `solution_outline.md`. The Step 2.5 re-entry guard did not catch this because it
only checks for existing `TASK-NNN.json` files (there were zero), not for stale scratch/staging
content in `work/`.

## Resolution Approach

Detected the mismatch by comparing the `batch-add` return payload's task titles/deliverable
numbers against the just-read `list-deliverables` output (3 deliverables) — the persisted
tasks referenced a nonexistent deliverable 4 and different affected-file paths. Recovered by:

1. Removing all 7 erroneously created tasks via `manage-tasks remove --task-number N` (highest
   number first).
2. Re-`Write`-ing the correct 5-task batch JSON directly to the WORKTREE-relative absolute path
   (`.../worktrees/{plan_id}/.plan/local/plans/{plan_id}/work/tasks-batch.json`) — the exact path
   the relative `--tasks-file` argument resolves to — rather than the main-checkout path.
3. Re-running `batch-add`, which then correctly created 5 tasks matching the 3-deliverable
   outline.

## Anti-pattern to avoid

When staging a batch JSON file for a `manage-*` script's `--tasks-file` (or any relative
`--*-file` path) argument in a plan that uses a worktree, do NOT `Write` to an absolute path
computed from the main-checkout root while the accompanying Bash call passes a *relative*
path — the two can resolve to two entirely different files when the Bash cwd differs from the
assumed main-checkout root (a stale artifact from a prior attempt in the worktree's own nested
`.plan` tree can then be silently consumed instead of the freshly authored content). Either:

- `Write` to the exact same relative-path resolution the subsequent Bash call will use (verify
  cwd first via a `pwd` probe if uncertain), or
- Always re-`Read` the staged file immediately before invoking the consuming script, to confirm
  its content matches what was just authored — especially when a plan uses a worktree and the
  Bash tool's cwd for the session is not verified to be the main checkout.

The Step 2.5 re-entry guard (which checks `TASK-NNN.json` count only) does not protect against
this class of staleness — a scratch/staging file under `work/` is invisible to it. Consider a
future enhancement: `batch-add --tasks-file` could log the resolved absolute path and a content
digest so a caller can cross-check it against what it just staged.
