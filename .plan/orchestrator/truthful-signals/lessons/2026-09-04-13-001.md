# A dispatched finalize step resolves its workflow doc against the MAIN checkout, so a plan editing that doc runs the pre-plan version

## Rule

When a finalize step's authoritative workflow/standards doc is inside the plan's
own footprint, the dispatcher MUST forward the worktree-absolute path of that doc
— or the step MUST re-read it from `WORKTREE` before executing.

## Observation

The `execution-context` dispatch resolves `workflow: plan-marshall:phase-6-finalize/workflow/X.md`
against the **main checkout**, not the plan's worktree. A plan that edits `X.md`
therefore hands every dispatched round the **pre-plan** instructions.

Observed live in PLAN `shipped-guards-assume-the-meta-projects-own-layout`:
`pre-submission-self-review` round 5 was handed a copy declaring **three** verdicts
where the worktree copy declared **five**, and omitting the symmetric `--force`
rule entirely. The agent noticed only incidentally — a test under review asserted
against four labels — then re-read the worktree copy and executed against that.
Nothing in the dispatch contract makes the divergence detectable in general.

## Why the existing contract does not cover it

`phase-6-finalize/SKILL.md` carries a **post-rebase step-doc re-resolution
contract**, but it is armed by a rebase folding an *upstream* change into the
worktree. This case has no rebase: the plan's own edit is simply never resolved
from the worktree at all, so nothing arms the re-resolution.

## How to apply

- Dispatcher side: when a step's doc is in `references.affected_files`, pass the
  worktree-absolute path rather than the notation.
- Step side: if the workflow doc you were handed governs behaviour your own plan
  is changing, re-read it from `WORKTREE` first and execute against that copy.
- Reviewer side: a step whose instructions contradict the live document is a
  version-skew symptom, not a step defect — check provenance before filing.
