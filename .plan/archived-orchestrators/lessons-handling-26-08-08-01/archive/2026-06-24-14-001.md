# Late-stage finalize baseline drift on shared files: rebase-onto-main is a viable first-class recovery, not only the phase-2-refine re-cycle

## Context

During `phase-6-finalize` of the `routing-v2-recipe-match` plan, while the
finalize pipeline was running, `origin/main` advanced with PR #770, which edited
the *same* source file this plan touched (`manage-execution-manifest.py`).
The finalize flow looped back into `phase-5` to re-verify, and the merge of the
advanced baseline against the plan's branch produced **content-overlap
conflicts** on the shared file.

This is distinct from the freshness-gate-staleness drift class already captured
in `2026-06-20-16-002` and `2026-06-24-09-002`: those concern *local* worktree
mutation invalidating the pre-commit freshness gate. This lesson concerns
*remote* baseline drift — `origin/main` advancing on overlapping files during a
late finalize loop-back — and the recovery strategy for it.

## What happened

The canonical late-stage drift recovery the workflow steers toward is a
`phase-2-refine` re-cycle (re-clarify the request against the moved baseline,
then replan). For a small, well-understood content-overlap conflict, that full
re-cycle is heavy: the request had not changed, only the baseline had moved.

The user instead chose a **surgical rebase-onto-main + conflict-resolution**:
rebase the plan branch onto the advanced `origin/main`, resolve the file-level
overlap by hand, and continue the finalize pipeline. This resolved the drift
correctly with far less ceremony than a full refine re-cycle.

## Lesson

When late-stage finalize drift is a bounded content-overlap conflict from
`origin/main` advancing on shared files (not a semantic change to the request
or the plan's design), **rebase-onto-main + conflict-resolution is a legitimate
first-class recovery** — it is not inferior to, nor a shortcut around, the
`phase-2-refine` re-cycle. The two recoveries address different drift shapes:

- **`phase-2-refine` re-cycle** — the *request* or the design assumptions moved
  (the baseline change invalidates what the plan set out to do). Re-clarify and
  replan.
- **rebase-onto-main** — only the *baseline content* moved on overlapping files;
  the plan's intent and design are still valid. Rebase, resolve the overlap,
  continue.

## How to apply

- The finalize workflow's late-stage drift-recovery branch should offer rebase
  as a first-class option alongside the refine re-cycle, with a discriminator on
  *what* drifted: request/design (→ refine re-cycle) vs baseline content on
  overlapping files (→ rebase).
- Choose rebase when: the request is unchanged, the conflict is file-level
  content overlap, and the plan's design assumptions still hold against the new
  baseline. Choose the refine re-cycle when the baseline change invalidates a
  design assumption the plan depends on.
