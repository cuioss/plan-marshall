# tool_name-to-config-namespace indirection seam: internal-id-keyed config read silently misses when id diverges from public namespace

When a function maps an **internal identifier** onto a **user-facing config
namespace**, the two names can silently diverge. A build factory read the wrong
marshal.json key because it indexed the config block with an internal tool id
(`tool_name='python'`) instead of the documented public namespace
(`build.pyproject.*`). The mismatch passed every internal gate and was caught
only by the external CodeRabbit reviewer.

## Where it surfaced (historical — closed)

**Closed:** `_read_require_wrapper_override(...)` in
`marketplace/bundles/plan-marshall/skills/script-shared/scripts/build/_build_execute_factory.py`
was deleted in full by plan `remove-the-require-wrapper-knob-entirely-auto-dete`,
which removed the `require_wrapper` feature entirely. The specific seam no longer
exists in the build factory.

For reference: the factory read `build.{tool_name}.require_wrapper` from
marshal.json using the **internal** build-system id (`config.tool_name`). For
the pyproject build system that id is `'python'`, so the code read
`build.python.require_wrapper` — a key that does not exist — instead of the
documented and seeded `build.pyproject.require_wrapper`. The override therefore
never took effect for pyproject builds; it silently degraded to the static
per-build-system default.

## Root cause

A name-indirection seam between two namespaces that are *almost* but not
*identically* aligned:

- **Internal id** — `tool_name` (e.g. `'maven'`, `'gradle'`, `'npm'`,
  `'python'`). Used to qualify log lines, queue keys, and `ExecuteConfig`.
- **Public config namespace** — `build.{system}.*` in marshal.json (e.g.
  `build.maven.*`, `build.pyproject.*`). Documented, seeded, user-visible.

For maven/gradle/npm the two names coincide, so a single `tool_name`-keyed read
happens to hit the right config block. For pyproject they diverge
(`'python'` vs `'pyproject'`), and the read silently misses. The seam is
invisible precisely on the one build system where the names differ.

## Why every internal gate missed it

- **Unit tests** exercised the override only for **maven-shaped keys**
  (`build.maven.require_wrapper`), where `tool_name == namespace`. No test
  drove the `python → pyproject` path, so the divergent case was never asserted.
- **phase-3-outline q-gate-validation, phase-4-plan, phase-5 task execution,
  pre-submission-self-review, and the whole-tree-gate** all passed: the read
  *degraded silently* to a valid default rather than erroring, so there was no
  failing signal anywhere in-run.
- The defect surfaced only when the **external CodeRabbit reviewer** flagged the
  key-name mismatch. A silent-degrade indirection bug produces no internal red.

## How to apply

- **Treat every identifier→namespace mapping as a divergence risk.** When code
  indexes a user-facing config namespace with an internal id, audit whether the
  two name sets are identical across **all** members, not just the common ones.
  When the id and namespace diverge for even one member (e.g. internal `'python'`
  vs public `build.pyproject.*`), add an explicit normalization map at the call site.
- **Parametrize the indirection test across every member of the id set.** A test
  that covers only the member where the names happen to coincide
  (maven) cannot detect the diverging member (pyproject). When a config read is
  keyed by an internal id, the test matrix MUST include each build system whose
  internal id differs from its public namespace.
- **Silent-degrade reads are the dangerous shape.** A config read that falls
  back to a default on a missing key (rather than erroring) converts a
  wrong-key bug into a no-signal bug. When a key read degrades silently,
  add a positive test asserting the override *takes effect* with the documented
  key — green-on-default is not evidence the key path is correct.
- **Cross-check the key string against the documented/seeded namespace.** Grep
  the config defaults / seed for the literal key the code constructs and assert
  the code path can produce exactly that string for every relevant build system.

## Impact

The pyproject `require_wrapper` override was a no-op for the entire window the
bug existed: users setting `build.pyproject.require_wrapper` in marshal.json saw
no effect, with no error to explain why. The class generalizes to any
internal-id-keyed read of a user-facing namespace — a recurring seam wherever an
abstraction's internal vocabulary (`tool_name='python'`) and its public
configuration vocabulary (`build.pyproject.*`) are maintained separately and
allowed to drift.
