# The self-review surfacer enumerates the hand-mirrored-table class but reported clean where a reviewer found three

## Observed

On PR 1455 (PLAN-155), `default:pre-submission-self-review` recorded
`self-review clean: 194 candidates examined, no check matched`. CodeRabbit then
filed 7 actionable comments on the same diff. The review retrospective classified
**4 of the 7 as `gate_addressable`** — defects a gate that already exists could have
caught — and three of those four (`c6d03d`, `525092`, `5f3517`) are one class:

> a hand-maintained test table mirroring a set that production already declares and exports

That is a class the `ext-self-review-plan-marshall` surfacer **already enumerates**
(`source-of-truth duplicates` / `duplicate-claimable keys`). So this is not a missing
detector — it is a detector that ran, produced 194 candidates over the right files,
and matched none of the three instances.

The remaining 3 escapes are `gate_structural`: semantic falsifiability judgments — a
parametrize row whose value cannot discriminate the behaviour its own `ids=` string
names — which no current gate class reaches. Those are a separate, harder problem and
are NOT what this lesson is about.

## Directive

Investigate why the surfacer's source-of-truth-duplicate detection did not match the
three instances, given it enumerates the class. Candidate causes, in the order worth
checking:

1. The detector may key on a *literal duplicated between two files* and not on the
   shape here, which is a literal table in a test whose counterpart is an exported
   Python object (`EXCLUDE_DIRS`, the live subparser `choices`, `CANONICAL_COMMANDS`).
   Those are not textually duplicated — the test restates the set's MEMBERS, not the
   set's source.
2. The candidate volume (194) may be diluting: if the class fires but ranks below a
   reporting threshold, the finding exists and is never surfaced.
3. The surfacer may be scoped to `marketplace/bundles/**` shapes and reach test files
   only incidentally.

Add a regression fixture from the real instances — the simplest is
`test_build_discover.py`'s pre-fix excluded-dir table against `EXCLUDE_DIRS` — so a
fix is falsifiable rather than asserted.

## Why it matters beyond one PR

An in-house gate that reports **clean** on a diff where an external reviewer then finds
four addressable defects is worse than one that reports nothing: its clean verdict is
read as evidence. This is the same shape the gate's own documentation warns about — a
narrow gate whose green reads as whole-tree assurance — appearing in the gate written
to prevent it.

The `gate_addressable` vs `gate_structural` split from the review retrospective is the
useful discriminator to keep: it separates "a gate could have caught this and did not"
from "no gate reaches this class", and only the first is a defect.
