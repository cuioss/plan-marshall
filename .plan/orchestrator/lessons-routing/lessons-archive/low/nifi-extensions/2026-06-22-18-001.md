# Verify framework runtime behavior empirically before designing around version-specific documentation

When designing an integration that depends on a framework's runtime
behavior — especially version-specific behavior — verify the actual
behavior empirically against the real running version before architecting
around what the documentation (or community lore) says.

## Context

This plan integrated gateway counters into NiFi's native metrics. Community
docs and older NiFi reporting-task documentation indicated that user
`session.adjustCounter` counters are NOT included in NiFi's Prometheus
export, which would have forced a second mechanism (a custom
`ReportingTask`) to surface the counters on the Prometheus endpoint.

An empirical probe against the actually-running NiFi 2.9 container proved
the opposite: NiFi 2.9 DOES export user-defined counters at
`/nifi-api/flow/metrics/prometheus` as the
`nifi_processor_counters{counter_name=...}` metric family.

## The lesson

Sequence an empirical-verification deliverable FIRST, before the
design-dependent deliverables. Here, probing the live endpoint up front
proved the planned Tier B custom `ReportingTask` was redundant — the Tier A
`session.adjustCounter` bridge alone reaches BOTH `/nifi-api/counters` and
the Prometheus endpoint. The redundant deliverable was dropped, simplifying
the implementation.

## Rule

Do X instead of Y:

- **Do**: probe the real runtime (the running container / actual framework
  version) to confirm framework behavior, then design around the observed
  reality. Make the empirical-verification step an explicit, early
  deliverable when a later design hinges on the answer.
- **Instead of**: designing around documentation or community claims for
  version-specific framework behavior — docs lag, are version-skewed, or
  describe a different release than the one actually deployed.
