# Name the canonical deliverable read call in the execute workflow

## Context

In plan `unified-sync-all-harnesses` three separate execute envelopes each issued

```text
manage-solution-outline get-deliverable --plan-id {plan_id} --number N
```

and each was rejected: the flag is `--deliverable-number`. Every envelope was a fresh dispatch, so each one made the same guess independently, logged the rejection, and retried. No state was changed by the rejected calls.

## Root cause

OBSERVED: a content search over the 3563 inventoried files (clean coverage) finds `get-deliverable` in `manage-solution-outline/SKILL.md`, its script and two test files only. Neither `phase-5-execute` nor `execute-task` names the call, so an execute leaf that needs a deliverable's text has no invocation to quote and composes one.

Not established: which workflow step sent the leaf to the deliverable in the first place, or whether the task record was meant to make that read unnecessary.

## Proposed action

- At the step of the execute workflow that needs deliverable text, either quote the exact call or point to the `manage-solution-outline` canonical-invocations entry for `get-deliverable`.
- If the task record already carries what the leaf needs, say so at that step so the read is not attempted.
- Do not add a `--number` alias: the typed-ID flag convention names the flag `--deliverable-number`.

## Evidence

- script_failure_analysis: `manage-solution-outline` / `get-deliverable`, exit 2, `occurrence_count: 3`.
- work.log ERROR pairs at 2026-10-02T14:50:06Z, 15:18:56Z and 16:21:50Z, each "`--number` is not declared ... ['deliverable-number', 'plan-id']".
- chat_history_analysis: the envelope 2, 3 and 4 reports each list the rejected call as a process note.
- `architecture search --content --literal --pattern get-deliverable`: 4 files, none under `phase-5-execute` or `execute-task`.
