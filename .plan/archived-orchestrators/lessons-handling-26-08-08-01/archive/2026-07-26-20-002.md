# A kind=build ledger entry written by the test suite can satisfy the production pre-commit freshness gate

## Problem

During phase-5-execute Step 12a on plan `executor-version-split-resolvers` (2026-07-26), the
`pre-commit-verify-freshness` gate was satisfied by a `kind=build` change-ledger entry whose
`matched_notation` was `plan-marshall:build-npm:js_coverage` — a notation this plan never ran. The
entry had been written into the worktree's REAL change-ledger by the module test suite itself, which
exercises `manage-change-ledger` against the live store rather than an isolated fixture store.

The verdict happened to be substantively correct on this run (the executing agent's own `verify` and
`coverage` runs had genuinely covered the same tree), so nothing was mis-shipped. That is exactly
what makes it dangerous: the gate reported green for a reason unrelated to the evidence it was
supposed to be checking, and no signal distinguished the two.

## Impact

Any module-test run pollutes the worktree's production change-ledger with `kind=build` rows. A
production freshness gate that scans that ledger can therefore be satisfied by test-authored
evidence — a confidence-hides-a-caveat defect in the same family as the epic this plan belongs to
(`truthful-signals`). The gate cannot currently tell a real build's ledger stamp from a test
fixture's.

## Directive

- Isolate the change-ledger store used by tests from the worktree's production store: point the
  test suite at a `PLAN_BASE_DIR`-scoped or `tmp_path` store the way `PlanContext`-based tests
  already do for plan state, so `manage-change-ledger` writes from tests never land in the real
  ledger.
- Independently, make the freshness gate's match evidence auditable: when a gate is satisfied, the
  decision record should name the matched notation AND that notation should be cross-checked against
  the plan's own resolved canonical commands, so a match on an unrelated notation is at minimum
  visible rather than silently accepted.
- Add a regression test asserting that running the module test suite leaves the production
  change-ledger unmodified.
