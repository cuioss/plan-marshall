# Dependency-bump fallout enumerated on an unverified interpreter - read the interpreter from the build log header before measuring, or the whole fallout set must be re-measured

A pytest 9 / pytest-xdist 3.8 bump plan enumerated its fallout on **CPython 3.14.6** — the host
interpreter — while CI resolves **3.12**. Every failure mode, every refutation, and every
"absorbed at root cause" claim in the first measurement pass was taken on the wrong runtime and
had to be re-measured from scratch on 3.12 before any of it could be trusted.

## What happened

The plan's premise, carried from refine through outline into TASK-001, was that pyprojectx
provisions the interpreter named by `tool.pyprojectx.lock-python-version` (3.12), and that the
host `python3` is therefore never the build interpreter. Direct observation refuted it:

- Both the pre-bump venv (`main-38be737804e77e6d7c68021fa457233d-py3.14`) and the post-bump venv
  (`main-6eb3510003797a57ceb59c2e1705f5fe-py3.14`) were `py3.14`.
- Build log line 1: `Using CPython 3.14.6 interpreter at
  /Library/Frameworks/Python.framework/Versions/3.14/bin/python3.14`.
- pytest header: `platform darwin -- Python 3.14.6`.

`lock-python-version` pins the pyprojectx *bootstrap* venv; it does not bind the interpreter the
aliases run under. Nothing in the build's own output was being read to confirm the premise.

## Cost

Three findings had already been filed off the 3.14 run and each needed an explicit re-measurement
pass on 3.12 before its verdict could stand:

- the class-scoped-fixture-as-instance-method hard error (**reproduced** on 3.12 — a genuine
  pytest 9 change, not a 3.14 artefact);
- the `assert not self._finalizers` AssertionError (**reproduced**, and on re-reading it was a
  *cascade* of the first, not a second root cause — 16 fixtures across 4 files, one fix drove both
  shapes to zero);
- the xdist 3.8.0 worker-crash cap rationale (**refuted** on both 3.14 and 3.12 — 10/10 workers,
  no `node down`, no loadscope `KeyError WorkerController`).

Had the re-measurement been skipped, the plan would have shipped a `conftest.py` fix set and a cap
removal justified entirely by evidence from an interpreter CI never runs.

## Rule

For any dependency- or toolchain-bump plan:

1. **Establish the build interpreter empirically before enumerating fallout.** Read it from the
   build's own output — the `Using CPython X.Y.Z interpreter at ...` line and the pytest
   `platform ... -- Python X.Y.Z` header — never from a config declaration.
2. **Never treat a version-pinning config key as proof of what runs.** A key that names a version
   is a request; the log header is the observation. `lock-python-version` in particular pins the
   bootstrap venv only.
3. **Make interpreter parity with CI a precondition of the first fallout measurement**, not a
   parallel deliverable. Fallout measured before parity is established is provisional by
   construction and must be re-run.
4. **Re-measure, do not extrapolate**, when the runtime turns out to differ. Record for each
   finding whether it *reproduced* or was *refuted* on the corrected runtime; both outcomes are
   load-bearing and neither is inferable from the first pass.
5. When two failure shapes appear together, check whether the second is a **cascade** of the first
   before treating it as an independent mode — fixing the first and re-running is cheaper than
   diagnosing both.

## Resolution in this plan

Fixed at root cause rather than by pinning pyprojectx: dev tools moved out of
`tool.pyprojectx.main` into a PEP 735 `dependency-groups.dev` group resolved by uv into
`uv.lock`; `tool.pyprojectx.main` now requires `uv` only; `lock-python-version` removed; and
`UV_PYTHON=3.12` declared in `tool.pyprojectx.env`, which pyprojectx `cli.py _run_alias` merges
into every alias environment and which nested `uv run` calls in `build.py` inherit. Confirmed by
the whole-tree verify log: `platform darwin -- Python 3.12.3`, interpreter `.venv/bin/python3`.
The pyprojectx bootstrap venv stays on host 3.14 and is harmless because it now holds only `uv`.
