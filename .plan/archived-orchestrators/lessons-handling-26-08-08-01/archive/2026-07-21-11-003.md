# pre-push-quality-gate module-tests divergence gate has no zero-scoped-modules branch, so a docs-only footprint falls into a scoped run with a null target

## Symptom

This plan's footprint was documentation-only (no buildable Python source).
At the `pre-push-quality-gate` finalize step, the whole-tree module-tests
divergence gate resolved the scope and got back an EMPTY scope:

```toon
scoped_modules[0]:
divergence_possible: false
recommended_target: null
```

The step's documented decision table has no branch for this state. Reading
it literally, `divergence_possible == false` routes to step 4, whose
instruction is to run:

```bash
python3 .plan/execute-script.py plan-marshall:build-pyproject:pyproject_build \
  run --command-args "module-tests {recommended_target}" --plan-id {plan_id}
```

With `recommended_target: null` this expands to a scoped run against a null
target — either a literal `module-tests None` invocation or, depending on
how the executing agent interprets the placeholder, an improvised whole-tree
run. Neither is what the doc intends.

## Root cause

`marketplace/bundles/plan-marshall/skills/phase-6-finalize/standards/pre-push-quality-gate.md`
§ "Whole-tree module-tests divergence gate" enumerates exactly three
branches:

2. `whole_tree_available == false` → warn and pass (honest degradation).
3. `divergence_possible == true` and `whole_tree_available == true` → run
   whole-tree `module-tests`.
4. `divergence_possible == false` → run scoped `module-tests
   {recommended_target}`.

Branch 4's prose justifies itself with "a single isolated module cannot
diverge from the whole tree (match by equivalence)" — it was written
assuming `divergence_possible == false` implies EXACTLY ONE scoped module.
But the resolver also returns `divergence_possible: false` for ZERO scoped
modules, which is the correct resolution for a footprint with no buildable
source. Zero and one collapse into the same branch, and only the one-module
case has a usable `recommended_target`.

This is the same premise the repository already handles correctly one layer
up: `.github/workflows/python-verify.yml` opts in to `skip-on-docs-only:
true` precisely because a docs-only change has nothing to build. The
finalize-side gate never got the equivalent branch.

## Impact

- A null target reaches the build wrapper. Because `pyproject_build` exits 0
  even on failure (its status must be read from the TOON), a malformed
  invocation risks being read as a pass.
- The alternative failure mode is worse for cost: an agent that resolves the
  null placeholder by "helpfully" dropping the module arg silently pays a
  full whole-tree pytest run on a docs-only push — the exact cost the
  escalate-only-on-trigger design exists to avoid.
- Either way the step's behavior on the commonest cheap footprint
  (docs-only) is undefined by its own specification, so the outcome depends
  on the executing agent's improvisation rather than the documented contract.

## Corrective action

Add an explicit zero-scoped-modules branch to the divergence gate, ordered
BEFORE the current branch 4 so it cannot fall through:

> **`scoped_modules` is empty** → the footprint contains no buildable
> module; there is nothing for pytest to gate. Do NOT run `module-tests` at
> all. Record the skip in the work log (naming the docs-only footprint so
> the pass is attributable, not silent) and proceed to Mark Step Complete
> (Success). Branch A's `--display-detail` should distinguish this state,
> e.g. `quality-gate green for {N} bundle(s), module-tests skipped
> (docs-only footprint)`.

Only then evaluate `divergence_possible == false` with a non-empty
`scoped_modules` as the genuine single-module scoped-run case, and tighten
branch 4's prose so it states its precondition (`exactly one scoped
module`) rather than leaving it implicit.

Additionally: make the seam self-defending. `resolve-test-scope` should not
emit a `divergence_possible: false` verdict that consumers cannot act on —
either return a distinct third state for the empty scope, or have the
consumer contract require a `recommended_target` non-null check before any
`{recommended_target}` interpolation.

## Recurrence signature

Any workflow/standards step that interpolates a resolver-returned optional
field (`{recommended_target}`, `{module}`, `{target}`) into a command
without a documented branch for that field being null/empty. The tell is a
decision table whose branch conditions are derived from a boolean while the
command template consumes a nullable value guarded by that same boolean —
the boolean is false for both "one item" and "zero items", but only the
former populates the value.
