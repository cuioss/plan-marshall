# Owed architecture hint: token-sheriff-validation-quarkus-deployment — Maven builds rewrite the tracked package-lock.json

This is a follow-up record for an architecture hint that could not be written by the step that found it. The step runs after the merge, where a write to the architecture descriptors would be an uncommitted change on `main`. It is not a defect lesson.

## Owed hint

- **Module:** `token-sheriff-validation-quarkus-deployment`
- **Enrich verb:** `tip`
- **Hint text (verbatim):** "A Maven build that reaches this module rewrites the tracked file `package-lock.json` in the module root. After a build, check `git status` and restore the file unless the task is a dependency change; otherwise it is committed by accident or leaves the tree dirty for the next freshness check."
- **Reasoning to record:** "From plan implement-test-duration-analysis-proposals"

The owed call, to be run on a feature branch so the change can be pushed:

```text
architecture enrich tip --module token-sheriff-validation-quarkus-deployment --tip "<hint text above>" --reasoning "From plan implement-test-duration-analysis-proposals"
```

## Evidence

Verified in the plan's work log: tasks that did not target the file list it as written by their build — TASK-8, TASK-14, TASK-17, TASK-18 and TASK-19 each record "Wrote token-sheriff-quarkus-parent/token-sheriff-validation-quarkus-deployment/package-lock.json".

Reported by the orchestrator of the run, not found in the logs by this step: the rewritten file made the pre-commit freshness check report the tree as stale until a build was run against the restored clean tree.

## Recurrence — 2026-10-13 (issue-801)

It happened again, and this time restoring the file was itself the problem.

- The whole-tree build (`npm install` inside `token-sheriff-validation-quarkus-deployment`) rewrote `package-lock.json` again. The change drops the `libc` fields from the lock entries.
- The file was restored after the green whole-tree build. The restore changed the tree after the build that the push freshness gate checks against, so the gate reported the build as stale.
- Every new whole-tree build rewrites the file again, so "restore, then build again" cannot reach a clean state. The operator chose to commit the rewritten lockfile with the change (reported by the orchestrator of the run).

### Broadened scope

The old hint ("restore the file after a build") is wrong when a freshness gate follows. Suggested replacement hint text for the owed `tip`:

"A Maven build that reaches this module runs `npm install`, which rewrites the tracked `package-lock.json` (it drops the `libc` fields). Do not restore the file after the final green build: that makes the push freshness gate report the build as stale, and the next build rewrites it again. Decide before the final build: either commit the rewritten lockfile with the change, or fix the source of the rewrite (for example `npm ci`, or a pinned npm version that keeps the `libc` fields)."

### Rule for the next run

Settle the lockfile before the last whole-tree build, not after it. Never change a tracked file between the final green build and the push.

### Follow-up owed

The root cause (the build's `npm install` rewriting a tracked lockfile) is still open. A fix in the build configuration would remove this recurring churn for every plan.

## Recurrence — 2026-10-14 (issue-800)

The third plan in a row hit the same rewrite. The lockfile commit from the previous run did not settle it.

- The final quality sweep (`verify -Ppre-commit`, green, 3085 tests) left the worktree dirty: it dropped 10 `libc` entries from optional native-binary packages in `package-lock.json`. The execute phase stopped with `triage_required` and filed finding `af4903` (work log 2026-10-13T21:17:37Z, `f1c14d`).
- The finding was resolved by restoring the file to `HEAD`, without committing it. That is the step the previous recurrence says not to take after the final build.
- According to the orchestrator of the run, every later whole-tree `verify -Ppre-commit` rewrote the file again. It made the freshness check report the build as stale twice; both times the operator approved a logged override. The finalize commit step would have swept the rewritten file into a commit if it had not been restored.
- The last commit before this run that touched the file is fc50c7ed (#803). It did not stop the rewrite here. The cause is probably the local npm version, not the content of the committed file.

### What this adds

- Committing the rewritten lockfile once does not end the churn. A different local npm version produces a different rewrite, so each plan meets the problem again.
- The two choices from the previous recurrence (commit it, or restore it after the build) both cost a run something. The only lasting fix is the root cause: make the build use `npm ci`, or pin the npm version the build uses, so that a build never writes a tracked file.

### Follow-up owed

Raise priority of the root-cause fix above. Until it lands, each plan should expect this and decide before the last whole-tree build, as the rule above says.
