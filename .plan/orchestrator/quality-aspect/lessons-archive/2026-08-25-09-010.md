# compute-footprint diffs against local main, inflating the footprint after an upstream landing

# compute-footprint diffs against LOCAL main, inflating the footprint after an upstream landing

## Context

`compute-footprint` reported **39** files for this plan against a real footprint of
**14**. The 25 extra paths belong to a commit that landed upstream while this plan was
in flight and that the plan's own sync-baseline rebase then pulled onto its branch.

The over-count is not cosmetic: the footprint is the denominator for the
declared-vs-achieved coverage checks, for `check-routing-decisions`, and for the
metrics `files_modified` figure. A plan that absorbs a sibling's files into its own
footprint reports coverage over a surface it never touched.

## Root cause

Verified in source. `_references_core.resolve_base_ref` resolves, in order:
`--base-ref` → `references.base_branch` → the literal `'main'`. Every one of those is a
**local** branch name; `origin/main` is never consulted.
`compute_plan_branch_diff` then runs `git diff --name-only {base_ref}...HEAD`.

The three-dot form is correct, and its docstring's claim — that it "excludes files that
arrived on the branch from `base_ref` via an absorb merge" — holds only while `base_ref`
is CURRENT. In a plan worktree, local `main` is not fast-forwarded: sync-baseline rebases
onto the fetched remote, leaving the local `main` ref at the old tip. The merge-base is
therefore the stale fork point, and every upstream commit the rebase replayed underneath
the branch now sits on the branch side of the range and counts as branch-only.

So the defect is not in the diff form; it is that the base is a ref which goes stale
precisely when an upstream landing makes it matter.

## Proposed action

Resolve the base against the remote-tracking ref (`origin/{base_branch}`) when one
exists, falling back to the local branch only when it does not. Alternatively pin the
base to the recorded fork point captured at worktree materialization, which cannot go
stale at all.

Either way, report the resolved base ref alongside the count — `compute-footprint`
already returns `base_ref`, so a consumer can be given the means to notice the base is
behind the remote rather than discovering it from an implausible file count.

## Evidence

- observed: 39 files reported, 14 real; the 25 extras are one upstream commit's files
- `_references_core.resolve_base_ref` — three fallbacks, all local branch names, no `origin/`
- `_references_core.compute_plan_branch_diff` — `{base_ref}...HEAD`, whose exclusion
  guarantee is conditional on a current base
- the same run's `capture-footprint` writes `references.realized_footprint` from this
  identical computation, so an inflated live set is persisted as the realized one
