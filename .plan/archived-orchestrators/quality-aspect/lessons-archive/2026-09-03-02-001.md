# direct-gh-glab-usage cannot see decision.log, where a self-reported bypass lands

## Context

On plan-170 the `direct-gh-glab-usage` aspect returned `counts.total: 0` with an empty `findings[]`, i.e. a clean CI-abstraction verdict. The same plan's `decision.log` carries entry `34f7ec`, a self-reported hard-rule violation: `gh pr view 1385 --json body` invoked directly, twice, while repairing a truncated PR Intent section. The aspect and the log disagree completely, and the aspect is the one a report reader would trust.

`references/direct-gh-glab-usage.md` declares Surface A's inputs as `logs/work.log` and `logs/script-execution.log`. `decision.log` is not read.

## Root cause

Two compounding gaps, and the second is the load-bearing one.

1. `decision.log` is absent from Surface A's input set, and it is exactly where an agent records a self-observed violation.
2. More fundamentally, a raw Bash `gh` invocation is never routed through `.plan/execute-script.py`, so it produces no `script-execution.log` line, and nothing obliges it to produce a `work.log` line either. **Neither file Surface A reads can contain the primary evidence.** The surface is described as capturing "runtime evidence of a direct CLI invocation during plan execution", but the only way such an invocation reaches those files at all is if the agent voluntarily wrote about it — and the channel agents actually write self-reports to is the one not read.

So the aspect's zero is not a measurement of compliance. It is structurally near-guaranteed regardless of what happened.

## Proposed action

- Add `logs/decision.log` to Surface A's input set in `scripts/direct-gh-glab-usage.py` and in the Inputs table of `references/direct-gh-glab-usage.md`.
- Because decision-log prose legitimately *discusses* `gh` (this lesson's own evidence does), do not reuse the bare `gh `/`glab `/`gh.` match there. Either require a command-shaped context, or file decision-log hits as a distinct lower-severity `self_reported_leak` category so a discussion is not graded as an invocation.
- State the residual honestly in the reference doc: with no hook recording raw Bash `gh` calls, this aspect detects only *self-reported* and *code-level* leaks. A zero should be rendered as "no leak recorded on the channels scanned", not as compliance. Consider publishing the scanned-channel list beside the count, the way other aspects publish `evaluated_population`.
