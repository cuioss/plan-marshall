# A test task paired with a documentation-only implementation task trips the module-mapping check


Source record: quality-check finding ace2b8 (phase 4-plan, `module_mapping_validator`, test/impl module mismatch for deliverable 3, resolution taken_into_account) of plan `jwks-unknown-kid-refresh`.

The task plan split deliverable 3 into an implementation task (TASK-5) and a module-testing task (TASK-6). TASK-6 declared `integration-tests/src/test/java/de/cuioss/sheriff/gateway/integration/JwksKeyRotationIT.java` (module `integration-tests`). Its sibling TASK-5 declared as its only write target `doc/development/integration-test-topology.adoc` (module `documentation`); every other TASK-5 target was read-only.

The check reads that pairing as "the test passes without exercising the changed code path". The cross-module routing had a real reason, which the plan did not state: the topology document is a test input of `OneOffGatewayContainersTest`.

## Resolution in this run

TASK-5 and TASK-6 were merged into one deliverable-3 task that writes the test rig, `JwksKeyRotationIT`, `JwksLateIdpReadinessIT` and the topology document together, so no implementation/test pairing remains for the deliverable. The port constant and the host-port row land in the same task. The documentation task was re-created as TASK-6 depending on TASK-5.

## Candidate lesson

A deliverable whose whole substance is integration tests plus a document those tests read has no separate implementation half. Plan it as one task. Splitting it by the default implementation/module-testing pattern produces a pairing with a documentation-only write target, which the module-mapping check rejects. The alternative the check offers, a row in `doc/developer/test-impl-mapping.adoc`, fits only when the cross-module routing is meant to persist.

## Impact

One re-plan round in phase 4. No effect on the shipped change.
