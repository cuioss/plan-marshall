# An ADR task paired with a spec in one deliverable trips the module-mapping Q-Gate; plan the mapping up front

## What happened

Deliverable 2 of plan token-sheriff-dpop-htu-backchannel held a spike spec (`DpopBackChannelOriginSpecIT`, module `token-sheriff-quarkus-integration-tests`) and the ADR that records its evidence (`doc/adr/0015-...adoc`, module `documentation`).

The phase 4-plan module-mapping validator pairs a `module_testing` task with the `implementation`-profile tasks of the same deliverable and flags them when the modules differ. It flagged the pair twice:

- Finding `4aadda` (first plan): spec and ADR in one deliverable, different modules.
- The re-plan split the ADR into its own task. That did not help: an ADR task can only carry profile `implementation` (the task contract accepts only `implementation`, `module_testing`, `verification`), so the pairing stayed. Finding `f0d2a1` (re-validation) flagged it again.
- The operator then accepted `f0d2a1` as intentional. Cost: one extra re-plan, one extra validation run, and the plan waited for the operator from 2026-10-18T21:03Z to 2026-10-19T05:13Z.

## Rule

When a deliverable pairs a test or spec with documentation that only records its result (ADR, evidence doc):

- Re-profiling or splitting the doc task does not clear the finding. Do not spend a re-plan on it.
- Decide at outline time instead. Either put the ADR in a deliverable that has no `module_testing` task, or add a row to `doc/developer/test-impl-mapping.adoc` (the validator's documented escape; the file does not exist yet in this repository) as a step of the ADR task.
- If neither is done, expect the finding and resolve it as accepted with that reason on the first validation, not after a re-plan.

- Work log: tasks removed and re-created at 2026-10-18T20:46Z to 20:56Z; second validation completed 21:03:46Z.
