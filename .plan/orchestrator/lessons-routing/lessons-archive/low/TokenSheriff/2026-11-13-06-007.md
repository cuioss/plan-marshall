# fetch_findings self-response-loop guard fires on a bot's in-place-edited summary comment

The `github_pr fetch_findings` self-response-loop guard must check whether any actionable finding is still pending, or whether the only reviewer activity is an in-place edit of a bot summary comment, before it escalates. An edit-only bump on a bot summary comment is not a new cycle.

## What happened

In plan validation-public-seams (PR #899), `fetch_findings` reached `count_self_response_current_cycle=3` (bound 3; `count_skipped_self_response=4` over the PR history) and raised an operator-decision finding (qgate d803c2). The loop was not real: CodeRabbit edits its summary comment in place, so each pass looked like reviewer activity with no new reviewer comment, and the guard counted the plan's own replies as a non-converging cycle. Every reviewer thread was answered, 0 pr-comment and sonar findings were pending, CodeRabbit's review covered head 2c167f4e and CI was green; the operator accepted it as benign.

## Rule

Escalate only when an actionable finding is pending; do not count an in-place edit of a summary or review-status comment as reviewer activity.
