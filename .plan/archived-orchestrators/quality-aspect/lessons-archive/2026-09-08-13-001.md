# archive-plan is the one finalize step whose own completion record can be silently lost, with nothing downstream to catch it

## What happened

On the `remediate-user-facing-sites` finalize run the dispatcher reached the terminal manifest step `default:archive-plan`. The step was executed as `manage-status archive` first and `mark-step-done` second — the inverse of the order `standards/archive-plan.md` mandates. The archive succeeded and moved the plan directory to `.plan/local/archived-plans/2026-09-08-remediate-user-facing-sites`. The subsequent `mark-step-done` then failed with `error: file_not_found / status.json not found`, because `status.json` had already left `.plan/local/plans/{plan_id}/`.

Net result: the plan is validly complete (the archive path runs `_invariants.assert_finalize_findings_clean`, which passed), but the archived `status.metadata.phase_steps["6-finalize"]` map is missing its `archive-plan` row. 22 of 23 manifest steps carry a record; the 23rd does not, and the record can never be added because its store is gone.

## Why it matters beyond one operator slip

`archive-plan` is structurally unique among finalize steps: it is the only one that **destroys the store into which its own completion record is written**. Every other step's record is verifiable afterwards — the `phase_steps_complete` handshake invariant re-reads `phase_steps` at the next boundary and refuses to advance on a missing row. `archive-plan` sits at `order: 1100`, the terminus of the banded allocation contract, so there is no next boundary. Nothing downstream ever reads the map again.

That combination means the failure mode is **silent by construction**:

- `manage-status archive` does not require, check, or even observe the step's own `mark-step-done` record. It archives a plan whose `archive-plan` row is absent exactly as readily as one whose row is present.
- The `mark-step-done` that fails afterwards returns `status: error`, but per the exit-code convention the wrapper still exits 0, so an inattentive dispatcher reads no signal at all.
- The archived artefact is the only surviving evidence, and it records the absence rather than the error.

`standards/archive-plan.md` states the ordering constraint clearly and explains it correctly ("This MUST happen BEFORE the archive call below, because archive moves `status.json` ... and any subsequent `mark-step-done` call would fail to locate the plan"). The document is not at fault. The gap is that the constraint is **prose-enforced only** — a step that is documented as un-reorderable but is not mechanically prevented from being reordered, on the one code path where reordering leaves no trace.

The same reasoning applies to the Pre-Archive Foreign-PR Landing Gate, which the same inverted execution skipped. It happened to be a no-op here (all three deliverables were in-repo, so the gate would have returned `status: clear`), but a run with a foreign deliverable would have archived past a `pushed_no_pr` block with no record that the gate was never consulted.

## Proposed remedy

Move the invariant out of prose and into `manage-status archive`, where it is unskippable:

1. `archive` reads `status.metadata.phase_steps[current_phase]` before moving anything, and refuses (`status: error`, a named error code such as `terminal_step_unrecorded`) when the terminal step named in the manifest is absent from the map. This makes the ordering constraint self-enforcing: an operator who archives first is stopped by the archive itself rather than by a post-hoc error against a store that no longer exists.
2. Alternatively — or additionally — give `archive` an `--archive-step` flag that lands the terminal step's record and performs the move in one atomic operation, removing the two-call sequence whose order is the entire hazard.

Option 1 is the smaller change and closes the silence; option 2 removes the hazard class outright.

## Detection

Any archived plan whose `phase_steps["6-finalize"]` lacks a row for the terminal step named in its own `execution.toon` `phase_6.steps` list was archived out of order. This is a cheap retrospective scan over `.plan/local/archived-plans/` and would establish whether the defect has recurred previously or is a first observation.
