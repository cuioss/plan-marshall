# Never post "fixed" on a review thread before the fix commit exists

## Context

On PR #1704 of plan `plan-pr-078-review-bot-fleet-opt-in`, the unified triage dispatch (`plan-marshall/workflow/verification-feedback.md`) handled four CodeRabbit findings. It edited seven files in the worktree to fix three of them, then ran `post_responses`, which posted "Fixed in a follow-up commit on this branch" on all three inline threads and resolved them. At that moment nothing was staged or committed and no build or test had run; the leaf said so in its return ("The follow-up commit does not exist yet. If verify fails or the edits are dropped, those three replies are wrong and the threads need reopening"). The orchestrator then ran `verify`; the first run timed out and a second passed about 25 minutes after the replies were posted, and the fix commit followed.

## Root cause

Two things combined. The leaf was told by the orchestrator to fix inline and return a `commit_message`, which departs from `triage.md` (FIX allocates a fix task and stops, leaving no uncommitted edits). And RESPOND runs inside the same dispatch as the inline edits, ahead of the commit and the verify that only the orchestrator can run, so the public statement is made before the fact it asserts.

## Proposed action

- Order RESPOND after the fix commit has landed and the verify build is green; a `fixed` disposition is transmitted only with the commit SHA it refers to.
- If the inline-fix path stays, have the triage dispatch return its dispositions untransmitted and let the orchestrator call `post_responses` after the commit, or post a neutral "addressing in a follow-up commit" reply and resolve the thread only once the commit exists.
- Document the inline-fix variant in `triage.md` if it is sanctioned, so a leaf does not have to choose between the workflow doc and the dispatch instruction.
