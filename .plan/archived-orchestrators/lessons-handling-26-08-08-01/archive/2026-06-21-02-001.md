# phase-3-outline mandated an edit to a symbol a prior shipped plan had already removed (_FINALIZE_STEP_PARAMS); outline did not verify the target API still existed, forcing phase-5 to mark the task infeasible

## Context

During `merge-lock-queue-wait` (the FIFO merge-queue-wait plan, PR for
`branch-cleanup.md`'s Pre-Merge Gate), phase-5-execute **TASK-3 returned
`status: infeasible`**. The solution outline's D2 design note instructed the
executor to edit `_FINALIZE_STEP_PARAMS['default:branch-cleanup']` in
`marketplace/bundles/plan-marshall/skills/.../scripts/_config_defaults.py` to add
a new step param — but **that centralized constant no longer exists**. It was
removed by the already-shipped `config-schema-step-nested-params` plan (PR #716),
which moved step-owned finalize params out of one central dict and into each
step's own `configurable:` frontmatter.

The executor could not perform the mandated edit (no such symbol), correctly
declined to silently substitute a different target, and returned `infeasible`. The
orchestrator re-scoped TASK-3 to the live mechanism — `branch-cleanup.md`'s
`configurable:` frontmatter, surfaced via
`configurable_contract.resolve_step_defaults_optional` — and the plan completed.

## The defect

phase-3-outline authored a design note that **mandated an edit to a named API
surface (`_FINALIZE_STEP_PARAMS`) that a prior shipped plan had already deleted**,
without verifying the symbol still existed in the live tree before writing the
mandate. This is *not* CLI-shape invention from memory (the symbol genuinely
existed historically); it is an outline written against a **stale-but-real** API
that a sibling plan retired between when the outliner last knew the codebase and
when the outline was authored.

Symptom signature:

- A solution-outline deliverable / design note names a specific symbol, constant,
  dict key, or function (e.g. `_FINALIZE_STEP_PARAMS['default:branch-cleanup']`)
  as the edit target.
- phase-5 execution finds the symbol absent and returns `infeasible` (or, worse,
  silently substitutes an adjacent target — the no-silent-substitution contract is
  what made this surface cleanly rather than corrupt).
- A `git log` / grep shows the symbol was removed by an earlier, already-merged
  plan; the outline referenced the pre-removal shape.

## Root cause

phase-3-outline treated a remembered API surface as still-current and wrote a
hard edit mandate against it without a cheap existence check. The centralization
that PR #716 dismantled (`_FINALIZE_STEP_PARAMS` central dict → per-step
`configurable:` frontmatter) is exactly the kind of structural refactor that
invalidates a remembered symbol name while leaving the *concept* (step-owned
params) intact — so the outline's intent was right but its named target was dead.
The outline lane that mandates a concrete edit owes a verify-the-target step the
same way a call site owes a verify-the-flag step.

This is the **outline-time, structural-refactor facet** of the broader
stale-API-surface family. It is distinct from:

- `2026-06-20-12-001` (phase-4-plan / call-time **CLI-shape invention from
  memory**) — there the wrong shape never existed; here the target existed and was
  *removed*. Different phase (phase-3-outline vs phase-4/call-time) and different
  mechanism (stale-real-symbol vs invented-symbol).
- `2026-06-21-01-001` / `2026-06-21-00-002` (frozen-manifest / step-key
  divergence) — those are about manifest-vs-`marshal.json` surfaces, not outline
  edit targets.

## How to apply

- **When a phase-3-outline design note mandates a concrete edit to a named symbol,
  constant, dict key, or function, verify the target still exists in the live tree
  before writing the mandate.** A one-line `grep`/`architecture find` for the
  symbol name is the cheap pre-check — if it returns zero hits in source (only
  docs/prose), the outline is referencing a removed API and must re-scope to the
  current mechanism.
- **Treat a recently-shipped structural refactor as a stale-symbol risk.** When the
  outline's edit target lives in an area a sibling plan recently centralized,
  nested, renamed, or split (here: PR #716's central-dict → per-step-frontmatter
  move), assume the remembered symbol may be dead and confirm the current
  mechanism (`configurable:` frontmatter +
  `configurable_contract.resolve_step_defaults_optional`) before mandating the
  edit.
- **A phase-5 `infeasible` return whose detail names a missing edit target is the
  signature** of this outline-authoring gap — the fix is to re-scope the outline's
  mandate to the live API, not to re-add the deleted symbol. The
  no-silent-substitution contract (PR #724) is what converts this from a silent
  corruption into a clean, attributable `infeasible` signal; honour it.

## Impact

An outline that mandates an edit to a removed symbol costs a full phase-5 task
dispatch that can only return `infeasible`, plus an orchestrator re-scope round
trip, before the plan can proceed. The cost is bounded (the no-silent-substitution
contract prevents corruption), but it is avoidable: a symbol-existence pre-check at
outline-authoring time keeps the deliverable→task→edit chain anchored to the live
API surface instead of a remembered one.

## Recurrence — 2026-06-21 (finish-portability-gaps-implementation, TASK-5 / Gap 1)

A second, complementary facet of the same outline-vs-live-tree gap, where the
target did **not** go missing — it was **already present**, and the outline
**inverted the premise of the work**. During `finish-portability-gaps-implementation`
(PR #739), phase-5-execute TASK-5 (Gap 1, permission tooling) was
**infeasible-blocked** at a mid-execute orchestrator planning gate, then re-scoped
by a user decision. The stored deliverable mandated two things that contradicted
the live architecture:

1. **Add ops that already existed.** The outline asked the executor to ADD five
   low-level permission CRUD ops (`read_settings` / `write_settings` /
   `list_permissions` / `add_permission` / `remove_permission`) to
   `claude_runtime.py`. But `claude_runtime.py` **already implemented** the seven
   high-level permission ops (`permission_configure` / `analyze` / `fix` /
   `ensure_wildcards` / `ensure_steps` / `web_analyze` / `web_apply`) with real
   `.claude/settings` I/O. Adding the five low-level ops would have **duplicated**
   the existing seven-op mechanism — the infeasible premise.
2. **Reversed dependency direction.** The deliverable framed the work as "give the
   runtime the settings ops"; the real seam was the inverse — the runtime already
   owned the ops but **back-imported its path-resolution + load/save helper bodies
   FROM the scripts** (`permission_common.get_project_settings_path_for_write` /
   `load_settings_path`, `permission_doctor.skill_permission_covered`). The actual
   fix was to relocate those helper bodies INTO the runtime and make the four
   permission scripts thin delegators — the opposite direction to the one the
   outline described.

So the outline's edit target was not *missing* (the removed-symbol facet above);
it was **already done**, and the stated direction of work was **backwards relative
to the live module graph**. The executor could not satisfy a deliverable whose
premise was already satisfied + inverted, the infeasible signal fired, and the
orchestrator + user re-scoped TASK-5 to the real seam (eliminate the runtime→script
back-import; relocate helper bodies; thin-delegate the scripts; give OpenCode a real
backend or honest no-op stubs). The re-scoped task then completed cleanly (7/7).

**Why this is the same lesson, broadened:** identical component (`phase-3-outline`),
identical root cause (an outline edit-mandate written against a *remembered* view of
the codebase rather than the *current* one), identical downstream signal (phase-5
`infeasible` → orchestrator re-scope, surfaced cleanly by the no-silent-substitution
contract). The original facet was "verify the target still **exists**"; this facet
adds "verify the work isn't **already done** and the **dependency direction is
correct**." Both reduce to the same discipline: an outline that mandates a concrete
structural edit owes a check of the **current** state of that area — symbol presence,
work-already-shipped, and import/ownership direction — not just a recollection of how
it once looked.

**How to apply (added):**

- **Verify current state, not just existence.** Before mandating "ADD op X to module
  M" or "move responsibility from A to B", confirm against the live tree that (a) op X
  is not *already* present in M, and (b) the dependency/import direction you describe
  matches the actual module graph. A `grep`/`architecture find` for the op name and a
  quick read of the existing import edges is the cheap pre-check — the dual of the
  symbol-existence check above.
- **A re-scope toward "the mechanism already exists; only the seam differs" is the
  signature** of this inverted-premise facet — distinct from the removed-symbol facet
  (re-scope toward a *renamed/relocated* target). In both, the remedy is to anchor the
  mandate to the live architecture, never to force the outline's stale premise.

## Recurrence — 2026-07-17 (metrics-corpus-integrity)

A third facet of the same outline-vs-live-tree gap, this time the target was
neither missing nor already-done — it was **unshippable**. The solution outline
for `metrics-corpus-integrity` scoped a docs-only deliverable (a corpus caveat)
that mandated edits to `.plan/plan-optimization/01`, `.plan/plan-optimization/02`,
and `.plan/temp/token-analysis/gen.py`. Those paths are all matched by
`.gitignore:41` (`.plan/*`) — they are **local-only artifacts, absent from the
plan worktree's tracked tree, and cannot be committed or shipped through the
normal PR flow**. phase-5-execute correctly returned `infeasible` for the task,
and the operator dropped the deliverable rather than force a workaround.

Unlike the removed-symbol facet (target existed once, then vanished) or the
already-done facet (target existed in a different form), this facet's target
**never lived in the tracked tree at all** — it was excluded by design via
`.gitignore`. The verification gap is therefore not "does the symbol/API still
exist" but "is the edit target git-tracked and hence PR-shippable."

**Why this is the same lesson, broadened again:** identical component
(`phase-3-outline`), identical downstream signal (phase-5 `infeasible` →
operator re-scope/drop, surfaced cleanly by the no-silent-substitution
contract), identical root defect (an outline mandate written without checking
the *current, real* state of the target — this time its git-tracked status
rather than its existence or completion state).

**How to apply (added):**

- **When a phase-3-outline design note mandates an edit to a file path (docs,
  config, generated artifact), verify the path is git-tracked** — i.e. not
  matched by `.gitignore` — before locking scope. A cheap `git check-ignore
  {path}` (or an `architecture find` / `git ls-files` check) against the path
  is the pre-check: if the path is gitignored, the deliverable cannot ship via
  the normal PR flow and must be re-scoped (e.g. to a tracked doc, or dropped
  entirely) before phase-4-plan allocates a task against it.
- **A phase-5 `infeasible` return whose detail names a gitignored/untracked
  target is the signature** of this facet — distinct from the removed-symbol
  facet (re-scope to a renamed/relocated target) and the already-done facet
  (re-scope to the real seam): here the remedy is to drop or redirect the
  deliverable to a tracked file, since no live-tree equivalent exists to
  re-scope onto.
