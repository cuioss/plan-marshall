# Config docs and Javadoc promise fail-fast or replacement behaviour the code or its guard conditions do not give

## Problem

In plan-08 (PR #850) the code and its documentation diverged three times on the same configuration feature, each caught only by a review loop-back: the operator config doc listed the JWE multi-key property without its required `.path` leaf and omitted the new fail-fast rules; the Javadoc and a doc NOTE promised a startup failure for a bare `decryption-keys.<kid>` value that the code still ignored; and the NOTE claimed partial JWE configuration "fails at application startup" although `TokenValidatorStartupInitializer` resolves it only when at least one issuer is enabled. A fourth case: the `@DefaultBean` Javadoc said any application bean of the type replaces the default, which is wrong for a bean with a custom qualifier.

## Solution

A deliverable that changes validation rules or the property shape of a configuration feature updates the operator config doc rows and notes for that feature in the same deliverable. Before documenting a startup-time guarantee, find the code path that triggers it and state the conditions that guard it. Every case a doc enumerates as "fails at startup" or "is rejected" gets its own negative test. For a `@DefaultBean` producer, state that only an unqualified (or `@Named`-only) bean replaces it and add a custom-qualifier negative case to the replacement test.

## Impact

Each divergence cost a code-review loop-back through finalize, and one needed an operator scope exception because the fix touched rows outside the deliverable's declared scope.

## Recurrence - 2026-11-05 (plan-22-residual-docs-tests-adrs)

Plan-22 (PR #863) hit the same defect class again in ADRs and Javadoc of the client and validation modules: wording that restates what the code guarantees without the exact code condition behind it. Over-claiming words (every, always, unchanged, cleared, dropped, fails closed) were the dominant defect class across nine finalize review rounds, not only for configuration docs.

Examples, each tied to the code condition the wording must name:

- `clearRefusedSession` compares the refresh token only and has no recency check, so "a re-login stored a newer grant" is not what the compare-and-set tests.
- `revokeAndClearFailClosed` catches only `TransportException`, so a throwing revoke or remove replaces the original refusal; "rethrown unchanged" holds only when neither throws.
- Revocation needs an advertised revocation endpoint; without one the clear is the only step.
- The clear is attempted, not guaranteed: "quarantined / cleared fail-closed" needs "attempted".
- ADR-0021 check order, ADR-0020 iat-less rationale, ADR-0005 rotation family and the TokenValidator.close() Javadoc Throwable scope were all narrowed to the scope the enforcing code gives.

Additional rule: when documenting a guarantee, name the exact condition (method, exception type, configured prerequisite) in the sentence, and enumerate the paths from the code first (see lesson 2026-11-05-23-007: a "covers every path" claim hid a real fail-open in `doRefresh`). Fix the wording as one sweep per statement shape (lesson 2026-11-05-23-001).
