# Review findings fixed in-PR took six fix tasks and several finalize loop-backs; a second review pass found what the first missed

- Component: pm-workflow (plan instance header, composition rules, instance store); process: plan-marshall:phase-6-finalize
- Suggested category: improvement
- Signal: plan-24-plan-instance, automatic review (6 fixed pr-comment findings in the last round, 140 findings in total)

## Observation

The review findings of PR #67 were fixed in the PR itself. That took six fix tasks (TASK-16 to TASK-21) and
several finalize loop-backs. The triage budget was spent (3 of 3) and the code-review step granted 2 more
rounds. The rounds were driven by two things.

1. **A defect found only on the second review pass.** `HeaderJson.intValue` called `toBigIntegerExact()` on a
   header number such as `1e999999999`. The value is short, so the number-length limit of the JSON parser does
   not refuse it, and the schema check accepts it as an integer of at least 1. The conversion then tries to build
   a value of about a billion digits and hangs or runs out of memory. The first pass did not report it. The PR
   description even listed the missing exponent range check as known. A second pass reported it, and the fix
   (TASK-16) bounded the magnitude before the conversion.
2. **A write-once race found by CodeRabbit.** `PlanInstanceStore.recordComposed` checked `exists(versionPath)`
   before staging. Two `ScopeTransaction`s from one `LockTransaction` both passed the check, and the second
   commit moved its staged file over the first version. The fix (TASK-20, documented in TASK-21) moved the
   check to commit time (`ScopeTransaction.create` refuses when the version file exists).

The other findings of the last round were smaller: a Mermaid front matter title that was not escaped, a request
whose event and `post_run` fact could disagree, a budget-argument set copied from the remediation schema, and an
ADR that promised a guarantee the public constructor did not give.

## Suggested correction

- A defect the PR description lists as known and "local" is fixed before the PR is opened. A known gap in the
  description is a finding the bots will report anyway.
- A check-then-act on a store (`exists` then `replace`) is a race unless the check runs inside the commit. Ask
  for the write-once or uniqueness guarantee at the commit step in the outline, with a test that opens two
  transactions on one lock.
- Numbers read from untrusted input are bounded in magnitude before any exact conversion
  (`toBigIntegerExact`, `BigInteger` arithmetic), including exponent forms.
- Plan one explicit second review pass over the new parsing and store code before the first push, so the
  second-pass finding arrives before the PR and not as a loop-back.
- Budget the finalize rounds: a plan that adds a new parser plus a new store should expect more than the default
  triage budget and say so up front.
