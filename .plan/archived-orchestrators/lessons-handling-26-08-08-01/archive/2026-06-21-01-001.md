# Self-modifying plan that removes a finalize step's standards file leaves its own composed-at-outline execution.toon referencing the deleted step; validate-loadable fails until the per-plan manifest is recomposed

## Context

This plan (`whole-tree-gate-deleted-symbol-detection-must-be`) retired the
`whole_tree_gate` phase-6 finalize step and folded its F1 check into
`finalize-step-plugin-doctor`. Retiring the step meant **deleting its standards
file** (the workflow doc that `phase_6.steps` references) AND removing it from the
global finalize candidate set in `marshal.json` via
`manage-config remove-step`.

At finalize entry, phase-6-finalize's loadability check
(`manage-execution-manifest validate-loadable` — "Verify standards-file presence
for `phase_6.steps` entries") **failed**, because the plan's own per-plan
execution manifest (`execution.toon`) still listed the now-deleted
`whole_tree_gate` step. The check correctly reports a missing standards file for a
step the manifest still claims to run.

## The defect

A self-modifying plan that **removes a finalize step it itself traverses** creates
a temporal/propagation gap between two distinct surfaces:

- **Global candidate set** — `marshal.json` `plan.phase-6-finalize.steps`, mutated
  in-plan via `manage-config remove-step`. This is the live, mutable source for
  *future* plans' manifest composition.
- **Per-plan execution manifest** — `execution.toon`, composed **once at outline
  time** (`manage-execution-manifest compose`) and then **frozen** for the life of
  the plan. The phase-6-finalize dispatcher reads the step set from THIS frozen
  manifest, not from `marshal.json`.

`manage-config remove-step` mutates only the global candidate set. It does **not**
reach back into already-composed per-plan manifests. So the plan that performs the
removal still carries the deleted step in its own `execution.toon`, and
`validate-loadable` fails at finalize entry on the missing standards file.

Symptom signature:

- A plan deletes (or renames) a finalize step's standards/workflow file as part of
  its own deliverables.
- The same plan removes that step from `marshal.json` via `manage-config
  remove-step`.
- At phase-6-finalize entry, `manage-execution-manifest validate-loadable` reports
  a missing standards file for the deleted step — because the plan's own
  `execution.toon` (composed at outline time, before the deletion) still lists it.

## Root cause

`execution.toon` is composed once at outline time and is authoritative for the
plan's finalize run; `marshal.json` is the live candidate set for *future* plans.
The two are deliberately decoupled (the freeze gives the plan a stable manifest to
execute against — see the manifest-vs-marshal.json divergence also noted in lesson
`2026-06-21-00-002`). But that decoupling means a self-modifying plan's own
removal of a step does not propagate to the frozen manifest it will finalize
against. The candidate-set mutation is forward-looking; the plan's own manifest is
already cast.

## How to apply

- **When a plan deletes/retires a finalize step's standards file AND removes the
  step from `marshal.json`, it MUST also recompose its OWN per-plan manifest** so
  `execution.toon` no longer references the deleted step. Re-run
  `manage-execution-manifest compose` for the plan after the `remove-step`, before
  reaching the phase-6-finalize loadability check. The candidate-set removal alone
  is insufficient for the self-modifying plan.
- **Treat a `validate-loadable` failure on a step the plan itself deleted as the
  signature of this gap** — the manifest is stale, not the deletion wrong. The fix
  is recompose-own-manifest, not re-adding the standards file or skipping the
  loadability check.
- **Fold the own-manifest recompose into the plan at outline/plan time** for any
  plan whose deliverables retire a finalize step. The step-set change has a
  blast radius that includes the plan's own frozen manifest — exactly the surface
  the composed-at-outline freeze hides from a naive candidate-set edit.

## Impact

Without the own-manifest recompose, every plan that retires a finalize step it
traverses blocks its own finalize at the loadability gate until the manifest is
manually recomposed. The mutation tooling (`manage-config remove-step`) is
correct — it scopes to the global candidate set by design — so the durable
remediation is a plan-authoring discipline (recompose own manifest after
removing a step), or a `remove-step`-time hook that also recomposes the manifest
of the still-active plan performing the removal.

## Recurrence — 2026-07-13 (plan-16-step-key-hygiene)

The **mirror direction** of the same seam — step ADDITION, not removal. This plan
(`plan-16-step-key-hygiene`) **registered a NEW finalize step**
(`project:finalize-step-era-stamp-fill`, D3a) in `marshal.json` during phase-5,
intending its own D6 self-stamp to run at this same plan's finalize. It never ran:
the plan's per-plan execution manifest (`execution.toon`) was composed at
phase-4-plan — **before** the phase-5 registration existed — so the newly-registered
step was absent from the frozen manifest, and the phase-6-finalize dispatcher
(which reads the step set from the frozen manifest, NOT from `marshal.json`) never
scheduled it. A step a plan registers during phase-5 cannot self-schedule at that
same plan's finalize.

Same root cause as the removal case above: `manage-config` step-set mutations are
**forward-looking** — `add-step` just as much as `remove-step` — changing the
global candidate set for *future* plans without reaching back into the mutating
plan's own already-frozen `execution.toon`. The two directions differ only in how
they surface:

- **Removal → fails LOUD**: `validate-loadable` reports a missing standards file
  for a step the frozen manifest still lists.
- **Addition → fails SILENT**: the self-registered step simply never runs; there is
  no error, the D6 self-stamp could not self-schedule, and only an audit notices
  the omission.

**Broadened remediation**: ANY plan that mutates its own phase-6 step-set
(`add-step` OR `remove-step`) and expects the change to take effect at its OWN
finalize MUST recompose its own per-plan manifest (`manage-execution-manifest
compose`) after the mutation, before phase-6-finalize reads the frozen manifest.
The silent-skip variant is the more dangerous of the two because no gate fires —
fold the own-manifest recompose into the plan at outline/plan time whenever a
deliverable registers or retires a finalize step it intends to self-run.

## Recurrence — 2026-07-13 (plan-7-execute-task-tests)

A THIRD occurrence of the same silent-skip variant, same day, different plan —
confirming this is a structural gap in the manifest-composition timing model, not
a one-off authoring slip. `project:finalize-step-era-stamp-fill` had been
registered as a global finalize-step candidate by an earlier-merged PR (#885,
landed on `main` after this plan's own `execution.toon` was composed at
phase-4-plan). Because this plan's manifest was frozen before that registration
existed, `finalize-step-era-stamp-fill` was absent from `phase_6.steps` at
finalize time, and the phase-6-finalize dispatcher never scheduled it.

Recovery here was manual and in-band: the finalize dispatcher noticed the gap and
ran `project:finalize-step-era-stamp-fill` **inline, off-manifest**, at its
designed order-21 slot, resolving the D4 `PR-PENDING` era-stamp sentinel and
committing/pushing the result so it still rode the same PR. This shows the
addition-mirror gap is not limited to a plan registering its OWN new step
(plan-16's case) — it equally hits any plan whose manifest freezes BEFORE an
unrelated, already-merged PR's new global step registration lands, making the
frozen-manifest staleness risk broader than "self-registered steps only": any
step newly added to the global candidate set between a plan's phase-4-plan
manifest-compose and its own phase-6-finalize entry is invisible to that plan's
run, regardless of which plan registered it.

**Further-broadened remediation**: the phase-6-finalize dispatcher (or an earlier
finalize-entry step) should diff the plan's frozen `phase_6.steps` against the
CURRENT `marshal.json` candidate set at finalize-entry time and flag/backfill any
step present in the live candidate set but absent from the frozen manifest —
not only rely on plan-authoring discipline to recompose after a step-set mutation
the plan itself performed, since staleness can also originate from an unrelated,
concurrently-merged plan's step registration.
