# change_type is read from the first deliverable so a discovery-first plan under-reports its own risk

## What happened

The finalize ceremony pre-filter silently dropped `finalize-step-security-audit` from a plan whose
delta touched **47 files**. The drop was **correct by code and wrong by intent**: the gate's
`change_type` leg read a value that described only part of the plan.

`phase-4-plan` derives `change_type` from the **first deliverable**. A plan that opens with a
read-only discovery or verification deliverable therefore reports `change_type: verification`
however much code its later deliverables mutate. The security gate consulted that value, found
"verification", and dropped the audit.

⭐ The plan that fixed this **reproduced the defect on itself**: its own phase-4 `execution.toon`
carried `security_audit_omitted=true` and dropped the security audit from its own finalize, despite
an operator-chosen full posture. Re-composing against the fixed composer restored it (23 → 24 steps).

The fix removed the `change_type` leg from **one** gate. The mis-scoped read itself is still live
everywhere else `change_type` is consumed — including `finalize-step-simplify`'s `simplify_inactive`
gate, which retains the same defect.

## Why it matters

This is not a wrong value. `change_type` was computed exactly as specified; the specification takes a
**part for the whole**. That makes it invisible to every check that validates the value's derivation,
because the derivation is faithful — only its *scope* is wrong.

A scope error in a summary field is uniquely dangerous because the field is consumed far from where
it is derived. Each consumer reasonably treats it as describing the plan. Nothing at the consumption
site can tell that it describes deliverable 1.

The failure mode is **silent omission of a safety step**, which produces no error and no missing
output — just an absent audit that nobody was told to expect.

## How to apply

- **A plan-level field must be derived from the whole plan.** If a field is named for the plan
  (`change_type`, `affected_files`, `risk`), deriving it from any single deliverable is a scope bug
  regardless of how correct the per-deliverable read is.
- Where a whole-plan derivation is genuinely unavailable, **fail toward inclusion**: drop a
  protective step only when *every* signal says it is unnecessary, never when *one* summary says so.
  The shipped gate now drops only when the declared affected files AND the live footprint are **both**
  empty.
- **Derive a protected population, do not enumerate it.** The fixed gate takes membership from the
  step's frontmatter (`persona: persona-security-expert`) rather than a hardcoded step id, so a future
  security-class step is protected the day it is added.
- **Make the drop loud.** A boolean `security_audit_omitted` became
  `security_class_omitted: [{step, reason}]` plus a `[STATUS]` decision-log line. An omission that
  used to be invisible now has to be read past.
- ⛔ **When you remove a mis-scoped read from one consumer, enumerate the others.** Fixing the gate
  that surfaced the bug leaves every other consumer of the same field defective, and the surfacing
  gate is the one place you now know is safe.
