# Gate 2 of lesson creation cannot read a worktree-resident plan's scope from the main checkout

## Context

`manage-lessons/standards/lesson-creation-policy.md` Gate 2 requires, before any lesson is
filed, that the candidate's component + root cause be compared against **each active plan's
request scope**, folding the observation into a covering plan instead of filing a standalone
lesson. `plan-retrospective/references/lessons-proposal.md` § "Gate 2" prescribes
`manage-status list` for the enumeration.

Running that gate from the main checkout during plan
`misconfigured-reviewer-name-reads-missing-review`'s finalize:

```text
manage-status list            -> 5 plans, 3 marked location: worktree
manage-plan-documents request read --plan-id shipped-guards-…
                              -> status: error / error: document_not_found
```

The enumeration verb is cross-checkout-aware and reports exactly where each plan lives. The
`manage-plan-documents` read a Gate 2 comparison needs is not, and it carries no `--any-checkout`
escape of the kind `manage-findings` declares on its five read verbs for precisely this
situation. Gate 2 was therefore executed against **2 of 5** active plans.

Two of the three unreadable plans were plausibly relevant:
`shipped-guards-assume-the-meta-projects-own-layout` (a guard assuming this repository's layout
— arguably the family of one candidate) and `planning-lane-change-type-scope-execution-manifest`
(same skill as another candidate, apparently a different surface). Neither overlap could be
resolved; both were filed with a named `possible_overlap` flag instead.

## Root cause

`plans/{plan_id}/` moves into its worktree at phase-5 (ADR-002) and back at finalize, so a
running plan's directory is genuinely absent from the main checkout. `manage-findings`
recognised this and added the four-state store discriminator plus `--any-checkout` on its reads;
`manage-plan-documents request read` still returns a bare `document_not_found`, which is
shape-identical to "no such plan".

That indistinguishability is the defect, not the absence itself. A caller following Gate 2
literally gets a per-plan `file_not_found`, has no signal that the gate was partial, and reports
a clean "no covering plan found" over a population it could not read — the same
could-not-look-reports-benign collapse `manage-findings` `findings_store_state` exists to close.

## Proposed action

1. Widen `manage-plan-documents request read` to resolve through the same
   `git-workflow locate-plan-checkout` verb `manage-findings` uses. Reads only — no write verb
   takes the fallback, per that skill's stated guarantee.
2. Until then, make its refusal legible: when `manage-status list` can see the plan at
   `location: worktree` but `request read` cannot reach it, return a distinct error naming the
   checkout that holds it, rather than a bare `document_not_found` whose `suggestions[]`
   recommend creating a document that already exists elsewhere.
3. Have the Gate 2 step in `lessons-proposal.md` publish a coverage figure —
   `scopes_readable` / `active_plans_enumerated` — so a partial gate is visible in the report
   instead of presenting as a completed one. This retrospective did that by hand; it should not
   depend on the analyst noticing.

## Recurrence — 2026-09-13 (the-foreign-gate-population-and-branch-f-recovery)

Reproduced unchanged, ten days on, during this plan's own retrospective:

```text
manage-status list                                        -> 6 plans, 4 marked location: worktree
manage-plan-documents request read --plan-id plan-truth-139 --section title
                                                          -> status: error / error: document_not_found
                                                             suggestions: ["Create the request document first",
                                                                           "Check plan_id spelling"]
```

Gate 2 was executed against **2 of 6** active plans. The four unreadable ones —
`plan-pr-046`, `plan-truth-103`, `plan-truth-127`, `plan-truth-139` — are all
`location: worktree`, and all four are themselves in `6-finalize`, so each is precisely the kind of
live plan a covering-scope check most needs to see.

Two observations this recurrence adds:

- **The error text actively misleads, beyond being indistinguishable.** The original filing noted
  that `file_not_found` is shape-identical to "no such plan". The `document_not_found` return goes
  further: its `suggestions[]` propose *"Create the request document first"* and *"Check plan_id
  spelling"* for a plan whose id was copied verbatim from `manage-status list` one call earlier and
  whose request document certainly exists. A caller following the suggestions would create a
  duplicate request document in the main checkout. Proposed action 2 should therefore be read as
  urgent rather than cosmetic: the refusal is not merely illegible, it recommends a harmful action.
- **Proposed action 3 is still carried by the analyst.** This retrospective again published the
  coverage figure by hand (`readable_from_main_checkout: 2` / `active_plans_total: 6`,
  `status: unevaluable`) and again declined to report Gate 2 clear. That is twice that a correct
  outcome depended on the analyst noticing, which is exactly the dependency action 3 exists to
  remove.

Neither new candidate on this run was dropped for it — both were filed with the gate explicitly
reported `unevaluable` rather than clear — but the gate provided no assurance, and a covering plan
among those four would not have been found.
