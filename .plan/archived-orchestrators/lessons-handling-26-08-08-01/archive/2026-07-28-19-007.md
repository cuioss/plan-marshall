# Markdown under marketplace/bundles/** IS a build input — tests parse SKILL.md bodies, so the proposed doc-only freshness-neutrality exemption is unsafe in this repo

## The constraint

**In this repository, a markdown file under `marketplace/bundles/**` is a first-class build
input.** Tests parse SKILL.md and standards-doc bodies at test time to derive their expected
populations. Editing one of those files changes what the test suite computes, exactly as
editing a `.py` file does.

This is not incidental. It is the direct consequence of the **population-derived detector**
pattern the `test-suite-quality` epic standardised on (`test/_shared/_dispatch_roster.py` and
its descendants): a detector derives its population from the document that declares the
contract, so the document becomes an input to the assertion.

Concrete instances in the tree:

- `test/plan-marshall/phase-6-finalize/test_step_completion_emission.py` parses
  `phase-6-finalize/SKILL.md` to derive its expected emission sites.
- `test/plan-marshall/phase-6-finalize/test_step_termination_contract.py` parses
  `ref-workflow-architecture/standards/agents.md` for the corollary enumeration.
- `test/plan-marshall/plan-retrospective/test_registered_aspects_render.py` parses
  `plan-retrospective/SKILL.md`'s Step-3 aspect table.
- `test/plan-marshall/phase-6-finalize/test_dispatch_roster_closure.py` parses
  `standards/dispatch-inline-split.md`'s two rosters.

## Why this is filed as a constraint, not an observation

`2026-06-20-16-002` (finalize-step worktree mutation vs the freshness gate) proposes, in two
separate recurrence sections, a doc-only exemption:

> "exclude markdown-only diffs from the freshness-relevant SHA, or let the gate short-circuit
> the rebuild when the delta since the stamped build touches only non-compiled paths"

**That fix is unsafe as stated in this repo, and adopting it would ship a real false-green.**
A markdown-only diff under `marketplace/bundles/**` can change test outcomes. Short-circuiting
the rebuild on "markdown only" would certify a tree whose tests were never re-run against the
edit that changed what they assert.

The corrective in `2026-06-20-16-002` remains right in its *shape* — the docs-only footprint
needs a legal green path through finalize — but the discriminator must not be the file
extension. `build_map` (the pending WS-10 PLAN-35 consolidation) is the correct oracle: a path
is buildable when the map says so, not when its suffix looks inert.

## The observing case (PR #1036, PLAN-10)

The plan's `pre-push-quality-gate` completed at `52a9de7d6`. Pre-submission self-review then
filed and fixed a Q-Gate finding, producing a **second commit** `6d51ae704` —
`fix(phase-6-finalize): name the timeout path in the step-completion pairing enumeration`.
That commit edits `phase-6-finalize/SKILL.md`, which
`test_step_completion_emission.py` — a file the same plan had just added — parses at test time.

So a finalize-internal `mutates_source` step changed source that the test suite reads, after
the gate that certified the tree. A "nothing changed since the verify" reconciliation over
that commit would have been factually wrong.

Two things made the trap well-hidden:

1. **The mutating step's own `display_detail` read as a no-op.** `finalize-step-simplify`
   reported "0 edits, 0 findings" while its `head_at_completion` had already advanced to
   `6d51ae704` — the HEAD move came from a *sibling* settle-band step. A reader checking the
   step that reports the new HEAD sees "0 edits".
2. **Doc-shaped edits look non-buildable.** A `.md` under `marketplace/bundles/**` reads as
   documentation, so the reflex is "docs-only, no rebuild needed". In this repo that reflex is
   precisely inverted.

**This run did the right thing** — the build was re-run and CI was green at `6d51ae704`. The
lesson records the trap and corrects the proposed fix; no defect shipped from it.

## Guidance

- **Never use the file extension, or "is it under a docs path", as the buildable/non-buildable
  discriminator.** Use `build_map` as the oracle. Until PLAN-35 lands, the conservative rule
  stands: treat markdown under `marketplace/bundles/**` as buildable.
- **A freshness-reconciliation record is valid only when no `mutates_source` step committed
  between the verify's `head_at_completion` and current HEAD.** When one did, the record is
  void — re-run the build; do not reconcile. Do not weaken this to "re-run only if the changed
  files look buildable".
- When reading a settle-band HEAD advance, attribute it to the step that **committed**, not to
  the step whose `head_at_completion` first reports the new value. Those are routinely
  different steps, and the reporting one may honestly say "0 edits".
- Applies to every finalize run in which a settle-band `mutates_source` step
  (pre-submission-self-review, simplify, security-audit, plugin-doctor, era-stamp-fill)
  produces a commit after `pre-push-quality-gate` — the majority of non-trivial plans.
