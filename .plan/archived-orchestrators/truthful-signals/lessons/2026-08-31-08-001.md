# A probe that reads only one stream reports absent for a message it never looked at

# A probe that reads only one stream reports "absent" for a message it never looked at

## The archetype

A diagnostic reads **one** of a subprocess's output channels — or only its return code — and
reports a conclusion the other channel would have contradicted. The result is not a wrong
answer to the right question; it is a confident answer to a question the probe never asked.

## Two instances, observed the same day, in unrelated components

1. **`script-failure-analysis` reads only `stderr`.** An executor rejection whose explanatory
   note is written to `stdout` therefore reads as *no note at all*, and the analysis reports an
   unexplained failure over a failure that explained itself.
2. **`ci_base.check_auth_cli` reads only the return code.** It runs `gh auth status` as
   `returncode, _, _ = run_fn([...])` and maps **any** non-zero exit to
   `error_cause: auth_failed`, discarding both streams. Because `gh auth status` validates the
   token over the network, a transient network failure is indistinguishable from "not
   authenticated" — and the consumer is correctly fail-closed, so a false `auth_failed` turns a
   fully successful merged run into a `[FAILED]` headline.

## Why it keeps happening

Both probes were written from the **happy path**, where one stream carries everything that
matters. The failure modes that populate the *other* stream are exactly the ones nobody
exercised. And in both cases the discarded stream is the only evidence that could discriminate
the two states being collapsed.

## What to do

- **Never collapse "could not verify" into "verified false".** They have opposite remedies: one
  is retry-or-investigate, the other is fix-your-credentials. A probe that cannot tell them
  apart must report a third state, not pick one.
- **Capture every stream a probe consumes, and put the discriminator in the payload.** If a
  return code is the whole input, the probe can only ever report a binary — say so, rather than
  naming a specific cause it did not establish.
- **A named `error_cause` is a claim about mechanism.** Emitting a specific cause from a generic
  failure is the same defect class as a vacuous guard: the value looks precise and is not.
- **Test with a matched control.** Assert the probe returns authenticated when the underlying
  tool exits 0, *and* returns the failure cause only when it genuinely does — a test that only
  exercises the failing side cannot catch an over-broad mapping.

## Related

The consumer being fail-closed is correct and must not be softened as the remedy — fix the
producer's claim, never the barrier that trusted it.
