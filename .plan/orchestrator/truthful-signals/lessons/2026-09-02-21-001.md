# A daemon-routed build timed out at 1800s while the same command ran well inside 1800s in-process

## Problem

On 2026-09-02, two daemon runs of `module-tests plan-marshall` timed out at exactly
1800 s. The same command run `--execution-mode in_process --timeout 3000` completed in
**1502 s total / 1486.69 s of tests** (19527 passed, 1 failed, 10 skipped) — comfortably
**inside** the 1800 s bound.

So those daemon timeouts are not explained by "the suite needs more than 1800 s." The
suite does not. Something made those particular daemon runs ≥ 20 % slower than the
in-process run, and that cause is **unidentified**. Candidates not yet discriminated:
daemon-side execution overhead, contention with concurrently-running builds, or a hang in
the daemon's supervised child. Do not repeat the "roughly half of all runs time out by
construction" inference — it was derived from a learned 1790 s figure against the 1800 s
default bound, and the measured 1486 s refutes the premise it rested on.

## Why it matters

- **A timeout is neither green nor red.** It reports no findings, so the orchestrator-tier
  handler is explicitly forbidden from routing it into `verification-feedback` — that
  would sweep an empty set and report a false green. The step can neither pass nor fail;
  it stalls.
- **The wrapper exits 0.** `status: timeout, exit_code: -1` rides on a process exit of
  `0`, so a caller reading the exit code sees success.

## Directive

- **Before treating the bound as the cause of any given timeout, measure the command
  in-process.** A daemon timeout at exactly 1800 s with an in-process duration well under
  it means the bound was the messenger, not the cause — investigate the
  daemon-vs-in-process divergence instead of raising the number.
- Do NOT re-run a daemon build a third time after two 1800 s timeouts; switch mechanism to
  get a measurement, then compare.

## Detection

`status: timeout` with `duration_seconds: 1800` AND `timeout_used_seconds: 1800` on a
submit that named no explicit `--timeout`. That equality is the daemon's own default
bound being applied — it is NOT by itself evidence that the command needed more than
1800 s.
