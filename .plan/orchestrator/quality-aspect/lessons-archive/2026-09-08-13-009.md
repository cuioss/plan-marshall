# Name the accepted evidence in the build_scope_narrow freshness refusal

## Context

The freshness gate refused this plan's push twice with `build_scope_narrow`. Both refusals were
correct: individually-run gates are each too narrow to serve as freshness evidence, and only a
whole-tree verify over the current worktree sha satisfies the gate.

The refusal names what it rejected and not what it would accept. The natural response to being told
a build was too narrow is to run another build — and running more narrow green builds cannot satisfy
this gate, however many of them pass. Both refusals therefore cost a round trip that a
self-describing refusal would not have.

This is worth recording precisely because the gate behaved correctly. The lesson is not that the
gate was wrong; it is that a correct refusal which does not name its acceptance criterion still
costs the caller a cycle, and the criterion here is fixed and known to the gate at refusal time.

`pre-push-quality-gate` fired 10 times on this plan. Not all of those were freshness refusals, but
the step is on the hot path of the finalize loop and each avoidable round trip is a dispatch.

## Root cause

The refusal is expressed as a diagnosis of the evidence supplied rather than as a statement of the
evidence required. The gate knows both halves; it publishes only one.

## Proposed action

Extend the `build_scope_narrow` refusal payload to name the evidence it would accept — a whole-tree
verify at the current `worktree_sha` — alongside the scope it rejected. The value is already
available at refusal time, so this is a payload addition rather than new logic.
