# DSL-JSON ParsingException messages echo raw header bytes incl. CR/LF; never put them in log lines or exception messages

## Problem

When DSL-JSON fails to parse a JOSE header (JWE protected header or inner-JWS header), its `ParsingException` message quotes a section of the raw input bytes. Attackers control those bytes, and they can include CR/LF and other control characters. In plan-05-jwe-ecdh-es, header-decode failure paths in `NonValidatingJwtParser` and `JweDecryptor` passed that message (or `e.getMessage()`) into a LogRecord or a `TokenValidationException` message. That is log injection / log forging (CWE-117). It took several review rounds to close fully (TASK-006 quiet decode modes, TASK-007 alg/enc sanitization and JwkKey coordinate logging, TASK-008 JWE header-decode message hardening, TASK-009 inner-JWS decode log hardening and a CR/LF assertion).

## Rule

- Never put a DSL-JSON `ParsingException` message, or any exception message built from token bytes, into a log line or an exception message.
- Log a fixed, structured reason instead (which header and which check failed), plus at most a sanitized or length-bounded value. CR/LF and U+2028/U+2029 are stripped or escaped.
- Header values echoed from the token (`alg`, `enc`, `kid`, JWK coordinates) need the same sanitization before they reach a LogRecord.
- Every such path gets a test that feeds CR/LF (and U+2028/U+2029) in the header and asserts the logged or thrown text contains none of them.

## Scope

All token-parsing surfaces in token-sheriff-validation (`pipeline/NonValidatingJwtParser`, `jwe/JweDecryptor`, `commons/transport/JwkKey`, `JWTValidationLogMessages`). Doc counterpart: `doc/LogMessages.adoc`.
