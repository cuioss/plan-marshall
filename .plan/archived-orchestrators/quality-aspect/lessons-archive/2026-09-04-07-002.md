# manage-lessons consult resolves main-anchored and cannot find a worktree-resident outline

component: plan-marshall:manage-lessons
category: bug

## Observation

During a phase-3-outline re-grounding pass on plan `unreviewed-merge-gate-holes` — a
phase-5+ plan whose directory had already been MOVED into its worktree by the ADR-002
move-in — the mandatory lessons consult failed:

```text
manage-lessons consult  ->  outline_not_found
```

`consult` looks for the plan's `solution_outline.md` under the MAIN checkout
(`/home/oliver/git/plan-marshall/.plan/local/plans/`), but after move-in the plan's
artifacts live only in the worktree
(`.plan/local/worktrees/{plan_id}/.plan/local/plans/{plan_id}/`). It fails identically
whether invoked through the worktree executor or main's, and the verb exposes no
`--project-dir` escape hatch.

Every other script in the same pass resolved to the worktree correctly. The two
anchoring rules therefore disagree with each other.

## Why it matters

The lessons consult is a **mandatory** outline step, not an optional enrichment: it is
what stops a plan repeating a failure the corpus already recorded. Under ADR-002 the
plan directory is moved into the worktree from phase-5 onward, so **every** re-entry
into outline after that point — every baseline-drift re-cycle, every loop-back —
silently loses the consult. The failure is a clean `outline_not_found`, which reads
like "this plan has no outline" rather than "this verb looked in the wrong tree", so
the natural response is to shrug and continue.

The workaround an agent is most tempted into is worse than the bug: re-running the
consult against an empty result and recording a fabricated "no applicable lessons"
disposition. On this plan the agent correctly refused, preserving the seven existing
dispositions and logging a WARNING instead — but nothing in the contract forced that
choice.

## Directive

Resolve `consult`'s plan directory the same way every other plan-scoped verb does —
through the uniform cwd walk-up (ADR-002), so a call made from inside the worktree
finds the worktree-resident copy:

- Route the outline lookup through the shared plan-context resolver rather than a
  main-anchored path join. `merge_lock` is the ONE sanctioned main-anchored resolver;
  `consult` is not, and should not become a second.
- Failing that, accept the same `--plan-id` / `--project-dir` two-state contract the
  Bucket B scripts use, so a caller that knows the tree can say so.
- Distinguish the two states in the return: "no outline exists for this plan" and
  "an outline exists but not in the tree I searched" are different facts with opposite
  remedies, and collapsing them into `outline_not_found` is what makes the defect
  read as benign.

Add a regression test that invokes `consult` with cwd pinned inside a worktree whose
plan directory has been moved in, and asserts the outline resolves. Without that
fixture the suite cannot see this class of defect at all — the move-in is exactly the
state no unit test sets up by default.

## Evidence

- Plan `unreviewed-merge-gate-holes`, phase-3-outline baseline-drift re-grounding pass.
- Plan dir at `.plan/local/worktrees/unreviewed-merge-gate-holes/.plan/local/plans/unreviewed-merge-gate-holes/`;
  `consult` searched `/home/oliver/git/plan-marshall/.plan/local/plans/`.
- Reproduced through both the worktree executor and main's executor.
