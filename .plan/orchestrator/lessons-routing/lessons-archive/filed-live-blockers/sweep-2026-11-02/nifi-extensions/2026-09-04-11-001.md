# A masking helper is not a sanitizer - maskToken keeps an attacker-controlled prefix, so a masked value still needs LogSanitizer.forLog before a log sink

# Candidate lesson: a partially-sanitized log call passed self-review and was caught only by the review bot

## What happened

Line 207 logged `processorId` and `maskToken(token)` without `LogSanitizer.forLog(...)`, while the *same class* already
applied `LogSanitizer.forLog(processorId)` at line 235. `maskToken` masks the token's middle but retains an
attacker-controlled prefix, so a CRLF-bearing prefix reached the log unsanitized.

This is a slipped-then-caught defect: the plan introduced and reviewed the sanitization helper, the security-audit and
pre-submission-self-review finalize steps both ran green, and the gap was found only by the external review bot on the PR.

## Candidate rule (for orchestrator judgement)

The failure mode is *inconsistent application of a just-introduced guard within a single file*. The signal that would have
caught it locally is structural and cheap: when a plan introduces a sanitizer/guard helper, every call site of the sink it
guards — in the files the plan touches — should be enumerated and checked, not spot-checked.

Possible dispositions:

- Add a "guard introduced -> enumerate the guarded sink's call sites in the footprint" check to pre-submission self-review
  (this is close to the existing symmetric-pair / lone-unguarded-boundary candidate classes in
  `pm-plugin-development:ext-self-review-plan-marshall`, but that implementor is plan-marshall-domain only — the
  equivalent for a Java/production-code footprint may not exist).
- Or capture it as a Java security standard: a masking helper is not a sanitizer, and masked values still need
  `forLog(...)` before reaching a log sink.

## Why this is cross-plan

Nothing here is specific to this plan's requirement. Any plan that adds an output-encoding or sanitization helper to an
existing class can leave a sibling call site unguarded, and the current finalize gates do not detect it.

## Orchestrator corroboration (2026-09-04, at HEAD b14b092)

Verified in the merged code, not taken on the plan's word.
`JwtVerificationServlet` now wraps BOTH values and states the reason in the code itself:

```java
// Both values are externally sourced and reach the log sink before any validation:
// maskToken keeps the caller-controlled first characters verbatim, so it neutralizes
// nothing for CWE-117 purposes.
LOGGER.debug("Request received - processorId: %s, token: %s",
        LogSanitizer.forLog(processorId), LogSanitizer.forLog(maskToken(token)));
```

The standing rule for this repository: **masking and sanitizing are orthogonal.** A helper
that redacts *content* (`maskToken`) does not neutralize *structure* (CRLF, control
characters), so a masked value reaching a log sink still needs `LogSanitizer.forLog(...)`.
When a plan introduces such a guard, enumerate every call site of the guarded sink in the
files it touches -- this one was missed by both the security-audit and self-review finalize
steps and was caught only by the external review bot.
