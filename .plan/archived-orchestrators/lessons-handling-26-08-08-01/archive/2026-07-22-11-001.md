# A cwd/state isolation guard written as an autouse fixture cannot see monkeypatch restores and false-positives on correct usage - it belongs in a pytest_runtest_teardown hook wrapper

## Symptom

A test-isolation guard was promoted from silent-restore to fail-loud: the
existing `_restore_cwd` autouse fixture in `test/conftest.py` restored a leaked
process-wide cwd without telling anyone, so an offending test passed while
every later test inherited a cwd it never asked for. Making it raise turned a
green suite into roughly 520 teardown errors.

The blast radius was read as evidence that the suite was pervasively leaking
cwd, and the escalation that followed was scoped to migrate ~17 test files to
`monkeypatch.chdir`. Almost none of those errors were real leaks.

## Root cause

pytest runs `monkeypatch.undo()` — which is what reverts a
`monkeypatch.chdir()` — **after** every fixture finalizer, including an
autouse fixture declared in the same `conftest.py`. The ordering is:

```text
test body ends
  -> autouse fixture finalizers run   <-- the guard's post-yield code is HERE
  -> monkeypatch.undo() restores cwd  <-- the restore happens AFTER
```

A guard implemented as an autouse fixture therefore samples `os.getcwd()` at a
point where pytest has not yet had the chance to restore it. It sees the
test's chdir'd directory and reports a leak — for a test that used
`monkeypatch.chdir` exactly as prescribed. The guard was structurally incapable
of observing the correct behaviour it was written to enforce, so it
false-positived on every well-behaved test that changed directory.

The generalisation: **an autouse fixture is the wrong seam for any check whose
verdict depends on state that pytest's own teardown machinery
(`monkeypatch.undo`, and anything else sequenced after fixture finalization)
is responsible for restoring.**

## Impact

- A one-line seam defect presented as a ~520-error suite-wide failure.
- The escalation that followed sized the remediation at ~17 files of
  `monkeypatch.chdir` migration. The real fix was **one file** — relocating
  the guard. Nearly the entire proposed scope was chasing false positives.
- Had the migration been executed on the fixture-based guard, the guard would
  still have false-positived afterwards, because migrating to
  `monkeypatch.chdir` is precisely the usage the fixture cannot observe.

## Corrective action

Implement process-wide-state isolation guards as a **hook wrapper on
`pytest_runtest_teardown`**, checking post-yield, so the check runs after all
fixture finalization:

```python
_ENTRY_CWD_KEY = pytest.StashKey[str]()


@pytest.hookimpl(tryfirst=True)
def pytest_runtest_setup(item):
    item.stash[_ENTRY_CWD_KEY] = os.getcwd()


@pytest.hookimpl(wrapper=True)
def pytest_runtest_teardown(item, nextitem):
    result = yield                       # post-yield == after fixture finalization
    original_cwd = item.stash.get(_ENTRY_CWD_KEY, None)
    if original_cwd is None:
        return result
    leaked_cwd = os.getcwd()
    if leaked_cwd != original_cwd:
        os.chdir(original_cwd)           # unpoison the NEXT test first
        raise RuntimeError(
            f'cwd guard: test {item.nodeid} leaked the process-wide cwd:\n  '
            f'{original_cwd} -> {leaked_cwd}'
        )
    return result
```

Three properties this shape gets right and the fixture shape cannot:

1. **Post-yield in the teardown hook runs after `monkeypatch.undo()`**, so a
   correct `monkeypatch.chdir` is invisible to the guard and only a genuinely
   unrestored cwd trips it.
2. **Entry state is captured in `pytest_runtest_setup` and carried on
   `item.stash`**, not in a fixture-local closure — the two halves are
   decoupled from fixture ordering entirely.
3. **Restore first, then raise.** The following test is unpoisoned even
   though the offending test is reported.

The same reasoning applies to any other process-wide-state guard
(`os.environ`, `sys.path`, cwd, global registries) that a prescribed
`monkeypatch.*` helper is expected to restore.

## Recurrence signature

A newly fail-loud isolation guard whose failure count is implausibly large
(hundreds of teardown errors across unrelated modules) and whose reported
"leaks" are concentrated in tests that already use the prescribed
`monkeypatch.*` restore helper. Before sizing any migration off that count,
check the seam: if the guard is an autouse fixture, the ordering — not the
tests — is the defect. Confirm by reading a single reported nodeid and
verifying it does call the prescribed helper.
