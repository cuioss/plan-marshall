# Unquoted template placeholder in a documented shell command mis-parses on empty expansion: argparse consumes the next flag as its value — quote possibly-empty {placeholders}

A documented `bash` command block that substitutes a `{placeholder}` which can
legitimately expand to the empty string must **quote the placeholder**, or the
command mis-parses exactly in the case the surrounding feature exists to handle.

## The defect

`execute-task/SKILL.md` documented the per-task test-scope resolution as:

```bash
python3 .plan/execute-script.py plan-marshall:build-pyproject:pyproject_build resolve-test-scope \
  --changed-paths {changed_paths} --plan-id {plan_id}
```

When the task touches no build-relevant files, `{changed_paths}` expands to
nothing, the shell drops the argument entirely, and `argparse` consumes the
following `--plan-id` token as the *value* of `--changed-paths` — a parser
error. This is the docs-only footprint case, i.e. precisely the scenario D1's
test-scoping was built to support. Caught by CodeRabbit, missed by every
in-house gate (no gate lints the shell-safety of documented command blocks).

## Fix

Quote every template placeholder that can expand to empty (or contain spaces):

```bash
  --changed-paths "{changed_paths}" --plan-id "{plan_id}"
```

An empty value is then passed as a single `--changed-paths ""` argument, which
the script resolves to an empty footprint, and paths containing spaces stay one
argument.

## Rule

When authoring a documented shell command that interpolates a plan/task-supplied
`{placeholder}`, quote it whenever the value is optional, footprint-derived, or
otherwise possibly-empty. Reserve bare (unquoted) placeholders for values that
are structurally guaranteed non-empty and space-free. The failure mode is
invisible in the happy path and only surfaces on the empty-expansion edge — the
same edge the feature is usually meant to cover — so it slips local review and
every in-house gate.
