# Rewriting the persisted task file BEFORE the resolution/validation gate loses data on gate failure — return-then-persist so the write happens only after the gate clears

## Context

During plan `execution-manifest-gaps` (P4), CodeRabbit caught a latent data-loss bug
in the manifest task-verification routing path that the plan's OWN tests missed:
`_route_task_verification_commands` in `manage-execution-manifest` rewrote the
persisted task file BEFORE the resolution/validation gate that decides whether the
routing is valid. On a gate failure — or any early return after the rewrite — the
task file had already been mutated in place, so the pre-mutation content was gone and
a failed resolution left the task file in a corrupted, partially-rewritten state with
no recovery path.

The fix (TASK-12) refactored the function to RETURN the routing result as a tuple and
DEFER task-file persistence until after the resolution gate clears, so a gate failure
leaves the on-disk task file untouched. (Note: that same refactor's return-shape
change regressed five direct-call-site tests that quality-gate-only verification did
not catch — see lesson 2026-07-14-16-001's 2026-07-17 recurrence.)

## The bug

A function that both (a) mutates persistent state (rewrites a file, updates a store)
and (b) runs a validation/resolution gate that can fail or early-return MUST NOT
perform the destructive mutation before the gate passes. Writing first means a gate
failure has already destroyed the pre-write state — classic write-before-validate
data loss. In-module unit tests missed it because they exercised only the happy path
where the gate always passes; only an adversarial reviewer walking the failure branch
surfaced it.

## How to apply

- **Order: gate first, then persist.** Compute the result and run every
  validation/resolution gate BEFORE any destructive write. Persist (rewrite the file /
  commit the mutation) only on the success path, after the last gate that could reject
  or early-return.
- **Prefer return-then-persist over mutate-in-place.** Have the routing/compute
  function RETURN its result (e.g. a tuple) and let a single downstream site perform
  the persistence once, so there is exactly one write and it is unconditionally after
  the gate.
- **Test the failure branch explicitly.** Add a test that drives the gate to FAIL and
  asserts the persisted state is unchanged. A happy-path-only test set cannot catch
  write-before-gate data loss — the very branch that loses data is the one the tests
  never exercise.

## Recurrence signature

- A function mutates persistent state (file rewrite / store update) AND runs a
  validation or resolution gate that can fail / early-return.
- The mutation is performed BEFORE the gate.
- Unit tests cover only the gate-passes path; the gate-fails branch (where the data
  loss occurs) is untested.
- A PR review bot, not an in-house gate, catches the latent data loss.
