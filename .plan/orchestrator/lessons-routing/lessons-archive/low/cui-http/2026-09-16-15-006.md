# A success criterion phrased over documents missed its in-source Javadoc twin, caught twice by the scope validator at outline and again at plan

## Observation

A deliverable's success criterion was "neither published document still presents the
error-category set as five members." The outline's `affected_files` for that deliverable covered
only the `.adoc` documents. The identical five-arm exhaustive switch also existed as a Javadoc code
sample inside `HttpResult.java` — a file that WAS listed under a sibling deliverable, but whose
"Change per file" entry covered only the status contract and null-safety, not the Javadoc sample.
Once a sixth category was added, that sample would have been non-exhaustive and non-compiling if
copied. `scope_criterion_validator` flagged the gap as `under_coverage` at 3-outline, and — because
it was still unresolved at task-creation time — flagged the SAME gap again at 4-plan.

## Corrective

When a success criterion is phrased over "documents," operationalise it as a content search over
the WHOLE repository, not the doc tree: a documentation claim duplicated as an in-source
Javadoc/docstring sample is the same claim and the same defect. A file appearing in a sibling
deliverable's `affected_files` does NOT make it covered — coverage is per "Change per file"
instruction, not per file listing.

## Scope

The validator caught this twice, which is the good news; a gap detected at 3-outline surviving
unresolved into 4-plan is the bad news. Worth considering whether an unresolved `under_coverage`
finding should block task creation for the affected deliverable rather than being re-raised at the
task-level footprint.
