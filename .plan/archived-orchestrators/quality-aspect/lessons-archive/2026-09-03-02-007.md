# A self-review round can return findings without persisting them to the finding store

## Context

`pre-submission-self-review` round 2 on plan-170 returned **3 findings** in its TOON payload and recorded `--outcome failed`. It persisted **none** of them: `qgate list --resolution pending` returned `filtered_count: 0`, and the only `6-finalize` records in the store were round 1's four, already resolved.

Round 1 had persisted correctly (`5f9815`, `4700ef`, `11b1be`, `37ee78`), so the behaviour is intermittent rather than a uniformly missing code path.

The orchestrator recovered by re-filing the three findings from its own reading of the returned descriptions (`655699`, `376349`, `e7a89c`) and resolving them, so the audit trail exists — but it was reconstructed by the consumer, not written by the producer.

## Root cause

The workflow states that *"every returned finding is written to the plan's `qgate-6-finalize.jsonl` finding store before the step's `--outcome failed` is recorded"*, but nothing enforces the ordering or the fact. `mark-step-done` accepts `--outcome failed` without reference to the finding store, and the dispatcher's post-dispatch guard (`assert-step-recorded`) checks only that a terminal outcome record exists — not that the findings the payload claims were actually filed.

So a producer that returns findings and skips the persistence step is indistinguishable, at the handshake, from one that persisted correctly. The gap was caught here only because the orchestrator independently ran `qgate list` and noticed the count was zero; nothing obliged it to look.

## Proposed action

- Make the obligation checkable at the boundary. When a dispatched step records `--outcome failed` or `loop_back` with a non-empty `findings[]` in its return payload, have the dispatcher assert that the finding store gained at least that many records for the phase since the dispatch started — and fail loudly when it did not, naming the count returned versus the count persisted.
- Alternatively invert the ownership: have the step return findings and let the **dispatcher** persist them, so there is exactly one writer and the producer cannot skip it. This is the more robust shape and removes the class rather than detecting it.
- Either way, do not leave the contract stated only in workflow prose — this run demonstrates that prose alone does not hold across re-firings of the same step.
