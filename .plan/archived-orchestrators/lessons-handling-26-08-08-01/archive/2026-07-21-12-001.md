# Canonical step-key migration seam shipped legacy-key-blind: get(canonical) misses pre-existing default:-prefixed records on resume, double-prefix input non-idempotent — only PR bots caught it

When a plan introduces a "canonicalize the step key and migrate to the bare
form" seam (the D2 record-key work in `execution-accounting-integrity`), the
implementation shipped correct for freshly-written canonical keys but blind to
the two states a *resumable* pipeline actually presents on re-entry:
pre-existing legacy `default:`-prefixed records left by an earlier run, and
doubly-prefixed inputs (`default:plan-marshall:automatic-review`). Every
in-house gate (scoped quality-gate, module-tests, plugin-doctor) passed because
the plan's own tests only exercised the clean new-key path. All four defects
below escaped to PR review and only the bots (CodeRabbit Critical/Major, Gemini)
caught them.

## The four slipped defects (one root cause)

1. **`canonicalize_step_key` not idempotent under double-prefix**
   (`script-shared/scripts/_step_key_canonical.py`). It checked
   `PROMOTED_BUILTIN_STEP_IDS` membership *before* stripping `default:`, so
   `default:plan-marshall:automatic-review` needed two passes to reach
   `automatic-review`. Fix: strip the `default:` prefix **first** (reuse the
   existing `_strip_default_prefix` helper — do not re-implement with manual
   string slicing), then map promoted ids. A canonicalizer must be a fixed point
   on any input.

2. **Legacy-key shadowing via dict insertion order** (Critical,
   `manage-status/scripts/_cmd_assert_step_recorded.py`). The lookup scanned
   `phase_entry.items()` calling `canonicalize_step_key(stored_key) == step` and
   broke on the first match. A pre-migration `default:push: failed` entry sits
   *before* the fresh `push: done` write, so the scan returned the stale
   `failed` and falsely failed the pipeline. Fix: try the exact canonical key
   first (`phase_entry.get(step)`) and fall back to the scan only when that
   misses — the latest canonical write must win.

3. **Conflict-check bypass + duplicate state on write** (Major,
   `manage-status/scripts/_cmd_mark_step.py`). `phase_entry.get(step)` (step
   already canonicalized) misses a legacy `default:push` key, so the conflict
   check was skipped and the write left BOTH keys in the dict. Fix: scan for the
   legacy equivalent to enforce the conflict check, and `pop` the legacy key on
   successful write so no duplicate/orphan record survives the migration.

4. **Doc-command shell-quoting** (see the sibling anti-pattern lesson) — same
   plan, different root cause; not part of this cluster.

## Rule

Introducing a canonicalize-and-migrate key seam is a data-migration change, not
a pure-function change. Before shipping:

- **Canonicalize the input first**, and prove idempotency on the worst-case
  double-prefixed / already-promoted inputs (a fixed-point test).
- **Prefer an exact canonical-key match over an order-dependent scan**, so a
  freshly written canonical record is never shadowed by an older legacy-prefixed
  one that happens to sort first.
- **On write, migrate: enforce the conflict check against the legacy equivalent
  and delete the legacy key**, so the store never carries duplicate
  bare+prefixed records for the same step.
- **Seed a test fixture with a pre-existing legacy-prefixed record and re-enter**
  — the clean new-key path is not representative of a resumable pipeline. The
  missing fixture state is exactly why every in-house gate was green.

## Impact

Any manage-status / manage-execution-manifest resumable re-entry against a plan
that ran before the canonicalization landed. A false `failed`/`step_record_missing`
on resume deadlocks the phase_steps_complete handshake; a duplicate key silently
corrupts step state.
