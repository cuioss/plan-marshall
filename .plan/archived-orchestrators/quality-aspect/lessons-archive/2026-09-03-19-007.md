# Batch fragment registration instead of one collect-fragments add per aspect

## Context

This retrospective registered 17 aspect fragments with 17 separate
`collect-fragments add` calls, and ran 9 script-backed aspects with a
byte-identical capture command each:

```bash
python3 .plan/execute-script.py plan-marshall:plan-retrospective:{script} \
  run --plan-id {plan_id} --mode live > work/fragment-{aspect}.toon
```

That is roughly 26 Bash calls whose arguments are fully determined by data the
system already holds, before any analysis happens.

## Root cause

The capture-and-register loop is documented as a per-aspect pattern in
`plan-retrospective/SKILL.md`, and the registry that would let it be driven
already exists: `scripts/retro_sections.py` `SECTION_SPEC` declares the aspect
keys and which are script-backed, and `extension_discovery
list-retrospective-aspects` declares the domain-contributed ones with their
script notation. Nothing in the loop requires judgement — only the fragment
*bodies* of the LLM aspects do.

## Proposed action

Two independent, separately-shippable steps:

1. `collect-fragments add-batch --fragment-dir {dir}` — register every
   `fragment-*.toon` in one call, deriving each aspect key from its filename.
   The mapping is already one-to-one. Low complexity.
2. A `run-deterministic-aspects` driver that walks `SECTION_SPEC`'s script-backed
   rows plus the domain-filtered extension rows, runs each with the standard flag
   set, and registers the output. Medium complexity, and it would also remove the
   chance of a hand-typed aspect key diverging from the registry.

## Evidence

- aspect: llm_to_script_opportunities — candidate 1, repetition_count 10, complexity low; candidate 2, repetition_count 9, complexity medium
- The SKILL.md aspect table already warns that three aspect keys differ from their reference basename, which is exactly the class of error a registry-driven loop cannot make
