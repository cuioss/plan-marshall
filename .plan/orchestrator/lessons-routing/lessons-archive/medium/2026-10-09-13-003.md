# Read workflow docs from the worktree, not the stale plugin cache, mid-plan

## Context

On plan lb-23-verify-builds the orchestrator counted finalize loop-backs with a plan-wide scalar and told the operator the self-review was on the last of its five rounds. By its own account it was following a cached skill copy; the worktree copy of the same workflow carries a per-source `loop-back admit` rule. The operator's decision to close the review was made on that basis.

## Root cause

The skill loader serves the installed plugin cache (version 0.1.1873 in this session), which is refreshed only by the sync step at the end of finalize. A plan running in a worktree whose branch, or whose base, has moved the workflow documents therefore executes one version of the workflow while editing and testing another. The skills loaded for this retrospective also came from the 0.1.1873 cache, while the workflow document itself was read from the main checkout source.

## Proposed action

- Make the orchestrator read phase and workflow documents from the checkout it is running against (the worktree in phases 5 and 6), as dispatched leaves were told to do in the later rounds, rather than from the plugin cache.
- Surface a cache-versus-source version mismatch at phase entry, so a stale cache is a stated condition instead of a silent one.
- Where a count is shown to the operator as a limit ("last round"), name the rule it was derived from.
