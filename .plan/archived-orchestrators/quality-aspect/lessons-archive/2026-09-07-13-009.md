# The four dispatch context-load flags are optional and no call site passes them, so the measure is dark

## Context

Measured on plan `plan-04-autonomy-gate-defaults` (epic `operator-ux`, PR #1437):
`context_position_cost` is populated for **0 of 23** dispatch boundaries, and
`logging_gap_analysis` reports gap `DISPATCH_CONTEXT_LOAD` for the whole run.

The four context-load fields are declared as **optional flags** on the metrics recorder, and no call
site anywhere passes them. The measure has therefore never produced a value for any plan.

## Root cause

Optionality without a caller. The recorder accepts the flags, the schema documents the columns, and
the analysis step knows the gap's name — so every layer is present except a producer. Because the
flags are optional the recorder cannot complain, and because the columns are nullable the report
renders a clean empty rather than a missing input.

⛔ **This is why the earlier lesson did not close it.** `2026-08-25-09-004` asked for the four
columns to be populated and `enrich` to be run at the metrics close — a remedy aimed at the
*consumer* end. The cause is at the *producer* end: no dispatch site passes the flags, so enrich has
nothing to enrich. Filed separately for that reason, with the fix site named.

## Proposed action

1. Make the four flags **required** at the dispatch recording seam, or derive them at the recorder
   from data the dispatch already carries, so a boundary cannot be recorded without them.
2. Until a producer exists, have `logging_gap_analysis` report the measure as **unmeasured** rather
   than as a zero — `0 of 23` reads as a finding about the plan when it is a finding about the
   instrument.

## Impact

Every cost analysis this epic has performed on dispatch position has been running on an empty
column, including the finalize-cost arguments in three landing reports. Those arguments were made
from token totals and step firing counts instead, so they are not invalidated — but the one measure
that would attribute cost to context position has never existed, and its absence has been reported
as a zero for long enough that it reads as normal.

## Recurrence — 2026-09-09 (close-the-runtime-slice-parametrization, PR #1455)

Still dark, now measured across three phases rather than one. `context_position_cost` reports
`measured_rows: 0` against `unmeasured_rows: 26` — every row of every dispatching phase:
`4-plan` 0/1, `5-execute` 0/10, `6-finalize` 0/15. `position_multiple` and
`position_multiple_basis` both read `unmeasured`.

Every one of those 26 rows carries the same
`unmeasured_columns: [input_tokens, output_tokens, cache_read_input_tokens,
cache_creation_input_tokens]`, with `unrecognised_columns` and `indeterminate_columns` both
empty — so this is cleanly the producer gap this lesson names, not a parse or schema problem.

Two things this run adds. First, proposed action (2) has **landed**: the measure now reports as
`unmeasured` rather than as a zero, at both the row level and in `context_position_cost`, so the
finding reads as one about the instrument. Proposed action (1) — a producer at the dispatch
recording seam — has not. Second, the consequence is now visible in a live column: the plan's
`Billing (cost)` total is `totals_billing_weighted_total: 0` with
`totals_billing_weighted_total_population_count: 0`, because the weighted total is computed from
the same four fields. The derived-cost measure for a 10.1M-token plan is therefore absent
plan-wide, and only the population count distinguishes that from a plan that cost nothing.
