# Exhaustiveness and guard coverage claimed by prose or a hand list, not enforced: enum switch statement, hand-listed ArchUnit population, class-level predicate for a package rule

Merged from three candidates of PLAN-V02-25 (#487): plan-v02-25-edge-route-decomposition-004, -005, -006. All three were CodeRabbit findings fixed in-run (commit f6f3a7e). This is the same defect class as 2026-10-15-09-001 (a hand-kept list mirroring a set the code owns) and 2026-10-04-09-009 (derive a guard's stated limit from its matcher). Here it shows up in a dispatch switch and in architecture tests.

## What happened

1. **Unchecked enum dispatch.** The `DispatchPath` Javadoc said the assembler and the edge dispatch switch "can never disagree". `DispatchPath.of` is a switch expression, but the consumer in `GatewayEdgeRoute.process` was an arrow-label switch *statement*. Java does not check a statement switch over an enum for exhaustiveness. A fourth constant, which `doc/development/protocol-processors.adoc` tells contributors to add, would have compiled with no arm, and requests on that route would have gone unanswered until the client timed out.
2. **Hand-listed guard population.** `EdgeSubPackageArchTest.DECOMPOSED_SUB_PACKAGES` copied by hand the sub-package set that `edge/*/package-info.java` declares. A new sub-package that later lost its classes would quietly drop out of the cycle rule, and the non-vacuity check would still pass.
3. **Guard predicate narrower than the rule.** ADR-0068 and `edge/package-info.java` forbid sub-packages from depending on the edge *root package*. The ArchUnit predicate forbade only `GatewayEdgeRoute`, so a second root class would have slipped past both rules.

## Corrective rule

- When a switch over an enum must handle every constant, write it as a switch expression with no `default`, so a missing arm is a compile error. Never claim exhaustiveness in Javadoc that the compiler does not enforce.
- An architecture test derives its population (packages, slices, classes) from the source it guards, such as the `package-info` declarations, and checks that each derived member is non-empty.
- A guard's predicate matches the documented rule's unit: if the rule names a package, match the package, not the one class that lives there today.

## Recurrence — 2026-10-22 (plan-v02-43-validator-reserved-header-topology-rules, #505)

Three CodeRabbit findings, all fixed in-run, show the same class again:

1. **One-direction mirror guard (finding 876ead).** `BootValidationConcernMapContractTest` checked that every rule registered in `ConfigValidator.DEFAULT_RULES` is listed in the concern-map row of its class in `doc/development/boot-validation-rules.adoc`. It did not check the reverse. A rule left in its old row after a move, or a renamed or deleted rule, kept the test green, while the page and the ADR claimed a stale map "fails the build". Fixed by adding the reverse check with its own synthetic control (TASK-14).
2. **Hand-copied configuration values in docs (finding 9ebed0).** `doc/development/re-review-on-loopback.adoc` repeated the `required_bots` / `optional_bots` values from `.plan/marshal.json` with nothing binding them (TASK-15).
3. **ADR claimed more than the guard checks (finding 6aff9b).** ADR-0071 said the guard rejects every inline rule body. The contract test only counts concern-class calls per entry, so an entry with one call plus an extra `ConfigError` statement passes. Fixed by narrowing the ADR sentence to what the test checks.

Sharper rule from this recurrence:

- A guard that keeps a hand-written list in step with a code-held set checks both directions: everything in the code is in the list, and everything in the list is in the code.
- Before an ADR or Javadoc says that something "fails the build" or is "rejected", name the test assertion that does it. If no assertion does, narrow the sentence.
