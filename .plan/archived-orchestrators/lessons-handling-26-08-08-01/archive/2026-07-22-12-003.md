# Routed build reported outer status success while the daemon child had failed, because terminal status was classified from a build wrapper exit code that is always 0

A build routed to the `marshalld` daemon returned an outer `status: success`
while the daemon's child build had genuinely failed. The daemon classified the
job's terminal status from the build wrapper's **process exit code**, and that
wrapper is documented to exit `0` even on failure — its real verdict lives in
the TOON `status` / `errors[]` payload it prints, not in its return code. The
routing layer therefore inherited a truth source that structurally cannot
express failure, and every routed failure was laundered into a success.

## What happened

Finding `2fa4dd` on plan `pyproject-routing-integration`: a routed
whole-bundle verify came back green. Nothing in the returned envelope was
wrong-looking — the status field said success and no errors were listed. The
defect was caught only because the reported **duration was implausible**: a
whole-bundle verify that normally takes minutes had "completed" in ~3 seconds.
Reading the daemon's job log showed the child build had failed almost
immediately, and the daemon had stamped `success` because the wrapper process
had exited `0`.

The plan fixed the classification defect in deliverable 4 (the daemon now
classifies from the wrapper's structured result payload rather than its exit
code), so the specific code path is closed. The durable residue is the
**verification discipline**, which no code fix retires.

## The generalizable rules

1. **Never trust a routed build's outer status at face value — read the job
   log.** A routed (daemon-executed) build has two status surfaces: the
   client's outer envelope and the daemon's per-job log. When the two can
   disagree, only the job log is ground truth. Treat the outer envelope as a
   claim to be corroborated, especially before acting on a green.

2. **Implausible duration is a first-class failure signal.** A verify that
   completes in seconds when its baseline is minutes has not passed — it has
   not run. Duration is the cheapest available cross-check on a status claim
   and is the only thing that surfaced this defect. Compare a build's reported
   duration against its known baseline before accepting its verdict.

## Why it slipped every in-house gate

The classifier was internally consistent and unit-tested against a wrapper
stub that returned the exit codes the test author assumed it would return.
No test asserted the *premise* — that the real wrapper differentiates success
from failure by exit code. This is the fail-open-classifier shape already seen
elsewhere in the corpus: the seam is correct given its inputs, and the defect
lives entirely in the unverified assumption about what those inputs mean.

## Impact

High. Every routed build failure between the routing seam shipping and this
fix was reported as a success, so a routed verify was worthless as a gate — it
could only ever say green. Detection depended on a human noticing an
implausible wall-clock time, which is not a control.
