# refire-report reads only execution_log, so it under-counts the steps that re-fire most

## Context

`phase-6-finalize/standards/verdict-currency.md` § "Obtaining the re-fire count" names
`manage-execution-manifest refire-report` as the way the re-fire count is obtained, and
states that the count is "derived from instrumentation that already exists" because
`record-step` appends one `execution_log[]` row per firing "for every finalize step,
dispatched and inline alike".

On plan `misconfigured-reviewer-name-reads-missing-review` that premise did not hold. Three
of the seven dispatched finalize steps disagree between the two ledgers that count firings:

| step | `status.json` `firing_count` | `execution_log` rows | delta |
|---|---|---|---|
| `automatic-review` | 3 | 2 | 1 |
| `finalize-step-simplify` | 5 | 3 | 2 |
| `ci-verify` | 2 | 1 | 1 |

`manage-metrics reconcile-ledgers` independently found three `6-finalize` dispatch-boundary
rows with no `record-step` partner, totalling **736,467 tokens — 19.6 % of the phase's
3,753,083 recorded dispatch spend**:

- `2026-09-03T19:07:58Z`, 182,906 tokens — `automatic-review` iteration 2, `returned_with_findings`
- `2026-09-03T20:20:38Z`, 187,858 tokens — `automatic-review` iteration 3, `blocked_user_review`
- `2026-09-03T21:45:30Z`, 365,703 tokens — the wait-region unified triage, a `verification-feedback`
  dispatch that is not a manifest step at all

## Root cause

`record-step` is called on the dispatcher's normal completion path. Its outcome vocabulary
was `executed` / `error` / `skipped`, so a dispatch terminating `loop_back` or
`blocked_user_review` reached `mark-step-done` (which increments `firing_count`) without
reaching `record-step`, and a dispatch that is not a manifest step has no `step_id` to
record. `refire-report` reads `execution.toon` only, so every one of those firings is
invisible to it.

**The `loop_back` half of that gap is CLOSED.** `VALID_RECORD_OUTCOMES` is now
`executed` / `skipped` / `loop_back` / `failed` / `error`, the widened set is reachable from
every caller surface, and `summarize_refires` counts `loop_backs` / `failures` / `errors` in
separate columns. `blocked_user_review` still has no recordable outcome, and a non-manifest
dispatch still has no `step_id`, so the under-count persists on those two paths — narrower
than when this lesson was filed, and in the same direction.

The direction of the error is the problem: the missing firings are concentrated in exactly
the steps that re-fire *most*, so the instrument understates the re-stale treadmill it exists
to measure, and understates it worst where the cost is highest.

## Proposed action

1. Have `refire-report` read `work/metrics-dispatch-boundaries-{phase}.toon` alongside
   `execution.toon` and publish `union_firings` beside `firings`, plus the per-step
   dispatch-boundary token sum. `manage-metrics reconcile-ledgers` already implements the
   phase + timestamp-window join and already publishes `union_rows` as "the count a reader
   should take"; reuse it rather than writing a second join.
2. Either call `record-step` on the `blocked_user_review` terminal path, or state in
   `verdict-currency.md` § "Obtaining the re-fire count" that `firings` excludes it — the
   section still claims the opposite ("for every finalize step, dispatched and inline
   alike"), and it was not updated when the outcome set widened, so it now under-states the
   exclusion by exactly one path instead of two.
3. Add the `status.json` `firing_count` ledger as a third pairing in `reconcile-ledgers`.
   It is a third independent writer of the same fact and nothing currently compares it to
   either of the other two.
