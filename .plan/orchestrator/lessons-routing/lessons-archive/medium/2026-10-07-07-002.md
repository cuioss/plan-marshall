# Regenerate the worktree executor when a plan changes a script's flags

## Context

Plan `plan-pr-078-review-bot-fleet-opt-in` added three flags (`--scope`, `--match`, `--job`) to `tools-integration-ci:ci checks logs` in TASK-9 and then needed to call the new flags in TASK-11 of the same plan. `ci checks logs --help` listed all three flags, and the task's own precondition check passed on that basis. Every real call was then refused before the script started with `invalid_invocation / unknown_flag: --scope rejected, accepted=[run-id]`, with and without `--project-dir`. TASK-11 was held, the leaf handed back to the orchestrator, the executor was regenerated, and a further dispatch finished the task.

## Root cause

The generated executor embeds a per-script accept-set (`SCRIPT_SURFACES`) derived when it was generated. `--help` bypasses that check and prints the live script, so the two disagree for exactly the scripts a plan has just changed. A plan that both changes a script's argparse surface and consumes the change has no step that regenerates the executor in between; the only regeneration in the lifecycle is in finalize (`finalize-step-plugin-doctor`), after execute has ended.

## Proposed action

- In `phase-5-execute`, regenerate the worktree-bound executor after any task whose diff touches a registered script's argparse surface, before the next task runs.
- Make the refusal say what it is: when the embedded accept-set rejects a flag the live script's parser declares, report `stale_executor` with the regeneration remedy instead of `unknown_flag`.
- Stop treating `--help` as proof a flag is callable in precondition checks; probe with a real call instead.
