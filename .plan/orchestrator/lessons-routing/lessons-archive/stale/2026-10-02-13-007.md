# Participation guard reports PR-Agent (cuioss-review-bot) as participated_stale when its Reviewer Guide was edited in place to 'Review updated until commit <HEAD>'


## Observed (API-Sheriff PR #356, plan-19-session-fallback-on-bearer, 2026-09-24)

After a loop-back fix push (d0a250f -> 2a7c68a), the automatic-review FIND re-fire recorded
`cuioss-review-bot: participated_stale` and looped back to 6-finalize. In fact PR-Agent had re-reviewed
the new HEAD: it edits its single "PR Reviewer Guide" issue comment IN PLACE, and the body read
"(Review updated until commit .../2a7c68a...)" with "No major issues detected". The classifier keyed
staleness on the comment's createdAt (15:56Z, before the fix commit), not on the in-place
"updated until commit <sha>" marker. A second loop-back would reproduce the same verdict forever.

Related: the CLAUDE.md convention "post `/review` to re-request PR-Agent" no longer fires anything
in this repo (no issue_comment workflow run since 2026-09-18 after the cuioss-organization workflows
v0.30.0 bump) — PR-Agent now re-reviews on `pull_request` synchronize by itself. `@coderabbitai review`
answered "Already reviewed the last commit": CodeRabbit is incremental and had reviewed 2a7c68a on push.

## Directive

- Treat a PR-Agent guide whose "Review updated until commit <sha>" names the current HEAD as fresh
  participation at that HEAD (registry `participation_evidence` for cuioss-review-bot should read the
  marker, or fall back to the comment's updatedAt / edit history), not createdAt.
- Treat a CodeRabbit "Already reviewed the last commit" reply as evidence of a review at HEAD.
- Update the API-Sheriff CLAUDE.md step 6 note about re-requesting PR-Agent via `/review`.

## Recurrence — 2026-10-02 (plan-23-session-route-scope-parity)

Same component and same symptom (`cuioss-review-bot: participated_stale` after a loop-back fix push,
API-Sheriff PR #369), but this time the verdict was correct: the bot had not re-reviewed.

- After the fix push to 9e34163a the automatic-review step returned `loop_back`: cuioss-review-bot
  had reviewed a18c3b0c only, CodeRabbit had reviewed 9e34163a (work log 2026-10-02T06:48Z). The bot
  was still stale one triage round later (work log 2026-10-02T06:59Z).
- After the next fix push (53d1b363) the orchestrator posted a `/review` comment by hand (decision
  b9f11d). The workflow did not post it; the orchestrator's hand-off names `re_review_on_loopback=false`
  as the reason (the setting itself was not re-read for this record).
- At 378a063f the bot's guide was "updated for this HEAD" and was accepted as participation
  (decision 56960c), so the in-place update is now read as fresh evidence. The first directive above
  appears to be in effect.

**The "Related" paragraph above no longer describes this repository.** As of 2026-10-02 PR-Agent has
no push trigger: `CLAUDE.md` step 6 states that `.github/workflows/pr-agent.yml` triggers on
`opened` / `reopened` / `ready_for_review` plus on-demand `issue_comment` commands, and that a
`/review` comment must be posted after every fix push. The third directive above is done, in that
direction.

CodeRabbit shaped the cadence as well: each of its three reviews on this PR reported "1 included
review per hour; 0 remain after this review". The rounds were more than an hour apart, so no review
was refused, but a fix push inside that hour would wait for the allowance.

### Directive (added)

- The review-bot registry should record how each required bot is re-triggered (on push, or by a
  command comment). For a command-triggered bot the automatic-review loop should post the command
  after each loop-back fix push itself, whatever `re_review_on_loopback` says, or that setting should
  default to on for such bots. Without it every fix round ends in a `participated_stale` loop-back
  that only a manual comment clears, and each such loop-back consumes a finalize iteration.
- Before a fix push, check the time of CodeRabbit's last review on the PR and expect no new review
  within the hour.
