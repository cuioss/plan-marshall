# test_module_subcommand_accepts_canonical_module budgets 30s for an architecture module call that costs 24-57s

## Problem

`test/plan-marshall/manage-architecture/test_architecture_input_validation.py:47`
(`test_module_subcommand_accepts_canonical_module`) shells out to
`architecture.py module --module my-module` through `test/conftest.py:314`'s `run_script`, which
imposes a **30-second** `subprocess.run(timeout=...)` budget.

The verb it invokes does not reliably fit that budget. Measured on 2026-09-02, one call at a time,
no parallel test load:

| Tree | Elapsed |
|---|---|
| main checkout | 24.3s |
| plan worktree | 32.3s |
| plan worktree | 38.5s |
| plan worktree | 50.0s |
| plan worktree | 57.2s |

24s on the *best* observed run against a 30s budget leaves ~20% headroom, and the observed spread
reaches nearly 2× the budget. Under `pytest -n` parallelism the margin is gone entirely, which is
where it actually fails.

## How it surfaced

The `pre-push-quality-gate` module-tests arm went red during a finalize run for
`dual-homed-hook-install-renders-identically`, a plan whose 8-file footprint is entirely
`platform-runtime` + `marshall-steward` + one platform-runtime test module. It touches
`manage-architecture` not at all.

```text
tests: passed 19525 | failed 1 | skipped 10
E  subprocess.TimeoutExpired: Command '[... architecture.py, module, --module, my-module]'
   timed out after 30 seconds
```

The failure is a **subprocess timeout, not an assertion** — the verb returns `exit 0` and a correct
168KB payload every time it is allowed to finish. Nothing about the command's behaviour is wrong;
only its latency against an arbitrary budget.

## ⛔ CORRECTION — the latency numbers above are CONTAMINATED

The measurements in the table were taken while **two abandoned `module-tests` suites were still
running on the same machine**, orphaned by earlier `timeout` verdicts that never reaped their
children (see [[2026-09-02-21-002]]). A process scan found 20 live processes from this worktree:
two pytest controllers with their xdist pools, plus an orphan re-parented to init.

So "one invocation at a time, no parallel test load" is **false** — there was heavy load, self-inflicted
by the retry ladder. Treat 24-57s as an upper bound observed under contention, not as the verb's cost.

After reaping, the full suite ran **19526 passed, 10 skipped, 0 failed** — including this test, under
the raised budget. The budget fix is still right (a 30s bound with no derivation is fragile, and the
file now passes in 125s), but **the latency defect this lesson asserts in its Directive is not
established.** Re-measure on a verified-quiet machine before acting on it; the honest open question is
whether ~24s was ever real.

## Two hypotheses tested and REFUTED — do not re-derive them

1. **"Parallel test load makes it flaky."** Refuted: solo, unloaded invocations still took 32-57s.
   Load worsens it but is not the cause.
2. **"The finalize `architecture-refresh` step's baseline extraction under `.plan/temp/` inflates the
   crawl."** Refuted by a matched control: removing
   `.plan/temp/architecture-baseline/` + `.tar` made the call *slower* (50.0s → 57.2s), not faster.
   The timings are simply noisy.

What IS established: the verb costs tens of seconds inherently, and the budget does not accommodate
that on any tree.

## Directive

Two separable problems; do not conflate them.

**The test.** Its 30s budget is not derived from anything — raise it to a value derived from measured
latency with real headroom, or mark the test as one that must not run under parallel load. A budget
chosen to be "obviously enough" that sits within 20% of the best observed run is a latent red that
fires on unrelated plans, which is exactly what happened here: a `platform-runtime` change was
blocked at its push gate by a `manage-architecture` test.

**The latency.** ~24s for a single-module descriptor read is the more interesting defect and the one
worth measuring before fixing. Establish where the time goes (tree crawl? per-call re-derivation? no
warm cache across invocations?) rather than assuming — the cold-cache hypothesis is already partly
refuted, since a second consecutive call was not meaningfully faster (38.5s then 32.3s).

Derive the blast radius rather than assuming this is the only test affected: enumerate every test
that invokes an `architecture` subcommand through `run_script`'s 30s budget, and check each against
measured latency. This one is the instance that happened to fire, not necessarily the only one at
risk.
