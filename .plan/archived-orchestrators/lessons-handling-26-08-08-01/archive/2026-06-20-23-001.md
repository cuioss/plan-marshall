# Phase-5 end-of-phase verification must run full verify when a plan changes a widely-consumed default; module-scoped verify misses project-local test dirs

When a plan changes a **widely-consumed domain-invariant default** (a `DEFAULT_PLAN_*`
constant in `_config_defaults.py`, or any value read by code across many modules and
the project-local test directories), the phase-5 end-of-phase verification MUST run the
**full `verify`** (all modules + project-local test dirs), not just the modules the
plan's `affected_files` touched. A module-scoped `verify {bundle}` sweep can pass green
while a consumer of the changed default — living in a test directory the plan never
edited — is silently broken.

## Where it surfaced

While shipping `step-param-config-follow-ups-fold-orphaned-phase-k`, deliverable D2
flipped an ownerless step-params default from `{}` to `None` (suppression of the empty
nested map). The plan's `affected_files` were under `marketplace/bundles/plan-marshall`
and `marketplace/bundles/pm-plugin-development`, so the natural module-scoped
verification was `verify plan-marshall` / `verify pm-plugin-development` — both green.

But two **project-local** tests consumed the changed default through membership checks:

- `test/finalize-step-deploy-target/`
- `test/finalize-step-sync-plugin-cache/`

Both did `'x' in DEFAULT_PLAN_FINALIZE['steps']`, which raised
`TypeError: argument of type 'NoneType' is not iterable` once the default became `None`.
Neither test directory was in the plan's touched-module set, so a module-scoped sweep
never ran them. Only the **full CI `verify`** (all modules + every project-local test
dir) caught the regression.

## Root cause

The phase-5 end-of-phase verification scope is keyed off the plan's touched modules.
That scoping is correct for *localized* changes — but a default constant that the whole
codebase (and the project-local test dirs) reads has a blast radius far wider than the
files that define it. The change to the constant lived inside the touched module; its
*consumers* did not. Module-scoped verification therefore cannot see the breakage by
construction: the broken test is in a directory the plan never declares.

Symptom signature:

- A plan edits a default/constant/shared-config value in module M (and only M's files
  are in `affected_files`).
- `verify M` (and any other touched module) passes green.
- A test in a project-local test dir NOT owned by M consumes the changed value and
  fails (`TypeError`/`KeyError`/`AssertionError`) — surfaced only by full `verify`.

## How to apply

- **Trigger on the change kind, not the file set.** When a plan modifies a
  domain-invariant default (`DEFAULT_PLAN_*` in `_config_defaults.py`), a shared
  constant, or any value with a project-wide read surface, escalate the phase-5
  end-of-phase verification scope to the **full `verify`** regardless of how narrow the
  `affected_files` set looks. The narrow file set is exactly what makes the wide blast
  radius invisible to module-scoped verification.
- **Project-local test dirs are first-class verification targets.** `test/finalize-step-*`
  and the other project-local test directories are not covered by any
  `verify {bundle}` invocation; only the full `verify` runs them. A plan that could
  affect them must run full `verify`, not a module subset.
- **Cheap pre-check at outline/plan time.** When a deliverable changes a value in
  `_config_defaults.py` (or another shared-constant module), grep the project-local
  test dirs for the constant name and treat any hit as a mandate to run full `verify`
  at end-of-phase. A membership/iteration check (`x in DEFAULT...`) over a value that
  might become `None`/non-iterable is the canonical breakage shape.

## Impact

Module-scoped verification is a real token/time saver and should stay the default for
localized changes — but it has a structural blind spot for shared-default changes whose
consumers live outside the touched modules. The fix is scope escalation keyed on the
change kind, not abandoning module-scoping. A green module-scoped sweep on a
shared-default change is a false-confidence signal: the regression is in a directory the
sweep never visited.

## Related

- The consumer-repo migration corollary (project memory: "Known Consumer Repos Need
  marshal.json Migration After Config-Default Changes") — the same `_config_defaults.py`
  change-kind that triggers full-verify here is also what triggers downstream consumer
  marshal.json migration. Both are blast-radius consequences of a shared-default change.

## Recurrence — 2026-06-29 (remove-the-require-wrapper-knob-entirely-auto-dete): symbol REMOVAL, not just default-value change

The same blast-radius blind spot recurs for a **symbol removal**, widening this lesson
beyond shared-default *value* changes. The `remove-the-require-wrapper-knob` plan
removed the `require_wrapper` knob and its supporting symbols. A test —
`test_pyproject_build.py::test_execute_direct_returns_error_when_no_wrapper` —
referenced the removed symbol but was NOT listed in any deliverable's `affected_files`,
so the planning-phase footprint under-scoped the true consumer set. The break was
caught only by the orchestrator execute-exit verify gate; the phase-5
q-gate-validation sweep caught the sibling `test_pyproject_execute.py` but missed
`test_pyproject_build.py`.

What this occurrence generalizes:

- **`affected_files` completeness, not just verify scope.** The originating lesson
  framed the fix as escalating *verify scope*; this occurrence shows the upstream
  defect is incomplete `affected_files` *enumeration* at outline/plan time. A symbol
  whose definition lives in one file has test/consumer references that per-file-sibling
  reasoning misses — and a sweep that catches one sibling test can still miss another.
- **Trigger on symbol REMOVAL, not only default-value flips.** When a deliverable
  removes (or renames) a symbol — a config knob, constant, function, or class — grep
  the WHOLE source AND test tree (including project-local `test/` dirs) for every
  reference to the removed identifier at outline/plan time, and enumerate every match
  in `affected_files`. This is the symbol-removal counterpart of the `DEFAULT_PLAN_*`-
  value pre-check already named in "How to apply": same blast-radius root, same grep-
  the-tree remediation, extended from *value change* to *symbol removal/rename*.
