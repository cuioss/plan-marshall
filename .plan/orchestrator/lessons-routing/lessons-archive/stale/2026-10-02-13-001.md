# Self-review rounds only sweep surfaced lines, so prose a behaviour change made false on untouched lines survives round after round


## Observed (API-Sheriff PR #369, plan-23-session-route-scope-parity, 2026-10-01)

The pre-submission self-review ran six rounds (the first pass plus five loop-backs, 13:15Z to 19:44Z)
before the pull request existed. Every finding belonged to one class: a statement the plan's own
behaviour change had made false.

| Round | Finding | What was stale |
|-------|---------|----------------|
| 1 | 9a8292, b99e53 | `SealedSessionCookieCodec` FORMAT_VERSION Javadoc; `BffRuntimeProducer` refresh wording and a lambda parameter name |
| 2 | ac0132 | `TokenRefreshCoordinator.rotate()` Javadoc ("the one component the rotation may change") |
| 3 | c41253 | `CallbackEndpoint.CallbackOutcome` Javadoc, two `TokenRefreshCoordinator` Javadoc sites |
| 4 | c8dcd6 | `ReturnTargetScopes` Javadoc (a second caller existed); verifier dispatch failed, round unverified |
| 5 | ed0cf7 | `BffRuntimeProducer` inline comment enumerating the legs |
| 6 | e10859 | three "refresh token never presented twice" sites (false in cookie mode) and one ADR-0055 line |

The class was named after round 2 (decision a7afc0: all findings are doc-claim findings on prose the
finalize security hardening 499e5e93 invalidated or left behind; resolve by deletion). It still took
four more rounds and did not close: at the ceiling the operator chose "fix, then skip the check"
(decision 9d6b63).

## Why the rounds did not converge

- The surfacer offered 32 to 34 candidates in 13 to 15 of 87 to 97 files. The author's verdict stayed
  inside that set (decision fad1fd). The stale statements of the next round were each time on lines the
  diff did not touch, or in files that produced no candidate (decisions 3c65fe, 1b544b). A check that is
  driven by touched lines cannot see a sentence that became false because code elsewhere changed.
- A sweep that reported reading a file in full still missed a stale Javadoc in it (finding c8dcd6).
- The whole-file read of all 36 production files was only requested in round 6 (decision edb049), cost
  about 1.15 million tokens in that round alone, and the verifier still rejected it.
- Part of the fallout was caused inside finalize: the security-audit hardening changed behaviour
  (granted set follows the grant, new `sid`) after the execute phase had written the prose.

The six rounds found no behavioural defect. After the pull request was opened the review bots found
four (a missing fourth OIDC interaction-needed error, reserved-path values with a query or fragment, a
session recreated by an in-flight write after logout, hand-kept reason lists). A long doc-claim loop is
not a substitute for the external review, and it delayed it by about six hours.

## Directive

- Treat "statements this change made false" as a class from the first round. List the behaviours the
  plan changed (what holds now that did not, and the reverse), then read every production file of the
  diff in full, in small groups, together with the documents and ADRs that describe those behaviours.
  Do this before the candidate-driven round, not as the sixth.
- Resolve by deleting the over-claiming statement. Do not write replacement prose that makes a new
  claim to verify.
- A finalize step that changes behaviour (a hardening edit from the security audit) owes the same sweep
  for its own change in the same commit.
- When the verifier answers `may_close=no` because of a leftover outside the surfaced set, change the
  method (class sweep by whole-file read). Running another round of the same shape reproduces the result.
- Tool side: the surfacer should say in its report that statements on untouched lines are outside what
  it can see, so a clean verdict over its candidates is not read as a clean surface.
