# Re-anchor OP-emitted URLs to host port in native-container Keycloak client ITs

Re-homed from the TokenSheriff consumer store 2026-07-16 ([[feedback_manage_lessons_cwd_store_resolution]]).

**Context:** TokenSheriff PR #550 (OIDC client). The integration realm's `frontendUrl` is the Docker-internal `https://keycloak:8443`, which Keycloak emits verbatim in the discovery-document issuer, the login-page form-action (login-actions) URL, and discovery-advertised endpoints (e.g. `pushed_authorization_request_endpoint`). The `*IT` tests run on the CI runner **outside** the Docker network, where Keycloak is only reachable via the host port map `https://localhost:1443`.

**Why the new client ITs failed while the existing ones passed:** the passing validation ITs build every request URL themselves against `localhost:1443` and never follow a Keycloak-emitted URL. The new client ITs (auth-code login, PAR) FOLLOW Keycloak-emitted URLs, so they connected to `keycloak:8443` → `java.net.ConnectException`; and `DiscoverySpecIT` asserted the issuer equals `localhost:1443` when Keycloak actually advertises `keycloak:8443`.

**How to apply:** Client ITs that follow OP-emitted URLs need a `toExternal()` helper that re-anchors the emitted authority to the reachable host base (preserving raw path/query), applied at the login form-action POST and any discovery-sourced endpoint. The discovery issuer assertion must expect the realm `frontendUrl` value, not the host URL. These native-container Keycloak ITs cannot be validated locally without the container — confirm via CI.
