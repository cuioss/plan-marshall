# Merge-provenance helper recorded only the parent dotted path in its wholesale-subtree-copy branch, misclassifying freshly-merged children downstream — the existing test always had the child present so only the recursion branch was exercised and the bug slipped every in-house gate

## Context

During plan `finalize-lane-materialization` (PR #896), the `sync-defaults` merge path
used `_deep_merge_missing()` to fill absent config subtrees from defaults, and
`_materialize_finalize_lanes()` then classified each finalize step by provenance
(freshly-merged default vs pre-existing user config) to decide whether to materialize
an explicit `lane: off`.

`_deep_merge_missing()` had two structural branches:

1. **Per-element recursion** — when a subtree key was present on both sides, it
   recursed key-by-key and recorded provenance for each child at the child's dotted
   path.
2. **Wholesale subtree copy** — when a subtree was absent entirely, it copied the
   whole default subtree in one move and recorded provenance for only the PARENT
   dotted path, never stamping the copied children.

Because the wholesale-copy branch recorded only the parent path,
`_materialize_finalize_lanes()` could not tell that the freshly-merged step children
came from defaults, so it materialized them with their effective lane instead of
`off` — undermining the plan's own "infra steps must be opt-in" design.

The defect slipped every in-house gate and was caught by CodeRabbit PR review
(comment 533767). The existing unit test for `_deep_merge_missing` always had the
`steps` key present on both sides, so it exercised ONLY the per-element recursion
branch — the wholesale-copy branch (and its provenance-recording bug) was never
executed by any test.

## The bug

A merge/provenance helper with two structural branches recorded provenance correctly
in one branch (per-element recursion) and incorrectly in the other (wholesale subtree
copy — parent path only, children unstamped). Downstream logic that keys off the
provenance stamp then misclassified the wholesale-copied children.

The test gap is the load-bearing half: **a fixture that always presents the child key
triggers only the recursion branch, so a bug isolated to the wholesale-copy branch is
invisible.** Single-path coverage of a multi-branch function gives false confidence —
green tests certify the exercised branch, not the function.

## How to apply

- **When a merge / copy / provenance helper has distinct structural branches
  (per-element vs wholesale-subtree, present-key vs absent-key), write a fixture that
  triggers EACH branch.** For provenance-recording code specifically, the absent-subtree
  fixture (which drives the wholesale-copy branch) is the one that exercises the
  bulk-stamp path — do not rely on a present-key fixture that only recurses.
- **Provenance must be recorded at the granularity the downstream consumer reads it.**
  Here the consumer keyed off per-child provenance, so a parent-only stamp on the
  wholesale-copy path was structurally insufficient — the wholesale branch must stamp
  every copied descendant, not just the subtree root.
- Assert the downstream classification (`materialize` vs `off`) for a step that was
  merged via the wholesale-copy branch, not only for a step present in user config.

## Recurrence signature

- A helper with a present-key/recursion branch and an absent-key/wholesale-copy branch.
- Provenance / metadata is stamped correctly by one branch, under-stamped by the other
  (parent-only instead of per-descendant).
- The unit test's fixture always presents the key, exercising only the recursion branch.
- Downstream logic that reads the per-element stamp misclassifies the wholesale-copied
  elements; in-house gates pass and only the PR bot catches it.
