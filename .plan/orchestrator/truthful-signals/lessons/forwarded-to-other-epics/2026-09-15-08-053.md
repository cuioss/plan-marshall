# A partial batch write stranded documents because the index sync was not in a finally

Source: PR #1489 CodeRabbit inline finding 43da9d (resolution=fixed, TASK-043).

api_init builds the `initialised` list in a per-module loop over save_module_enriched and
then calls sync_module_index(initialised, project_dir) AFTER the loop, with nothing
guarding the exception path. A raise at module k strands the documents already written
for modules 0..k-1 with a _project.json still describing the description and generation
header they no longer carry.

The sibling names the correct shape exactly: _cmd_enrich._batched_index_sync flushes its
owed entries on the way out even when the body raised, and its docstring states the
reason in those terms. api_init was the one live-path writer not following it.

## Solution

Move the sync call into a `finally`, keep the existing `if initialised` guard so a run
that wrote nothing still performs no _project.json write, and extend coverage so the
EXCEPTION path is asserted rather than only implemented. No second parallel write path;
the staged `discover --force` writer stays out of the live path per the constraint
recorded in stamp_concept_document.

The recurrence worth noting: this is the SECOND finding in the same review about api_init
diverging from the enrich path's persistence discipline (see finding d82638). One writer
that skipped a shared convention produced two independent defects.

## Impact

Partial-failure corruption of the exact store whose truthfulness the plan targeted.
