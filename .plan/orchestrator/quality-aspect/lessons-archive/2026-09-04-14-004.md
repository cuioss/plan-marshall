# prepare_execute prepare's idempotent no-op path misses when called from inside the worktree

## Context

Plan `domain-glob-seeding` entered `5-execute` three times (`work.log` carries one `Starting` and two `Re-entering` markers, and `prepare_execute prepare` was invoked at `2026-09-03T22:43:38Z`, `2026-09-04T10:16:35Z` and `2026-09-04T10:32:00Z`).

On re-entry the verb returned `worktree_add_failed`, with the underlying git error `Branch feature/domain-glob-seeding existiert bereits` — although at that moment:

- the worktree at `.plan/local/worktrees/domain-glob-seeding` already existed and was checked out on that branch;
- the plan directory had already been moved into it per ADR-002;
- `status.metadata.worktree_path` and `worktree_branch` were both persisted.

Every precondition for the documented idempotent no-op held, and the no-op path did not trigger. The verb attempted `git worktree add` with a fresh-branch creation and failed on the branch that its own prior invocation had created.

## Root cause

The idempotency check does not hold when the verb is invoked **from inside the worktree it is being asked to prepare**. Under the cwd-pinned model (ADR-002) phase-5 re-entry runs with cwd already inside `.plan/local/worktrees/{plan_id}`, so a check that resolves the worktree root or the existing-branch state relative to cwd sees a different answer than it does from the main checkout — the same cwd-keyed resolution class as lesson `2026-08-30-16-001` (`manage-lessons consult`) and `2026-09-04-07-002`.

The failure was **invisible in the logs**: `script-execution-2026-09-04.log:3178` records it as

```text
[2026-09-04T10:32:00Z] [INFO] [32620c] plan-marshall:workflow-integration-git:prepare_execute prepare (0.37s)
```

— an `[INFO]` line with a duration and no status, because the verb returns `status: error` under exit code 0. `script-failure-analysis` classifies on exit code and stderr signature, so it reported 12 failures for this plan and none of them was this one. See lesson `2026-09-03-11-003` for that reporting half.

## Proposed action

1. **Resolve the worktree state main-anchored, not cwd-relative**, in `prepare_execute prepare`: read `status.metadata.worktree_path` / `worktree_branch` through `manage-status get-worktree-path` and test the resolved path, rather than deriving either from cwd.
2. **Take the no-op path on the three-way state, not on the add attempt's failure.** When `get-worktree-path` returns `worktree_state: materialized` and the resolved path exists and is checked out on the recorded branch, return the no-op success without calling `git worktree add` at all. Reaching `git worktree add` and interpreting its failure is what makes the outcome locale-dependent — the observed diagnostic was German, so any string match on the git message is wrong by construction.
3. **Add a regression test that invokes the verb with cwd set inside the target worktree**, since the main-checkout invocation already passes and is what the current tests exercise.
