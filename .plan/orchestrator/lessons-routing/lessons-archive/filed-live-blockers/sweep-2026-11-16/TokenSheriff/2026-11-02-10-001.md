# Status decided under a lock but published after release, and tests that pin less than the spec names

## Problem

In plan-21 (PR #849) CodeRabbit caught a lock-release race in `HttpJwksLoader.initJWKSLoader`: the status returned by `handleUnexpectedInitializationFailure` was decided under `lifecycleLock` but used to complete the reserved future after the lock was released. A concurrent `close()` in that window left the future completing with `ERROR`, contradicting the Javadoc promise that a superseded initialization completes with `UNDEFINED`. The same review found three under-pinned tests: a branch that asserted only the absence of a fixture instead of the exact message the spec names, a decode-mode group missing its quiet-mode case, and a destruction test that did not assert the JWKS loader was closed.

## Solution

When a status is computed under a lock and later used to complete a future or to publish a result, either publish inside the lock or re-check the state after releasing it, and cover the interleaving with a close or supersede in a test. When a spec names an exact message, pin it with an equality assertion; when a fixture has several modes (normal, quiet, opaque), cover every mode the production path branches on; when a test claims a resource was released, assert the release.

## Impact

The race is invisible in a single-threaded test run and only shows up as a wrong terminal status under concurrent close. Weak pins let a regression through that the test names suggest is guarded.
