title: "Recipe: obtain a post-hoc CodeRabbit review for an already-merged delta"
content: "## Context

When a delta reaches `main` without the review it was supposed to receive, the obvious recovery does not work: posting `@coderabbitai review` on the merged PR is refused with \"Pull request is closed\". This run needed that recovery after discovering post-merge that CodeRabbit had never reviewed the head it merged from, and established a route that does work.

## Root cause

Not a defect — a missing documented procedure. The recovery is non-obvious in two specific ways that each cause a silent failure on the first attempt, so every future occurrence re-derives it under time pressure.

## Proposed action

Document the recipe in the automatic-review recovery surface:

1. Create two throwaway branches at the endpoints of the unreviewed delta (here, `d75ded9e..1af15958`) and open a scaffolding PR between them.
2. Post an **explicit** `@coderabbitai review` comment. Auto-review does **not** fire on a PR whose base is a non-default branch, so the scaffolding PR is silent until asked.
3. That same base-branch filter is a benefit, not only an obstacle: it is why the scaffolding PR sidesteps the heavy `verify` workflow, so the recovery costs no CI.
4. Triage the resulting findings against the real target, fix them in a normal PR, then close the scaffolding PR **unmerged** and delete both throwaway branches.

Worked here: the recovered review found a Major (`parse_toon` deleting the first character of a shallow-indented block-scalar payload) and a Minor, fixed in PR #1441 (`05ca6fe7b`). Without the recipe both would have shipped unseen.

## Evidence

- PR #1440 — scaffolding PR, closed unmerged, both branches deleted.
- PR #1441 (`05ca6fe7b`) — the fixes the recovered review produced.
- observed refusal: `@coderabbitai review` on a merged PR returns \"Pull request is closed\".
- observed silence: the scaffolding PR produced no auto-review until an explicit trigger comment was posted."
