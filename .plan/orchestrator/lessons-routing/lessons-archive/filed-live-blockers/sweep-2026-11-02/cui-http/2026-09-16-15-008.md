# A cross-principal negative test passed vacuously because a new invariant made the asserted absence unreachable by construction

## Observation

A test asserted that a 4xx response must NOT serve a cached fallback, seeding the cache as
principal A and probing as principal B. But `generateCacheKey` unconditionally appends the
credential-derived `principalBinding` — exactly ADR-0023's invariant — so principal B never had a
cache entry to fall back on in the first place. The `cachedEntry != null` precondition was already
false; the test would have passed identically with the assertion under test deleted. The
`CachedFallbackRestriction` Javadoc compounded it by stating the two principals share one cache key,
which the implementation contradicts. Caught by CodeRabbit on PR #240. Fixed by seeding and probing
with the SAME principal so an entry actually exists, and correcting the stale Javadoc.

## Corrective

When a new invariant is introduced (here: per-principal cache-key binding), re-check every existing
test whose SETUP depends on the invariant NOT holding. Such a test does not fail — it goes green
and vacuous, the worst outcome. A negative assertion (`assertNull`, `assertNotServed`) is only
meaningful when a positive control proves the precondition it negates was reachable.

## Scope

Two-part sweep worth generalising: (1) tests asserting an absence guaranteed by construction rather
than by the behaviour under test; (2) Javadoc making a sharing/identity claim an ADR invariant has
since falsified. Both caught by an external review bot, not by the suite or the plan's own gates.
