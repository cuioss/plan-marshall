# A task that adds shared mutable state in a cache or single-flight refresh must carry an interleaving review and a stale-publisher test

A task that adds or changes a component holding shared mutable state across threads (a cache, a single-flight refresh, a compare-and-set publication) must carry an explicit interleaving review and at least one test that forces the stale-publisher interleaving, so the defect is found in 5-execute and not at finalize code-review.

## What happened

In plan client-refresh-verification-discovery-cache (PR #907), TASK-005/006 added `CachingDiscoveryResolver` (token-sheriff-client, discovery package), a cache with a single-flight refresh and a stale-grace policy. Execute-phase verification was green: compile, `verify -Ppre-commit`, and the adversarial and stale-policy tests. The finalize `default:code-review` step then raised a blocking finding (Q-Gate cdc31c, severity error, lines 164-177): a refresh that failed could overwrite a newer successful cache entry with a failed state derived from a stale snapshot. That forced a code-review loop-back (iteration 1/5) and an inline fix commit. The execute-phase tests had exercised only the single-thread success, failure and stale-grace paths; nothing modelled refresh A starting on snapshot S0, refresh B publishing S1, and A then failing and publishing "failed" over S1.

## Rule

- For each publish into shared state, confirm it is conditional on the snapshot it was derived from (compare-and-set or a version check).
- Add at least one test that forces the stale-publisher interleaving, with a negative control that fails when the guard is removed.
- Put the obligation in the task's verification profile for any component whose purpose is shared mutable state; otherwise only the finalize review catches it, and every fix there advances HEAD and re-runs the review rounds (see the companion candidate on review re-run cost).
