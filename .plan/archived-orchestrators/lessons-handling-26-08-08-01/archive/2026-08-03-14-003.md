# Retrospective session capture overwrites the plan's execution session_id

## Context

`plan-retrospective` SKILL.md Step 1 instructs the workflow to "capture the runtime session token for downstream metrics":

```bash
python3 .plan/execute-script.py plan-marshall:platform-runtime:platform_runtime \
  session capture --plan-id {plan_id}
```

`session capture` stores the **current** session id. When the retrospective runs as a dispatched finalize step it is executing in a *different* session from the one that ran the plan, so the call overwrites the plan's execution session id with the auditor's.

Observed on `content-search-seam`:

- `2026-08-02T20:52:03Z` — `[MANAGE-STATUS] Metadata: session_id=95a455ca-7744-4dc8-ae04-5a9a74a00c5c` (phases 1–5 session)
- `2026-08-03T14:02:45Z` — `[MANAGE-STATUS] Metadata: session_id=585eca2d-08c3-425a-8cba-526fee1ad608` (the retrospective's own session)

After the retrospective, `status.metadata.session_id` names a session in which no plan work was performed.

## Root cause

The field is written by a capture verb whose semantics are "the session I am in right now", but it is read by consumers whose semantics are "the session the plan ran in". The two agree for every producer except the retrospective, which is by construction a later, separate session looking backwards.

The damage is silent and one-way: the previous value is replaced, not appended, so the execution session id is not recoverable from plan state afterwards. On this plan the finalize session (2026-08-03) had already replaced the execute session's id in an earlier overwrite, so both prior ids are now gone.

## Proposed action

1. In `plan-retrospective` Step 1, do **not** call `session capture`. Read the stored `session_id` instead — that is the value the chat-history aspect and `manage-metrics enrich` both need — and pass the retrospective's own session id, if it is needed at all, as a separate field.
2. If a retrospective-scoped session id is genuinely required, store it under a distinct key (e.g. `metadata.retrospective_session_id`) so it cannot collide with the execution field.
3. Make the field append-only or list-valued. A plan that spans sessions (this one spanned at least three) has more than one execution session id, and a scalar field cannot represent that; the current shape guarantees data loss on every session boundary, not only at retrospective time.
4. Add a test asserting that running the retrospective against a plan leaves `status.metadata.session_id` byte-identical.

## Downstream impact

`manage-metrics enrich --session-id` resolves per-phase token attribution by walking the transcript for that session. Run after the retrospective with the stored id, it walks the **retrospective's** transcript and attributes the auditor's spend to the plan's phases. `record-metrics` is ordered after `plan-retrospective` in this plan's manifest, so this is the live ordering, not a hypothetical one.

## Evidence

- plan: `content-search-seam`, work.log 2026-08-02T20:52:03Z and 2026-08-03T14:02:45Z.
