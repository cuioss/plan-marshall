# finalize-step-simplify can propose reverting a fix that automatic-review committed in the SAME run — the pipeline has no reconciliation contract and relies on ad-hoc orchestrator judgment to honor the in-run reviewer commitment

**Context:** Plan `architecture-resolution` (PR #917), phase-6-finalize. Two finalize-pipeline stages that both look at the same diff disagreed within a single run, and only orchestrator judgment prevented an automated revert of a reviewer-requested fix.

## What happened

1. `automatic-review` triaged a Gemini suggestion to **FIX** — it added a membership guard (TASK-015). The fix was committed and the disposition acknowledged on the PR review thread.
2. `finalize-step-simplify`, running **later in the same run**, analyzed the diff and flagged that exact guard as provably-dead code, proposing to revert it.
3. The orchestrator **declined the simplify revert** to honor the in-run reviewer commitment already acknowledged on the PR thread.

The outcome was correct, but only because a human-in-the-loop-style orchestrator judgment intercepted it. There is no documented reconciliation contract between the two steps: had the orchestrator applied the simplify proposal mechanically, the pipeline would have silently reverted a fix it had committed and publicly acknowledged to the reviewer minutes earlier — a self-contradicting changeset and a broken commitment to the review bot.

## Root cause

`automatic-review` (a loop-back that ADDS defensive/guard code to satisfy a reviewer) and `finalize-step-simplify` (a later pass that REMOVES provably-dead code) operate on the same diff with no awareness of each other's in-run actions. A guard added purely to satisfy a reviewer can be genuinely unreachable, so simplify's dead-code verdict and the reviewer's fix-request are both individually correct yet mutually exclusive. The pipeline has no rule for which wins, so the reconciliation defaults to ad-hoc orchestrator judgment.

## Corrective direction

Give the finalize pipeline an explicit reconciliation contract instead of leaning on ad-hoc judgment. Candidate mechanisms (design at outline time, do not assume one here):

- Treat lines committed by a same-run `automatic-review` fix as an out-of-scope / do-not-remove set for a later `finalize-step-simplify` (mirroring how simplify already respects the changeset-scope boundary — see lesson `2026-06-25-08-003`).
- When simplify flags code that a same-run reviewer commitment introduced, do NOT silently revert — surface the conflict explicitly (back to the reviewer thread or to the operator) rather than resolving it inside simplify.

## Why it slipped every in-house gate

Both steps passed their own contracts: the review fix was committed and acknowledged; the simplify analysis was correct that the guard was dead. Neither step is individually wrong, so no per-step gate flags the contradiction — only a cross-step reconciliation view (which the pipeline lacks) exposes it.
