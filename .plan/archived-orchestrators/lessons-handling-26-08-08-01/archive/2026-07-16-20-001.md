# compose change_type sourced from the first deliverable can be unrepresentative when that deliverable is a deliberately-sequenced outlier, silently dropping simplify/security-audit finalize steps

## Context

During phase-4-plan Step 7b (execution manifest compose) for `execution-manifest-gaps`, the
Step 7b input contract instructs: "change_type — read from solution outline metadata (use the
first deliverable's change_type when the outline has more than one)". This plan's six
deliverables are, in order: `verification` (deliverable 1 — retire two stale lessons),
`bug_fix` (2), `enhancement` (3), `bug_fix` (4), `tech_debt` (5), `bug_fix` (6). Deliverable 1
was deliberately sequenced first by the outline author ("Do this FIRST so no later task fixes
a non-bug") — a small, atypical housekeeping cleanup, not representative of the plan's actual
bulk of work (four bug_fix/enhancement deliverables touching 14 files).

Following the documented rule literally, `compose --change-type verification` was passed. The
composer's `simplify_inactive` / `security_audit_inactive` pre-filters gate on
`change_type ∈ {feature, bug_fix, tech_debt}` — `verification` is not a member, so both fired
and dropped `finalize-step-simplify` and `finalize-step-security-audit` from `phase_6.steps`,
even though `affected_files_count == 14 > 0` and the plan's real work is squarely bug-fix
shaped. (Notably, this exact plan's own deliverable 2 fixes an analogous gap: the composer's
`_SIMPLIFY_CHANGE_TYPES` frozenset silently excluding `enhancement`.)

## Root cause

The "first deliverable's change_type" heuristic assumes deliverable order correlates with the
plan's dominant nature. That assumption breaks when the outline deliberately orders a small,
atypical deliverable (verification-only cleanup, docs-only correction, etc.) ahead of the
plan's substantive work for execution-sequencing reasons unrelated to manifest composition.
The heuristic has no majority-vote or severity-weighting fallback, so a single outlier
deliverable can silently steer the composed manifest's ceremony-gate decisions for the whole
plan.

## Status — security-audit leg fixed 2026-07-29 (plan `ceremony-prefilter-dropped-the-security-audit`)

The `finalize-step-security-audit` half of this defect is fixed. The composer's
`security_audit_inactive` pre-filter (change_type-gated, shared logic with `simplify_inactive`)
was replaced with `security_class_inactive`: it has no `change_type` leg at all — it fails
toward inclusion, dropping a security-class step only when both the declared
`affected_files_count` AND the live footprint are empty — and its population is derived from
each candidate's `persona: persona-security-expert` frontmatter scalar rather than a hardcoded
step id. Every drop is now recorded as a `{step, reason}` list plus a `[STATUS]`
decision-log line that `phase-4-plan` Step 7b surfaces, so an omission is loud rather than a
silent absence from the step list.

**`finalize-step-simplify` remains fully exposed.** The fix explicitly left `simplify_inactive`
and its shared `_apply_code_step_inactive` gate untouched — the first-deliverable change_type
heuristic this lesson documents still silently drops `finalize-step-simplify` on exactly the
outlier-first-deliverable shape described above. The Recommended action below still applies,
now scoped to `finalize-step-simplify` only.

## Recommended action

When phase-4-plan's Step 7b change_type derivation would select an atypical first deliverable
(e.g., `verification` or `analysis` while later deliverables are `bug_fix`/`enhancement`/
`tech_debt`), the phase should not apply the literal first-deliverable rule uncritically to
`finalize-step-simplify`'s `simplify_inactive` gate (the only remaining consumer of this
heuristic after the security-audit fix above):

- Consider deriving `change_type` from the majority/dominant deliverable type (or from
  `status.metadata.change_type`, independently classified by phase-3-outline Step 4's
  heuristic against the whole request) rather than strictly "first deliverable" when the
  deliverable set is heterogeneous.
- At minimum, when this divergence is detected, log a decision entry naming the chosen
  change_type and its consequence (that `finalize-step-simplify` was dropped) so the
  finalize-phase reviewer is not silently surprised.
- The durable fix is at the tool layer (phase-4-plan Step 7b): make the change_type-selection
  rule aware of deliverable-type heterogeneity, e.g. select the modal (most common) change_type
  across deliverables, falling back to the first deliverable's value only when there is no
  clear majority. Alternatively, mirror the security-class fix's approach — a no-change-type,
  fail-toward-inclusion gate — if `simplify_inactive` is ever revisited.

## Evidence

Plan `execution-manifest-gaps` (this plan). Step 7b compose returned
`simplify_omitted: true`, `security_audit_omitted: true` from `--change-type verification`
(deliverable 1's type), while deliverables 2/3/4/6 are `bug_fix`/`enhancement` touching 14
files. Logged explicitly via a decision-log WARNING at compose time so the finalize reviewer
sees the consequence; this lesson records the recommended durable fix for phase-4-plan's own
compose-input derivation.

## Recurrence — 2026-07-21 (domain-conditional-loading-concept)

Second confirmed instance. PLAN-25 is a design-first plan whose first four deliverables are
docs/specs (ADR-010, ext-point-domain-verb, domain-aware-notation-spec, domain-residency
inventory) and whose fifth deliverable (D5) is a production-code fix to
`manage-execution-manifest.py` plus a regression test. Compose classified the plan
`change_type=analysis` (`affected_files_count=7`) and both ceremony pre-filters fired,
dropping `finalize-step-simplify` and `finalize-step-security-audit` (decision.log entries
`92a6b3`, `427325`), even though the realized footprint DID touch production code. The
plan-retrospective routing-decisions aspect flagged this as a `mis_prune:finalize-step-simplify`
(predicate `no_code_delta` false against the realized footprint). Note the divergence:
`status.metadata.change_type=bug_fix` (phase-3-outline's whole-request heuristic detected
`bug_fix`, confidence 0.75) yet compose's ceremony pre-filter used `analysis` — reinforcing the
recommended durable fix (derive the ceremony-gate change_type from the modal deliverable type or
from `status.metadata.change_type`, not a doc-heavy leading deliverable). Practical impact here
was low: the D5 code delta was still gated by pre-push-quality-gate (ruff+mypy), module-tests,
and plugin-doctor — `simplify`/`sonar-roundtrip` are additive passes, not the sole gate.
