# Finalize-step worktree mutation after the phase-5 build staleness-invalidates the pre-commit freshness gate, forcing a redundant rebuild

## Context

While finalizing `an-infeasible-mid-execute-deliverable-must-be-repo` (PR #724), the
phase-6-finalize pre-commit freshness gate (the `manage-change-ledger` worktree-sha
freshness API that certifies the last build matches the current worktree HEAD) went
**stale mid-finalize**. A finalize step that runs *after* the phase-5 build —
specifically the plugin-doctor executor regeneration / cache-sync step — mutated the
worktree (regenerated derived state under the tree), advancing the worktree SHA past
the SHA stamped on the most recent `kind=build` ledger entry. The freshness gate
correctly detected the mismatch and forced a **redundant full rebuild** before commit.

## The bug

The defect is finalize-step **ordering**, not the freshness gate. The freshness gate is
working as designed: it refuses to certify a build whose stamped worktree SHA no longer
matches the live tree. The problem is that a finalize step which mutates the worktree
(executor regen, cache sync, or any derived-state writer) is sequenced *after* the
build-verification step it invalidates. Every such interleaving guarantees a wasted
rebuild: build → mutate-tree → freshness-gate-fails → rebuild.

Symptom signature:

- The phase-5 build/verify completed green and stamped a `kind=build` ledger entry at
  worktree SHA `A`.
- A later phase-6-finalize step writes into the worktree (regenerates `execute-script.py`,
  syncs the plugin cache target, or otherwise touches tracked/derived files), advancing
  the worktree SHA to `B`.
- The pre-commit freshness gate compares HEAD/worktree SHA `B` against the build entry's
  SHA `A`, finds them unequal, and re-triggers a full build that produces identical
  results — pure wasted wall-clock and tokens.

## Root cause

A worktree-mutating finalize step is allowed to run between the authoritative build and
the freshness-gated commit. The freshness contract assumes the worktree is frozen from
the last build through commit; any step that writes derived state into the tree after the
build breaks that assumption. The two classes of finalize step have conflicting
relationships with the freshness gate and must not interleave naively:

- **Tree-mutating steps** (executor regen, cache-sync target writes, simplify edits) —
  must complete *before* the authoritative build, OR their output must be excluded from
  the freshness-relevant SHA, OR they must explicitly re-stamp a fresh build entry.
- **Verification/gate steps** (the freshness check, commit) — assume a frozen tree.

## How to apply

**Ordering prescription — SHIPPED (plan-8-context-trim, PR #899). Do not re-propose it.**
The "sequence every worktree-mutating step ahead of the authoritative build/commit" fix is
now the codified finalize model: phase-6-finalize is a **mutation-settling stage**
(`SKILL.md` § "Mutation-settling stage (settle → push once → wait)") in which every local
HEAD-changing step settles at `order < 10`, the single `default:push` barrier ships the
settled HEAD at `order: 10`, and the wait region runs after it. Ordering is governed by each
step doc's `order:` frontmatter resolved through the single choke-point
`_manifest_validation._sort_steps_by_frontmatter_order` (consumed by both the manifest
composer and `manage-config steps-sort`). The dispatcher's commit instrumentation
(`SKILL.md` Step 3 item 5f) commits each `mutates_source: true` step's edits before the
barrier — so, as that contract now states, "push only once the mutating quality steps have
converged falls out of plain `order:` values with no special placement invariant."

The residual, still-uncovered concern is the **doc-only freshness-neutrality** point in the
Recurrence section below — the gate still cannot distinguish a markdown-only mutation from a
source mutation, and still rebuilds regardless.

Related: [[feedback_orchestrator_owns_long_builds]] (long builds are expensive; a wasted
finalize rebuild compounds that cost), and the ADR-002 per-tree derived-state model that
makes the executor a worktree-mutating artifact at finalize.

## Recurrence — 2026-07-11 (steward-sync-defaults-executor-stale-noop)

A doc-only plan (edited a single `mode:workflow` SKILL.md — zero compiled/source-behavior
change) hit this exact ordering defect through the **finalize commit path**, in an
amplified form:

- `finalize-step-simplify` committed **twice** — once on the forward pass, and again on
  the automated-review loop-back re-fire. **Each** commit advanced the worktree SHA past
  the last `kind=build` stamp, re-staling the pre-push freshness gate and forcing a full
  compile re-run before push.
- Because the diff was markdown-only, every one of those rebuilds was **pure
  ledger-refresh ceremony** — nothing a compile can affect had changed, yet the gate
  cannot distinguish a doc-only mutation from a source mutation, so it rebuilds regardless.
- On the loop-back, the re-stale also forced a **fresh ~13-min CI wait** before push,
  compounding the wasted wall-clock well beyond a single local rebuild.

Broadened scope / additional corrective action:

- For a **doc-only changeset** (no files under the freshness-relevant source/compile set),
  a finalize commit should be freshness-neutral: either exclude markdown-only diffs from
  the freshness-relevant SHA, or let the gate short-circuit the rebuild when the delta
  since the stamped build touches only non-compiled paths. A markdown-only finalize commit
  forcing a full compile + CI wait is the doc-only face of this same ordering defect.
- The loop-back re-fire double-counts the cost: any finalize step that both commits AND
  can re-fire on loop-back should re-stamp (or freshness-neutralize) its commit so the
  second fire does not re-trigger the whole build + CI cycle.

## Recurrence — 2026-07-21 (orchestrator-dispatch-ruleset)

Third occurrence, and the one that upgrades the diagnosis: for a **docs-only footprint**
this is not merely a wasted rebuild — it is a **structural deadlock between two gates that
disagree by construction**.

Sequence observed (twice in a single run — once at phase-5 exit, and again after the
automated-review loop-back commit):

1. `build-decision` evaluates the live footprint, matches no `build_map` glob (the change
   was a two-word markdown edit), and correctly rules the build `not_necessary`.
2. Because no build runs, **no `kind=build` ledger entry is ever stamped** at the current
   worktree SHA. Not "a stale one" — *none*.
3. `pre-commit-verify-freshness` then fails **closed**, demanding exactly the artifact
   step 1 guaranteed would never be produced.

The only way forward was to run a whole-tree pytest (~200 s each time) whose sole purpose
was to stamp a ledger row — a build that `build-decision` had just certified as
unnecessary, executed purely to satisfy a gate that cannot read that certification.

### Why this is more than the doc-only-neutrality point above

The 2026-07-11 recurrence framed the docs-only case as *wasteful* (the gate rebuilds
because it cannot distinguish markdown from source). This run shows the stronger property:
the two gates hold **contradictory premises about the same footprint**, so a docs-only plan
has no legal path through finalize at all.

- `build-decision` premise: "no buildable footprint ⇒ no build entry should exist."
- `verify-freshness` premise: "a build entry stamped at the current SHA must exist."

For any footprint where the first premise holds, the second is unsatisfiable except by
violating the first. Recurrence is guaranteed on every docs-only plan, and it re-fires once
per post-build commit (loop-back, mutating finalize step), so the cost scales with the
number of settle-stage commits rather than being paid once.

### Corrective action

Make the freshness gate consume `build-decision`'s verdict instead of assuming a build
always happens. Concretely, the gate needs a third outcome alongside fresh/stale:

- **`not_required`** — `build-decision` ruled the footprint `not_necessary` for the
  current worktree SHA ⇒ the absence of a `kind=build` entry is the *correct* state, and
  the gate passes without demanding one (recording the docs-only attribution in the work
  log so the pass is auditable, never silent).

Equivalently and preferably, have the docs-only path stamp a **zero-cost freshness token**
(a `kind=build` entry with `decision=not_necessary` and no build executed) so the ledger
stays the single source of truth and the gate needs no special case at all. Either shape
is acceptable; what is not acceptable is the current state where the resolution is "run a
build you were just told not to run."

Note the same premise is already handled correctly one layer up in CI:
`.github/workflows/python-verify.yml` opts in to `skip-on-docs-only: true` and still
reports the required check green. The local finalize chain is the only place where the
docs-only footprint has no green path.
