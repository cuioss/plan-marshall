# Unguarded read_text(encoding=utf-8) at a real I/O boundary raises uncaught UnicodeDecodeError instead of a structured refusal

## Context

Second, independent defect caught in the same finalize review pass
(plan-41-phase-1-init-spec-ingestion), same script surface (`_cmd_request.py`).

## Symptom

`_cmd_request.py` reads a referenced spec file via
`.read_text(encoding='utf-8')` with no guard. A non-UTF-8 file at that path
raises an uncaught `UnicodeDecodeError` that propagates out of the script
instead of the intended structured refusal (e.g. `spec_pointer_unreadable`).

## Root cause / archetype

An I/O boundary that has already committed to a structured-failure contract
for one class of unreadable input (missing file) must apply the same
contract to every other class of unreadable input (undecodable bytes).
Treating "exists but can't be decoded" as an unhandled exception instead of
routing it through the same fail-loud/structured-refusal path leaves a real
trust-boundary gap: externally-influenced file content can crash the
ingestion step instead of being cleanly rejected.

## Fix

Wrap the `read_text` call at this boundary in a guard that catches
`UnicodeDecodeError` (and any other decode-class failure) and routes it into
the same structured-refusal path used for a missing pointer.

## Generalization

Any `read_text` / `open(...).read()` call at a boundary that ingests
externally-influenced file content must enumerate ALL of "missing",
"unreadable" (permissions/IO), and "undecodable" (encoding) as first-class
failure branches with the same structured-refusal shape — not just the
first failure class the author thought of. This is a required-real-boundary
error-handling gap, distinct from (but sibling to) the syntax-vs-existence
classification defect recorded in lesson 2026-07-23-10-002 on the same
component.
