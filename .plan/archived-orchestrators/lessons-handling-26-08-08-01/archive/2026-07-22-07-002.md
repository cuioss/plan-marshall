# New audit/logging emission on a routing seam must suppress itself on daemon-child re-entrancy or it double-emits

## Context

Plan `client-resolution-log-capture` (07-21/07-22) added `_record_resolution` to `_build_execute_factory.py` — the single audit call that emits the `[BUILD-SERVER] resolved build (requested=..., resolved=..., reason=..., notation=..., plan=...)` line, the fix that finally made the client's daemon-routing decision visible (previously a handler-less `logger.info` call, silently discarded — see lesson `2026-07-21-14-001`).

## Symptom

CodeRabbit (PR #971, inline comment on `_build_execute_factory.py:618`, finding `c77ed5`) caught: a routed build re-executes the *same command* inside a `MARSHALLD_JOB` daemon-child process. The child receives `reason='in_daemon_job'` back from `_route_to_daemon`, and the newly-added, unconditional `_record_resolution` call fired a **second time** on that child — emitting `resolved=in_process` immediately after the routing parent had already emitted `resolved=routed` for the identical logical request. One routed build therefore produced two contradictory `[BUILD-SERVER] resolved build` stderr lines (and two work-log records whenever `--plan-id` was forwarded).

## Root cause

Any code path that can be re-entered as its own daemon child (the `MARSHALLD_JOB` env / `in_daemon_job` reason marker) executes the **identical function body** as the parent invocation. Adding a new logging/audit/metrics call to that body without first checking for the re-entrancy marker makes the emission fire once per **physical process**, not once per **logical client request** — silently producing a duplicate, contradictory record for what the caller experiences as a single event.

## Fix (landed in this plan)

`_build_execute_factory.py` now derives an explicit `in_daemon_child` boolean from `reason == 'in_daemon_job'` and gates the in-process branch's `_record_resolution` call on `not in_daemon_child`:

```python
if not in_daemon_child:
    _record_resolution(execution_mode, 'in_process', fallback_reason, notation, plan_id)
```

The routing parent — which already recorded `resolved=routed` before spawning the child — owns the sole audit record for the request; the child suppresses its own.

## Rule

Before adding a new logging/audit/metrics emission to any code path, ask: **"can this function body execute twice for one logical request — once as the parent, once as a re-entrant daemon/worker child?"** If yes, identify the re-entrancy marker (an env var, a routing-reason string, a re-entry flag threaded through the call) *before* writing the emission call, and gate the new side-effect on it. Do not add the emission first and rely on code review to catch the double-count — the daemon-re-entrancy shape is easy to miss because the duplicate only surfaces on the *routed* path, never on a plain in-process run, so a quick local smoke test will not reproduce it.
