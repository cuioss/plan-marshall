# Async lifecycle close(): bind a generation up front and fence every side effect and read path, not only the publish

## Problem

A component with close/re-init semantics and asynchronous work (init future, scheduled refresh, endpoint resolution) had its races found one narrow window per review round. In `HttpJwksLoader` (plan-01, PR #830) the code review hit its loop-back ceiling of 3 rounds: reserving the init future and clearing `closed` were two non-atomic steps; a generation superseded by `close()` completed ERROR instead of UNDEFINED; the same wrong outcome in the window between `adoptResolution` and `publishStatus`; a Javadoc promised re-init that an owned, shut-down executor made impossible. An epoch binding closed the family. In plan-07 (PR #844) the epoch fence covered the publish path but not every side effect of the cycle: a failed cycle's `finally` still incremented the failure counter after `close()` reset it, `close()` during re-discovery still ran the egress check and a blocking fetch, and the staleness-degraded state was bypassed by the access-token cache hit path and by an awaited OK future in `IssuerConfigCache`. Seven review findings, two loop-backs.

## Solution

Design generation or epoch binding up front. Every async completion checks that it belongs to the current generation before it publishes state. Then enumerate EVERY side effect of the fenced cycle (counter mutations, fetches, egress checks, flag sets) and EVERY read path that can serve the guarded state (caches, awaited futures), and gate or test each one. A Javadoc claim of the form "X never happens after close or degrade" needs a mechanism and a test at every site, including one test per publish point that closes the component inside that window. When two consecutive loop-backs cite the same root cause, fix the whole class, not the cited line.

## Impact

Avoids repeated review rounds for what is one design defect, and avoids a security-relevant bypass (a degraded issuer still served from cache).
