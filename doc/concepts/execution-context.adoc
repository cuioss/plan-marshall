= Execution Context
:nofooter:
:toc: left
:toclevels: 2

xref:../../README.md[Plan Marshall] » xref:README.adoc[Concepts]

Each subagent dispatch in a stock assistant session is often a fresh ad-hoc invention — a different prompt shape, an arbitrary tool subset, an inconsistent skill load order, and unmanaged model assignments. Reproducibility suffers, model-tier selection per workflow is impossible, and prompt contracts drift with every change.

Plan Marshall solves this by shipping **exactly one role-eligible canonical agent** — `plan-marshall:execution-context` — and every `Task:` / subagent invocation in the marketplace dispatches through it. One canonical agent file; seven level-suffixed variants emitted at build time; and a structured prompt-body contract that every workflow body declares against.

== One Generic Dispatcher

`plan-marshall:execution-context` is the sole role-eligible canonical agent in the marketplace. It encapsulates the dispatcher lifecycle (load `persona-plan-marshall-agent`, load caller-specified skills, locate the workflow doc, execute, emit return TOON) exactly once, parameterising the workflow body at dispatch time. The caller passes five prompt-body fields:

* `name` — human label for logging and `mark-step-done`
* `plan_id` — plan identifier (or the sentinel `none` for free-standing dispatches)
* `skills[]` — caller-loaded skills, in deterministic load order
* `workflow` — bundle-prefixed notation for the workflow doc to run (e.g. `plan-marshall:phase-3-outline/SKILL.md`, `plan-marshall:plan-marshall/workflow/triage.md`)
* `WORKTREE` — repo-relative working directory (`.` for main checkout)

The dispatcher loads `persona-plan-marshall-agent` implicitly, then the caller-specified `skills[]`, then reads the resolved workflow path and executes it. Workflow-specific runtime inputs (`finding_type`, `track`, `scope`, etc.) flow through additional prompt-body fields declared by the workflow doc.

A new LLM-judgement workflow worth pinning its own model is added simply by authoring a workflow doc that declares `implements: ext-point-execution-context-workflow` and registering a new role key. No new agent file and no new emitted variant families are required.

[#level-variants]
== Level Variants & The Two-Axis Model

Plan Marshall models compute demand using an abstract seven-tier ordinal scale (`level-1` through `level-7`, plus `inherit`). Each level represents a coordinate in a **Two-Axis Effort Model**:

$$\text{Level} = (\text{Model Axis}, \text{Effort Axis})$$

* **Model Axis (Capacity)**: Selects the model class (e.g. fast/compact vs. frontier reasoning).
* **Effort Axis (Reasoning Intensity)**: Controls the thinking budget or reasoning effort (e.g. `low`, `medium`, `high`, `max`).

=== Target Realization & Local Ladders

The project repository (`marshal.json`) configures only the target-neutral level intent. The concrete mapping of levels to native engine primitives is determined machine-locally via `.plan/local/effort-ladder.json` (git-ignored), with built-in defaults seeded by `marshall-steward`:

[cols="1,2,2,2", options="header"]
|===
| Dimension | Claude Code | Google Antigravity | OpenCode

| **Subagent Definition**
| Emitted agent files (`target/claude/.../agents/execution-context-level-N.md`)
| Emitted agent files (`target/antigravity/agents/execution-context-level-N.md`) deployed to `~/.gemini/config/plugins/...`
| Emitted agent files (`target/opencode/agent/execution-context-level-N.md`) deployed to `~/.config/opencode/agent/`

| **Frontmatter State**
| Static (`model:`, `effort:`) baked at generate time
| Static (`model:`, `effort:`) baked at generate time
| Static frontmatter; unpinned (`inherit`) in all emitted variants

| **Session Cache Lifecycle**
| **Session-pinned**: Scanned once at session boot; mid-session variant changes require `/reload-plugins` or restart.
| **File-backed**: Antigravity reads plugin files dynamically on dispatch.
| **File-backed**: OpenCode reads markdown agent files dynamically on dispatch.

| **Default Behavior**
| Emits with canonical default ladder (`haiku` through `fable max`).
| Emits with **Option 1 default ladder** (`flash low` through `pro high`).
| **Stays at `inherit`**: Because agent files are static markdown definitions and OpenCode has no universal provider or built-in in-place re-emitter, all OpenCode level variants emit without `model:`, cleanly inheriting the caller's session model.
|===

=== Unconfigured Fallback

If `.plan/local/effort-ladder.json` is absent or the active target is unconfigured, all variants emit unpinned (`inherit`) and a visible warning is logged.

[#per-role-model-selection]
== Per-Role Model Selection

The assignment of models and effort levels to LLM-judgement workflows reduces to three concepts:

1. **Levels**: The seven ordinal tiers (`level-1` through `level-7`) plus the `inherit` sentinel.
2. **Roles**: The phase-scoped registry of LLM-judgement workflows that can be assigned a level — covering phases `phase-2-refine` through `phase-6-finalize`.
3. **Variants**: The emitted agent files (`execution-context-level-1.md` .. `level-7.md`) and canonical dispatcher (`execution-context.md`).

The runtime path:
* The caller invokes `manage-config effort resolve-target --phase <phase> [--role <subkey>]`.
* The resolver walks: `phase.role` → `phase.default` → `phase` shorthand → plan-wide `effort` → `inherit`.
* The resolver returns the variant agent name (e.g. `plan-marshall:execution-context-level-3`), which the orchestrator dispatches.

== Granularity

Not every step belongs in its own dispatch. The granularity heuristics in link:../../marketplace/bundles/plan-marshall/skills/extension-api/standards/dispatch-granularity.md[`extension-api:dispatch-granularity`] govern the call:

* **Script-over-dispatch**: Deterministic operations (regex matching, JSON manipulation, build calls) belong in scripts. Subagents are reserved for LLM judgement.
* **Bundle-shared-context**: Multi-step LLM workflows run inside ONE dispatch envelope rather than multiple sequential dispatches.
* **Parallel fan-out**: Subagent fan-out is justified only when each subagent performs independent parallel work.

== Dispatch Lifecycle

Dispatches are synchronous. The calling orchestrator suspends on the subagent invocation for the entire duration of the subagent run (skill loads, workflow execution, internal loops, user interactions) and resumes only when the subagent completes its task and returns its structured TOON record.
