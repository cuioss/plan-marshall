# Maven build rewrites package-lock.json every run, so a finalize freshness gate cannot see a tree that is both clean and build-observed

# Freshness gate plus lockfile-rewriting build makes a clean-and-build-observed tree unreachable in finalize

## Cross-repo note

The `component` above names the `plan-marshall` bundle, which the
`nifi-extensions` repo does not own. Filing this into the nifi-extensions
lessons store would be refused with `error: wrong_store`. It belongs in the
marketplace repo's store, or needs `--allow-foreign-store` if deliberately
filed locally. The *second half* of the observation below is genuinely
project-local (`nifi-cuioss-ui`) and could be split out under a prefix-less
component.

## What happened

Two independent facts collided during plan `config-surface-traps`' finalize
and produced a state the freshness gate could not be satisfied from:

1. **The freshness gate hashes git state, not just file content.**
   `pre-commit-verify-freshness` re-stales on ANY finalize-internal commit — not
   only on commits that touch build inputs. So a finalize round that commits
   anything at all (a review-fix, a doc touch, a re-stamp) invalidates a build
   observation that is still substantively valid.

2. **This project's Maven build rewrites `nifi-cuioss-ui/package-lock.json`
   on every `verify -Psonar` run.** The locally-installed npm strips the `libc`
   fields that dependabot's npm emits, so running the build always dirties the
   lockfile.

Together: running the build to satisfy the freshness gate dirties the tree
(fact 2); committing the regenerated lockfile to clean the tree re-stales the
gate (fact 1). The tree can never be simultaneously clean and build-observed
unless the regenerated lockfile is committed *and* the gate is then re-run —
one extra mandatory round every time.

## The corrective rule

- When a finalize round on this repo needs a fresh build observation, **commit
  the regenerated `nifi-cuioss-ui/package-lock.json` first**, then run the
  build, then let the gate observe. Do not treat the lockfile diff as
  accidental churn to be discarded — discarding it guarantees the next build
  re-creates it.
- Longer-term project fix: pin the npm toolchain so local and dependabot npm
  emit the same lockfile (commit `c6a5982` "normalize package-lock to the
  pinned npm toolchain" is the same defect class recurring). Until the two
  emitters agree, this trap is structural, not incidental.
- Longer-term plan-marshall question for the epic: a freshness gate keyed on
  git state alone cannot distinguish "a commit changed a build input" from "a
  commit happened". Whether it should is an epic-level design call, not a
  plan-level one.
