# Triage leaf writes tests it structurally cannot run, with CI as the only covering gate

## Context

Both `verification-feedback` triage passes on `content-search-seam` closed with the same caveat, in near-identical wording:

```text
CAVEAT: module-tests resolves execution_tier=orchestrator (747s, exceeds_bash_ceiling) so the new
tests were NOT run in this leaf -- quality-gate (mypy 269 files, ruff, SPDX) passed clean and
ci-verify on the re-push is the covering gate.
```

```text
CAVEAT: module-tests resolves execution_tier=orchestrator so the 4 new/changed tests were NOT run
in this leaf -- whole-tree quality-gate passed clean at the log layer [...] and CI on the re-push
is the covering gate.
```

Across the two passes, 13 findings were fixed inline and 4 new or changed test modules were written. None of those tests was executed before the commits were pushed.

## Root cause

`persona-plan-marshall-agent` already specifies the correct behaviour:

> **`execution_tier: orchestrator`** — […] Sub-agents MUST NOT invoke the command via Bash from inside the dispatch. When the loaded workflow documents a hand-off step, follow it; otherwise return control to the orchestrator (with a TOON indicating the command cannot run within this dispatch) […]

The leaf complied with the first clause (it did not run the command) but the second clause has no target: `verification-feedback.md` documents no hand-off step, and returning control mid-triage would abandon partially-applied fixes. The only remaining action is to proceed and record a caveat, which is what happened — twice, correctly, by a leaf behaving as well as the contract permits.

So the gap is structural, not behavioural. The persona says "otherwise return control"; the triage workflow makes returning control the worse option; and the caveat is where the tension is discharged into prose.

## Why the compensating gates are not equivalent

- **quality-gate** runs mypy, ruff and SPDX. It type-checks a new test module; it does not execute it. A test that passes both pre- and post-fix — the vacuous-test failure mode lesson `2026-07-16-17-004` names — is invisible to it.
- **CI on the re-push** does execute the tests, but only after the commit is pushed, and its failure lands as a new finalize loop-back. On this plan the loop-back budget was already exhausted (see `2026-08-03-14-001`), so a CI-detected test failure at that point had no iteration left to absorb it.

The gates are real, but neither answers the question the leaf could not: *does this new test discriminate?*

## Proposed action

1. Add an explicit orchestrator hand-off to `verification-feedback.md`: when a triage pass writes or modifies test files and the covering verification resolves `execution_tier=orchestrator`, the leaf returns a `tests_pending_orchestrator_run` signal alongside its applied fixes, and the orchestrator runs module-tests in its own envelope before the push rather than after.
2. Make the caveat machine-readable. It is currently free prose inside a decision-log body, so nothing downstream can gate on it. A structured field on the triage return lets the push step refuse to proceed while an unexecuted-test obligation is outstanding.
3. Scope the run narrowly. `module-tests plan-marshall` at 747s exceeded the leaf's Bash ceiling, but a path-scoped run over only the 4 changed test modules would very likely not — the tier resolution is computed for the whole module, not for the actual target set.
4. Until then, state the exposure at the point of decision. The caveat currently appears only in `decision.log`; the operator approving the land-it decision at 10:01:12Z saw no surfaced warning that new tests had never been executed.
