# Re-running qgate mechanical checks REOPENS accepted findings, silently reverting operator triage

## Problem

`add_qgate_finding`'s dedup logic carries a **reopen** path keyed on same-title +
same-content-discriminator. When a q-gate finding is re-emitted by a deterministic
checker that had already been run, the store flips the existing row's `resolution`
from a terminal value back to `pending`.

Observed on plan `planning-lane-change-type-scope-execution-manifest` (2026-09-02,
phase `4-plan`): six `declared_scope_reconciliation` findings (830b48, e1a839,
f552cf, 0c114b, 106403, 76d9d2) had been resolved `accepted` by explicit operator
triage at the review gate. A subsequent verification re-run of
`plan-marshall:manage-tasks:qgate-mechanical-checks` — run only to confirm an
unrelated fix had landed — re-emitted all six and reverted every one to `pending`.

## Why it matters

The reopen is **silent and lossy in the direction that matters**. An `accepted`
resolution is an operator decision with recorded reasoning; `pending` is the
absence of a decision. Re-running a *read-only verification* therefore destroys
triage state, and the destruction is invisible unless someone re-lists the store
and notices the count moved.

Two consequences beyond the immediate loss:

- **The blocking gate is armed by it.** `pending_findings_blocking_count` counts
  only `pending`, so a re-run of a mechanical checker can re-arm a finalize-time
  block that an operator had already cleared.
- **It punishes verification.** The safe, disciplined move — re-run the checker to
  confirm a fix — is exactly the move that corrupts the store. The more carefully
  a run verifies itself, the more triage it loses.

This is the `truthful-signals` theme with the sign flipped, and a close sibling of
the `record-step` / `mark-step-done` vocabulary defect (a productive outcome
recorded as a failure): here a *settled* state is recorded as *unsettled*.

## Directive

- A re-emitted finding whose content discriminator is unchanged MUST NOT overwrite
  a terminal resolution (`fixed`, `accepted`, `suppressed`, `rejected`,
  `taken_into_account`). Reopen is only defensible when the discriminator changed
  — i.e. the finding is materially different, not merely re-observed.
- If a genuine re-open is needed, it must be a distinct, explicit verb, not a side
  effect of an idempotent checker re-run.
- Until fixed: after ANY re-run of `qgate-mechanical-checks` on a plan whose
  findings were triaged, re-list the store with `--resolution pending` and restore
  every reverted row. Do not assume a verification re-run is side-effect-free.

## Detection

`manage-findings qgate list --plan-id P --phase 4-plan --resolution pending`
returns rows that a prior triage had already resolved, with no intervening edit to
the artifact those rows describe.
