# Loop-back ceiling is detected after it is crossed, not enforced at the boundary

## Context

Plan `content-search-seam` (PR #1084) ran three finalize loop-backs. The orchestrator then emitted, verbatim:

```text
[STATUS] (plan-marshall:phase-6-finalize) Loop-back ceiling reached (4 of max 3) - halting and
returning control to user. PR #1084 carries 5 new pending pr-comment findings from coderabbit at
HEAD 728081b03, two of them Major. Branch is pushed and CI-green. The merge has NOT been performed.
```

The message reports a count of 4 against a documented maximum of 3, in the same sentence that announces the ceiling was "reached". Iteration 4 had already been entered, had already dispatched `automatic-review` (155,429 tokens, 26 tool uses, 504s per the dispatch-boundary record at 11:30:48Z), and had already produced its findings before the check fired.

## Root cause

The ceiling is evaluated as a post-hoc report on the iteration counter rather than as an admission gate on entry to the next iteration. A gate asks "may iteration N+1 start?" before spending anything; this check asks "how many iterations have we had?" after the spend has landed. Both read the same counter, which is why the defect is invisible in the counter itself and only visible in the arithmetic of the message.

The wording compounds it: "ceiling reached (4 of max 3)" reads as a normal terminal state to a human skimming the log, when it is in fact a report that the bound was exceeded.

## Proposed action

1. Move the comparison to the top of the loop-back entry path so iteration N+1 is refused before any dispatch, and make the halting message report the refused iteration (`loop-back 4 refused, max 3`) rather than a completed one.
2. Add a regression test that drives the loop-back path to the ceiling and asserts the number of `automatic-review` dispatches equals the configured maximum, not maximum+1. Asserting only on the halt message would pass against the current defect, since the current code does halt.
3. Treat the arithmetic in an operator-facing status line as a checkable invariant: a message of the form `X of max Y` where `X > Y` is always a bound-violation report and should never be phrased as a normal terminal state.
