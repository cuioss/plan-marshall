# derive-verification emits compile / test-compile build_class commands that manage-execution-manifest's per-task orchestrator-tier routing cannot map to a valid phase-5 canonical

## Context

While planning `inbox-sequence-reuse-collides-with-the-archive` (phase-4-plan), the Step 6 per-task verification stamp called `architecture derive-verification --changed-artifacts {targets}` for each task and wrote the returned commands verbatim into `task.verification.commands`, per the documented Step 6 procedure.

For a task whose `steps[]` targets only production `.py` files (no test files), `derive-verification` classified the artifacts via the `build_map` and returned `build_class: compile`, an `orchestrator`-tier command (`compile plan-marshall`, `bash_timeout_seconds: 630`). For a task whose `steps[]` targets test `.py` files, it returned `build_class: module-tests`, which resolves to **two** commands: `test-compile` and `module-tests`, both `orchestrator`-tier.

Both `compile` and `test-compile` are legitimate `build_class` values per `manage-architecture/standards/resolve-command.md` § "Build-class → verification command" — the doc's own worked example shows `compile` as a derivable command. However, `manage-execution-manifest compose`'s per-task `execution_tier` routing pass (Step 7b) attempts to map every `orchestrator`-tier command to a canonical `default:verify:{canonical}` phase-5 step ID, and the **only** recognized canonicals are `quality-gate`, `module-tests`, and `coverage` (per `extension-api/standards/ext-point-build-verify-step.md` § Current Implementations — the sole built-in build-verify-step implementor's `canonicals: [quality-gate, module-tests, coverage]`). `compile` and `test-compile` are NOT members of that set.

The result: `compose` fails hard with `status: error`, `error: unresolvable_step`, naming `verify:compile` (or `verify:test-compile`) as "an unknown canonical — no ext-point-build-verify-step implementor (nor the composer canonical→role table) declares it". This happened twice in the same plan (once for `compile`, once for `test-compile` after the first fix), forcing two remove/re-add cycles of all four tasks to correct the staged verification commands before `compose` could succeed.

## Root cause

Two independently-documented surfaces disagree about a shared vocabulary:

- `manage-architecture/standards/resolve-command.md` documents `derive-verification`'s `build_class → command` mapping as `compile`, `module-tests` (→ `test-compile` + `module-tests`), `verify`, `none` — and shows `compile` in its own worked `Output` example.
- `extension-api/standards/ext-point-build-verify-step.md` documents the phase-5 canonical-verify-step set as exactly `quality-gate`, `module-tests`, `coverage` (plus the domain-appended `arch-gate`).

`compile` and `test-compile` are outputs of the first surface that have no corresponding entry in the second surface. Since `derive-verification`'s commands are always `orchestrator`-tier for pyproject builds (the 600s pytest floor alone exceeds the 600s ceiling), and Step 7b's per-task routing pass mandatorily routes every `orchestrator`-tier command to a phase-5 canonical, any task whose derived command is `compile` or `test-compile` (rather than `module-tests`/`quality-gate`/`coverage`) is structurally unroutable — `compose` cannot succeed for it, regardless of authoring care in phase-4-plan.

The deliverable's own outline-declared verification command for both deliverables in this plan was `module-tests plan-marshall` (not `compile`) — confirming that `compile`/`test-compile` are over-derivations from the deterministic deriver that do not match the actually-intended verification surface for this project.

## Resolution applied in this plan

Phase-4-plan is documented (Step 6 "Verification") to always stamp `derive-verification`'s returned commands verbatim. Since neither `compile` nor `test-compile` can survive `compose`, this plan's task authoring dropped both from the staged `verification.commands`:

- The pure-production-only implementation task (no test files in its own `steps[]`) got `verification.commands: []` — its correctness is covered holistically by the paired `module_testing` task's `module-tests` run and by the phase-5 `quality-gate` / `module-tests` / `coverage` sweep steps.
- The `module_testing` tasks kept only the `module-tests` command, dropping the `test-compile` companion command `derive-verification` also returned.

## Recommendation

Either (a) extend the phase-5 build-verify-step canonical set (`canonicals:` in `phase-5-execute/standards/canonical_verify.md`) to include `compile` and `test-compile` so `derive-verification`'s full output space is routable, or (b) narrow `derive-verification`'s `build_class → command` mapping so it never emits a canonical that has no phase-5 route — i.e., collapse `compile` into `module-tests`/`quality-gate` at the deriver level, and drop the standalone `test-compile` command from the `module-tests` build_class's derived command pair. Option (b) is likely cheaper since `module-tests` already exercises the equivalent of a compile check via pytest's import step, making `test-compile` and standalone `compile` redundant outputs of the same underlying safety net. Until one of these lands, phase-4-plan authors must manually filter `derive-verification`'s output to the `{quality-gate, module-tests, coverage}` set before stamping `task.verification.commands`, rather than passing the deriver's output through verbatim as Step 6 currently instructs.
