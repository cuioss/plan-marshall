# Say what the run is waiting for when a finalize gate halts the session

## Context

The session that ran this plan carried 883 turns. The signal reduction retained two operator
turns. One was the answer to a triage gate. The other, and the only free-form operator
message in the entire session, was:

> why did you stop?

The operator could not tell from what was printed whether the run had finished, failed, or was
waiting on them.

## Root cause

The finalize phase halts at several points that look identical from outside: an
`AskUserQuestion` gate, a merge-queue wait, a review-bot rate window, and a genuine
completion all end with the main context going quiet. Nothing in the phase-boundary output is
obliged to state which of those happened, so a halt that needs the operator is
indistinguishable from one that does not.

This is precisely the gap the plan under retrospective was written to close. Its own Rule 3
defines the required phase-boundary shape as three parts — **what changed**, **what is next**,
**what needs the user** — and the third part is the one whose absence produced this question.
The rule landed as prose in `user-communication.md`; nothing in `phase-6-finalize` yet emits
that shape at a halt.

## Proposed action

Make the third part mandatory at any point where finalize yields control:

- When the phase stops for an operator decision, print a `what needs the user` line naming the
  decision and what is blocked behind it.
- When it stops to wait on an external signal (merge queue, CI, review-bot window), say what
  it is waiting for and roughly how long — a wait is "what is next", not "what needs the user",
  and conflating them is what makes silence ambiguous.
- When it stops because it is done, say so explicitly rather than by going quiet.

This is the enforcement half of Rule 3 at one call site. CodeRabbit's `652212` comment on
PR #1387 made the same structural observation from the other direction — the rule ships as
prose with no executable enforcement — and was declined on scope with a recorded follow-up.
This lesson is the concrete, bounded first site for that follow-up.

## Evidence

- aspect: `chat_history_analysis` — the only free-form operator turn in an 883-turn session is

- The plan's own D3 defines the three-part boundary shape including "what needs the user".
- PR #1387 finding `652212` (`taken_into_account`): the rule has no executable enforcement;
