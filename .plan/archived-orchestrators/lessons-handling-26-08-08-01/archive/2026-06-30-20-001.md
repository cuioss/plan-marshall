# A new helper/command mirroring a canonical must mirror its full sibling-invariant surface (exception set, guard/error-shape flows, and a parity test per shared branch) — sibling-contract symmetry no in-house gate enforces

When a new helper duplicates the read-and-parse error handling of an existing
canonical parser, it must catch the canonical's **full** set of exceptions —
catching a strict subset silently changes behavior for the omitted classes.

## What happened

PR #810 (plugin-doctor declarative rule registry + AstCache) added the standalone
read/parse helpers `_parse_test_file()` and `_parse_script()` in
`marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_analyze_resolver_matrix_coverage.py`.
Both were written to mirror the canonical `AstCache._parse()`, which treats an
undecodable file as `None` by catching `OSError`, `SyntaxError`, **and**
`UnicodeDecodeError`. The new siblings caught only `OSError` and `SyntaxError`,
so a non-UTF-8 file would raise out of the standalone paths instead of being
skipped — inconsistent with the canonical parser the whole change set was built
around.

The defect passed phase-5 verify and local pre-submission self-review and was
caught only by a CodeRabbit "outside diff range" comment, then fixed in-run
(commit `f4c15e75`): `UnicodeDecodeError` added alongside `OSError`/`SyntaxError`
in both helpers.

## The generalizable rule

Exception-set symmetry between a new helper and the canonical sibling it mirrors
is a **sibling-invariant family** — the same lockstep-or-drift failure mode the
`plugin-script-architecture` sibling-element invariant standard (PR #807) was
built to catch. But the standard's enumerated families are
guard / payload / range-clamp / dispatch-registration / normalize-before-decision /
input-parsing. The caught-exception set of a duplicated read/parse path is not
one of them. When you copy a canonical parser's error-handling shape into a new
helper, copy the **entire** `except (...)` tuple, not a subset.

## Why it slipped — and the proposed fix

There is no in-house gate for sibling-contract asymmetry; it is governed only by
an authoring **document**, so divergence is invisible until a PR bot flags it
(the same "caught only by PR bots, no in-house gate enforces it" pattern as
lessons `2026-06-24-23-001` / `2026-06-25-02-001`). The actionable residue:
broaden the `plugin-script-architecture` sibling-element invariant standard to
add **exception-set symmetry across a new read/parse helper and its canonical
sibling** as a seventh invariant family, with the canonical example being the
`AstCache._parse()` / standalone-helper exception tuple.

## Impact

Low blast radius for this instance (skip-vs-raise on non-UTF-8 corpus files), but
the class is recurring: every duplication of a canonical I/O+parse routine into a
new entry point risks dropping one exception class. Folding it into the standard
gives reviewers and authors a named checklist item.

## Recurrence — 2026-07-09 (fix-missing-get-deliverable-subcommand)

The class recurred in a **different component** — `plan-marshall:manage-solution-outline`,
well outside the plugin-doctor scripts the original instance covered — confirming
the sibling-contract-symmetry failure mode is cross-cutting, not confined to the
plugin-doctor parser family.

The plan added a `get-deliverable` subcommand that mirrors the existing
`read --deliverable-number` verb. The request explicitly scoped extracting **one**
shared helper (the deliverable-lookup / parsing logic — "no duplicated
deliverable-parsing logic"), which the implementation did correctly. But a
**second** sibling-invariant slipped through: the `document_not_found` guard flow
(`plan_id` → path → existence → content) was left **duplicated** between `cmd_read`
and the new `cmd_get_deliverable` instead of being extracted into a shared guard
helper, and the CLI parity test covered only the success and `deliverable_not_found`
branches — the `document_not_found` parity branch was missing.

Both were caught only by a sourcery-ai PR-review comment on PR #860 (a "guard"
sibling-invariant family plus a missing parity test), then fixed in-run under
TASK-4: a shared `document_not_found` guard helper extracted and consumed by both
commands, plus a `document_not_found` parity test added. Same "no in-house gate
enforces sibling-contract symmetry — caught only by a PR bot" signature as the
original instance.

## Generalized scope

Across both instances the invariant is one rule, wider than the original
exception-set framing: **when a new helper or command mirrors an existing
canonical one, it must mirror the canonical's full sibling-invariant surface, and
each mirrored branch needs its own parity test.** That surface includes at least:

- the caught-**exception set** of a duplicated read/parse path (the 2026-06-30 instance);
- **guard / error-shape flows** such as `document_not_found` — extract them into a
  shared helper rather than re-inlining the error shape (the 2026-07-09 instance);
- a **parity test per shared error branch**, not only the success and happy-error paths.

A request that scopes extracting one shared helper is not a licence to leave a
sibling guard duplicated; enumerate every branch the two commands share before
declaring the extraction complete. No in-house gate enforces this; the standing
remedy remains folding the family into the `plugin-script-architecture`
sibling-element invariant standard as a named, reviewer-checkable item.

## Recurrence — 2026-07-13 (harden-plugin-cache-resolver, PR #894)

Third instance, and the first where the mismatched siblings were **embedded
template STRING CONSTANTS that become generated code**, not functions or commands.
FIX C inlined a `Path.home()` / `Path.resolve()` cache-version resolver into
`generate_executor.py`'s `_CLAUDE_RESOLVER_TEMPLATE` with `except (OSError, ValueError)`.
Its sibling `_OPENCODE_RESOLVER_TEMPLATE` already caught **`RuntimeError`** as well —
which `Path.home()` raises in restricted environments (minimal Docker containers,
CI with no `$HOME`). The Claude template would therefore propagate an unhandled
`RuntimeError` where the OpenCode template returned `None` gracefully: exactly the
strict-subset exception-set asymmetry of the original instance, in a new medium.

Same slip signature as all prior instances — it passed (a) implementation,
(b) pre-submission self-review (recorded "7 candidates examined"), and
(c) module-tests (no restricted-env `$HOME`-unset path is exercised) — and was
caught only by the gemini PR review, then fixed in-run under TASK-6 (`RuntimeError`
added to the Claude template's `except` tuple).

### New residue — the self-review symmetric-pair surfacer is blind to template-string pairs

Beyond re-confirming the class, this instance exposes a concrete gap in the
in-house surfacer meant to be the first line of defence. `ext-self-review-plan-marshall`
has a **symmetric-pair** candidate surfacer, but it pairs **functions** via an AST
heuristic. The two resolver templates are module-level **string constants**
(`_CLAUDE_RESOLVER_TEMPLATE` / `_OPENCODE_RESOLVER_TEMPLATE`) whose bodies are
generated Python source, so the AST symmetric-pair heuristic never pairs them and
the asymmetry is invisible to self-review — which is why the "7 candidates examined"
pass missed it. Actionable residue for this instance: extend the
`ext-self-review-plan-marshall` symmetric-pair surfacer to also pair **embedded
code-generation template string constants** that share a naming/role suffix
(`_*_RESOLVER_TEMPLATE`, `_*_TEMPLATE` families) and diff their `except (...)`
tuples / guard shapes the same way it diffs sibling functions. Until that surfacer
covers template-string pairs, embedded-codegen sibling asymmetry remains a
PR-bot-only catch — the same standing remedy (a named, reviewer-checkable in-house
gate) as the two earlier instances, now widened to cover the string-constant medium.

## Recurrence — 2026-07-14 (finalize-lane-unification): two self-review-catchable sibling-consistency issues each cost a full loop-back cycle

Fourth datapoint, and the sharpest cost datapoint yet for the standing residue:
`automatic-review` looped back **twice** during this plan's finalize, each
iteration costing a full ~15-minute CI wait plus a re-review before the third
pass converged. Both loop-back causes were **sibling-pattern consistency**
issues squarely in this lesson's family:

- **except-clause breadth** (Gemini, TASK-020) — an `except (...)` tuple
  narrower than its sibling's, the same exception-set-asymmetry class as the
  original 2026-06-30 and 2026-07-13 instances.
- **canonical step-id** (CodeRabbit, TASK-021) — a doc referenced a step by a
  non-canonical key form instead of the canonical one its siblings use (the
  same bare-vs-qualified step-key family as lesson `2026-07-13-12-003`).

Both are shapes the pre-submission `ext-self-review-plan-marshall` candidate
surface is *nominally* meant to cover (symmetric-pair / canonical-forms
candidates), yet the self-review pass did not fire on either — reconfirming the
2026-07-13 residue that the surfacer's coverage is incomplete in practice, not
just for template strings. The new cost signal: because these slipped to the PR
bots, each one drove a **full remote-CI loop-back cycle** (~15 min wait + re-review)
rather than a cheap pre-PR fix, and this plan's finalize paid **four** such CI
waits driven by the loop-back cycle. The residue is unchanged in direction but
strengthened in priority: broadening the in-house self-review surfacer to
actually catch sibling-consistency shapes (exception-set, canonical-forms) has a
concrete measured payoff of multiple ~15-minute remote-CI cycles avoided per
plan, not just a cleaner diff.

## Recurrence — 2026-07-21 (terminal-title-refresh-cadence, PR #964)

Fifth instance, and the first where the mirrored medium is an **observability
contract** rather than error-handling code, and the first where BOTH mirrored
seams are NEW — added by the SAME plan — rather than one new helper mirroring an
already-shipped canonical.

Deliverable 2 of this plan established an observable-non-delivery contract on
the `_drive_repaint` drive seam in `claude_runtime.py`: a failed repaint drive is
reported, not silently swallowed. Deliverable 3 added a sibling `_drive_teardown`
seam (title-reset + terminal-binding release) in the SAME plan but did not apply
the same observable-non-delivery contract to it, so a failed title reset or
binding release stayed silent. CodeRabbit caught the asymmetry on PR #964;
TASK-010 fixed it in-run by extending the same non-delivery-observability
contract to `_drive_teardown`. Same slip signature as every prior instance:
implementation, self-review, and module-tests all passed clean; only the
external review bot caught it.

### Generalized scope, widened again

The four prior instances all involved a **new** helper/command mirroring an
**existing, already-shipped** canonical. This instance shows the failure mode is
not confined to "mirror an existing canonical" — it also covers "a plan that
introduces a contract on one seam must apply it to every structurally-sibling
seam the SAME plan adds," even when neither seam pre-existed the plan.
Corrective action, restated for this medium: when a deliverable establishes an
observability/reporting contract (a slipped-and-caught defect gets surfaced, not
silently swallowed) on one seam, check at outline/plan time whether a LATER
deliverable in the same plan adds a structurally-parallel seam, and require the
same contract on it explicitly — do not rely on catching the asymmetry only
after CI review flags the gap.
