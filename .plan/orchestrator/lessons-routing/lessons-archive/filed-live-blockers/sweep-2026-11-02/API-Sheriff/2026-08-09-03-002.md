# Bucket B --plan-id stops resolving the worktree after integrate_into_main moves plan state back

## Observed

In phase-6-finalize for `plan-v02-02-java-idiom-sweep`, `integrate_into_main` ran (as the Step 0
return-to-main ordering prescribes) and moved the plan directory from the worktree back to the main
checkout. The worktree itself was **still present and still needed** — the late `branch-cleanup`
rebase had not run yet.

A subsequent Bucket B build routed the documented way, with `--plan-id`:

```
maven run --command-args "verify -Ppre-commit" --plan-id plan-v02-02-java-idiom-sweep
```

It failed in **0 seconds** with `exit_code: 2` and this executor payload:

```
status: error
error: build_failed
errors[1]{file,line,message,category}:
  <job log>,-,"Build failed but no structured errors were parsed; see full log: ...",build_failure
```

The job log contained only `status: error / error: worktree_resolution_failed`. `--plan-id`
auto-resolves through `manage-status get-worktree-path`, and after the move-back that resolution no
longer returns the worktree.

## Why it matters

The failure is **misreported as a build failure**, not as a routing failure. `status: build_failed`
plus an unparsed-errors row reads exactly like a real red build, so the natural next move is to hunt
a compilation error that does not exist. The 0-second duration is the only tell, and it is easy to
miss. This is the same misparse family as the recorded `worktree-lacks-execute-script` lesson —
different cause, identical confusing surface.

The window is real and not narrow: `integrate_into_main` runs BEFORE `branch-cleanup`, so every
build between the move-back and worktree removal is exposed. A late rebase that needs re-gating —
exactly what happened here, because upstream advanced mid-finalize — lands squarely inside it.

## Directive

- After `integrate_into_main` has run and before the worktree is removed, route Bucket B calls with
  the explicit escape hatch `--project-dir {worktree_path}`, **not** `--plan-id`.
- Read a 0-second `build_failed` with no structured errors as a **routing** failure first. Open the
  job log and look for `worktree_resolution_failed` before treating it as a red build.

## Fix candidate

`get-worktree-path` should keep resolving the worktree while the worktree still exists, or the
wrapper should surface `worktree_resolution_failed` as its own error class rather than collapsing it
into `build_failed`. A routing failure and a compile failure should not be indistinguishable in the
payload a caller routes on.
