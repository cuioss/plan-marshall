# Phase-5 fix-task leaf wrote edits to the MAIN checkout via absolute paths instead of the cwd-pinned worktree, stranding them

A phase-5 fix-task dispatched into an `execution-context` leaf wrote its edits to the
**main checkout** using absolute `/Users/oliver/git/plan-marshall/...` paths instead of the
cwd-pinned worktree the dispatch was bound to. The edits landed on the wrong tree, were
invisible to the plan's worktree build/verify, and had to be recovered with a shared `git
stash` (stash in the main checkout, pop in the worktree). The leaf had the correct
`WORKTREE` value in its prompt body but bound its `Write`/`Edit` tool calls to a
remembered absolute main-checkout path rather than to `WORKTREE`.

## Why the in-house gates missed it

The stranded edits produced no signal in the worktree: the worktree build was green because
the intended change was simply absent there, and the main checkout is never the tree the
plan's verification runs against. Nothing failed — the work was silently misplaced. The miss
surfaced only when the operator noticed the expected change was not in the diff.

## Root cause

The `execution-context` envelope already declares `WORKTREE` authoritative — "Bind every
Edit/Write/Read tool call against the `WORKTREE` value verbatim" — but a leaf that has the
main-repo absolute path in working memory (from an earlier read, or from the worktree path
containing the repo root as a prefix) can reconstruct an absolute path anchored at the main
checkout instead of the worktree. Under the cwd-pinned (ADR-002) model the leaf's cwd is
already the worktree, so a **relative** path resolves correctly, while an **absolute**
main-checkout path silently escapes the worktree.

## Corrective action

The recovery-and-prevention that worked in this run was an explicit re-dispatch instruction:
**"use RELATIVE paths for every Edit/Write/Read, never an absolute main-checkout path."**
After that instruction the leaf wrote to the correct tree and the misplacement did not recur.

Fold this into the phase-5 fix-task (and any `execution-context`) dispatch discipline:

- **A dispatched leaf must anchor every file operation to its `WORKTREE`, and the safe form
  is a path RELATIVE to the pinned cwd** — never an absolute path that begins with the
  main-repo root. When the worktree path is
  `.../.plan/local/worktrees/{plan}` and the main checkout is the repo root, an absolute
  `{repo_root}/marketplace/...` path targets the WRONG tree; the relative
  `marketplace/...` path (resolved against the pinned worktree cwd) targets the right one.
- **Never edit the main checkout from inside a plan-bound leaf.** The main checkout is not a
  work surface during phase-5/6 — all mutation belongs to the plan's worktree.
- **Recovery when misplacement already happened**: `git stash` in the main checkout, then
  pop the stash from the worktree, to move the stranded edits across trees without losing
  them. This is the established cross-tree edit-rescue recipe.

This is the leaf-topology sibling of the "plain `git` in a cwd-pinned context, never an
absolute worktree path" targeting rule: the same cwd-pinned model that makes bare `git`
correct also makes RELATIVE file paths correct — and makes absolute main-checkout paths a
silent tree-escape.
