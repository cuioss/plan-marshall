# A doc placeholder interpolating an element of a structured list must name the field, not the element - adding a second group whose element type differs turns a loose placeholder into a type mismatch only the PR bot catches

## Context

PR #975 (`domain-ambiguity-candidate-set`) added a second option group to the
phase-1-init Step 7 ambiguous-domain `AskUserQuestion` block. The pre-existing
illustrative line read:

```text
- label: "{candidate_1}" description: "Detected candidate domain"
```

`candidates` entries are objects (`{domain, matched_aliases}`), so interpolating
the whole entry can render a serialized object rather than a selectable label.
The placeholder had been loose for a long time without visible harm.

The plan then added a sibling group whose elements are **bare strings**:

```text
- label: "{additional_1}" description: "Configured for this project, not detected in the request"
```

Introducing the second group is what made the first placeholder actively
misleading: two adjacent lines now use the identical `{x_n}` interpolation shape
for element types that differ (object vs string), so a reader cannot tell which
one needs a field accessor.

## What every in-house gate missed

Fully green before push: `quality-gate` (ruff + mypy), 12,271 tests, scoped
`plugin-doctor` across 30 rules, and `pre-submission-self-review` over 9
surfaced candidates. The self-review surfaced the exact line as a
`user_facing_strings` candidate and adjudicated it clean.

The defect is a **cross-artifact type mismatch** — a documentation placeholder
disagreeing with the return schema of the script that produces the value. No
single-artifact linter can see it: ruff/mypy never read illustrative markdown,
plugin-doctor's structural rules do not type-check placeholder interpolation
against an emitting script's return shape, and the self-review's wording check
reads the string for ambiguity, not for schema agreement. Only the PR bot
(CodeRabbit) caught it.

## Directive

When a doc interpolates an element of a list the surrounding contract also
defines, name the **field**, not the element — `{candidate_1.domain}`, not
`{candidate_1}` — whenever the list's elements are structured. Treat the
following as the trigger to re-check every sibling placeholder in the block:

**Adding a new group/list to an existing illustrative block whose elements have a
different shape than the existing group's.** The new group is usually written
correctly; the risk is that it retroactively makes a pre-existing loose
placeholder ambiguous by sitting next to it in the same visual shape.

State the asymmetry explicitly in the block when two adjacent groups differ, e.g.
a trailing comment noting that one group's entries are objects and the other's are
bare keys, so the next reader does not have to re-derive it from the emitting
script.
