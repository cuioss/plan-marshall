# mark-step-done accepts a --head-at-completion that resolves to no commit, so a fabricated anchor is persisted

# mark-step-done accepts a --head-at-completion that resolves to no commit, so a fabricated anchor is persisted

## Context

On plan `unreviewed-merge-gate-holes`, round 2 of `pre-submission-self-review` was
recorded with:

```text
head_at_completion: 36a800cff8e9e0e01d5e2ba0d4b0c5f8b8e0c9a1
```

That is not a commit in this repository. The real SHA is
`36a800cff22f322e5ee02b80da5ee5d334c2b6b9`. The recorded value was produced by
extending the short hash `36a800cff` to 40 characters instead of resolving it
through git. `manage-status mark-step-done` accepted it and wrote it to
`status.metadata.phase_steps`.

The error surfaced one dispatch later, when round 3's surface helper refused:

```text
script_failure notation=pm-plugin-development:ext-self-review-plan-marshall:self_review
exit_code=1 failure_kind=script_internal_failure
detail=--since-ref '36a800cff8e9e0e01d5e2ba0d4b0c5f8b8e0c9a1' does not resolve to a
commit inside .../worktrees/unreviewed-merge-gate-holes, so the delta surface cannot
be computed. The round is refused rather than silently widened to a full sweep.
```

## Root cause

`head_at_completion` is load-bearing twice over: it is the dispatcher's staleness
anchor for the step, **and** the delta anchor the next round scopes its
`--since-ref` against. It is written by `mark-step-done` with no validation that
the value names a real commit.

A field that is a git ref everywhere it is *read* is an opaque string where it is
*written*. Validation therefore lands at every consumer instead of at the single
producer, and a consumer can only fail — it cannot correct.

The downstream fail-closed behaviour was exactly right: the helper refused rather
than silently widening to a full sweep, which is what surfaced the problem at all.
But it fires after an envelope has been spent, and the recorded anchor in the
meantime names a tree that never existed.

## Proposed action

Validate at the write site. In `manage-status mark-step-done`, when
`--head-at-completion` is supplied, resolve it with `git rev-parse --verify
{sha}^{commit}` against the plan's active tree and reject a value that does not
resolve, with a structured `error: unresolvable_head_at_completion` naming the
value.

Two properties make this cheap and safe:

- It is a single subprocess call on a write that already happens once per step
  completion.
- It cannot weaken anything: today's behaviour on a *valid* SHA is unchanged, and
  the only new outcome is a rejection of a value that no consumer could have used.

Consider also **accepting a short SHA and storing the resolved full form**. The
fabrication here was an attempt to satisfy a 40-character field from a 9-character
value; if the field resolved short refs itself, the pressure that produced the
invention disappears.

## Impact

If the value had stood, every subsequent self-review round would either refuse
(as round 3 did) or silently re-sweep the whole surface, and the persisted record
would name a nonexistent tree as the point the step completed at. On this plan it
cost one wasted `pre-submission-self-review` round; `firing_count` reached 4 with
three failed firings, and the step's total spend across all firings was roughly
985K tokens.

The broader shape is worth stating plainly: an agent fabricated a plausible-looking
identifier rather than resolving it, and only a fail-closed consumer prevented it
from becoming persisted history. Structural validation at the producer is the
remedy that does not depend on an agent not doing that.
