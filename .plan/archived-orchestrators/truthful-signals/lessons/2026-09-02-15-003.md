# change-type-heuristic returns analysis at confidence 1.0 for any plan whose title contains a review-domain word

## Observation

Phase-1-init Step 8a.5 ran `manage-status change-type-heuristic --plan-id
review-packs-become-published-artifacts --persist` against a request body ingested from
`PLAN-PR-038-review-packs-become-published-artifacts.md`. It returned:

```text
change_type: analysis
confidence: 1.0
ambiguous: false
scores:
  analysis: 1
  feature: 0
  enhancement: 0
  bug_fix: 0
  tech_debt: 0
  verification: 0
```

The classification is wrong. The request carries five build-and-delete deliverables: change the
generator's emission unit to one artifact per derived domain, add a publish path to a foreign
repository, extend a drift guard, delete `.pr_agent.toml`, and add a `pr-agent:` block to
`.github/project.yml`. Nothing in it is read-only investigation.

## Why the signal is confidently wrong

Every non-`analysis` bucket scored exactly 0 and `analysis` scored exactly 1, which yields
`confidence: 1.0` and `ambiguous: false`. A single matched token therefore produces the maximum
possible confidence with no competing evidence — the confidence figure measures *unanimity among
matched keywords*, not *how much evidence was matched*. One keyword hit and a thousand keyword hits
are indistinguishable in the output.

The matched token is the review-domain vocabulary in the plan's own title and body ("Review packs",
"review charter", "drift guard asserts"). Any plan **about** review tooling is therefore classified
as a plan that **does** review work. The `review-apparatus` epic stages a whole corpus of such
plans, so the misfire is systematic within that epic rather than a one-off.

The independent `aspect-classify` verb, run seconds earlier on the same narrative, returned
`aspect: implementation` — the two classifiers directly contradicted each other, and only the
contradiction made the defect visible.

## Consequence

`change_type` feeds the Step 8b planning-lane router: `s3_deep` fires on membership in
`_DEEP_CHANGE_TYPES`. A wrong `change_type` silently routes the lane on a false signal. It is also
persisted plan metadata that downstream phases read as settled fact.

The Step 8b classification-validation gate does **not** catch this: its three flagged classes are
`feature_as_bug_fix`, `non_empty_affected_files_with_null_scope`, and
`scale_mismatch_light_routing`. There is no `implementation_as_analysis` class, and the gate does
not cross-check `change_type` against the `request_aspect` the sibling classifier just persisted.

## Directive

1. Make `confidence` report evidence volume, not bucket unanimity. A single matched keyword must
   not yield `1.0`. A total-matches floor below which the result is `ambiguous: true` (deferring to
   the LLM `detect-change-type` writer) is the minimum fix.
2. Add a cross-classifier consistency check to the Step 8b classification-validation gate:
   `change_type == analysis` together with `request_aspect == implementation` is a mismatch class
   (`analysis_over_implementation_aspect`) and should emit a Q-Gate finding the same way the
   existing three do. The two verbs already run within a few steps of each other on the same
   narrative, so the signal is free.
3. Damp domain-vocabulary tokens that name the plan's *subject* rather than its *action*. A plan
   titled "Review packs become published artifacts" is not a review; scoring `analysis` from
   "review" conflates topic with verb.
