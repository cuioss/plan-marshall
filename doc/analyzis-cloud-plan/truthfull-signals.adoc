= Cloud-run quality analysis: `truthful-signals`
:toc: left
:toclevels: 3
:sectnums:

Analysis of the `truthful-signals` plans executed as standalone cloud runs, measured against the 10
most recent plans executed locally through the full plan-marshall lifecycle.

**The contract under analysis.** The cloud lane is defined by two project-local skills:
link:../../.claude/skills/cloud-plan-lane/SKILL.md[`cloud-plan-lane`], the execution contract loaded
as the first action of every run, and
link:../../.claude/skills/author-cloud-plan/SKILL.md[`author-cloud-plan`], the authoring judgement
applied when a plan is written. Every lane-contract finding below names one of them.

[IMPORTANT]
====
**Measured at repository HEAD `3e9ce88e1`, 2026-08-22.** Every figure is re-derivable by script from
the ingested corpus at `.plan/local/orchestrator/truthful-signals/cloud-runs/`.

This document carries a measurement instant, which the project documentation standard otherwise
forbids. The deviation is deliberate and is the subject of the analysis: a comparative measurement
without its instant is exactly the untruthful signal this epic exists to remove.
====

== Population, and the two PRs excluded from it

The epic's cloud PRs are of **two kinds**, and only one belongs in a quality analysis:

[cols="2,4",options="header"]
|===
| Kind | Treatment

| **Plan work** — a run of an authored `plan.md` under the `cloud-plan-lane` rule-set | **analysed**
| **Fixes to the `cloud-plan-lane` skill itself** — ad-hoc edits made *outside* the rule-set | **excluded**
|===

Excluding the second kind is not a judgement call: those PRs were never governed by the contract
this report evaluates, so counting their defects against it would measure the wrong thing.

=== The exclusion, derived rather than asserted

Criterion: a PR is a lane-fix when **the only production file it touches is
`.claude/skills/cloud-plan-lane/SKILL.md`** (plan documents under `doc/plans/` are not production).
Applied to every landed commit in the repository:

* **44 cloud-plan-lane fix PRs exist in total.**
* **42 are outside this corpus already** — ad-hoc `chore(cloud-plan-lane):` edits with no plan
  directory, so they never entered the analysis.
* **2 were inside it and are now removed**: `030` / #1137 and `450` / #1147. Both touch exactly one
  production file, and that file is the lane skill.

**`120` / #1162 also edits that file and is deliberately NOT excluded** — it touches **64**
production files (the `marshall-orchestrator` → `plan-orchestrator` rename) and is plan work that
happens to include the lane skill among its targets. The criterion is *only* production file, not
*any*.

[NOTE]
====
**A resolution defect was caught and corrected while deriving this.** Resolving each PR's landing
commit with `git log --grep "(#NNNN)"` matched a *different* commit whose body mentioned the number,
which falsely classified `320` / #1213 as a lane-fix. Anchoring the match to the end of the **subject
line** resolves it correctly to `4ac413261`, six production files, not a lane-fix.

Recorded because an unanchored `--grep` silently returns a plausible wrong commit, and the resulting
exclusion would have been invisible in the output.
====

**Analysed population: 45 plans, 245 deliverables, 299 gaps.**

== The comparison is not effort-controlled

The two lanes were run at different model and effort settings, and this cuts in opposite directions.

[cols="2,3,3",options="header"]
|===
| | Cloud lane | Local plan-marshall

| Model / effort | **Opus at max effort**, uniform | resolved **per phase**, custom preset
| Rationale | chosen **to anticipate the missing plan-marshall guardrails** | effort is a per-phase knob, spent where it pays
| Observed | one setting, no per-phase variation | outline level-5 · **plan level-3** · execute level-5 · finalize level-5
| Source | operator statement, no artifact in the corpus | verified from `manage-config effort resolve-target`
|===

**On cost this weakens the comparison** — part of any gap is the model tier, so the cost figures are
*not effort-controlled*.

**On quality it strengthens the conclusion** — the cloud lane had the most expensive setting
available, explicitly as compensation for absent guardrails, and still produced the fidelity and
resolution figures below. ⇒ **Raising effort did not substitute for the machinery.**

== Why so many gaps? The taxonomy answers it

[IMPORTANT]
====
**The gap count is substantially a function of what the verification call ASKED FOR.**

`verification.md` and `gaps.md` were not produced by the plan runs. They come from a separate,
operator-issued verification pass whose brief asks for a *thorough review of all code and
documentation in the repository*, explicitly covering correctness and edge cases; hidden traps and
false security; whether the security posture fails closed; whether tests are real content tests
rather than coverage tests; whether generators and positive/negative cases are used correctly; and
whether documentation — Javadoc and AsciiDoc — is sensibly structured and matches the code.

**Read the taxonomy below against that checklist and the correspondence is close to exact.**
⇒ **`299` is the yield of one particular review question, not a lane-quality constant.**

**Two findings are NOT prompt artifacts**, because they are measured against the plans' own
claims rather than an external checklist:

* the **20.4% deliverable fidelity failure rate**;
* the **57.1% CodeRabbit resolution rate**.

Those two carry the verdict. The raw gap count does not.

=== The resolution rate is the discriminator

**Local plans resolved 47 of 47 CodeRabbit findings — 100%. Cloud plans resolved 48 of 84 — 57.1%.**

6 cloud PRs received findings and resolved **none**: `090`, `130`, `180`, `250`, `300`, `390`.

This is the cleanest evidence for outcome 1. The local lane has a *findings pipeline* —
`automatic-review` files each comment as a `pr-comment` finding, a unified triage dispositions every
one, and the blocking-finding invariant refuses the phase transition while any actionable finding is
`pending`. **A local plan structurally cannot merge with an unresolved review finding.**

=== Why coverage was low in BOTH lanes

Every decline sampled, in both lanes, carries the identical notice: *Review limit reached — you've
reached your PR review limit.* An **account-level quota**, not a `skip-bot-review` label and not a
lane decision. The local lane also lost 4 of 10 PRs to it.

[IMPORTANT]
====
**A second-order effect.** The cloud lane pushed dozens of PRs through review in a short window, which
is itself a plausible driver of the quota exhaustion that then degraded review for *everything* in
the same period — including the local plans.

So the reviewer dimension splits: **coverage** is environmental and shared (outcome 3), while
**resolution** is a lane property (outcomes 1 and 2). Only the second explains the corpus.
====

=== The comparison, stated honestly

[WARNING]
====
**The two defect counts are not the same measurement and must not be subtracted.**

Cloud gaps were found by a verification pass that swept the repository against a broad checklist.
Local findings were raised by each plan's *own in-run gates* and resolved before merge. One counts
what a sweep found; the other counts what the gates caught.
====

==== Local plans ARE post-hoc verified — and the rate is measurable

An earlier draft of this report claimed no post-hoc verification exists for local plans and that their
escape rate is therefore unknown. **That was false**, and the correction matters enough to state
rather than quietly fix.

The orchestrator contract requires it: every landed plan's result is passed back to the orchestrator,
and the `analyze` verb **must verify each claim against ground truth — actual code, artifacts, PR
state — before recording it.** A pasted claim is explicitly a lead, never a fact. The landing records
under `landings/` are that verification's output.

Measured over the **61 orchestrator-written landing records**:

[cols="4,1",options="header"]
|===
| Signal | n

| Landings recording at least one **CONTRADICTED / REFUTED** plan claim | **20 of 61 (33%)**
| Total contradiction / refutation occurrences | 35
| Landings explicitly recording corroboration | 38 of 61
| Total `corroborat*` occurrences | 88
|===

So the local lane has a post-hoc ground-truth check, it fires, and **it contradicts something a plan
claimed in a third of landings.**

===== The nearest like-for-like comparison

Both lanes measure *a claim the producer made against what the tree actually shows*, at plan
granularity:

[cols="3,2,2",options="header"]
|===
| Plans with ≥1 claim contradicted by ground truth | Cloud | Local

| Rate | **26 of 45 — 58%** | **20 of 61 — 33%**
| Instrument | verification pass, deliverable fidelity axes | orchestrator `analyze`, landing corroboration
|===

**Still not identical instruments.** The cloud pass checks every deliverable on four axes and sweeps
adjacent surfaces; the orchestrator checks the claims a plan actually made in its landing message and
report. The cloud instrument is the more searching of the two, so some of the 58-vs-33 gap is
instrument depth rather than plan quality. It is a *comparison*, not a controlled experiment — but it
is no longer an absence.

== Adjudication of the three candidate explanations

=== 1. plan-marshall shows its benefit — *SUPPORTED*

The local lane runs gates the cloud lane structurally does not have:

[cols="3,3",options="header"]
|===
| Local gate | Cloud-lane equivalent

| `pre-push-quality-gate` — per-bundle + whole-tree build and tests | conditional `./pw verify`, skipped on a docs-only footprint
| `pre-submission-self-review` | none
| `automatic-review` + unified triage + findings pipeline | review bots only, no triage pipeline
| Q-Gate findings blocked at **every** phase boundary | none
| `phase_handshake` invariants incl. blocking-finding gate | none
| `finalize-step-simplify`, `finalize-step-security-audit` | none
| `plan-retrospective` + `review-retrospective` | none
| Per-phase metrics, token and billing accounting | none
|===

Direct evidence: local resolved **100%** of reviewer findings, cloud **57.1%**; cloud shipped a
**20.4%** deliverable fidelity failure rate.

[WARNING]
====
**Do not over-claim.** The two instruments differ in depth — the cloud verification pass checks every
deliverable on four axes and sweeps adjacent surfaces, while the orchestrator's `analyze` checks the
claims a plan actually made. Some of the 58%-vs-33% gap is instrument depth, not plan quality. The
defensible claims are: **the local lane catches more before merge**, and **its post-hoc check
contradicts a plan claim less often**.
====

=== 2. `cloud-plan-lane` / `author-cloud-plan` is faulty — *SUPPORTED, with named mechanisms*

**(a) The run report is self-assessed.** The agent that does the work writes the report attesting to
it. Consequence: **48 of 299 gaps (16.1%) are corrections to the runs' own reports.** Three reports
were internally self-contradictory (`060`, `310`, `500`).

**(b) Derived figures are taken before the review cycle closes.** `520` had two files added by
CodeRabbit after its counts were taken; `500` omitted a *production* file from § Collateral for the
same reason; `510` used a floating `origin/main` endpoint three sections after its own § Build gate
corrects that defect.

**(c) The build gate skips on a docs-only footprint** — so a markdown-only plan ships with no gate,
and over half this corpus's gaps are prose defects.

**(d) The lane assumes affordances a fresh clone lacks.** `230/D0`, `440/D4` had gates that could not
be opened; `.plan/` state is git-ignored.

**(e) Nothing governs many agents in one working tree.** The audit run hit this itself — agents
mutation-testing concurrently corrupted each other's snapshots. Fixed in-flight; the contract still
carries no rule.

=== 3. A general Claude Code issue — *WEAKLY SUPPORTED*

* **Reviewer coverage** degraded in both lanes, same account-quota cause — see the reviewer section.
* **Squash merges** make every per-commit claim uncheckable; four `verification.md` headers cite base
  commits absent from the clone.

None of these explains the corpus. They explain why *review* was thin.

== Verdict

[IMPORTANT]
====
**Outcomes 1 and 2, jointly — the same finding seen from two sides.**

The cloud lane is not broken; it is **thin**. It gives up the in-run verification machinery that
produces plan-marshall's quality — and then buys that verification back as a **separate,
separately-billed third call**, which is where every gap in this report came from.

The verdict does **not** rest on the raw gap count, which is a function of what that call asked for.
It rests on the two measurements taken against the plans' *own claims*: a
**20.4% deliverable fidelity failure rate** and a **57.1% reviewer resolution rate** against
the local lane's 100%.

**Raising effort did not substitute for the machinery.** The cloud runs used Opus at max effort,
chosen to compensate for the absent guardrails, and still landed those figures — while the local lane
spent level-3 on an entire phase and resolved every reviewer finding. The gap is structural.

The corpus's own best evidence: the three *remediation* plans, run in the same lane, closed 90 gaps
and **filed 25 new ones**, two `high`. The lane does not self-correct.
====

== What the cloud lane is genuinely good at

* **Breadth under parallelism** — 44 plans verified and adversarially re-reviewed. The audit report's
  own § Cost claims "99 agents … this single Claude Code cloud session's dispatch tree"; the operator
  reports the work actually spanned **multiple sessions at a maximum of 3 parallel runs**. The
  single-session framing is **corrected here**, and it is worth noting *how* the error entered this
  report: it was taken from a self-assessed run report, which is the exact defect class § Adjudication
  (a) files against. The breadth is real; the concurrency figure was not.
* **Mechanically-derived figures survive.** In `500`, *every* census figure re-derived exactly while
  five narrative sections went stale. **Derivation held; assertion did not.**
* **The adversarial second pass works** — it corrected verdicts in both directions and caught defects
  in the *fixes being proposed*.
* **`320` and `520` are genuine successes** — 10 of 10 and 29 of 30 upstream gaps closed.

== Recommendations

1. **Do not run implementation plans in the cloud lane without a verification gate.** Reserve it for
   breadth work — audits, sweeps, verification fan-outs.
2. **Add a mandatory final re-derivation** after the review cycle closes.
3. **Give the lane a blocking findings gate.** Highest-value single change: reviewer findings were
   raised and never resolved because nothing refused the merge.
4. **Stop self-assessing the run report**, or stop treating it as evidence.
