# New tests asserted weaker properties than they were written to protect

## Problem

Tests written in plan-04 (PR #834) passed but would not have caught the regressions they guard. CodeRabbit reported four gaps: the problem `type` was checked with `endsWith("token-invalid")`, which accepts a wrong namespace; the leak check looked for the exception-message suffix, not the submitted token, so a response echoing the token would pass; `TokenSheriffClientProcessorTest` called `registerClientExceptionMapper()` directly, so removing `@BuildStep` went unnoticed; and `FailingResolver` threw from the first resolver call, so the second call's failure path was never exercised.

## Solution

A leak or negative assertion must test the actual sensitive input (the submitted token), not a derived string that happens not to contain it. Pin published contract values (problem-type URIs) with `equalTo`, not suffix or prefix matchers. When a test calls a Quarkus build-step method directly, also assert its `@BuildStep` annotation is present. When code guards several calls with one try/catch, write one failure test per call.

## Impact

Two review rounds and two fix tasks, each restarting the gate, CI and review cycle.
