# ARTIFACT emission stops after the first task of the first execute envelope

## Context

Plan `refactor-test-suite-pytest-standards` ran 14 tasks across 3 execute envelopes, producing 12 commits over a 75-file footprint. Its `work.log` contains exactly **three** `[ARTIFACT] (plan-marshall:phase-5-execute:N)` lines — all three carry `:1`, i.e. all three belong to TASK-1:

```
[ARTIFACT] (plan-marshall:phase-5-execute:1) M test/conftest.py
[ARTIFACT] (plan-marshall:phase-5-execute:1) A test/_shared/_input_validation_fixtures.py
[ARTIFACT] (plan-marshall:phase-5-execute:1) D test/plan-marshall/_pm_input_validation_fixtures.py
```

TASK-2 alone mutated 24 files across 23 logged steps and emitted zero artifact lines. Every subsequent file-mutating task did the same. The per-file artifact trail covers 3 of ~75 files — 96% absent.

The `logging-gap-analysis` aspect's `ARTIFACT_EMISSION` rule is written to catch exactly this, but its canonical check is `counts.artifact_entries > 0` for a non-empty footprint. That check passes here (10 artifact entries plan-wide, 3 from execute), so a total emission collapse after the first task reads as healthy.

## Root cause

The emission is not driven off a per-task loop invariant. TASK-1 completed via the ordinary path and emitted its three lines; from TASK-2 onward the workflow took paths that skip the emission point — TASK-1+TASK-2 were landed as a joint D1+D2 commit under the planned-failure exception, and thereafter tasks completed through `[OUTCOME] Per-deliverable commit` without passing back through the artifact-emitting step. Whatever the precise branch, the emission is positionally coupled to one code path rather than being an unconditional post-condition of task completion.

The detection rule compounds it: a `> 0` threshold cannot distinguish "emitted for every task" from "emitted for the first task only".

## Proposed action

1. Make `[ARTIFACT]` emission an unconditional post-condition of task completion in phase-5-execute — emit from the same seam that writes the `[OUTCOME] Completed TASK-NNN` line, so the two are structurally paired and no completion path can skip one while taking the other.
2. Tighten the `ARTIFACT_EMISSION` rule in `plan-retrospective/references/logging-gap-analysis.md` from `artifact_entries > 0` to a per-task pairing: for every `[OUTCOME]` line whose task produced a non-empty diff, require at least one `[ARTIFACT]` line carrying the same task number. The reference already describes this stricter `outcome_with_changes` vs `artifacts_after_outcome` comparison — it is specified but evidently not what the deployed check evaluates.
3. Cover the same seam for the two adjacent outcome-shape gaps observed in this plan: a task dropped as infeasible (TASK-9) emits no outcome line at all, and an orchestrator-tier task (TASK-13) emits a free-form line no mechanical check can pair to a task number.

## Evidence

- work.log lines 81-83 — the only three `[ARTIFACT] (plan-marshall:phase-5-execute:N)` lines, all `:1`
- work.log lines 84-107 — TASK-2's 23 step-completions and terminal `[OUTCOME]`, with no artifact line
- `analyze-logs` fragment — `counts.artifact_entries: 10` plan-wide, so the existing `> 0` rule passes
- `analyze-logs` fragment — `outcome_for_diffed_tasks.tasks_with_diff_no_outcome: [TASK-009, TASK-013]`
- Realized footprint: 75 files, 12 commits

## Recurrence — 2026-07-22 (propagate-parallel-plan-hardening) — not first-task-only; emission survives an envelope boundary but dies mid-envelope

Second sighting, during the user-invocable retrospective of
`propagate-parallel-plan-hardening` (PR #977, 9 tasks / 2 envelopes / 28 files).
The emission pattern **refines this lesson's title**: it is not "first task of the
first envelope only".

```
TASK-001  (envelope 1)  [ARTIFACT] emitted   (1 line)
TASK-002..TASK-007      no [ARTIFACT]        (6 file-mutating tasks, silent)
TASK-008  (envelope 2)  [ARTIFACT] emitted   (3 lines)
TASK-009  (envelope 2)  [ARTIFACT] emitted   (1 line)
```

So emission fires for the first task of BOTH envelopes and for TASK-009, and dies
across the long TASK-002..007 run inside envelope 1. That run is exactly the
stretch containing the escalation/re-entry (TASK-002 escalated, was resolved
overnight, and the envelope was re-entered) — consistent with this lesson's root
cause that emission is positionally coupled to one completion path rather than
being an unconditional post-condition, and inconsistent with any
"first-task-only" reading. Recommend re-titling to "ARTIFACT emission is coupled
to one task-completion path and is skipped by the others".

The detection-rule half also recurred verbatim: `analyze-logs` reported
`counts.artifact_entries: 20` plan-wide, so the deployed `> 0` check passed while
6 of 9 file-mutating tasks emitted nothing. The stricter per-task
`outcome_with_changes` vs `artifacts_after_outcome` pairing is still specified but
still not what the deployed check evaluates — this retrospective had to compute
the 9-vs-3 comparison by hand.
