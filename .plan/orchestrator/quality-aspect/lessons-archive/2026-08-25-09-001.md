# Capture the realized footprint at branch-cleanup before the worktree is removed

## Context

Five independent consumers asked for this plan's realized footprint during its own run and post-merge retrospective, and none could answer:

- `check-artifact-consistency` returned `inconclusive` on BOTH `affected_files_recall` and `affected_files_exact_match`, with `footprint_resolved: false` — \"no live worktree diff, no realized-footprint capture, no merge-commit, no modified_files key\".
- `analyze-logs` emitted `ARTIFACT_COVERAGE_UNMEASURABLE`, disabling the `[ARTIFACT]`-emission floor.
- `manage-execution-manifest compose` recorded decision `4ffcc8` at plan time: \"kept pre-push-quality-gate on an unknown build verdict: plan footprint unresolvable — no materialized worktree carries evidence of what this plan changed\".
- `check-routing-decisions` had to be handed a `--diff-file` this retrospective built by hand.
- The metrics denominator `files_modified` fell back to the stale declared `references.affected_files` count (10) against a realized 14.

The footprint is recoverable — `git show --name-only --format= 00b92fca` yields all 14 files in one call — but no tier of the shared resolver looks there.

## Root cause

Every tier of the shared footprint resolver depends on state that `branch-cleanup` destroys before the retrospective runs: the worktree is removed, the branch is deleted, and the merge-commit tier does not match how this repository actually lands PRs (a squash through a merge queue, whose commit has no second parent). `references.modified_files` — the legacy key — is never written; only `affected_files`, the *declared* set, exists.

## Proposed action

Persist the realized footprint at `branch-cleanup`, BEFORE the worktree is removed, at the plan-relative path the shared resolver already probes for its realized-footprint capture tier. One path per line, from the same `{base}...HEAD` diff the step already has in hand.

Secondary, and independently valuable because it repairs already-archived plans that no forward-looking capture can reach: add the squash-merge commit as an explicit resolver tier, derived from the merge sha the plan already records.

## Recurrence — 2026-09-06 (every-test-runs-and-the-suite-does-not-slow-down, PR #1426)

**Proposed action 1 has landed, and this run is the first where it shows.** The footprint
resolver resolved on every consumer that asked: `check-artifact-consistency` reports
`footprint_resolved: true`, and `check-routing-decisions` / `check-outline-vs-shipped` both
report `footprint_source: resolved` without a hand-built `--diff-file`. Three runs of
hand-derivation ended. `references.realized_footprint` carries 27 paths.

**But the capture is not at `branch-cleanup`, and the timing is the whole lesson.** It was
written at `2026-09-05T22:05:44Z`, mid-finalize, as an ad-hoc repair after `plugin-doctor`
noticed `affected_files` was stale. Three loop-back iterations then advanced HEAD three more
times and nothing re-captured. Against the landed merge diff (`git diff --name-only
1c4e6feb^ 1c4e6feb`, 29 paths) the 27-path capture is missing
`build-pyproject/SKILL.md`, `build-pyproject/scripts/pyproject_build.py` and
`test/test_skip_gate.py`, and carries `uv.lock`, which did not land. A capture taken at
`branch-cleanup` — the point this lesson names, and the last point before the worktree is
removed — would have been correct.

**The denominator half reproduced with a new and nastier shape.** `references.affected_files`
was corrected to 29 paths at `2026-09-05T22:34:19Z` and is *also* 29 in the landed diff — but
they are not the same 29. `affected_files` holds `uv.lock` (did not land) and omits
`test/test_skip_gate.py` (did land, created by the `TASK-010` loop-back fix on 2026-09-06,
after the correction). The sets are equal in size and disjoint by one element in each
direction, so `files_modified: 29` is a *correct-looking* denominator over a wrong
population, and any count-only check reads `29 == 29` as agreement.

`manage-references reconcile-scope` implements exactly this comparison — it "compares pairwise
by symmetric difference in both directions, so two equal-sized but disjoint sets are reported
as fully disagreeing rather than as identical". It was never called during the run. The
capability that detects this class already ships; what is missing is a call site.

**Adds to the Proposed action:** run the capture at `branch-cleanup` as stated, *and* re-run
it after every loop-back re-entry that advances HEAD, since a single mid-finalize capture is
invalidated by the next fix commit. Gate the merge on a `reconcile-scope` whose symmetric
differences are empty, rather than on the two sets having the same length.
