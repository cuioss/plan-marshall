# architecture search --content answers about the main checkout in a worktree-bound dispatch

## Observed

During the PR-comment triage of plan `plan-v02-02-java-idiom-sweep` (PR #198), a dispatched agent
ran `architecture search --content` against the plan's worktree and got **2 hits** for
`LOG_FILE_PATH` in `integration-tests/.../ItProfileConfigBindingWiringTest.java`. Reading the file
directly showed **zero**. The main checkout's copy still held the pre-rename content; the worktree's
did not. The search had silently resolved against `/home/oliver/git/API-Sheriff` rather than the
worktree it was pointed at.

The response carried clean coverage fields the whole time — `files_scanned: 954`, `unreadable[0]`,
`truncated: false`. Nothing in the payload marks it as answering about a different tree.

## Why it matters

This is the **confidently-wrong-POSITIVE** mirror of the already-recorded
`architecture-search-false-negative-yaml` lesson. There the zero was wrong; here the hits are wrong.
Both wear the same trustworthy coverage fields, so neither is self-announcing.

The concrete near-miss: the agent was triaging a CodeRabbit finding that a skill doc overclaimed
what a test guards. Had it trusted the search, it would have declined a **valid** finding as
"already guarded" — closing a real documentation defect on the strength of a file the tree does not
contain.

## Directive

- In a **worktree-bound dispatch**, do not use `architecture search --content` to establish presence
  or absence in a specific file. Use a direct `Read` of that file.
- Treat a `search --content` result as a claim about *some* tree, not necessarily the one you asked
  about. Corroborate any load-bearing hit or zero with a direct read before acting on it.
- `Grep` is typically **not granted** inside these dispatch envelopes, which removes the obvious
  fallback and makes the direct `Read` the only reliable instrument. Plan the check accordingly.

## Fix candidate

`architecture search --content` should either honour the worktree routing flag it was given, or
refuse when it cannot — and in every case the response should name the tree it actually scanned so a
caller can tell. A coverage block that reports `files_scanned` without naming the root is not
falsifiable by its reader.
