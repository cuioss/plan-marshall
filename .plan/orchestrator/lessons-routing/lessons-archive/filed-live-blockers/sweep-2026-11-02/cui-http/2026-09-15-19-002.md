# Javadoc asserted a guard/sanitisation ordering the calling code does not have — caught only by an external review bot

## Observation

`ContextPaths.containsUnsafePathConstruct`'s Javadoc asserted an ordering property: that the guard
runs **before** sanitisation. In fact `containsUnsafePathConstruct` is invoked only inside
`ContextPaths.normalize()`, which `ForwardedHeaderResolver.resolveContextPath` calls **after**
`sanitize()`. The documented ordering did not exist anywhere in the code. The claim slipped past
authoring, the outline's own Q-Gate, per-task verification, and the pre-push quality gate, and was
caught only by an external review bot (CodeRabbit, PR #237) — fixed in-run via a loop-back task
(TASK-012, commit `d8bbf1c`) that reworded the Javadoc to state the true rationale (this class
never decodes, so percent-encoding is rejected wholesale) without asserting an ordering it does
not have.

## Why this is lesson-bearing

The failure class is a security-relevant ordering claim written at the callee, verifiable only at
the caller. The claim is locally unfalsifiable: nothing in `ContextPaths.java` alone can confirm or
refute "runs before sanitize", because the ordering lives in `ForwardedHeaderResolver`, a different
class. This is precisely the class none of the in-repo gates check — they do not compare a
Javadoc behavioural/ordering claim against the actual call graph.

Notably, this defect landed in the SAME plan run that produced four outline-stage instances of the
sibling class "asserted a fact about code never read off the file" (see the paired lesson on
`plan-marshall:phase-3-outline`) — the same root failure mode (documenting a mental model instead
of the actual code) recurred at both the outline stage and inside the shipped implementation.

## Corrective

Do not document an ordering, precedence, or short-circuit behaviour in a doc comment unless the
implementation guarantees it AND a caller can depend on it. For a predicate whose checks are
internally reorderable, document WHAT it returns, not the sequence in which it decides. When an
ordering genuinely is part of the contract, add a test that fails if the order changes — otherwise
the Javadoc is an unenforced claim that drifts on the first refactor. More generally: an
ordering/guard claim about a relationship between two classes must either (a) be stated at the call
site that actually establishes the ordering, or (b) name the caller it depends on, so a later
reader — or gate — has somewhere concrete to check it against.

## Scope

All Javadoc on predicate and validation methods, especially ones invoked from a different class
than the one whose ordering they describe. Candidate: a pre-submission self-review detector for
"ordering/guard/skip/disable claim in a doc comment with no test and no same-class verification" —
the CodeRabbit path instruction that caught this already exists externally; the open question is
whether an equivalent check belongs earlier in the pipeline.
