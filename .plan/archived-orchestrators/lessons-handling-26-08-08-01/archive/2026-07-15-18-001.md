# Dispatched phase agents improvise non-existent manage-* subcommands, hitting exit-2 argparse_rejection — consult the target script's Canonical invocations for the exact verb

Across a single plan run, three separately-dispatched phase agents each
invoked a `manage-*` subcommand that does not exist in the script's argparse
`choices`, and each call was rejected with `exit_code=2`
(`failure_kind=argparse_rejection`). The three instances share one root cause:
the agent **paraphrased or generalized** a verb rather than using the exact
subcommand documented in the target script's `SKILL.md` § "Canonical
invocations".

## Evidence (this plan, three phases)

| Phase | Improvised call | Actual argparse surface |
|-------|-----------------|-------------------------|
| 1-init | `manage-files add` | `manage-files` has no `add`; valid: `read, write, remove, list, exists, mkdir, create-or-reference, discover, open-in-ide, detect-ide` (the caller recovered with the correct verb on the next call) |
| 2-refine | `manage-status phase-handshake` | `phase_handshake verify` is a **standalone script** (`plan-marshall:…:phase_handshake`), NOT a `manage-status` subcommand |
| 3-outline | `manage-findings qgate query` | the `qgate` action group is `{add, list, resolve, clear}` — there is no `query`; the intended verb is `qgate list` |

All three self-corrected within the same phase (no shipped defect), so they
never blocked the run — they surface only as `[ERROR] … script_failure`
work-log lines. The recurrence is the signal: subcommand improvisation is a
persistent, cross-phase habit, not a one-off.

## Why it happens

The confusables are seductive because sibling scripts *do* carry the guessed
verb. `add` exists on `manage-tasks`, `manage-findings`, `manage-lessons`,
and `manage-references`, so an agent generalizes `add` onto `manage-files`
(which uses `create-or-reference` / `write` instead). `phase_handshake verify`
reads like a status operation, so it gets attached to `manage-status`. `query`
is a natural synonym for `list`. In every case the agent reasoned from analogy
instead of reading the exact choices.

## Corrective action (do X, not Y)

- **Do** consult the target script's `SKILL.md` § "Canonical invocations"
  (the plugin-doctor `manage-invocation-invalid` source-of-truth) for the exact
  subcommand + flag surface BEFORE invoking any `manage-*` verb you have not
  used verbatim in this session. The workflow-discipline hard rule "Never
  improvise script subcommands — use only those documented" governs this.
- **Do not** generalize a verb across scripts by analogy (`add`, `query`) or
  attach a standalone script's verb to a `manage-*` namespace
  (`phase_handshake` onto `manage-status`).
- **On recurrence / after the fact**, the dedicated
  `pm-plugin-development:recipe-fix-argparse-rejection` remediation recipe
  targets exactly this `exit_code=2 / argparse_rejection` class (invented or
  paraphrased subcommands and flags).

## Impact

Self-corrected argparse rejections are cheap individually but the pattern
wastes a dispatch turn per occurrence and pollutes the work-log's
`script_failure` signal. Anchoring every `manage-*` call to the Canonical
invocations block eliminates the class at the source.

## Recurrence — 2026-07-27 (refusal-recognizer-generalizes-phrasing) — the documented-absence sub-facet reproduced one plan later, and the mechanism behind it is now identified

`git-workflow commit … --push` was guessed again by the phase-5 leaf, hit the exit-2
rejection, and the leaf fell back to plain `git`. This is a **verbatim reproduction of the
sub-facet introduced only one plan earlier** (2026-07-26 entry, row 4). A sub-facet whose
whole point was "an explicit negative statement in the standard did not prevent the guess"
recurring on the very next plan is the strongest possible confirmation of its own thesis.

Re-verified this run: `git-workflow --help` lists exactly
`{format-commit, analyze-diff, detect-artifacts, force-push-with-lease, switch-and-pull,
prune-local-and-remote-ref, branch-sync-state, worktree-path, worktree-create,
worktree-remove, worktree-list, locate-plan-checkout, worktree-rebase-to,
baseline-reconcile}`. No `commit`. No `push`.

**Identified mechanism — skill/script co-naming across two different execution modes.** The
prior entry recorded WHAT was guessed; this run establishes WHY this particular verb is the
one that keeps getting guessed, and it is a structural property, not a lapse:

- `plan-marshall:workflow-integration-git` is a `mode: workflow` skill whose SKILL.md carries
  a **"Workflow: Commit Changes"** section with a `push` parameter. Its Step 5 stages and
  commits via raw `git -C {worktree_path} commit -F …`; its Step 6 pushes via
  `git -C {worktree_path} push`. There is deliberately no script verb behind either step.
- `plan-marshall:workflow-integration-git:git-workflow` is the script in that same skill, and
  it is co-named with it.
- Callers legitimately write `Skill: plan-marshall:workflow-integration-git` followed by
  "Execute the git_workflow skill's **Workflow: Commit Changes** with `push: true`"
  (`phase-6-finalize/standards/push.md` lines 104-111; `phase-5-execute` Step 10a is the
  same shape).

So the calling doc contains the tokens *git*, *workflow*, *Commit*, and *push: true* in
close proximity, and the bundle exposes a script whose name matches the skill. An agent that
reads the instruction as a script invocation rather than a workflow-mode skill body derives
`git-workflow commit --push` almost mechanically. **The calling docs are correct** — this was
checked directly this run, and no correction is owed to `push.md` or to phase-5 Step 10a. The
misread is on the consuming side, and it is predictable from the naming, which is why a
negative sentence in `argument-naming.md` does not suppress it: the agent is not consulting
the script's contract at all, it believes it is following the workflow doc.

**What this adds to the corrective action.**

1. **Add the mode check to the pre-call validator's remit.** Before deriving a script call
   from a workflow instruction, confirm the instruction names a script verb and not a
   `mode: workflow` skill section. A `Skill:` load followed by "execute the X workflow" is an
   in-context skill body to follow, never a subprocess to invoke — the two are distinguishable
   at parse time by the presence of the `Skill:` directive.
2. **Treat skill/script co-naming as the risk marker.** `workflow-integration-git` /
   `git-workflow` is the known instance; any `mode: workflow` skill that ships a co-named
   script has the same confusable surface, and its workflow-section headings will read as verb
   names. Worth an inventory sweep.
3. **The standing conclusion is unchanged and now has a second independent proof point.**
