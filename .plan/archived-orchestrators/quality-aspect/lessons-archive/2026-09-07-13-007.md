# State the arithmetic that makes a closure claim checkable, or do not make the claim

## Context

Across plan `plan-04-autonomy-gate-defaults` (epic `operator-ux`, PR #1437), **nine** findings in one
run flagged the same shape: a claim that a set was closed — every site swept, all cases covered, the
population fully handled — asserted without the count that would let a reader check it.

Five in 6-finalize (`942b81`, `f95edc`, `c53c11`, `9409e3`, `f4bda1`), three in 3-outline
(`143cee`, `1cf925`, `5c519f`), one from PR review (`01f18a`). Three phases, two reviewers, one
shape.

## Root cause

A closure claim is a statement about a **population**, but it is written in the grammar of an
observation. "All the call sites now pass the flag" reads as a report of work done; it is in fact an
assertion that the number of call sites equals the number changed. Without both numbers a reader
cannot tell a swept set from a sampled one, and neither can the author on re-reading.

The claim is cheap to make and expensive to check, which is why it recurs — and why it survives
review rounds that are looking at the change rather than at the claim.

## Proposed action

A claim of the form *all / every / no remaining / fully* carries its arithmetic in the same
sentence: the population, the count handled, and how the population was derived. "All 23 call sites
(`architecture search --content`, clean coverage) now pass the flag" is checkable; "all call sites
now pass the flag" is not.

Where the population cannot be derived, say that instead — an unbounded set is a legitimate answer
and a false closure claim is not.

## Impact

Nine instances in one run, none of which was a wrong *fact* — the sweeps had largely been done. The
cost is that no reader, and no later author, can distinguish these from the ones that were not; the
claims are unfalsifiable as written, so they carry no evidence either way.

This generalises past this plan: it is the authoring-side complement of the count-without-a-
denominator defects the corpus already records on the instrument side (`2026-09-06-08-002`,
`2026-09-06-07-001`). Same failure, one on machines and one on prose.
