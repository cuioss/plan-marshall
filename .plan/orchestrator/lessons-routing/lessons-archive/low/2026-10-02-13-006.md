# Execute leaves repeat the same argparse rejections on every re-dispatch: get-deliverable --number and post_run_source_guard --fail-on-dirty


## Observed (API-Sheriff, plan-23-session-route-scope-parity, 2026-09-25 to 2026-10-01)

The same script calls were rejected by argparse (`exit_code=2`) again and again, each time by a
freshly dispatched leaf that had no memory of the previous rejection.

| Call | Rejection | Occurrences |
|------|-----------|-------------|
| `manage-solution-outline get-deliverable --number N` | `--number` is not declared; the declared flag is `--deliverable-number` | 2026-09-25T09:37Z and 12:47Z; 2026-10-01T07:41Z, 07:55Z, 08:10Z and 10:26Z (twice) |
| `manage-solution-outline read --deliverable` | `--deliverable` is not declared (declared: `deliverable-number`, `plan-id`, `raw`, `section`) | 2026-09-25T08:43Z, phase-4-plan |
| `phase-6-finalize:post_run_source_guard check --fail-on-dirty` | `--fail-on-dirty` is not declared (accepted: `project-dir`, `step-id`) | 2026-10-01T11:44Z |

Every `--number` call was retried with `--deliverable-number` and succeeded, so each occurrence cost
one round trip and one ERROR line, and nothing carried the correction to the next leaf. For the third
row the leaf reported that the Step 11b clean-tree command documented in `phase-5-execute/SKILL.md`
does not match the installed script.

A fourth rejection in the same run (`architecture search` with `--project-dir` placed after the verb)
is the already documented flag-position signature and is not counted here.

## Possible cause, not verified

During the lessons-capture step of this plan the workflow document resolved from plugin cache version
0.1.1719 while the skills loaded from version 0.1.1787. Two plugin versions were live in one session.
A document of one version calling a script of the other would produce exactly a "documented flag is
not declared" rejection. Whether that explains the three rows above was not checked.

## Directive

- The step in `phase-5-execute` (and `execute-task`) where a leaf needs a deliverable should carry
  the exact call inline: `manage-solution-outline get-deliverable --plan-id {plan_id}
  --deliverable-number {N}`. A leaf that has to derive the flag derives `--number`.
- Check the Step 11b clean-tree command in `phase-5-execute/SKILL.md` against the
  `post_run_source_guard check` parser and remove `--fail-on-dirty` from whichever side is wrong.
- A rejection that repeats across dispatches of one plan should reach the next dispatch (for example
  as a line in the dispatch prompt), since a new leaf cannot learn from the work log on its own.
- After a plugin update, confirm that the executor and the loaded skills resolve from the same
  version before a long run.
