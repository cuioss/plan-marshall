# Rebase a stacked child PR after its base squash-merges before re-reading a refusal

## Context

The 112-file pass was split into two stacked PRs: #1436 (part-1, based on `main`) and #1435 (part-2, based on part-1's branch). Part-1 was reviewed, fixed, re-reviewed and **squash-merged** as `5c1c8b2`.

Because a squash merge leaves no merge commit linking part-1's branch, GitHub kept computing part-2's diff from the pre-split merge-base. Part-2 retargeted to `main` and reported **112 files again** — back over the review bot's 100-file cap. The bot surfaced this as "Action not completed - Review rate limited", which reads as a quota problem.

Two operator-authorised 90-minute quota waits, over three hours of wall time, were spent waiting for a quota window that was never the blocker. The actual fix was one command — `git rebase --onto origin/main be27eb720` — after which part-2 reported its true 36 files and was reviewed.

## Root cause

Two compounding causes:

1. **Mechanical.** A squash-merged base leaves a stacked child's merge-base stale. Retargeting the child to `main` does not repair it; only rebasing the child's own commits onto the new `main` does.
2. **Diagnostic.** A size refusal was masked behind a rate-limit notice, and the wait path was taken on the notice's wording rather than on a re-measurement. The PR's own reported file count — 112, unchanged after part-1 merged 76 of them — was visible the whole time and directly contradicted the rate-limit reading.

## Proposed action

1. When a stacked PR's base merges, rebase the child onto the new base branch before re-requesting review — make this a step, not a judgement call.
2. Before spending a quota wait on any review refusal, re-measure the PR's changed-file count. A file count that did not fall after the base merged is proof the merge-base is stale, and waiting cannot move a file-count ceiling. This is the same class as the already-recorded rule that a structural refusal is not waitable; it needs to survive being *disguised* as a waitable one.
3. Treat "the observable did not move after the action that should have moved it" as a provenance trigger, per the establish-provenance-before-re-attempting principle. The second 90-minute wait was a blind retry of the first.
