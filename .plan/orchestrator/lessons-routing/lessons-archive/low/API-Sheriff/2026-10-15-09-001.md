# Candidate lesson: a boot reader that hand-lists policy-block scopes misses a widened scope

**Source**: plan-v02-24-policy-block-resolution, PR #465, CodeRabbit inline finding 53de56 (fixed in-run by TASK-13, commit 0ad1f16d).

## What happened

The plan widened the scope sets of the `PolicyBlock` descriptors (one rule resolves every policy block, nearest declared scope wins). `ConfigBootPipeline.maxDeclaredBodyBytes` scanned `max_body_bytes` declarations by hand-listing the anchor, endpoint and route scopes instead of reading them from `PolicyBlock.SECURITY_FILTER`. If the descriptor gains a scope, the boot check silently skips declarations at that scope. Nothing in the local gate caught it. CodeRabbit flagged it under the "hardcoded list that mirrors a set defined elsewhere" path instruction.

## Corrective rule

A boot-time or validation reader that walks policy-block scopes must take its scope set from the `PolicyBlock` descriptor itself, through an exhaustive `switch` over the scope enum, so the compiler rejects a new scope that has no handling. It must not re-enumerate scopes by hand. When a plan widens or narrows a descriptor's scope set, search for every reader of that block's key, not only the resolver.

## Suggested classification

Project-local (API-Sheriff config/boot). Candidate component: `api-sheriff` config boot pipeline. Related to candidate "doc enumerations of PolicyBlock.ALL" from the same run (same defect class, applied to prose).

# Candidate lesson: prose that enumerates PolicyBlock.ALL goes stale; link the test-bound scope table instead

**Source**: plan-v02-24-policy-block-resolution, PR #465, CodeRabbit inline findings a6698a (`doc/adr/0007-anchor-scoped-policy.adoc`), 8c538b (`doc/architecture.adoc`) and 7cab73 (`doc/user/anchors.adoc`). All three were fixed in-run in commit 5d3ffd36.

## What happened

Three documents each restated the full list of policy blocks in running prose. `PolicyBlockSchemaContractTest` binds exactly one documented list to `PolicyBlock.ALL`: the scope table in `doc/user/anchors.adoc` (`_policy_block_scopes`). The other three copies had no guard, so a future descriptor change would leave them stale without any failing test. CodeRabbit raised the same path instruction on each copy.

## Corrective rule

A document must not enumerate the policy-block inventory, or any other set that the code owns, outside the one test-bound table. Point to `_policy_block_scopes` instead. When the enumeration is the point of the passage, as in an ADR amendment that decides scope sets, label it as the set decided at that time and link the live inventory. Before a plan touching `PolicyBlock` is submitted, run a content search for the block names across `doc/` to find unguarded copies.

## Suggested classification

Project-local (API-Sheriff docs). Same defect class as the boot-reader scope candidate from this run. Could be one lesson: "derive or link, never re-enumerate, a set the code owns."

# Candidate lesson: widening a policy block's scope set leaves user-doc scope labels and fallback chains wrong

**Source**: plan-v02-24-policy-block-resolution, PR #465, CodeRabbit findings 996382 (inline, `doc/user/endpoint-routes.adoc:126`) and dc8117 (review body, outside-diff, `doc/user/endpoint-routes.adoc` "Defaults for omitted blocks", `allowed_methods` row). Both were fixed in-run (commits 5d3ffd36 and ec6cb7b5).

## What happened

The plan widened descriptor scope sets so that one nearest-declared-wins rule resolves every block. Two prose descriptions in `endpoint-routes.adoc` still described the old scope set.

- A YAML example comment said a `forward` block inside `routes[]` was refused "at the endpoint as here". The block shown is route-level, and the refusal applies at either scope.
- The omitted-block defaults table described the `allowed_methods` fallback as anchor, then global, then the standard verb set. It did not say that a declared endpoint list is the nearest scope and wins (`PolicyBlock.ALLOWED_METHODS`: gateway, anchor, endpoint).

Neither statement is covered by a test, so only the review bot caught them. CodeRabbit's suggested wording for dc8117 would have contradicted the row it was editing, so the fix had to be rewritten rather than applied verbatim.

## Corrective rule

When a plan changes a `PolicyBlock` descriptor's scope set, audit every user-doc passage that names a scope ("at the endpoint", "anchor's list", fallback chains) for that block, including YAML example comments and default tables. Review the bot's suggested wording against the row or example it edits before taking it.

## Suggested classification

Project-local (API-Sheriff user docs). Companion to the two "derive, never re-enumerate" candidates from this run. This one covers scope *labels* in prose rather than inventory lists.
