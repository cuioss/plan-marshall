# Documented startup and liveness guarantees were broader than what the code enforces

## Problem

Plan-04 (PR #834) added user-facing statements about startup validation and liveness that overstated what the code enforces, and CodeRabbit flagged both. `health-checks.adoc` claimed an invalid `sheriff.token.issuers.*` configuration fails the boot, but `IssuerConfigResolver` validates only enabled issuers. `README.adoc` claimed a configuration or JWKS problem never triggers a container restart, but an invalid issuer configuration aborts startup (`TokenValidatorStartupInitializer` rethrows), so the container exits and its restart policy applies.

## Solution

When docs state a guarantee ("X fails the boot", "Y never restarts"), check its exact scope against the enforcing code path before committing, paying attention to enabled/disabled, property-configured/external and startup/runtime. Prefer naming the enforcing component and its condition over absolute wording ("always", "never", "any invalid configuration").

## Impact

Each overstatement cost a review round and a fix commit, and in operations an overstated boot or liveness guarantee misleads people about restart behaviour.
