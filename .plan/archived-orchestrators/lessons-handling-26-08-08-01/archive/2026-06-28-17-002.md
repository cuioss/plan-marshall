# A taxonomy-renumber sweep must re-home each cross-reference by semantic content, not substitute old number for new — content that moved between categories is invisible to a pure number-substitution pass

When migrating a document set from one version of an external taxonomy to a newer
one (OWASP Top 10 2021 → 2025, a CWE revision, any versioned external category
scheme), the renumber sweep MUST re-home every cross-reference by the SEMANTIC
content it describes — asking "which category does this concern belong to *now*?"
— not by mechanically substituting the old category number with the new one. A
pure number-substitution pass is structurally blind to any content whose category
membership *moved* between versions, because such content's old number maps to a
new number that no longer describes it.

## Symptom

During the OWASP 2021 → 2025 harmonization, `secrets-handling.md` mapped
"supply-chain / CI-CD secret handling" to **A08 Software and Data Integrity
Failures** (its 2021 home). In OWASP 2025, supply-chain concerns were split out
into their own dedicated **A03** category, so the parenthetical should now map to
A03 — the concern *moved categories*, it was not merely *renumbered*.

The plan's own phase-3-outline and phase-5 execution performed a number-for-number
substitution across sibling-doc cross-references. That pass correctly updated every
reference whose concern stayed in the same category (only the number changed), but
it silently left the one cross-reference whose *semantic content had changed
category* pointing at the wrong (substituted) category. No in-house gate caught it
— the document was internally well-formed and the number was a valid 2025 number;
it was simply the wrong category for that concern. The gap was surfaced only by the
post-PR review bots (Gemini + CodeRabbit).

## Root cause

A taxonomy migration conflates two distinct operations:

1. **Renumber** — the same category exists under a new number (A→B). A
   number-substitution pass handles this completely.
2. **Re-home** — a concern's category membership *changed*: content that lived in
   category X under the old version belongs to a *different* category Y under the
   new version (supply-chain: A08-2021 → A03-2025). Number substitution is wrong
   here, because it maps the concern to whatever the old number became, not to the
   category that now owns the concern.

A pure number-substitution sweep models the migration as case (1) only. Case (2)
content is invisible to it: the substitution produces a syntactically valid, wrong
mapping, and per-document validation cannot detect it because each document is
individually consistent. This is the migration-time sibling of lesson
2026-06-28-12-001 (the dual-version *coexistence* hazard — cite the target doc's
version numbers when two versions live side by side). That lesson governs
references *between* docs of different versions; THIS lesson governs the *act of
migrating* a doc set from one version to the next.

## Durable fix

When outlining or executing a taxonomy/standard version-migration sweep:

1. **Re-home by semantic content, not by number.** For each cross-reference,
   re-derive the target category from the concern it describes under the *new*
   version's category definitions — do not assume `new_number = renumber(old_number)`.
2. **Build the old→new mapping at the CATEGORY-MEMBERSHIP level, not the
   number level.** Explicitly enumerate which concerns *moved categories* between
   versions (e.g., the 2025 split-outs and merges) and treat those as re-home
   targets, distinct from the bulk renumber targets.
3. **A number-substitution pass is a starting heuristic, never the whole sweep.**
   After substitution, walk every reference whose *concern* could have changed
   category and validate its target by content, because no deterministic in-house
   gate validates a cross-category semantic move.

## Impact

Applies to any plan-marshall sweep that migrates a document set across versions of
an external taxonomy or standard where categories are added, split, or merged
between versions. Phase-3-outline must scope the deliverable as a semantic
re-homing task (concern → current-version category) and not as a flat
number-substitution; phase-5 execution must not collapse it to a find-replace.
Without that framing, content that moved categories ships with a valid-looking but
wrong cross-reference that only adversarial PR review catches.
