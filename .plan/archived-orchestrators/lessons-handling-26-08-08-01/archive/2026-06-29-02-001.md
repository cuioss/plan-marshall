# Phase-3-outline get-module-context resolved use_worktree=true and required worktree_path before the worktree was materialized (created at phase-5), so the call exit-2 rejected

During phase-3-outline a context-gathering call into
`plan-marshall:manage-solution-outline` (a `get-module-context`-style read)
resolved `use_worktree=true` and required `worktree_path`, but the worktree
does not exist yet during outline. The script's runtime precondition guard
rejected the call with `exit_code=2` and the message
`use_worktree=true but worktree_path is empty`.

This is NOT the invented-subcommand / wrong-flag-placement argparse class
governed by `persona-plan-marshall-agent` § "Never invent script
subcommands" (signatures 1-4). The invocation shape was valid; it failed a
worktree-materialization precondition. Worktrees are created at phase-5
move-in (ADR-002) — every phase before phase-5 runs against the main
checkout with no worktree. Any phase-3 step that resolves `use_worktree=true`
and then dereferences `worktree_path` will therefore fail deterministically
for any plan whose `metadata.use_worktree==true`.

## Solution

Phase-3-outline (and any pre-phase-5 caller) MUST resolve module/context
reads against the main checkout, not a not-yet-materialized worktree:

- Gate any `worktree_path`-dependent branch on a non-empty `worktree_path`
  AND `worktree_state==materialized`, falling back to the main checkout when
  the worktree is absent.
- Do not let a context-gathering verb resolve `use_worktree=true` before
  phase-5 move-in. Until the worktree exists, `use_worktree` must behave as
  `false` for the purpose of path resolution during outline.
- The script-side guard (`use_worktree=true but worktree_path is empty`) is
  correct as a containment boundary — the defect is the premature caller, not
  the guard. Fix the call site / phase-3 resolution order, not the guard.

## Impact

Recurrence-class: affects every plan with `metadata.use_worktree==true` that
runs a worktree-dependent context read during phase-3-outline. The failure is
advisory-noisy (exit-2 in the work log) rather than fatal, which is why it
slips through unfixed; the corrective is a pre-phase-5 main-checkout
resolution rule, not a per-call patch.
