# reduced_transcript is truncated and reordered by the consumer TOON round-trip while its counts still describe the intact text

## Context

The chat-history aspect (Aspect 14) receives its whole input from
`extract-chat-signal run --session-id ...`. That script does not read a transcript
itself: it invokes the platform-runtime `chat extract-signal` op in a subprocess
hop, parses the op's stdout with `parse_toon`, and re-emits the parsed record with
`output_toon`.

The runtime emits `reduced_transcript` as a **multi-line quoted scalar**. The
consumer's `parse_toon` does not preserve it.

Measured on plan `unreviewed-merge-gate-holes`, session `ceab9df4`:

| Field | Runtime emits | Consumer forwards |
|-------|---------------|-------------------|
| `reduced_transcript` | 2,475 bytes, 4 operator turns | ~575 bytes, 2 turns |
| `reduced_bytes` | 2475 | 2475 |
| `operator_turn_count` | 4 | 4 |
| `gate_decision_count` | 4 | 4 |

Session `e716a770` loses proportionally more: 4,641 bytes and 16 operator turns in,
roughly 800 bytes and 2 turns out.

The surviving fragments are also **reordered** against the source. The runtime's
text has `user: why did you stop?` before the final `operator-decision:` block; the
consumer's output has it after, with three intermediate operator decisions and the
`<command-args>` line missing entirely.

## Root cause

Two things go wrong together, and only their combination is dangerous.

1. The payload is lost in transport — a multi-line quoted TOON scalar does not
   survive `parse_toon` in the consumer hop.
2. The **counts do not degrade with the payload**. `reduced_bytes`,
   `reduced_turn_count`, `operator_turn_count` and `gate_decision_count` are all
   forwarded verbatim from the runtime record (`cmd_run` reads them straight off
   `record`), so they describe the intact text the consumer no longer holds.

`over_budget` is then computed as `reduced_bytes > read_budget` — against a size
the consumer does not have. Because `no_signal` is false and `over_budget` is
false, the pre-pass routes to **Tier 1**: "feed `reduced_transcript` to the LLM
analysis prompt". The aspect is handed a fifth of the transcript and told it is
complete. There is no skip-reason token, and nothing downstream can distinguish a
truncated transcript from a genuinely short one.

This is the same *symptom* as lesson `2026-09-04-14-002` (a starved transcript
presented as Tier 1) reached by a different route. That lesson concerns the
**reducer's keep predicate** dropping operator-authored turns. Here the reducer
behaved correctly — it kept 4/4 and 16/16 operator turns — and the loss happened
downstream. Fixing the keep predicate would not close this.

## Proposed action

In `marketplace/bundles/plan-marshall/skills/plan-retrospective/scripts/extract-chat-signal.py`:

1. **Stop round-tripping the payload through TOON.** Have the runtime write the
   reduced transcript to a file and return its path, or transport it in a form
   that survives (single-line escaped, or base64), so the consumer forwards bytes
   it actually received.
2. **Re-measure `reduced_bytes` on the value the consumer holds**, and publish the
   runtime's figure separately (e.g. `reduced_bytes_upstream`). When the two
   disagree, the transport lost data and the fragment must say so instead of
   forwarding a count it cannot back.
3. **Route a transport loss to Tier 2** with its own skip-reason token, rather
   than presenting a truncated transcript as Tier 1.

Point 2 alone would have made this defect self-reporting — exactly the property
`2026-09-04-14-002` point 2 asks for, at the next seam down.

## Impact

Every retrospective run on a target that exposes a session transcript. The aspect
that exists to analyse operator interaction has been reading roughly a fifth of it
while reporting full coverage. Any behavioural verdict this aspect has produced —
including "no permission prompt observed" and operator-intervention counts — was
computed over a silently truncated corpus.

## Evidence

- Runtime output captured directly: `work/runtime-chat-s1.toon` (2,475 bytes,
  4 turns, ordered) and `work/runtime-chat-s2.toon` (4,641 bytes, 16 turns)
- Consumer output for the same sessions: `work/chat-signal-s1.toon` and
  `work/chat-signal-s2.toon` — same counts, a fraction of the payload, reordered
- `extract-chat-signal.py` `cmd_run` — `'reduced_transcript': record.get('reduced_transcript', '')`
  forwards the post-`parse_toon` remnant; `reduced_bytes` is forwarded from the
  same `record` unchanged
- The retrospective that found this analysed the runtime output directly,
  bypassing the consumer, because the consumer's output was unusable

## Recurrence — 2026-09-14, plan sweep-the-three-single-instance-defect-classes (epic test-quality)

Same seam, and this occurrence names the concrete mechanism: `reduced_transcript` is not
newline-escaped before it is written, so the TOON round-trip re-parses embedded newlines as
record boundaries. The consumer then reads a structurally different document from the one
the producer wrote, while every count in it still describes the intact text — which is the
property this lesson already records.

Remedy: escape newlines in the `extract-chat-signal` `reduced_transcript` field at the
producer, so the value survives the round-trip as one scalar rather than being re-split by
the reader.
