# Stop extract-chat-signal truncating the reduced transcript across its hop

**Carried out of the `review-apparatus` epic inbox** — message `review-packs-become-published-artifacts-001.md`, sender `review-packs-become-published-artifacts`, promoted by the orchestrator drain of 2026-09-04.

## Context

The chat-history aspect (aspect 14) obtains its transcript from `extract-chat-signal`, a pure consumer that invokes the `platform_runtime chat extract-signal` operation over the executor subprocess hop. Running both sides of that hop against the same session on this plan shows the consumer loses most of the payload it is forwarding.

The upstream runtime op emits the full reduced transcript: 9 turns, 2382 bytes, containing 4 gate decisions and 8 operator turns. The consumer re-emits 4 turns and roughly 765 bytes — while still reporting `reduced_turn_count: 9` and `reduced_bytes: 2382`, both forwarded verbatim from the upstream record. The counts therefore describe a payload the consumer no longer carries.

## Root cause

`_run_chat_signal_op` (`marketplace/bundles/plan-marshall/skills/plan-retrospective/scripts/extract-chat-signal.py:92`) re-parses the runtime's stdout with `parse_toon`, which does not round-trip a multi-line quoted scalar. `cmd_run` then forwards `record.get('reduced_transcript', '')` (line 153) to `output_toon`, re-serialising the already-mangled value. The consumer's output shows doubled escaping (`\\"` where the upstream emits `\"`), confirming the second escaping pass.

The counts survive because they are scalars on the same record, so nothing in the payload signals the loss. This is the confident-signal-hides-a-caveat shape: the fragment reads complete.

## Proposed action

Do not route a multi-line payload through a TOON round-trip. Either have the consumer read the runtime's `reduced_transcript` from a file the op writes (path returned on the record), or have the op emit the reduction to a side-channel file and keep only scalars on the TOON record. Failing that, base64 the field across the hop.

Add a regression test asserting that the consumer's emitted `reduced_transcript` line count and byte length match the `reduced_turn_count` and `reduced_bytes` it reports — the invariant that would have caught this.

## Evidence

- aspect: chat_history_analysis — upstream op emits 9 turns / 2382 bytes; consumer emits 4 turns / ~765 bytes with identical counts
- Lost content includes 6 of the 8 operator turns: the merge-conflict instruction, the `_REGENERATE_COMMAND` question, the CodeRabbit monitor request, the push-cancels-previous-run attribution hypothesis, the one-review-plus-one-re-review ruling, and 3 of the 4 gate decisions
- The operator turns are precisely this aspect's primary signal, so the loss is concentrated in the highest-value part of the payload
