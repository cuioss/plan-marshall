This document records the architectural design, tool mappings, runtime findings, and operational model for the Google Antigravity distribution target in Plan Marshall.

== Overview

The `antigravity` target generator (`marketplace/targets/antigravity/`) compiles Plan Marshall's native Claude Code marketplace bundles into artifacts consumable by Google Antigravity and the Antigravity CLI (`agy`).

Source format remains Claude Code native; the Antigravity target is an export derived from it via the multi-target generator framework.

== Target Architecture

The target is registered in `TARGET_REGISTRY` (`marketplace/targets/__init__.py`) and participates in the `./pw generate` workflow:

[source,bash]
----
./pw generate --target antigravity --output target/antigravity
----

=== Output Layout

Unlike OpenCode's singular directory layout (`skill/`, `agent/`, `command/`), Antigravity uses standard plural directory naming:

[source,text]
----
target/antigravity/
├── skills/
│   ├── plan-marshall-execute-task/
│   │   ├── SKILL.md
│   │   ├── standards/
│   │   ├── references/
│   │   └── scripts/
│   └── ...
├── agents/
│   ├── execution-context.md
│   ├── execution-context-level-1.md ... level-7.md
│   └── execution-context-reader.md
├── commands/
│   ├── plan-marshall-plan-marshall.md
│   └── ...
├── plugin.json
└── dist-manifest.json
----

The sub-directories under a skill in the tree above are examples, not a fixed set. The emitter writes the transformed `SKILL.md` and copies the rest of the source skill directory byte-identical, whatever its sub-directories are named, so a new one ships the moment it exists. A file is left out only when it is one of three things:

* under a directory named in `EXCLUDED_DIR_NAMES` — the bytecode and tool-cache directories;
* a dot-file, or under a dot-directory;
* scoped away from the `antigravity` target by a `targets:` declaration, on the skill or on the file itself.

The rule has one statement, `iter_emitted_skill_files` in `marketplace/targets/component_targets.py`, which the OpenCode emitter shares. The dot-file exclusion belongs to these two emitters: the Claude emitter mirrors a bundle wholesale and still ships dot-files.

=== Filesystem Safety

The emitter strictly enforces containment invariants via `marketplace/targets/fs_safety.py`:

* `refuse_tree_overlap(output_dir, marketplace_dir)`: Refuses generation if the output directory overlaps the source marketplace in either direction.
* Stale output pruning: Removes old bundle artifacts while preserving untouched target outputs.

=== Harness-Specific Rules Bundle (`plan-marshall-antigravity`)

The `plan-marshall-antigravity` bundle (`marketplace/bundles/plan-marshall-antigravity/`) provides harness-specific operational rules, tool invariants, execution discipline, and runtime constraints tailored exclusively for Google Antigravity environments:

* **Target Scoping**: Its `.claude-plugin/plugin.json` declares `"targets": ["antigravity"]`. The multi-target generator includes it in the Antigravity distribution (`target/antigravity/`) while excluding it from other targets (such as Claude Code and OpenCode).
* **Target Rules Skill**: Contains the `target-rules` knowledge skill (`skills/target-rules/SKILL.md`) and the normative rules standard (`skills/target-rules/standards/antigravity-rules.md`).
* **Zero-Token Workspace Delivery**: When installed with `./install.sh --workspace` or `--emit-rules`, the installer synchronizes `skills/plan-marshall-antigravity-target-rules/standards/antigravity-rules.md` into `<workspace>/.agents/rules/plan-marshall-target-rules.md`. Antigravity automatically discovers and injects workspace rules into assistant context without requiring runtime tool calls.
* **Uninstallation Lifecycle**: During full uninstallation (`./install.sh --uninstall`) or selective uninstallation of `plan-marshall-antigravity`, the synchronized `.agents/rules/plan-marshall-target-rules.md` is cleanly pruned.

== Tool & Permission Mapping

Antigravity operates with a distinct set of native tools compared to Claude Code. The mappings are declared in `mapping.json`:

[cols="1,1,2", options="header"]
|===
| Claude Code Tool | Antigravity Tool | Operational Semantics
| `Bash` | `run_command` | Execute shell commands in POSIX runtime. Respects terminal sandbox policies.
| `Read` | `view_file` | Read local file contents by absolute path (lines 1-indexed, slice-based pagination).
| `Write` | `write_to_file` | Create or overwrite files.
| `Edit` | `replace_file_content` | Precision contiguous line edits with exact target match.
| `Glob` | `find_by_name` | Filename search using `fd` glob pattern matching.
| `Grep` | `grep_search` | Content regex and literal searching using `ripgrep`.
| `AskUserQuestion` | `ask_question` | Interactive user prompts and multi-choice selections.
| `Task` | `invoke_subagent` | Spawns subagent execution envelopes.
| `NotebookEdit` | _None (null)_ | Target-absent sentinel: Antigravity provides no native notebook editing tool; fail-closed omit.
|===

== Model Selection & Two-Axis Effort Ladder

Plan Marshall models subagent compute demand using a target-neutral seven-tier ordinal scale (`level-1` through `level-7`, plus `inherit`), realized as a **Two-Axis Effort Model**:

$$\text{Level} = (\text{Model Axis}, \text{Effort Axis})$$

=== Engine Capabilities

Antigravity executes subagents via Google Gemini models. The engine capabilities are declared in `marketplace/targets/antigravity/mapping.json`:

* `flash` (**Gemini Flash 3.8**): Ultra-fast, cost-efficient model. Supports effort values: `low`, `medium`, `high`.
* `pro` (**Gemini Pro 3.1**): Frontier reasoning model. Supports effort values: `low`, `high`.

=== Option 1 Default Ladder

The Antigravity emitter adopts **Option 1** as its canonical default ladder, allocating Flash across levels 1–5 with graduated reasoning effort, and Pro for complex reasoning at levels 6–7:

[cols="1,1,1,2", options="header"]
|===
| Level | Model | Effort | Cognitive Role

| `level-1` | `flash` | `low` | Fast mechanical transforms, log parsing, simple file lookups
| `level-2` | `flash` | `low` | Routine scoped code edits, unit test adjustments
| `level-3` | `flash` | `medium` | Analytical triage, verification feedback, multi-file inspection
| `level-4` | `flash` | `medium` | Solution planning, cross-component refactoring
| `level-5` | `flash` | `high` | Deep investigation, full test suite analysis, exploration
| `level-6` | `pro` | `low` | Complex cross-cutting synthesis, race condition/concurrency analysis
| `level-7` | `pro` | `high` | Maximum architectural synthesis, high-stakes security analysis
| `inherit` | (parent) | (parent) | Inherits parent session's model (omits `model:` and `effort:`)
|===

=== Lockstep Palette Invariant

Target emitters maintain independent, target-native ladder definitions rather than sharing a single vendor-bound model table. The lockstep invariant enforced by `test_level_table_lockstep.py` guarantees that:

1. `DEFAULT_LADDER.keys() == set(LEVEL_PALETTE)` (exact 1:1 parity with the seven canonical rungs).
2. Every model in `DEFAULT_LADDER` is registered in `mapping.json::model_map`.
3. Every effort in `DEFAULT_LADDER` is declared in that model's `supports_effort` list in `mapping.json`.

=== Machine-Local Customization & Steward Seeding

While project configuration in `marshal.json` declares only abstract levels (`level-1` .. `level-7`), local realization can be customized machine-locally in `.plan/local/effort-ladder.json`:

* `marshall-steward` automatically seeds the default Option 1 ladder for Antigravity under `targets.antigravity`.
* The Antigravity variant emitter reads `.plan/local/effort-ladder.json` (or passed `level_pins`) during target generation.
* If `.plan/local/effort-ladder.json` is missing or unconfigured, the generator falls back to the built-in Option 1 defaults in CI and outputs a warning.

== Body Transformations

Skill and agent markdown bodies undergo deterministic transformation before emission:

1. **Skill Directives**:
   `Skill: {bundle}:{skill}` is rewritten to:
   `Call the \`view_file\` tool on \`{bundle}-{skill}/SKILL.md\` before continuing.`
2. **Read Directives**:
   `Read: {path}` is rewritten to:
   `Call the \`view_file\` tool with \`{ AbsolutePath: "{path}" }\` before continuing.`
3. **Slash Commands**:
   `/{name}` invocations are normalized to the registered bundle-prefixed command names.

== Cloud & Sandboxed Environment Findings

Analysis of `.claude/skills/cloud-plan-lane/SKILL.md` and live execution in the Antigravity workspace revealed several critical operational constraints:

=== Sandboxed Execution & Network Egress

* Antigravity provides a secure execution sandbox (`BypassSandbox: false` default).
* Git remote commands (`git fetch`, `git push`, `git clone`) require network access and must be executed with sandbox bypass (`BypassSandbox: true`).
* Build toolchain commands (`./pw`, `uv`, `pytest`, `mypy`) execute within the local environment; when running in worktrees, python virtualenv symlinks (`.venv`, `.pyprojectx`) must link back to the host repository root.

=== Executor Bootstrap & Stale Caching

* Plan Marshall scripts validate command syntax against the generated `.plan/execute-script.py`.
* In isolated worktrees, symlinking `.plan/execute-script.py` from the main repository satisfies `conftest.py` preflight checks.
* `plugin-doctor` caches argparse surfaces on disk at `.plan/temp/plugin-doctor-help-cache/`. When new subcommands or CLI flags are added upstream, deleting this temporary cache directory triggers fresh derivation of script surfaces.

== Consumer Distribution & Installer Mechanics

Plan Marshall provides a consumer installation experience on par with Claude Code's marketplace via the `dist-antigravity` branch.

=== Branch Assets

The emitted `target/antigravity` tree contains:
* `README.adoc`: Copied from `doc/user/install-antigravity.adoc`, rendered directly on GitHub at `cuioss/plan-marshall/tree/dist-antigravity`.
* `install.sh`: A self-contained bash installer script with executable permissions.
* `plugin.json`: Standard Antigravity plugin descriptor.
* `bundle-components.json`: Component attribution inventory mapping each bundle to its relative component paths (`skills`, `agents`, `commands`), generated by the emitter to drive downstream selective installation and pruning.
* `skills/`, `agents/`, `commands/`: Standard Antigravity component directories.

=== Installer Modes & Destinations

1. **Remote Execution (`curl -fsSL ... | bash`)**:
   Downloads the branch or release archive from GitHub, extracts into a temporary directory, and stages into the destination. Bootstrap can target either the latest development branch (`dist-antigravity`) or an immutable release tag (`antigravity/v*`).
2. **Local Execution (`./install.sh`)**:
   Detects local components sibling to `install.sh` and stages them directly. The installer is also copied into the installed plugin directory for local updates and uninstallation.
3. **Destinations**:
   * Global (default): `~/.gemini/config/plugins/plan-marshall`
   * Workspace (`--workspace` / `-w`): `<cwd>/.agents/plugins/plan-marshall`
   * Custom (`--target-dir <path>`): User-specified directory

=== Selective Bundle Installation & Dependency Closure

The installer supports installing subsets of the marketplace while preserving component integrity:

* **Mandatory Core**: The `plan-marshall` core bundle is strictly mandatory and cannot be excluded.
* **Domain Bundle Aliases**: Provides shorthand aliases for tech stacks:
  ** `core`: `plan-marshall`
  ** `java`: `pm-dev-java`, `pm-dev-java-cui`
  ** `python`: `pm-dev-python`
  ** `frontend`: `pm-dev-frontend`, `pm-dev-frontend-cui`
  ** `oci`: `pm-dev-oci`
  ** `docs`: `pm-documents`
  ** `reqs`: `pm-requirements`
  ** `plugin-dev`: `pm-plugin-development`
  ** `all`: All marketplace bundles (default).
* **Dependency Closure**: The embedded Python helper automatically expands required dependencies (e.g. `pm-dev-java-cui` automatically includes `pm-dev-java`, and `pm-dev-frontend-cui` automatically includes `pm-dev-frontend`).
* **CLI Flags**: Supports `--all`, `--core-only`, `-b, --bundles <csv>`, and `--without-bundles <csv>`. Unknown bundles, excluding core, or excluding a base bundle while its child is selected fail closed with exit code 2.
* **Interactive Selection**: When run in an interactive terminal without flags, prompts on `/dev/tty` using an embedded Python stdlib helper (no `jq` or external dependencies required). Non-interactive invocations (such as CI or `PLAN_MARSHALL_NON_INTERACTIVE=1`) default to `--all`.

=== Persistent Manifest & Config Tailoring

During installation:

1. **Installation Manifest (`.install-manifest.json`)**:
   The installer generates `.install-manifest.json` in the target directory recording `installed_bundles`, `bundle_aliases`, and all `managed_files` (relative component paths plus `install.sh` and `bundle-components.json`). Manifest generation is deterministic and contains no timestamps.
2. **Plugin Descriptor Tailoring**:
   The installer rewrites `plugin.json` in the target directory, pruning entries in `"bundles"` that were not selected so that Antigravity only indexes the installed bundles.

=== Atomic Updates (`-U, --update`)

The `-U` / `--update` flag enables safe, atomic updates for existing installations:

* **Prior Selection Detection**: Automatically inspects `.install-manifest.json` in the target directory and preserves the previously installed bundle set unless overridden by CLI flags. Supports `--without-bundles` overlay to subtract bundles during an update.
* **Pre-Update Backup**: Creates a snapshot in `$TARGET_DIR/.install-backup/` containing all previously tracked managed files, `plugin.json`, and `.install-manifest.json`.
* **Obsolete File Pruning**: Prunes files that belonged to previous bundles but are not in the new installation set.
* **Rollback on Error**: Traps errors during staging and manifest updates, restoring the entire installation from the backup directory upon failure before exiting.

=== Safe & Selective Uninstallation

* **Full Uninstall (`--uninstall`)**:
  Removes the entire target directory cleanly without leaving orphaned configuration.
* **Selective Uninstall (`--uninstall --bundles <csv>`)**:
  Validates dependency closures (refuses removal of core or base bundles whose children remain installed), deletes only the managed files belonging to the specified bundles, updates `.install-manifest.json`, and tailors `plugin.json` accordingly.

== Developer Inner Loop (`sync-harnesses`)

For contributors iterating on Plan Marshall bundles, the Antigravity developer workflow is the same command Claude Code and OpenCode use:

1. Edit bundle sources under `marketplace/bundles/`.
2. Regenerate and deploy into the local Antigravity plugin installation:
+
[source]
----
/sync-harnesses --target antigravity
----

Without `--target`, `/sync-harnesses` syncs all three harnesses in one run. The command regenerates the Antigravity distribution target and then runs the sync engine. The same two steps by hand:

[source,bash]
----
./pw generate-antigravity
python3 marketplace/targets/sync.py --target antigravity
----

The project-level workspace skill (`.agents/skills/sync-harnesses/SKILL.md`) is a thin pointer at the single sync engine (`marketplace/targets/sync.py`). For the Antigravity target the engine:

* Deploys `skills/`, `agents/`, `commands/`, `plugin.json`, `install.sh`, and `README.adoc` to `~/.gemini/config/plugins/plan-marshall/` (or `--target-dir`).
* Prunes stale managed entries in `skills/` and `commands/` belonging to the synced bundles while preserving unmanaged user files and agents.
* Supports `--bundles <name>` for scoped deployments and `--dry-run` for non-destructive preview.
* Emits a compact, structured TOON report summarizing deployed component counts (`skills_count`, `agents_count`, `commands_count`, `assets_count`, `deployed_count`) and pruned entries.

== Runtime Abstraction & Permission Configuration

Beyond static generation, Plan Marshall integrates Antigravity as a first-class execution target (`runtime.target: antigravity` in `.plan/marshal.json`) through the platform abstraction layer (`platform-runtime`), permission tooling (`tools-permission-fix`, `tools-permission-doctor`), and project setup (`marshall-steward`).

=== AntigravityRuntime (`platform-runtime`)

The `AntigravityRuntime` subclass implements target operations:

* **Layout Resolution**:
  ** `layout_skill_roots()`: Returns `['.agents/skills', '.agents/plugins/plan-marshall/skills', '.claude/skills']`.
  ** `layout_bundle_cache_root()`: Returns `['~/.gemini/config/plugins/plan-marshall/skills', '~/.gemini/antigravity/skills']`.
* **Harness Constraints**: Enforces a 600-second ceiling for bash execution timeouts.
* **Health Check**: Inspects presence of `~/.gemini/config/config.json` and the installed plugin directory.
* **Session Metrics**: Tracks tokens and lifecycle phase transitions.

=== Permission Architecture & Configuration Storage

Antigravity models permissions using a two-tier configuration hierarchy:

1. **Global Configuration (`~/.gemini/config/config.json`)**:
   Holds machine-wide permissions under `userSettings.globalPermissionGrants.allow`.
2. **Project-Scoped Configuration (`~/.gemini/config/projects/<project_uuid>.json`)**:
   Holds project-specific grants under `permissionGrants.permissionGrants.allow`.

=== Project UUID Resolution

Project configuration files in `~/.gemini/config/projects/*.json` are mapped to workspaces by matching their resource URI:

[source,json]
----
{
  "projectResources": {
    "resources": [
      {
        "gitFolder": {
          "folderUri": "file:///path/to/project"
        }
      }
    ]
  },
  "permissionGrants": {
    "permissionGrants": {
      "allow": [
        "command(python3 .plan/execute-script.py)",
        "command(./pw)"
      ]
    }
  }
}
----

When configuring project-local permissions, `AntigravityRuntime.permission_settings_path("project")` scans existing project manifests for a matching `file://<project_dir>` URI. If absent, a new project manifest with a generated UUID is initialized.

=== Permission Grant Grammar

Antigravity permissions use function-call syntax:

* `command(<pattern>)`: Authorizes CLI command prefixes (e.g. `command(python3 .plan/execute-script.py)`, `command(./pw)`).
* `read_file(<pattern>)`: Authorizes file read access.
* `write_file(<pattern>)`: Authorizes file creation and editing.
* `read_url(<pattern>)`: Authorizes network URL fetch access.

`permission_fix` (`ensure-executor`, `ensure`, `apply-fixes`) translates abstract requests into the Antigravity grammar when `runtime.target == 'antigravity'`, ensuring zero-prompt execution for the Plan Marshall executor and build tools.

=== Marshall Steward Integration

`marshall-steward` integrates harness awareness, deterministic configuration, and plugin discovery for Antigravity:

* **Plugin Discovery & Path Resolution (`bootstrap_plugin.py`)**:
  ** `--target antigravity`: Probes workspace-local (`.agents/plugins/plan-marshall`) and global (`~/.gemini/config/plugins/plan-marshall`) plugin roots.
  ** Path resolution in `resolve_bundle_path`: Transparently maps bundle-relative paths (e.g. `skills/manage-tasks/SKILL.md`) into Antigravity's flat skill layout (`skills/plan-marshall-manage-tasks/SKILL.md`).
* **Harness Detection & Preflight Verification (`determine_mode.py`)**:
  ** Detects active harness via `target_context.resolve_target()`.
  ** `determine_mode.py mode` returns `harness: antigravity`, `target_source`, `harness_configured`, and `harness_reason`.
  ** Subcommand `determine_mode.py check-harness` verifies `.plan/local/harness/antigravity.json` schema, `dist_manifest_sha` freshness against the installed distribution or `.plan/execute-script.py` SHA fallback, and verifies `checks.rules_emitted`, `checks.harness_paths_valid`, and `checks.executor_ready`.
* **Deterministic Script Configuration (`configure_harness.py`)**:
  ** `configure_harness.py` runs deterministically with zero conversational LLM prompt overhead.
  ** Invokes `AntigravityRuntime.project_initial_setup()` and `project_install_hook()` (a deterministic no-op as Antigravity executes without PreToolUse lifecycle hooks; `.agents/hooks.json` is not created), verifies paths and executor readiness, and atomically writes `.plan/local/harness/antigravity.json`.
  ** In Menu Mode preflight, unconfigured checkouts automatically trigger `configure_harness.py` before presenting the steward menu.
* **Worktree State Inheritance**:
  ** Harness configuration paths resolve via `marketplace_paths.resolve_main_anchored_path(f'harness/{target}.json')`, enabling linked worktrees under `.plan/local/worktrees/{plan_id}` to inherit the main checkout's configured harness state without duplicate state files.

== Verification & Test Coverage

The test suite provides complete coverage across:

* `test/marketplace/targets/antigravity/`:
  ** `test_target.py`: Target registration, capability inspection, and layout emission.
  ** `test_config_files.py`: JSON schema validation for `mapping.json` and `frontmatter-rules.json`.

  ** `test_body_transforms.py`: Directive rewriting and slash command expansion.
  ** `test_emitter.py`: Bundle traversal, verbatim copying of the whole skill directory under the emission rule (see _Output Layout_), stale artifact pruning, target-scoped bundle emission, `bundle-components.json` attribution emission, and installer lifecycle validation (selective bundle flags, aliases, dependency closure, manifest persistence, `plugin.json` tailoring, atomic update backup/rollback, workspace rule emission, and selective uninstallation).
  ** `test_variant_emitter.py`: Role-eligible subagent variant generation and ADR-021 model pin application.
  ** `test_level_table_lockstep.py`: Table object identity assertion against Claude target and model alias validity.
* `test/sync-harnesses/`:
  ** `test_sync_antigravity.py`: Component deployment, root asset handling, dry run semantics, managed entry pruning, unmanaged entry preservation, prefix ambiguity resolution, and error exit codes.
* `test/plan-marshall/platform-runtime/`:
  ** `test_antigravity_runtime.py`: `AntigravityRuntime` unit tests covering layout, permission paths, settings I/O, default grants, and health checks.
* `test/plan-marshall/marshall-steward/`:
  ** `test_bootstrap_plugin_behavior.py`: Antigravity plugin-root detection and bundle path resolution tests.
  ** `test_harness_config.py`: Unit test suite covering `check_harness`, `configure_harness`, schema verification, freshness checks, multi-harness coexistence, `determine_mode` return fields, and worktree inheritance.
