title: "pr merge-queue reports enqueued=true corroborated only by the branch rule being active, not by the PR entering the queue"
content: "## Problem

`ci pr merge-queue --pr-number 1425` returns:

```toon
status: success
enqueued: true
enqueue_corroboration: merge_queue rule active on branch
```

`enqueue_corroboration` reads as evidence for `enqueued: true`, but it proves a **different
proposition**: that the branch has a merge-queue rule configured. That is a *precondition* for
enqueueing, not a confirmation that this PR was admitted. Every reason a PR might fail admission
leaves this corroboration true.

The field therefore makes the report more convincing while adding no evidence for the claim it
accompanies. A caller reading `enqueued: true` **with a corroboration attached** has stronger
apparent grounds than one reading the bare boolean, and the extra grounds are spurious.

The same string appears as the `context` of `safe-merge`'s refusal, where it IS apt — there it
explains why an immediate merge is forbidden. Reused as an enqueue corroboration it answers the
wrong question.

## What is NOT established — read before acting on this

The caller (this session) initially concluded the enqueue had failed, on the grounds that
`merge_state` stayed `clean` where a queued PR would report `QUEUED`. **That reasoning is wrong and
the conclusion is unsupported.** GitHub's `mergeStateStatus` enum has no `QUEUED` member — the values
are `CLEAN`, `BLOCKED`, `DIRTY`, `BEHIND`, `UNSTABLE`, `HAS_HOOKS`, `DRAFT`, `UNKNOWN`. Queue
membership is exposed by `isInMergeQueue` / `mergeQueueEntry`, which the `ci` abstraction does not
surface at all.

So this lesson does **not** claim the enqueue fails. It claims something narrower and checkable: the
verb reports an outcome it does not observe, and the caller has no exposed field with which to check
it. Whether the PR actually entered the queue in this instance remains undetermined — which is
itself the point.

The one surviving observation is weak and is recorded as weak: no `merge_group` check run appeared
within ~13 minutes of the enqueue. A queue legitimately holds entries behind other PRs, so that is
suggestive, not decisive.

## Consequence

A caller cannot distinguish \"admitted to the queue\" from \"call made, outcome unknown\". It waits out
`merge_queue_wait_budget_seconds` (1800s default) holding the cross-plan merge mutex, blocking other
plans, with no way to tell a slow queue from a failed admission. A caller that trusted
`enqueued: true` and skipped the landing poll would record a merge that may not have happened.

## Directive

Make the return report the observation rather than the attempt:

- Base `enqueued: true` on a post-condition read — `isInMergeQueue` / `mergeQueueEntry` for this PR,
  or the platform's queue listing containing it — never on the branch rule.
- Surface queue membership through the `ci` abstraction so a caller can check it without reaching
  for `gh` directly, which the project's hard rules forbid.
- When the post-condition cannot be read, return a distinct `unknown` token. An unobservable enqueue
  is not a success.
- Either give `enqueue_corroboration` content that bears on enqueueing, or remove it. A corroboration
  field addressing a neighbouring proposition is worse than none.

## Verification

Assert against a PR that genuinely enters the queue and, as the matched negative, one whose admission
is refused — the verb must separate them by its return alone. A test exercising only the happy path
passes today against a verb that checks nothing."
