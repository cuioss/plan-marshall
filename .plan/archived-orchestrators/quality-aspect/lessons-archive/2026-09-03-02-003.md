# pr_intent_section render appends, duplicating Intent on an already-populated body

## Context

On plan-170 the created PR body carried an `## Intent` section truncated mid-sentence — the distillation ran to 1492 of its 1500-char budget and the "Explicit non-goals" paragraph was cut. Repairing it meant re-rendering the section against the existing body.

Invoking `pr_intent_section render` on that populated body produced a **second** `## Intent` section rather than replacing the first. The script also recorded an exit-1 internal error during the same sequence. The repair was completed by re-fetching the body and editing it directly instead.

## Root cause

`render` implements append semantics, which is correct for the one flow it was built for — composing a fresh body during `create-pr`, where no `## Intent` section exists yet. Nothing in the verb detects an existing section, and nothing in its contract warns that a second invocation is not idempotent.

The result is a verb that is safe exactly once and silently corrupting thereafter. Because the corruption is a duplicated section rather than an error, it lands in the published PR body and is only caught by a human reading it.

## Proposed action

Pick one and document it in the script's canonical-invocation block:

- **Preferred — make `render` idempotent.** Detect an existing `## Intent` heading and replace its block through to the next `## ` heading or end-of-body. This makes the create flow and the repair flow the same call.
- **Alternative — refuse.** Detect the existing section and exit non-zero with a `section_already_present` payload naming the offset, so the caller must choose `--replace` explicitly.

Do not leave it as append-only with a prose warning: the create flow and the edit flow reach the same verb, and the failure is silent.

Depends on a body-returning read verb existing in the CI abstraction (lesson 2026-09-03-02-002) for the replace path to be performed compliantly.
