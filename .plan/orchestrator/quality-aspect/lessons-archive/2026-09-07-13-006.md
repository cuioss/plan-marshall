# CodeRabbit rate_limit_eta_patterns all require a trailing phrase the observed reset notice does not use

## Context

On plan `plan-04-autonomy-gate-defaults` (epic `operator-ux`, PR #1437) the participation guard
recorded `coderabbit:refused_awaitable ... coderabbit stated no eta`, while sourcery's ETA extracted
cleanly. Ninety minutes later the same run read CodeRabbit's reset time **off the comment by eye**:
*"its notice stated reset in 57 minutes (~07:23Z)"*.

The information was present in the comment; the extraction missed it.

## Root cause

`automatic-review/standards/coderabbit.md:75-78` declares three `rate_limit_eta_patterns`, and every
one requires a trailing phrase — `before requesting another review` or `before ... limit resets`.
The observed notice states the same fact without either phrase, so all three miss.

The patterns are *extraction* regexes behind a separate detection seam, so the refusal itself was
still recognised; only the ETA was lost. That is the mitigating half. The aggravating half is that
the caller then reports the window as unknown, and an unknown window is what makes a waiter decide
it cannot wait.

## Verified still live at HEAD

⛔ **PR #1433 (`fix(automatic-review): arm the CodeRabbit rate-window recovery`) did NOT fix this.**
It armed the recovery path and flipped `review_rate_window_await` to `true`, but
`coderabbit.md:75-78` is byte-identical to the three patterns quoted in the report. Checked at HEAD
rather than assumed from the PR title.

## Proposed action

Add a phrase-free extraction arm keyed on the reset semantics rather than the sentence tail, and add
the observed wording to the pattern list. More durably: the corpus already records that refusal
recognition is ENUMERATIVE and a rewording nobody enumerated is its own state — the same argument
applies to ETA extraction, so an unmatched notice that clearly contains a duration should be
reported as *ETA present but unparsed*, not as *no ETA*.

## Impact

Now materially larger than when observed. `review_rate_window_await` is `true` at HEAD and CodeRabbit
is a **required** bot, so the gate waits on a window whose length it cannot read. On this run only 1
of 10 quota waits was spent and the real blocker was a missing trigger rather than a closed window —
but that is luck, not design.
