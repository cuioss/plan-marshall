Plan Marshall builds a dependency graph of your project's modules and answers four questions over it: what the whole graph looks like (`graph`), how two modules connect (`path`), what sits next to a module (`neighbors`), and what breaks if you change one (`impact`).

The graph is derived, not configured. You declare nothing, and there is no dependency file to maintain: Plan Marshall reads the dependency declarations your build system already has. This page tells you *what you get for your ecosystem*, and — just as importantly — how to tell an empty answer that means "nothing depends on this" from one that means "nothing could answer".

== The four verbs

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-architecture:architecture graph
----

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-architecture:architecture impact --module my-module
----

[cols="1,3", options="header"]
|===
| Verb | Answers

| `graph`
| The whole edge set, plus topological layers. Add `--full` to keep aggregator modules that are otherwise filtered out.

| `path SOURCE TARGET`
| How two modules connect, if they do. Both module names are positional.

| `neighbors --module M [--depth N]`
| What sits within `N` hops of a module.

| `impact --module M`
| Every module that transitively depends on `M` — what you risk breaking by changing it.
|===

Canonical invocations for every flag live in xref:../../marketplace/bundles/plan-marshall/skills/manage-architecture/SKILL.md[`manage-architecture`].

== What your ecosystem gets

Nothing here is opt-in. If your project is one of the ecosystems below, the graph verbs work on a fresh checkout with no configuration.

[cols="1,2,2", options="header"]
|===
| Ecosystem | Identity the graph joins on | Where it reads it

| Maven
| `groupId:artifactId` coordinate
| Each module's coordinate against every module's declared dependencies.

| Gradle
| `group` + module name
| The same coordinate join — Gradle publishes the same pair. See <<gradle-limit>> for the one form it misses.

| Python
| The declared distribution name
| Each module's declared name — PEP 621 `[project]`, else `[tool.poetry]`, else `setup.cfg` — against every module's dependency lists (runtime, plus `dev` where the descriptor form has one).

| npm / yarn / pnpm
| The `package.json` `name`
| Each package's name against every package's `dependencies` and `devDependencies`, workspace members included.
|===

Three further joins run over cross-references rather than build declarations: Python `import` statements, marketplace markdown references, and AsciiDoc cross-document references. Those need a crawled marketplace or documentation corpus, so an ordinary application project will not see them contribute. Your build-system join does not depend on them.

[NOTE]
====
*You will see every discovered resolver in every response* — one row each, whatever your project is built with. Resolver discovery is registry-wide, not project-scoped, so a Python project still carries an `npm` row and an npm workspace still carries a `maven` one, each reporting `edge_count: 0`.

A zero row is usually not a defect and not a sign that something is misconfigured: it normally means that resolver ran and had nothing to contribute here. Check the row's `status` to tell that apart from the two other reasons a row can be empty — `error` (it ran and failed) and `not_dispatched` (it never ran, because this machine switched it off; see xref:configuration.adoc#derivation-resolvers[Configuration › Which derivation resolvers run]). What matters overall is `resolver_count` — see <<reading-an-empty-answer>>.
====

=== Python specifics

Names are matched the way Python packaging matches them: case-insensitively, with any run of `-`, `_` or `.` treated as equivalent. A module publishing `sample-api` is therefore reached by a dependency spelling it `Sample_API`.

Up to two scopes are read, depending on which descriptor form supplied the name: a runtime dependency list, and a `dev` group. PEP 621 gives both (`[project] dependencies` and the `dev` extra under `[project.optional-dependencies]`); Poetry gives both (`[tool.poetry.dependencies]` and `[tool.poetry.group.dev.dependencies]`); `setup.cfg` gives runtime only (`[options] install_requires`), because it has no `dev` equivalent. A `dev` entry is a real edge, because changing the module you depend on can break your tests.

Other extras are *not* read. A sibling named only under a `test`, `docs` or `all` extra produces no edge — move it to `dev` (or to `dependencies`) if you need it in the graph.

A directory that names no distribution in any of the descriptor forms below publishes nothing, so nothing can depend on it. It still appears as a module and its own dependencies still produce edges — it simply cannot be the *target* of one.

Three descriptor forms are read, in this order: PEP 621 `[project]`; then `[tool.poetry]` in the same `pyproject.toml`, when `[project]` is absent or names nothing; then `setup.cfg` (`[metadata]` for the name, `[options] install_requires` for runtime dependencies). The later forms are strict fallbacks — neither overrides a name PEP 621 already supplied.

[WARNING]
====
*The NAME decides which forms are read, and one hybrid layout loses its edges because of it.* If `[project]` supplies a `name`, no later form is consulted at all — including its dependency lists. So a `pyproject.toml` with a `[project]` table carrying the name and its dependencies under `[tool.poetry.dependencies]` publishes the name and *no dependencies*: the module becomes a valid edge target and contributes no outbound edges, with nothing in the output saying why.

The gate is the name on purpose: `metadata` and `dependencies` are read by consumers beyond edge derivation, and letting a later form supply a name the earlier one already gave would make which descriptor wins depend on read order. If your project is in this shape, move the dependencies under `[project] dependencies`, or remove the `name` from `[project]` so the Poetry table is read whole.

NOTE: When an earlier form supplies dependencies but *no* name — `[project]` with a `dependencies` list and no `name`, which is invalid PEP 621 — the later form is consulted and its dependencies are *added* to what the earlier one already contributed. The result is a union, never an override, so no declaration is lost; but it does mean "only one form is read" holds for the name, not for every field.
====

`setup.cfg` behaves the same way for the same reason: it is consulted only when neither table in `pyproject.toml` supplied a name.

`setup.py` is *not* read, and cannot be: it is executable Python rather than a declaration, so no static reader can tell what it will pass to `setup()`. A module whose only descriptor is `setup.py` therefore publishes no name and no dependencies — it appears as a module, but nothing can depend on it and it declares nothing. Add a `[project]` table or a `setup.cfg` to bring it into the graph.

A `pyproject.toml` that does not parse — an unbalanced bracket, a bad encoding — publishes nothing *from that file*, and a *warning naming it* is written to the run log. The `setup.cfg` fallback still applies, so a module with both may still publish a name; a module with only the broken `pyproject.toml` publishes none. That warning is the difference between the module declaring nothing and its descriptor being broken, and the second case also silently costs you every edge pointing *at* that module, because the name those edges match on was never published.

=== npm specifics

Workspace members need no setup. Plan Marshall resolves the `workspaces` globs from `package.json` (both the array and `{"packages": [...]}` forms) and pnpm's `pnpm-workspace.yaml`, then treats each member as a module.

Scoped names work unchanged: `@scope/pkg` is one name, and the scope is part of it. The `workspace:*` protocol never reaches the join, because only the dependency's *name* is read — the version specifier is irrelevant to whether the edge exists.

`devDependencies` count, for the same reason `dev` extras do in Python.

Two of npm's four dependency kinds are read: `dependencies` and `devDependencies`. `peerDependencies` and `optionalDependencies` are *not*. A package that names a sibling only under one of those produces no edge — which matters most for `peerDependencies`, the idiomatic way a plugin package declares its dependency on a workspace's core package. Move the sibling to `dependencies` or `devDependencies` if you need it in the graph.

A package with no `name` in its `package.json` cannot be published, so nothing can depend on it — same rule as Python, same consequence: a source of edges, never a target.

[[gradle-limit]]
=== The Gradle limitation

Gradle modules are covered by the coordinate join, with one gap. A dependency declared by full coordinate — `implementation "com.example:core:1.0"` — produces an edge. A dependency declared the idiomatic inter-project way — `implementation project(":core")` — does not: it is recorded as `project:core:compile`, and the join compares the first two segments (`project:core`), which match no module's published coordinate.

If your Gradle build wires its modules together with `project(...)`, expect an empty internal graph today.

[[reading-an-empty-answer]]
== Reading an empty answer

An empty result has several very different meanings, and the response tells you which one you are looking at. Check `resolver_count` — which counts the resolvers that *ran*, never the ones that *contributed*, and never the ones this machine switched off:

[cols="1,3", options="header"]
|===
| Response | What it means

| `resolver_count: 0` with no edges
| *Nothing could answer.* No resolver ran at all — the empty graph is a missing capability, not a finding about your project.

| `resolver_count: N` with no edges
| *N resolvers ran and found nothing.* This is a real answer: your modules genuinely declare no dependencies on each other.

| `resolver_count: 0` but the `resolvers` list is *not* empty
| *Resolvers exist here, but this machine switched them off.* Every row carries `status: not_dispatched`. Re-enable one through `/marshall-steward` → Configuration → Derivation Resolvers — see xref:configuration.adoc#derivation-resolvers[Configuration › Which derivation resolvers run].
|===

Never read a bare empty list as "my project has no internal dependencies". That is the second row's meaning, and only the count — read together with the `resolvers` list — distinguishes it from the other two.

=== Every edge says who found it

Each edge carries a `producers` list naming the resolvers that derived it, so you can tell where a claim came from. An edge found by two resolvers carries both — they corroborated, they did not conflict.

Two producer names are not resolvers:

* `declared` — you (or a curated overlay) declared this dependency explicitly, and that declaration replaced whatever the resolvers derived for that module.
* `sibling-cross-link` — the two modules are the same directory under two build systems.

A resolver's own report also carries `notes`, which is where it says what it *refused* to answer. The most common entry: two modules publishing the same name. Rather than pick one arbitrarily, the resolver emits no edge for that name and says so — an ambiguous answer is reported as ambiguous rather than guessed.

== Declaring dependencies yourself

If a real dependency is not expressible in your build files, set `internal_dependencies` on the module. A non-empty declaration wins over everything derived for that module, and its edges are stamped `declared`.

An *empty* list is not a declaration. `architecture init` seeds `"internal_dependencies": []` into every module, so an empty list cannot be told apart from an unset one and therefore suppresses nothing.
