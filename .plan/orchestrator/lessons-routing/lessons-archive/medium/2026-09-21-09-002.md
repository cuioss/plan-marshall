# Evaluate files_exist write-new intents against the authoring-time baseline

## Context

In plan plan-04-persona-behavior, Q-Gate findings `05b549` and `4d49f5`
(4-plan, triage, files_exist) flagged TASK-002 write-new targets —
`test_persona_behavior_rules.py` and `__init__.py` — as already existing on
disk. Both resolutions were backfilled post-execute as `taken_into_account`:
write-new was true at authoring, and the files exist only because phase-5
created them in-run.

## Root cause

The `files_exist` check reads post-execute disk state, so every write-new step
a plan itself creates becomes a self-inflicted violation when the gate is
evaluated after execution. The check has no authoring-time baseline to compare
against, and nothing distinguishes "existed before the plan" from "created by
the plan".

## Proposed action

Snapshot the existence baseline for every write-new target at plan-authoring
time (or record the creating task per path), and evaluate `files_exist`
against that baseline instead of raw post-execute disk state. Until the gate
carries a baseline, resolve in-run creations as `taken_into_account` with the
backfill note used here — "write-new was true at creation; file exists
because phase-5 created it" — rather than correcting an intent that was never
wrong.

## Evidence

- aspect: qgate — findings `05b549` and `4d49f5`, both resolved
  `taken_into_account` 2026-09-20 with the backfill note above
- plan: plan-04-persona-behavior, phase 4-plan, TASK-002
