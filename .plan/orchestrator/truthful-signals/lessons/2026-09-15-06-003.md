# A hardcoded list that must mirror a set defined elsewhere is a defect unless derived from that source at build or run time

source_plan: plan-truth-148, plan-truth-157
source_pr: 1488, 1494
source_epic: truthful-signals

## Context

Two independent landings the same day hit the identical archetype from opposite directions:

**`plan-truth-148`** — `record-metrics.md` carried a hardcoded parenthetical list of agent-dispatched
steps that must mirror the dispatcher-owned set in `phase-6-finalize/SKILL.md` Step 3. A new dispatched
step makes the statement false and silently obscures its accumulator contribution. This was the THIRD
instance of the same class found in the same plan's own run, across three different documents — the
self-review found two instances (Q-Gate findings `7bdcff`, `7d57d0`) and CodeRabbit found a third the
self-review had not reached (`49e11e`, `record-metrics.md:41`). Fixed by replacing the parenthetical
roster with a pointer at the dispatcher-owned set.

**`plan-truth-157`** — CodeRabbit found the SAME shape from the other end: hardcoded enumerations of the
orchestrator dispatch surfaces in three test sites (`test_config_defaults.py:2025`,
`test_orchestrator_scope.py:620,645`), which drift when a new surface is registered — the new surface
stays unpinned and untested while every existing assertion keeps passing. A related nitpick asked that a
seven-entry dispatch index in a standards document be DERIVED from the verb documents and compared
against the index, with a non-empty assertion on the derived population so the check cannot pass
vacuously. Fixed by replacing the hardcoded set with the authoritative registered surface set at all three
sites, deriving the population from both source documents and asserting it is non-empty.

## Root cause

A hardcoded enumeration of a set that is authoritatively defined elsewhere (a dispatcher's own step
roster, a registered surface list) will drift the moment the authoritative set gains or loses a member.
The enumeration reads as documentation or as a passing test either way — the failure is silent loss of
coverage, not a visible defect, which is why a review bot can correctly file it as a "trivial/nitpick"
while the actual consequence (an untested new member) is not trivial at all.

**Finding one instance is evidence of siblings, not of completeness.** In `plan-truth-148`'s run, the
class recurred three times across three documents in the same plan; a sweep for other instances of the
same class is owed once the first is found, not treated as a one-off.

## Proposed action

Treat a hardcoded list that must mirror a set defined elsewhere as a defect unless it is derived from that
source at build or run time — either a pointer at the authoritative source (documentation) or a derived,
non-empty-asserted population compared against the authoritative set (tests/assertions). When one instance
is found in a codebase, sweep the surrounding skill/document set for siblings before considering the class
closed. A derived-population guard composes with, and does not replace, a separate VALUE pin on the same
surface — a set guard and a value guard answer different questions.
