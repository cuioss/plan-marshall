# A deliberate deviation from a lint-scanned pattern must carry the analyzer's sanctioned suppression marker at the call site, or it ships as a latent spurious lint hit

## Context

The `session-binding-gc-and-conflict-semantics` plan's deliverable 3 appended a
new logging call to
`marketplace/bundles/plan-marshall/skills/phase-6-finalize/standards/archive-plan.md`:

```bash
python3 .plan/execute-script.py plan-marshall:manage-logging:manage-logging \
  work --level INFO --message "..."
```

The `--plan-id` flag is **deliberately** omitted so the entry lands in the
*global* work log — by the time `archive-plan` runs, the plan directory has been
archived away and a plan-scoped write would have nowhere to go. The omission is
correct on the merits, and `manage-logging`'s argparse surface confirms
`--plan-id` is optional on the write subcommands.

## Signature (slipped, then caught in-run)

The phase-3-outline Q-Gate (finding `0d6464`) flagged the deliverable before any
source was written: `manage-logging` is on the auto-routing whitelist that the
**WL-C** worktree-linter pattern scans for, and *any* `manage-*` invocation
without `--plan-id` in a skill markdown file is a WL-C match. WL-C's suppression
rule fires only for:

- the centralized `worktree-handling.md` standard itself, or
- a line carrying an explicit `Anti-pattern` / `Forbidden` / `Do NOT` marker.

The new line carried neither. As authored, it would have passed every gate in
this plan (the lint that owns WL-C was not in this plan's scoped footprint) and
then surfaced as a **spurious lint hit on some unrelated future plan** whose
footprint happens to include `archive-plan.md` — at which point a maintainer with
no context would have to re-derive, from scratch, whether the omission was a
defect or intentional, and would plausibly "fix" a correct call by adding a
`--plan-id` that cannot resolve.

Resolved in-run (`taken_into_account`) by adding to the deliverable's *Change per
file* text an explicit requirement that the no-`--plan-id` global-log call carry
an approved WL-C suppression marker / global-log justification at the call site.

## Root cause

A correct-on-the-merits deviation from a convention that a **static analyzer
enforces by pattern match** is indistinguishable, to that analyzer and to the
next human reader, from the defect the pattern exists to catch. Correctness of
the deviation and self-documentation of the deviation are two independent
properties, and shipping the first without the second is what creates the latent
finding.

Three properties compound the cost:

1. **Deferred blast radius.** The author's own plan does not pay the price — the
   lint hit lands on a *later, unrelated* plan whose footprint happens to include
   the file. The person who must triage it has none of the context that made the
   deviation obviously correct at authoring time.
2. **Alarm-fatigue erosion.** Each un-suppressed intentional deviation lowers the
   signal-to-noise ratio of the analyzer, training reviewers to wave through the
   pattern class — which is precisely how a *real* instance of the defect later
   slips.
3. **Wrong-direction repair risk.** The natural triage response to a lint hit is
   to make the lint pass, i.e. to add the flag. For a deliberate omission, that
   "fix" is a regression.

## Corrective rule (do X, not Y)

When authoring a change that **intentionally deviates from a convention some
analyzer scans for by pattern**:

- **Y (avoid):** shipping the deviation bare because it is correct, and because
  the analyzer that owns the pattern is not in the current plan's scoped
  footprint so nothing goes red today.

- **X (do):**
  1. **Ask the pattern question at authoring time.** Before adding a call/idiom
     that departs from a whitelisted shape, ask: *is there an analyzer or lint
     rule that pattern-matches this shape?* For `manage-*` invocations in skill
     markdown, the answer is yes — WL-C in
     `workflow-integration-git/standards/worktree-handling.md`.
  2. **Emit the analyzer's own sanctioned suppression marker**, in the exact form
     that analyzer recognizes — not a free-form comment that reads as a
     justification to a human but is invisible to the matcher. Read the
     analyzer's suppression rule and reproduce its trigger literally.
  3. **State the positive justification at the call site**, cross-referencing the
     contract that makes the deviation correct (here: `manage-logging`'s
     documented global/no-plan write path). The marker silences the analyzer; the
     justification tells the next reader *why*, so the deviation is never
     re-litigated.
  4. **Both, in the same change.** A suppression marker added in a follow-up plan
     has already cost the round-trip this rule exists to prevent.

## Why in-house gates miss it

Nothing gates this at authoring time. A scoped `plugin-doctor` / worktree-lint
run only covers the touched-skills footprint of the *current* plan, so a file
edited by plan A but linted under plan B's footprint has no gate in plan A that
would surface the match. There is also no surfacer candidate class for "newly
added line matches a known analyzer pattern but lacks that analyzer's suppression
marker" — the analyzer knows the pattern, and the self-review pass knows the
diff, but nothing joins the two at authoring time.

The defense here was the **outline Q-Gate reading the deliverable against the
lint contract**, which is a reviewer-judgment catch rather than a deterministic
one. Until a deterministic surfacer exists, the proactive discipline above is the
only reliable defense.

## Impact

Caught and corrected at outline in this plan, so nothing latent shipped. The
class affects every skill markdown file that documents a deliberate departure
from a whitelisted/linted invocation shape — the `manage-*`-without-`--plan-id`
global-log path is the concrete instance, but the same shape recurs for any
pattern-matching analyzer with a marker-based suppression rule. The cost of
missing it is not a broken build but a **future maintainer's wasted triage cycle
plus a live risk of "repairing" a correct call into a broken one**.
