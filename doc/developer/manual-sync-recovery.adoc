= Manual Sync Recovery
:nofooter:
:toc: left
:toclevels: 3

xref:../../README.md[Plan Marshall] » xref:README.adoc[Developer Guide]

How to recover the build target (`target/claude/`) and the host plugin cache (`~/.claude/plugins/cache/plan-marshall/`) when a commit landed on the marketplace source without running phase-6-finalize. This page is a recovery surface — the canonical sync path during normal plan execution is the local-finalize chain (`project:finalize-step-deploy-target` followed by `project:finalize-step-sync-plugin-cache`). Empirical motivation: lesson `2026-05-20-08-005`.

== Overview

The meta-project ships through a two-tier sync model:

1. **SOURCE → TARGET**: `marketplace/bundles/` is the authoritative source. `marketplace/targets/generate.py` regenerates `target/claude/` from that source, expanding role-eligible agents into per-level variants and emitting a variant-aware `plugin.json` per bundle plus the top-level `target/claude/.claude-plugin/marketplace.json`.
2. **TARGET → CACHE**: `~/.claude/plugins/cache/plan-marshall/` is what Claude Code actually loads after install. The `/sync-harnesses` slash command rsyncs `target/claude/` into the host cache with `--delete` for exact mirroring. That is its Claude leg, implemented by `marketplace/targets/claude/cache_sync.py`; the same run also syncs the OpenCode and Antigravity installs unless `--target claude` narrows it.

Both tiers exist because Claude Code's plugin loader reads from the cache, not from `target/claude/` directly. `target/claude/` is the registered marketplace path the loader consults at install time; the cache is the runtime load path.

The two slash commands `/finalize-step-deploy-target` and `/sync-harnesses` are meta-project-only — consumer projects of Plan Marshall do not get this surface.

== Symptom → Command decision table

[cols="3,2,4", options="header"]
|===
| Symptom | Command(s) to run | Why

| Modified marketplace bundle source and want changes live in the current session.
| `/sync-harnesses`
| The command regenerates the target trees from the new source and then mirrors `target/claude/` into the host cache so Claude Code loads the new version. One run reconciles both tiers.

| Manual commit to marketplace source landed without running phase-6-finalize (e.g. lesson `2026-05-20-08-005`).
| `/sync-harnesses`
| The regeneration reconciles `target/claude/` with the committed HEAD; the sync mirrors that reconciled tree into the cache. Both tiers were bypassed by the manual commit, and the one command reconciles both.

| Plugin cache looks stale but `target/claude/` matches source.
| `/sync-harnesses --target claude`
| Only the cache mirror is stale. The regeneration is a no-op on a current tree, and the sync refreshes the cache.

| Variant agent dispatch fails with `Agent type not found` (e.g. a `Task:` to `execution-context-level-4` fails immediately).
| `/finalize-step-deploy-target`
| Per-level variants live only in `target/claude/`; the source carries canonicals only. The deploy step is what materialises the variant files Claude Code's agent registry needs.

| Skill changes do not take effect at runtime despite a clean `target/claude/`.
| `/sync-harnesses --target claude`
| The cache mirror is the actual load path. `target/claude/` being current is necessary but not sufficient.

| Skill text is older than the scripts it calls.
| `python3 marketplace/targets/claude/registry_pin.py --apply`, then a full restart of the session
| The registry still names the previous version. The sync moved the plugin cache forward, so scripts resolved through the regenerated executor are current, while a session loads skill bodies from the version the registry is pinned at. A second sync mirrors the same cache again and leaves the same pin, and `/reload-plugins` does not re-read it.

| The sync reports `guard_outcome: stale` for the Claude target.
| `/finalize-step-deploy-target`, then re-run the sync
| The staleness guard in `cache_sync.py` saw a `target/claude/` that is missing, incomplete, or behind `marketplace/bundles/`. Regenerating the tree is the remedy.

| The sync reports `guard_outcome: probe_failed` for the Claude target.
| Repair the probe the `summary_message` names
| A guard check could not run, so the tree's freshness is unknown. Regenerating is not the fix.
|===

== What each command does

`/finalize-step-deploy-target`::
Runs `./pw generate-claude`, `./pw generate-opencode` and `./pw generate-antigravity` to regenerate the build targets from `marketplace/bundles/` — always through the `./pw` wrapper, because `uv` lives in the project-local `.pyprojectx/` tree and is not on `PATH`. For the Claude target it generates per-level agent variants (`{name}-level-1.md` through `{name}-level-7.md`), expands the variant-aware `plugin.json` per bundle, and emits the top-level `target/claude/.claude-plugin/marketplace.json`. Reads source, writes `target/`. Does NOT touch `~/.claude/plugins/cache/` or any other harness install.

`/sync-harnesses`::
Regenerates the selected target trees and then runs the single sync engine, `marketplace/targets/sync.py`. With no arguments it syncs the Claude, OpenCode and Antigravity installs; `--target claude` restricts the run to the plugin cache. The Claude leg, `marketplace/targets/claude/cache_sync.py`, runs `rsync --delete` from `target/claude/` into `~/.claude/plugins/cache/plan-marshall/`. It refuses when `target/claude/` is missing or stale relative to `marketplace/bundles/`. That staleness guard is what protects a direct engine run, `python3 marketplace/targets/sync.py --target claude`, which does not regenerate from source. When the Claude result reports `cache_status: success` the command runs `marketplace/targets/claude/reconcile_daemon.py`, which reconciles a running build daemon with the new cache version, and then the repin script in its report form. The gate is `cache_status`, not the Claude `status`: a `status: partial` caused only by a registry that is `behind` leaves the cache complete, so both still run.

`python3 marketplace/targets/claude/registry_pin.py`::
The repin step. It compares every plan-marshall entry of the plugin registry (`~/.claude/plugins/installed_plugins.json`) with the version in the plugin cache and prints one row per entry — its version before and after, and the action taken — followed by the `registry_parity` verdict: `in_parity`, `behind`, `ahead` or `unreadable`. Without a flag it is a dry run that writes nothing; `/sync-harnesses` runs it in that form after a Claude cache sync. With `--apply` it rewrites an entry that is `behind` to the synced version. It never moves a pin backwards, so an `ahead` entry is reported and left alone. A session reads the registry once, at start, so an applied repin takes effect only after a full restart. xref:marketplace-build.adoc#after-a-claude-sync[Marketplace Build → After a Claude sync] states the whole sequence and the machine-local setting that lets the finalize step apply the repin itself.

== Authoritative path vs manual recovery

The local-finalize chain — `project:finalize-step-deploy-target` followed by `project:finalize-step-sync-plugin-cache`, both running automatically as phase-6-finalize steps — is the canonical sync path during normal plan execution. Both steps run on every phase-6-finalize entry that completes; no developer action is required when a plan ships through the standard flow.

Manual `/finalize-step-deploy-target` and `/sync-harnesses` invocations are recovery surfaces for the rare cases where a commit bypassed the finalize chain. Lesson `2026-05-20-08-005` is the empirical motivation for documenting this path: a manual commit landed on the marketplace registry without running phase-6-finalize, leaving `target/claude/` out of sync with the committed source and the host cache out of sync with `target/claude/`. Operator awareness of which command resolves which symptom is the cheapest mitigation; a CI gate was considered and explicitly declined in favour of this documentation surface.

== When NOT to run these

During an active plan flow these commands run automatically as finalize steps — do not invoke them manually mid-plan. Manual invocation mid-plan can race against the dispatcher's HEAD-dependent re-entry logic for the finalize steps themselves, leaving `phase_steps` records that disagree with the on-disk state of `target/claude/` and the cache. Wait for the plan to reach phase-6-finalize, and let the dispatcher run the steps.

Manual invocation outside a plan flow is the supported recovery surface — that is the entire reason this page exists. The constraint is only against mixing manual invocation with an in-flight plan.
