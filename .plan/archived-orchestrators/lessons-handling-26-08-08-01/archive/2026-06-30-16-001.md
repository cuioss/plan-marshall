# Case-sensitive denylist membership check on caller-controlled keys is bypassable by a case-variant — normalize the key before the check (CWE-178)

A security guard that filters caller-controlled keys against a denylist (or a
reserved-key set) MUST case-normalize the key before the membership test. A
denylist compared against the raw key is bypassable by any case-variant of a
forbidden key.

## What happened

This plan's D3 facet hardened `manage-providers` `configure`/`edit` `--extra`
passthrough by mirroring the `_cred_edit.py` secret-key denylist. The new
`apply_extra_passthrough` (`_providers_core.py`) screened secret keys with a
case-sensitive lookup:

```python
if key in SECRET_PLACEHOLDERS:   # case-sensitive — bypassable
    continue
provider_config[key] = value
```

Supplying `--extra Token=real_token` (capital T) sailed past the `token`
denylist entry and wrote a live secret straight into the git-tracked
`credentials_config` block of `marshal.json`. CWE-178 (improper handling of
case sensitivity) on a credential-write boundary.

All in-house gates (module-tests, quality-gate, plugin-doctor) passed — none of
them model an adversarial mixed-case key. The in-run **security-audit recipe**
caught it (finding 70ab99), the highest-value slipped-then-caught class:
defect introduced and refuted inside the same run.

## Fix

Lowercase the caller-supplied key once, then test every denylist / reserved-key
set against the normalized form:

```python
normalized_key = key.lower()
if normalized_key in SECRET_PLACEHOLDERS or normalized_key in RESERVED_EXTRA_KEYS:
    continue
provider_config[key] = value
```

Ship a case-variant rejection test alongside the fix (`--extra Token=...` must be
dropped exactly like `--extra token=...`), so the regression is locked by a test
that the case-sensitive form would fail.

## Generalizable rule

Whenever a membership test gates caller-controlled input against a fixed set of
forbidden / reserved tokens — secret-key denylists, reserved config keys,
blocked command names, header-name allow/deny sets — normalize the input
(case, and where relevant Unicode/whitespace) into the SAME canonical form the
set is stored in, BEFORE the `in` check. The set being lowercase is not enough;
the lookup key must be lowercased too. A guard that only normalizes one side
silently admits the variant it was written to block.

This generalizes the same one-sided-normalization defect class as the
`--extra url=...` reserved-key gap the PR bot flagged in the same file: a
caller-controlled key reaching a trusted write sink needs its full canonical
guard, not a partial one.
