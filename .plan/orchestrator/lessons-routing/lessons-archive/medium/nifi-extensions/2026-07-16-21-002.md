# build-maven kind=build change-ledger auto-append silently no-ops in a worktree (freshness gate fails closed) — append manually via manage-change-ledger

## Problem

While running builds from an active plan **worktree** during the
`e2e-route-cleanup-rest-api` run, the `build-maven` executor's `kind=build`
change-ledger auto-append **silently no-ops**. The executor's worktree-sha
freshness gate does not resolve against the worktree, so the auto-append fails
closed with no error surfaced — the ledger entry simply never lands. This
happened repeatedly: a manual `manage-change-ledger append` was required **three
times** across the run to keep the ledger current.

## Root Cause

The build-maven auto-append path computes the freshness gate against the
main-checkout worktree-sha context. Inside a plan worktree that anchor does not
match, the gate fails closed, and because the append is best-effort the failure
is swallowed — no non-zero exit, no warning. The result is a silent gap in the
`kind=build` change-ledger substrate whenever the build runs from a worktree.

## Rule / Workaround

- **Do not rely on the build-maven `kind=build` auto-append inside a worktree.**
  Treat the ledger as *not* updated after a worktree build.
- **Append manually after each worktree build** via
  `manage-change-ledger append` so the ledger stays current and the downstream
  freshness API has a real entry to read.
- When finalizing a plan that built from a worktree, verify the change-ledger
  actually captured the build entries before trusting freshness-gated steps.

## Impact

Any plan-marshall plan that runs `build-maven` from a worktree (the normal
plan-execution model). The silent gap can mislead any freshness-gated finalize
step that assumes the ledger reflects the latest build.
