# baseline-reconcile conflict parser misreads localized git merge-tree output

## Problem

`baseline-reconcile.py` derives its `conflicts[]` list by scanning the human-facing
text output of `git merge-tree --write-tree`. It does two things wrong:

1. It does not force a C locale on the git subprocess.
2. Its conflict-line matcher treats **any** line naming a file as a conflict, rather
   than matching an actual `CONFLICT` marker.

On a German-locale git installation the informational `Auto-merging X` line renders as
`automatischer Merge von X`, and the real marker `CONFLICT (content): Merge conflict in X`
renders as `KONFLIKT (Inhalt): Merge-Konflikt in X`. The parser therefore:

- emits **duplicate** findings for one file (the plain path, the localized auto-merge
  line, and the localized conflict line each counted separately), and
- emits **false-positive** conflict findings for files that only produced an
  informational auto-merge line with no matching conflict marker.

## Observed impact

Plan `sweep-preambles-shipped-accessors`, Step 3d baseline reconciliation: **8 conflict
findings emitted for what were actually 2 real content conflicts**. The inflated count
drove a full `baseline_drift` recovery cycle (phase-5-execute aborted at its entry gate,
phase-2-refine re-dispatched) that a correct count would still have triggered — but the
six spurious findings all had to be individually diagnosed and resolved by hand before
refine could proceed.

The failure is silent and locale-dependent: on an English-locale machine the same tree
reconciles cleanly, so this does not reproduce in CI.

## Directive

Fix the parser in
`marketplace/bundles/plan-marshall/skills/workflow-integration-git/scripts/baseline-reconcile.py`:

- Force `LC_ALL=C` / `LANG=C` on the `git merge-tree` subprocess so its output is
  locale-independent, **and**
- Match only on the locale-independent `CONFLICT` marker rather than on any line that
  names a file.

Prefer parsing `git merge-tree`'s machine-readable output over its human-facing text —
that removes the dependency on message wording entirely rather than pinning a locale.

Add a regression test that feeds the parser localized (non-English) `merge-tree` output
and asserts the conflict count matches the real marker count, not the line count.

## Why this matters beyond the one bug

A conflict count is a **gate input**: it decides whether drift is self-absorbed or
escalated into a refine re-cycle. An over-count is not a cosmetic reporting error — it
routes the orchestrator down the expensive branch and presents work that does not exist
as work that must be reconciled. Any parser whose output feeds a gate should read a
machine-readable form or pin the locale, never scrape localized prose.
