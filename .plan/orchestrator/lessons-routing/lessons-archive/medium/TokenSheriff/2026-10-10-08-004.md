# Run a new integration test before push; a status-only health assertion hid unregistered checks

## What happened

Two separate defects met in one CI failure.

**1. A new integration test was pushed without ever being run.** `WellKnownRetryConfigSpecIT` (TASK-19) was only compiled locally. The task log says so: `verify -pl token-sheriff-quarkus-integration-tests -am` "compiles the integration-test sources; the integration tests themselves need the native image and compose stack and are not executed locally". Its first execution was the first CI run of PR #795 (run 37997213117), where it failed. That cost a loop-back from finalize to execute and one more full CI cycle.

**2. The failure exposed a production defect that an existing test should have caught.** The Quarkus extension never registered `JwksEndpointHealthCheck` and `TokenValidatorHealthCheck` in a consuming application: the runtime jar has no bean-archive marker and `TokenSheriffProcessor.additionalBeans()` listed neither class. `/q/health/ready` answered `{"status":"UP","checks":[]}` whatever the JWKS state. The defect was already on `main`. `HealthCheckIntegrationIT` did not catch it because it asserted only the status `UP`, which an empty check list also produces.

The production fix (c380b117) shipped in the same PR by operator decision (decision log 2026-10-10T06:22:20Z), with a build-step test that pins the registration.

## Rules

- **A new test is not done until it has run once and been seen to pass and to fail.** For an integration test that needs the native image and the compose stack, either run the integration-test profile locally before push, or state in the task result and the PR that the test is unexecuted and that the first CI run is its first run. Do not report such a task as verified.
- **A JVM-mode reproduction is an acceptable local substitute** when the native build is too slow. It was what confirmed the health-check defect here.
- **Never assert only an aggregate status.** A health test must assert that the named checks are present (`jwks-endpoints`, `jwt-validator`) and then their state. `UP` over an empty list is a pass for the wrong reason. The same holds for any "no errors" or "count >= 0" style assertion.
- **A new bean in the Quarkus runtime module needs an explicit registration** in `TokenSheriffProcessor` and a build-step test for it, because the runtime jar is not a bean archive.
