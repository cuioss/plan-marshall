# Dispatched execution-context leaves have Grep/Glob revoked at harness runtime despite being declared, and no project surface can widen the grant

## Constraint

A dispatched `execution-context` leaf does **not** receive the `Grep` and `Glob` tools at runtime, even though the agent definition declares them and no project surface denies them. The revocation happens at harness level, above every configuration surface this repository owns.

Verified at HEAD:

- `marketplace/bundles/plan-marshall/agents/execution-context.md` frontmatter declares `tools: Read, Write, Edit, Glob, Grep, Bash, Skill`. The grant is already asked for.
- `.claude/settings.json` `permissions.deny` is `[]`. Nothing project-side withholds it.
- Observed live in five separate dispatches across one plan run (phase-2-refine, phase-3-outline, q-gate-validation, phase-5-execute, and a follow-up doc dispatch). One leaf received the harness message verbatim: *"Grep is not available in this session — search file contents with grep via the Bash tool instead"* — advice that the project's own R2 enforcement hook denies.

## Why it matters

This produces a **permission asymmetry**: the "No shell file operations" hard rule prescribes the `Grep` tool as its own remedy for content search, but a dispatched leaf has that permission withdrawn while the prohibition on bare `grep` via Bash stays fully enforced. Permission withdrawn, prohibition retained.

The consequence is a truthfulness defect, not merely an ergonomic one. A leaf asked for a broad content sweep and left with no reachable primitive completes by improvisation or silently degrades to a sample, then reports coverage. The caveat — *the sweep was a sample, not an enumeration* — is invisible at the return site. This is the **volume-read-as-coverage** archetype with a tooling root cause rather than a reporting one: the leaf could not have enumerated even if it intended to.

## Do not attempt this repair

"Grant `Grep` to `execution-context` leaves" is **not an available repair from this repository**. It names a state the repo is already in. Editing the agent frontmatter to add `Grep` is a no-op — it is already there. Adding an allow entry to `.claude/settings.json` does not restore a harness-revoked subagent grant. Any plan proposing this as a deliverable should be re-scoped before implementation, not after.

## Working remedy

`architecture search --content --pattern P` is the sanctioned broad-content-sweep primitive under the revocation. It is a script seam reached through the executor, so it is available to a dispatched leaf regardless of the harness tool grant. See `plan-marshall:manage-architecture/standards/client-api.md` § search for the response contract.

Do **not** fault `architecture find` for this. It is a path glob over the files inventory, working exactly as designed, and the "Structured queries first" rule is scoped to navigation. Criticising it for not doing content matching is criticising a tool for not being a different tool — `search --content` is that different tool.
