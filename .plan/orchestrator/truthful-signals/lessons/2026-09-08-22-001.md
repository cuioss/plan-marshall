# The finalize commit seam's stage-specific-files rule is prose, not a mechanical allowlist (CWE-200)

## Problem

The phase-6-finalize dispatcher's item-5f commit instrumentation commits a `mutates_source: true` step's output by loading `workflow-integration-git`'s **Commit Changes** workflow. That workflow's Step 5 says:

> Stage specific files relevant to the logical change (use `git -C {worktree_path} status --porcelain` to review)

That is **prose an LLM follows, not an allowlist a script enforces**. `git-workflow.py` exposes no verb that constrains what may be staged, so nothing mechanically prevents an unrelated — or sensitive — path from entering a finalize-owned commit. An untracked `.env` sitting in the worktree is committable by this path.

The porcelain sweep item 5f performs is whole-tree and carries no path filter, so the set offered to that staging decision is the entire dirty tree, not the step's own output.

Raised by CodeRabbit against PR #1454 as a Major finding, classified CWE-200, at `marketplace/bundles/plan-marshall/skills/workflow-integration-git/scripts/git-workflow.py`.

## Scope of the exposure — stated precisely, because it is narrower than it first reads

The gap is **pre-existing and shared**, not introduced by any single step's declaration. Every `mutates_source: true` settle-band step already routes through this same seam.

In particular, `default:finalize-step-sync-baseline` (order 3) declares `mutates_source: true` and is `lane.class: core` — it resolves at the `minimal` tier, is never predicate-pruned, and a weakening `off` override is ignored, so an operator cannot switch it off. It fires item-5f **unconditionally and first**, in every reachable manifest. Any untracked or unrelated tracked file present at finalize entry is therefore already reachable by the order-3 commit, before any later step runs.

This is why the finding was ACCEPTED rather than fixed on PR #1454 (which flipped `default:pre-push-quality-gate` to `mutates_source: true`): that flip adds a member to an existing set and opens no new window. **The gap itself is real and unfixed** — the accept was about attribution, not about severity.

## Why it matters

Two properties make this worth closing rather than tolerating:

1. **The safeguard is the least reliable kind.** It is an instruction in a workflow document, executed by an LLM, at the moment a commit is being cut — the point where a wrong call is hardest to notice and most durable, because the result is pushed.
2. **The blast radius is every mutating finalize step, on every plan.** A single enforcement point would cover all of them; today each firing re-decides the question from prose.

## Directive

Give the seam a mechanical staging boundary. Sketch, to be settled on the merits rather than adopted as written:

1. **Add an explicit allowlist parameter to the Commit Changes flow** — the caller (item 5f) passes the paths the step is entitled to commit, and `git-workflow.py` stages exactly those, refusing anything outside. Item 5f would need a source for that set; the step's own declared footprint is the obvious candidate.
2. **Failing that, add a denylist floor** that refuses to stage untracked files matching a secrets-shaped pattern set (`.env*`, `*.pem`, `id_rsa*`, credential filenames) regardless of caller, and reports the refusal loudly rather than silently dropping them.
3. **At minimum, make the whole-tree sweep's breadth visible at the commit site** — item 5f currently commits what it finds with no record of what it considered, so a swept-in file leaves no trace distinguishing it from a step-owned one.

Whichever is chosen, add a regression test that places an untracked secrets-shaped file in a throwaway worktree, runs the instrumentation path, and asserts the file is NOT in the resulting commit.
