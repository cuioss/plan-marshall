# A short-circuit/bypass branch must be documented BEFORE the dispatch it bypasses, not after; spec ordering let a classifier failure override the never-rebase needs_user path

## Context

The plan `finalize-early-baseline-rebase` (PR #786) added a new built-in finalize
step `default:finalize-step-sync-baseline` (order 3) that rebases the worktree
feature branch onto `origin/{base_branch}` at the start of phase-6-finalize, so the
downstream local quality gates and CI validate the actual to-be-landed tree. The
deliverable was a standards doc
(`phase-6-finalize/standards/finalize-step-sync-baseline.md`) plus wiring rows in
`SKILL.md` / `required-steps.md` and unit tests — no new git primitives.

The step has an `auto_rebase_threshold` conflict-gate knob whose `never` value is
documented to short-circuit the rebase to `decision = needs_user` (escalate to the
user) without running the overlap classifier at all.

## Signature

A CodeRabbit inline comment on PR #786 (finding `b9c017`,
`finalize-step-sync-baseline.md:75`, 🟠 Major, Functional Correctness) caught a
control-flow ordering defect in the standards-doc spec, caught-and-fixed in-run
(slipped, then caught — the highest-value lesson class):

> The spec currently says to run `baseline-reconcile`, then later says `never`
> should skip the classifier entirely. That changes behavior: a broken classifier
> would error out instead of taking the documented `needs_user` path. Move the
> bypass ahead of the classify step so the contract is unambiguous.

The doc prescribed the steps in the order: dispatch `baseline-reconcile` (the
overlap classifier) FIRST, then later branch on `threshold == never`. Because the
`never` bypass was written downstream of the classifier dispatch it was meant to
bypass, a classifier failure (`baseline-reconcile` erroring) would surface as a hard
error on the very path (`never` → `needs_user`) that exists precisely to NOT depend
on the classifier. The fix moved the `threshold == never → decision = needs_user`
short-circuit (logged via `manage-logging decision`, no `baseline-reconcile`
dispatch) AHEAD of the classify step, so the `never` contract is honored regardless
of classifier health.

## Root cause

A bypass / short-circuit branch was placed in the documented step sequence AFTER the
operation it is supposed to bypass. Reading top-to-bottom the prose looked correct —
"run the classifier, then handle the threshold cases" — but the `never` case is by
definition the case that must NOT run the classifier. Putting the guard after the
guarded operation makes the guarded operation's failure mode leak into the path the
guard was meant to protect. This is a spec-level ordering defect: the document is the
executable contract, and the contract said "do X, then decide whether X should have
happened."

This is distinct from the two adjacent finalize lesson families:

- It is NOT `2026-06-22-11-001` (doc-prose semantic accuracy — a knob description
  used a looser verb than the code enforces). Here every individual statement is
  accurate; the defect is the ORDER of two correct statements.
- It is NOT `2026-06-24-14-003` (code-test coverage gaps — a missing tie-break /
  filter predicate the structural gate can't see). Here there is no code-under-test
  whose negative case was unprobed; the defect lives entirely in the prescribed
  step ordering of a standards doc.

Every in-house gate passed clean (plugin-doctor quality-gate, pre-submission
self-review, CI all green) because none of those gates reasons about whether a
documented short-circuit is positioned before or after the operation it guards.
Only the adversarial PR bot, reading the spec as an executable contract, caught that
the `never` bypass was unreachable-before-the-dispatch-it-bypasses.

## How to apply

- **Place every bypass / short-circuit / guard clause BEFORE the operation it
  guards.** When a value (`threshold == never`, `mode == dry_run`, `enabled ==
  false`, `count == 0`) is documented to skip a dispatch / build / external call,
  put the skip branch ahead of that dispatch in the step sequence — never "do the
  thing, then decide whether the thing should have run." The guard's entire purpose
  is to NOT depend on the guarded operation, including its failure modes.

- **Read a standards/workflow doc as an executable contract, in order.** A finalize
  step's prose IS its behavior. When a doc enumerates a special-case value whose
  semantics are "skip step N", verify that the special-case branch is written
  upstream of step N. A correct-sentence-but-wrong-order spec passes every structural
  gate and only an adversarial reader catches the unreachable / order-dependent
  guard.

- **When the bypass exists to insulate from a dependency's failure, make the
  insulation structural, not positional-by-accident.** State explicitly in the doc
  that the `never` path does NOT dispatch the classifier (here:
  `baseline-reconcile`) and logs the decision directly — so a later editor cannot
  re-introduce the ordering bug by "tidying" the two branches together.

## Impact

Caught and fixed in-run before merge, so nothing shipped. Had it shipped, an operator
who set `auto_rebase_threshold: never` to force a manual-rebase escalation would have
seen a hard classifier error instead of the documented `needs_user` prompt whenever
`baseline-reconcile` hit any internal failure — the exact opposite of the
fail-to-the-user guarantee the `never` setting is supposed to provide.
