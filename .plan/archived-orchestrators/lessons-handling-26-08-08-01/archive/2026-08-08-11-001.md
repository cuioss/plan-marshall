# assert_test_identifiers reports every PARAMETRIZED test as missing when the caller supplies the documented bare-function nodeid, so a compliant module_testing task is spuriously blocked

## Observed

During phase-5-execute of `absent-names-two-states-with-opposite-remedies` (TASK-003, `module_testing`
profile), the mandated diff-assertion sub-step returned `passed: false` with `found_count: 8`,
`missing_count: 4` against a module-test run that was **fully green (15031 passed, 0 failed)**.

The four "missing" identifiers were *exactly* the four parametrized test functions:

```
test_unchanged_comment_reports_stale_participation_on_a_later_fetch
test_updated_at_movement_credits_participation_and_reports_no_stale
test_a_fresh_comment_outranks_a_stale_one_through_the_subtraction
test_a_refusal_outranks_stale_participation
```

Every one of them had genuinely run. Re-running the same assertion with the parameter suffix
appended (`...on_a_later_fetch[pr-agent]`, `...outranks_stale_participation[coderabbit]`, etc.)
returned `passed: true`, `found_count: 14`, `missing_count: 0`.

## Root cause

`assert_test_identifiers.py` matches each identifier with a boundary-anchored regex:

```python
pattern = re.compile(rf'{re.escape(identifier)}(?:\s|$)')
```

pytest writes a parametrized case as `nodeid[param]` — the `[` follows the function name with **no
intervening whitespace**. So for a parametrized test the anchor can never be satisfied by the bare
function name: the character after the name is `[`, which is neither `\s` nor end-of-line.

The anchor itself is deliberate and correct — its docstring explains it prevents `test_login`
false-matching `test_login_failure`. The defect is the *interaction* between that anchor and the
**documented caller contract**, which tells the caller to supply `{rel_path}::{test_function}`
(`execute-task/SKILL.md` § Profile: module_testing → "Collect pytest nodeids for every newly-written
test file: `{rel_path}::{test_function}`"). A caller following that contract literally gets a false
negative for every parametrized test it wrote.

## Why it matters

This is a **false negative in a guardrail whose entire purpose is to catch a false positive** — the
silently-skipped test. The workflow's `passed: false` branch is not advisory:

> On `passed: false`: do NOT mark the task `done` — the run was silently incomplete. Log, mark the
> task `requires_attention`, and surface the mismatch in the return value.

So a `module_testing` task that authors parametrized tests — the project's *preferred* shape, since
population-derived `@pytest.mark.parametrize` sweeps are mandated by
`persona-module-tester` ("Every set-guarding detector must be population-derived") — is spuriously
driven to `requires_attention` on a green suite. The two standards pull against each other: the
testing standard pushes toward parametrization, and this guardrail punishes it.

The failure mode is also **silently self-concealing in the other direction**: a caller who notices
the mismatch and "fixes" it by dropping the parametrized entries from the identifiers file restores
`passed: true` while removing exactly the tests most worth asserting.

## Remedy

Fix at the tool layer (the project owns this helper), not by asking callers to hand-append suffixes:

1. **Match a parametrized nodeid** — widen the anchor to accept `[` as a terminator alongside
   whitespace/EOL, e.g. `rf'{re.escape(identifier)}(?:\[|\s|$)'`. This keeps the
   `test_login` / `test_login_failure` prefix-collision guard (an `_` still fails the anchor) while
   admitting `name[param]`. Add a positive/negative control pair: a parametrized identifier must
   match, and a prefix-colliding name must still NOT match.
2. **Then state it in the contract** — record in `execute-task/SKILL.md` that the bare
   `{rel_path}::{test_function}` form covers all of a function's parametrized cases, so callers never
   need to enumerate parameter values (which they cannot always predict, since the population is
   registry-derived at import time).

Until (1) lands, a `module_testing` task that wrote parametrized tests MUST verify a `passed: false`
result against the log's real nodeids before treating it as a genuine gap — a bare-name mismatch on
a green suite is this artifact, not a skipped test.
