# plugin-doctor static analyzers over-approximate when their model omits a runtime dispatch mechanism (askuserquestion dispatched-leaf and manage-invocation router-level verbs) — allowlist the mechanism but keep validating the rest

## Context

Discovered during plan-6-prompt-reachability (D4). The plan intended to flip the
`askuserquestion-in-dispatched-workflow` plugin-doctor rule from advisory to gating,
on the premise that D1/D2 had closed the last unreachable in-leaf `AskUserQuestion`
call sites. Flipping the rule and running a whole-tree quality-gate surfaced **8
findings** in files that are NOT dispatched leaves.

## Defect

The analyzer's dispatched-leaf discriminator classifies a workflow/skill doc as a
"dispatched leaf" when it carries `implements: ext-point-execution-context-workflow`
in frontmatter AND contains no `Task:` directive. That over-approximates: a
main-context orchestrator workflow that is loaded via `Skill:` (not dispatched) and
that itself performs no further dispatch also matches both conditions, so its
legitimate main-context `AskUserQuestion` calls are flagged as unreachable.

Confirmed false positives (all legitimate main-context prompt sites):
- `plan-marshall/workflow/planning-lessons-aggregate.md:43`
- `plan-marshall/workflow/recipe.md:36` (the recipe action's orchestrator workflow — runs phase-1-init inline, no Task: dispatch)
- `plan-retrospective/SKILL.md:305`
- `recipe-refactor-to-profile-standards/workflow/selection-flow.md:92,166`
- `pm-documents/ref-asciidoc/workflow/link-verification.md:138,244`
- `pm-plugin-development/plugin-doctor/SKILL.md:147`

`planning.md` / `execution.md` escape the flag only incidentally — they happen to
contain `Task:` dispatches, so the discriminator excludes them. That is luck, not
soundness: a main-context workflow with no downstream dispatch is indistinguishable
from a true dispatched leaf under the current signal set.

## Directive

Before the reachability rule can gate the build (the dropped D4 goal), the analyzer
needs a SOUND way to distinguish a genuinely-dispatched leaf from a main-context
`Skill:`-loaded workflow. Two candidate directions:

1. **Declarative opt-out (cheaper):** a positive frontmatter marker (or the existing
   plugin-doctor declarative suppression, PR #680) applied to the legitimate
   main-context sites, so the rule skips them; then flip to gating.
2. **Sound discriminator (proper):** replace the `implements: + no Task:` heuristic
   with a positive signal that only a truly-dispatched workflow carries (e.g. an
   explicit `execution_context: leaf|orchestrator` frontmatter key, or cross-file
   analysis of which docs are named as the `workflow:` target of a `Task:` dispatch).

Until one lands, the `askuserquestion-in-dispatched-workflow` rule MUST stay
advisory (analyze-only) — gating it as-is fails the build on legitimate prompts.

## Recurrence — 2026-07-15 (plan-8-context-trim)

Second occurrence of the same defect class in a different plugin-doctor analyzer,
confirming this is a recurring pattern rather than a one-off. The
`manage-invocation-invalid` analyzer flagged legitimate docs as invalid because its
model of the argparse surface was **incomplete**: it did not model **router-level
verbs** — verbs that `main()` intercepts and dispatches BEFORE argparse subcommand
parsing (e.g. `ci barrier`). Those verbs never appear in the script's argparse
`choices`, so the analyzer concluded the documented invocation was invalid, when in
fact the verb is real and handled upstream of argparse.

Fix mirrored the D4 remedy: teach the analyzer about the missing dispatch mechanism
via an allowlist (`_ROUTER_VERBS`), later hardened (TASK-023) so the allowlisted
router verbs still have their FLAGS validated (an allowlist that skips a verb
entirely would blind the analyzer to genuine flag errors on those verbs).

**Generalized directive (broadens this lesson's scope from the askuserquestion rule
to all plugin-doctor static analyzers):** a plugin-doctor analyzer that models a
runtime dispatch/argparse surface MUST account for EVERY dispatch mechanism the
runtime supports — main-context `Skill:` loading vs `Task:` dispatch (D4), and
router-level verb interception ahead of argparse (this recurrence). An analyzer whose
static model omits a real mechanism emits false-positive "invalid"/"unreachable"
findings on valid constructs. When teaching the analyzer via an allowlist, keep
validating the allowlisted entries' remaining surface (flags, args) — allowlist the
DISPATCH mechanism, not the entire construct, or the analyzer goes blind to real
defects on those entries.

## Recurrence — 2026-07-18 (plan-server-core)

Third occurrence of the same over-approximation class, this time in the
**naming-heuristic** discriminator rather than a dispatch/argparse model. The
build-extension analyzer classifies a skill as a build-SYSTEM extension by matching
`skill_name.startswith('build-')` and then applies the EC-01/EC-40 build-system
contract checks. The new `build-server-client` skill (part of the `marshalld`
build-server surface) matched the prefix but is NOT a build-system implementer, so
it drew false EC-01/EC-40 contract findings. Fix mirrored the D4/router-verb remedy:
narrow the model by excluding the `build-server` namespace from the `build-` prefix
match, keeping the contract checks active for genuine build-system extensions.

**Convention captured:** the `build-` prefix names build-SYSTEM extensions only
(`build-maven`, `build-npm`, `build-pyproject`, `build-gradle`); adjacent
`build-server*` skills are the daemon/client surface and are NOT build-system
implementers. Any analyzer keying off the `build-` prefix must exclude the
`build-server` namespace. This is the same failure signature as the two prior
recurrences: a static discriminator (here a name prefix, previously a dispatch/argparse
model) over-approximates its target set; the fix narrows the model to exclude the
legitimate non-member while keeping the real checks live for true members.
