# baseline-reconcile --no-emit leaves a merge commit on the feature branch instead of aborting its probe

## Observed

During phase-6-finalize branch-cleanup for plan `build-decision-oracle-consolidation`
(PR #985), the pre-merge classifier call

```bash
python3 .plan/execute-script.py plan-marshall:workflow-integration-git:git-workflow \
  baseline-reconcile --plan-id build-decision-oracle-consolidation --no-emit
```

returned `classification: overlap_no_content_conflict`, `auto_reconciled: true`,
`merge_commit_sha: 6ca356fb0ea910ba9766f1ff8fff914dee520d92`.

That `merge_commit_sha` was not a probe artifact confined to the object store — it
was left as the feature branch's HEAD. `git worktree list` showed the plan's
worktree at `6ca356fb0`, and `git log --oneline` confirmed:

```text
6ca356fb0 Merge remote-tracking branch 'origin/main' into feature/build-decision-oracle-consolidation
058a880c6 fix(script-shared,pm-dev-java-cui): relocate marker detector ... (#986)
e9aeebc7d fix(plan-marshall): resolve CodeRabbit PR #985 review findings
```

The real branch HEAD was `e9aeebc7d`. The probe advanced it by a merge commit.

## Why this is a defect

`branch-cleanup.md` § Constraints states the classifier's safety property
explicitly:

> `baseline-reconcile --no-emit` is idempotent, performs only `fetch + diff +
> merge-tree` (with an internal `git merge` probe that is **always aborted before
> any working-tree mutation persists** — see the `auto_reconciled: false` downgrade
> path inside the script)

The abort evidently does not fire on the `auto_reconciled: true` path: when the
probe merge SUCCEEDS, the resulting commit is retained rather than reset away. The
documented invariant only holds for the failure path.

A classifier that mutates the branch it is classifying is the sharpest possible
violation of the read-only-probe contract, and it is silent — the returned TOON
looks like a normal successful classification.

## Blast radius

The stray merge commit would have been force-pushed to the PR by the very next
step in branch-cleanup (`force-push-with-lease` before the merge). The PR would
then have landed a merge commit into a squash-merge repository, and the merge would
have been performed with no verification run against the merged tree, because the
flow expects to rebase-then-verify, not to arrive already-merged.

This defect is masked whenever the classifier returns `no_overlap` (no probe merge
is attempted at all), which is the common case. It surfaces only on the
`overlap_no_content_conflict` + `auto_reconciled: true` path — i.e. exactly when
another plan has landed on a shared file, which is also when a semantic conflict is
most likely.

## Directive

- Make the `git merge` probe restore the pre-probe HEAD on the SUCCESS path too,
  not only on the `auto_reconciled: false` downgrade path — an unconditional
  `finally`-shaped guard, not a branch-local abort.
- Add a regression that runs `baseline-reconcile --no-emit` over a fixture whose
  upstream and feature branches overlap without a content conflict, and asserts
  `git rev-parse HEAD` is unchanged before and after the call. A test that only
  asserts the returned `classification` cannot catch this.
- Consider whether `merge_commit_sha` should be returned at all on a `--no-emit`
  probe. A caller has no legitimate use for a SHA that is supposed to have been
  discarded, and returning it invites exactly the "the probe left it for me"
  misreading.

## Detection in the wild

Cheap check for any caller: capture `git rev-parse HEAD` before and after the
classifier call and compare. In this incident the divergence was caught only
incidentally, by reading a `git worktree list` run for an unrelated purpose.
