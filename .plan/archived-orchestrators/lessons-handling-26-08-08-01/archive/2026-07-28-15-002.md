# derive-verification's compile/test-compile build_class breaks manifest compose (unresolvable_step verify:compile)

## Context

Plan `unchecked-finding-persist-loses-the-finding`, phase-4-plan, Step 6
"Verification" stamp. Following the SKILL.md's documented procedure literally
- call `architecture derive-verification --changed-artifacts {steps[].target
comma-joined}` and write each returned row's `executable` into the task's
`verification.commands` - produced a task whose sole changed artifacts were
production `.py` files with no paired test-file changes in the same task
(the 1:N implementation/module_testing split routinely produces exactly this
shape). The deriver correctly classified the changed set and returned a
`build_class: compile` row (`pyproject_build run --command-args "compile
plan-marshall"`), which is a legitimate, distinct build_class from
`module-tests`.

Stamping that `compile` command into the task and then running
`manage-execution-manifest compose` failed:

```
status: error
error: unresolvable_step
message: "phase_5 step `verify:compile` in marshal.json is unresolvable: step
`verify:compile` names an unknown canonical `compile` - no
ext-point-build-verify-step implementor (nor the composer canonical->role
table) declares it"
```

Per `manage-execution-manifest/standards/decision-rules.md` § "execution_tier
Routing", the composer's canonical fast-path only recognizes three declared
canonicals - `quality-gate -> verify:quality-gate`, `verify`/`module-tests ->
verify:module-tests`, `coverage -> verify:coverage` - and generalizes every
OTHER parseable verb to a bare `verify:{verb}` step. That bare `verify:compile`
/ `verify:test-compile` step is then never resolvable against the
`ext-point-build-verify-step` implementor table, because no implementor
declares `compile` or `test-compile` as a holistic canonical-verify role -
those two build_classes exist only as `architecture resolve --command compile
/ test-compile` per-module commands, not as phase-5 canonical-verify steps.
The routing pass only reaches this failure when the resolved command's
`execution_tier` is `orchestrator` (i.e. its `bash_timeout_seconds` exceeds
the 600s Bash ceiling) - for `plan-marshall`, EVERY build command (`compile`,
`test-compile`, `module-tests`) currently resolves to the same 630s timeout
and `execution_tier: orchestrator`, so any task whose changed set derives
`compile` or `test-compile` alone (rather than `module-tests`) trips this
unconditionally.

## Resolution

Removed all 5 tasks (`manage-tasks remove`) and re-composed the batch using
the deliverable-authored, uniform "module-tests plan-marshall" verification
command for every task (all five deliverables' `solution_outline.md`
Verification blocks already specified this one command verbatim) instead of
per-task-derived `compile` / `test-compile` commands. `module-tests` is one
of the three declared canonicals, so it routes cleanly through
`execution_tier Routing` to `verify:module-tests`, and `manage-execution-
manifest compose` + `validate` both succeeded afterward.

## Recommendation (not applied - outside phase-4-plan's mutate scope)

The `derive-verification` deriver and the manifest's canonical-verify role
table are out of sync: the deriver can legitimately emit `compile` /
`test-compile` build_class rows for narrowly-scoped tasks (production-only
or test-only changed sets), but the composer's `execution_tier` routing has
no declared canonical for either. Either (a) the deriver should collapse
`compile`/`test-compile` into `module-tests` when the resolved
`execution_tier` is `orchestrator` (since the holistic `module-tests` command
already subsumes both), or (b) the composer's canonical fast-path / the
`ext-point-build-verify-step` implementor table should register `compile`
and `test-compile` as additional recognized canonicals. Until one of those
lands, future phase-4-plan runs on this project should prefer the
deliverable's own verbatim Verification command over the per-task
`derive-verification` output whenever the changed-artifact set is
production-only or test-only (i.e., does not include both a production file
and its paired test file), to avoid re-hitting this `unresolvable_step`
failure.
