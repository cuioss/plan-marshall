# Deliverable file-type bucket declared from narrative intent instead of derived from Affected files drops a required profile and can skip the very build that validates the change

Two of three deliverables in one outline declared a file-type bucket that contradicted their own
`Affected files` list. The bucket had been chosen from what the deliverable was *about*, not
derived by running the File-type classifier over the files it actually writes.

## What happened

Both misdeclarations were caught by the 3-outline Q-Gate, both on the same file:

**Deliverable 1 — declared `documentation_only`.** Affected files were
`.github/workflows/python-verify.yml` (read), **`pyproject.toml` (write-replace)**, and
`doc/developer/build.adoc` (write-replace). The classifier assigns the documentation role only
to `.md` / `.adoc` / `.asciidoc`; `pyproject.toml` is a non-documentation write target, so the
correct bucket was `mixed_with_docs`.

**Deliverable 2 — declared `test_only`, profiles = `module_testing` only.** Affected files were
**`pyproject.toml` (write-replace)** and `test/conftest.py` (write-replace). `pyproject.toml` is
not a test path, so the classifier resolves `mixed_code`, whose normative profile pair is
`implementation` **and** `module_testing`.

## Why it is not cosmetic

Each misdeclaration had a concrete downstream consequence, and they are different consequences:

- **Deliverable 1 — the gate that must validate the change gets skipped.** `documentation_only`
  normatively means implementation-only and never `module_testing`, applied to a deliverable
  that mutates the *interpreter declaration file*. Worse, `.github/workflows/python-verify.yml`
  sets `skip-on-docs-only: true`, so a docs-only-shaped footprint skips the heavy pyprojectx
  build — precisely the build that has to prove the interpreter change works. A green
  `verify / conclusion` would have been vacuous.
- **Deliverable 2 — a substantive edit has no task to carry it.** phase-4-plan creates one task
  per declared profile. With `module_testing` as the only profile, the production edit (lifting
  the pytest / pytest-xdist specifiers and deleting the two cap-rationale comment blocks in
  `pyproject.toml`) had no implementation task at all.

## Root cause

The bucket was asserted as a *summary of intent* ("this deliverable is about documentation",
"this deliverable is about tests") rather than **computed from the Affected-files set**. A single
non-matching write target is enough to move the bucket, and the narrative framing hides it
because the file is a one-line edit inside a deliverable that is mostly prose or mostly tests.

`pyproject.toml` is the repeat offender: it is small, it reads like configuration, and it appears
as a supporting edit in deliverables whose headline work is elsewhere — while being the highest-
consequence write target in the tree.

## Rule

- Derive the bucket **mechanically from the `Affected files` write set**, then check the narrative
  against it — never the reverse. Every write-target path gets classified; the bucket is the join.
- Any deliverable with a **write** entry outside `*.md` / `*.adoc` / `*.asciidoc` cannot be
  `documentation_only`. Any deliverable with a write entry outside `test/**` cannot be `test_only`.
- Reconcile the `Profiles` list with the classifier table row for the resolved bucket in the same
  edit — a re-bucket that leaves the old profile list behind reintroduces the missing-task defect.
- Record a bucket-rationale bullet naming the consequence the bucket controls (which gates run,
  which profiles get tasks), so a later reader can tell the bucket was derived and not guessed.
- Treat `pyproject.toml`, `marshal.json`, and workflow YAML appearing anywhere in a write set as a
  hard stop on any `documentation_only` / `test_only` declaration.

## Impact

Both were caught at Q-Gate, so the cost was two re-authoring rounds rather than a broken build.
Had either shipped, the plan would have merged an interpreter change validated by a skipped build,
or lost a production edit entirely.

## Recurrence — 2026-07-22 (marker-detector-ownership-and-fixture) — same failure on the `module` field

Same day, same root cause, a DIFFERENT deliverable-metadata field: `module`.

In plan `marker-detector-ownership-and-fixture` (PR #986), deliverable D3 declared
`module: pm-dev-java-cui` because the deliverable was *about* establishing the marker
detector in that bundle. Roughly **35 of its ~45 Affected files resolved to module
`plan-marshall`** — the manage-config argparse widening, the extension-api describe-side
sweep, the script-shared retirement, and the build-maven / build-gradle subcommand
removal. The 3-outline Q-Gate caught it (finding `13d006`), verifying both sides with
`architecture which-module`.

**Why it is not cosmetic.** A deliverable carries exactly one `module`, and phase-4-plan
consumes it verbatim as `architecture module --module` while the phase-4 module-mapping
validator cross-checks each `module_testing` task's test module against its sibling
implementation task's module. A two-module file set is therefore *not representable* in
one deliverable: the declaration would have mis-routed task placement and then tripped
the validator one phase later. Resolving it required splitting the deliverable along the
module boundary — D3 (`pm-dev-java-cui`, 10 files) and D4 (`plan-marshall`, 39 files) —
which turned 3 deliverables into 4 and forced re-scoping of both `Module_testing` blocks,
a new `depends_on` edge, and 36 additional per-file assessments.

**What this adds to the rule.** The existing rule tells the author to derive the
*file-type bucket* mechanically from the Affected-files write set. Generalize it: **every
deliverable metadata field that phase-4 consumes must be DERIVED from the Affected-files
set, not summarized from intent.** For `module` specifically:

- Run `architecture which-module --path P` over every Affected file and take the set of
  results. If its cardinality is greater than 1, the deliverable is not representable and
  MUST be split along the module boundary — there is no "primary module" escape hatch.
- Record the derivation, not the conclusion: the module claim should cite the
  which-module result, the same way the bucket claim should cite the classifier result.
- This check is fully deterministic and belongs at authoring time. It currently runs
  nowhere — it was found by LLM reasoning at Q-Gate, one phase before the validator that
  would have caught it mechanically and much more expensively.

The `module` field shares the file-type bucket's tell: the narrative framing ("this
deliverable is about bundle X") hides a file set whose majority lives elsewhere, and the
misdeclaration is invisible unless someone actually classifies the paths.
