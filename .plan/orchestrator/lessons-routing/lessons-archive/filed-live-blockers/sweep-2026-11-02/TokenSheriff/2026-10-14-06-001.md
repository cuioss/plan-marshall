# A new client setting must reach every doc surface and keep raw values out of rejection messages

## What happened

Plan issue-800 added the `backChannelOrigin` setting to `token-sheriff-client` (requirement CLIENT-24) and mapped it in the Quarkus client extension as `sheriff.client.back-channel-origin`. Execution was green: every task build passed and the whole-tree `verify -Ppre-commit` ran 3077 tests green.

The code review then found seven defects in two rounds. Each round cost one more execute loop and one more whole-tree build. None of the seven was a fault in the routing logic itself. They fall into three groups:

**1. A rejection message echoed the raw value (security).** The validation messages for a bad `backChannelOrigin` included the value as given. On the rejection branches that do not check for user-info, a value such as `ftp://user:pw@host` was written into the message with its credentials (finding `bfe2cb`). The security audit raised the same point. Fixed in 5617977d.

**2. Documents that list or describe settings were not updated, or contradicted the code.**
- `token-sheriff-client/README.adoc` said `allowInsecureHttp` is checked only against the contacted host, so an https back-channel origin needs no flag. `DiscoveryResolver.enforceTls` still checks the issuer scheme, so an http issuer with an https back-channel origin fails with `NON_TLS_ISSUER` (finding `0e6a98`).
- The Javadoc of `ClientConfiguration` and `quarkus-config-doc.adoc` left out the same caveat (finding `f18f75`, round 2).
- The control table for back-channel HTTP in `doc/client/architecture.adoc` did not mention the origin rewrite (finding `d63edc`).
- The traceability matrix in `doc/client/specification/test-strategy.adoc` had no CLIENT-24 row (finding `ef70f0`).
- The document map in `doc/client/README.adoc` still gave the requirement range as CLIENT-1 to CLIENT-22 (finding `9d90f3`, round 2).

**3. A documented MUST had no test.** `doc/client/requirements.adoc` states that the issuer-scheme check still applies when the back-channel origin is https. No test covered "http issuer + https back-channel origin + `allowInsecureHttp=false` fails discovery" (finding `6df400`, round 2). Fixed in 1a9c2d83.

## Rule

When a change adds or changes a setting or a requirement in the client:

- **Never put a raw configuration value into an error or log message** if it can be a URL. URLs can carry user-info (`user:password@`). Name the setting and the rule that failed; do not echo the value. Apply this to every rejection branch, not only to the branch that checks for user-info.
- **Find every interaction with existing checks before writing any document.** Here the new origin met the existing TLS check on the issuer scheme. State that interaction the same way in the README, the Javadoc, the Quarkus config doc and the architecture doc, and check the claim against the code (`DiscoveryResolver.enforceTls`) before writing it.
- **Update every list that enumerates requirements or settings in the same change:** the requirement range in `doc/client/README.adoc`, the traceability matrix in `doc/client/specification/test-strategy.adoc`, the control tables in `doc/client/architecture.adoc`, and `quarkus-config-doc.adoc`.
- **Every MUST in `requirements.adoc` needs a test that fails when the MUST is broken.** Add the test in the same task that adds the MUST.
