# Surefire reports 'Tests run: 0' for the outer class when @DisplayName + @Nested are combined — trust TEST-*.xml, not the .txt/console row

## Context

While verifying a newly added flat `@Test` in `JwtVerificationServletTest`, the module test run was green but the
per-class surefire report claimed the class had executed nothing:

```text
Test set: de.cuioss.nifi.ui.servlets.JwtVerificationServletTest
Tests run: 0, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 6.177 s
```

The console showed the same shape: the two `@Nested` rows reported counts (69, 4), while the outer
`-- in JwtVerificationServlet tests` row reported `Tests run: 0`. This looks exactly like the
"silently incomplete run" failure mode (a green suite that never executed the new test), and it consumed a
full diagnostic cycle.

## Finding

The `Tests run: 0` outer-class row is a **surefire console/`.txt` reporting artifact**, not a real gap. It appears
for test classes that combine a class-level `@DisplayName` with `@Nested` inner classes: the reporter attributes
counts to the display-name rows and leaves the outer class row at 0.

The flat `@Test` methods **do** run. `target/surefire-reports/TEST-<fqcn>.xml` is authoritative and lists each one
as `<testcase name="..." classname="<display name>">`. Two corroborating signals:

- The outer row's `Time elapsed` is large (6-10 s) despite claiming 0 tests — the work happened.
- Selecting a single flat method (`-Dtest=Class#method`) reports `Tests run: 1` and passes.

The same pattern is visible across the repo (`GatewayProxyServletTest`, `ComponentInfoServletTest`,
`Extended Tests for MultiIssuerJWTTokenAuthenticator`) — every class mixing `@DisplayName` with `@Nested`.
Classes without `@Nested` (e.g. `AttachmentsEndpointHandlerTest`) report their real count (15), which is what
makes the 0 look anomalous by comparison.

## Action

When asserting that a newly written Java test actually executed:

1. Read `target/surefire-reports/TEST-<fqcn>.xml` and confirm a `<testcase name="<method>">` entry with no nested
   `<failure>`/`<error>` child. This is the authoritative per-method record.
2. Do NOT treat the `.txt` report's or console's `Tests run:` line as the diff assertion for a class that uses
   `@Nested` — it under-reports the outer class to 0.
3. `-Dtest=Class#method` is a cheap confirmation, but it changes discovery, so it proves the method is runnable,
   not that it ran in the unfiltered suite. Use the XML for the latter.

Note: the generic `assert_test_identifiers` helper is pytest-nodeid shaped and does not apply to Maven/surefire;
the XML check above is the Java-idiomatic equivalent of that diff assertion.
