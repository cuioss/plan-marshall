# A build-server submit whose inner command carries no plan selector builds the main checkout and reports success for the wrong tree


## Observed (API-Sheriff, plan-23-session-route-scope-parity, 2026-10-01T06:36Z)

The orchestrator submitted the module-tests build for TASK-10 to the build server. Job
7b7ae13eefea498ca0baeb3fd28b43a3 returned `success` after about twelve minutes. It had built the
**main checkout**, not the plan's worktree:

- the log was written under `plans/NO_PLAN`,
- it compiled 199 main sources and none of the plan's new test classes.

Cause (decision d6bfa6): the submit passed `--project-path` for the main checkout and the inner
command carried no plan or project selector. The result was discarded as "no verdict" and the build
was resubmitted as job 2d3d20ac9f5e44edb70b5603509ba962 with `--plan-id` in the inner command, which
then ran the worktree (4053 tests).

The wrong-tree build was found only because the orchestrator read the log path and the source count.
The job status, the wait result and the work-log line were identical to those of a correct build.

## Why this matters

A green result for a tree that does not contain the change is the most expensive kind of false
positive: it would have closed TASK-10's verification without one of its tests having run.

## Directive

- The submit or wait reply should state which tree was built (project path and the tree hash), and
  the caller should compare it with the plan's worktree before it accepts the verdict.
- A submit issued for a plan that has a worktree, whose inner command resolves to the main checkout,
  should be refused or at least answered with a warning.
- Until the tool changes: always put `--plan-id {plan_id}` into the inner command of a build-server
  submit, and check that the reply's `log_file` lies under the plan's `build-results`, not under
  `plans/NO_PLAN`, before recording the result.
