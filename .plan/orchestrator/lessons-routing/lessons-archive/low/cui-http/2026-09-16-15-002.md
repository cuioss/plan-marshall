# A Sonar re-scan can return byte-identical issue keys against a stale, superseded snapshot after a verified fix

## Observation

After fix commits for a set of Sonar findings landed and were independently verified by reading the
post-fix source, a subsequent `sonar-roundtrip` re-scan returned the SAME issue keys and line
numbers. The re-scan was stale — it had analysed a superseded snapshot — but nothing in the
payload distinguishes "still present" from "analysed an older commit": key and line are identical
either way, so the output reads as confirmation of an unfixed defect. Taking it at face value would
have re-opened closed findings and driven an unnecessary loop-back against already-correct code.
Suspected cause: SonarCloud CE analysis lag behind the `sonar-build` check's report-submission step.

## Corrective

When a Sonar finding reappears after a fix for that EXACT finding has landed, do not accept the
re-scan as evidence the defect persists. Establish provenance first: read the current source at the
reported file/line and confirm the flagged construct is still there. Only treat the finding as live
when the code corroborates it — "establish provenance before re-attempting a failing fix," applied
to an external analyser's output rather than a test failure. Durable remedy: compare the analyser's
reported analysed-commit against live HEAD before triaging; treat an absent/mismatched
analysed-commit as UNKNOWN, not as a live finding.

## Scope

Any finalize-time external-analyser roundtrip (Sonar, review bots, CI annotations) that can report
against a stale revision.
