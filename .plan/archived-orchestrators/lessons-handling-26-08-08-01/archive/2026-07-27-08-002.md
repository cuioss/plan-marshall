# pre-commit-verify-freshness returns fresh off a kind=build row from a quality-gate-only run, admitting a tree whose tests never ran

## Observation

Both phase-5-execute dispatches on plan `retrospective-checker-assertion-integrity`
independently reported the same thing: the `pre-commit-verify-freshness` gate
returned `fresh`, and the entry it matched was

```
kind=build
matched_notation: plan-marshall:build-npm:js_coverage
```

produced by a **quality-gate-only run**. No test suite had executed against that
worktree state. The gate nonetheless certified the tree as verification-fresh, so
Step 12a would have admitted the 5-execute → 6-finalize transition on a tree
whose tests had never run.

The gate did nothing wrong by its own definition. It scans the change ledger for
a `kind=build`, `status=success` row whose `worktree_sha` matches the current
tree, and one existed. The defect is that the predicate it evaluates and the
claim its consumers read off it are different propositions.

## Root cause — the ledger row records that *a* build ran, not *which* build ran

A `kind=build` row is tier-blind. It carries the notation, the exit code, the
status and the worktree sha, but nothing that says which build target executed:
`quality-gate` (ruff + mypy), `module-tests`, `verify`, `coverage`, or a
scoped-vs-whole-tree variant of any of them. Every one of them writes the same
undifferentiated row.

So the gate proves exactly one thing:

> some build-class command exited 0 against this worktree sha

while every consumer of `fresh` reads it as:

> this tree has been verified — its tests pass

Those are not the same statement, and the gap between them is exactly the set of
build targets that do not run tests. A quality-gate-only run is the common case
that lands in that gap, because it is the cheap command a task profile reaches
for first.

## Why it matters

This is a false-green with the widest possible blast radius, because it sits on
the transition that hands work from execution to finalize. Everything downstream
of Step 12a — commit, push, PR creation — is predicated on the assertion that the
tree was verified, and the gate is the only thing making that assertion.

It is also silent by construction. There is no anomaly to notice: the gate
returns `fresh`, which is the expected, healthy-looking answer. Nothing in the
returned payload distinguishes "fresh because tests passed" from "fresh because
ruff passed". The only reason it was caught here is that two independent
executors happened to report the matched notation, and the notation
(`js_coverage`) was visibly wrong for the plan's footprint.

Note that this survives the fixes proposed for its two siblings. Restricting the
`kind=build` stamp to genuine build subcommands (`2026-07-22-16-003`) still
records a quality-gate `run` as a build. Excluding test-suite-authored rows
(`2026-07-26-20-002`) does not touch a production quality-gate row. The tier axis
is independent of both, and it is the axis on which the gate is wrong even when
everything else is correct.

## Directive

1. **Record the build target on the ledger row.** A `kind=build` entry must carry
   the resolved target/tier it executed (`quality-gate` | `module-tests` |
   `verify` | `coverage`) and its scope (module name, or whole-tree). Without
   that field no consumer can ever ask a tier-specific question, and every
   consumer is forced to over-read the row.

2. **Make the freshness query state the tier it requires.** The gate must ask for
   the tier that substantiates its own claim — a gate standing in for "tests
   passed" must require a row whose target actually runs tests, and must return
   `stale` (not `fresh`) when the only matching rows are of a weaker tier.

3. **Surface the matched row's tier in the gate's own return payload.** `fresh`
   with no provenance is unauditable. `fresh` accompanied by
   `matched_target: quality-gate` would have made this defect visible the first
   time anyone read the output, instead of requiring two executors to
   cross-report it.

4. **Fail closed on a tier that cannot be determined.** A row with no recorded
   target must not satisfy a tier-qualified query. Per ADR-009, an unanswerable
   question yields an explicit refusal, not the most permissive answer.

## Generalized rule

**A gate may only assert what its predicate actually tests.** When a gate's name
or its consumers' reading is stronger than the predicate it evaluates
(`a build happened` standing in for `tests passed`), the gate is vacuous for
precisely the cases it exists to catch — and its healthy-looking green is worse
than no gate at all, because it displaces the check a caller would otherwise
have performed. Whenever a gate stands in for a claim, the record it reads must
carry enough discriminating detail to substantiate that specific claim.

- `2026-07-23-01-002` (plugin-doctor) — the same vacuous-gate shape one level up:
  a gate that skips items lacking the very key it enforces.

Four active lessons now converge on the same store. The pattern across them is
not four independent bugs but one structural gap: **the `kind=build` row is an
under-specified record being asked to answer questions it does not carry the
fields to answer.** A fix that adds discriminating fields (verb class,
provenance, real outcome, target tier) closes all four; four point fixes to the
individual writers close none of the others.
