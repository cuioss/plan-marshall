# A change that adds files, moves a figure or refactors a mechanism leaves stale prose in headers, Javadoc, ADRs and sibling docs that green tests do not catch

Source: PLAN-V02-20 (#527), candidate lessons 003, 005 and 007; two outline findings, three finalize residuals and two CodeRabbit findings.

## Observation

All of these passed the build and were found only by a later review:

- A fixture header enumerated "THREE differences" between two overlays; the change added a fourth. A test's Javadoc said every key file in a directory holds PEM blocks; the new files in that directory do not. The assertions stayed green while the stated contract became false.
- The cookie budget was re-measured and the documents updated, but a comment in one overlay still carried the old figure (2700 bytes, 32.8 %).
- An ADR decision described a mechanism that a later commit in the same plan had refactored.
- Docs said a key file read is bounded at 256 bytes, while the code reads 257 to detect an oversized file; and the key-change procedure said "replace the file" for a key resolved once at boot, which needs a restart.

## Rule

- When a change adds files to a directory, or a difference between sibling fixtures, re-read every comment, header enumeration and Javadoc or DisplayName that describes that directory or difference set, and move them into the mutate set.
- After re-measuring a figure, search every tracked file for the old figure.
- After refactoring a mechanism that an ADR or doc describes, re-read that decision in the same commit.
- When documenting a size bound, state the file limit and the detect-oversize read separately. In an operator procedure for material loaded at boot, put the restart step inside the procedure.

## Apply

Any plan that changes a fixture set, a measured figure, a loader or a documented operator procedure.
