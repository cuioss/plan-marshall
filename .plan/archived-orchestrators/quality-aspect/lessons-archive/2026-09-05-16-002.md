# A down daemon silently removes cross-plan build serialization, so concurrent suites exhaust memory and the harness kills them

## Context

Plan `unreviewed-merge-gate-holes` had two full builds killed by the harness for
system memory pressure, roughly four hours apart.

**First occurrence, 2026-09-04T08:54:43Z.** A post-rebase `module-tests` run was
killed. `free -h` showed 27Gi/30Gi RAM used with swap fully exhausted (8.0Gi/8.0Gi,
88Ki free). The top consumer was a *sibling plan's* full coverage `pytest -n auto`
in the `domain-glob-seeding` worktree, 1h04m elapsed, ~3GB across its workers.

**Second occurrence, 2026-09-04T12:32:55Z.** `verify plan-marshall` was killed.
`free -h` showed 22Gi/30Gi with swap at 4.3Mi free; `ps` attributed ~6Gi to ~17
pytest workers whose argv resolved to a different plan's worktree
(`plan-145-publish-the-missing-parser-seams`, `pytest -n auto --dist=loadgroup`).

Only at the second occurrence was the root cause found one level deeper:

```text
[BUILD-SERVER] marshalld unreachable: last reachable at 2026-09-04T08:08:28Z,
unreachable since 2026-09-04T11:08:41Z, 4 builds degraded to in-process
(reason=unreachable). Further identical fallbacks are suppressed until the daemon
is reachable again.
```

Every build that session resolved `mechanism=in_process_fallback`. With no daemon
there is no build queue, so **nothing serialized builds across plans** — which is
why two full suites ran concurrently at all.

## Root cause

The daemon-down fallback is designed to keep a single plan working, and it does
that correctly. What it silently drops is a *cross-plan* property that no single
plan can observe: the queue is the only thing serializing concurrent full suites
on one machine.

The degradation is reported per build as an INFO/WARNING routing line
(`resolved=in_process, reason=unreachable`), which reads as a local routing detail.
Nothing states the consequence — that concurrency control for the whole machine is
now absent — and nothing surfaces it at the point a plan is about to submit a
memory-heavy full suite. The suppression of "further identical fallbacks" makes the
signal quieter still as the situation persists.

`plan-marshall:phase-1-init:build-server` had reported `Preflight ready (marshalld v1)`
at 20:05 the previous evening, correctly caveated as point-in-time. The daemon then
went away mid-run and no gate re-checked the *implication*, only per-build liveness.

## Proposed action

1. **Escalate the class of the message.** When a build degrades to
   `in_process_fallback`, say what was lost: "no build queue — builds are not
   serialized across plans on this machine". A routing token is not a consequence.
2. **Do not suppress the repeat for heavy builds.** Suppression is right for a
   compile; it is wrong immediately before a full `verify` / `coverage` run, which
   is exactly when the missing queue bites.
3. **Check liveness before submitting an orchestrator-tier build, not only at
   init.** `execution_tier=orchestrator` builds are the memory-heavy ones; a
   `build_server ping` at that point costs nothing and would have caught this three
   builds earlier.
4. **Consider a machine-local advisory lock as the fallback's fallback**, so
   losing the daemon degrades serialization rather than removing it.

## Impact

Two wasted full-suite runs and roughly an hour of wall time on this plan alone,
plus the analysis cost of diagnosing a killed build twice. The failure also
consumed operator attention: the second occurrence required an
`AskUserQuestion` and an explicit authorisation to start the daemon.

Both kills were correctly *not* blind-retried — provenance was established each
time before any re-run, per persona Principle 8 — so no wrong verdict was recorded.
The cost was entirely in wasted work and wall time.

One further trap was found while recovering: starting the daemon from the plan's
worktree resolves the *worktree copy* of `marshalld.py` as the binary path, and
that path disappears when the worktree is removed at finalize. It must be started
from the main checkout, where it resolves the version-pinned plugin-cache copy.
