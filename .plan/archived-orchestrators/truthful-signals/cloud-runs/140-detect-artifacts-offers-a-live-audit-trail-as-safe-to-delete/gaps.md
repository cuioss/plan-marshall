## G1 — A plan's own live state is protected only by `.gitignore` when its worktree is the scan root

- **Kind:** bug
- **Severity:** high
- **Where:** `marketplace/bundles/plan-marshall/skills/workflow-integration-git/scripts/git-workflow.py:652` — `scan_artifacts` (and `cmd_detect_artifacts`, line 723); the false absolute is at `marketplace/bundles/plan-marshall/skills/workflow-integration-git/SKILL.md:100`
- **What is wrong:** the nested-boundary pruning never applies to the scan **root** itself. During phase-5+ the working directory is pinned to the plan's own worktree (`file_ops.py:60-78`, `get_base_dir`) and `cmd_detect_artifacts` defaults `--root` to `Path.cwd()`, so the plan's own checkout *is* the scan root, and the plan directory has moved into it (`<worktree>/.plan/local/plans/{id}/logs/work.log`). In that configuration the **only** thing keeping the live audit trail out of `safe` is the gitignore lookup. Three reproduced triggers defeat it (each executed against a purpose-built repo + linked worktree with the production plan-state layout, git 2.43.0):
  1. `scan_artifacts(<plan worktree>, respect_gitignore=False)` → `safe = ['.mypy_cache/3.11/b.json', '.plan/local/plans/EXAMPLE-PLAN/logs/work.log', 'scratch2.temp']`.
  2. **Default flags, `.gitignore` without the `.plan/*` rule** (a project where `marshall-steward`'s `gitignore_setup.py` has not run, or a branch based before it did) → `scan_artifacts(<plan worktree>, True)` → `safe = ['.plan/local/plans/EXAMPLE-PLAN/logs/work.log', 'scratch2.temp']`. No flag required.
  3. **Default flags, git call fails** — with `git ls-files --others --ignored --exclude-standard` raising (git absent from `PATH`, 30s timeout, non-zero exit), `get_gitignored_files` returns `set()` and the same `safe` list is produced in a repo that *does* ignore `.plan/*`. See G5 for the fail-open itself.
  This is precisely the dependency D3 was written to remove ("whichever direction D2 takes"): the invariant is not independent of gitignore at the scan root, it is entirely a consequence of it.
- **Why it matters:** `SKILL.md:100` instructs the agent "For safe artifacts, delete them" and documents `--no-gitignore` as a supported flag. `SKILL.md:100` also tells the reader the loss cannot happen — "Between the two mechanisms a plan's finalize never offers the run's own live artifacts (its in-flight `logs/work.log` and build caches) for deletion" — an absolute that all three triggers falsify. This is the shipped false signal, not merely a missing feature.
- **Fix:** in `git-workflow.py`, make the exclusion of plan-runtime state unconditional in `scan_artifacts` rather than a consequence of gitignore: before the `respect_gitignore` branch, drop any relative path whose first segment equals the plan-state directory name (`git-workflow.py:753` already reads it as `_PLAN_DIR_NAME = os.environ.get('PLAN_DIR_NAME', '.plan')`), so neither `--no-gitignore`, nor a missing `.plan/*` ignore rule, nor a failed git call can defeat it. Then rewrite the `SKILL.md:100` sentence and the `scan_artifacts` docstring (`git-workflow.py:662-669`) so they name that unconditional exclusion as the guarantee instead of `.gitignore`.
- **Done when:** three tests in `test/plan-marshall/workflow-integration-git/test_git_workflow.py` build a repo whose scan root is the plan's own worktree with `.plan/local/plans/{id}/logs/work.log` under it and a control artifact beside it, and assert `work.log` is in neither `safe` nor `uncertain` while the control artifact **is** in `safe`, for (a) `respect_gitignore=False`, (b) `respect_gitignore=True` with a `.gitignore` that does not mention `.plan`, and (c) `respect_gitignore=True` with `get_gitignored_files` monkeypatched to return `set()`; and removing the new unconditional exclusion turns all three red.
- **Module/topic:** `plan-marshall:workflow-integration-git` — `detect-artifacts` classification

## G2 — Give the prefix-aware gitignore exclusion a test that fails without it

- **Kind:** vacuous-test
- **Severity:** high
- **Where:** `test/plan-marshall/workflow-integration-git/test_git_workflow.py:946` — `TestDetectArtifactsLivePlanArtifacts::test_gitignored_worktree_contents_excluded_per_contract`; code under test at `marketplace/bundles/plan-marshall/skills/workflow-integration-git/scripts/git-workflow.py:641` — `_is_ignored`
- **What is wrong:** the test's docstring names the exact-match defect ("the collapsed `.plan/local/worktrees/EXAMPLE-PLAN/` entry does not exclude its descendants"), but its fixture is a nested git worktree, which `_is_nested_git_boundary` prunes before the ignore test runs. Reverting `scan_artifacts` to the pre-fix exact-string membership test (`rel.replace(os.sep,'/') in ignored_files`) while keeping the pruning leaves the whole file green: **96 passed, 0 failed**. Removing the pruning instead while keeping the prefix-aware exclusion turns **3** tests red — and this test is *not* one of them, because the prefix branch then covers the same fixture. Only removing **both** mechanisms (i.e. restoring the actual pre-fix classification) turns it red (**4 failed, 92 passed**). So the test is pinned by the *disjunction* of the two mechanisms and can attribute its redness to neither: it is genuinely non-vacuous against the pre-fix code, and blind to the loss of either mechanism on its own. Separately, in the shipped code the `ignored_dirs` prefix branch is never reached from `scan_artifacts`: measured on git 2.43.0 over a probe tree containing an ignored directory with files, an ignored directory with only nested directories, an ignored directory tree three levels deep, an empty ignored directory, an ignored nested git repository, a non-ignored nested git repository and a symlink to an ignored directory, `git ls-files --others --ignored --exclude-standard` emitted exactly **one** trailing-slash entry — the nested git repository — and every such directory is pruned before the ignore test runs.
- **Why it matters:** the report presents this test as the verification of D5(a)/D2 direction (a). A test that passes against the defect its own docstring names is the epic's namesake failure. Concretely: the prefix-aware exclusion — the change the report calls the D2(a) fix — could be deleted by a future refactor with no signal from the suite, and the docstring would still claim to guard it.
- **Fix:** either (i) add an integration test that reaches the prefix branch without the boundary — construct the ignored-directory entry deterministically, e.g. by monkeypatching `git_workflow.get_gitignored_files` to return `{'ignored-tree/'}` for a plain (non-repo) ignored directory containing a matching artifact, and assert nothing under `ignored-tree/` is offered; and rename/rescope `test_gitignored_worktree_contents_excluded_per_contract` so its docstring names the mechanism it actually pins — or (ii) if the prefix branch is judged genuinely unreachable, delete `_split_ignored`/`_is_ignored` together with `TestIgnoreExclusionHelpers` and state in the `scan_artifacts` docstring that the collapsed-directory case is handled by boundary pruning alone.
- **Done when:** reverting the exclusion test in `scan_artifacts` to the pre-fix exact-string form makes at least one test in `test_git_workflow.py` fail — or the code path and its unit tests are removed and the docstring no longer claims a mechanism the tree does not exercise.
- **Module/topic:** `plan-marshall:workflow-integration-git` — `detect-artifacts` tests

## G3 — Correct the `get_gitignored_files` docstring: it uses `git ls-files`, not `git check-ignore`

- **Kind:** stale-statement
- **Severity:** medium
- **Where:** `marketplace/bundles/plan-marshall/skills/workflow-integration-git/scripts/git-workflow.py:534` — `get_gitignored_files`
- **What is wrong:** the docstring reads *"Uses `git check-ignore` to respect .gitignore rules"* while line 539 runs `['git', 'ls-files', '--others', '--ignored', '--exclude-standard']`. It predates this plan and this plan's own re-documentation pass left it. (**Not** attributable to a commit from this clone: `git log -S 'git check-ignore'` on the file returns only `87c677bb`, but `.git/shallow` contains exactly `87c677bb410882e230d83fad44ad7efb9a346caf` — it is the graft root of a shallow clone, so every `--diff-filter=A` there is an artifact of truncated history. The introducing commit is not determinable here.) The two commands differ in exactly the property this plan turns on — `git ls-files` collapses a nested-repository directory to a single trailing-slash entry, while `git check-ignore` answers per queried path and never collapses.
- **Why it matters:** a reader debugging the exclusion behaviour (the audience this plan created) is pointed at the wrong command and would not find the collapse mechanism the fix is built around; it also makes the `_split_ignored` rationale (line 626, which correctly names `git ls-files`) read as contradicting the function it partitions.
- **Fix:** replace the sentence with one naming the actual command and its two relevant properties — `git ls-files --others --ignored --exclude-standard`, which enumerates ignored files individually but reports a nested repository as a single trailing-slash directory entry — and keep the existing "returns empty set if not inside a git repo or git is unavailable" clause.
- **Done when:** the docstring names `git ls-files` and no occurrence of `check-ignore` remains in `git-workflow.py`.
- **Module/topic:** `plan-marshall:workflow-integration-git` — `detect-artifacts` documentation

## G4 — State the unconditional nested-boundary skip where `--no-gitignore` is documented

- **Kind:** doc-drift
- **Severity:** low
- **Where:** `marketplace/bundles/plan-marshall/skills/workflow-integration-git/scripts/git-workflow.py:2025` — the `--no-gitignore` argparse `help=`; and `marketplace/bundles/plan-marshall/skills/workflow-integration-git/SKILL.md:285` — the `--no-gitignore` parameter line
- **What is wrong:** both say only "Include gitignored files in results". Since `fb41f014` the nested git repository/worktree skip is unconditional — `--no-gitignore` does **not** make a nested worktree's contents appear. Both strings promise a completeness the flag no longer delivers.
- **Why it matters:** these are the two places a caller reads before passing the flag; a user who passes `--no-gitignore` expecting the full untracked set gets a silently narrower one, and has no documented reason why.
- **Fix:** extend both strings, e.g. "Include gitignored files in results (nested git repositories and worktrees are still never traversed)".
- **Done when:** `git-workflow.py:2025` and `SKILL.md:285` both mention that the nested-boundary skip is unaffected by the flag.
- **Module/topic:** `plan-marshall:workflow-integration-git` — `detect-artifacts` documentation

## G5 — `get_gitignored_files` fails open: any git error silently means "nothing is ignored"

- **Kind:** bug
- **Severity:** medium
- **Where:** `marketplace/bundles/plan-marshall/skills/workflow-integration-git/scripts/git-workflow.py:537-549` — `get_gitignored_files`; consumed at `git-workflow.py:682-684` in `scan_artifacts`
- **What is wrong:** every failure mode of the git call — non-zero exit (line 545-546), `TimeoutExpired` at the hard-coded 30s ceiling, `FileNotFoundError` when git is not on `PATH`, any `OSError` (line 548-549) — returns `set()`, which `scan_artifacts` cannot distinguish from *"this tree has no ignored files"*. The most dangerous possible answer is the silent default. Executed: with the `git ls-files --others --ignored --exclude-standard` call forced to raise inside a real repo whose `.gitignore` carries `.plan/*`, `get_gitignored_files(<worktree>)` → `set()` and `scan_artifacts(<worktree>, respect_gitignore=True)` → `safe = ['.plan/local/plans/EXAMPLE-PLAN/logs/work.log', 'scratch2.temp']`. `cmd_detect_artifacts` reports `status: success` with no indication that the ignore set was never obtained.
- **Why it matters:** D2 direction (a) is *"genuinely exclude gitignored paths"*, and `SKILL.md:100`/`SKILL.md:276` promise that exclusion without qualification. A guard whose failure mode is to pass silently, producing a clean-looking result from a check that examined nothing, is this epic's archetype. The run report dismissed the adjacent non-repo case as residue on the rationale *"a running plan is always inside a git repo"* — that rationale does not cover a git call that fails **inside** a repo, which is the case reproduced above.
- **Fix:** in `git-workflow.py`, give `get_gitignored_files` a return type that distinguishes "no ignored files" from "could not determine" — e.g. return `set() | None`, `None` on any exception or non-zero exit — and have `scan_artifacts` propagate that: when `respect_gitignore=True` and the ignore set is indeterminate, `cmd_detect_artifacts` must return `make_error(...)` (as it already does for a missing directory, line 728) rather than a `safe` list computed from an empty ignore set. Keep the deliberate non-repo behaviour available for callers that want it by requiring an explicit `--no-gitignore`.
- **Done when:** a test in `test/plan-marshall/workflow-integration-git/test_git_workflow.py` monkeypatches the `git ls-files --ignored` subprocess call to raise, invokes `cmd_detect_artifacts` with default flags against a repo containing one gitignored artifact, and asserts the result carries an error status and no `safe` entry for that artifact; and `grep` finds no remaining bare `return set()` on an exception path in `get_gitignored_files`.
- **Module/topic:** `plan-marshall:workflow-integration-git` — `detect-artifacts` classification
