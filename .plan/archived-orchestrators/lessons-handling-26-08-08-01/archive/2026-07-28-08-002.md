# A doc-claimed concurrency property (idempotent, safe-to-resume) needs an interleaving test, not a prose-presence assertion

## Observation

`orchestrator-inbox-pickup` added `cmd_inbox_archive`, whose docstring and its
governing deliverable both explicitly claimed the operation is "idempotent on
repeat" and "safe to resume." Six rounds of self-review over this plan
validated that PROSE — confirming the docstring said the words, confirming
the deliverable's acceptance criterion referenced them — without once
exercising the actual INTERLEAVING a resumed or concurrently-invoked archive
operation would produce. A TOCTOU race (a check-then-act window between
verifying a message is unarchived and moving it to `archive/`) falsified the
claim; an external reviewer found it, not any of the six local passes.

## Why it matters

A claim about a CONCURRENCY property (idempotent, safe-to-resume, race-free,
atomic) is a claim about behavior under a specific adversarial condition —
repeated invocation, resumed-after-partial-failure invocation, or concurrent
invocation. Verifying that claim by reading the docstring, or by running the
happy-path test once, tests a completely different property: that the
function behaves correctly on a SINGLE, uninterrupted call. Self-review
rounds that repeatedly re-confirm the doc-contract's wording ("yes, the
docstring still says idempotent") are strengthening confidence in the wrong
thing — they can run arbitrarily many times without ever touching the
interleaving that would break the claim, and each clean pass produces a
false sense of increasing assurance.

This generalizes: any function whose contract includes a concurrency-shaped
adjective needs a test that constructs the SPECIFIC adversarial interleaving
the adjective promises safety against, not a functional test of the
single-call path plus a documentation-presence check.

## Rule

When a doc, docstring, or deliverable acceptance criterion asserts a
concurrency property, treat that assertion as UNVERIFIED until a test exists
that:

1. Names the specific interleaving the property promises safety against
   (e.g., for "idempotent on repeat": call the operation, then call it again
   before/without the first call's side effects being visible to the
   second, and assert the outcome is unchanged; for "safe to resume": kill
   or interrupt the operation mid-way and assert a subsequent invocation
   completes correctly without duplicating or losing state).
2. Actually exercises that interleaving — not merely calls the function
   twice sequentially in the common case where the first call's effects are
   already fully settled before the second begins, which does not exercise
   the race window at all.
3. Would FAIL if the concurrency property were violated — i.e., the test is
   falsifiable in the direction that matters, mirroring the general
   vacuous-guard-test discipline (a test that cannot fail in the direction
   the claim is about is not evidence for the claim).

A self-review pass that re-validates the SENTENCE claiming the property
(docstring text, deliverable wording) across multiple rounds provides zero
additional assurance about the property itself and should not be counted as
having verified it — module-testing coverage for a concurrency-shaped claim
means an interleaving test exists, not that the claim is documented.
