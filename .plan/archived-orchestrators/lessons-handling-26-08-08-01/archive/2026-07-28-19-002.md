# Review participation must be derived from review CONTENT, and a bot review can arrive AFTER the merge — a bot's own status prose and the finalize-time comment snapshot are both non-oracles

## Context

PR #1036 (epic `test-suite-quality`, PLAN-10). Three review bots enabled. The plan's own
landing report concluded: *"Three reviewers are enabled; zero produced any review content on
this PR"* and *"Do not read this PR's green finalize as evidence the bots saw the diff."*

The orchestrator re-ran `ci pr comments --pr-number 1036` at analyze time and the record is
**different from what the plan saw** — in both directions. Both halves of that divergence are
the lesson.

## Half 1 — a bot's own status prose is not a completion oracle

At 15:44:05 UTC CodeRabbit answered an explicit `@coderabbitai review` with
**"✅ Action performed — Review finished."** Six seconds later, at 15:44:11, it *updated* its
own still-live rate-limit notice, refreshing "Next review available in: 46 minutes". Same bot,
same PR, six seconds apart: a green success string emitted by a path that had not reached the
goal. The reply's small print ("CodeRabbit is an incremental review system and does not
re-review already reviewed commits") describes a no-op the reader is invited to read as
completion — the commits had never been reviewed.

Sourcery refused outright ("weekly rate limit of 500000 diff characters"). pr-agent posted a
content-free "PR Reviewer Guide" table (tests present / no security concerns / no major
issues) with no actionable suggestion.

`finalize-step-review-retrospective` reported **"1 of 3 reviewers reviewed"**. By content, the
truthful answer at that moment was **0 of 3**.

## Half 2 — THE CORRECTION: the review arrived 2m42s AFTER the merge

The plan's "zero review content" conclusion was true when written (16:24:13 UTC) and is
**false now**. CodeRabbit's rate-limit window expired and it posted a real review:

| Time (UTC) | Event |
|------------|-------|
| 16:35:23 | second commit `530e5fac` pushed (the timeout-path fix) |
| **16:42:47** | **PR #1036 MERGED** (`a8cc8acef`) |
| **16:45:29** | **CodeRabbit posts "Actionable comments posted: 5"** — 5 inline findings |

The review base was `741a1c99d..530e5face` — i.e. CodeRabbit reviewed the **final** tree,
including the second commit. All 12 comments on the PR are **unresolved**. Three of the five
findings were independently confirmed against merged main by the orchestrator.

**This is the second consecutive occurrence in the same epic.** On #1026 a CodeRabbit finding
landed 58 s post-merge and stayed open in main; on #1036 five findings landed 2m42s
post-merge. The pattern is causal, not coincidental: the bot is rate-limited at finalize time,
finalize proceeds and merges, the rate-limit window expires, and the review lands on a closed
PR nobody re-reads.

## Corrective rule

**Derive review participation from review CONTENT, and treat the finalize-time comment
snapshot as provisional whenever any reviewer refused for a transient reason.**

1. A reviewer counts as having reviewed only when it emitted at least one comment that is
   **not** a rate-limit notice, a command acknowledgement, or a content-free summary table.
   Bot acknowledgement bodies (`✅ Action performed`, `Review limit reached`, sourcery's
   rate-limit body, pr-agent's bare "PR Reviewer Guide") are **meta**, and meta is not
   participation. `review-retrospective`'s "N of M" headline must be computed this way.
2. A rate-limit / refusal notice is a **first-class non-participation fact for that PR head**,
   and is NOT cancelled by a later success string from the same bot unless real review content
   accompanies it.
3. **A transient refusal makes the merge-time review record provisional.** When a bot refused
   for a rate-limit reason, the PR MUST be re-read after the stated window expires — the
   notice carries the window ("Next review available in: 46 minutes"), so the re-read time is
   knowable. A merge that proceeds past a transient refusal owes a post-merge comment sweep;
   without one, findings against the merged tree are filed where nothing will ever read them.
4. Never read a green finalize as evidence the bots saw the diff. Both directions of this
   lesson are the same failure: the review record at any single instant is a snapshot, and the
   snapshot was taken at the one moment the bots were guaranteed silent.

## Recurrence — 2026-08-03 (content-search-seam, PR #1084)

Third consecutive occurrence, and the first where the pipeline's own instrumentation named the
divergence **at the time**, in the shape this lesson prescribes:

```text
Only pr-agent reviewed PR #1084. coderabbit refused (awaitable_window) and sourcery refused
(hard_quota), review_rate_window_await=false so no recovery attempted. The green participation
verdict proves participation, not review coverage - 2 of 3 configured reviewers never saw this diff.
```

So rule 1 (participation from content) and rule 2 (a refusal is a first-class
non-participation fact) are **working**. The failure moved to rule 3.

**Rule 3 is still owed, and this run shows why it is not optional.** The provisional record was
never re-read by design. What re-read it was an accident: an unrelated triage fix moved HEAD,
which triggered a `head_dependent` re-fire ~50 minutes later, and CodeRabbit — whose
`awaitable_window` had by then expired — delivered **14 findings**, two of them Major. The
step's own log:

```text
The head_dependent re-fire caught a late reviewer: coderabbit … delivered a full inline review of
the branch and filed 14 findings - while pr-agent simultaneously WITHDREW its own finding and now
reports no major issues. A single green participation verdict at the first HEAD would have merged
this branch with 14 unseen comments.
```

Two additions to the lesson's evidence base:

- **The re-read trigger is keyed on the wrong thing.** It fires on HEAD movement, i.e. on
  whether more code changed — not on whether an outstanding transient refusal was ever
  discharged. With a clean self-review round, no commit lands, no re-fire happens, and the 14
  findings never surface. The rescue was a coincidence.
- **A bot can WITHDRAW a finding between snapshots.** pr-agent's earlier finding disappeared on
  the re-read. Half 1 and Half 2 both concern content appearing late; this is content
  *vanishing*, which breaks the assumption that a snapshot is at least a lower bound on
  findings. It is not monotone in either direction.

Sourcery's refusal was `hard_quota` (size-keyed, 500,000 diff chars) — unrecoverable per
`2026-07-28-23-002`, correctly not counted against it. CodeRabbit's was `awaitable_window` —
demonstrably recoverable, and demonstrably not recovered by design.

The pipeline-side half of this recurrence is filed separately as `2026-08-03-14-002`
(`plan-marshall:phase-6-finalize`), since the defect there is the absence of a designed
re-review path rather than a mis-read of the review record.

## Impact

Every PR that finalizes while a review bot is rate-limited — the common case on this org, not
the edge case (CodeRabbit and Sourcery refused within nine seconds of each other on #1036).
The failure is silent in both directions: the retrospective over-counts participation at merge
time, and real findings arrive afterwards on a PR that is already closed. On #1036 that cost
three confirmed live defects in merged main (see the epic's Open Defects).
