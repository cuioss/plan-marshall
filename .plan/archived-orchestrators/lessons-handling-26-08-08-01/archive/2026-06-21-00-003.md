# module_testing task profile ran only module-tests (pytest), not quality-gate (ruff+mypy), letting an F401 ruff defect slip past phase-5 to the phase-6 verify gate; the profile contract must run both

## Context

During `finalize-step-review-retrospective`, the phase-5 `module_testing` task
profile did NOT run the quality-gate (ruff + mypy) for at least one task (task 6) —
only `module-tests` (pytest) ran. As a result an unused-import ruff defect
(`F401 pathlib.Path`) slipped through phase-5 entirely and was first caught at the
phase-6 commit-push freshness / verify gate, forcing an orchestrator-owned rebuild
mid-finalize.

Notably, a sibling task in the same plan (task 2) DID run both `module-tests` and
`quality-gate`, so the gap was per-task profile-application inconsistency, not a
plan-wide config setting.

## The defect

The `module_testing` profile's verification contract is under-specified (or applied
inconsistently): a task can complete the profile having run only pytest, leaving
lint and type defects uncaught until a later phase. pytest passing is NOT sufficient
evidence of a clean module — `ruff` (F401 unused import, etc.) and `mypy` errors are
orthogonal to test outcomes and slip straight through a tests-only gate.

Symptom signature:

- A phase-5 `module_testing` task records done with only a `module-tests` run in its
  trail; no `quality-gate` run for the same task.
- The defect (an F401 / ruff / mypy error) is first reported at the phase-6
  commit-push freshness / verify gate, which runs the full `verify` and forces a
  rebuild the task should have caught in-phase.

## Root cause

The `module_testing` profile ran only the test command and skipped the
lint/type-check command for the affected task. Whatever drove task 2 to run both
commands did not fire for task 6 — so the profile contract is either ambiguous about
which commands constitute "module testing" or it is being applied non-uniformly
across tasks.

## How to apply

- The `module_testing` profile contract MUST run BOTH `module-tests` (pytest) AND
  `quality-gate` (ruff + mypy) for every task it governs — the same shape task 2
  exercised. A tests-only run does not satisfy the profile.
- Catch lint/type defects in-phase (phase-5), where the cost is one task's re-run,
  rather than at the phase-6 verify gate, where the cost is a full rebuild plus a
  mid-finalize loop.
- Treat a phase-6 verify-gate failure on a ruff/mypy defect (with passing tests) as
  the signature of this profile gap — it means the module_testing profile ran tests
  but not quality-gate for the owning task.
- The durable fix is in the `execute-task` `module_testing` profile definition (run
  both commands unconditionally), not in per-task prose reminding the agent to also
  run quality-gate.

Related: the project memory note "Run `./pw quality-gate` Before Committing"
(module-tests passing is not sufficient; mypy + ruff slip through) — this lesson
moves that discipline from human/orchestrator commit-time into the per-task
profile contract so it is enforced in-phase. Distinct from lesson
`2026-06-20-23-001` (which governs verify *scope* — full vs module-scoped — when a
plan changes a widely-consumed default), and from `2026-06-20-16-002` (which is
finalize-step *ordering* vs the freshness gate).

## Recurrence — 2026-06-24 (eliminate-or-statically-guard-manually-maintained)

Same root cause, observed on a different fix-application path: the
`automated-review` fixes during this plan's finalize run (replacing `ast.walk`
with explicit stack traversal) introduced two mypy type errors
(`list[stmt].extend` fed an `Iterator[AST]`) that the verification done after
the fix used **`module-tests` (pytest) only, not the full `quality-gate`
(ruff + mypy)**. The tests passed, so the fix looked clean; the two mypy errors
only surfaced when the orchestrator's subsequent full `verify` ran.

This widens the lesson beyond the phase-5 `module_testing` profile to a second
caller: the **finalize-phase fix-application path** (automated-review /
sonar-roundtrip loop-back fixes). The same discipline applies — a fix that
mutates source MUST be re-verified with `quality-gate` (ruff + mypy), not just
`module-tests`, before it is trusted as clean. Re-verifying with `module-tests`
alone after applying a finalize fix is the recurring trap: type errors and lint
defects are orthogonal to test outcomes and slip straight through a tests-only
re-verify. Treat "fix applied → re-verify with module-tests → it passed" as the
signature, and substitute `quality-gate` (which runs both) for the re-verify
step.

## Recurrence — 2026-07-09 (plan-11-audit-check-refresh)

Same root cause, a different ruff family: **six `UP037` lint issues** (unnecessary
quotes around type annotations) slipped straight past phase-5 because the phase-5
verification ran `module-tests` (pytest) but not `quality-gate` (ruff + mypy), and
were first caught at the **phase-6 push freshness / verify gate** — the identical
"tests passed, lint slipped to phase-6" shape as the original `F401` and the
2026-06-24 `mypy` recurrence. The corrective is unchanged: `quality-gate` (ruff +
mypy) must run in-phase, not only at the phase-6 gate.

This recurrence also surfaces the **structural reason the gap keeps recurring on this
repo**: `module-tests` on the `plan-marshall` bundle is orchestrator-tier
(`execution_tier=orchestrator`, ~700s, auto-backgrounds), so a phase-5 execution
sub-agent physically cannot run the quality-gate inline — the long-running command is
owned by the orchestrator. When phase-5 verification is dispatched to a sub-agent that
can only run the fast `module-tests` slice, the ruff/mypy slice is silently deferred to
the orchestrator's phase-6 gate. The durable fix remains the `module_testing` profile
contract (run both), but on orchestrator-tier build modules the profile must route the
`quality-gate` slice to the orchestrator (not skip it) so lint/type defects are still
caught before phase-6. See CLAUDE.md § "Bash: Timeout from architecture-resolved
canonical command" (`execution_tier=orchestrator` hand-off) and lesson
`2026-06-24-09-002` (orchestrator builds + freshness re-registration) for the
orchestrator-tier mechanics.

## Recurrence — 2026-07-14 (finalize-lane-unification): the complementary direction — static quality-gate alone is blind to a semantic branch-not-firing bug

The three prior instances all run one direction: **lint/type defects slip past
a tests-only run**, so `quality-gate` (ruff + mypy) is the load-bearing
addition. This plan observed the **complementary** failure of the same two-gate
pair: a real semantic bug that `quality-gate` (mypy + ruff) is structurally
incapable of catching, where only the behavioral **module-tests sweep** caught
it. `_apply_unresolved_ask_provider_drop` failed to strip the `plan-marshall:`
notation prefix before its lane-override lookup, so the provider-drop branch
silently never fired for the prefixed `automatic-review` step — the exact
provenance feature this plan shipped, broken for the common (prefixed) case. It
was well-typed and lint-clean, so per-task `quality-gate` passed; the
branch-not-firing was invisible until the orchestrator-tier `module-tests`
sweep exercised the behavior and failed.

The reinforced rule, seen now from both sides: the `module_testing` /
finalize-fix verification contract must run **both** gates because they cover
**orthogonal** defect classes — `quality-gate` (static) catches lint/type
defects that tests miss, and `module-tests` (behavioral) catches
semantic/branch-firing bugs that static analysis cannot see. Dropping either
gate leaves a whole class uncaught. Concretely for this repo where
`module-tests` is orchestrator-tier and auto-backgrounds: a plan that changes
control-flow logic (a new branch, a guard, a prefix-strip) MUST reach the
orchestrator-tier `module-tests` sweep before it is trusted — a green per-task
`quality-gate` is necessary but not sufficient evidence of a correct branch.
