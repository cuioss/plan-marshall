title: @coderabbitai review is the wrong trigger when automatic reviews are not paused - push is
content: "## Context

On plan `shipped-guards-assume-the-meta-projects-own-layout`, CodeRabbit had not reviewed HEAD `0617a8221`. The workflow's event-generation action posted an explicit `@coderabbitai review` command. It was refused at 23:04:59Z (`awaitable_window`, `cause: quota`, no ETA, after 903s / 28 polls). The operator policy was applied verbatim: sleep >= 5400s, retry.

After a full 90-minute wait, the same command was refused again at 00:53:42Z (931s / 29 polls). This time the run read the **full** refusal body rather than only its classification, and the diagnosis changed completely. The body said:

> \"CodeRabbit is an incremental review system and does not re-review already reviewed commits. This command is applicable only when automatic reviews are paused.\"

Automatic reviews were **not** paused on that PR. The explicit command was therefore never an applicable trigger for this situation — the natural trigger is a **push event**. The 22:40Z push that would have triggered a review had been dropped only because it landed about three minutes inside a then-spent window.

Evidence that the hourly cycle itself was working fine: reviews completed at 19:29Z and 21:43Z.

Two operator waits — roughly three hours of wall clock plus two full poll cycles — were spent on an instrument the bot itself declares inapplicable.

## Root cause

The refusal classifier reads the refusal's **class** (`awaitable_window` / `cause: quota`) and routes on it. It does not read the refusal **body**'s statement about instrument applicability. A quota-shaped refusal and an inapplicable-instrument refusal are indistinguishable to the router, so both route to \"wait for the window and retry the same command\" — which can never succeed for the second kind, however long the wait.

Compounding it: the run's own window arithmetic was independently wrong twice (decision entry 354 — first inferring \"long open\" from an 08:09Z trigger, then inferring a reset at ~22:43Z from a 21:43Z spend), so the retry timing was also unreliable. But timing was not the blocker here. The instrument was.

## Proposed action

1. In `automatic-review`, when a refusal body states the command is applicable only under a condition that does not hold (CodeRabbit's \"applicable only when automatic reviews are paused\"), classify it as `wrong_instrument` rather than `awaitable_window`, and do **not** consume an operator wait on it.
2. For `bot_kind: coderabbit`, make the event-generation action prefer a **push** event over the `@coderabbitai review` command whenever automatic reviews are active on the PR. Reserve the explicit command for the paused case it documents.
3. Record in `automatic-review/standards/coderabbit.md` that a no-op re-push of the same HEAD generates no event, so a real event is required.

## Impact

Each mistaken wait costs at least 5400s of wall clock plus a poll cycle, and under an unattended policy with a wait ceiling it also burns one of a finite number of retries. On this plan two of three spent waits were spent this way, on a policy ceiling of ten.

## Evidence

- decision.log entry 355 — the full refusal body, the \"automatic reviews are NOT paused\" finding, and the conclusion that a push is the natural trigger
- decision.log entry 354 — \"the orchestrator's window arithmetic has now been WRONG TWICE ... stop inferring it\"
- `status.metadata.unattended_run` — `waits_spent=3`, `coderabbit_rate_window_wait_seconds=5400`, ceiling 10
- work.log 2026-09-05T01:10:12Z — `waits_spent` advanced to 3"
