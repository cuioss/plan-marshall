# Log-summary extractors must anchor to the summary line before reading counts, not count-scan the whole log

A build/test-log summary extractor must first **isolate the canonical summary
line**, then read counts from that isolated line. It must NOT count-scan the
whole log for `passed` / `failed` / `skipped` (or equivalent) patterns.

## Defect

`_extract_pytest_summary` (build-pyproject log parser) matched the
`passed` / `failed` / `skipped` count patterns across the **entire** log
body rather than first locating pytest's summary line (the terminal
`=== N passed, M failed, K skipped in T ===` line) and extracting counts
only from it. Any stray occurrence of those tokens elsewhere in the log —
inside a traceback, an individual test's captured stdout, an assertion
message, or narrative output — is a false match that corrupts the parsed
counts. The parser produced a structurally-valid TOON summary with wrong
numbers.

## Why it slipped

Every in-house gate passed: the code compiled, the quality-gate was clean,
and the module-tests exercised the happy path (a log whose only count-token
occurrences were in the real summary line). The whole-log-scan vs
summary-line-scan distinction is a **match-scope** correctness property that
no structural lint or type check can see, and the existing fixtures did not
include a log with count tokens outside the summary line. Only the PR review
bot (Gemini, flagged high-priority) caught it.

## Corrective rule

For any log/output summary parser:

1. **Anchor first.** Locate the single canonical summary line by its
   distinctive anchor (for pytest: the `====...` short-test-summary /
   final-status line), then extract counts *from that line only*.
2. **Never count-scan the whole log** for status/count tokens — those tokens
   recur in tracebacks, captured output, and narrative and will false-match.
3. **Fixture the adversarial case.** Add a test whose log contains the count
   tokens *outside* the summary line (e.g. an assertion message reading
   "expected 3 passed") and assert the parser ignores them.

## Scope

This is a cross-parser rule. All four build-wrapper parsers
(`build-pyproject`, `build-maven`, `build-gradle`, `build-npm`) extract
summary counts from tool output and share this failure mode; audit each for
whole-log count-scanning when touching its summary-extraction path.
