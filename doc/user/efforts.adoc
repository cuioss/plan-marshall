= Efforts — Per-Role Model Selection
:nofooter:
:toc: left
:toclevels: 3

xref:../../README.md[Plan Marshall] » xref:README.adoc[User Guide]

How a project author tunes which model and effort tier runs for each LLM-judgement workflow in Plan Marshall. This page is self-contained for everyday use; spec-level details (precise resolution order, two-axis model, build-time guards) live in link:../../marketplace/bundles/plan-marshall/skills/plan-marshall/standards/effort-variants.md[`effort-variants.md`].

== What this does

By default, every sub-agent `/plan-marshall` hands work to inherits the model from the parent session. Most workflows don't need that — paying frontier tokens for routine refactors or mechanical lookups is wasteful. The *Efforts* system lets you assign target-neutral cognitive tiers (`level-1` through `level-7`) per phase, and optionally per workflow inside a phase. End result: research, solution design, and architectural triage run on heavyweight models with deeper thinking budgets; routine edits run on faster, cost-effective models.

The configuration lives in `.plan/marshal.json`. The resolver reads `marshal.json` fresh every time work is handed off.

[#level-palette]
== The Level Palette

Plan Marshall defines seven ordinal tiers plus an `inherit` sentinel. Each tier maps to a coordinate in the **Two-Axis Effort Model**:

$$\text{Level} = (\text{Model Axis}, \text{Effort Axis})$$

[cols="1,2,1,1,3", options="header"]
|===
| Level | Cognitive Purpose | Claude Code | Antigravity | When to use

| `level-1` | Fast mechanical transforms | Haiku | Flash (low) | Log scrubbing, simple lookups, deterministic file transforms.
| `level-2` | Routine scoped edits | Sonnet (medium) | Flash (low) | Routine code edits, unit test updates, documentation fixes.
| `level-3` | Analytical triage & validation | Sonnet (high) | Flash (medium) | Analytical work: triage, multi-file inspection, test validation.
| `level-4` | Advanced solution formulation | Opus (medium) | Flash (medium) | Architectural outline, solution design, cross-component refactoring.
| `level-5` | Deep exploration & analysis | Opus (high) | Flash (high) | Comprehensive test suite analysis, deep investigation.
| `level-6` | Complex cross-cutting synthesis | Opus (xhigh) | Pro (low) | Cross-cutting architectural synthesis, subtle concurrency/race analysis.
| `level-7` | Maximum capability ceiling | Fable (max) | Pro (high) | High-stakes security review, definitive architectural decisions.
| `inherit` | Session model inheritance | (parent) | (parent) | Sentinel: uses canonical variant, inheriting the parent session's active model.
|===

* **Claude Code**: Realizes levels via Anthropic model aliases (`haiku`, `sonnet`, `opus`, `fable`) and effort tiers.
* **Google Antigravity**: Realizes levels via Gemini engines (**Flash 3.8** with low/medium/high effort, and **Pro 3.1** with low/high effort) following the default Option 1 ladder.
* **OpenCode**: Emits all seven variants unpinned (`inherit`), running all subagents on the session model by default.

Canonical definitions: link:../../marketplace/bundles/plan-marshall/skills/plan-marshall/standards/effort-levels.md[`effort-levels.md`].

== Machine-Local Effort Ladders (`.plan/local/effort-ladder.json`)

While project configuration in `marshal.json` specifies target-neutral levels (`level-1` .. `level-7`), the mapping of what each level actually provisions on a local workstation can be customized machine-locally in `.plan/local/effort-ladder.json` (git-ignored).

Running `/marshall-steward` automatically seeds the file with standard defaults:
* **`antigravity`**: Option 1 ladder (`flash low` to `pro high`)
* **`claude`**: Canonical ladder (`haiku` to `fable max`)
* **`opencode`**: Inherit ladder (all levels unpinned)

If the local ladder file is absent, all levels cleanly fall back to `inherit` and a warning is logged.

[#what-you-can-tune]
== What you can tune

Plan Marshall's role registry is **phase-scoped**: five groups, named after each SKILL.md (`phase-2-refine` … `phase-6-finalize`). (phase-1-init runs in the main session rather than being handed to a sub-agent, so it has no effort role.) Inside each group, you can either set a single level (applies to every workflow under that phase) or set per-workflow sub-keys.

Sub-keys recognised per phase:

[cols="1,3", options="header"]
|===
| Group | Recognised sub-keys

| `phase-2-refine` … `phase-4-plan` | `default`
| `phase-5-execute` | `default`, `verification-feedback`
| `phase-6-finalize` | `default`, `verification-feedback`, `post-run-review`
|===

Plus the plan-wide fallback `plan.effort` (a single string applied to anything no phase pinned).

The full registry — which workflow doc each sub-key drives, and therefore which `execution-context-{level}` variant runs when that role fires — is in link:../../marketplace/bundles/plan-marshall/skills/plan-marshall/standards/effort-roles.md[`effort-roles.md`].

== Recommended starting point — presets

Don't tune individual sub-keys until you've tried a preset. Three are bundled and cover most projects:

[cols="1,3", options="header"]
|===
| Preset | Profile

| `economic` | Cost-optimised. Default `level-3`. Lifts `phase-3-outline`, `phase-5-execute.default`, and `phase-6-finalize.post-run-review` to `level-4`; the triage (`verification-feedback`) slots stay at `level-3`. Summed-level spread 30.
| `balanced` | Middle of the road. Default `level-4`. Lifts the analytical phases (`phase-2-refine`, `phase-4-plan`) to `level-4` and the highest-value reasoning slots (`phase-3-outline`, `phase-5-execute.default`, `phase-6-finalize.post-run-review`) to `level-5`; triage stays at `level-3`. Summed-level spread 36.
| `high-end` | Upper-tier. Default `level-4`. Pushes every analytical phase, `phase-5-execute.default`, and `post-run-review` to `level-5`; only the triage (`verification-feedback`) and finalize-default slots stay at `level-4`. Summed-level spread 41. `level-6`/`level-7` require explicit per-phase opt-in.
|===

The three presets form an evenly-spaced ladder along the summed-level spread (30 / 36 / 41), so each rung is genuinely distinct — no preset collapses onto its neighbour.

Apply via the wizard:

[source,bash]
----
/marshall-steward         # → Configuration → Effort → preset picker
----

…or directly:

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-config:manage-config \
  effort apply-preset --preset balanced
----

The preset payloads live in link:../../marketplace/bundles/plan-marshall/skills/plan-marshall/scripts/effort_presets.py[`effort_presets.py`].

== Direct configuration

If presets don't fit, edit `marshal.json` directly. The `plan.<phase>.effort` field is polymorphic — a string applies that level to every workflow under the phase; an object sets per-sub-key overrides plus an optional `default` slot. The plan-wide fallback is `plan.effort`.

[source,jsonc]
----
{
  "plan": {
    "effort": "level-2",                            // plan-wide fallback
    "phase-3-outline": { "effort": "level-3" },     // string form — applies to everything under phase-3-outline
    "phase-5-execute": {
      "effort": {                                   // object form — per-sub-key overrides
        "default": "level-3",
        "verification-feedback": "level-5"
      }
    }
  }
}
----

**Resolution in one line**: deepest match wins — explicit sub-key → phase `default` slot → phase string → `plan.effort` → `inherit`. The full 5-step resolution rules and edge cases live in link:../../marketplace/bundles/plan-marshall/skills/plan-marshall/standards/effort-variants.md[`effort-variants.md`].

The `effort` block is **opt-in**: when absent entirely, every sub-agent inherits the parent session's model — same as if every key were `inherit`.

== Worked example

A project author wants:

* Research at the absolute top tier in phase-3-outline.
* The planning-time quality checks (phase-3 and phase-4) on `level-3`.
* Verification triage on `level-3` in both phase-5 and phase-6.
* Everything else on the default.

[source,jsonc]
----
{
  "plan": {
    "effort": "level-2",
    "phase-3-outline": {
      "effort": {
        "default": "level-3",
        "research": "level-7"
      }
    },
    "phase-4-plan": { "effort": "level-3" },
    "phase-5-execute": {
      "effort": { "verification-feedback": "level-3" }
    },
    "phase-6-finalize": {
      "effort": {
        "default": "level-2",
        "verification-feedback": "level-3"
      }
    }
  }
}
----

After saving:

* The phase-3-outline quality check runs on `execution-context-level-3` via the phase-3 `default` slot. The phase-4 quality check runs on `execution-context-level-3` via the bare-string at `phase-4-plan.effort`.
* `--phase phase-5-execute --role verification-feedback` runs on `execution-context-level-3`.
* `--phase phase-6-finalize --role verification-feedback` runs on `execution-context-level-3`.
* The rest of phase-6-finalize (create-pr, pre-submission-self-review, post-run-review) runs on `execution-context-level-2` via the phase-6 `default` slot.
* Everything else (phase-2-refine, phase-5-execute body) runs on `execution-context-level-2` via the plan-wide fallback.

[#troubleshooting]
== Troubleshooting

=== My configured level isn't taking effect

Check, in order:

1. **Spelling.** Role keys are kebab-case and match the SKILL.md name exactly (`phase-6-finalize.verification-feedback`, not `phase_6.verification_feedback`, not the bare `phase-6-finalize`).
2. **Level value.** Valid: `level-1`, `level-2`, `level-3`, `level-4`, `level-5`, `level-6`, `level-7`, `inherit`. Case-sensitive.
3. **Target rebuilt.** For meta-project developers only: if you changed variant frontmatter, target trees need regenerating. Consumer projects don't have this concern — the variants are static and only the resolver selection changes.

=== `level-6` / `level-7` isn't running on the expected model (Claude target)

`level-6` and `level-7` are alias-capability-gated on the Claude target. When the build target can't emit that variant because the resolved alias does not accept the level's effort (`xhigh` or `max`), it skips emission and the work falls back to the canonical no-suffix variant, which inherits the parent session's model. Check `.plan/logs/` for the build warning.

=== Wizard refuses my level value

Valid levels are listed above. Typos (`lvl-3`, `Level-3`, `LEVEL-7`) are refused at save time, by design.
