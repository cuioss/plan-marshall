# Pre-PR self-review rounds and post-PR review-fix rounds share one finalize loop-back counter, so the first exhausts the budget of the second


## Observed (API-Sheriff PR #369, plan-23-session-route-scope-parity, 2026-10-01 to 2026-10-02)

The finalize loop-back ceiling (`max_iterations` 5) counts every loop-back of the phase with one
counter, whatever step asked for it.

- Iterations 1 to 5 were all consumed by `pre-submission-self-review` before the branch was pushed
  (work log: "Loop-back ceiling breached ... next would be 6 > max_iterations=5", 2026-10-01T19:44Z).
- The pull request was then created with zero iterations left. The first review round raised two
  Sonar fix tasks and one CodeRabbit comment, and the triage's request for iteration 6 was refused:
  "The findings this round raised have no remaining iteration in which their fixes could be reviewed"
  (2026-10-01T21:16Z).
- The operator had to raise the ceiling for this plan twice, to 7 (decision 8084a6) and to 9
  (decision bca564). Iteration 9 was the last admitted round and was used for a real review fix
  (decision ffeb7b). `marshal.json` stayed at 5; the raise was a per-plan operator decision each time.
- One of the five pre-PR iterations bought no verdict at all: the round-4 verifier dispatch failed
  with an API 529 and was not retried, so the round stayed unverified and still counted
  (decision 35cf78).

## Why this is a defect

The ceiling exists to stop a loop that does not converge. Here it stopped a different loop: the
review-fix rounds were each productive (one round, one fix, closed), but they inherited an exhausted
budget from a step that runs before the pull request exists. The operator was asked three times to
decide something the workflow could have known: that the review rounds had not started yet.

## Directive

- Count pre-submission rounds and post-submission review-fix rounds separately, or reset the counter
  when the pull request is created.
- A round that produced no verdict because a dispatch failed (API overload) should be retried once
  and should not consume an iteration.
- When the ceiling is reached before the push, say so in the stop message: "the review phase starts
  with no loop-back budget". The operator can then raise the limit once, before the push, instead of
  at each later stop.
- Until the tool changes: on a plan whose self-review loops more than twice, raise the per-plan limit
  at the first ceiling stop by the number of review rounds expected, not by two.
