# manage-tasks update has no write-back flag for verification.commands, blocking phase-4-plan's Step 6 derive-verification stamp

## Context

During `phase-4-plan` for plan `no-extension-claims-yaml-infrastructure-paths`, Step 6's
"Verification" sub-step instructs the phase to call `architecture derive-verification`
with each task's changed-artifact list and "stamp the returned command set into
`verification.commands`" via `manage-tasks update`. Attempting to follow this literally
surfaced two problems:

1. **No write-back flag exists.** `manage-tasks update --help` exposes `--cost-size`,
   `--predicted-cost-tokens`, and `--envelope-id` for the cost-sizing pipeline, but there
   is no `--verification-commands` / `--verification-criteria` flag. There is therefore no
   sanctioned script path to persist a re-derived verification list onto an already-created
   `TASK-NNN.json` — direct JSON edits are explicitly forbidden.
2. **The deriver's output would be destructive if it did have a write-back path.**
   `derive-verification` only classifies paths against the `build_map` (compile /
   test-compile / module-tests / coverage). For doc-only changed-artifact sets (an ADR
   amendment, a batch of `SKILL.md` / `standards/*.md` edits) it returns `command_count: 0`,
   which would wipe out an outline-authored custom verification command (e.g. a
   `manage-adr scan` check or a `plugin-doctor quality-gate --paths ...` invocation) that is
   the deliverable's actual, correct success check. For a task whose outline verification is
   already `module-tests plan-marshall` (the full-suite regression check demanded by the
   deliverable), the deriver instead resolves a narrower `compile` build_class — replacing
   the full-suite check with a narrower one would also be a regression.

## Root cause

`task-contract.md`'s "Provenance" section states verification commands are "copied verbatim
from the deliverable's Verification: Command field... downstream phases do not re-resolve
them" — this is the existing, correct behavior for deliverables that specify a genuine
custom check. `phase-4-plan/SKILL.md` Step 6's "Verification" deriver-stamp sub-step was
added on top of that without reconciling the two: it neither documents a merge/supplement
semantics (only add a derived command when one is missing) nor exposes the write-back
verb it depends on.

## Recommended action

- Add a `manage-tasks update --verification-commands` (and optionally
  `--verification-criteria`) flag so the stamp can be persisted without touching JSON
  directly.
- Clarify `phase-4-plan/SKILL.md` Step 6 so the deriver-stamp is explicitly additive:
  only append a derived build command when the task's existing `verification.commands`
  is empty, or when the deliverable's outline verification is itself unset/generic — never
  overwrite an outline-authored custom check, and never narrow an outline-authored
  full-suite check (e.g. `module-tests`) down to a per-file build_class (e.g. `compile`).

## Disposition applied in this plan run

Retained the deliverable-verbatim `verification.commands` for all 5 tasks (per
`task-contract.md`'s Provenance rule), logged the observed gap as a WARNING decision-log
entry, and relied on Step 7b's `execution_tier` routing pass — which independently
re-resolves each surviving verification command via `architecture resolve` at manifest
compose time — to still perform the orchestrator-tier / `bash_timeout_seconds` stamping
that the Step 6 deriver-stamp would otherwise have provided.
