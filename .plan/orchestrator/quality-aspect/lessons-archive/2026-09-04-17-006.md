# Do not hand check-manifest-consistency a post-merge base-ref without a caveat

## Context

The manifest-decisions aspect reported a `fail` on this plan: "phase_6.steps includes branch-cleanup but the observed diff is empty — the footprint resolved to no changed path at all, so no implementation file changed", with `diff.files_total: 0`. The plan actually shipped 521 realized paths, and the two sibling aspects that resolve the footprint through the shared resolver both measured it correctly. The finding is a false positive.

## Root cause

Ordering. In the composed manifest, `branch-cleanup` is step 13 of phase_6 and `plan-marshall:plan-retrospective` is step 17 — the PR has already merged by the time the retrospective runs. `check-manifest-consistency` obtains its diff from `--base-ref`, and after the merge `origin/main` CONTAINS the plan's own changes, so `HEAD..origin/main` is legitimately empty. The SKILL.md canonical block says "Supply `--base-ref` whenever `--diff-file` is absent — it is how the script obtains a diff at all", with no post-merge caveat, so following the documented guidance produces a confident wrong answer on every plan whose finalize includes branch-cleanup ahead of the retrospective.

## Proposed action

Either (a) have the SKILL.md step pass the shared-resolver footprint as `--diff-file` rather than a `--base-ref`, which is what the other two footprint-consuming aspects already do, or (b) add a post-merge caveat to the canonical block and have the script report `base: merged_or_unknown` / `indeterminate` when the supplied base-ref contains HEAD. Option (a) is preferable and also satisfies the separate proposal to resolve the footprint once per finalize run.

## Evidence

- aspect: manifest_decisions — checks.branch_cleanup_changes `fail`; findings[1] `branch_cleanup_without_changes`; diff.files_total 0 with `diff_available: true` and `oracle_available: true`, so the emptiness was measured rather than unresolved
- aspect: outline_vs_shipped — footprint_source `resolved`, footprint_path_count 521, on the same tree
- aspect: routing_decisions — footprint_source `resolved`, same run
- manifest phase_6.steps ordering: branch-cleanup at index 13, plan-marshall:plan-retrospective at index 17

## Recurrence — 2026-09-13, plan implement-plan-165-close-orphan-defects (epic test-quality)

Second occurrence, identical mechanism and identical false `branch_cleanup_without_changes`
finding: `--base-ref origin/main` at retrospective `order: 995` yielded
`diff.files_total: 0` with `oracle_available: true` and `diff_available: true` — a
*resolved empty* footprint rather than an indeterminate one, which is what let the rule
fail rather than abstain. Re-running the same check with the true 4-path footprint
(`--diff-file work/footprint.txt`) turned it green: 2 passed, 0 failed, 0 findings.

### The second half this recurrence adds: resolver parity

The caveat this lesson asks for is a documentation fix, and it leaves the caller carrying
the burden. The deeper defect is that **one of three sibling aspects in the same skill
cannot recover a footprint its siblings recover routinely**. On this run
`check-routing-decisions` and `check-outline-vs-shipped` both resolved the correct 4-path
footprint through the shared resolver with **no `--diff-file` supplied**
(`footprint_source: resolved`, `footprint_path_count: 4`), while
`check-manifest-consistency` has no such fallback and its canonical-invocation note
instructs the caller to supply `--base-ref` whenever `--diff-file` is absent.

So the stronger remedy is to give `check-manifest-consistency` the shared footprint
resolver as its fallback, which removes the caller's opportunity to choose a wrong base
at all. The caveat remains worth writing until that lands, because a documented trap is
better than an undocumented one — but a caveat is the weaker of the two fixes and this
recurrence is the evidence that documentation alone did not prevent the repeat.

## Third occurrence — 2026-09-14, plan sweep-the-three-single-instance-defect-classes (epic test-quality)

Same mechanism a third time, and this run measured the OTHER failure direction too, which
names the correct remedy for the first time.

Three aspects produced **three different footprints for one plan**:

| Source | Footprint | Verdict |
|---|---|---|
| `check-manifest-consistency --base-ref origin/main` | **0** files, `diff_available: true` | false `branch_cleanup_without_changes` — again |
| the shared footprint resolver | **130** paths | over-wide: ~43 belong to sibling commits rebased under the branch |
| `references.affected_files` | **86** paths | matches ground truth |

Ground truth is `git show --stat f21a0dc66`: **87 files**, 2082 insertions, 132 deletions.

So the resolver-parity remedy recorded above is **necessary but not sufficient**. Handing
`check-manifest-consistency` the shared resolver would have moved it from 0 paths to 130 —
from a false empty to a false wide, both wrong, in opposite directions. The earlier
occurrences only ever exhibited the empty direction, which is why the resolver looked like
the whole answer.

### The remedy this occurrence names: anchor to the MERGE BASE

The resolvers assume a live worktree on an unmerged branch. At `order: 995` —
after `branch-cleanup` has squash-merged and removed the worktree — that assumption is
guaranteed false, so the placement makes this systematic rather than incidental. The diff
against `origin/main` is empty because the branch **is** `origin/main`, and any wider base
sweeps in whatever else was rebased underneath.

Anchor the realized footprint to the **merge base** of the plan's branch and its target, or
to the merged commit itself (`git show --stat {merge_commit_sha}`), which the landing facts
already carry. Both are stable after cleanup; neither the post-merge HEAD nor a widened base
is.
