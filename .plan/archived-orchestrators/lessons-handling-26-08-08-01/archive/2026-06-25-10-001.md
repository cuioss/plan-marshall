# A standards doc that narrates the coverage of an authoritative machine-readable list (frontmatter canonicals:, discovery-query universe) must enumerate it exactly — prose that paraphrases the universe overstates or understates it, and only the PR bot catches the drift

## Context

The `verify-step-ext-point-discovery` plan (PR #779) converted the hardcoded
`BUILT_IN_VERIFY_STEPS` / `BUILT_IN_VERIFY_STEP_DESCRIPTIONS` constants into
`ext-point-verify-step` discovery via `extension_discovery.find_implementors`.
The change authored a new ext-point standard
(`marketplace/bundles/plan-marshall/skills/extension-api/standards/ext-point-verify-step.md`)
and reworked the discovery surface `_discover_all_verify_steps()` plus the seed
in `_config_defaults.py`. Two of the new docs narrate, in prose, the contents of
an authoritative machine-readable list:

1. **`ext-point-verify-step.md`** describes what `_discover_all_verify_steps()`
   returns — its "universe".
2. **`canonical_verify.md`** has a `canonicals:` frontmatter list
   (`[quality-gate, module-tests, coverage]`) AND body prose that re-enumerates
   the canonical set.

In both cases the prose and the authoritative source it narrates fell out of sync.

## Signature (slipped, then caught by the PR bot)

CodeRabbit caught two doc-vs-source-list drift defects on PR #779 that every
in-house gate (phase-5 authoring, scoped plugin-doctor quality-gate,
pre-submission self-review) passed clean:

- **(a) Coverage overstatement.** `ext-point-verify-step.md` described
  `_discover_all_verify_steps()` as if the ext-point implementors were its only
  source. In fact the function ALSO merges project-local `verify-step-*` skills
  as a *second* discovery source. The prose described a narrower universe than the
  code actually assembles — the standard *overstated* the ext-point's coverage by
  implying the ext-point was the whole universe when a second merge source exists.

- **(c) Body-vs-frontmatter enumeration mismatch.** `canonical_verify.md`'s body
  prose listed a *broader* canonical set (compile / integration-tests / e2e) than
  the authoritative `canonicals:` frontmatter list actually declared
  (quality-gate / module-tests / coverage). The machine-readable list is the
  source of truth the seed expands into `default:verify:{canonical}` step IDs;
  the body prose narrated a different, wider set.

Both were caught-and-fixed in-run before merge (the highest-value lesson class:
slipped, then caught).

## Root cause

When a standards/reference doc **narrates the contents or coverage of an
authoritative machine-readable list** — a frontmatter list the code parses, or
the universe a discovery query assembles at runtime — the prose is a *second,
hand-maintained copy* of that list. The single source of truth is the
machine-readable artifact (the `canonicals:` frontmatter; the set
`_discover_all_verify_steps()` actually returns). The prose copy drifts in two
directions:

- **Overstatement** — the prose claims the list/query covers MORE than it does,
  or that a single source IS the whole universe when the code merges additional
  sources (defect a).
- **Understatement / divergence** — the prose enumerates a DIFFERENT set than the
  authoritative list, omitting members or naming members the source does not
  contain (defect c).

No in-house gate reads doc prose against the machine-readable list it paraphrases:
plugin-doctor `quality-gate` certifies *structure* (frontmatter presence, nesting,
naming, the generic `validate_extension_contracts` EC-01/02/03 implements: checks),
and the `ext-self-review-plan-marshall` surfacer has no candidate class that
compares a prose enumeration against a same-or-sibling-doc frontmatter list or a
discovery-query's actual return set. Only the adversarial PR bot, which read the
discovery function source alongside the doc, caught that the prose and the source
list disagreed.

This is the **list-enumeration-coverage facet** of the standing "in-house gates
check structure, not domain correctness" family. It is adjacent to but distinct
from its siblings:

- `2026-06-22-11-001` (doc prose mis-described an async-wait *completion verb*) —
  that is a single semantic verb wrong; this is an *enumeration / coverage* of a
  multi-member list wrong.
- The doc-contract-drift family (`2026-06-21-12-003`) — that is *under-enumerating
  the edit sites* that must change in lock-step; this is the prose *describing the
  set's membership/coverage incorrectly* at a site that WAS edited.

## Corrective rule (do X, not Y)

When authoring or reviewing a standards/reference doc whose prose narrates the
contents or coverage of an authoritative machine-readable list (a frontmatter
list the code parses, or the runtime universe a discovery query assembles):

- **Y (avoid):** paraphrasing the universe in prose ("the discovery query returns
  the ext-point implementors", "the canonical set is X, Y, Z") from memory or from
  the doc's own narrative, without opening the authoritative source.

- **X (do):**
  1. **State the universe exactly, sourced from the authoritative artifact.** For
     a frontmatter list, copy the `canonicals:` members verbatim from the
     frontmatter into the body — do not re-derive a "broader" set from intent. For
     a discovery query, open the discovery function and enumerate EVERY source it
     merges. Here `_discover_all_verify_steps()` merges TWO sources (ext-point
     implementors AND project-local `verify-step-*` skills); the doc must say so,
     not imply the ext-point is the whole universe.
  2. **Name whether the description is exhaustive or built-ins-only.** A discovery
     query that merges a second project source makes any "the ext-point covers X"
     claim an overstatement unless the doc explicitly scopes it ("the *built-in*
     source is the ext-point; *project* `verify-step-*` skills are merged as a
     second source"). State the scope of the claim, never imply totality.
  3. **Cross-check body prose against same-doc frontmatter before submission.**
     When a doc carries BOTH a machine-readable list (frontmatter) AND prose that
     enumerates the "same" set, diff the two by hand — the frontmatter is the
     source of truth the code reads; the body prose is the copy that must match it.
  4. **When the module defines SEVERAL adjacent lists, bind the prose to the one
     the described mechanism actually reads.** See the 2026-07-26 recurrence below
     — naming the right *kind* of list is not enough when a superset sibling sits
     ten lines away.

## Why in-house gates miss it

No deterministic in-house gate compares a prose enumeration against the
machine-readable list it narrates. plugin-doctor reads frontmatter for *presence
and format*, not for *agreement with the body's prose enumeration*; the
self-review surfacer has no candidate class for "prose set vs frontmatter set"
or "prose-described universe vs discovery-query actual return set". Until such a
surfacer/analyzer exists, the only defenses are the proactive
copy-from-the-authoritative-source discipline above and an authoring-time
cross-check — both must run before the PR, or the defect costs a guaranteed
PR-bot round-trip.

## Impact

Both occurrences were caught and fixed in-run before merge, so nothing inaccurate
shipped. The class affects every ext-point standard or reference doc whose prose
narrates the coverage of a discovery query or the membership of a frontmatter
list — i.e. exactly the documents that describe plan-marshall's discovery-based
extension surfaces. A shipped overstatement would mislead a future maintainer
about which sources a discovery query consults (defect a) or about which steps
the canonical seed actually produces (defect c), seeding a wrong mental model of
the extension surface that a later change could act on incorrectly.

## Recurrence — 2026-07-22 (session-binding-gc-and-conflict-semantics)

**New sub-shape: citing a DERIVED/DEFAULTED value as if it were the DECLARED
attribute.** The two original occurrences drifted on list *membership*. This
recurrence drifts on *attribute identity* — the prose named a field that the
authoritative frontmatter does not contain at all, even though the value it
implied was semantically correct.

A phase-3-outline solution outline (deliverable 3, plus the Overview rationale)
stated that a finalize step "is `lane: minimal` (it runs in every finalize
lane)". The target file's frontmatter actually declares:

```yaml
lane:
  class: core
  cost_size: XS
```

There is no `tier` sub-field. Per `ext-point-lane-element.md`, `class` and
`tier` are distinct sub-fields, and `class: core` *defaults* to `tier: minimal`
(the default-tiers table lists `archive | core | minimal`). So the substantive
conclusion — a minimal-tier element runs under every posture — was CORRECT, but
the cited attribute is not what the file declares. A phase-5 implementer
verifying the claim by opening the file would find no `lane: minimal` field and
would have to reconstruct the defaulting rule to discover the claim was true
after all.

Caught by the phase-3-outline Q-Gate (finding `5c95da`) and resolved in-run by
restating the rationale as "`lane.class: core`, which defaults to tier
`minimal`, so it runs under every posture", with a cross-reference to
`ext-point-lane-element.md`.

**Scope broadening.** The corrective rule above now covers three drift
directions, not two:

- **Overstatement** — prose claims the list/query covers MORE than it does.
- **Understatement / divergence** — prose enumerates a DIFFERENT set.
- **Derived-value-as-declared-attribute** (this recurrence) — prose cites a
  field name that does not exist in the authoritative declaration, substituting
  a value the schema *derives by default* for the attribute actually written.

The added rule: when a schema defines a defaulting relationship (declared field
→ derived field), cite the **declared** field verbatim and state the defaulting
step explicitly, with a cross-reference to the doc that owns the defaulting
table. Never collapse "declares X, which defaults to Y" into "is Y" — the
collapsed form is unverifiable at the cited file and reads as a factual error
to the next reader even when the conclusion it supports is sound.

Unlike the original occurrences, this one was caught by an in-house gate (the
outline Q-Gate) rather than by a PR bot — the Q-Gate does read outline prose
against the files it cites, so outline-authored citations have a defense that
standards-doc-authored citations still lack.

## Recurrence — 2026-07-26 (orchestrator-queue-row-field-setter)

**New sub-shape: the module defines TWO adjacent authoritative lists, one a
superset of the other, and the prose cited the WRONG sibling.** Every prior
occurrence drifted against a *single* authoritative list — the prose was the only
copy, and the failure was paraphrasing it instead of reading it. This recurrence
is sharper: the author DID bind the prose to a real machine-readable constant in
the implementing module. It was simply the wrong one of two, defined ten lines
apart in the same file.

**What happened.** The plan added a `queue --set-row` verb to
`marshall-orchestrator/scripts/orchestrator.py` and, in the same change, authored
the `Reconciliation Actions` checklist in
`marshall-orchestrator/templates/landing-analysis.md`. The checklist correctly
enumerates the three row-result fields `--set-row` may write, matching:

```python
PLAN_ROW_FIELDS = frozenset({'plan_marshall_plan_id', 'pr', 'landing'})
```

The final checklist item then described the `resume-summary` gap marker as
clearing "once the three fields above are stamped". But the marker's condition is
a *different* constant, defined immediately below the first:

```python
TERMINAL_REQUIRED_FIELDS = ('pr', 'landing')
```

`plan_marshall_plan_id` is a writable row field but is NOT part of the marker
condition. The prose overstated the completeness requirement for clearing the
marker by one member, because the "three fields above" the checklist had just
enumerated were the *write surface*, not the *marker's required set*.

**What this adds to the root cause.** The existing rule says "open the
authoritative source and copy it verbatim". That is necessary but not sufficient
when a module carries several adjacent lists over the same domain nouns. Here
both constants are `frozenset`/tuple literals of row-field names, both live in the
same constants block, and both are legitimately "the authoritative list" — for
*different mechanisms*. Local proximity plus overlapping membership (`pr` and
`landing` appear in both) makes the wrong pick read as correct on review: the
enumeration is real, the names are real, and only the *mechanism binding* is
wrong.

**Added rule — bind the citation to the mechanism, not to the domain.** Before
citing a machine-readable list in prose, identify the specific code path the
sentence describes and trace which constant THAT path reads. When more than one
list over the same nouns exists in the module:

1. Name the constant explicitly in the prose or in a same-line parenthetical, so
   the binding is checkable rather than inferable ("the marker checks those two
   result links, not `plan_marshall_plan_id`").
2. Never carry an anaphoric reference ("the three fields above", "these fields")
   across a mechanism boundary. The referent the reader resolves is the nearest
   enumeration, which is exactly the superset that is NOT the marker's condition.
   Restate the members at the point of the new claim.
3. Treat a *superset/subset relationship between sibling constants* as the tell:
   if one list's members are contained in another's, any prose that conflates them
   is wrong in one direction and unfalsifiable by name-matching review.

**Detection.** Caught in-house by the phase-6-finalize self-review Q-Gate
(`pm-plugin-development:ext-self-review-plan-marshall`, finding `3e3f74`,
`contract_drift`) and fixed in-run before merge. This is the second consecutive
recurrence caught by an in-house gate rather than a PR bot — the self-review
surfacer now demonstrably does read authored prose against the source constants
the same change introduced, which narrows (but does not close) the "no in-house
gate reads prose against the list it narrates" gap recorded above. The gap that
remains is for docs whose narrated list lives in a module the change did NOT
touch.
