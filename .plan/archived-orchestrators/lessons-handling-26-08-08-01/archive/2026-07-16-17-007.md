# Wired-flow assertions must cover every new security binding/overload; finalize security-audit is the backstop

Re-homed from the TokenSheriff consumer store 2026-07-16 ([[feedback_manage_lessons_cwd_store_resolution]]).

**Context:** TokenSheriff plan `client-code-review-fixes` — a 47-finding OIDC/OAuth client security remediation. The plan's own root-cause finding **S0**: *security components are unit-tested in isolation but never wired into the executable flow.* That exact anti-pattern RECURRED during finalize: the **M4 `at_hash` binding** was implemented AND unit-tested in isolation, but `AuthorizationCodeFlow.exchange` called the 2-arg overload instead of the binding-carrying overload, so the `at_hash` check never executed in the real flow. Caught only by the finalize-time `finalize-step-security-audit` sweep (which drives the real flow), NOT by phase-5 verification whose isolated unit tests all passed green.

**Why it slipped:** A unit test exercising a binding directly proves the binding *works*, but nothing about whether the production call site *invokes* it. A new binding behind a new method overload leaves the old call site on the old overload — dead code in the real flow. Green isolated unit tests are NOT evidence the check runs end-to-end.

## How to apply

1. **When a plan's premise IS "components are not wired into flows", the wired-flow / negative-path assertion must cover EVERY new binding and EVERY new overload** — not a representative sample. For each new security binding, add a test that drives the real production entry point with a *malicious* input and asserts rejection. An isolated unit test on the binding object is necessary but not sufficient.
2. **Treat a new method overload as a wiring risk.** Adding a binding-carrying overload beside an existing one silently leaves every existing call site on the old path. Grep every call site of the old overload and confirm migration, or assert the old overload is gone.
3. **Keep a finalize-time security audit that drives the real flow as a backstop.** The `finalize-step-security-audit` sweep is the control that actually caught this — high-value for the "not wired" plan class because it is the only gate observing the production call path.

## Impact

Applies to any security-hardening plan whose findings add bindings/checks behind new call paths (OIDC/OAuth flow validation, token binding, signature/hash verification). The failure is silent (all unit tests pass), so close it with wired-flow assertions plus the finalize security-audit backstop, not unit-coverage metrics.
