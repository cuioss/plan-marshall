# decision-rules.md claims the composer's recipe-provenance surrogate matches the audit re-derivation, but the audit omits the recipe_key fallback: Row 2 is vacuous there and recipe-routed plans report false drift

## Observed

Surfaced by the full-corpus archived-plan retrospective audit (115 plans, 2026-07-26).

- **The live composer reads BOTH keys.** `manage-execution-manifest/scripts/_manifest_decide.py:235`
  iterates `for field in ('plan_source', 'recipe_key')`, so a plan whose status metadata carries only
  `recipe_key` still selects decision-rule Row 2 (`recipe`).
- **The audit's re-derivation reads only one.**
  `.claude/skills/audit-archived-plan-retrospectives/scripts/audit.py:873` reads
  `metadata.get("plan_source")` and nothing else, with a comment asserting `plan_source` is
  "equivalent to `recipe_key` for matrix purposes".
- **Live plans use `recipe_key`, not `plan_source`.**
  `2026-07-26-build-queue-fifo-ordering-nondeterminism/status.json` carries
  `"recipe_key": "surgical-fix"` and no `plan_source`. Across all 114 metrics-bearing archived plans
  the audit reported `recipe_routed: 0`.
- **`decision-rules.md:475` asserts the parity explicitly** — "The composer's surrogate matches the
  `audit-archived-plan-retrospectives` re-derivation, so a fresh recipe/lesson plan reports
  `actual_rule = recipe` against its `expected_rule`." That sentence is false as written.

## Impact

One missing fallback makes three separate audit signals wrong at once:

1. `derive_expected_rule`'s Row 2 (`if recipe: return "recipe"`, `audit.py:946`) is **unreachable** — a
   vacuous branch.
2. The `execution-context-manifest` check emits a **false `drift`** verdict
   (`expected=default, actual=recipe`) on every recipe-routed plan. The composer was right; the audit
   was blind.
3. The `lane-lever-effectiveness` check's `recipe_routed` column is structurally always `false`, so the
   recipe lever is never credited and `estimated_avoided_tokens` is an under-count.

**Why:** the consumer was written against one of two accepted provenance keys, and a doc line asserted
the parity instead of a test pinning it. This is the vacuous-authority family — a doc claiming an
equivalence the code does not implement (cf. the PLAN-73/74/75 cluster in the `truthful-signals` epic).

## How to apply

- Add the `recipe_key` fallback at `audit.py:873` so the audit mirrors `_manifest_decide.py:235`.
- Pin the parity with a test fixture whose status metadata carries ONLY `recipe_key`, asserting the
  audit re-derives `recipe` — the assertion must FAIL against today's code.
- Do not let a doc sentence stand as the only guarantee of cross-module parity: either the two readers
  share one helper, or a test asserts they agree.
- General rule: when a producer accepts N alias keys, every consumer must read all N, or the narrowest
  reader silently redefines the contract.
