# A literal semicolon inside a quoted --message/--detail argument trips the one-command-per-Bash-call hook even though it is not a shell separator

The one-command-per-Bash-call enforcement hook scans the RAW command line for
shell separators (`&&`, `;`, `&`, newline). It does not parse shell quoting
first, so a literal `;` inside a fully-quoted `--message`/`--detail` argument —
e.g. a `manage-logging work --message "did X; then Y"` call — is
indistinguishable to the hook from an actual command separator, and the whole
call is rejected even though nothing about it violates the one-command rule in
spirit.

## What happened (this plan, three separate hits)

Across a single plan run (`terminal-title-refresh-cadence`, PR #964), this hit
THREE times, always on prose that used a semicolon as normal punctuation inside
a quoted flag value:

- Once in the phase-2-refine leaf, on a `manage-findings qgate add --detail`
  message.
- Twice in the orchestrator, on `manage-logging decision --message` calls.

Each time the only recovery was to rewrite the prose to avoid the character —
replacing the semicolon with a comma or splitting into two sentences with a
period.

## The generalizable rule

**Never use a literal `;` inside prose destined for a `--message`/`--detail`/
`--body`/any free-text CLI flag**, regardless of quoting. The enforcement hook
cannot distinguish "a semicolon that is shell syntax" from "a semicolon that is
punctuation inside a quoted string" — it does not tokenize with shell-quoting
awareness, so both trip the same rejection. Treat this as a hard authoring
constraint for any Bash-mediated `manage-*`/`ci`/logging call: use commas or
periods instead of semicolons in the message text, every time, not just when a
rejection is anticipated.

## Why it happens

The hook exists to catch a real hazard — `cmd1; cmd2` chaining two commands in
one call — and a naive raw-line scan is the cheapest way to catch that
reliably across arbitrary command shapes. The false-positive cost (a
well-formed single command whose quoted argument happens to contain `;` as
punctuation) is accepted as the tradeoff for not having to shell-parse quoting
correctly inside the hook. This is a known, accepted false-positive class, not
a bug to fix in the hook — the corrective action lives entirely on the
authoring side (avoid the character), not the enforcement side.

## Impact

Low cost per occurrence (one rejected call, immediately corrected by rewording),
but it recurred three times in one run, confirming this is a durable authoring
habit rather than a one-off. Treating "no semicolons in free-text CLI flags" as
a standing constraint — the same way markdown-heading-in-heredoc and
`$()`-substitution are standing constraints — avoids the wasted round-trip.
