# Plan-efficiency `seconds_per_task` is computed from wall-clock, so it grades operator idle time as agent cost

## Context

`references/plan-efficiency.md` § "Mandatory ratio computation" defines

```text
seconds_per_task = totals.duration_seconds / max(totals.tasks_completed, 1)
```

`totals.duration_seconds` is **wall-clock**: it includes every operator-gate wait,
infrastructure stall, and idle gap between phases. The Section 1 fallback threshold
(`seconds_per_task > 900` → warning) therefore grades a plan on how long a human took
to answer a gate, not on how much agent work the plan required.

The input needed to compute the ratio honestly already exists and is simply not used —
`metrics.md` separates **Worked / Reported (wall) / Idle** per phase.

## Proposed action

Compute `seconds_per_task` from the **worked** duration rather than wall-clock, using
the per-phase Worked figure `metrics.md` already reports. A ratio that fires on
operator response latency is measuring the wrong thing.

## Evidence — the ratio tripped on idle, not work, on four consecutive retrospectives

- first sighting — `seconds_per_task=1817.9`.
- `propagate-parallel-plan-hardening` (PR #977) — `seconds_per_task=4060`, dominated by
  a single ~7-hour operator escalation wait, not by agent work (worked-only: 1086s).

- `marker-detector-ownership-and-fixture` (PR #986) — `seconds_per_task=2324`, where
  6240s of the 18591s wall-clock was idle across five phase gates (worked: 7920s), on a
  plan with zero loop-backs and CI green first pass.
- `build-decision-oracle-consolidation` (PR #985) — `seconds_per_task=1478.67`, on a
  five-deliverable consolidation both the request and the routing-decisions posture
  verdict judged appropriately provisioned for its declared scope.

- `finalize-dispatch-audit-integrity` (PR #1026) — `seconds_per_task=6147.6`, where
  roughly 8h of the 15h22m wall-clock was one infrastructure stall plus operator-gate
  waits, against ~2h8m of recorded worked time across phases 2–5.

In every case the warning was spurious in its stated terms: the ratio fired on wait
time, so it carries no information about the plan's agent-side spend.

## Recurrence — 2026-08-03 (content-search-seam)

Sixth consecutive sighting. PR #1084, `seconds_per_task = 70744 / 7 = 10106` — the highest
recorded on this lesson, and again dominated by idle rather than work.

The 6-finalize wall window alone is 55,221s of the 70,744s total, and it contains a ~7.4-hour
overnight gap: the phase opened at `2026-08-02T22:44:39Z` and the next dispatch is
`2026-08-03T06:06:31Z`. Recorded worked time for phases 2–5 is 15,140s against 15,523s of
wall-clock for the same phases, so the plan's agent-side pace was in fact unremarkable; the
ratio's 11× exceedance of the 900s threshold is composed almost entirely of one operator sleep
cycle.

This sighting adds a second, independent defect on the same ratio: **`totals.duration_seconds`
has no honest value at all for 6-finalize, because that phase never closed its metrics
boundary.** `metrics.toon` carries `[6-finalize] start_time` with no `end_time`, so any
denominator for the phase is a live-clock reading taken at whatever moment the retrospective
happens to run — it would differ on every re-run of the same completed plan. The worked-duration
fix proposed above also resolves this, since `agent_duration_ms` accumulates per dispatch and
does not depend on the phase boundary being closed.

**Do not fix by clamping or by excluding long gaps heuristically.** The Worked figure is already
recorded per phase; the ratio simply needs to read it.

## Closed sibling concern — the calibration-anchors coverage gap

This lesson originally also recorded a calibration-anchors gap: `multi_module`, `broad`,
and `tech_debt` had no row on either axis of the `(scope_estimate, change_type)` table,
so those plans fell through to the Section 1 fallback ratios — which mis-graded cheap
plans as expensive and, in the PR #1026 sighting, flattened a genuinely over-budget plan
into the same output as an unremarkable one.

That half is **closed**. The table is now the exact cross-product of the two live axes,
with every pair either `anchored` or explicitly `fallback`-graded, and
`test/plan-marshall/plan-retrospective/test_plan_efficiency_anchors.py` re-derives both
axes from their owning sources and asserts set equality in both directions, so a new or
retired enum value cannot ship unreconciled. Only the `seconds_per_task` wall-clock
residual above remains open.
