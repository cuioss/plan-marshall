# The DPoP proof path must enforce the same key-binding checks as the access-token path, ideally through one shared check

## Problem

For JWKS keys the access-token path binds the JWS `alg` to the EC curve (`KeyProcessor` and `TokenSignatureValidator`: ES256 with P-256, ES384 with P-384, ES512 with P-521). The DPoP proof path only checked that `alg` was a supported algorithm and never compared it with the `crv` of the JWK embedded in the proof, so an ES384 proof with a P-256 key reached signature verification (plan-09, PR #851, found by CodeRabbit in a follow-up review). A DPoP proof carries its own key in the `jwk` header, so it is the less trusted of the two inputs, and a check that exists on the JWKS path but not on the DPoP path is a parity gap an attacker can choose.

## Solution

Every key-sanity check the token path applies to a JWKS key must also be applied to the key embedded in a DPoP proof: alg/curve binding, key type against alg family, minimum key size, and the ECDSA range check. When hardening one signature path, check the other for the same check and add a wired DPoP test per mismatch class. Prefer one shared check that both paths call, so they cannot drift apart. plan-09 added the alg/curve check to `DpopProofValidator` (rejecting with `DPOP_PROOF_INVALID` and a message naming the mismatch) and moved the range check into `SignatureVerificationUtil.verifySignature`, which both paths already share.

## Impact

Without parity, hardening one path leaves the same weakness reachable through the other, and the second path is the one fed by the caller's own key material.
