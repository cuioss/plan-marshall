# A fix is the highest-risk moment in the pipeline: mandate a named adversarial self-re-read of every fix's own diff

## Observation

Across a single plan's review cycle (`orchestrator-inbox-pickup`), four
independent findings across two review sources were traced to the SAME root
cause: **the fix for the immediately-preceding finding introduced the next
one.**

- Self-review round R3's finding was introduced by R2's fix.
- Self-review round R5's finding was introduced by R4's fix.
- CodeRabbit round R2's two findings were both introduced by the R1 fix (an
  atomic-claim rewrite).
- CodeRabbit round R4's `_section` finding was introduced by the helper added
  to fix R1's vacuous guard.

In every case, the finding that started the chain was resolved correctly and
completely on its own terms — the regression was not carelessness in
addressing the original finding, it was a NEW defect the corrective code
introduced while doing so. The chain broke, twice, specifically at the point
an explicit adversarial re-read of the fix's own diff was performed — asking
"does this new code have an unhandled interleaving, an escaping exception
path, or an ordering bug?" — and that re-read only happened because it was
named explicitly in that dispatch's prompt. Nothing in the standard review
flow currently REQUIRES it.

## Why it matters

A fix is not a neutral event in a review pipeline — it is the highest-risk
moment. The code most likely to contain the pipeline's NEXT defect is the
code just written to remove its LAST one: it is freshly-written, has had the
least scrutiny of anything in the diff, and is being added under the
cognitive framing of "solving problem X," which narrows attention away from
whatever new problem the solution itself might introduce. A review loop that
treats "the finding is fixed" as the terminating condition, without a
distinct verification pass over the fix's OWN diff, is structurally exposed
to exactly this chain — and a multi-round review (self-review AND
automated-review loop-back alike) can cycle through several such
fix-introduces-defect rounds before anyone runs the adversarial pass that
actually catches it.

This generalizes past this plan's specific findings. Any code-review or
self-review workflow that iterates fix -> re-check -> fix -> re-check is
vulnerable: the "re-check" step commonly re-verifies that the ORIGINAL
complaint is resolved, not that the FIX itself is clean. Those are different
claims, and only the second one closes the loop.

## Rule

After every fix — whether produced by self-review's own internal loop or by
automated-review's fix-and-loop-back cycle — run a **named, mandatory**
adversarial re-read of the fix's own diff (not the original finding) before
accepting it as done. The re-read asks, specifically, of the new/changed
code:

1. Does it introduce an unhandled interleaving (a check-then-act window, a
   race between two async paths, an ordering assumption the surrounding code
   does not guarantee)?
2. Does it introduce an escaping exception path (a new code path that can
   raise where the surrounding contract promises it cannot, or that
   swallows/misclassifies an error the caller needs to see)?
3. Does it introduce an ordering bug (a boundary/threshold comparison, a
   loop-termination condition, or a sequencing assumption that is correct
   for the motivating case but wrong for an adjacent one)?

This is a distinct pass from "verify the original finding is resolved" and
must not be skipped or folded implicitly into that verification — the whole
point of this lesson is that the implicit expectation does not reliably
fire. `pm-plugin-development:ext-self-review-plan-marshall` and
`plan-marshall:automatic-review`'s loop-back re-review are the two loci
where a fix's diff is produced and then re-checked; both should treat "a fix
was just applied" as a trigger for this specific adversarial pass, not only
for re-verifying the finding it was meant to resolve.
