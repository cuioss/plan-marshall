# PLAN-LB-14: The launch gate judges each candidate against the plans that can collide with it

## Objective

The orchestrator's `next` verb admits a staged plan only when `corpus cross-check` reports `candidate_comparison_determinate: true`, and that field is true only when every spec of every other epic, plus every live plan, declares a comparable file surface. One spec anywhere without one — a shipped plan's spec written as prose, a retired plan's, a spec in an epic closed long ago — makes the field false for the whole epic, so `next` refuses every candidate and each launch needs an operator override. An override that is always needed protects nothing. This plan makes the verdict per candidate and computes it over the plans that can actually run at the same time: specs whose queue row is terminal, and specs of closed or archived epics, are not gate candidates at all; an in-flight plan with no known surface still blocks, because that is a comparison that never happened. The rule "an unchecked negative is never a clean pass" (ADR-019) stays in force and is stated per candidate instead of once per store. No earlier spec covers this.

## Deliverables

1. **The gate compares against in-flight work only, and says what it left out.** `cmd_corpus_cross_check` derives a gate population beside the existing scan population. A sibling spec is a gate candidate only when its epic is active (present in the active store root and its `status.json` `phase` is not `closed`) and its queue row status is not in `TERMINAL_PLAN_STATUSES`; the decision in the verify-first clause below settles which of the live statuses (`staged`, `launched`, `running`, `parked`) count as able to collide. Live plans stay gate candidates as today. Every exclusion is published as a stated count per reason on every successful call (for example `gate_excluded[]{reason,count}` over `row_terminal`, `epic_closed`, `epic_archived`, and the not-in-flight reason if the decision adopts one), computed from the declared vocabularies so a reason with no member reports zero. Anything that cannot be read stays in: an unreadable or missing queue row, a row status outside `VALID_STATUS_VOCABULARY`, an unreadable epic `status.json` or a missing `phase` all keep the spec a gate candidate. The duplicate-work direction is unchanged: `source_origin_matches[]` and `file_overlap_matches[]` are still computed over the full scan population, archived epics included, because `cleanup` uses them to find duplicated work, which a shipped plan can still be. *Done when:* a test with a sibling epic holding one prose-surface spec whose row is `shipped` reports that spec under `row_terminal` and not as a gate-blocking candidate; the same spec with an unreadable row file is still gate-blocking; a spec in an epic at `phase: closed`, and one under the archived root, are each reported under their reason; `file_overlap_matches[]` for a comparable shipped sibling spec is byte-identical before and after.

2. **The verdict is per candidate spec.** The payload gains one row per own spec — for example `spec_comparisons[]{spec,comparison_determinate,blocking_candidate_count,blocking_candidates,reason}` — where a blocking candidate is a gate candidate (D1) whose surface is not comparable (`indeterminate` or `unreadable`), together with any other own spec at a non-terminal status that is not comparable. The `reason` is derived in the script from the blocking rows, naming kind, name and state, as `_candidate_indeterminate_reason` does today. The existing epic-wide `candidate_comparison_determinate` and `candidate_indeterminate_reason` stay in the payload and become the roll-up of the per-spec rows over the gate population (true only when every row is true), so a consumer reading the old field is never told "determinate" when a row says otherwise. *Done when:* a test with one in-flight indeterminate sibling shows every own spec row `comparison_determinate: false` naming that sibling; a test where the only indeterminate siblings are terminal or in closed epics shows every row `true` and the roll-up `true`; a property test asserts the roll-up equals the conjunction of the rows and that `reason` is empty exactly when the row is `true`.

3. **A live plan with no captured footprint is compared through its source spec.** A real active plan whose `references.json` `affected_files` is empty is today always indeterminate, and every plan is in that state between launch and outline. When the plan's `source_id` pointer resolves to a spec whose surface is `declarative`, use that spec's resolved paths as the plan's comparison surface, publish which source was used (`surface_source: affected_files | source_spec | none`), and compute overlap rows from it. A plan whose source resolves to no spec, or to a non-declarative one, stays indeterminate and blocks. *Done when:* a test with a pre-footprint live plan launched from a declarative spec reports it comparable with `surface_source: source_spec` and yields an overlap row against an own spec sharing a path; a test with a pre-footprint plan and no resolvable source spec keeps `live_indeterminate_plans[]` naming it and every own spec row `false`.

4. **`next` reads the per-candidate row, and the documents state the new contract.** In `workflow/orchestrate.md` Step 4 the third conjunct becomes "the candidate's own `spec_comparisons[]` row carries `comparison_determinate: true`", joined by the same `PLAN-NN-` prefix rule as the other two conjuncts; the shortfall reason for a refused candidate is that row's `reason`, transcribed. The return template forwards the gate-exclusion counts beside the candidate tallies. `persona-plan-orchestrator/standards/orchestration-model.md` § "The gate's reading contract" states which specs are gate candidates, what stays fail-closed, and that exclusion is reported, never silent. `plan-orchestrator/SKILL.md` § Canonical invocations → `corpus cross-check` documents the new keys and corrects the sentence that says the verdict is true "only when the WHOLE candidate population was comparable". *Done when:* the doc-contract tests for the Step 4 admission rule and for the `corpus cross-check` payload keys pass against the amended documents, and no document under `plan-orchestrator/` or `persona-plan-orchestrator/` still describes the third conjunct as a whole-population verdict.

5. **A regression fixture shaped like the observed store.** One test builds a store with nine sibling epics, eight at `phase: closed`, 179 sibling specs of which six are non-comparable (five on terminal rows, one `staged` in the active epic) and one comparable live plan, runs `corpus cross-check` for an epic with two declarative staged specs, and asserts the outcome the decision below fixes: under the recommended rule both own specs are determinate with the exclusions counted by reason. A second test flips the one active-epic spec's row to `launched` and asserts both own specs are refused naming it. *Done when:* both tests pass, and the first fails against the current handler with `candidate_comparison_determinate: false`.
