# Lesson-conversion plans predictably trip the refine-phase narrative_vs_code_validator Q-Gate because the source lesson captured an already-fixed defect; the stale-narrative finding is expected, resolve taken_into_account and extract only the generalizable residue

When a plan is created from a lesson via the lesson-conversion path
(`convert-to-plan` / `/plan-marshall lesson=...`), the plan's `request.md`
embeds the source lesson's narrative verbatim. If that lesson captured an
**in-run-fixed "slipped-then-caught" defect** — the highest-value lesson class
(see `2026-06-20-12-001`) — the narrative necessarily cites code patterns that
were **already corrected in-run** by the originating plan, before the lesson was
even authored. The refine-phase `narrative_vs_code_validator` Q-Gate then
**predictably fires a stale-narrative finding** for each such citation, because
the cited pattern no longer exists in the live tree.

This is expected, not a defect. The correct disposition is
`taken_into_account`: confirm the cited code is already fixed, then extract and
ship only the **generalizable residue** (the carve-out refinement, the authoring
discipline, the contract change) — never re-fix the already-corrected code.

## Where it surfaced

While shipping `simplify-self-review-must-remove-exception-swallow` (a
lesson-conversion plan sourced from `2026-06-14-08-001`, `2026-06-20-17-005`, and
`2026-06-20-17-006`), the phase-2-refine Q-Gate raised **three**
`narrative_vs_code_validator` findings, all resolved `taken_into_account`:

- `729760` — the `2026-06-14-08-001` narrative said the `_run_spec` test fixture
  in `test/pm-plugin-development/plugin-doctor/_fixtures.py` wraps the analyzer
  call in `except Exception`. Current code: the guard was already removed in-run
  (PR #669). Actionable residue: the `required-vs-speculative` carve-out in
  `code-organization.md` still lacked a test-layer (should-fail-loudly)
  restriction — that refinement shipped (TASK-1). The cited guard was NOT
  re-touched.
- `156749` — sub-task `2026-06-20-17-005` cited two stale count-prose sites
  (`pre-submission-self-review.md:187` "these four checks", now five;
  `ext-point-self-review-surfacing.md:172` "seventeen", now eighteen). Current
  code: both already correct (fixed in-run, PR #728). The lesson's value was
  codifying the count-prose-sweep discipline, not re-fixing the sites.
- `d1650c` — sub-task `2026-06-20-17-006` cited two ordinal-reference parser bugs
  in `self_review.py` (blank-line lookahead, first-match block resolution). The
  lesson itself states "Both were fixed in-run". Current production code is
  correct. The lesson's value is its authoring guidance (enumerate messy-document
  edge cases before authoring a structural parser), not a code fix.

All three were correctly resolved `taken_into_account` at outline time, and only
the one genuinely-actionable residue (the carve-out refinement) became a code
deliverable. The plan shipped clean.

## Root cause

The lesson-conversion path is deliberately faithful: it carries the source
lesson's narrative into the new plan's request so the plan has full context. But
the most valuable lessons document defects that were **caught and fixed within
the same run** — so by construction their narrative describes a code state that
the originating plan already moved past. The `narrative_vs_code_validator` is
working as designed when it flags the mismatch; the mismatch is intrinsic to the
in-run-fixed lesson class, not evidence of a wrong narrative or wrong code.

Symptom signature:

- The plan was created from a lesson (`request.md` `source` is a lesson id, or
  carries `consolidated_lessons` / `consolidated_from` sections).
- The source lesson(s) describe an in-run-fixed / "slipped-then-caught" defect
  ("fixed in-run", "the step recorded outcome=done with zero outstanding
  comments", a resolved-in-run Q-Gate or pr-comment finding).
- phase-2-refine raises one or more `narrative_vs_code_validator` Q-Gate findings
  whose `detail` says the cited pattern is "already removed / already correct in
  current code".

## How to apply

- **Treat a refine-phase `narrative_vs_code_validator` finding on a
  lesson-conversion plan as expected, not as a defect to debug.** When the
  finding's detail confirms the cited code is already fixed, the disposition is
  `taken_into_account` — record that the narrative is faithfully stale and move
  on. Do NOT re-fix the already-corrected code, and do NOT treat the stale
  narrative as a reason to abandon or rewrite the request.
- **Extract the generalizable residue, not the cited instance.** An in-run-fixed
  lesson's durable value is its *discipline* — the carve-out refinement, the
  authoring rule, the contract change that prevents the class — not the specific
  already-patched line it cites. Scope the plan's deliverables to that residue.
- **Sanity-check that residue still exists before scoping a deliverable around
  it.** Confirm the generalizable fix is genuinely absent in the live tree (here:
  the carve-out lacked the test-layer restriction) — that is the one part of the
  narrative that IS still actionable, distinct from the cited-but-already-fixed
  instance. This is the verify-the-target discipline of `2026-06-21-02-001`
  applied to lesson-conversion: confirm what is still missing vs what was already
  shipped.
- **The Q-Gate count is a stale-narrative count for these plans, not a defect
  count.** When the lessons-capture Signal Gate reports a non-zero
  `signal_qgate_pending_count` on a lesson-conversion plan, expect the underlying
  findings to be `taken_into_account` stale-narrative confirmations rather than
  pending defects — read the resolution before treating the count as a problem.

## Impact

Bounded: the three findings here were all resolved cleanly and the plan shipped.
But the pattern is inherent to **every** lesson-conversion plan whose source
lesson documents an in-run-fixed defect — the most common high-value class — so
each such plan will predictably surface this stale-narrative Q-Gate noise. Naming
the pattern keeps the refine/outline disposition fast and correct
(`taken_into_account` + extract residue) instead of re-investigating an
already-fixed citation or, worse, re-fixing code that is already correct.
