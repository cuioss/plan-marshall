# Normative worked-examples are a semantic-correctness surface structural self-review misses — verify each example in an authored standard actually models the discipline it preaches

When a plan authors or rewords **normative guidance** — a standard, a Core-Development-Principle
section, a discipline rule — the *worked examples* inside that guidance are a first-class
correctness surface. One narrow class of it is now gated: a clause carrying a fenced BAD/GOOD
contrast pair whose GOOD half branches on a recoverable predicate is adjudicated by the
pre-submission self-review's worked-example clause-mismatch check. Everything outside that shape
remains ungated — a prose example, an illustrating command, a clause with no contrast pair, a
clause naming no normative predicate, or a GOOD half with no recoverable branch predicate. For
those, neither self-review nor plugin-doctor evaluates semantic soundness: they check symmetric
pairs, regex overfit, wording, duplication, and contract drift — structural properties. They do
not evaluate whether a normative claim or its illustrating command is *logically valid*.

## The slipped-then-caught instance (plan docs-contract-consistency, PR #930)

This plan promoted a diagnosis-discipline standard into
`persona-plan-marshall-agent/standards/agent-behavior-rules.md` whose whole premise is "verify a
signal against ground truth, never explain it away." The first draft's own example told agents to
run `git log origin/main..HEAD -- <failing-test-file>` and treat the result as evidence about
whether the check was green on `main`.

That is unsound, and it is self-referential: a standard about verifying against ground truth
shipped an example that modeled an *unsound* ground-truth check.

- `git log origin/main..HEAD -- <file>` establishes **provenance** only — whether the branch
  *touched* the file. It CANNOT establish that the exact check *passed* on `origin/main`.
- A green-baseline determination requires an **actual result**: run the exact failing check at the
  merge base, or read a trusted-CI baseline. Git history is supplementary provenance evidence, not
  a baseline oracle.

In-house gates (pre-submission self-review "clean: 8 candidates examined"; plugin-doctor "clean:
whole-tree 29 rules, 0 issues") all passed the draft. The external review bot (CodeRabbit) caught
it as a Major functional-correctness issue, and TASK-4 reworded the standard to require a verified
baseline. The corrected git-log-vs-baseline wording now lives in the standard itself — this lesson
is about the *verification gap*, not that wording.

## Corrective

For any plan whose deliverables **author or reword normative prose** (standards, principles,
agent-behavior rules, discipline sections):

1. Treat every worked example / illustrating command as a semantic-review target, not just a
   wording/structure target. Outside the fenced BAD/GOOD contrast-pair shape the self-review's
   worked-example check adjudicates, structural self-review will pass it clean regardless of
   whether it is logically sound.
2. Cross-check each example against the very rule it illustrates — a "verify against ground truth"
   rule whose example does not itself verify against ground truth is a defect no gate sees unless
   the example happens to be a fenced BAD/GOOD contrast pair with a recoverable branch predicate.
3. Specifically for provenance/diff-vs-main diagnosis guidance: a branch-range git command
   (`git log origin/main..HEAD -- <file>`) proves the branch *touched* something; it never proves
   a check *passed* on `main`. Require a real baseline result for any "is main green?" claim.

## Impact

Applies to every standard-authoring or principle-authoring change in this meta-project. The
structural self-review gate is necessary but not sufficient for normative content; the semantic
validity of examples must be reviewed deliberately (or left for the external review bot to catch
post-push, which costs a loop-back).

## Recurrence — 2026-07-21 (orchestrator-dispatch-ruleset)

Same class, sharper variant: the authored worked example was an instance of a **contract
another document owns**, and it was got wrong **three times in one plan** before it was
right.

The plan added a new rule section documenting the canonical `Task:` dispatch form. The
example dispatch block inside that section is not free prose — it is an instance of the
`execution-context` prompt-body contract, which `execution-context.md` owns normatively.
It was hand-written rather than derived from the owning contract, and each gate caught a
different defect in the *same* few lines:

1. **Q-Gate at 3-outline** (`eba657`, error severity) — the canonical dispatch form
   contradicted the `execution-context` prompt-body contract.
2. **The fix for (1)** was itself hand-patched against the reviewer's comment rather than
   re-derived from `execution-context.md`, so it re-shipped malformed.
3. **CodeRabbit, post-push** — two inline findings on that same new section, one of them
   `skills[0]: []`, a notation that mixes a TOON array-length index with an empty-list
   literal and is valid under neither reading. Both confirmed real; fixed via loop-back
   TASK-005.

A second Q-Gate error in the same pass (`0de711`) has the same shape one level up: a
non-adoption rationale that **misread the `agents.md` standard it cited**. Both defects are
"authored prose asserts something about a document it references, without reading that
document as the authority."

### Corrective (extends the three corrective points above)

4. **An example that instantiates a contract owned elsewhere must be derived from the
   owning doc, not composed from memory.** Before authoring a dispatch block, a prompt
   body, a config fragment, or a CLI invocation into a standard, open the owning contract
   (`execution-context.md`, the skill's `## Canonical invocations`, the schema) and copy
   its field set, ordering, and literal notation. "It reads plausibly and matches the
   surrounding prose" is exactly the failure mode — all three defects here read fine in
   context.
5. **Likewise for any claim *about* a referenced standard.** If authored prose says "we do
   not adopt X because `standard.md` says Y", read `standard.md` and quote it. A
   paraphrase-from-memory of a cross-referenced standard is the same unverified-assertion
   defect as an unverified example.
6. **When a gate flags an example once, re-derive the whole example — never patch the
   flagged line.** This is the mechanism that let strike 3 through: the Q-Gate finding was
   treated as a spot correction, so the *rest* of the hand-written block kept its original
   unverified provenance. One finding against an authored contract-instance should
   invalidate the entire instance.

### Recurrence signature

Three or more independent catches (Q-Gate, self-review, external bot) landing on the *same*
authored block across a single plan. That clustering is not bad luck — it is the signature
of a block whose provenance was never the owning contract, and each catch only removes one
visible symptom of that.
