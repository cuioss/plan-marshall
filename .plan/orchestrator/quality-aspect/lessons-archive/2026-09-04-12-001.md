# Manifest step-params snapshot is stale for any knob the plan's own deliverable writes, and reconcile cannot see it

## Context

`phase-4-plan` composes `execution.toon` by snapshotting each finalize step's params out of `marshal.json`. `automatic-review` then reads `required_bots` / `optional_bots` off **that snapshot**, not off live `marshal.json` — `automatic-review/SKILL.md` says so explicitly at both read sites (the `fetch_findings` classification read and the `review_completeness` quorum read).

That is fine for a knob nobody changes mid-plan. It is not fine for a knob the plan's own deliverable writes.

## What went wrong

Plan `unreviewed-merge-gate-holes` had a deliverable whose whole point was promoting CodeRabbit to a required reviewer. During `5-execute` it set, in `marshal.json`:

- `required_bots: coderabbit,cuioss-review-bot`
- `optional_bots: sourcery`

The manifest snapshot, composed back at `4-plan`, still carried the pre-change split:

- `required_bots: cuioss-review-bot`
- `optional_bots: coderabbit,sourcery`

Left alone, `phase-6-finalize`'s `automatic-review` would have read the snapshot and treated CodeRabbit as **optional** — its silence non-blocking — on the very PR that introduces the rule making it required. The deliverable would have shipped while being disabled for its own change, and the operator's standing rule (CodeRabbit is a required reviewer, never moved to `optional_bots` to clear a blocked gate) would have been inverted by omission rather than by decision.

## Why the existing guard did not catch it

`manage-execution-manifest reconcile` reconciles the frozen `phase_6.steps` **list** against live `marshal.json`. On this plan it reported `reconciled: false`, `stale[0]`, `broken[0]` — a clean bill — because the step list genuinely had not changed. Only the params *inside* a step changed, and the verb does not look there. The clean result actively reassures the reader that the manifest agrees with config when one of its dimensions does not.

## Remedy applied

Two targeted writes, after which both surfaces agreed:

```bash
python3 .plan/execute-script.py plan-marshall:manage-execution-manifest:manage-execution-manifest step-params set \
  --plan-id {plan_id} --phase 6-finalize --step-id plan-marshall:automatic-review \
  --param required_bots --value "coderabbit,cuioss-review-bot"
```

(and the matching `optional_bots` write).

## Structural remedies worth considering

1. **Extend `reconcile` to the params dimension** — diff each snapshotted `step_params` object against live `marshal.json` and report divergence, so the verb's clean result means the whole manifest agrees rather than only its step list.
2. **Re-snapshot on declared writes** — when a deliverable declares it will write a config knob, have `5-execute` re-snapshot that step's params at phase exit.

Of the two, (1) is the more valuable: it turns a silent divergence into a reported one for every knob, not only the ones a deliverable remembered to declare.

## Detection heuristic

Whenever a plan's deliverable writes `marshal.json`, check whether any finalize step consumes the same knob through the manifest snapshot before entering `6-finalize`. The read sites are greppable — a step reading a knob "off the execution-manifest step-params snapshot" is the signature.

## Recurrence — 2026-09-04, plan `domain-glob-seeding` (PR #1406)

**Same step, same knob, second pathway — and this one defeats the detection heuristic above.**

Roughly two hours after the instance recorded above, plan `domain-glob-seeding` hit the identical
divergence on the identical step and knob: `plan-marshall:automatic-review`, `required_bots`. Its
frozen manifest snapshot carried `required_bots: pr-agent`; live `marshal.json` carried
`cuioss-review-bot`.

The trigger was **not** the plan's own deliverable. Commit `cc5ea40a1` (PR #1392,
*"feat(automatic-review): flag unknown bot-kind tokens; rename pr-agent"*) renamed the token on
`main`, and this plan **absorbed that commit through the finalize rebase**
(`finalize-step-sync-baseline`: "rebased onto origin/main, 2 upstream commit(s)"; `decision.log`
`10:20:36Z` records the semantic re-verify against `cc5ea40a1`). Live config moved with the
rebase; the snapshot, composed at `4-plan` against a pre-rename `main`, did not.

The consequence surfaced at `12:59:47Z` as an `unregistered_kind` warning — *"configured
reviewer token 'pr-agent' matches no registered bot kind"* — with the corrective at `13:02:18Z`
applying the same `step-params set` remedy this lesson already prescribes. The bot stayed
required; no demotion to `optional_bots`.

**What this adds:**

1. **The detection heuristic is insufficient.** It keys on "a plan's deliverable writes
   `marshal.json`". Here no deliverable wrote anything — an upstream commit did, and the plan
   merely absorbed it. Any plan that rebases onto a `main` carrying a config change inherits a
   stale snapshot with no local write to notice. Widen the heuristic: **every** `finalize-step-sync-baseline`
   rebase that absorbs commits is a step-params staleness event, whatever the plan itself wrote.

2. **This strengthens the case for structural remedy (1) over (2).** Re-snapshotting on *declared*
   writes cannot help here — there was no declared write to hang the trigger on. Extending
   `reconcile` to the params dimension covers both pathways, because it compares state rather
   than tracking causes. On this plan `reconcile` would again have reported the step list clean.

3. **The invariant record saw the drift and could not connect it.** `handshakes.toon` recorded
   `main_sha` drift at two phase boundaries (`2-refine`→`3-outline`, `3-outline`→`4-plan`) and the
   `summarize-invariants` aspect raised warnings for both. But `main_sha` drift is reported as a
   fact about a SHA, with nothing linking it to the frozen params that SHA invalidated — and the
   finalize-time rebase, which is the drift that actually mattered here, is captured by no
   invariant at all.

## Recurrence — 2026-09-04, plan `plan-145-publish-the-missing-parser-seams` (PR #1395)

**Third instance, same step, same knob, same rebase-absorption pathway** — and
therefore the second consecutive one the detection heuristic cannot see.

This plan's frozen `phase_6.step_params["automatic-review"]` again named
`pr-agent` after commit `cc5ea40a1` (the `pr-agent` → `cuioss-review-bot`
rename) landed in **this branch's own rebase base**. No deliverable of this plan
wrote `marshal.json`; the plan shipped three test files. The dispatcher caught
and corrected the token mid-run.

Two things this third instance settles:

1. **It is not a coincidence of one epic.** Three plans in roughly one day hit
   the identical divergence on the identical `automatic-review.required_bots`
   knob, two of them purely by absorbing an upstream commit. Any plan whose
   finalize rebases onto a `main` carrying a config change inherits a stale
   snapshot, so the exposure is proportional to how long a plan sits between
   `4-plan` and `6-finalize` — and this plan sat for **96 hours** in `4-plan`
   alone.
2. **Structural remedy (1) is the only one that would have worked.** Confirmed
   for a second time from the opposite direction: there was again no declared
   write to trigger re-snapshotting on, and `reconcile` would again have
   reported the step list clean while the params dimension diverged.

The residual risk is the one the parent lesson names: this run's stale value was
caught by an agent noticing the token, not by any gate. A rebase-absorbed
staleness that happens to leave a *plausible* value in place would still ship
silently.

## Evidence (recurrence)

- `execution.toon` `phase_6.step_params["automatic-review"]` vs live `marshal.json` after the finalize rebase
- `4-plan` wall duration 96h6m against 9m5s worked — the snapshot-to-consumption gap this exposure scales with
- Prior instances: `unreviewed-merge-gate-holes` (deliverable-written), `domain-glob-seeding` PR #1406 (rebase-absorbed)
