# Footprint path-to-module classifier feeding build-target selection must fail safe at every boundary AND derive ownership from the whole footprint (nest-inside guard, empty-scope to whole-tree fallback, no build-relevance pre-filter)

When a footprint (changed-file set) is mapped to a set of modules that then
selects a build/test target, the classifier must **fail safe at every path
boundary**. In the scoped-vs-whole-tree module-tests divergence gate
(`_test_scope_divergence.py`), two boundary defects shipped in the initial
implementation and were caught by PR review bots (gemini + coderabbit,
high/functional-correctness) rather than by the in-run build or the initial
unit tests:

1. **Shallow/root-level paths were misclassified as module names.** The path→module
   helper extracted a segment whenever `len(segments) > 1` (for `test/…`) or
   `> 2` (for `marketplace/bundles/…`). A root-level file such as
   `test/conftest.py` has exactly two segments, so `'conftest.py'` was
   returned as a bogus "module" and polluted `scoped_modules`. A file only
   *belongs* to a module when it nests **inside** that module's directory, so
   the guard must require one more segment (`> 2` / `> 3` respectively) and
   return `None` for anything shallower.

2. **An empty module set produced an invalid target instead of falling back to
   whole-tree.** When the footprint held build-relevant files (e.g.
   `pyproject.toml`) that map to no specific module, `scoped_modules` came out
   empty, which drove `divergence_possible = False` and
   `recommended_target = None` — the gate would then run the invalid command
   `module-tests None`. The correct behaviour is to track whether any
   build-relevant file matched, and force `divergence_possible = True` (→
   whole-tree) when relevant files matched but resolved to zero modules.

## Root cause

A path→module classifier that feeds target selection has two failure
directions that are NOT symmetric: over-classifying (naming a non-module) and
under-classifying (empty set). Both must resolve toward the *safe* target —
"no module here" for a single path, and "run the whole tree" for an empty
overall set. The initial implementation handled the common nested case and
left both boundaries to produce silently-wrong output: a fake module name, or
an unrunnable `None` target.

## Corrective rule

When building any footprint/path → module → build-target resolver:

- **Nest-inside guard**: only extract a module name when the path extends
  *inside* the module directory (segment count strictly greater than the
  prefix depth); every shallower or root-level path resolves to no module.
- **Empty-scope fail-safe**: if build-relevant files matched but resolved to
  zero modules, escalate to whole-tree — never emit a scoped target that is
  empty/`None`. Distinguish "no relevant files touched" (nothing to run) from
  "relevant files touched but unmapped" (must run whole-tree).
- **Unit-test the boundaries explicitly**: add cases for a root-level file
  (`test/conftest.py`), a build-relevant-but-module-less file
  (`pyproject.toml`), and the shared-infra path, asserting the safe target —
  not just the happy nested-module path. The initial tests here covered only
  the nested case, which is exactly why the boundary bugs reached review.

## Recurrence — 2026-07-27 (finalize-dispatch-audit-integrity)

A third failure direction in the same resolver (`resolve_test_scope` in
`_test_scope_divergence.py`), this one **upstream of** the boundary guards
above: the footprint was narrowed by a filter that answers a *different
question* before ownership was derived at all.

`resolve_test_scope` derived a path's owning module only inside the
`if any(fnmatch(path, glob) for glob in build_map_globs):` branch. The
`build.map` globs answer **"is this file build-relevant"** (does it trigger a
compile/test run). Module ownership answers the different question **"could a
scoped run miss a regression"**. Because the globs match only `*.py`, a
cross-bundle change whose second bundle is reached solely through a `.md` file
— a rule catalogue, a roster document, a schema doc that that bundle's tests
assert on — contributed **no** module. This plan's own two-bundle footprint
resolved to a single module, which would have driven
`divergence_possible = False` and scoped the module-tests gate away from the
very bundle whose tests assert on the changed file. Neither guard above fires:
the set is non-empty and every member is a real nested module — it is simply
the *wrong* set, silently narrower than the truth.

The fix hoists the `_module_for_path` call out of the glob branch: the globs
now set only `has_matching_files` (build relevance), while module ownership is
derived from **every** footprint entry.

### Added corrective rule

- **One question per filter — never narrow a derivation's input population
  with a predicate that answers a different question.** Before reusing an
  existing filter as a pre-pass, state in one sentence what that filter
  decides and what the derivation downstream of it decides. If the two
  sentences are not the same question, the filter belongs on a sibling output
  (a separate flag), not on the derivation's input. Under-scoping produced
  this way is invisible to boundary tests: the resulting set is well-formed,
  non-empty, and wrong. Test it with a footprint whose cross-module reach is
  carried by a file class the filter *rejects* (here: a `.md` file under a
  second bundle) and assert the module span, not just the target's validity.
