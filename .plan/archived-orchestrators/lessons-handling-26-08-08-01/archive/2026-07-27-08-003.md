# A success criterion that rests on pre-existing test coverage must locate that coverage at authoring time, or the criterion is unmeetable and the change ships unsubstantiated

## Observation

On plan `retrospective-checker-assertion-integrity`, TASK-2 step 2 instructed the
executor to

> "confirm the existing `extract_deliverables` coverage still passes unchanged,
> which is what substantiates the `split_deliverable_blocks` extraction as
> behaviour-preserving"

No such coverage existed. `extract_deliverables` had **zero references anywhere
under `test/`**. The clause that was supposed to carry the entire
behaviour-preservation argument for the refactor pointed at nothing.

Deliverable 1's Success Criterion was therefore unmeetable as written, and the
extraction shipped with no evidence that it preserved behaviour. The executor
logged the gap rather than quietly marking the step done — the correct response,
and the only reason this surfaced at all. It was closed within the plan by an
operator-directed fix task (TASK-4), but the authoring-side defect is the
reusable part.

## The defect

An outline/task authored a mandate that **asserted the existence of a
verification artifact it never checked for**, and then leaned the deliverable's
entire correctness argument on that assertion.

The distinguishing feature is *what* the unverified assertion was about. The
existing outline-authoring lessons are all about the **edit target**: the symbol
was removed (`2026-06-21-02-001`), the work was already done, the path is
gitignored, the declared set is incomplete (`2026-07-21-17-004`). Every one of
those fails **loudly at execute** — the executor cannot perform the edit and
returns `infeasible`, which is a clean, attributable signal.

This one is about the **verification substrate**, and it fails *quietly*:

- The edit itself is perfectly performable. `split_deliverable_blocks` extracts
  cleanly.
- The task can run green end to end. Nothing errors.
- The only thing that does not exist is the evidence, and absent evidence
  produces no error — it produces a step that passes while proving nothing.

A refactor justified as "behaviour-preserving because the existing tests still
pass" is exactly as strong as those tests. When there are none, the phrase
"still passes unchanged" is *trivially true* (vacuously: no test changed
because no test exists) and reads as green. That is the whole failure mode:
**the criterion cannot fail, so it cannot verify.**

## Root cause

Authoring wrote "the existing coverage" from a plausible assumption that a
public-ish helper in a well-tested module must be covered, and never spent the
one search that would have refuted it. Coverage existence is precisely the kind
of claim that feels safe to assume and is cheap to check — which is why it gets
assumed.

Structurally, this is a premise inherited into the deliverable with no
provenance and no discharge, the same class `2026-07-21-17-004` § "Proposed
action 2" names for premises inherited from consumed artifacts — but here the
premise was self-generated by the outline rather than inherited, and its subject
is the test tree rather than the source tree.

## How to apply

1. **Locate the coverage before citing it.** When a deliverable, success
   criterion, or task step justifies a change by appealing to *existing* tests
   ("the existing X coverage still passes", "covered by the current suite", "no
   new tests needed — behaviour-preserving"), the authoring pass MUST resolve
   that claim to concrete test files/functions and name them in the criterion.
   One `architecture find --pattern {symbol}` or a `test/` scan is the entire
   cost. A symbol with zero test references cannot be the basis of a
   behaviour-preservation argument.

2. **Name the coverage, do not gesture at it.** `"the existing
   extract_deliverables coverage"` is unfalsifiable prose. `"test/plan-marshall/
   .../test_extract_deliverables.py::test_multi_block"` is checkable by anyone
   reading the criterion, and its absence is immediately visible.

3. **No coverage found → the deliverable owes a characterization test, not a
   softer criterion.** The remediation is to add the pinning test *before* the
   extraction (so it demonstrably passes pre- and post-refactor), not to reword
   the criterion into something weaker that the existing state happens to
   satisfy. Rewording is how an unsubstantiated change ships looking green.

4. **Treat "behaviour-preserving refactor" as a claim requiring a named
   discriminator.** It is the single most common criterion shape that carries no
   verification of its own. Pair it with the specific test that would fail if
   behaviour changed — which is the same discipline `2026-07-16-17-004` demands
   of fix-recipe tests (prove the test discriminates), applied one phase earlier
   to the criterion that cites it.

## Signature

An executor reporting "the coverage this step references does not exist" — or,
far worse, a step marked done whose success criterion contains the words
"existing coverage"/"still passes" with no test path anywhere in the
deliverable. The second form is the one that ships.
