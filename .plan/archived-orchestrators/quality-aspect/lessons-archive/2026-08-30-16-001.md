# consult resolves the plan directory main-anchored, returning a false outline_not_found under the cwd-pinned worktree model

## Observed

During a phase-3-outline dispatch running **inside a materialized worktree** (cwd pinned to the
worktree root per ADR-002), `manage-lessons consult` returned `outline_not_found` even though
`solution_outline.md` existed and was readable at the cwd-relative path.

Observed in plan `plan-170-make-the-attribution-usable`, whose phase was rewound `5-execute` →
`3-outline` for a baseline-drift re-grounding while the worktree stayed materialized.

## Cause

`consult` resolves the plan directory **main-anchored**. Under the move-based model (ADR-002) the
plan directory has been MOVED into the worktree at phase-5 entry, so during phase-5+ there is no
plan directory on main at all. The verb therefore looks where the outline structurally cannot be.

## Why it matters

The failure is a **false negative that degrades silently**. `outline_not_found` reads as "this plan
has no outline to consult", not as "the store resolver looked in the wrong tree", so a caller can
discharge — or believe it discharged — its lessons-consult obligation against an empty result.
In the observed run the correct answer was one active matching lesson (`2026-08-25-09-016`), not
zero; an outline that trusted `surfaced_count: 0` would have recorded a clean consult that never
happened.

Any phase re-entered while the worktree is materialized hits this: a drift re-grounding that
rewinds to an earlier phase, or any phase-5+ step that consults lessons.

## Directive

Resolve the plan directory by the **same uniform cwd walk-up** every other `manage-*` script uses
(nearest ancestor of cwd containing `.plan/local`), or fall back to the worktree-resident plan
directory via `manage-status get-worktree-path`.

Until that lands, `consult`'s `outline_not_found` **must not** be read as an absent outline when the
plan is phase-5+ or its worktree is materialized. Distinguish the two states explicitly — an
unresolved store is not a resolved-empty one. (This is the same absent-vs-resolved-empty distinction
`manage-findings` was corrected for in #1369.)

## Workaround used

`manage-lessons list --status active` filtered over the plan's component set, with the match
recorded by hand. Equivalent in outcome, but it is not the documented path and it does not fail
loudly when it finds nothing.
