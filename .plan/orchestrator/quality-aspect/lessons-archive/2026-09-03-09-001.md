# Verification-only guard's affected_files-empty check misfires on survey-scope deliverables carrying a populated mutation_scope

## Context

Plan `every-module-counts-and-the-campaign-can-finish` carried three survey-scope deliverables (D5, D7, D8) whose `Affected files:` list is intentionally empty — they declare `Files to survey:` / `Files expected to mutate:` instead, per the survey-scope shape. Each of the three had a real, populated `mutation_scope` (7, 138, and 70 entries respectively) and a declared `profiles:` of `module_testing` (D5, D7) or `[implementation, module_testing]` (D8) — never `verification`.

phase-4-plan Step 5's Verification-Only Guard pseudocode reads:

```
IF D.affected_files is empty OR (D.change_type == verification AND every affected_files entry has intent == read):
  D.profiles = [verification]
```

Read literally, the `D.affected_files is empty` disjunct fires unconditionally for every survey-scope deliverable, regardless of `change_type` or how much real work `mutation_scope` declares — because a survey-scope deliverable's `affected_files` is empty *by construction*, not because it is read-only. Applying the guard literally would have collapsed all three deliverables' `module_testing`/`implementation` tasks down to empty `[verification]` tasks, silently discarding the plan's three largest and most consequential deliverables (a dedup sweep, a 138-file sys.path migration, and a 70-file suppression conversion).

## Resolution

Treated `mutation_scope` (non-empty) as the write-bearing signal for survey-scope deliverables, mirroring the guard's own stated purpose ("A deliverable is write-bearing when ANY entry ... carries an intent in {write-new, write-replace, delete}" and "never collapsed to verification-only — even when D.change_type == verification"). Kept each deliverable's already-declared profiles intact and proceeded with normal task creation. Logged the judgment call inline in this planning run rather than silently applying the literal pseudocode.

## Recommendation

`phase-4-plan/SKILL.md` Step 5's Verification-Only Guard pseudocode should be corrected to check `D.affected_files is empty AND D.mutation_scope is empty` (or equivalently, gate on the survey-scope pair when it is the deliverable's declared shape) rather than `D.affected_files is empty` alone. The prose above the pseudocode already states the correct intent (write-bearing forces implementation-capable tasks); only the pseudocode's literal condition is out of step with it for the survey-scope case.
