# Retrospective report's Executive Summary section has no producer and is always empty

`retro_sections.py`'s `SECTION_SPEC` carries an `_executive-summary` row that is
always emitted (`conditional_trigger = None`), but no aspect or script populates
that fragment key. Compiled output opens with `_No executive summary provided._`
on every run — the section exists in the layout with no producer feeding it, the
mirror image of a producer whose aspect has no section (which is what this
lesson originally guarded; see History).

## Observed

Confirmed during the `finalize-dispatch-audit-integrity` retrospective
(2026-07-27): compiled output opened with the placeholder text on a run whose
other sections all rendered real content.

## SECOND INSTANCE — `dispatch_boundaries` (2026-07-28, PR #1036)

The same producerless-row shape was found on the very next plan, on a **different
key**, and this one carries a rich payload that is being thrown away.

`compile-report` reported:

```text
sections_written[15]: … (15 sections)
sections_omitted[1]:
  - Phase Dispatch Boundaries
sections_dropped[0]:
```

`Phase Dispatch Boundaries` landed in the **benign** bucket ("the trigger fragment
was absent, so there was nothing to lose"). That classification is wrong here: the
payload exists and `analyze-logs` produced it richly —

```text
dispatch_boundaries:
  4-plan:      1 row     289,886 tokens
  5-execute:   2 rows    322,584 tokens
  6-finalize:  9 rows  1,169,707 tokens   <- larger than phases 2-5 combined
```

The data is emitted **nested inside the `log-analysis` fragment** under a
`dispatch_boundaries:` key, while `SECTION_SPEC` carries a *separate top-level row*
`('Phase Dispatch Boundaries', 'dispatch_boundaries', 'dispatch_boundaries')` and
`should_emit` looks for a fragment registered under that key. No producer ever calls
`collect-fragments add --aspect dispatch_boundaries`; the plan-retrospective Step-3
aspect table does not list it as an aspect at all. So the section can never render,
on any plan, and it fails **quietly into the benign bucket**. The finalize-phase
token accounting — the single largest cost centre in a plan — is dropped twice over.

### Why the new D1 guard does not catch it

`test_registered_aspects_render.py` asserts two directions:

- **(a) registerable ⇒ renderable** — `dispatch_boundaries` **has** a row, so it
  passes trivially.
- **(b) dispatched ⇒ has a static row** — `dispatch_boundaries` is **never
  dispatched**, so it is not in the population at all.

Neither is **(c) has a row ⇒ some producer registers it**. A row with no producer
is invisible to both.

### A second, stacked blind spot

```python
_ASPECT_DISPATCH_RE = re.compile(r'--aspect\s+([a-z][a-z0-9-]*)')
```

`dispatch_boundaries` contains an **underscore**, which `[a-z0-9-]*` cannot match.
So even if a producer were added tomorrow with a literal
`add --aspect dispatch_boundaries`, the scan would silently skip it and direction
(b) would stay vacuous for this key. It is the only underscore-bearing key in
`SECTION_SPEC` — which is exactly why nobody noticed.

## THIRD INSTANCE — both rows reproduced together (2026-08-03, PR #1084)

`content-search-seam`. Both producerless rows failed again, in the same run, with 16 aspects
registered (the largest fragment bundle recorded against this lesson) and `sections_dropped[0]`:

```text
sections_written[17]:  … opens with "## Executive Summary" → "_No executive summary provided._"
sections_omitted[1]:
  - Phase Dispatch Boundaries
sections_dropped[0]:
```

`compile-report` returned `status: success`. Nothing in the TOON envelope distinguishes this
run — where a structurally unfillable row silently ate the phase's token accounting — from a
genuinely clean one.

The `dispatch_boundaries` payload was again produced richly by `analyze-logs`, nested inside the
`log-analysis` fragment, and again for the largest phase in the plan:

```text
dispatch_boundaries:
  4-plan:      1 row     270,452 tokens
  5-execute:   3 rows    823,747 tokens
  6-finalize: 17 rows  2,702,989 tokens   <- 3.3x phases 2-5 combined
```

Two observations that sharpen the guidance rather than merely repeating it:

1. **The payload was not lost on this run only because the retrospective's LLM pass read it out
   of the `log-analysis` fragment by hand.** The 6-finalize row set is the single most
   load-bearing fact in this plan's efficiency analysis — 4 of its 17 rows terminated `error` or
   `blocked_session_restart`, accounting for 859,366 tokens (32% of the phase's recorded
   dispatch spend). A reader relying on the report's section list would see none of it, because
   the heading that would have carried it is reported as a benign omission.
2. **The registry `add` verb already validates aspect keys against the same registry the
   compiler renders from, and `dispatch_boundaries` is in that valid-key list.** Attempting
   `collect-fragments add --aspect invariant-outcomes` on this run was rejected with an explicit
   valid-key enumeration that *includes* `dispatch_boundaries`. So the key is advertised as
   registerable to any caller who trips the validator, while no documented step produces it —
   the registry actively invites a producer that the Step-3 aspect table does not define. That
   is a stronger form of the direction-(c) gap: not merely unchecked, but contradicted by a
   live, user-facing error message.

Direction (c) and the `_ASPECT_DISPATCH_RE` underscore widening both remain owed; neither was
exercised or falsified by this run.

## Guidance

- **A render registry and its producer set must be checked in BOTH directions**,
  and the "nothing to render" bucket must not absorb a row that no producer can
  ever fill. Omission is benign only when a producer COULD have registered and
  legitimately did not; a *structurally unfillable* row is a defect, not an
  omission.
- Add direction **(c)** to `test_registered_aspects_render.py`: every
  non-underscore-prefixed `SECTION_SPEC` `fragment_key` must be either in the
  scanned producer population or on an **explicit, justified** exemption list.
- Widen `_ASPECT_DISPATCH_RE` to `[a-z][a-z0-9_-]*` and add a non-degeneracy anchor
  pinning that an underscore-bearing key is matched — otherwise fixing (c) leaves
  the scanner unable to see the fix.
- For `_executive-summary`: either synthesize a fragment (e.g. `compile-report`
  deriving a short synopsis from the other rendered sections) and register it, or
  drop the always-emitted row and its heading from `SECTION_SPEC` /
  `report-structure.md` if no producer is ever planned.
- For `dispatch_boundaries`: either give it a producer (splitting it out of the
  `log-analysis` fragment — the useful fix, given the payload's value) or drop the
  row.
- This is a distinct failure mode from a mis-registered producer (aspect exists,
  no section): here the section exists and no aspect targets it at all, so the
  producer/registry/layout three-surface-agreement test does not catch it.
