# Meta-project finalize dispatch loads renamed skills from the still-stale host plugin cache, hard-failing skill_load_failure until the post-merge sync

## Context

This is a **meta-project-only** defect — it applies when plan-marshall develops
its own marketplace bundles, not to consumer projects. During phase-6-finalize of a
**breaking skill-rename plan** (`persona-ref-profile-identity-model`, which renamed
skills such as `ref-code-quality`), a dispatched `execution-context` finalize step
hard-failed at skill-load time.

## The bug

phase-6-finalize dispatches its sub-steps (`simplify`, `pre-submission-self-review`,
etc.) as `execution-context` envelopes. The dispatched agent loads every skill named
in its `skills[]` from the **host plugin cache** (`~/.claude/plugins/cache/...`),
NOT from the worktree's `marketplace/bundles/` source. The cache is only refreshed by
the `finalize-step-deploy-target` + `finalize-step-sync-plugin-cache` steps, which run
**late** in phase-6 (after branch-cleanup / on the post-merge path).

So during a skill-rename plan there is a window where the worktree source already
carries the NEW skill name but the host cache still carries the OLD (pre-plan) name.
A finalize step dispatched in that window with a NEWLY-RENAMED skill name in its
`skills[]` (e.g. `ref-code-quality`) cannot resolve it in the stale cache and the
dispatcher returns:

```toon
status: error
error: skill_load_failure
```

This bit `finalize-step-simplify` in this run.

## Root cause

Cache-freshness is not a precondition of the finalize dispatch loop: the dispatch
resolves `skills[]` against the host cache, but the cache-refresh steps that would
make a renamed skill resolvable are sequenced AFTER the steps that consume it. For a
rename-target skill, the dispatch's view of the skill universe lags the worktree by
exactly the un-synced rename.

This is the same family as lesson 2026-06-20-16-002 (a finalize step's relationship
to derived state that is only refreshed late in the phase), but the failure surface
is different: that lesson is about the freshness *gate forcing a rebuild*; this one
is about a *skill name that cannot be loaded at all* because the cache predates the
rename.

## How to apply

- During a breaking skill-rename plan, for ANY phase-6-finalize dispatch whose
  `skills[]` would name a rename-TARGET skill, pass the **OLD / cached** skill name
  (the content is identical — only the notation changed) until the post-merge cache
  sync has run. The dispatcher resolves the old name from the still-current cache and
  the loaded skill body is the same.
- Treat `error: skill_load_failure` on a finalize-step dispatch during a rename plan
  as the signature of this cache-lag window — not as a genuinely missing skill.
- The durable fix (if pursued in a future plan) is to make cache-freshness a
  precondition of the finalize dispatch loop for rename plans, or to resolve
  finalize-step `skills[]` against the worktree source rather than the host cache, so
  a renamed skill is loadable the moment the worktree carries it. Until then, the
  old-name workaround above is the operational rule.
- Scope: meta-project (plan-marshall self-development) ONLY. Consumer projects do not
  dispatch finalize steps that load just-renamed in-tree skills, so this window does
  not exist for them.

## Recurrence (2026-07-21): a plan that edits a finalize step's OWN body executes stale, silently

`review-barrier-residuals` (PLAN-21) broadened this defect's scope from a *hard*
`skill_load_failure` to a *silent* stale-logic execution. D4 of that plan changed
`automatic-review/SKILL.md` — the body of a finalize step that the same finalize run
would re-dispatch. Because the plugin-cache sync (`project:finalize-step-sync-plugin-cache`,
order 85) runs late (post branch-cleanup), a re-dispatched `automatic-review` leaf in
the same run loads the STALE cached SKILL.md and runs the pre-plan logic. Unlike the
rename case there is no `skill_load_failure` to signal the lag — the leaf loads fine
and silently applies the old completeness logic, which is strictly worse than a hard
failure.

**Manifestation delta:** rename plan → dispatch names a skill absent from the cache →
`skill_load_failure` (loud). Self-modifying-step-body plan → dispatch names a skill
PRESENT in the cache but with stale content → old logic runs (silent). Same root
cause (finalize dispatch resolves against the host cache; the sync that would refresh
it is sequenced after the steps that consume it), same durable fix (resolve
finalize-step bodies against the worktree source, or make cache-freshness a
precondition of the dispatch loop).

## Recurrence (2026-07-26): a stale cached SCRIPT MODULE rejects an aspect key and silently drops a report section — and the staleness spans MULTIPLE merges, not one in-run window

`test-suite-quality-unit-testing-residue` (PR #1012) broadens this defect a third
time, on two independent axes.

**Axis 1 — the stale artifact is a script module, not a skill body.** The dispatched
`plan-marshall:plan-retrospective` finalize step called
`collect-fragments add --aspect chat-history-analysis` and was refused:

```toon
status: error
error: "Unregistered aspect key: 'chat-history-analysis'. ... Valid aspect keys:
  ['artifact-consistency', 'dispatch_boundaries', 'invariant-summary',
   'lessons-proposal', 'llm-to-script-opportunities', 'log-analysis',
   'logging-gap-analysis', 'manifest-decisions', 'permission-prompt-analysis',
   'plan-efficiency', 'request-result-alignment', 'routing-decisions',
   'script-failure-analysis', 'wrapper-tangle']"
```

The registry doing the refusing is `retro_sections.py`, which the executor resolves
from the host plugin cache. The cached copy
(`~/.claude/plugins/cache/plan-marshall/plan-marshall/0.1.1194/skills/plan-retrospective/scripts/retro_sections.py`)
has no `('Chat History Analysis', 'chat-history-analysis', 'chat-history-analysis')`
row; the worktree/main copy at
`marketplace/bundles/plan-marshall/skills/plan-retrospective/scripts/retro_sections.py`
does. So the lag now bites through a **shared Python module the scripts import**, not
only through a `skills[]` entry or a SKILL.md body — widening the blast radius from
"skills a dispatch names" to "any cached code path a dispatched step executes".

**Axis 2 — the lag is not the single in-run window this lesson describes.** Both prior
manifestations were caused by the CURRENT plan editing the artifact and the sync being
sequenced later in the SAME run. Here the plan never touched `retro_sections.py`. The
chat-history row landed on main in **#998 (`a594c94a4`)**, several merges before this
plan started, and the cache still lacked it — so the cached copy was behind main across
multiple completed finalize cycles, each of which nominally ran
`project:finalize-step-sync-plugin-cache`. The operational assumption that "the cache
is current as of the previous merge" does not hold, and no gate reports the drift.

**Manifestation delta (third row).** rename plan → named skill absent from cache →
`skill_load_failure` (loud). Self-modifying-step-body plan → skill present, content
stale → old logic runs (silent). **Stale shared script module → a documented,
SKILL-mandated aspect key is rejected → the corresponding report section can never be
produced (silent, and attributable to the wrong layer: the error text reads as
"the caller used an invalid key", not "your cache is old").** The third row is the
most misleading of the three, because the refusal message actively points the reader
away from the real cause.

**Practical consequence in this run.** Three aspects SKILL.md Step 3 instructs the
orchestrator to produce — the execution-context dispatch audit, `direct-gh-glab-usage`,
and `chat-history-analysis` — have no registerable key in the cached registry. Their
findings had to be folded into neighbouring sections to reach the report at all.

**Rule to add:** treat "a script rejects a value that the loaded SKILL.md documents as
valid" as a cache-staleness signature first and a caller error second. Before debugging
the call, compare the cached module against the worktree copy. The durable fix is
unchanged and now three-times motivated: resolve dispatched-step code against the
worktree source, or make cache-freshness a checked precondition — and, given axis 2, a
freshness check that compares cached-vs-source content rather than assuming the last
sync succeeded.

**Operational rule for self-modifying finalize plans:** when a plan modifies the body
of a finalize step that its own run will re-invoke, do NOT re-dispatch that step in
the same run — the orchestrator runs the changed logic INLINE instead (for D4 this
was the `fetch_findings` responded-bots + `review_completeness check --settled-bots`
path executed directly in the orchestrator context rather than via a re-dispatched
`automatic-review` leaf). This is the general form of the rename-plan old-name
workaround: any meta-project plan that edits the finalize pipeline's own step docs
must assume the re-dispatched leaf sees the pre-plan body until the late cache sync.
