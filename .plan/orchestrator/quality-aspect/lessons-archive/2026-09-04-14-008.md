# build_queue release fails with cannot resolve main checkout from inside a worktree

## Context

Four non-zero exits of `plan-marshall:build-pyproject:pyproject_build run` were recorded in the plan's `script-execution.log`, starting `2026-09-03T17:44:35Z`, all carrying the same stderr signature:

```text
build_queue release failed for plan-145-publish-the-missing-parser-seams
  (id=plan-145-publish-the-missing-parser-seams:7bc9908c-87aa-4c2c-9a9d-4fb0d7752d2a):
  release failed: cannot resolve main checkout
```

The build itself proceeded — the failure is in the **release** of the build-queue slot, after the work is done. That is why it never surfaced as a red gate: the quality gate and module-tests both reported green on the same runs, and the only trace is a script-level exit code 1 that `script-failure-analysis` classified as `script_internal_error` with `occurrence_count: 4`.

## Root cause

The build-queue release path resolves the **main checkout** to reach the machine-global lock store, but phase-5+ pins cwd to the plan's worktree (the move-based, cwd-pinned model, ADR-002). From inside the worktree the main-checkout resolution fails, so the release aborts.

A failed release does not fail the build, so the consequence is a **leaked queue slot** rather than a visible error. This is consistent with the machine contention the operator was asked to triage twice during this run ("the pre-push test gate can't get a verdict while another plan saturates the machine") — leaked slots make the concurrency limiter under-count available capacity over time.

Same family as lesson `2026-08-25-09-015` (a session restart resets cwd off the worktree, breaking every `manage-*` call), but the trigger here is not a restart: the release path resolves main-anchored state unconditionally, so it fails on every worktree-resident build.

## Proposed action

1. Resolve the build-queue lock store main-anchored via the shared `file_ops` store handle rather than by walking up from cwd, so the release works identically from a worktree and from the main checkout.
2. Make a failed release **loud** — it currently exits non-zero with the build already green, which is the worst of both: the caller sees an error it cannot act on, and the leaked slot is silent.
3. Add a reconciliation path (or a TTL) so an orphaned queue entry cannot starve later builds indefinitely.
