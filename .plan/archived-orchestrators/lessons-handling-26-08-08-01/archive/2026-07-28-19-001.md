# architecture derive-verification emits an unresolvable `test-compile` command behind `status: success`

## Observed — first-party, 2026-07-28, at HEAD

`architecture derive-verification --changed-artifacts test/plan-marshall/marshall-orchestrator/test_orchestrator_read_boundary_contract.py`
returns `status: success` with `command_count: 2`:

| build_class | command | execution_tier |
|-------------|---------|----------------|
| `module-tests` | `test-compile` | `orchestrator` |
| `module-tests` | `module-tests` | `orchestrator` |

But `architecture resolve --command test-compile` returns:

```
status: error
error: architecture_error
message: Command not found
available[6]: clean, compile, quality-gate, verify, module-tests, coverage
```

`test-compile` is **not** in the canonical command set, and it is **not** declared in the only
registered `ext-point-build-verify-step` implementor
(`phase-5-execute/standards/canonical_verify.md`, `canonicals: [quality-gate, module-tests, coverage]`).

## Impact — blocks phase-4-plan at Step 7b

phase-4-plan Step 6 writes the derived executables into the task's `verification.commands`
verbatim, exactly as its SKILL documents. At Step 7b, `manage-execution-manifest compose`
generalizes the unrecognized orchestrator-tier verb to a bare `verify:test-compile` step id,
then its own `unresolvable_step` gate rejects the manifest it just composed:

```
status: error
error: unresolvable_step
step_id: "verify:test-compile"
```

Any plan whose deliverables touch a Python test file under a module whose
`bash_timeout_seconds` exceeds the 600s Bash ceiling (so `execution_tier: orchestrator`)
hits this. Observed on plan `orchestrator-read-boundary-self-contradiction` (PLAN-94),
which was halted mid-phase-4.

## Root cause — a producer/consumer contract split

`derive-verification` (producer) and `resolve` / the canonical-verify registry (consumers)
disagree on the canonical command vocabulary. The producer emits a verb the consumers do not
accept, and reports `status: success` while doing it. Note the two emitted rows share
`build_class: module-tests` — the build_class is the real routing key, and it is already
correct on both rows.

## Why this matters beyond the immediate break

This is the **confident-signal-hides-a-caveat** archetype (the `truthful-signals` epic theme)
occurring inside the tooling that epic's plans run on. `status: success` with `command_count: 2`
reads as a fully-resolved verification set; one of the two entries is unusable, and nothing in
the payload says so. A caller obeying the documented contract (write the derived executables
verbatim) is led into a guaranteed downstream failure.

## Directive

Fix at the producer, not with a runtime guard at the consumer. Options, in preference order:

1. **Collapse on `build_class`** — `derive-verification` should not emit two rows whose
   `build_class` is identical and whose canonical vocabulary differs. Emit the resolvable
   canonical (`module-tests`) for the `module-tests` build_class.
2. **Make `test-compile` a real canonical** — if the fast import/syntax precursor is wanted as a
   distinct step, add it to the architecture command set AND to `canonical_verify.md`'s
   `canonicals:` frontmatter in lock-step, so producer and consumer move together.

Whichever arm is chosen, add a regression asserting that **every `command` value
`derive-verification` emits is resolvable by `architecture resolve`** — a
population-derived check over the emitted set, not a fixed list of the verbs that happen to
work today. That is the property whose absence let this ship.

Do NOT resolve this by having `manage-execution-manifest` silently drop unresolvable steps —
that converts a loud, correct failure into a silent coverage hole.
