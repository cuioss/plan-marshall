# Analysis/measurement plans should use an existing architecture module, not 'project-wide'

## Context

During phase-4-plan for `measure-uncompressed-output`, the solution outline specified `module: project-wide` for a single-deliverable analysis plan. The architecture query `architecture module --module project-wide` returned `status: error / Module not found`, leaving the task with no architecture-resolved skills.

Available modules at the time: `default`, `plan-marshall`, `pm-dev-python`, `pm-documents`, `pm-plugin-development`, `pm-requirements`, and four others. There is no `project-wide` module registered.

## Resolution Approach

For analysis/measurement deliverables that span the whole project, the phase-3-outline skill should select an existing module that best represents the domain of work being analyzed:

- If the analysis targets Python scripts or test infrastructure, use `plan-marshall` or `pm-dev-python`.
- If the analysis produces a documentation artifact (e.g. a `.md` file under `doc/`), use `pm-documents`.
- The `default` module may also be appropriate when no more specific module fits.

Using `project-wide` as a module name triggers a hard lookup failure in phase-4-plan because the architecture registry has no such module. Phase-3-outline must use a registered module name, or the architecture must be enriched to add `project-wide` if cross-cutting analysis plans are a recurring pattern.

## Workaround Applied

Phase-4-plan applied graceful degradation: logged a WARNING, set `task.skills = []` from the module lookup, then applied persona-skill augmentation (persona-implementer resolved to `plan-marshall:ref-code-quality` and `pm-dev-python:python-core`) to give the task a minimum useful skill set. A Q-Gate triage finding was also emitted so the gap is visible at plan review time.
