# Documentation restating validator rules was written without a drift guard until a review bot asked

# Candidate lesson: documentation that restates validator rules needs a drift guard when it is written, not after a review bot asks

**Source:** plan-28-jwks-refresh-follow-ups, automatic-review on PR #437. Two CodeRabbit inline findings were remediated during the run (`--type pr-comment --resolution fixed`).

## Findings

1. **b904d3, doc/configuration.adoc:4721 (the main one).** TASK-7 added a boot-validation summary listing the three JWKS refresh keys, their ranges (60-86400 / 0-3600 / 5-3600) and the refusal of `source: file`. That is a hand-copied mirror of the three `checkJwksRefreshKey` rules in ConfigValidator, with nothing tying the two together. CodeRabbit flagged it under the cuioss path instruction "a hardcoded list that must mirror a set defined elsewhere is a defect unless derived". It was fixed by TASK-13 (commit 5d9e0170): one definition of the three keys in ConfigValidator, plus a DocumentedSetsContractTest-style contract test that fails when the documented list drifts.
2. **380074, doc/LogMessages.adoc:98 (minor wording).** The ApiSheriff-137 entry said the failure is "logged nowhere", but the record itself is a log entry. It was reworded to say that the throwable and its message are not logged at any level and that this record is the only trace (commit f33a18b0).

## Proposed rule

When a documentation task writes down a set the code enforces (config keys, ranges, refused values), add or extend the DocumentedSetsContractTest guard in the same task. The project already has that pattern, and its review instructions treat an unguarded mirror as a defect. Each time the guard is left to the review round, it costs one extra fix task, one re-push and one CI cycle.

## Scope hint

This is project-local (API-Sheriff documentation practice). It could go in the documentation module's architecture hints or in the doc-task profile defaults.
