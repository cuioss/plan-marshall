# Replace the standalone sleep pacer the dispatched leaf cannot execute

## Context

`automatic-review/SKILL.md` prescribes bare-`sleep` pacing at three poll sites, in each case explicitly as a *standalone* Bash call:

- Completion-aware poll, stated twice — "pacing between polls is a single standalone `sleep {interval}` Bash call (`{interval}` = 30s)", and in the poll-outcome table: "pace with a single standalone `sleep 30` Bash call, then re-issue the `bot_completion` poll".
- Rate-window poll — "pacing between polls is a single standalone `sleep {interval}` Bash call (`{interval}` = 60s)", with a literal `sleep 60` block.

None of the three is executable in the envelope that runs them. The host blocks a foreground `sleep` and directs the caller to a Monitor tool that the dispatched leaf is not granted. The skill's own frontmatter confirms it by declaration: `allowed-tools: Read, Bash, Skill` — no Monitor. So the pacer is unavailable by contract, not merely by runtime policy.

On PR #1382 the agent hit this and improvised, decision-logging the substitution at `2026-09-03T00:31:01Z`: it used the workflow's own bounded condition-wait (`ci pr wait-for-comments`) between `bot_completion` polls, keeping the command vocabulary and the `review_completion_poll_timeout_seconds=600` budget tracking intact.

## Root cause

The pacing instruction was written for an execution context that can block on wall-clock. A dispatched leaf cannot, and the skill's own `allowed-tools` never granted it a tool that can. The instruction and the declared tool surface were never reconciled.

## Proposed action

Replace all three `sleep` pacers with the substitution the run already validated: a bounded wait on the actual observable. `ci pr wait-for-comments --timeout {interval}` is already in this skill's vocabulary and waits on the signal rather than the clock, which is also what `plan-marshall/standards/waiting.md` asks for at the rate-window site ("a bounded wait over a concrete observable, NOT a blind sleep"). Note that the rate-window site (Branch 3) already argues against blind sleeping in prose while prescribing `sleep 60` two paragraphs later — the doc contradicts itself there.

## Recurrence — 2026-09-04, plan `plan-145-publish-the-missing-parser-seams` (PR #1395)

Third occurrence, and it **closes off the last remaining escape hatch** —
which changes the shape of the required fix.

The previous recurrence established that the procedure has no executable form
because the sanctioned call (`sleep`) is blocked and the sanctioned fallback (a
shell until-loop) is prohibited by the project's own hard rules. It noted that
the operator improvised a background until-loop anyway.

**On this run that improvisation also failed.** The harness repeatedly killed
the backgrounded long-poll waits, citing low memory — while roughly **19 GB was
free**. So all three candidate pacers are now known-unavailable:

| Pacer | Status |
|---|---|
| foreground `sleep` | blocked by the harness |
| shell `for`/`while`/`until` loop | forbidden by the project Bash hard rules |
| `run_in_background` long-poll | killed by the harness, on a stated reason the machine state contradicts |

That the kill reason does not match observable memory matters independently of
the pacing question: it means the background wait is **unreliable rather than
merely lossy**, so the `await-long-running` seam's documented "known-lossy,
detected-on-wake" contract understates the failure mode. A caller cannot
distinguish a genuine resource kill from a spurious one, and therefore cannot
choose a backoff.

### What this adds to the proposed action

The previous recurrence asked for the rule to be restated against a *primitive*
(a bounded wait on a concrete observable) and then swept across every site
spelling it `sleep`. This run shows that **the primitive must actually exist and
be reachable from a dispatched leaf** before that sweep can land — today there
is no such primitive in a leaf's granted surface.

`manage-locks` already owns the cross-plan review-bot rate-window claim, which
is precisely the observable being waited on here. A bounded blocking wait verb
there would give the sweep a target, and would be reachable through the script
executor that every leaf already has.

Three of this plan's five loop-back iterations were rate-window waits, so this
is not an edge case: it is the pacing path the finalize review loop takes by
default.

## Recurrence — 2026-09-09, plan `close-the-runtime-slice-parametrization` (PR #1455)

Fourth occurrence, and the **workaround from occurrence one is now the only surviving path** —
which is the argument for making it the documented one.

All three pacers were unavailable exactly as the previous recurrence tabulated: the
completion-aware poll's standalone `sleep 30` is blocked in the foreground; the project's
no-shell-constructs hard rule bars the until-loop the harness redirects to; and the
`run_in_background` long-poll was killed **twice** by host memory pressure, each time after
roughly a minute, during the 90-minute CodeRabbit quota wait at 23:05Z–00:37Z. The kills are
recorded in `decision.log` at 2026-09-09T00:37:49Z.

The step nonetheless completed, by falling back to precisely the substitution PR #1382
improvised three occurrences ago: pacing on `ci pr wait-for-comments`, a bounded wait over a
concrete observable already in the skill's vocabulary. That improvisation has now been
independently re-derived on four separate plans by four separate runs, because the document
still prescribes the blocked call.

This is the point at which the recurrence stops being evidence of a defect and becomes evidence
about the fix: the substitution needs no new primitive, is already granted to a dispatched leaf,
and satisfies `plan-marshall/standards/waiting.md`. The `manage-locks` bounded-wait verb the
previous recurrence proposed remains the better long-term target for the rate-window site
specifically, but the completion-aware poll can be corrected today by replacing `sleep 30` with
the wait already in use.
