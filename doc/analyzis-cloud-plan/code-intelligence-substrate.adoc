= Cloud-run quality analysis: `code-intelligence-substrate`
:toc: left
:toclevels: 3
:sectnums:

Analysis of the `code-intelligence-substrate` plans executed as standalone cloud runs, measured
against the plans executed locally through the full plan-marshall lifecycle.

**The contract under analysis.** The cloud lane is defined by two project-local skills:
link:../../.claude/skills/cloud-plan-lane/SKILL.md[`cloud-plan-lane`], the execution contract loaded
as the first action of every run, and
link:../../.claude/skills/author-cloud-plan/SKILL.md[`author-cloud-plan`], the authoring judgement
applied when a plan is written. Every lane-contract finding below names one of them.

[IMPORTANT]
====
**Measured at repository HEAD `e3ef31cbb`, 2026-08-22 (UTC)** (`main` at `31211a99b`; the two differ only
by the ingest commit, which deletes the export tree and touches no measured surface). Every figure is
re-derivable by script from the ingested corpus at
`.plan/local/orchestrator/code-intelligence-substrate/cloud-runs/`.

This document carries a measurement instant, which the project documentation standard otherwise
forbids. The deviation is deliberate and is the subject of the analysis: a comparative measurement
without its instant is exactly the untruthful signal this epic exists to remove.

**The zone is stated because it is load-bearing here.** The measurements were taken across a
local-midnight boundary (CEST, UTC+2), so the local calendar date advanced while the UTC date did
not. The commit itself is `2026-08-22T21:28Z`. An unzoned date would have been ambiguous by one day
— a small instance of exactly the defect class this corpus is full of.
====

== Population, and the zero that had to be derived

The epic's cloud PRs are of **two kinds**, and only one belongs in a quality analysis:

[cols="2,4",options="header"]
|===
| Kind | Treatment

| **Plan work** — a run of an authored `plan.md` under the `cloud-plan-lane` rule-set | **analysed**
| **Fixes to the `cloud-plan-lane` skill itself** — ad-hoc edits made *outside* the rule-set | **excluded**
|===

=== The exclusion, derived rather than asserted

Criterion: a PR is a lane-fix when **the only production file it touches is
`.claude/skills/cloud-plan-lane/SKILL.md`** (plan documents under `doc/plans/` are not production).
Applied to every landed commit in the repository:

* **40 lane-fix PRs exist repo-wide.**
* **All 40 are outside this corpus** — ad-hoc `chore(cloud-plan-lane):` edits with no plan directory,
  so none ever entered the analysis.
* **0 were removed from the corpus.**

[NOTE]
====
**This is a `0` that had to be derived, not assumed.** The sibling `truthful-signals` analysis found
two lane-fixes *inside* its corpus and removed them. Here the same criterion, run over the same
repository, removes none — because this epic's plan directories were authored from orchestrator
specs and the lane-fix PRs were raised separately. **Stating "no exclusions" without running the
criterion would have been indistinguishable from not looking.**

**A resolution defect the sibling analysis recorded was avoided here by construction.** Each PR's
landing commit is resolved by anchoring the match to the **end of the subject line**; a bare
`git log --grep "(#NNNN)"` also matches commits that merely mention the number in their body. All 37
PRs resolved to a landing commit under the anchored rule.

**One PR resolved only after a second correction.** Plan `350` records `PR: none — run 01 was halted
before the PR cycle` in `report-01.md`; its PR (`#1295`) is in `report-02.md`. A reader of the first
report alone would have dropped the plan from the population. The extractor now reads the **last**
`report-NN.md`, not the first.
====

[cols="2,3,3",options="header"]
|===
| | Cloud lane | Local plan-marshall

available, explicitly as compensation for absent guardrails, and still produced the fidelity figures
below. ⇒ **Raising effort did not substitute for the machinery.**

== Why so many gaps? The brief answers part of it

[IMPORTANT]
====
**The gap count is substantially a function of what the verification call asked for**, and this
corpus's brief was **narrower and more claim-relative** than the sibling epic's. From
`cloud-runs/_audit/summary.md`, the two artefacts written per plan were:

[quote]
____
`verification.md` — Per-deliverable verdict against the tree, correctness review, test adequacy,
report accuracy, residue status, and the method used to reach each

`gaps.md` — Every defect as an actionable entry — kind, severity, topic, `path:line`, evidence,
consequence, action, observable *done when*, effort, risk if fixed
____

Each pair was then attacked by an independent reviewer across **eight classes**: fabricated findings,
missed findings, vacuous evidence, wrong counts and quotes, unactionable entries, mis-calibrated
severity, coverage holes, and internal inconsistency.

⇒ **This is not a repository-wide checklist sweep.** It is *"check this plan's claims against the
tree, then check the checker"*. That makes the raw total more meaningful here than in a checklist
sweep — but the verdict below still rests on **deliverable fidelity** and **reviewer resolution**,
never on the raw total.

== CodeRabbit: the reviewer signal

An independent reviewer's findings are the one quality measurement neither lane authors about itself.

[IMPORTANT]
====
**The classifier was validated against ground truth before being trusted**, as the method requires.
Two local plans ran `finalize-step-review-retrospective`, whose per-reviewer `inline` count is an
independent measurement of the same quantity:

[cols="2,2,2,3",options="header"]
|===
| PR | Retrospective `inline` | This classifier | Verdict

| #1127 | 12 | **12** | exact match
| #1123 | 9 | **9** | exact match
|===

**The retrospective's headline "14 actionable" for #1127 is a different quantity** — it adds 2
`review_body` summaries to the 12 `inline` findings. The method's definition counts inline comments
carrying the `cr-comment:v1` fingerprint, so 12 is the correct figure under this definition and the
delta is explained rather than reconciled away.

**`resolved` here is the thread's `resolved` flag, not a fixed-rate.** The #1127 retrospective
separately reports 11 of 14 *resolved as fixed* (78.6%). Thread-resolution and fixed-rate are
different measures; this report uses the former throughout, for both lanes, so the comparison is
like-for-like.
====

[cols="3,2,2",options="header"]
|===
| | Cloud lane | Local plan-marshall

| PRs | 37 | 11
| Reviewed | **11 (29.7%)** | **7 (63.6%)**
| Declined — quota / review limit | 26 | 4
| Reviewed and found nothing | 1 | 0
| Findings raised | 47 | 57
| Findings resolved | 45 | 57
| **Resolution rate** | **95.7%** | **100%**
|===

=== Coverage differs — and it is an ORDERING ARTIFACT, not a lane property

The obvious reading is that cloud PRs got half the review coverage. **That reading does not
survive the cadence measurement.**

[cols="2,2,2",options="header"]
|===
| | Cloud lane | Local plan-marshall

| Merge span | 2026-08-10 … 2026-08-21 (10 days) | 2026-08-08 … 2026-08-10 (3 days)
| PRs per day | **3.7** | **3.67**
| Reviewed per day | 1.1 | 2.33
|===

**The two lanes submitted PRs at an identical daily rate.** What differs is *when* they did it: the
local wave ran first, into a fresh quota window; the cloud wave ran immediately after, into a window
the combined volume had already depleted.

The decline notices name the mechanism themselves. Sampled from #1201:

[quote]
____
Review limit reached … You've used all free OSS reviews for now. … CodeRabbit uses adaptive limits
for sustained high-volume activity. When a developer's recent PR review activity reaches the 95th
percentile or higher among CodeRabbit users, additional reviews become available more gradually as
earlier reviews age out of the rolling window.
____

⇒ **The coverage difference is environmental, account-scoped, shared across both lanes, and
order-dependent.** Had the waves run in the opposite order the numbers would likely invert.
**Coverage is therefore removed as an explanation for the quality gap.**

=== The resolution rate is the control that eliminates a candidate

**This is the dimension where both lanes behave essentially identically**: 95.7% and 100% of what
a reviewer raised was resolved before merge.

⇒ **The cloud lane does not ignore reviewer findings.** Its findings *pipeline* — receive, triage,
respond, resolve — works about as well as the local one. Whatever produces the fidelity gap, it is
**not** a failure to act on external review.

A control that eliminates a candidate is worth more than one that supports it, and this one
eliminates the most obvious candidate.

=== The confound, stated before the comparison

[WARNING]
====
**The two defect counts are not the same measurement and must not be subtracted.**

The cloud's 479 gaps come from a verification pass sweeping each plan's claims against the tree
**after merge**. The local 227 findings are raised by the plan's **own in-run gates and resolved
before merge**. One counts what a sweep found; the other counts what the gates caught.

A plan-marshall plan that raises 27 qgate findings and fixes all 27 before merge shows a *high*
number and a *good* outcome. A cloud plan that raises none shows a *zero* only because nothing was
looking.
====

=== Local plans ARE post-hoc verified — and the rate is measurable

The orchestrator contract requires every landed plan's result to be verified against ground truth
before it is recorded; a pasted claim is a lead, never a fact. The `landings/*.md` records are that
verification's output.

**The 37 landing records written during the 2026-08-22 ingest are excluded** — they are this
analysis's own output, and counting them would be self-measurement.

**The remaining eligible records must also be split by lane**, because two of them describe cloud
runs. Mixing them would contaminate the comparison:

== Adjudication of the three candidate explanations

=== plan-marshall shows its benefit — *SUPPORTED*

Named mechanism with a measured consequence:

* **The local lane has in-run gates; the cloud lane has none.** 227 defect-shaped findings were
  raised and resolved **before merge** across 11 local plans. The cloud lane's 479 gaps were all
  found **after merge**, by a pass the lane does not contain.
* **On the claim-relative metric the local lane is ahead**: 50.0% of local landings record a
  contradicted claim against **75.7%** of cloud plans shipping a deliverable the tree does not
  support.
* **The cloud lane had the more expensive model setting** and still produced those figures. ⇒ The
  difference is **structural, not a matter of thinking harder**.

=== `cloud-plan-lane` / `author-cloud-plan` is faulty — *SUPPORTED, with four named mechanisms*

. **The run report is self-assessed and nothing re-derives it before merge.** Measured consequence:
  **78 gaps (16.3%) are `report-defect`** — corrections to the runs' own paperwork — and an
  independent measure over the `Where:` field agrees at 85 (17.7%).
. **Post-run verification is not part of the lane.** Plan `500` ran, merged, and sat **with no
  verification at all** until this ingest produced one. A lane whose quality artefact is
  operator-issued rather than contractual will silently skip it.
. **The lane has no rule for a run blocked on an environment prerequisite.** Six plans hit the same
  wall — the archived-plan corpus is git-ignored, so a fresh cloud clone cannot see it — and each
  independently invented its own response. **Two then mis-stated what the halt implied**: `080`
  reported *"nothing needs building, only the corpus needs to be present"* in four places, and its
  own audit proved the instrument the measurement is defined over **does not exist** and is
  git-derivable. This is a **predictable, structural** blind spot the contract does not name.
. **Nothing re-derives a count at publication.** Stale test counts, commit counts, file counts and
  gate figures appear in nearly every report — including, twice, **inside the report proposing a fix
  for stale figures**.

=== A general Claude Code issue — *NOT SUPPORTED as an explanation for the gap*

The environmental factor in this corpus is the CodeRabbit quota, and it is measured to be
**shared, order-dependent, and equal in rate across lanes** (identical 3.7 PRs/day). It explains
*coverage*, not *fidelity*.

⇒ **Removed as an explanation.** It remains a real operational constraint, just not a lane property.

== Verdict

[IMPORTANT]
====
**The cloud lane produced work that landed — all 37 plans merged, and no plan was found to have
shipped nothing — but it cannot tell you whether it worked.**

The evidence separates cleanly into what the lane *does* and what it *knows*:

* **Doing**: 47 reviewer findings raised, 45 resolved (95.7%) — statistically indistinguishable from
  the local lane's 100%. The cloud lane acts on external review perfectly well.
* **Knowing**: 75.7% of its plans shipped a deliverable the tree does not support as claimed, and
  16.3% of all recorded gaps are corrections to the runs' own reports.

⇒ **The deficit is not in execution, it is in self-knowledge.** The lane's only account of a run is
written by the agent that performed it, and nothing in the contract checks that account before the
work merges.

**The strongest single datum**: the epic's own two-stage audit found **37 of 37 plans *sound only
after correction* — not one was sound as written**. That base rate held on the 37th plan, audited
during this ingest, whose clean first-pass verdict (*6 of 6 confirmed, zero high gaps, no false
claims*) was overturned by an adversarial pass with two high-severity findings — one of them
**disproved by a sentence in the audited document itself**.
====

== What the cloud lane is genuinely good at

The analysis should not be read as a case against the lane. Measured strengths:

* **Throughput.** 37 plans landed in 10 days at 3.7 PRs/day, sustained, without an orchestrator
  session held open.
* **It lands what it starts.** 37 of 37 merged; 0 abandoned.
* **Reviewer discipline.** 95.7% resolution, essentially the local rate.
* **Honest halting.** The two D0-gated plans (`020`, `080`) **correctly refused to fabricate a
  measurement** over an unreachable population. `090` did better still — it split, shipped the
  git-derivable half, and left the rest explicitly blocked. That is exactly the right behaviour and
  it was reached from first principles, without a contract rule requiring it.
* **Refutation in flight.** Several plans refuted their own spec's premise mid-run and re-scoped
  rather than implementing against a stale brief — `310` in particular refuted its stated mechanism,
  confirmed the symptom, and fixed the real defect one layer down while **avoiding a no-op its spec
  had forbidden**.

== Recommendations

. **Make post-run verification contractual, not operator-issued.** Plan `500` proves the failure
  mode: a run that merges with no verification artefact at all. This is the highest-value change.
. **Stop the run report being the sole account of the run.** 16.3% of gaps are report corrections.
  Either derive the report's factual rows mechanically, or verify them before merge.
. **Add a lane rule for environment-blocked runs.** Name the git-ignored corpus explicitly, require
  the split `090` performed, and forbid the *"nothing needs building"* hand-off unless the
  instrument has been shown to exist.
. **Require every count in a report to carry the command that produced it**, re-derived at
  publication. This is F11 and it is nearly universal.
. **Keep the adversarial pass.** It is the single highest-yield step in the whole method: it changed
  the verdict on 37 of 37 plans, and on plan `500` it converted a clean result into two
  high-severity findings.
. **Write plan `500`'s adversarial re-ratings back into its `gaps.md`**, so the corpus files and the
  adjudicated figures agree.

== Reproducing this analysis

See xref:analyzis_rules.adoc[the analysis rules] for the instruction set. Every table above is
generated by script from the ingested corpus; none is transcribed.

[cols="3,4",options="header"]
|===
| Input | Location

| Cloud corpus | `.plan/local/orchestrator/code-intelligence-substrate/cloud-runs/{NNN}-{slug}/`
| Epic-level audit records | `cloud-runs/_audit/` (excluded from the plan population)
| Local corpus | `.plan/local/archived-plans/` (whole archive, 11 plans)
| Landing records | `.plan/local/orchestrator/code-intelligence-substrate/landings/`
| Reviewer signal | `ci pr comments --pr-number N`, aggregated without printing comment bodies
| **The derivation scripts** | `cloud-runs/_audit/analyze.py` (populations, fidelity, taxonomy) · `reviewer.py` (reviewer signal, both lanes) · `tables.py` (the AsciiDoc rows above)
|===

The per-PR ledger in this document was diffed against `tables.py`'s output before publication and reproduces it exactly, so the strongest finding in the sibling report — that mechanically-derived figures survive a run in which asserted prose goes stale — holds for this one too.

**Plan population = directories under `cloud-runs/` excluding `_`-prefixed ones.** The seven un-run
`5NN-*.md` files also live there as loose files; they are not directories and are therefore excluded
by construction, which is why the population is 37 and not 44.
