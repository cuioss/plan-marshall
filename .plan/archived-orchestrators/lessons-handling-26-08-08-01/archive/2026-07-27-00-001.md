# Routed builds misreport their own outcome: --timeout silently discarded, duration zeroed, and a daemon wait-expiry reported as a hard failure over a child that passed

## Observation

While recovering an orchestrator-tier `verify:coverage` step for plan `orchestration-inbox-channel`, two independent truthfulness defects surfaced on the routed (daemon) build path.

### (a) `--timeout` is silently discarded when the build routes to the daemon

Invocation:

```
pyproject_build run --command-args "coverage" --timeout 2400 --plan-id orchestration-inbox-channel
```

Resolution line: `resolved=routed ... mechanism=daemon_longpoll`.

The daemon's job log recorded:

```
status: timeout
timeout_used_seconds: 600
duration_seconds: 600
```

The requested `2400` never reached the executed command. No warning, no clamp notice, no field in the returned TOON naming the effective timeout. The caller has no way to learn from the response that the value it passed was overridden.

Re-running the identical command with `--execution-mode in_process` honoured the flag and the build completed cleanly at `duration_seconds: 1116` — 1.86x the ceiling that had been truncating it. So the step was never too slow in an absolute sense; it was too slow only for a ceiling the caller had explicitly tried to raise and been silently refused.

### (b) The routed outer envelope's `duration_seconds` contradicts its own job log

Same run. The outer envelope returned to the caller:

```
status: error
exit_code: -1
duration_seconds: 0
error: execution_failed
```

while the job log for that very job reported `duration_seconds: 600`. The outer envelope claims the job consumed no time at all, and reports a generic `execution_failed` where the job log carries the specific and actionable `error: timeout` with `timeout_used_seconds`.

A caller that trusts the outer envelope concludes "the build failed instantly" and looks for a startup/config fault. The truth — "your timeout was overridden and the job was cut off at the overridden value" — is only recoverable by knowing to open the job log.

## Why it matters

Both are the epic's signature shape: a confident signal hiding a caveat.

(a) is worse than a missing feature, because the flag is *accepted*. `--timeout` is declared in the argparse surface and documented as "Build timeout in seconds". A caller reasonably reads acceptance as effect. An unsupported flag that errored would be strictly better than one that is silently dropped.

(b) compounds it: the one field that would have exposed the truncation (`duration_seconds: 600`) is zeroed on the way out, and the specific error code is generalised away. The existing standing rule "never trust a routed build's outer status" was written about exit-0-hiding-failure and the fix shipped in #979 addressed that axis. This is the same class on the *duration* and *error-code* axes, still live.

## Directive

Fix at the tool layer — do not paper over this with caller-side guidance to "always read the job log".

1. **Make the daemon honour `--timeout`, or fail closed.** If the daemon has a hard ceiling it cannot exceed, a request above that ceiling must be REFUSED with a named error (`timeout_exceeds_daemon_ceiling`, carrying the ceiling value) rather than silently clamped. Per ADR-009, an unsatisfiable request yields an explicit refusal, never a quiet substitution.

2. **If clamping is genuinely the intended behaviour**, the returned TOON must carry the effective value (`timeout_used_seconds`) and a `timeout_clamped: true` marker at the OUTER envelope, so acceptance-implies-effect holds or is visibly denied at the point the caller reads the result.

3. **Propagate `duration_seconds` and the specific `error` code from the job log into the outer envelope.** `duration_seconds: 0` for a job that ran 600s is a false statement, not merely an omission. The outer envelope should surface the job's own `error: timeout` rather than flattening it to `execution_failed`.

4. **Add a test pinning outer-envelope/job-log agreement** on `duration_seconds` and `error` for at least the timeout path, so the two cannot drift apart again.

## Recurrence — 2026-07-27 (retrospective-checker-assertion-integrity)

Third axis on the same routed-build envelope, and the most dangerous one: **a
daemon wait-timeout was reported as a hard build failure while the supervised
child ran to completion and PASSED.**

**What happened.** `verify plan-marshall` was submitted on the routed path. The
build's own log records the truth:

```
12635 passed in 864.37s
=== verify: SUCCESS ===
```

The daemon job record for that same job reported:

```
status: timeout
exit_code: -1
duration_seconds: 622
```

and the outer wrapper TOON degraded it further to the already-known axis (b)
shape: `status: error, duration_seconds: 0`.

The daemon's wait timeout (622 s) was shorter than the real build duration
(~880 s). The child was never killed — it kept running and finished green ~4
minutes after the daemon had already declared the job failed. Ground truth was
recoverable only by opening the daemon job log and then, from it, the underlying
build log. The adaptive timeout self-corrected on the very next run (resolved
1397 s), so this is a **race between the learned timeout and a slow cold-cache
build**, not a static misconfiguration — which is exactly why it will recur
intermittently rather than reliably.

**What this adds.** Axes (a) and (b) above are about a build that genuinely was
truncated being *described* badly. This axis is the **mirror of the usual
false-green**: a real green reported as a hard failure. Its cost profile is
inverted and worse for the pipeline — an unwary run reads `status: error` and
enters a fix loop or a spurious loop-back against a tree that already passes,
burning a full remediation cycle to "fix" nothing.

The category error is that **the daemon conflates "I stopped waiting" with "the
job failed."** Wait-expiry is a statement about the supervisor's patience; it
carries no information about the child's outcome, and in this instance the child
had not even finished yet. `exit_code: -1` asserts a process result that did not
exist at the moment it was emitted.

**Directive (added).**

5. **A wait-expiry must not be reported as a terminal failure.** When the daemon
   stops waiting on a job whose child is still running, the returned status must
   be a distinct non-terminal value (`wait_expired` / `unknown`, per ADR-009's
   explicit-refusal-over-quiet-substitution rule) carrying the still-live job id,
   never `status: timeout` + `exit_code: -1`. `exit_code` must be absent while no
   exit code exists.

6. **Reconcile the job record when the child finally exits.** The child's real
   terminal outcome is known ~4 minutes later; the job record must be updated
   with it, so a subsequent poll on the same job id returns the truth instead of
   the frozen wait-expiry verdict. A wait-expiry that is never reconciled makes
   the false-failure permanent in the record.

7. **Never treat a routed `status: timeout` / `status: error` as build failure
   without reading the job log, and the build log below it.** This is the
   caller-side stopgap until (5) and (6) land — the tool-layer fix is still the
   real remedy. Note the symmetry with the standing rule "never trust a routed
   build's outer status": the outer status is untrustworthy in *both* directions,
   and a plausible-looking failure deserves the same corroboration a plausible
   green does.

**Related.** `2026-07-21-09-001` (build-pyproject adaptive internal timeout
self-caps below the architecture-resolved ceiling, returning a false
`status: timeout`) is the in-process sibling of this same false-timeout shape;
`2026-07-22-00-001` (task-envelope `bash_timeout_seconds` inherits the volatile
learned timeout with no floor) is the upstream cause-class. Together with this
recurrence they say the same thing about learned timeouts: **a self-rewriting
learned duration must never be the sole arbiter of a failure verdict.**

## Recurrence — 2026-07-28 (orchestrator-inbox-pickup)

Fourth axis, orthogonal to (a)/(b)/wait-expiry-as-failure: **the daemon does not
reap the child process when it stops waiting on it.** In this run, a `pytest`
child kept executing roughly 30 minutes past the point the daemon had already
reported the job as failed (the same wait-expiry-as-terminal-failure shape as
the 07-27 recurrence). Because the process was never killed or reaped, it
stayed resident and competing for the machine's CPU/IO for the full 30
minutes — and its load measurably corrupted the wall-clock timing of a
*separate, concurrent* build submitted after it. A caller reading the second
build's duration had no way to know an invisible orphan from an earlier,
already-reported-failed job was still running underneath it.

This closes the loop on why (5)/(6) above are necessary rather than cosmetic:
a wait-expiry that is merely *mis-reported* (the 07-27 shape) is bad enough,
but a wait-expiry that also **leaves the child alive and unmanaged** turns a
truthfulness bug into a resource-isolation bug — every subsequent build
submitted to the same daemon shares its host with however many orphans have
accumulated, with no accounting for their load anywhere in the returned
envelope.

**Directive (added).**

8. **On wait-expiry, the daemon must terminate (or explicitly detach-and-track)
   the child process — never merely stop polling it.** "I stopped waiting" and
   "the child is still consuming host resources" must not both be true with no
   record of the second fact anywhere the caller can see.

9. **If the daemon deliberately lets a wait-expired child run to completion
   (to preserve (6)'s reconciliation value), it must track that child's
   resource footprint and make the running-orphan count/list visible** (e.g.
   via a daemon status verb), so a caller investigating an implausible
   duration on a *different*, concurrent build can attribute it to background
   orphan load instead of treating the anomaly as unexplained.

**Related.** Same underlying family as the wait-expiry-as-failure recurrence
above — the daemon's child-lifecycle model on timeout is under-specified on
two axes now: what status it reports (axis 5/6) and what happens to the
process itself (axis 8/9).
