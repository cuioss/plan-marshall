# argparse_surface derivation misses a dynamically-registered GitHub-only flag on ci pr list

A from-scratch executor regeneration (delete `.plan/execute-script.py`, then `generate_executor.py generate --marketplace --marketplace-root .`) still produced `SCRIPT_SURFACES` flags `[head, state]` with no `limit` for `plan-marshall:tools-integration-ci:ci pr list`, even though `ci.py`'s own argparse (verified via a direct `--help` through the executor, which bypasses validation) correctly declares `--limit`. Two consecutive full regenerations (`surfaces_derived=116, surfaces_reused=0` on the second) reproduced identically, ruling out stale-cache reuse as the cause.

The flag is registered dynamically GitHub-side via `pr_sub.choices.get('list').add_argument(...)` in `github_ops.py` (added by an earlier task in plan `pr-065-settings-repo-accumulates-never-lands`), rather than declared inline in the initial `add_argument` sequence for the shared `pr list` subparser. Hypothesis: the derivation's `--help` subprocess invocation does not exercise whatever code path performs that dynamic registration, so the captured surface reflects the pre-registration parser state.

Needs investigation in `argparse_surface` (`script-shared`) or in `ci.py`'s provider-detection/dynamic-registration path. Workaround used: omit `--limit` and rely on the script's own default limit (100) when the population is smaller than that default — `truncated: false` in the response proves completeness without needing the blocked flag.
