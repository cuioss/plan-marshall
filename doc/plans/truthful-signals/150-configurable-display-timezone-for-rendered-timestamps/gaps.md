## G1 — Make the D5(c) storage-invariant test assert the digits, not a format literal

- **Kind:** vacuous-test
- **Severity:** high
- **Where:** `test/plan-marshall/manage-run-config/test_display_time_render.py:120` — `test_stored_timestamp_is_utc_under_any_knob_value`
- **What is wrong:** The test sets `display_timezone: 'Asia/Kolkata'`, asserts the knob reads back, then asserts `now_utc_iso().endswith('Z')`. The `Z` is a literal character inside the format string at `marketplace/bundles/plan-marshall/skills/tools-file-ops/scripts/file_ops.py:91` (`datetime.now(UTC).strftime('%Y-%m-%dT%H:%M:%SZ')`), so it survives any timezone conversion. Mutation-confirmed **twice, by two independent agents**: rewriting `now_utc_iso` to `datetime.now(UTC).astimezone(ZoneInfo('Asia/Kolkata')).strftime('%Y-%m-%dT%H:%M:%SZ')` — precisely the defect the test names — leaves it **green** (`uv run python -m pytest …::test_stored_timestamp_is_utc_under_any_knob_value -o addopts="" -q` → `1 passed`). The adversarial re-run additionally ran the plan's **entire** suite under that mutation: **25 passed** — no test in the plan observes the defect.
- **Why it matters:** `plan.md` § Verification marks D5(c) with ⛔ as *the* invariant test — the refusal in the Problem section expressed as an assertion. As written it certifies an invariant it cannot observe: a future change that let the display zone reach the write path would ship with this test green, which is this epic's namesake false signal. (The D4 guard would still catch the realistic form of that change, because it scans for the knob-consumer symbols; D5(c) adds no independent protection today.)
- **Fix:** Assert the value, not the suffix. Parse the produced stamp and compare it against an independently computed UTC clock, e.g. `parsed = datetime.strptime(now_utc_iso(), '%Y-%m-%dT%H:%M:%SZ').replace(tzinfo=UTC)` then `assert abs((parsed - datetime.now(UTC)).total_seconds()) < 60`. Better still, freeze the clock (monkeypatch `file_ops.datetime`) and assert the exact expected string, so the test is deterministic. Add the same shape for at least one other store primitive that is written *and* later compared — the lesson-identifier prefix built at `marketplace/bundles/plan-marshall/skills/manage-lessons/scripts/manage-lessons.py:148-151` (`now = datetime.now(UTC)` → `date`/`hour` → `prefix`) is the plan's own named STORE trap and its date/hour digits would visibly move under a converted clock.
- **Done when:** Applying the `astimezone(ZoneInfo('Asia/Kolkata'))` mutation to `file_ops.now_utc_iso` (and to the `manage-lessons` prefix derivation) turns the D5(c) test RED, and the unmutated tree is green.
- **Module/topic:** `plan-marshall:manage-run-config` — display-timezone tests (`test/plan-marshall/manage-run-config/`)

## G5 — The D4 guard whitelists whole RENDER files, and its stated mitigation does not exist

- **Kind:** guard-blind-spot
- **Severity:** high
- **Where:** `test/plan-marshall/manage-run-config/test_display_timezone_guard.py:140` — `allowed = set(classification['render_files']) | set(classification['knob_owner_files'])`; and `test/plan-marshall/manage-run-config/timestamp_render_classification.json` — the artifact that is supposed to record the limitation
- **What is wrong:** The isolation assertion is **file-granular**: any occurrence of a knob-consumer symbol inside a declared RENDER file is allowed unconditionally. Both whitelisted RENDER files also contain STORE writes, so the exemption is not theoretical:

  - `plan-retrospective/scripts/compile-report.py:66` builds the archived-report **filename** stamp (`'%Y%m%dT%H%M%SZ'`, explicitly "collision-free" and therefore sort-bearing).
  `render_timestamp` is already imported and in scope in both files, which makes these the *most* likely places in the whole tree for a future author to reach the knob by accident — and exactly the places the guard cannot see. **Mutation-confirmed:** replacing `data[_TOTALS_SAMPLED_AT_FIELD] = now_utc_iso()` at `manage-metrics.py:1945` with `render_timestamp(datetime.now(UTC), '%Y-%m-%dT%H:%M:%S', 'Z')` — a STORE field consulting `display_timezone`, precisely the leak D4 names — leaves the guard **green** (`test_display_timezone_guard.py` + `test_display_time_render.py` → `16 passed`). Separately, `report-01.md` § Findings **F3** accepts this granularity on the stated ground that *"the granularity is documented in the classification artifact"* — **it is not**: `grep -ni "granular\|file-level\|whole file\|whitelist\|per-file"` over `timestamp_render_classification.json` and `test_display_timezone_guard.py` returns **zero matches**. The accepted risk was accepted against a mitigation that was never written.
- **Why it matters:** `plan.md` D4 is the deliverable that *"keeps the refusal above true a year from now"*. A guard that stays green while a `metrics.json` field is converted to a civil zone is a guard passing against the defect it names — and the resulting corpus is exactly the plan's reason 2 failure mode (records written under different configured zones, incomparable, with no error). The false mitigation compounds it: a future reader who consults the classification artifact, as F3 directs, finds no caveat and reads the guard as site-granular.

In `timestamp_render_classification.json`, each `render_sites` entry already carries a `routed_through` expression; add a `render_call_budget` integer per entry (1 for each of the two sites today). In `test_display_timezone_guard.py::test_knob_symbols_never_reach_a_store_or_compare_site`, for each declared RENDER file assert `text.count('render_timestamp(') == budget` instead of exempting the file wholesale, so an added conversion call in a whitelisted file fails the guard and forces a deliberate classification update. If site-granularity is judged too costly, the minimum acceptable alternative is to make the artifact honest: add a `_guard_granularity` key to `timestamp_render_classification.json` stating that RENDER files are exempted whole-file and naming the STORE writes each one still contains, and print it in the census the guard publishes.
- **Done when:** Applying the `manage-metrics.py:1945` mutation above (routing `totals_sampled_at` through `render_timestamp`) turns `test_display_timezone_guard.py` **RED**, and the unmutated tree is green — **or**, under the fallback, `grep -n "_guard_granularity" test/plan-marshall/manage-run-config/timestamp_render_classification.json` returns the new key and the guard's census output contains it.

## Refuted during adversarial review

Nothing recorded above was refuted outright. Two items were considered and are recorded here so a
later reader does not re-open them.

### G3, refuted clause — "`DEFAULT_STRUCTURE` omits `display_timezone`, so `run_config init` never writes it"

The observation is true but is **not a defect of this plan**, and the original G3 wrongly made it the
primary remedy. `DEFAULT_STRUCTURE` (`marketplace/bundles/plan-marshall/skills/manage-run-config/scripts/run_config.py:60-66`)
seeds exactly three keys — `version`, `commands`, `maven`. **Every** optional section documented in
`manage-run-config/standards/run-config-standard.md` § "Optional Sections" is likewise unseeded:
`architecture_refresh`, `ci_durations`, `language_servers`, `derivation_resolvers`, and
`display_timezone`. Seeding only `display_timezone` would make it the sole exception to an
established, uniform convention. Changing that convention is a `run-configuration.json`-wide policy
decision — the analogue of what plan 090 does for `marshal.json` — and is not residue this plan
owes. G3 has been rewritten to drop this clause and to rest on the steward-menu asymmetry, which is
real: the steward *does* route to `derivation_resolvers`, `language_servers`, and
`architecture_refresh`, and routes to `display_timezone` from nowhere.

### Candidate gap considered and rejected — `ref-workflow-architecture/standards/manage-contract.md:105-117`

A sweep broader than the one verification ran surfaced § "Timestamp Format": *"All timestamps use ISO
8601 format in UTC timezone … Always UTC (Z suffix, never timezone offset)"*, declared as a canonical
format *"used across all manage-\* skills"*. This looks like a statement the plan made conditionally
false, since `manage-metrics` is a manage-\* skill that now renders a convertible timestamp. It is
not: the section scopes itself to values *"Generated via `now_utc_iso()` from `file_ops`"*, and the
`Generated:` line in `metrics.md` neither used `now_utc_iso()` nor carried the `YYYY-MM-DDTHH:MM:SSZ`
shape before this plan (it was `%Y-%m-%d %H:%M:%S UTC`). The statement was already outside that line's
scope pre-plan and remains accurate for every field it does govern. No gap.
