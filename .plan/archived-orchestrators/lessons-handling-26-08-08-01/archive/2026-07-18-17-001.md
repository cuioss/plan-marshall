# A daemon must containment-verify EVERY independently client-settable path field that reaches execution, not just the primary one

## Context

Discovered by the phase-6-finalize security-audit during plan-server-core (the
`marshalld` opt-in build-server epic). The daemon accepts a build request from a
client and, before executing, verifies the request against the registration record
to enforce that a client cannot make the daemon run an arbitrary binary.

## Defect (S2)

The verifier checked the client-supplied `exec_path` against the registered
executable — the obvious trust-boundary field — but did NOT verify the client-supplied
`project_path`. `project_path` is an independently client-settable field that is used
**verbatim as the build subprocess `cwd`**. A client could therefore leave `exec_path`
matching the registration (passing the check) while pointing `project_path` at an
arbitrary directory, steering execution outside the registered project. Only one of
the two execution-reaching path fields was containment-verified; the second was a
silent hole.

All in-house structural gates were green — the wired-flow tests exercised the
`exec_path` verification path. The gap surfaced only because the finalize
security-audit stage independently modeled the daemon's full input surface and asked
"which client-settable fields reach execution?" rather than "is the primary field
checked?".

## Directive

When a daemon (or any privileged executor) accepts **multiple independently
client-settable fields that reach execution parameters** — the binary, the cwd,
the environment, argv, a config path, a working directory — EVERY such field is a
distinct trust-boundary crossing and MUST be containment-verified against the trusted
registration/policy. Verifying only the primary/obvious field (the executable) leaves
the secondary fields (cwd, env, args) as an open channel: an attacker holds the
verified field constant and pivots through the unverified one.

Concretely:

- Enumerate the full set of client-settable fields that flow into the execution call
  (subprocess `args`, `cwd`, `env`, and any path derived from them), not just the one
  that named the intent.
- Apply the same containment check (registration match / allowlist / path-prefix
  confinement) to each field independently.
- A wired-flow / integration test must assert the containment failure for EACH such
  field in isolation (hold the others valid), or a newly-added field silently
  re-opens the hole — mirrors lesson 2026-07-16-17-007 (every new security binding
  needs its own wired-flow assertion).
