# get-module-context treats the legitimate phase-3 not_yet_materialized worktree state as worktree_resolution_failed

## Problem

`manage-solution-outline get-module-context` exits 2 with `worktree_resolution_failed` when invoked
during phase-3-outline, even though the plan is in a completely normal state for that phase.

`manage-status get-worktree-path` for the same plan correctly reports `worktree_state: pending` /
`not_yet_materialized: true` — the expected state, because the worktree is not materialized until
phase-5-execute Step 2.5 (ADR-002 move-based model). `get-module-context` treats that legitimate
pre-materialization state as a hard resolution failure rather than as a known, non-error state.

Observed on plan `executor-version-split-resolvers` (2026-07-26): the phase-3-outline envelope had to
skip an optional additive outline section and log a WARNING instead of consuming module context.

## Impact

Every deep-lane phase-3-outline run silently loses the module-context section. The failure is
non-fatal only because the consuming step is optional — a required consumer would hard-stop the
outline phase for a plan that is in a perfectly valid state.

This is the fail-closed-guard-misclassifies-a-normal-state archetype: the guard is correct to refuse
an *unresolvable* worktree, but `not_yet_materialized` is not unresolvable, it is "not yet, by
design".

## Directive

- Teach `get-module-context` the three-state contract `manage-status get-worktree-path` already
  returns: resolve against the current checkout when `worktree_state: pending` /
  `not_yet_materialized: true` (phases 1-4 run on the main checkout), and reserve
  `worktree_resolution_failed` for a genuinely unresolvable worktree.
- Add a regression test pinning the phase-3 (`not_yet_materialized`) invocation to a success return
  with main-checkout-anchored module context.
- Audit sibling `manage-solution-outline` verbs for the same conflation of "not yet materialized"
  with "resolution failed".
