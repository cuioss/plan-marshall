# Re-review freshness matcher shipped with naive-datetime comparison + gh-api --paginate-without-slurp; all in-house gates passed, only adversarial PR bots caught them

## Context

The plan `phase-6-finalize-post-merge-re-review` (PR #742) added a brand-new
re-review mechanism to phase-6-finalize: a `bot_kind`-keyed strategy registry whose
`await_fresh_review(pr_number, head_sha, trigger_time)` method polls a PR's reviews
until one is found whose reviewed commit SHA matches HEAD and whose `submittedAt`
is later than the trigger time. The core matcher lives in the new
`marketplace/bundles/plan-marshall/skills/workflow-integration-github/scripts/github_re_review.py`,
with the supporting reviews-fetch in `github_ops.py`
(`fetch_pr_reviews_with_commits`).

The plan shipped through the full in-house gate chain clean — phase-3-outline
q-gate-validation, phase-4-plan, phase-5 task execution (module-tests +
quality-gate), pre-submission self-review, and the scoped plugin-doctor
`quality-gate` — yet the **adversarial PR review bots (CodeRabbit + Gemini) caught
distinct correctness defects** in the freshness matcher and its reviews-fetch
that every in-house gate let through. All were caught-and-fixed in-run (the
highest-value lesson class: slipped, then caught), on PR #742.

## The defects (all in the same new re-review surface)

1. **Timezone-naive vs timezone-aware datetime comparison `TypeError`** (gemini
   `b56790`, coderabbit `f9faac`). `_parse_iso` did
   `datetime.fromisoformat(value.replace('Z', '+00:00'))` with no guard for input
   that carried no timezone info. GitHub timestamps end in `Z` (→ aware), but a
   timezone-naive ISO string (a manual CLI invocation, a local-git-derived
   `trigger_time`) parses to a **naive** datetime. Comparing the naive
   `trigger_dt` against the aware `submitted_dt` from the GitHub API raises
   `TypeError: can't compare offset-naive and offset-aware datetimes` and crashes
   the poll. Fix: coerce a naive parse result to UTC
   (`dt.replace(tzinfo=UTC)` / `astimezone(UTC)`).

2. **`gh api --paginate` parsed without `--slurp`** (coderabbit `4a06e7`).
   `fetch_pr_reviews_with_commits` called `gh api {endpoint} --paginate` then did a
   single `json.loads(stdout)`. Without `--slurp`, `gh api --paginate` emits
   **multiple separate JSON arrays — one per page** — which is not a single JSON
   document, so `json.loads()` fails the moment the reviews list spans more than
   one page. On a low-traffic PR the first page is the whole list and the bug is
   invisible; it only bites a PR with enough reviews to paginate. Fix: add
   `--slurp` (which wraps all pages in one outer array) and flatten the
   list-of-pages before the per-review projection.

A further, nitpick-level item (coderabbit `6adcb6`) was the missing regression test
for the timezone-naive `trigger_time` path — addressed by adding
`test_parse_iso_naive_datetime_is_normalized_to_utc` to
`test_re_review_strategy.py`.

## Why every in-house gate missed them

- **plugin-doctor `quality-gate`** certifies *structure* (frontmatter, nesting,
  naming, prose/canonical-invocation rules). A naive-datetime parse and a
  `--paginate`-without-`--slurp` call are both structurally well-formed Python;
  neither is a structural violation.
- **pre-submission self-review** surfaces plan-marshall-domain deterministic
  candidates (regexes, symmetric pairs, contract drift, count-prose, lone-unguarded
  boundary calls, …). None of its candidate classes targets *timezone-awareness in
  a datetime comparison* or *CLI-flag-completeness of a `gh api` pagination call*.
  So the cognitive review pass — bounded to the surfaced candidates — was never
  handed either of them.
- **module-tests + quality-gate** passed because the unit tests covered only the
  *happy path*: timestamps that already carried `Z` (aware), and reviews payloads
  small enough to fit one page. The divergent cases (naive input, multi-page
  pagination) were each **untested**, so the green suite was false-confidence on
  exactly the inputs that break.

This is the **freshness-matcher / external-API-fetch specialization** of the
standing "in-house gates check structure, not domain correctness" family
(`2026-06-16-14-001`, and its siblings `2026-06-20-16-004` phase-5 doc-port and
`2026-06-21-12-001` security-deny-list-canonicalization). The gate chain certifies
properties orthogonal to the one that actually matters for a time-comparison
freshness gate and a paginated API fetch: *timezone-awareness soundness* and
*pagination-completeness*.

## Recurrence signature

- A plan adds (or edits) a matcher/gate that **compares datetimes**, or a function
  that **parses a paginated `gh api` / external-API response**.
- The datetime parse has no timezone-awareness guard (`fromisoformat` on input that
  may be naive), OR a `--paginate` fetch is `json.loads`-ed without `--slurp`.
- module-tests/quality-gate pass; plugin-doctor `quality-gate` passes;
  pre-submission self-review surfaces no candidate.
- Only the adversarial PR review bots (CodeRabbit / Gemini) flag the bug —
  because they read the matcher/fetch logic against attacker/edge-case intent, not
  against the in-house structural rule set.

## How to apply

- **Datetime comparison soundness.** Any code that compares two datetimes must
  guarantee both sides share timezone-awareness. When parsing external timestamps,
  normalize to aware-UTC at the parse boundary (coerce a naive parse to UTC or
  reject it) — never let a naive datetime reach a comparison against an aware one.
  `datetime.fromisoformat` on input that *might* lack a timezone is the canonical
  trap; guard it at the single parse helper, not at each call site.
- **`gh api --paginate` always needs `--slurp` before `json.loads`.** A bare
  `--paginate` emits one JSON document *per page*; only `--slurp` wraps them into a
  single array. Pair the two flags whenever the result is parsed as one document,
  and flatten the page list. A single-page test will never expose the gap — add a
  multi-page fixture (or at least assert the `--slurp` flag is present in the
  constructed argv).
- **Test the divergent inputs, not just the happy path.** The defects each
  hid behind a green suite that exercised only aware timestamps and single-page
  payloads. For a parser/matcher, the regression tests that matter are the
  adversarial ones: naive-tz input and multi-page pagination. Add them at
  authoring time so the in-house gate, not the PR bot, is the one that catches the
  class.
- **For any new external-API-fetch or time-comparison surface, treat a clean
  in-house gate run as necessary-but-not-sufficient.** The gate chain is silent on
  timezone-awareness and pagination-completeness — exactly the properties an
  adversarial reviewer reads for. Where the deliverable's value IS that correctness
  (a freshness gate, a paginated fetch), budget for the PR-bot round trip or
  pre-empt it with explicit edge-case tests.

## Impact

The re-review mechanism is the plan's central deliverable. Had the defects
shipped: the naive-datetime crash would have taken down any re-review triggered
from a local-git-derived trigger time, and the `--paginate`-without-`--slurp`
parse would have crashed on any PR with enough reviews to paginate. All were
caught in-run by the PR bots and fixed before merge, but each is the kind of
correctness defect that in-house structural gates are constitutionally unable to
see — recorded here so the next plan that adds a datetime matcher or a paginated
`gh api` fetch front-loads the edge-case tests instead of re-discovering the class
via a PR-bot round trip.
