# Rate-limit refusal matching a registered refusal_pattern was filed as a finding and counted as participation

On PR cuioss/cui-http#199, Sourcery published a rate-limit refusal instead of a review.
The pipeline recorded it as an ordinary review comment, counted Sourcery as having
participated, and an agent hand-triaged it to `taken_into_account`. A reviewer that
reviewed nothing was recorded as a reviewer that reviewed.

## What was recorded

`artifacts/findings/pr-comment.jsonl`, finding `c84b98`:

```json
{"hash_id": "c84b98", "type": "pr-comment", "kind": "review_body",
 "author": "sourcery-ai", "bot_kind": "sourcery",
 "resolution": "taken_into_account",
 "resolution_detail": "Informational rate-limit notice from sourcery-ai (own review budget exhausted for 7 days) - no review content to act on, not a code suggestion",
 "body": "Sorry @OliverWolffGIP, you've used your own review budget of 250,000 diff characters for the last 7 days. ..."}
```

The producer reported `refused_bots: []` and `count_skipped_refusal: 0`.

## Why this is a defect, not a triage judgement

The body is a *registered* refusal, not an unrecognised one. `sourcery`'s registry block in
`automatic-review/standards/sourcery.md` declares:

```yaml
refusal_patterns:
  - "your pull request is larger than the review limit of"
  - "reached your weekly rate limit of"
  - "used your own review budget of"     # #1391 refusal notice
```

Verified against the version live during the run (`0.1.1589`):

```text
>>> [p for p in bot_registry.refusal_patterns('sourcery') if p in body]
['used your own review budget of']
```

The record also carries `bot_kind: sourcery`, so the producer had everything the
registry arm of `_github_pr._is_refusal_notice(body, bot_kind)` needs — a matching
registered pattern and a resolved bot_kind — and the refusal pre-filter still did not
fire. `github_pr.cmd_fetch_findings` should have taken the pre-filter-2 REFUSAL branch:
increment `skipped_refusal`, add `sourcery` to `refused_set`, and emit **no** finding.

`_is_refusal_notice`'s own docstring names the consequence exactly:

> Dropping the refusal is precisely what let a PR whose every required reviewer refused
> report a clean, complete review with substantively zero review coverage.

## Why it did not bite this time, and why that is luck

`sourcery` is in `optional_bots` for this repository, so its participation did not gate
the merge. Had it been in `required_bots`, the quorum layer would have counted a
manufactured participation and let a PR through with one fewer real reviewer than it
believed it had — silently, with no WARNING and no operator prompt. The blast radius is
set by config, not by the defect.

## Rules

1. **A refusal is positive evidence of NON-participation. It must be classified by the
   producer, never by hand-triage.** An agent resolving a refusal notice as
   `taken_into_account` is a symptom that the branch above it did not fire — treat that
   resolution on a rate-limit body as a bug report, not as a completed triage.
2. **Never infer refusal handling from the absence of a finding-shaped problem.** The
   only trustworthy signals are `refused_bots[]` and `count_skipped_refusal`. Empty
   `refused_bots` next to a finding whose body matches a registered `refusal_pattern` is
   the contradiction to look for.
3. **When a refusal reaches triage, re-run the registry arm before judging it.** If
   `bot_registry.refusal_patterns(bot_kind)` matches the body, the defect is upstream of
   triage; record it instead of absorbing it.

## Open question for whoever picks this up

The refusal arrived as `kind: review_body` (a PR review body, id `PRR_…`), not as an
`issue_comment`. The pre-filter loop in `github_pr.cmd_fetch_findings` iterates
`raw_comments`, and `_THREADLESS_KINDS` includes `review_body`, so review bodies are
expected to pass through the same filter — but this run is a counter-example, so whether
review bodies actually reach pre-filter 2 is the first thing to check. The alternative
hypothesis is that this finding was written by a path other than `fetch_findings`; note
that the same round logged an argparse rejection of
`plan-marshall:automatic-review:review_completeness check` (exit 2,
`logs/work.log:420`), so hand-assembly during recovery cannot be ruled out from the
artifacts alone.
