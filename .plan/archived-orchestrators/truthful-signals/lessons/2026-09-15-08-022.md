# A --help walk against the DEPLOYED copy reported a worktree-registered verb as unregistered

Source: Q-Gate finding 181b07 (5-execute, resolution=rejected — stale-evidence false positive).

plugin-doctor's ARGUMENT_NAMING_SUBCOMMAND_UNKNOWN reported that
manage-locks/SKILL.md:418 documents a `queue-list` subcommand that merge_lock.py does
not register, "confirmed via --help". The finding was wrong. merge_lock.py DOES register
queue-list (subcommands entry name 'queue-list' -> run_queue_list at lines 2134-2138,
named in the epilog at 2092), and create_workflow_cli registers every entry regardless
of an empty args list.

The evidence was a --help walk against a DEPLOYED copy predating the registration:
TASK-018 landed it at 21:43:57 in commit 991bce8df, thirty minutes before the finding
was filed at 22:14:17. The running copy's epilog omits the queue-list example the
worktree source carries.

## Solution

A rule that probes a live process cannot treat that process as the source of truth for
worktree code. Executor regeneration and plugin-cache sync are FINALIZE-time steps, so
during execute the deployed copy is systematically behind. Either read the worktree
source, or publish which copy was probed so the verdict is falsifiable.

## Impact

Blocked a per-task gate twice and consumed a triage round. A related recurrence in the
same run cleared 482 stale .plan/temp/plugin-doctor-help-cache/ entries after a second
false manage-invocation-invalid for `architecture derived-module --module`.
