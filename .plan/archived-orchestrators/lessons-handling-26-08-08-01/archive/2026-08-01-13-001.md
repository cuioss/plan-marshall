# A pytest run that reached its own green summary is still reported status=timeout exit_code=-1 when the wrapper budget expires in teardown - a false red over a completed suite

## What happened

During `phase-5-execute` of plan `path-attribution-seam`, the per-task breakable-test gate ran the
architecture-resolved canonical `module-tests plan-marshall`. The wrapper returned:

```toon
status: timeout
exit_code: -1
duration_seconds: 330
error: timeout
timeout_used_seconds: 330
```

Read at face value this is a red gate. Parsing the same run's build log through the structured slice
tells the opposite story:

```json
{"data": {"build_status": "SUCCESS", "issues": [], "summary": {"total_issues": 0}},
 "metrics": {"tests_run": 14124, "tests_failed": 0}}
```

pytest emits its `N passed` summary line only after the last test finishes, so the presence of a
14124/0 summary in the log proves the suite ran to completion. The wrapper's 330s budget expired
somewhere after that summary was written — in teardown, coverage finalisation, or the wrapper's own
subprocess wait — and the wrapper stamped the whole job `timeout` / `exit_code: -1`.

## Why it matters

This is a **false red over a completed, fully-green suite** — the inverse polarity of the more
familiar false-green defect, and strictly worse for throughput than a slow build:

- A caller that branches on the wrapper's outer `status` marks the task blocked, routes into Step 11
  triage, and hands `verification-feedback` a finding set that is empty — there is nothing to FIX,
  SUPPRESS or ACCEPT, because no test failed.
- The condition is **not** self-correcting. The adaptive timeout learns from *successful* runs, so a
  run that always trips the budget never raises it. Every subsequent task in the same plan pays the
  full budget and gets the same false red — here, once per task across an 11-task plan.
- A blind retry is the natural but wrong response: the suite legitimately needs more than the budget,
  so the retry reproduces the identical signal. This is exactly the identical-repeated-failure
  trigger that demands a provenance check before re-attempting.

## The rule

**A `status: timeout` from the build wrapper is a claim about the wrapper's clock, not a verdict on
the suite.** Before treating a timeout as a gate failure, parse the run's log through the structured
slice and read `build_status` / `tests_run` / `tests_failed`:

- Log carries a completed summary with `tests_failed: 0` → the suite passed. The timeout is a
  tool-layer misreport; record the evidence and do not route the task into failure triage.
- Log carries no summary line, or a summary with failures → the timeout is real (or is masking real
  failures); triage normally.

The same asymmetry the project already records for the outer status of a *routed* build applies here:
never trust the outer status alone, in either direction. An implausible `duration_seconds: 0` on the
routed envelope wrapping a `duration_seconds: 330` inner job is a second instance of the same
signal-laundering — the outer report discarded the inner one's duration entirely.

## Fix direction (tool layer)

The wrapper owns both halves of this and should not need a caller-side workaround:

1. **Reconcile the timeout verdict against the log before stamping it.** When the wrapper's budget
   expires but the captured log already contains a terminal pytest summary, the run's outcome is that
   summary, not `timeout`. At minimum emit a distinct status (e.g. `completed_over_budget`) so the
   two cases are separable without a second parse — collapsing them into `timeout` is the fail-closed
   discipline applied in the wrong direction.
2. **Let the budget learn from over-budget completions.** A run that finished at 330s+ is evidence
   the estimate is too low; discarding it because the job was stamped `timeout` is what keeps the
   estimate permanently stale.
3. **Propagate the inner duration through the routed envelope.** `duration_seconds: 0` on the outer
   report when the inner job ran 330s destroys the one field a caller would use to sanity-check the
   verdict.
