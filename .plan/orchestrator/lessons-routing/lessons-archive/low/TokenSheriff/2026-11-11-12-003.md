# Script invocations written from narrative or a sibling script are rejected by argparse: copy the canonical block (flag, verb, typed-ID flag, router-flag position)

## Problem

Agents keep writing script invocations from narrative or from a sibling script instead of copying the canonical-invocation block, and argparse rejects them (`exit_code=2`, `failure_kind=argparse_rejection`). The call is retried and succeeds, so no plan is blocked, but every instance is a wasted round and the same class has now recurred across three plans (quality-report epic: PLAN-26, PLAN-27, PLAN-28). The shapes seen:

1. **Invented flag borrowed from a sibling script.** `manage-findings list --limit N`: `--limit` exists on `manage-logging read`, not on `manage-findings list`, whose pr-comment output (51 KB for one plan) is the real motive for wanting it. Either the script needs a paging flag or its canonical block should say it has none.
2. **Invented verb.** `manage-findings qgate query` (the `qgate` noun registers only `add`, `clear`, `list`, `resolve`, `resolve-by-rule`, `resolve-evidenced`); issued twice nine minutes apart in one phase, so the first rejection did not correct the second call. Again `manage-findings query` (`query` is not a registered verb; the read verbs are `list` and `get`), PLAN-28 phase 6, work-log hash b83704.
3. **Required flag omitted.** `manage-references get` without `--field`, PLAN-28 phase 3-outline, hash 459284.
4. **Typed-ID flag shortened.** `manage-solution-outline get-deliverable --number` instead of `--deliverable-number`, PLAN-28 phase 5-execute, hash 6a94f5.
5. **Script name repeated as a verb.** `tools-integration-ci:ci ci checks ...`: the notation already names the script, so `ci` is not a valid first token (`pr`, `checks`, `issue`, `branch`, `repo`, `org`), PLAN-28 phase 6, hash 9545f1.
6. **Router flag after the verb.** `architecture search --content --pattern ... --plan-id P`: `--plan-id` and `--project-dir` are declared only at the top level, so they go BEFORE the verb (`architecture --plan-id P search ...`). The script prints the corrected form (`misplaced_router_flag`). The same agent had issued two correctly ordered calls two minutes earlier, so the position was known but not applied consistently (PLAN-26, hash ad988d).

Side observation from case 6: after the plan worktree was removed, the same correctly ordered `architecture --plan-id P search` call returned `status: success` with `files_scanned: 0`. A post-merge search through `--plan-id` silently scans nothing instead of failing, a fail-open read that deserves an error or a warning when the resolved worktree is absent.

## Solution

1. Caller side: copy the invocation from the script's canonical-invocation block, flag by flag and verb by verb; never carry a flag or a verb over from a sibling script, never shorten a typed-ID flag, never repeat the script name, and place router-scoped flags before the verb. Before a first call to an unfamiliar verb, read its `--help`.
2. Workflow prose: where a phase-3 or q-gate-validation doc says "query" next to the qgate surface, fix the wording (a doc fix in the caller workflow, not a script change). The recurrence inside one phase points at the prose, not at a one-off slip.
3. Script side, for the plan-marshall maintainers: consider a paging flag on `manage-findings list`; and fail (or warn) when `--plan-id` resolves to an absent worktree rather than returning an empty success.

## Impact

Small each time (one rejected call), but six shapes of one class across three plans show the canonical blocks are not what agents copy from. The fail-open empty search in the side observation can hide a real finding.
