## G1 — Publish the examined population size on a clean run, not only inside findings

- **Kind:** incomplete-sweep
- **Severity:** medium
- **Where:** `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_analyze_thinking_directive_in_workflow_docs.py` — `analyze_thinking_directive_in_workflow_docs`; consumed at `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_runner.py:203-205` (the `emit()` closure defined at `_runner.py:144-146`)
- **What is wrong:** `plan.md` § Verification requires *"D3's detector must publish the population size it examined **in its own output**. Verify by running it and reading that number."* The size is published only as `details.population_size` on a finding. On the real tree the rule is clean, so it emits zero findings and the runner records `{'rule': 'analyze_thinking_directive_in_workflow_docs', 'findings': 0}` — the population size appears nowhere. Running the rule and reading the number is impossible on a clean tree, which is the only state the gate ever passes in. Confirmed by executing `analyze_thinking_directive_in_workflow_docs(marketplace/bundles)` at HEAD (returns `[]`, population 33) and by reading `emit()` in `_runner.py`, which records only a label and a count.
- **Why it matters:** the mechanism the plan asked for is the one that survives a *degraded* population, not just an empty one. The committed guards cover the zero case (the `empty_population` finding) and a hard floor (`test_real_marketplace_population_is_non_empty` asserts `>= 20`), but a derivation that silently shrinks the population from 33 to, say, 21 still reports `findings: 0` with no number visible to the reader of the gate output. That is the "a zero reads as coverage" shape the epic is named for.
- **Fix:** have the analyzer surface the population size on every run, not only on findings. Either (a) return a clean-run informational record the runner can render (e.g. an entry whose `severity` is informational and which `_scoped`/exit-code accounting ignores), or (b) give the rule a summary hook so `_runner.py`'s `emit()` can record `{'rule': …, 'findings': 0, 'population_size': 33}` in `rule_summaries`. Add a test asserting the size is present in the emitted output for a **clean, non-empty** population — the current `test_population_size_published_in_finding` only covers the finding-bearing case.
- **Done when:** running the plugin-doctor quality gate against a clean tree shows the examined population size for `analyze_thinking_directive_in_workflow_docs` in its output, and a test asserts that on a clean non-empty population.
- **Module/topic:** `pm-plugin-development:plugin-doctor` — rule `thinking-directive-in-workflow-doc`

## G6 — The empty-population anti-vacuity finding is discarded by every scoped (`--paths`) quality-gate run

- **Kind:** vacuous-guard
- **Severity:** high
- **Where:** `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_analyze_thinking_directive_in_workflow_docs.py` — the `EMPTY_POPULATION_TYPE` finding in `analyze_thinking_directive_in_workflow_docs`, which sets `file=str(marketplace_root)`; filtered at `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/doctor-marketplace.py:588-604` (`_finding_in_scope`) via the `_scoped` closure at `doctor-marketplace.py:809-812`, applied to this rule at `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_runner.py:203-205`
- **What is wrong:** D3's anti-vacuity guard emits its `empty_population` finding anchored at the **marketplace root**. `_finding_in_scope` keeps a finding only when its `file` resolves to, or *under*, one of the supplied `--paths` scope dirs. The marketplace root is a **parent** of every possible scope dir, so it can never satisfy that test: under any `--paths` run the guard's finding is silently dropped and the rule reports `findings: 0` over an **empty** population. Confirmed by execution, not by reading: on a synthetic tree that defines `ext-point-execution-context-workflow.md` but declares zero implementors, `analyze_thinking_directive_in_workflow_docs(root)` returns 1 finding whose `file` is the bundles root, and `_finding_in_scope(finding, [root/'plan-marshall'])` and `_finding_in_scope(finding, [root/'plan-marshall/skills/some-skill'])` both return `False` — 1 finding in, 0 kept.
- **Why it matters:** the scoped run is not a corner case — `.claude/skills/finalize-step-plugin-doctor/SKILL.md:23` names scoping to the changed skill directories "the common case", and the whole-tree mode fires only on an F1 trigger (a plugin-doctor/plan-doctor script changed) or an indeterminate `affected_files` read. A derivation break caused by an *ordinary* edit — renaming the ext-point standard, or reshaping `implements:` frontmatter in a `plan-marshall` skill — routes to scoped mode, where the very guard written to catch it is discarded. This is the vacuous-guard archetype reintroduced inside the fix for it, which `plan.md` § Notes explicitly warns is this project's recurring failure. It also makes a shipped claim false: `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/references/rule-catalog.md` § Content Rules → `thinking-directive-in-workflow-doc` → **Anti-vacuity guard** asserts "so a clean result can never read as a vacuous pass over an unread population", which does not hold under `--paths`. Mitigations exist but are outside this rule: the whole-tree `cmd_analyze` path (`_runner.py:357`) is unfiltered, and `test_real_marketplace_population_is_non_empty` (asserting `>= 20`) fails in pytest. Neither is the gate this rule was wired into, and neither is what the rule catalog claims.
- **Fix:** make the empty-population finding survive scoping, the way `validate_extension_contracts` already does. Concretely, in `doctor-marketplace.py::cmd_quality_gate`, stop routing `analyze_thinking_directive_in_workflow_docs` through `_scoped` wholesale: split its result so that findings of type `thinking_directive_population_empty` bypass `_finding_in_scope` and are always appended (mirroring the `contract_errors` branch at `doctor-marketplace.py` that appends `validate_extension_contracts` errors unfiltered), while the per-file `thinking_directive_in_workflow_doc` findings keep the existing scope filter. Add a test in `test/pm-plugin-development/plugin-doctor/test_runner.py` (or the rule's own test file) that builds a tree defining the ext-point with zero implementors, runs the quality gate with a non-empty `scope_dirs`, and asserts the `empty_population` finding is still present. Then correct the **Anti-vacuity guard** bullet in `rule-catalog.md` if any residual scoping caveat remains.
- **Done when:** a quality-gate run with `--paths` pointed at any subdirectory, over a tree that defines `ext-point-execution-context-workflow.md` and derives zero implementors, reports a non-zero `findings` count for `analyze_thinking_directive_in_workflow_docs`; and a committed test asserts exactly that.
- **Module/topic:** `pm-plugin-development:plugin-doctor` — rule `thinking-directive-in-workflow-doc`, scoped-run finding filter
