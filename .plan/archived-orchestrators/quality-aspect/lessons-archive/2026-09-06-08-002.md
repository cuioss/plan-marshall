# Publish the population a signal-gate count was computed over, so a truncated count is distinguishable from an accurate one

## Context

During plan `domain-post-plan-narrow` (PLAN-03, epic `operator-ux`, PR #1422) the finalize
dispatcher forwarded `signal_script_failure_clusters_count: 1` to `lessons-capture`. Reading the
records behind the count — permitted, since the workflow prohibits *re-deriving* the count, not
reading the records — showed **two** distinct failing notations under the documented
`[ERROR] … script_failure` marker class:

| Timestamp | Notation | `failure_kind` |
|---|---|---|
| `2026-09-05T23:24:31Z` | `plan-marshall:workflow-integration-github:github_pr` | `argparse_rejection` (exit 2) |
| `2026-09-05T23:37:08Z` | `plan-marshall:automatic-review:review_completeness` | `argparse_rejection` (exit 2) |

The cluster definition is *"number of distinct failing script notations … union dedup by distinct
notation"*. Two distinct notations dedup to two, not one. The observed window covered the most
recent 400 of 695 work-log entries, so a wider read can only raise the figure, never lower it.

## Root cause

⚠ **Undiagnosed, deliberately.** The step did not re-derive the count, so the cause — a
marker-class gap, a dedup bug, or a window difference — is unestablished. What IS established is
the discrepancy between the forwarded value and the records it summarises.

The structural fault is independent of the cause: the count is published **without the population
it was computed over**, so no consumer can tell an accurate `1` from a truncated `1`.

## Proposed action

Have the gate publish the population alongside the count — the notation list and the entry window
scanned — so a consumer can discriminate. This is the same *"a count rides with its denominator"*
discipline already applied on the `corpus` and `inbox list` surfaces, where a zero states what was
scanned to reach it.

## Impact

The count is a **gate**, and `lessons-capture` is the consumer that acts on it. An undercount does
not merely misreport: at the boundary it silently converts a non-zero signal into a skip. On this
run the count was non-zero for other reasons, so nothing was lost. A run whose only signal was a
two-notation cluster reported as **zero** would skip `lessons-capture` entirely, and that skip
would be indistinguishable from a clean run.
