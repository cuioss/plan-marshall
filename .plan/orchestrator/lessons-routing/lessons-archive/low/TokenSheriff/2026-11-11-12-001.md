# Derive the outline's Affected files from a repository-wide content search of every surface that states or depends on the change, never from the request text or memory

## Problem

During PLAN-28 (epic quality-report, PR #892) the 3-outline and 4-plan Q-Gate sent the same kind of defect back for re-planning eight times: the outline's Affected files list came from the request text or from memory, not from a search of the repository for every surface that states or depends on the thing being changed. Each miss was caught by the scope-criterion validator (or later), not by the outline author, and each cost a regenerated task or a loop-back.

Instances (each is one finding; all were resolved in the run):

1. A read-reference path was written from memory and named the wrong sub-package (`jwks/HttpJwksLoader.java`, real path `jwks/http/HttpJwksLoader.java`). Finding 91b5b1.
2. A criterion "no `./mvnw test` instruction remains that the run proved fails" was operationalised over `AGENTS.md` and `CLAUDE.md` only. A content search found the same form in two READMEs. Finding 5ae537. The first fix still searched the literal `mvnw test` and missed `./mvnw clean test -pl ...` in a third README; the sweep had to widen to the regex `mvnw( clean)? test`. Finding 0b5c53 (second round on the same deliverable: the first re-plan did not generalise).
3. A carried defect counted instances ("both health-check suppressions"); a content search found one, and a planned write target carried no directive at all. Finding e5602d.
4. A change to an enumerated behaviour set (the STRICT refusal list of the `insufficient_scope` parser) left the specification that enumerates the same set (`step-up-and-logout.adoc`) out of the affected files. Finding 50992d.
5. A change to the set a sanitiser escapes (nine bidi controls) left ADR-0022, which claims to be the single definition of that set, out of the affected files. Finding a86bff. The same deliverable then missed `token-decryption.adoc`, which states the set and the truncation rule: the first fix corrected the ADR's pointer to that spec but not the spec. Two deliverables also wrote the same file while both declared `depends: none`. Finding b94f81.
6. A config-knob semantics change (the DPoP nonce cache becoming a soft cap) covered the config class Javadoc and the threat model but not the framework property-key constant's Javadoc nor the generated property reference. Finding e19b34, the third scope-criterion round in 4-plan; fixed by patching the task in place at the operator's direction.
7. A deliberate test inversion (`shouldAcceptUnquotedScope` replaced by `shouldRefuseUnquotedScope`, an operator-decided behaviour reversal) was not declared in the outline's Tests-to-remove, so the test-integrity check flagged it and needed an operator acceptance round. Finding 350da4.

## Solution

1. Derive Affected files (read entries included) from the file inventory plus a repository-wide content search, never from the files the request names and never from memory. Resolve every path against `git ls-files` before the outline is written.
2. Search for the thing that changes, not for one spelling of it: use a regex that allows interleaved goals and phases (`(mvnw|mvn)[^\n]*\btest\b`), and search for the class name, the API type names and the config key.
3. When a deliverable changes an enumerated set (a refusal list, an accepted grammar, a character set, a config knob), list every place that enumerates it: `doc/` specifications, `doc/adr/` (an ADR that claims to define the set is a mandatory write target), the Javadoc of the class AND of the property-key constant, and the generated or hand-written property reference. Following a pointer to a spec is not updating the spec: add the target.
4. When a carried defect counts instances ("both", "all three"), confirm the count with a content search before naming write targets.
5. When two deliverables write the same file, declare a dependency or split the edits by paragraph explicitly.
6. When a deliverable deliberately inverts or replaces a test, name the retired test identity in the outline's Tests-to-remove declaration, so the integrity gate passes without an operator question.
7. A second Q-Gate round on the same deliverable means the first re-plan fixed the instance and not the class: generalise the search before regenerating the task.

## Impact

Eight scope-criterion findings and several regenerated tasks in one plan, one of them a third round on a single deliverable, plus one avoidable operator question. Each would have been closed by one repository-wide search at outline time.
