# Renaming a bot registry key that is also a consumer-repo config token breaks required-bot matching

A required review bot resolved `absent` on both automatic-review rounds of plan
`remove-suspicious-path-blocklist` (PR cuioss/cui-http#199) even though it had
demonstrably reviewed. The run had to be forced past the pre-merge barrier twice with a
WARNING and finally needed an explicit operator merge-authorization.

## What happened

`marshal.json` was configured with:

```text
required_bots: "coderabbit,cuioss-review-bot"
optional_bots: "sourcery"
```

`review_completeness check` reported `cuioss-review-bot=absent` with
`stale_participation_bots: pr-agent:issue_comment`, and the plan's currency ledger
carried exactly one row:

```json
{"bot_kind": "pr-agent", "comment_id": "IC_kwDOPwSbp88AAAABShn5tA",
 "reviewed_commit_sha": "80cc8f77eafeab34ac570facbb9e8c644b3a9c48",
 "updated_at": "2026-09-04T09:03:11Z"}
```

The bot posted its `## PR Reviewer Guide 🔍` issue_comment, the producer credited it, and
the completeness check still could not see it.

## Root cause — a config-token rename that outran the registry rename

The bot's registry key was renamed `pr-agent` -> `cuioss-review-bot`. The two halves of
that rename shipped on different schedules and through different channels:

| Half | Where | When |
|------|-------|------|
| Consumer-repo config token (`required_bots`) | cui-http commit `c7862d0` "chore(config): rename the pr-agent reviewer token to cuioss-review-bot (#192)" | before this run |
| Registry key (`automatic-review/standards/{bot_kind}.md`) | plan-marshall `0.1.1589` -> `0.1.1592` (`pr-agent.md` -> `cuioss-review-bot.md`) | installed 2026-09-04 12:13, AFTER both review rounds |

Both automatic-review rounds (10:19-10:25 and 12:01-12:02) ran on `0.1.1589`, whose
registry resolved:

```text
login_to_bot_kind() == {'coderabbitai': 'coderabbit',
                        'cuioss-review-bot': 'pr-agent',
                        'sourcery-ai': 'sourcery'}
```

So the producer was correct: under that registry the login `cuioss-review-bot` mapped to
the kind `pr-agent`. The *config* was the half that had moved. `review_completeness` was
asked for a bot named `cuioss-review-bot` and no reviewer answered to that name.

The confusable pair is what made the config rename look safe: under `0.1.1589` the string
`cuioss-review-bot` was already a valid **author_login**, just not a valid **bot_kind**.
A reviewer eyeballing the standards doc sees the string present and concludes the token is
recognised.

## Why it was silent rather than loud

`0.1.1589`'s `review_completeness.py` had no state for "this configured token names no
registered reviewer" — an unknown token fell through to `absent`, which is
indistinguishable from "the bot was configured correctly and simply did not review". The
run therefore spent two force-done cycles and an operator merge-authorization on what a
one-line config diagnosis would have closed.

## Rules

1. **A registry key that doubles as a consumer-repo config token must not be renamed
   config-first.** Ship the registry rename (with an alias for the old key) BEFORE any
   consumer repo rewrites its config, and keep the alias for at least one release window.
   Consumer repos upgrade the plugin on their own schedule; a mid-run upgrade — this run
   straddled one — makes the skew a certainty, not a risk.
2. **When a configured token names no registered reviewer, say so.** Never let an
   unrecognised `required_bots` token degrade into `absent`. "No reviewer answers to this
   name" is a config defect whose remedy is a config edit; "nobody reviewed" is a review
   defect whose remedy is waiting or re-triggering. Collapsing the two costs an operator
   escalation every time.
3. **Do not treat an `author_login` match as evidence the token is a valid `bot_kind`.**
   Where a bot's login and kind are deliberately the same string, the two spellings are
   only accidentally interchangeable; grep for `bot_kind:`, not for the bare string.

## Status at time of writing

Both halves are closed forward in `0.1.1592`: the registry key is now `cuioss-review-bot`
(so it matches the config token), and `review_completeness.py` gained
`STATE_UNREGISTERED_KIND`, which distinguishes an unrecognised configured token from a
genuinely silent reviewer. What is NOT closed is the migration ordering itself — rule 1
above still has no mechanism enforcing it, so the same skew recurs on the next rename of a
registry key that consumer repos name in their own config.
