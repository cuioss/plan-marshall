# A Q-Gate mechanism substitution must be re-checked against the EXECUTING envelope's tool grant, not just the tool's verb list

A phase-3-outline deliverable named a mechanism the executing agent could not reach. The
Q-Gate caught the first instance, the re-authoring substituted a second mechanism, and the
substitute was **also** unreachable — because the fix validated the *tool's capability* and
never re-asked the reachability question against the *envelope that would run the step*.

## What happened

Deliverable 1 of `modernize-python-toolchain` had to read a SHA-pinned reusable workflow from
another repository to establish CI's resolved Python interpreter.

1. **Authored mechanism**: "read it via the CI abstraction `plan-marshall:tools-integration-ci:ci`,
   never `gh` directly". The 3-outline Q-Gate correctly refuted this — `ci.py` exposes only
   `pr`, `checks`, `issue`, `branch`, `repo`, and none of them reads an arbitrary file from
   another repo at a pinned SHA.
2. **Re-authored mechanism**: `WebFetch` against the SHA-pinned `raw.githubusercontent.com`
   URL, with an `ci checks logs` fallback. Structurally sound — the domain is allowlisted and
   the verb exists.
3. **Execute time**: the phase-5 dispatched leaf emitted
   `[BLOCKED] TASK-001 step 2 cannot proceed: WebFetch is not in this dispatched leaf's tool
   surface, and the sanctioned fallback (ci checks logs) returns only FAILED-job logs, so a
   green python-verify run yields no interpreter string.`
   The task escalated to the orchestrator and the deliverable stalled exactly where the Q-Gate
   had tried to prevent it stalling.

## Root cause

Two different questions were conflated:

- *Does a tool exist that can perform this operation?* — the question the Q-Gate fix answered.
- *Is that tool granted to the envelope that will execute this step?* — the question nobody asked.

`WebFetch` is real and the domain is allowlisted, but a **dispatched `execution-context` leaf
does not receive it**. The reachability property is a function of the (operation, executing
envelope) pair, not of the operation alone. An outline authored in the main-context
orchestrator — where the richer tool surface *is* present — will systematically overestimate
what a phase-5 leaf can do.

The failure also shows the Q-Gate remediation anti-pattern: the finding was closed by swapping
the named tool, which is the narrowest possible fix. The *class* of the finding was
"this deliverable mandates an operation its executor cannot perform", and the re-authored
mechanism belonged to the same class.

## Rule

When an outline deliverable names a concrete mechanism for an operation:

1. Determine **which envelope executes it** — a phase-5 dispatched leaf, or the main-context
   orchestrator. Deliverable steps run in a leaf by default.
2. Check the mechanism against **that envelope's tool grant**, not against the tool's existence
   or its verb list. `WebFetch`, `AskUserQuestion`, and (non-deterministically) `Grep`/`Glob`
   are not reliably available to a dispatched leaf.
3. When the operation genuinely requires an orchestrator-only tool, say so in the deliverable:
   declare it an orchestrator-tier step, or restate the success criterion so it is satisfiable
   from the leaf's actual surface, or provide an operator-supplied input.
4. When resolving a Q-Gate finding by **substituting** a mechanism, re-run the full reachability
   check on the substitute. A substitution is a new authoring act, not a patch.

## Impact

Cost the plan a full escalate-ask round trip plus an orchestrator-driven re-dispatch, and left
`build.adoc` carrying a false interpreter-parity claim that needed a separate corrective commit
(`4f5a81863`). Applies to every deliverable whose Change-per-file narrative names a tool.
