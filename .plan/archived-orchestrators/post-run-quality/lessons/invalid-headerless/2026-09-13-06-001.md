# Persisted step_params keep an override that lane resolution discarded

## Context

Plan `the-foreign-gate-population-and-branch-f-recovery` composed a manifest whose
`phase_6.step_params` records `lessons-capture: {lane: off}`. The compose decision log for the
same run says the opposite happened:

```text
lane_resolution warning — lessons-capture: override 'off' ignored for core floor element
  — immune, cannot be weakened
```

`lessons-capture` duly remained in `phase_6.steps[]`. So the manifest simultaneously carries the
step in its run list and an `off` lane in its parameters, and only the decision log records that
the `off` was refused.

The harm is not hypothetical and was observed on this run. The dispatch prompt for this plan's own
retrospective asserted *"`lessons-capture` is lane: off in this plan's manifest, so lessons you seed
are the run's durable output"* — a conclusion drawn directly from the persisted value, and wrong.
An author reading `step_params` has no way to know the value was discarded without separately
grepping the decision log for a `lane_resolution warning` line naming that step.

## Root cause

Lane resolution consumes the requested override, decides it cannot weaken a core floor element, and
discards it — but writes the **requested** value back into `step_params` rather than the
**effective** one. The refusal is recorded only in the decision log, which is a different artifact
with a different lifetime and no structural link to the manifest a consumer reads.

This is the general shape of a resolved-value/requested-value conflation: the record that survives
is the input to the decision, not its output, so every downstream reader re-derives the wrong
answer and none of them can tell.

## Proposed action

Make the manifest record the effective value, and make the refusal legible where the value lives.
Either:

1. Write the resolved lane (`immune`, or the floor value) into `step_params` and keep the requested
   value beside it under a distinct key (e.g. `lane_requested`), so a reader sees both and cannot
   mistake one for the other; or
2. Keep the requested value but add an explicit `lane_override_refused: true` (with the reason) to
   that step's params whenever resolution discards it.

Option 1 is preferred: it makes the common read (`what lane is this step on?`) correct by default,
which is the read every consumer actually performs. Whichever is chosen, a step present in
`steps[]` must never carry a bare `lane: off` in `step_params`, because those two statements
contradict each other and the contradiction is currently silent.

## Evidence

- aspect: manifest-decisions — `step_params.lessons-capture.lane: off` while `phase_6.steps[]`
  contains `lessons-capture`
- aspect: routing-decisions — `recorded_lane_decisions[]` carries
  `lane_resolution warning — lessons-capture: override 'off' ignored for core floor element`
- observed harm: this plan's retrospective dispatch prompt stated the step was off, reasoning from
  the persisted value
