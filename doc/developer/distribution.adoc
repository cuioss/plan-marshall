== Overview

`plan-marshall` publishes each of its distribution targets to refs on `cuioss/plan-marshall`. The `claude` target publishes to the `dist-claude` orphan branch (snapshot, force-updated on every push to `main`) and the immutable dist tag `claude/v{x.y.z}` (per-release). Each ref's root holds `.claude-plugin/marketplace.json`, a root `README.adoc` rendered on GitHub, and the expanded bundle tree, so Claude Code's `/plugin marketplace add` against the ref registers the marketplace directly. The `opencode` and `antigravity` targets publish to `dist-opencode` / `opencode/v*` and `dist-antigravity` / `antigravity/v*`. Each carries a root `README.adoc` and a self-contained `install.sh` script providing one-line installation (`curl -fsSL ... | bash`), workspace scoping, and uninstallation (xref:../user/install-opencode.adoc[Installation (OpenCode)], xref:../user/install-antigravity.adoc[Installation (Google Antigravity)]).

The install commands that follow are Claude-specific (`/plugin marketplace add`, `/reload-plugins`), with the full walkthrough at xref:../user/install-claude.adoc[Installation (Claude Code)].

== Installing — snapshot (bleeding edge)

[source,text]
----
/plugin marketplace add cuioss/plan-marshall@dist-claude
/plugin install plan-marshall@plan-marshall
----

Restart Claude Code or run `/reload-plugins`. Install additional bundles per xref:../user/install-claude.adoc[User Guide › Installation (Claude Code)] as desired.

The `@dist-claude` ref tracks `main`: every push to `main` force-updates this branch to the freshly regenerated `target/claude/` tree.

== Installing — pinned (specific release)

[source,text]
----
/plugin marketplace add cuioss/plan-marshall@claude/v{x.y.z}
/plugin install plan-marshall@plan-marshall
----

For example, `@claude/v1.2.3`. Restart Claude Code or run `/reload-plugins`.

The `claude/v{x.y.z}` tag is immutable — it remains pinned to the orphan commit produced for that release even after `dist-claude` is later overwritten by subsequent `main` pushes.

== Updating — snapshot users

[source,text]
----
/plugin marketplace update plan-marshall
----

Re-pulls `dist-claude` HEAD. Reinstall plugins to pick up updated `plugin.json` entries, then restart Claude Code or run `/reload-plugins`.

== Updating — pinned users

[source,text]
----
/plugin marketplace remove plan-marshall
/plugin marketplace add cuioss/plan-marshall@claude/v{new.x.y}
----

Reinstall plugins and restart.

== Versioning convention

Source tags follow `v{major}.{minor}.{patch}` (SemVer-flavoured) on the `cuioss/plan-marshall` repository. The dist tag mirrors the source tag with a `claude/` namespace prefix: source tag `v1.2.3` produces dist tag `claude/v1.2.3`.

The entire marketplace is versioned as a unit — every bundle ships under the same tag. Breaking changes to any bundle bump the major; backward-compatible feature additions bump the minor; bug fixes bump the patch. There is no per-bundle version channel.

The same source `v*` tag drives every target distribution. The per-target dist tag is `{target_name}/v{x.y.z}`, so the `opencode` target publishes `opencode/v1.2.3` from the same source `v1.2.3`.

== What triggers a publish

Two events trigger the `Claude Distribute` workflow:

* A push to `main` updates the `dist-claude` snapshot branch (force-orphan).
* A push of a `v{x.y.z}` tag updates `dist-claude` and creates the immutable dist tag `claude/v{x.y.z}` pointing at the new orphan commit.

A maintainer pushes the source tag manually; the workflow does the rest. Force-pushes to `dist-claude` and pushes of `claude/v*` dist tags are performed by the organization-wide `cui-release-bot` identity (the workflow authenticates via the `cuioss-release-bot` GitHub App), not by the maintainer who pushed the source tag.

The workflow sets `enable_jekyll: true` on each dist branch (`dist-claude`, `dist-opencode`) so a `.nojekyll` is not auto-injected — the published tree contains only the marketplace files the generator produced.

== Source tag vs. dist tag

The source repository's `v{x.y.z}` git tag remains pinned to the source commit on `main` — the auto-created GitHub Release for that source tag may exist with no attached assets. The dist tag `claude/v{x.y.z}` points at a different commit: the orphan commit on `dist-claude`. The two coexist by design. Install commands always reference the dist branch or dist tag, never the source `v*` tag.

== Multi-target architecture

The publish workflow is target-parametrized via a GitHub Actions `strategy.matrix`. Today the matrix has two active entries — `claude` and `opencode`, matching `.github/workflows/claude-distribute.yml` read at run time. Each matrix entry defines one distribution target with its own:

|===
| Entry | Branch | Dist-tag prefix | Publish dir | Generator flag

| `claude`
| `dist-claude`
| `claude/`
| `target/claude`
| `--target claude`

| `opencode`
| `dist-opencode`
| `opencode/`
| `target/opencode`
| `--target opencode`

| `antigravity`
| `dist-antigravity`
| `antigravity/`
| `target/antigravity`
| `--target antigravity`
|===

Both `dist-opencode` and `dist-antigravity` branches carry root `README.adoc` guides and `install.sh` scripts that allow consumers to install components without cloning the monorepo or running local generators. For contributors and CI pipelines, the local `./pw generate --target ...` workflow remains authoritative for emitting and validating target trees.

The single source `v{x.y.z}` tag drives all targets; versioning stays unified
across the marketplace. Adding another future target is not a config-only
change: it first needs generator support (a target registered in
`TARGET_REGISTRY` — `marketplace/targets/__init__.py`) before its workflow
matrix entry is appended. The matrix list is the final distribution step, not
the whole change.
