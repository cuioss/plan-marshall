# Simplify reconciles only against the findings store, so a decision recorded in outline prose is invisible to it

component: plan-marshall:phase-6-finalize
category: bug
surface: marketplace/bundles/plan-marshall/skills/phase-6-finalize/standards/finalize-step-simplify.md, marketplace/bundles/plan-marshall/skills/phase-6-finalize/scripts/review_commitments.py

## Observed

Plan `always-on-is-not-a-resolve` (epic `operator-ux`, PLAN-10). The solution
outline's § Approach point 3 recorded a deliberate, argued decision: keep
`domains = set(offerable) | always_on_set` in the zero-narrative-match
over-provision branch **even though the union is provably a no-op**, because it
"makes the branch's intent legible at the call site and keeps the retention true
if the offerable predicate ever narrows." That decision survived the phase-3
review gate and was implemented as written.

`default:finalize-step-simplify` (order 9) then removed exactly that union,
collapsed the branch into the existing over-provision return with a ternary
`reason`, and reported:

```toon
verdict: clear
commitments_considered: 0
deletions_considered: 3
conflicts[0]:
```

`commitments_considered: 0` was not a scan that found nothing. It was a scan that
looked in the one place the commitment was not: `review_commitments reconcile`
reads the plan's **findings store** (`--resolution` dispositions on triaged
review findings), and the commitment here lived in `solution_outline.md` prose.

## Why it matters

The reconcile exists to stop a simplify pass from silently undoing something the
run already decided. Against a review-bot finding disposition it does that. But
the *richest* decisions a plan makes — the ones with recorded rationale, weighed
tradeoffs, and an operator's gate approval behind them — are written in the
outline's Approach / Risks sections, and those are structurally outside what the
reconcile reads. So the check is strongest exactly where the stakes are lowest,
and blind exactly where they are highest.

The failure is silent by construction: `verdict: clear` is indistinguishable
from "no commitment existed" and "a commitment existed somewhere I do not read".
On this run the only thing that caught the reversal was the orchestrator reading
the resulting diff by hand.

## Directive

Widen what `review_commitments reconcile` treats as a commitment, or make its
`clear` verdict state the population it actually searched. Concretely, one of:

1. **Widen the population.** Have the reconcile additionally read the solution
   outline's decision-bearing sections (§ Approach, § Risks and Mitigations) and
   match a proposed deletion against text that argues FOR the deleted construct.
   This is the direct fix and the more useful one.
2. **Publish the boundary.** If the population stays findings-only, make the
   return say so — `commitments_considered: 0` must ride with the searched
   source set, so a caller can tell an empty search from an empty result. This is
   the same honest-coverage discipline `pre-push-quality-gate` already applies to
   its own dimensions (`_gate_coverage.structural_limits`) and that
   `pre-submission-self-review` applies to its `structural_limit`.

Option 2 is the minimum; option 1 is what would have caught this instance.

Note the second-order point: a no-op construct kept purely for future-proofing is
itself the wrong remedy — no test can distinguish it, so it would begin carrying
weight with zero coverage at the moment it started to matter. The correct
resolution on this plan was to take simplify's deletion AND pin the invariant the
union was standing in for (`_always_on_domains(cfg) <= _offerable_domains(cfg)`),
which is now a test. A reconcile that surfaces the conflict should therefore
prompt that adjudication, not automatically restore the deleted code.
