# Plan PR size against the 100-file reviewer cap, and split at outline time

## What happened

Plan `implement-test-duration-analysis-proposals` was outlined as one pull request against a ceiling of 140 files. The outline recorded "about 100 files affected ... below the 140-file ceiling, so one pull request" (decision log, 2026-10-09T15:30:34Z).

The required reviewer CodeRabbit refuses a pull request above 100 files. PR #795 reached 108 files after the fix rounds, CodeRabbit returned a structural refusal (`refused_structural`, "108 files, cap 100", decision log 2026-10-10T06:44:28Z), and the PR had no required review.

The PR was split after the fact: TASK-24 restored `token-sheriff-client/` to `origin/main`, the PR went down to about 95 files, and CodeRabbit then reviewed it. The split cost one extra execute round, one extra full CI run and a re-review. The client-module changes were left on the follow-up branch `feature/test-duration-client-tests`; the merge commit 262be1c0 states that its PR was not yet opened.

## Rule

- The binding ceiling for a pull request in this repository is the smallest limit of any **required** reviewer. Today that is CodeRabbit's 100 files, not 140.
- Decide the split at outline time, along module boundaries, so each pull request builds and is reviewable on its own.
- Leave headroom for fix-round files. This run grew from 105 to 108 files through CI and review fixes (documents, a new build-step test, a log-dump script). Plan for a margin of roughly ten files below the cap.
- Count the real diff (`git diff --name-only origin/main...HEAD`) before the first push, not the outline's estimate.

## Follow-up owed outside this lesson

- The project memory note `pr-file-ceiling.md` still says "keep PRs under 140 files". It was not changed by this step and should be corrected to the 100-file cap.
- The client-module follow-up PR from `feature/test-duration-client-tests` is open work.
