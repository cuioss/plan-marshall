# Finding: Tier-1 `--request-text` verbatim passing breaks on real issue bodies

## What happened

During `phase-1-init` Step 5c (`recipe-match`, `aspect-classify`) for plan
`issue-1697` (source: https://github.com/cuioss/plan-marshall/issues/1697),
the workflow requires passing the full request narrative verbatim as
`--request-text "{request_narrative}"`.

The issue body contains backticks, double quotes, and single quotes
(e.g. `` `stream-end` ``, `"inbox/: 1 queued and 50 archived"`,
`post-run-quality's`). Passed through a shell double-quoted argument this
triggers command substitution on backticks, breaks on embedded quotes, and
risks security-prompt corruption — the same class Step 5's path-allocate
flow was introduced to avoid for `--body`.

## Workaround applied (not a fix)

Invoked the verbs via a single `python3 -c` that reads
`.plan/local/plans/issue-1697/request.md` into a Python string and passes it
as an argv element via `subprocess.run([...])`, avoiding shell quoting
entirely. `recipe-match` returned 0 matches; `aspect-classify` returned
`implementation` (confidence 0.012). Init continued.

## What is owed (process-compliance)

- A file-based narrative input for `recipe-match` / `aspect-classify`
  (e.g. `--request-file PATH`, mirroring `request create --body-file`),
  so verbatim markdown never travels through shell quoting.
- Or a documented argv-safe invocation pattern in `phase-1-init` Step 5c,
  instead of `--request-text "{request_narrative}"` inline.
