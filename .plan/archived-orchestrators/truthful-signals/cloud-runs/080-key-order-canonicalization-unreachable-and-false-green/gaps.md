## G1 — Classify `ConcurrentConfigModificationError` as an expected error, not an `internal_error` crash

- **Kind:** bug
- **Severity:** low
- **Where:** `marketplace/bundles/plan-marshall/skills/manage-config/scripts/manage-config.py:169` — `@safe_main` on `main()`, and `:915-921` — the only per-arm `try/except`; the exception is raised at `marketplace/bundles/plan-marshall/skills/manage-config/scripts/_config_core.py:212-218` — `save_config`
- **What is wrong:** D4 introduced a new exception type that no caller handles by name — `grep 'except ConcurrentConfigModificationError'` across `marketplace/` and `test/` returns zero hits, against 36 `save_config` call sites in 14 files (35 outside `_config_core` itself, in 13 modules). Only the `normalize-keys` arm of `main()` has a `try/except`. The general path is nevertheless **not** unhandled: `main()` carries `@safe_main` (`file_ops.py:1664-1700`), which catches any `Exception`, prints `output_toon_error('internal_error', str(e))` on **stdout** and exits 1. An execution probe that races a concurrent write between `load_config` and `save_config` inside `_cmd_orchestrator.cmd_orchestrator_set` and then drives `manage-config.py:main()` produced exactly that: `stdout = "status: error\nerror: internal_error\nmessage: … changed on disk since it was loaded; refusing to overwrite a concurrent write. Reload the config and re-apply the change.\n"`, empty stderr, exit 1. What is wrong is the **tier and the discriminator**, not the presence of a signal: a concurrent modification is by construction an *expected, recoverable* condition (`_config_core.py:65-74` — "a lost update becomes a recoverable error (reload and re-apply)"), so exit 1 / `error: internal_error` tells the caller "the script crashed" where the contract reserves that tier for genuine crashes.
- **Why it matters:** `ref-workflow-architecture/standards/manage-contract.md:34-35` puts expected errors at exit 0 with `status: error`, and reserves exit 1 for "unexpected crash — reserved for `@safe_main` exception handler only". The generated executor classifies a non-zero exit as a `script_internal_failure`, so a recoverable "reload and re-apply" condition is presented to the LLM caller as an internal fault with a generic error code it cannot branch on.
- **Fix:** in `manage-config.py:main()`, wrap the dispatch (`result = cmd_*(args)` through `output_toon(result)`) in `except ConcurrentConfigModificationError as e: result = error_exit(str(e), error_type='concurrent_modification')`, leaving `@safe_main` in place for genuine crashes. Import the exception from `_config_core` alongside the existing imports. Remove the now-redundant per-arm `try/except` on `normalize-keys`, or leave it — the general path is the one that must stop reaching `@safe_main`.
- **Done when:** a test drives a `manage-config` verb other than `normalize-keys` through a load→concurrent-write→save race and asserts the CLI emits `status: error` with `error_type: concurrent_modification` and exit code **0**.
- **Module/topic:** `plan-marshall:manage-config` — config write path

## G3 — Stage 2's "position is load-bearing" claim is false; the Re-Run Pass contradicts it

- **Kind:** doc-drift
- **Severity:** medium
- **Where:** `marketplace/bundles/plan-marshall/skills/marshall-steward/references/upgrade-flow.md:321-327` — the load-bearing-position rationale; contradicted by `marketplace/bundles/plan-marshall/skills/marshall-steward/SKILL.md:490-504, 580-591, 632-646` — Re-Run Remediation Pass steps (a)/(e)/(f)
- **What is wrong:** Stage 2 runs `normalize-keys` **last** and states that "its position is load-bearing … running it after any key-adding reconcile gives it the final word". The Re-Run Remediation Pass runs `normalize-keys` as step **(a)** — first — with `sync-defaults` at (e) and `steps-sort` at (f). The run edited step (a)'s prose to surface `unrecognized_keys` but left the position untouched, although the plan's Expected surface names this file as one that "must stay consistent with the new Stage 2 wiring". An execution probe settles which half is wrong: `save_config` calls `order_config_keys` on every write (`_config_core.py:207`), so a key added *after* `normalize-keys` still lands canonically — loading `{'system': …, 'plan': …}`, adding `build`, and calling `save_config` yields `['plan', 'build', 'system']`. Both sibling verbs persist through `save_config` (`_cmd_sync_defaults.py:481`, `_cmd_steps_sort.py:84`), so **`normalize-keys`' position among them does not change the resulting key order.** Stage 2's *inclusion* of `normalize-keys` is load-bearing (it is the only unconditional writer); its *position* is not.
- **Why it matters:** the two documents give a reader opposite accounts of whether the position matters, and the position rationale that Stage 2 offers is a mechanism claim the code does not support — the same shape of unverified assertion this epic exists to remove. The D10(c) test pins the order inside Stage 2, so the false rationale is now test-enforced.
- **Fix:** in `upgrade-flow.md:321-327`, replace the "its position is load-bearing" sentence with what is true: `sync-defaults` and `steps-sort` are conditional writes, so on a config whose only drift is key order neither writes and `normalize-keys` — the unconditional canonicalizer — is required; every write canonicalizes through `save_config`, so its position among the three is immaterial and it is sequenced last only for readability. Leave `test_upgrade_flow_stage2.py` asserting the order (it still pins presence), and either leave the Re-Run Pass lettering alone or add a one-line note at `marshall-steward/SKILL.md:490` that step (a)'s position is likewise immaterial.
- **Done when:** `upgrade-flow.md` no longer asserts that `normalize-keys`' position changes the resulting key order, and the Re-Run Remediation Pass and Stage 2 no longer give opposite accounts of whether ordering matters.
- **Module/topic:** `plan-marshall:marshall-steward` — upgrade + remediation flows

## G4 — `runtime` and `project_dir` are first-party keys the new warning calls unrecognized

- **Kind:** bug
- **Severity:** medium
- **Where:** `marketplace/bundles/plan-marshall/skills/manage-config/scripts/_config_core.py:126-154` — `CANONICAL_TOP_LEVEL_KEY_ORDER`; producers at `_claude_runtime_impl.py:71-74` and `opencode_runtime.py:75-79`; reader at `platform_runtime.py:234-240` — `_resolve_target`
- **What is wrong:** `project initial-setup` writes top-level `runtime` (Claude and OpenCode targets) and `project_dir` (Claude target) into `marshal.json`, and `platform_runtime._resolve_target` reads `runtime.target` back. Neither key is in `CANONICAL_TOP_LEVEL_KEY_ORDER`. Executed against the current code, `unrecognized_top_level_keys({'plan':…, 'system':…, 'runtime':…, 'project_dir':…})` returns `['runtime', 'project_dir']` and `normalize_keys()` returns `{'status': 'warning', 'action': 'normalized', 'unrecognized_keys': ['runtime', 'project_dir']}` — and both Stage 2 (`upgrade-flow.md:327-330`) and the Re-Run Pass (`marshall-steward/SKILL.md:501-504`) instruct the operator to surface that list as "a stray or consumer-added block".
- **Why it matters:** the honest signal fires on the product's own keys, describing first-party configuration as stray. A warning that is always present on a legitimately-configured project is the noise that trains operators to ignore the signal — the failure mode this epic exists to prevent. The OpenCode seed is the reachable path: it is a read-modify-write that adds `runtime` to an already-initialized config and leaves the rest intact (verified by execution), so an OpenCode project warns on `runtime` on every `normalize-keys` call.
- **Fix:** add `runtime` (and `project_dir`, if it is meant to persist) to `CANONICAL_TOP_LEVEL_KEY_ORDER` at their intended slots in `_config_core.py:136-154` and document them in `manage-config/standards/data-model.md`; or stop persisting them as top-level keys in the two runtime seeds. If the plan's out-of-scope boundary on redesigning the canonical list is honoured, raise it as a schema decision rather than leaving the false warning in place.
- **Done when:** `normalize_keys()` returns `status: success` with `unrecognized_keys: []` for a `marshal.json` produced by `manage-config init` followed by `project initial-setup --target opencode` (the sequence that genuinely leaves both a full config and `runtime` in place), demonstrated by a test. ⚠ The reverse sequence is not a valid check: `manage-config init` refuses when marshal.json exists (`_cmd_init.py:22-23`) and `--force` rebuilds the document from `get_default_config()` (`:30, :53`), discarding `runtime` entirely — so an assertion written against "initial-setup then init" passes vacuously.
- **Module/topic:** `plan-marshall:manage-config` / `plan-marshall:platform-runtime` — marshal.json top-level schema

## G6 — Record the provider write path as an unguarded whole-document read-modify-write

- **Kind:** omission
- **Severity:** medium

## G8 — `upgrade.py`'s entry point is not `@safe_main`-wrapped, so a `save_config` failure emits no TOON at all

- **Kind:** bug
- **Severity:** medium
- **Where:** `marketplace/bundles/plan-marshall/skills/marshall-steward/scripts/upgrade.py:372-429` — `main()` (no decorator) and `:429` `sys.exit(main())`; the `save_config` call is at `:354` in `cmd_migrate_bot_lists` (`:316-355`)
- **What is wrong:** `cmd_migrate_bot_lists` does `load_config()` → mutate → `save_config()` with no exception handling, and `upgrade.py:main()` — unlike its sibling `bootstrap_plugin.py:339` and the 55 files in the tree that apply it — carries no `@safe_main`. An execution probe that races a concurrent write between the load and the save and then calls `upgrade.main(['migrate-bot-lists'])` produced `UNCAUGHT: ConcurrentConfigModificationError` with **empty stdout** — as a process that is a raw traceback on stderr, exit 1, and no TOON. The same hole swallows any `OSError` from the write and any `ValueError` from a malformed config, so it is not specific to D4; D4 merely widened the set of exceptions that reach it.
- **Why it matters:** `plugin-script-architecture/standards/output-contract.md:103` makes `@safe_main` *the* mechanism by which a crash still carries a parseable diagnostic payload, and `ref-workflow-architecture/standards/manage-contract.md:34-36` requires TOON on stdout for every outcome. An empty stdout with a traceback on stderr is the one output shape the contract rules out, and the generated executor can only report it as an opaque `script_internal_failure`.
- **Fix:** import `safe_main` from `file_ops` in `upgrade.py` and decorate `main()` with `@safe_main`, matching `bootstrap_plugin.py:339`; then add `except ConcurrentConfigModificationError` handling in `cmd_migrate_bot_lists` returning `{'status': 'error', 'operation': 'migrate-bot-lists', 'error': …, 'error_type': 'concurrent_modification'}` so the recoverable case stays at exit 0. (`cache_retention.py`, `determine_mode.py` and `gitignore_setup.py` share the missing decorator but write no config; they are context, not this gap.)
- **Done when:** a test that forces an exception out of `cmd_migrate_bot_lists` asserts that `upgrade.py` prints a parseable TOON `status: error` on stdout and never leaves stdout empty.
- **Module/topic:** `plan-marshall:marshall-steward` — upgrade verb script contract

## G9 — `ClaudeRuntime.project_initial_setup` overwrites an existing `marshal.json`, destroying the whole config

- **Kind:** bug
- **Severity:** high
- **Where:** `marketplace/bundles/plan-marshall/skills/platform-runtime/scripts/_claude_runtime_impl.py:70-80` — the unconditional `marshal_data` write in `project_initial_setup`; contrast the sibling implementation of the same contract operation at `opencode_runtime.py:68-79`
- **What is wrong:** the Claude implementation builds `marshal_data = {"runtime": {...}, "project_dir": ...}` and hands it to `claude_runtime._write_json(marshal_path, marshal_data)` with **no read of the existing file and no existence check**. ## Refuted during adversarial review

### G1 (partial) — "the process dies with a traceback and prints no TOON"

The original G1 asserted that, because no caller handles `ConcurrentConfigModificationError` and `main()` has no wrapper around `result = cmd_*(args)`, "the process dies with a traceback and prints no TOON", making the outcome "unparseable by the LLM callers these verbs exist for". That mechanism clause is refuted.

- The sweep behind it (`grep 'except ConcurrentConfigModificationError'`) was too narrow: the handler is a bare `except Exception` inside the `@safe_main` decorator, which the pattern could not match. `manage-config.py:61` imports `safe_main` and `:169` applies it to `main()`.
- `file_ops.py:1664-1700` `safe_main` catches every `Exception`, calls `output_toon_error('internal_error', str(e))` — which prints TOON to **stdout** (`file_ops.py:1502-1514`) — and exits 1.
- Executed: driving `manage-config.py:main()` with a `orchestrator set` verb over a forced load→concurrent-write→save race gave `stdout = "status: error\nerror: internal_error\nmessage: …"`, `stderr = ""`, exit 1. The caller receives a parseable payload naming the condition and the recovery.

What survives is narrower and is re-filed above as G1 at `low`: the tier (exit 1 / `internal_error`) misreports a recoverable condition as a crash, and there is no machine-readable discriminator. The genuine "no TOON at all" instance is `upgrade.py`, which has no `@safe_main` — filed separately as G8.
