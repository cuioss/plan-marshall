# When a claim is about a mechanism, read the mechanism - a timing, a comment or an ordering is a proxy, not the wiring

## Observation

Four instances in one session, across two agents, of the same move: **a claim about a MECHANISM
asserted from a PROXY, without reading the mechanism.**

| # | The proxy that was read | The claim it was used to support | Verdict |
|---|---|---|---|
| 1 | a comment in `application.properties` | that the comment stated a live constraint | wrong |
| 2 | a stale ledger entry | that plan X was still running, so surfaces overlapped | wrong |
| 3 | **per-module build timings** (1.5s / 18.4s) | that the resolver "can scope but didn't" | **wrong — the expensive step never consulted the resolver at all** |
| 4 | **post-merge `order:` frontmatter values** | that a stale-cache ordering defect was refuted | **wrong — that was the order the plan INSTALLED, not the order it RAN** |

⭐ **Instance 3 is the most instructive.** The timings were real, the arithmetic was right, and the
conclusion was still wrong — because the fast per-module runs came from a **different build path**
than the six slow ones. Reading `marshal.json`'s `build.map` (a glob→build_class table applied to the
actual diff) settled in minutes what the timings could only be used to guess at: the classifier **is**
wired and ran; the expensive `pre-push-quality-gate` is **whole-tree and never consults the
footprint**, and would have run identically on a pure `.adoc` change.

⛔ **A proxy can be accurate and still support the wrong conclusion**, because it is silent about
which mechanism produced it. That is what makes this different from working with bad data.

## Rule

- **When the claim is about how something WORKS, read the implementation.** Timings, log lines,
  comments, orderings and ledger entries are *evidence that something happened* — they are not
  evidence of *what is wired to what*.
- ⭐ **The tell is a causal verb in the claim**: *"the resolver chose"*, *"the gate selected"*, *"the
  sync ordered"*. A causal verb asserts a mechanism. **If no file has been read that implements that
  verb, the claim is a hypothesis** and must be labelled one.
- **Reading the mechanism is usually CHEAPER than the inference** — one `grep` for the config table
  versus an argument from six build durations. The inference feels cheaper because the proxy is
  already in hand.
- **Two artifacts that look like the same measurement may come from different code paths.** Before
  comparing them, establish that they do. (Instance 3: fast and slow builds; instance 4: installed
  order and executed order.)
- **Three or more instances is a habit, not a slip** — count them across a session and escalate the
  logging level rather than filing each as an incident.

## Impact

Every claim-labelled HYPOTHESIS/OBSERVED distinction in the plan and orchestrator tiers; the
verify-first discipline; and any analysis that reasons from metrics, logs or timings toward a
statement about wiring. Related: the sibling rule that a reviewer's named site list is a sample, and
the corpus rule to read a run's order from its own manifest rather than the tree it produced.
