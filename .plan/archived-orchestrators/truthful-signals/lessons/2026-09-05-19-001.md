# Build wrapper reports 'no structured errors were parsed' while the daemon job log carries a correct structured error

## Problem

The `pyproject_build run` wrapper returned a failing build whose outer TOON claimed no structured
errors were available:

```toon
status: error
exit_code: 1
error: build_failed
errors[1]{file,line,message,category}:
  <job-log-path>,-,"Build failed but no structured errors were parsed; see full log: <job-log-path>",build_failure
```

The claim was false. The daemon job log for the very same job already carried a correct structured
extraction — `errors[1]{file,line,message,category,detail}` with `category: test_failure`, the exact
failing file and line, plus a `tests:` block (`passed: 20140, failed: 1, skipped: 10,
duration_seconds: 531.05`). The parse had succeeded; only the surfacing failed.

Observed on a routed daemon build (`mechanism=daemon_longpoll`) of `verify plan-marshall`,
job `bdf9994241294ab8a3ec862a1839bd96`.

## Why it matters

The synthesized `build_failure` row is indistinguishable, at the consumer, from a build that
genuinely produced no parseable diagnostics. A caller that trusts the outer TOON concludes "the
build failed and told us nothing", and its only remaining move is to hand a 40,000-line log to an
LLM — which is exactly the expensive fallback the structured extraction exists to prevent. Here that
fallback cost a full sub-agent dispatch to re-derive a finding the daemon had already written down.

This is the *not looking renders identically to looked-and-found-nothing* archetype, one layer up
from where it is usually tracked: the wrapper is not wrong about the build failing, it is wrong
about **its own knowledge of why**. A confident negative ("no structured errors were parsed")
covers for a lost payload.

## Directive

Establish whether the routed/daemon path reads the job's structured `errors[]` at all before
synthesizing the `build_failure` placeholder. The placeholder must be reachable only when the
extraction genuinely yielded nothing — never as the default when the routed path simply did not look
at the job record.

Where the placeholder is legitimately emitted, it must say which of the two it is: extraction ran
and found nothing, versus extraction was not consulted. A single message covering both reproduces
the defect it is reporting.

## Verification

A routed daemon build with exactly one failing test must surface that test's file, line and
`category: test_failure` in the wrapper's own return — not only in the job log. Assert on the
wrapper return, not on the log: the log was already correct, so a test that reads the log passes
today and proves nothing.
