All eight deliverables landed and every *Done when* clause that can be executed was executed and holds: the D1 bypass turns three guards red under mutation, the pin-trap oracle returns `indeterminate` on all four unread-axis shapes and `fail` on both divergence shapes, the clean gate publishes three population figures, the shim recall is measured at 4-of-25 and published, and **every census and count figure in `report-01.md` re-derives exactly**. ## G1 — `analyze_argument_naming` reports `findings: 0` over a population it never examined, and the run never recorded the coverage gap

- **Kind:** vacuous-guard
- **Severity:** high
- **Where:** `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_analyze_argument_naming.py:938-952` — `analyze_argument_naming`; routed through `scoped(...)` at `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_runner.py:203`; the omission is in `doc/plans/truthful-signals/500-…/report-01.md`, which contains no mention of it
- **What is wrong:** the cluster resolves its ground truth from `marketplace_root.parent / '.plan' / 'execute-script.py'` and returns `[]` when that file is absent or its registry is empty — *"Treat as a no-op."* Confirmed by execution: over a synthetic bundles tree with no executor, `analyze_argument_naming(bundles)` returns `[]` and `cmd_quality_gate` records `{'rule': 'analyze_argument_naming', 'findings': 0}`. No population figure, no `EMPTY_POPULATION_TYPE` finding, no anti-vacuity anchor — the rule cannot be distinguished from one that examined every documented invocation and found them all correct. There is also no real-tree anchor test for the cluster; its only coverage is fixture-level. `plan.md` § Notes names this mechanism outright (*"the argument-naming cluster silently returns no findings without the executor"*), and the Claim-labels row for 060/G7 commits the run to a disclosure — *"the whole-tree gap is **recorded**, not asserted clean"* — while D3's own text says *"record the coverage gap in the run report rather than reporting the tree clean."* The report records nothing: no § Findings row, no coverage-check note, no mention of `.plan/` absence anywhere.
- **Why it matters:** this is the epic's headline shape, live in the shipped gate, in a file the plan's own Expected surface lists (D3, D6) and whose rule set this plan **grew** — `ARGUMENT_NAMING_ROUTER_FLAG_MISPLACED` was added here. In the very environment the plan was written for (a cloud clone, where `.plan/` is git-ignored and absent), the entire `ARGUMENT_NAMING_*` cluster including the new rule is inert and the gate reports it green. D1's derivation legitimately did not catch it — D1 enumerated rules that can emit a *root-anchored finding*, and this rule emits no finding at all — but that is exactly why the disclosure the plan asked for was the remedy, and it was not written.
- **Fix:** give the cluster the same treatment D5 gave the other three. Have `analyze_argument_naming` return `(findings, population_size)` from one derivation — the size being the count of registered notations actually scanned — so `_runner.py`'s `emit` publishes it on the rule summary, and emit a root-anchored `argument_naming_ground_truth_unavailable` finding when `load_registered_notations` yields an empty registry, so `_finding_is_tree_wide` carries it through a `--paths` run. Add a real-tree anchor asserting the registered-notation population is above a floor. If the population figure is judged out of scope, the minimum is to state the inertness in `rule-catalog.md`'s `ARGUMENT_NAMING_*` entry and in the module docstring, so the coverage gap is declared rather than silent.
- **Done when:** a quality-gate run over a tree with no `.plan/execute-script.py` reports either a non-zero `findings` count or a published `population_size` of 0 for `analyze_argument_naming`, and a committed test asserts it; or `rule-catalog.md` and the module docstring both state that the cluster is a no-op without the executor and that a clean result from it is not evidence of coverage.
- **Module/topic:** `pm-plugin-development:plugin-doctor` — the `ARGUMENT_NAMING_*` rule cluster

## G2 — The D1 control that claims to reject a finding-type registry cannot fail for that reason

- **Kind:** vacuous-test
- **Severity:** medium
- **Where:** `test/pm-plugin-development/plugin-doctor/test_quality_gate_root_anchored_findings.py:228-241` — `test_the_bypass_keys_on_the_anchor_not_on_a_finding_type`
- **What is wrong:** the test's docstring states *"The bypass must not degrade into a whitelist of the three finding types that anchor this way today … Driven with a synthetic finding type no rule emits, so a **type-list implementation fails here**."* It does not: the body calls only the two predicates `_finding_in_scope` and `_finding_is_tree_wide` and never `_scoped`, so an implementation that keys on finding types **inside `_scoped`** leaves both predicates returning exactly the same values. Confirmed by mutation, not by reading: replacing `or _finding_is_tree_wide(f, marketplace_root)` in `doctor-marketplace.py:855` with a hand-maintained registry — `f.get('type') in {'thinking_directive_population_empty','shim_marker_population_empty'} or (f.get('type')=='incident_reference' and f.get('pattern_family')=='empty_population')` — leaves this file at **7 passed** and the whole `test/pm-plugin-development/plugin-doctor/` directory green (1885 passed). No test anywhere kills that mutant.
- **Why it matters:** this is the same defect class CodeRabbit's C15 found in the sibling test *in this same file* — a control that cannot fail for the reason it names — corrected there and left standing here. And the property it fails to pin is the one the plan's ⛔ STOP CONDITION singles out: *"Do **not** fall back to a hand-maintained list of exempt finding types: a hand-maintained enumeration of a machine-derivable set is the defect class this epic exists to remove, and writing one here would reproduce it inside the fix."* The shipped implementation **is** anchor-keyed and correct; what is missing is any guard that keeps it that way. A future maintainer who "simplifies" the anchor test into a type list gets a fully green suite.
- **Fix:** rewrite the test to drive a real scoped `cmd_quality_gate` — the way `test_per_file_findings_still_obey_the_scope_filter` was rewritten for C15. Build a fixture tree that emits a root-anchored finding of a type no rule registers (a monkeypatched analyzer, or a fourth rule stub registered into the runner for the test), run the gate with a non-empty `--paths` scope, and assert the finding survives. Then mutate `_scoped` into a type registry and confirm the test reddens before landing it.
- **Done when:** replacing `_finding_is_tree_wide` in `_scoped` with any finding-type whitelist makes at least one committed test fail, and the test that fails is the one whose docstring claims to pin the property.
- **Module/topic:** `pm-plugin-development:plugin-doctor` — `cmd_quality_gate` root-anchor bypass

## G7 — The clean gate publishes the enum rule's population but not its blind-spot count, so `152` reads as coverage over 152

- **Kind:** incomplete-sweep
- **Severity:** low
- **Where:** `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_runner.py:160-180` (`emit`) and `:290-297`; the census lives on `marketplace/bundles/pm-plugin-development/skills/plugin-doctor/scripts/_analyze_canonical_enum_drift.py:1398` (`derive_coverage`) and on findings only (`:1516-1519`)
- **What is wrong:** on a clean tree the gate emits `{'rule': 'canonical-enum-choices-drift', 'findings': 0, 'population_size': 152}` — executed and confirmed. Re-derived from the same tree: of those 152 sites only **81** were actually compared against a live `choices=`; **71** are unresolved and **69** of those are blind spots. `unresolved_notation_fraction`, `unresolved_notation_blind_spots` and `unresolved_notation_causes` ride on **findings**, so they are absent in exactly the state the plan names as the only one a passing gate is ever in. The published figure's own docstring calls it *"the count of enum sites the sweep **examined**"*, which overstates it by 71.
- **Why it matters:** this is 040/G1's shape one level in, on the rule RÅ-3 wired *because of* 040/G1 — the population figure was rescued from the findings and the coverage census was not. A reader of a green gate sees "152 examined, 0 findings" and cannot tell that 45.4% of that population was never compared. It is **low** rather than medium only because the rule catalogue discloses it honestly and points at the alternative surface: `rule-catalog.md:1124` states that the keys ride on findings, that the runner summary carries `population_size` for that reason, and that *"`derive_coverage` over `derive_population` is the full clean-run surface."* The gap is declared, not silent — which is what the plan's Goal offers as the acceptable alternative.
- **Fix:** let `emit` take an optional coverage mapping alongside the size, and have `analyze_canonical_enum_drift_with_population` return `derive_coverage`'s `blind_spots` (and ideally `resolved`) from the same derivation, so a clean summary reads `{'rule': …, 'findings': 0, 'population_size': 152, 'resolved': 81, 'blind_spots': 69}`. Add a real-tree test asserting the blind-spot figure is present on a clean run, mirroring `test_population_publishing_rules_report_their_size_on_a_clean_tree`. Failing that, rename the finding-level docstring's "examined" to "collected", since 71 of them were not examined.
- **Done when:** a clean quality-gate run states, for `canonical-enum-choices-drift`, both the population it collected and the share of it it could not check; and a test asserts the second figure on a clean, non-empty population.
- **Module/topic:** `pm-plugin-development:plugin-doctor` — rule `canonical-enum-choices-drift`, runner summary
