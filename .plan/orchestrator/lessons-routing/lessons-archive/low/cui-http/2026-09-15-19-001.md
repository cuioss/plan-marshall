# An outline deliverable asserted a fact about current code (mechanism, symbol, site enumeration, or line citation) never read off the file — four instances in one Q-Gate cycle

## Observation

PLAN-07's solution outline (phase `3-outline`) produced exactly four Q-Gate rejections, and all
four are the same failure class: outline prose asserted a fact about current code — a
guard-placement mechanism, a method's existence, a set of Javadoc sites, a line-citation's
direction — that was never actually read off the target file at authoring time. Each instance
individually reads as plausible prose to anyone who does not open the file; the wrongness is
invisible at the citation site.

Two of the four were independently reported twice by the executing plan (once as a generic
phase-3-outline summary, once with the specific Q-Gate finding id) and are folded here as one
occurrence each, not two:

1. **Invented guard mechanism (deliverable 1).** The outline said the new positive host predicate
   is "applied at the same call site inside `parseHostPort`" and that the bracketed-IPv6 branch is
   "NOT routed through" it, but never named the mechanism that would exempt that branch. At HEAD
   the shared guard (line 582) is post-branch-chain — every branch reaches it, including the
   bracketed one — so a literal substitution there would have rejected every bracketed host,
   breaking the existing `rejectsBracketedNonLiteralHost` positive control. The deliverable stated
   an exemption without specifying how it is produced.
2. **Invented symbol name (deliverable 2).** The outline named `parseAllowedContextPaths` as one of
   two allow-list entry points. A complete-coverage literal sweep (303 files scanned) returned zero
   hits — the symbol does not exist anywhere in the repository. The real second entry point is
   `ForwardedResolverConfig.parseAllowlist(String)` (line 199). The substantive behavioural claim
   was correct; only the name was synthesized from the codebase's naming conventions rather than
   read from the file.
3. **Wrong Javadoc-site enumeration with a false rationale (deliverable 3).** The outline listed
   four Javadoc sites to update "because the host half now resolves empty too", but a
   complete-coverage sweep showed the rationale was false at every one of the four sites (none
   implies the host survives) and the enumeration itself was wrong (one site misattributed, two
   real sites omitted). Following the deliverable as written would have weakened six paragraphs of
   accurate prose while missing the one site that genuinely needed the edit — for a different
   reason than the one given.
4. **Inverted line citation, adjacent-range case (deliverable 5).** The outline instructed deleting
   "the stale clause ... (current lines 719-724)" while requiring a different clause be kept. At
   HEAD the stale clause was actually at lines 715-717, and 719-724 was the rationale paragraph the
   same deliverable required to be KEPT — the two ranges were inverted. A careful reader could
   recover from the prose quote, but only by ignoring the one thing the plan told the reader to
   trust: the re-derived line citation.

## Why this is lesson-bearing

All four are instances of one recurrence class — outline authoring asserting a fact about current
code without having read the code that would confirm or refute it — inside a single plan's single
outline pass. Q-Gate caught every instance (0 escaped to execution), but each catch cost a full
outline re-dispatch round-trip. The class is self-concealing at the authoring site: a plausible
mechanism, a conventionally-named symbol, a hand-recalled site list, and a line range that
resolves to something real (just the wrong something) all read as correct to an author who did not
re-open the file at the moment of writing.

## Correctives, one per instance shape

- **Mechanism claims** ("X is exempt", "Y is guarded before Z"): before writing, open the target
  method and read the control flow at the cited line; describe the mechanism that is actually
  there, or give a concrete implementable form (e.g. an early return) rather than asserting an
  outcome with no stated means.
- **Symbol claims**: quote every named symbol verbatim from the file, never reconstruct it from
  sibling naming conventions. Run a complete-coverage literal content sweep
  (`architecture search --content --literal --pattern <symbol>`) for every symbol an outline names,
  and treat a zero-hit result as a hard authoring error.
- **Site-enumeration claims** ("update the Javadoc on X, Y, Z"): re-derive the set from the
  declaring source at authoring time, not from memory. Where useful, mark surveyed-but-untouched
  sites DO-NOT-EDIT with the reason — the DO-NOT-EDIT list is what makes the enumeration
  falsifiable.
- **Line-citation claims**, and especially adjacent-range cases (one range to delete, an adjacent
  one to keep in the same comment block): re-open the file and confirm the cited line holds the
  construct described, including which of two adjacent ranges is which. Cite both ranges, state
  the direction explicitly in one line, and quote a distinguishing fragment of the KEPT range so
  the two cannot be silently swapped.

## Scope

All deep-lane outlines authored by `plan-marshall:phase-3-outline`. Related but distinct from
lesson `2026-09-09-10-001` ("An outline deliverable declared an affected file its own change list
never touched") — that lesson is about declared-surface accuracy; this one is about claims-about-
code-behaviour accuracy. Both share the root cause of unverified prose written from a mental model
rather than from the file.
