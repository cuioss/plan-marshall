# A producerless SECTION_SPEC row is an operator proposal, not an in-plan decision

## The rule

When a `plan-retrospective` change surfaces a `SECTION_SPEC` row whose renderer is live but whose
producer does not exist, the settled disposition is to **RECORD the choice as an operator proposal
carrying both options and a recommendation — and escalate it** — rather than to pick one inside the
plan that found it.

Registering a producer and deleting the row are both defensible, and they diverge on a standing
invariant: whether the compiler stays a pure assembler. That decision belongs to whoever owns the
invariant, not to the plan that happened to notice the row.

## Why this is not ordinary scope discipline

The two options are not "bigger fix vs smaller fix" — they point in opposite architectural
directions. Adding a producer imports an LLM-authored surface into a component documented as a pure
assembler; deleting the row removes a requirement the shipped specification still states as
mandatory. A plan that picks one silently has settled an architecture question as a side effect of a
detector fix.

Observed twice on PLAN-CIS-051 / PR #1370: `_executive-summary` (no producer may register it —
`valid_aspect_keys` filters underscore-prefixed keys — so the only writer in the repository is a test
fixture) and `dispatch_boundaries` (the sole producer nests it inside the `log-analysis` fragment
while the trigger looks for it at bundle top level). Both were recorded with options and a
recommendation, and neither was implemented in-plan.

## How to apply it

1. Establish that the row is genuinely producerless — a content sweep for the key that separates
   reads, comparisons and documentation from an actual injection site. A key whose only writer is a
   test fixture is producerless.
2. Write both options and name the invariant they diverge on.
3. Give a recommendation with its reasoning, so the escalation is a decision request and not a
   shrug.
4. Escalate; do not implement. Deleting a false claim the code makes about the row is in scope and
   is a different act from settling the row.

## The trap that makes this hard to see

A producerless row reads as benign in every report it appears in. The section lands in
`sections_omitted` — the half that means "there was nothing to lose" — so the compiler reports a
clean run over a section that can never render. Verification does not catch it either: fixtures inject
the key directly, so the drop-versus-omit predicate is exercised on a populated path that production
never takes. Four self-review rounds and 42/42 mutation kills missed it, because the mutation
population is the code the fixtures reach.
