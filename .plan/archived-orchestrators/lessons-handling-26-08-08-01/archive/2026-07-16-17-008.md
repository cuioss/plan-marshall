# Behavior-changing fixes: sweep ALL reactor consumers, not just the changed module's own tests

Re-homed from the TokenSheriff consumer store 2026-07-16 ([[feedback_manage_lessons_cwd_store_resolution]]).

**Context:** TokenSheriff plan `client-code-review-fixes` (OIDC/OAuth client security remediation). Two behavior-changing fixes altered observable protocol behavior: **C1** switched the authorization response to `response_mode=form_post`; **M5** made the client throw a typed `ClientProtocolException`.

These broke real-Keycloak integration SpecITs encoding the OLD behavior: `AuthCodePkceSpecIT` and `StepUpSpecIT` expected a `302` redirect (now `form_post`), `MixUpSpecIT` expected `IllegalStateException` (now the typed `ClientProtocolException`). Those SpecITs live in a **separate module** (`token-sheriff-quarkus-integration-tests`) that was **outside the plan's declared scope**, so phase-5 verification only ran the changed module's own tests and never touched them. The breakage surfaced only in CI, after push.

**Why it slipped:** Phase-5 verification scopes its test runs to the modules the plan declared in-scope. A change altering an *observable protocol behavior* (redirect mode, exception type, wire format, status code) has consumers asserting the old behavior wherever they live — including integration/E2E tests in sibling reactor modules the plan never named.

## How to apply

When a change alters an observable protocol behavior — redirect/response mode, thrown exception type, HTTP status, serialized wire format, header contract — **sweep for ALL consumers and tests across the WHOLE reactor, not just the changed module's own tests**:

1. Grep the entire reactor for assertions on the old behavior (`302`, `IllegalStateException`, the old status/mode literal), not just the changed module.
2. Explicitly run the sibling integration-test modules (`*SpecIT`, `*IT`) that exercise the changed flow end-to-end, even outside the plan's declared scope. Update them in the same plan/PR so the change lands atomically with its consumer updates.
3. Treat "out-of-scope module" as a scoping *input* to verification, not a reason to skip — a behavior change's blast radius is defined by its consumers, not by the plan's declared file set.
