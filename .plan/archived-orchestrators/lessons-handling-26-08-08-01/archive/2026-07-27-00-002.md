# kind=build rows record exit_code 0 for timed-out builds, and --help probes count as builds

## Observation

`pre-commit-verify-freshness` (the Step 12a gate that authorises the `5-execute → 6-finalize` transition) filters the change-ledger on `kind`, `exit_code`, and `worktree_sha`. Two classes of row satisfy that filter while representing no successful build. Both were observed live in plan `orchestration-inbox-channel`'s ledger.

Reproduce with:

```
manage-change-ledger query --kind build --exit-code 0
```

### (a) A TIMED-OUT build is recorded with `exit_code: 0`

Two rows in the live ledger, both returned by the `--exit-code 0` query above:

```
run --command-args coverage plan-marshall,                       0, build, ..., timeout, 21:56:45Z, 7c761eff…
run --command-args coverage --timeout 2400 --plan-id …,          0, build, ..., timeout, 22:12:16Z, 7c761eff…
```

`status: timeout`, `exit_code: 0`. The underlying wrapper reported `exit_code: -1` in both cases — the ledger append discarded that and wrote `0`. The truthful field (`status`) exists but is **not part of the gate's filter**, so a build that was cut off partway through and never completed is indistinguishable, to the gate, from one that passed.

This is the more serious of the two: it is not a hypothetical shape, it is two rows on the exact `worktree_sha` this plan transitioned on. The transition happened to be legitimate on other evidence (a genuine `verify plan-marshall` success at the same sha), but that was luck of ordering, not the gate working.

### (b) `--help` probes are recorded as successful builds

Nine rows on the same ledger, e.g.:

```
--help,                    0, build, ..., success, 21:21:31Z
check-warnings --help,     0, build, ..., success, 21:21:33Z
run --help,                0, build, ..., success, 22:01:21Z
--help,                    0, build, ..., success, 21:34:48Z   ← notation build-npm:js_coverage
```

The last one is notable twice over: it is an npm coverage script's `--help` in a **Python** repo, and the freshness gate cited exactly this row as its evidence (`matched_notation: plan-marshall:build-npm:js_coverage`, `21:34:48Z`) when it returned `fresh`.

An argparse help dump compiles nothing and tests nothing. It is recorded as `kind=build, status=success, exit_code=0`.

## Why it matters

Together these make the freshness gate satisfiable without any build having run. A plan whose only same-`worktree_sha` `kind=build` rows were a `--help` probe and a timed-out run would transition to finalize, and the gate would report `fresh` citing them.

The gate is doing exactly what it is documented to do — the defect is upstream, in what gets written to the ledger as a "build". This is the vacuous-guard archetype: a check whose predicate is satisfiable by inputs that carry none of the meaning the check exists to confirm. It sits squarely in the `truthful-signals` theme.

Note also that `status` is present and correct on every row. The information needed to reject both classes is already recorded — it is simply not consulted.

## Directive

Fix at the append site, not by loosening or special-casing the gate.

1. **Never write `exit_code: 0` for a non-success outcome.** Propagate the real exit code (the coverage timeouts were `-1` at the wrapper). A row whose `status` is `timeout` / `error` must not carry a success exit code — the two fields contradicting each other is the bug.

2. **Do not classify non-building invocations as `kind=build`.** A `--help` probe, a `--version`, or any argparse-only path that executes no build command should either not append a ledger row at all, or append under a kind that no freshness/verification gate consults. Decide which at the append site in `manage-change-ledger`, where the invocation args are known.

3. **Make the gate consult `status` as well as `exit_code`** as defence in depth, so that even if a contradictory row is written again the gate rejects it. This is secondary to (1) and (2) — it is a backstop, not the fix.

4. **Add a test** pinning that (i) a timed-out build append cannot produce `exit_code: 0`, and (ii) a `--help` invocation does not produce a row that satisfies the freshness predicate. Without (ii) the guard stays vacuous in exactly the way this lesson describes.

## Provenance

Surfaced by the phase-5-execute leaf during the Step 12a gate check on plan `orchestration-inbox-channel` (it flagged facet (b) and correctly declined to treat the green as proof); facet (a) and the `exit_code` contradiction were confirmed by the orchestrator querying the live ledger directly. Sibling lessons from the same session: [[2026-07-27-00-001]] (routed builds discard `--timeout` and zero out `duration_seconds`) and the phases-2/3/4 clean-main assertion tripping on sanctioned `architecture enrich` writes. All three are the same family — machinery whose recorded signal is more confident than the thing it observed.

## Recurrence — 2026-07-27 (refusal-recognizer-generalizes-phrasing)

Both facets reproduced verbatim on the very next plan, on a different `worktree_sha`, and this time they **co-occurred on the same sha** — producing exactly the composite the "Why it matters" section above predicted as hypothetical. `manage-change-ledger query --kind build` on this plan's ledger returns 37 rows; the relevant ones:

**Facet (b) reproduced, same notation.** Two rows at `worktree_sha 45801b3d…`:

```text
--help,          0, build, plan-marshall:build-npm:js_coverage, success, 10:40:20Z
analyze --help,  0, build, plan-marshall:build-npm:js_coverage, success, 10:40:32Z
```

Same `build-npm:js_coverage` notation as the original instance — an npm coverage script's `--help` in a repo with no npm build system — and the push-time `pre-commit-verify-freshness` again returned `fresh` citing it. The gate is notation-agnostic by design: it matches ANY `kind=build` row at the sha, so a foreign build system's help dump satisfies a Python plan's freshness precondition.

**Facet (a) reproduced, and on the SAME sha.** Two module-tests rows, also at `45801b3d…`:

```text
run --command-args module-tests --plan-id …, 0, build, …, timeout, 11:18:59Z
run --command-args module-tests,             0, build, …, timeout, 11:39:36Z
```

`status: timeout`, `exit_code: 0` — the exact field contradiction directive (1) exists to prevent.

**What the co-occurrence adds.** The original lesson said "a plan whose only same-`worktree_sha` `kind=build` rows were a `--help` probe and a timed-out run would transition to finalize" and flagged it as the hypothetical worst case. On `45801b3d…` that is the actual row set for testing: **every** module-tests row at that sha timed out, and the only other rows are two `--help` probes, two `quality-gate` runs, and a log `parse`. No test run succeeded at that content hash, and the gate said `fresh`. The original instance was saved by "luck of ordering" (a genuine `verify` at the same sha); this one had no such luck. The predicted failure mode is no longer hypothetical.

**New sub-facet — pure query/parse verbs also land under `kind=build`.** Beyond `--help`, this ledger carries eight `plan-marshall:build-pyproject:pyproject_build parse --log … --format json` rows recorded as `kind=build, status=success`, plus a `resolve-test-scope` row (the latter already filed as [[2026-07-22-16-003]]). `parse --log` reads an existing build log off disk; it compiles nothing and runs no test. This widens directive (2): the append-site classifier must exclude **every** non-building invocation of a build-notation script — argparse-only paths (`--help`, `--version`), pure read/query verbs (`parse`, `resolve-test-scope`), and any subcommand that does not shell out to the build tool — not just the help probes the original instance named. Keying `kind=build` on the notation's bundle:skill prefix rather than on what the invocation actually did is the shared root cause of this sub-facet and of [[2026-07-22-16-003]].

**Standing conclusion strengthened.** Two consecutive plans, both facets, same notation, now with the composite realized. Directive (3) — make the gate consult `status`, not only `exit_code` — was filed as a secondary backstop; on this evidence it should be promoted, because it is the only one of the four directives that would have blocked this run's `fresh` verdict without any change to the append site.
