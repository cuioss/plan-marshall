# A gate build row is written with `worktree_sha=None`, and the reason it is harmless rests on a convention, not an invariant

Filed because plan-pr-046 declined this finding and then carried it **nowhere** — it appears
in none of that plan's eleven inbox messages. It was dropped, not routed. This message is the
carry that was owed.

The `None` is deliberate and documented in the docstring at lines 460-466.

## The observation is valid; the impact argument is the weak half

CodeRabbit raised it as `c5db78` (Major) on PR #1477. Resolved `taken_into_account`, not
`rejected` — the code observation was never disputed. Its claimed consequence was: a direct
`cmd_run` build appends a `kind=build` row carrying no currency hash, so a consumer reading
that row for freshness sees `stale` and blocks the pre-commit transition.

That consequence was argued unreachable on two grounds, and **both are weaker than a refutation**:

1. **"The executor dispatch boundary already stamps the sha-bearing row for real runs."**
   True for builds that cross that boundary. The docstring itself states the complement:
   *"only a direct `cmd_run` call (including the red-first unit-test path) leaves this one
   alone."* So the unreachability depends on nothing calling `cmd_run` directly outside
   tests.
2. **"Routing all builds through the executor is a hard rule here."** This is a *convention*.
   A convention is enforced by review and documentation, not by the type system. The moment
   a caller bypasses the executor — a new seam, a consumer project, a future refactor — the
   path CodeRabbit described opens, and it opens silently, because the row is written
   best-effort and fail-open (`except Exception: pass`).

⚠ The distinction that matters to this epic: **"no current caller reaches it" is not
"unreachable".** A guard whose safety is a function of caller discipline should say so, or be
made unconditional.

## The real constraint, which is a genuine cost

The `None` was not chosen for convenience. Resolving the hash here would issue
`subprocess.run` git calls AFTER the build, hijacking the globally-patched `subprocess.run`
mock the **timeout-truthfulness suite** asserts on — its `call_args` would read the git call,
which carries no `timeout` kwarg. So the naive remedy CodeRabbit implied would break that
suite.

That is an argument for a **different** fix, not for none. Options worth weighing:

1. Resolve the sha BEFORE the build runs and pass it in, so no post-build subprocess call is
   issued and the mock is untouched.
2. Give the row an explicit `worktree_sha_unavailable` / `sha_source=seam_level` marker so a
   consumer can distinguish "not resolved here by design" from "resolved and empty" — today
   `None` conflates them.
3. Establish whether any consumer actually reads `worktree_sha` off a `kind=build` row for a
   freshness verdict. If none does, the finding is genuinely inert and that should be
   **derived and recorded**, not assumed — which is the check nobody ran.

Option 3 is the cheap one and should come first: it decides whether 1 and 2 are needed at all.
