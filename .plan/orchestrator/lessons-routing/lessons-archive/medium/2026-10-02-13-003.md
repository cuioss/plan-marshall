# PR-level issue comments are handled by coarse rules: a reviewer security concern is pre-filtered away, the workflow's own reply is filed as a finding, and post_responses cannot select or answer per finding


## Observed (API-Sheriff PR #369, plan-23-session-route-scope-parity, 2026-10-02)

Four linked failures in one review round, all on PR-level comments (kind `issue_comment`, no review
thread).

1. **A security concern was filtered out before triage.** CodeRabbit's walkthrough comment
   (IC_kwDOPatrT88AAAABYg2hwA) carried a "Security Architecture Review" section rated High: a widening
   or refresh write that lands after a logout recreates the terminated session. The producer drops
   walkthrough comments as noise, so no finding was filed. It reached triage only because the
   orchestrator had the comment read by hand and filed finding 5fcb44 itself (work log
   2026-10-02T06:48Z). The concern was real and was fixed in the same PR (TASK-20, commit 84c5d0be).
2. **The hand-filed finding could not be answered.** `github_pr post_responses` could not transmit
   the reply for 5fcb44 because a hand-filed finding carries no `pr_number` metadata (decision b9f11d).
   The reply was posted by hand as a PR-level comment.
3. **The workflow's own reply came back as a finding.** The next fetch filed that hand-posted reply
   (IC_kwDOPatrT88AAAABYpYySA, authored by the operator's account) as pr-comment finding 8d1ac5. It was
   rejected in triage as a misfiled self-response.
4. **`post_responses` has no per-finding selection.** It transmits every terminal pr-comment finding
   that has a `resolution_detail` and no `responded` marker. With 8d1ac5 in that set, running it would
   have published an internal triage note as a public reply to the operator's own comment
   (decisions a948c8, 515ccd). The triage leaf withheld the call, and the two legitimate replies were
   posted through `ci pr thread-reply` and `resolve-thread` by hand.

## Root cause

PR-level comments are classified by where they come from, not by what they contain: a walkthrough is
noise as a whole, and any other issue comment is a finding as a whole, including one the workflow
wrote. The responder then treats the terminal set as one batch.

## Directive

- The pre-filter must not drop a bot comment that contains a review section with a severity. Either
  file such sections as findings, or report "walkthrough comment skipped, contains N rated sections"
  so the skip is visible.
- Do not file comments authored by the account the workflow posts with; at least skip a comment whose
  id the workflow itself recorded as a posted reply.
- Give `post_responses` a per-finding selector, and let it answer a finding that has no thread by a
  PR-level comment when `pr_number` is supplied on the call.
- Hand-filing a pr-comment finding should require `pr_number` (and `kind`), so the finding stays
  answerable.
- Until the tool changes: have the FIND agent read the reviewer's walkthrough or summary comment in
  every round, and list the terminal, not-responded pr-comment findings before any `post_responses`
  call.
