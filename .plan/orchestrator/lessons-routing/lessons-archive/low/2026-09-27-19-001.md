# Module_testing scope narrowing is undocumented in phase-4-plan's task-split algorithm

## Context

`phase-3-outline/standards/outline-workflow-detail.md`'s File-type classifier explicitly
defines a `**Module_testing scope:**` block: for a `mixed_with_docs`-bucket deliverable, the
`module_testing` profile applies ONLY to the production/test paths, and phase-3-outline MUST
declare the narrowed scope in that block "so pytest does not burn cycles on documentation
files." The stated *purpose* is to shape downstream task-creation — but `phase-4-plan/SKILL.md`
never names or consumes the `Module_testing scope:` heading anywhere in its documented Step 5/6
algorithm. Its Contract Compliance section only cites `**Affected files:**` and the survey-scope
`**Files expected to mutate:**` / `**Files to survey:**` pair as the declared sources for
`task.steps`.

`manage-solution-outline list-deliverables` / `read --deliverable-number N` do not surface
`Module_testing scope:` as a structured field either — it is only visible via
`read --section deliverables --raw` (full markdown). A phase-4-plan run following only the
documented script API therefore cannot discover this heading exists without reading raw
markdown, which its own Step 6 pseudocode does not instruct.

## Resolution taken

During PLAN-13 (`plan-13-finalize-mechanism-defects`), for every `mixed_with_docs` deliverable
(D1-D4) I read the raw deliverable prose, found the `Module_testing scope:` block, and used it
to narrow each `module_testing`-profile task's `steps[]` to just that block's paths — while the
paired `implementation`-profile task kept the full `Affected files:` list (docs included). This
is a judgment call, not a literal instruction from `phase-4-plan/SKILL.md`; I proceeded on it
because leaving the heading unconsumed would make it a functionally inert declaration (phase-3
would be producing a narrowing signal no downstream consumer reads), and because the deliverable
mechanical Q-Gate (`qgate-mechanical-checks` — coverage, skill-resolution, acyclic, files-exist,
keyword-drift, structural-token-drift, declared-set-closure, declared-scope-reconciliation)
subsequently returned `total_failed: 0` across all 10 tasks / 5 deliverables, which corroborates
the interpretation did not break declared-set closure (the `implementation` task's full-list
steps still cover every declared path).

## Suggested follow-up

`phase-4-plan/SKILL.md` Step 5/6 (or the Contract Compliance "Steps Field" note) should
explicitly name `**Module_testing scope:**` as a third declared-steps source, alongside
`Affected files:` and the survey-scope pair, with the rule: implementation task steps = full
`Affected files:`; module_testing task steps = the narrowed `Module_testing scope:` block when
present, else the same full list. Ideally `manage-solution-outline list-deliverables` /
`read --deliverable-number N` would also surface `module_testing_scope` as a structured field
so a plan-4-plan run never has to fall back to raw markdown to discover it.
