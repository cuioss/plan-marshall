# The merge mutex survived a session boundary far past its hold budget with a waiter queued, and nothing reclaimed it

## Context

Plan `unreviewed-merge-gate-holes` acquired the merge mutex at 2026-09-05T15:25:39Z
to run `branch-cleanup`, and routed the PR to the platform merge queue. The session
then restarted mid-merge.

On re-entry at 15:43 the recovery found:

```text
The merge mutex was STILL HELD by this plan across the session gap, far past
merge_hold_budget_seconds (3600s), with waiting_count 1 at acquire time — a
live-but-slow holder blocking every other plan's merge, which is exactly the case
that budget bounds. Released it before doing anything else (waiting_count now 0).
```

The step's configured `merge_hold_budget_seconds` was 3600. Nothing enforced it.
The lock was released only because a human-initiated session restart happened to
route back through recovery logic that thought to check.

## Root cause

`merge_hold_budget_seconds` is a **declared** budget with no reclaim mechanism
behind it. The holder is the only party that can release, and a holder that stops
executing — session reclaimed, context lost, harness cancellation — releases
nothing. The FIFO admission queue then does exactly what it is designed to do and
holds every waiter behind a holder that will never return.

A budget that is only honoured by a cooperative, still-running holder is not a
bound; it is documentation. The failure mode it exists to prevent — "a live-but-slow
holder blocking every other plan's merge" — is precisely the one it did not
prevent, because a *dead* holder is indistinguishable from a slow one from the
waiter's side.

The lock file already carries plan liveness (`manage-locks` is built on a
plan-liveness core), so the information needed to break this is present; nothing
consults it against the budget.

## Proposed action

1. **Make the budget enforceable by a waiter, not only by the holder.** On
   `acquire`, when the current holder's hold age exceeds `merge_hold_budget_seconds`
   AND its plan-liveness check fails, allow the waiter to break the lock and record
   a `reclaimed_from` provenance entry. Liveness plus budget together, so a
   genuinely slow live holder is still respected.
2. **Publish the hold age and the budget on `check`.** A waiter today cannot see
   how long it has been blocked or whether the budget has blown; both are on disk.
3. **Release the merge mutex before yielding a session**, wherever a step can
   detect it is about to end its turn while holding it. The release-and-FIFO-re-enqueue
   contract already exists and already requires full re-validation on resume, so
   holding across a boundary buys nothing.

Point 3 is the cheap half and would have covered this instance; point 1 is the one
that covers a harness cancellation, where nothing gets to run on the way out.

## Impact

One waiting plan was blocked for approximately 18 minutes past a budget that
declared 60 minutes as its ceiling — and would have remained blocked indefinitely
had the session not been restarted. On a machine that routinely runs concurrent
plans (two other plans' worktrees were active during this run), an unreclaimable
merge mutex stalls every one of them.

Releasing it was correct and remained correct independently of the merge outcome:
the hold had blown its budget regardless of whether the PR had merged.
