# references.json affected_files not resynced after outline-phase Q-Gate file-target corrections

## Context

During `plan-marshall:phase-4-plan` for plan `finalize-flow-hardening`, Step 7b reads `manage-references get --field affected_files` as the `--affected-files-count` input to `manage-execution-manifest compose`. The returned list (16 entries) diverged materially from `solution_outline.md`'s per-deliverable `**Affected files:**` blocks (22 distinct targets across the 6 deliverables, after dedup).

The divergence traces to two Q-Gate corrections applied mid-outline (both documented inline in `solution_outline.md`):

- **Q-Gate 7007e8** (provider-path retarget): deliverable 5 originally targeted the non-existent `tools-integration-ci/scripts/{github,gitlab}.py`; the outline retargeted it to the real surface (`ci_base.py`, `github_ops.py`, `_github_pr.py`, `gitlab_ops.py`). `references.json::affected_files` still carries the pre-retarget `ci.py` entry and a differently-named test file (`test_ci_merge_queue.py` instead of the two real files `test_github_merge_queue.py` / `test_gitlab_merge_queue.py`).
- **Q-Gate 6aa487** (test-owner consolidation): the `merge_hold_window` / `merge_hold_budget_seconds` / `use_merge_queue` seed-assertion ownership moved to deliverable 6's `test_config_defaults.py`. `references.json` does not reflect this consolidation either.

`references.json::affected_files` appears to be populated once (likely at phase-2-refine or early phase-3-outline) and never re-synced when phase-3-outline's own Q-Gate loop mutates deliverable file targets afterward.

## Resolution Approach

phase-4-plan's Step 7b explicitly documents reading `affected_files_count` from `manage-references` (not from `solution_outline.md`), so this is not a phase-4-plan defect — it is a phase-3-outline / manage-references synchronization gap. Two candidate fixes for a future plan:

1. **Re-sync on Q-Gate mutation**: whenever phase-3-outline's Q-Gate auto-loop rewrites a deliverable's `**Affected files:**` block, also re-run `manage-references set --field affected_files` (or an equivalent re-derive-from-outline verb) so `references.json` stays the live projection of `solution_outline.md`, not a stale phase-2 snapshot.
2. **Derive at read time**: have `manage-execution-manifest compose`'s Step 7b caller derive `affected_files_count` directly from `solution_outline.md`'s per-deliverable blocks (via `manage-solution-outline list-deliverables`) instead of from `manage-references`, eliminating the second source of truth entirely.

Option 2 is likely the lower-risk fix since it removes a duplicated data surface rather than adding a new sync obligation. Not implemented here — filed as a lesson for a future dedicated fix plan since it is out of scope for `finalize-flow-hardening`'s deliverables.

## Impact Observed

Low in this instance — `--affected-files-count` only feeds the manifest composer's early-terminate / scope-derived decision-matrix threshold checks, and 16 vs 22 did not cross any relevant threshold for this plan's `multi_module` scope. The risk is a plan near a threshold boundary (e.g. `surgical` vs `single_module` cutoffs) making a wrong lane decision on a stale, undercounted `affected_files_count`.

## Recurrence — 2026-07-18 (terminal-title-stale-build-busy)

A more severe variant surfaced during `plan-marshall:phase-4-plan` for plan `terminal-title-stale-build-busy`: `manage-references get --field affected_files` and `manage-references get --field track` both returned `field_not_found` — `references.json` for this plan never had `affected_files` set at all (not stale, entirely absent), and `track` is not a `manage-references` schema field in the first place (the schema table in `manage-references/SKILL.md` lists `branch`, `base_branch`, `issue_url`, `build_system`, `domains`, `affected_files`, `external_docs` — `track` has never been one of them). Step 7b's documented `manage-references get --field track` invocation is therefore not a staleness bug but a standing contract error: the field it asks for cannot exist under the current `manage-references` schema for ANY plan. `track` (`simple`/`complex`) is only ever available as prose in `solution_outline.md`'s header block (read via `manage-solution-outline read`), which is where this phase-4-plan run sourced it as a fallback, logging the deviation via `decision.log`. This confirms Option 2 (derive-at-read-time from `solution_outline.md` / `manage-solution-outline`) is the correct fix, and extends its scope beyond `affected_files_count` to `track` as well — both inputs should be sourced from the solution outline (the actual source of truth for both fields) rather than from `manage-references`, which never captures `track` and does not reliably capture `affected_files`.

Three independent plans hitting the identical `field_not_found` pair is a strong signal the current `manage-references`-sourced contract in Step 7b is not a plan-specific anomaly but a standing defect affecting every plan.

**New and more concerning: the check that should have caught this reported PASS.**
`check-artifact-consistency` emitted `affected_files_exact_match: pass — "Outline
and references agree exactly"` alongside `affected_files_recall: skip — "No
Affected files declared in solution outline"`. Those two results are mutually
inconsistent, and neither compares `references.json` against the **realized
footprint** — the check only ever compares outline-to-references, so a drift that
originates outside the outline (loop-back fixes, finalize-step promotions) is
structurally invisible to it.

This strengthens Option 2 and adds a third requirement: whichever fix lands, the
retrospective's artifact-consistency check must gain a
references-vs-realized-footprint comparison, because deriving `affected_files`
from the solution outline at read time still would not have covered the two
finalize-step-promoted files. A `manage-references reconcile-footprint` verb run
at finalize (diff declared vs live footprint, report added/removed) would catch
all three mutation sources at the point they occur rather than at retrospective.
