# analyze-logs reports build_count 0 against 84 recorded pyproject_build calls

## Context

`analyze-logs` emitted `build_count: 0` for this plan. The same run's script-execution
log carries **84** `pyproject_build` calls totalling 4,122,990 ms — 48% of all script
time in the plan, and the single largest cost line in the run.

The two figures come from the same substrate and disagree completely. The retrospective
that consumed `analyze-logs` had to read the build cost off the script-cost rollup
instead, and did so by hand; the build-minimality facet that `build_count` exists to
feed had no population at all.

A `build_count: 0` is not obviously wrong to a reader. It reads as \"this plan ran no
builds\" — a plausible sentence about a plan — rather than as \"the counter did not match
anything\". That is the same confident-zero shape the epic keeps finding: a well-formed
success carrying a count nobody can distinguish from a real absence.

## Root cause

Not established from the outside. The observable is that the marker `build_count`
matches is not the marker the build calls actually emit for this run. This plan's builds
were **daemon-routed** through the build server rather than executed inline, so the
wrapper's own emission shape differs from the direct-execution shape — that is the most
likely discriminator, and it is testable by counting the same log both ways.

Worth checking against the sibling defect that was already fixed one commit earlier
(`1169fb5b`, finding `34fe2d`): the daemon-routed executed-test count was lost on
exactly the same seam, because the outer consumer re-parsed a log holding the wrapper's
TOON rather than the raw tool output. If `build_count` reads the same log the same way,
it is the same defect in a second consumer.

## Proposed action

Count builds from a marker the daemon-routed path actually emits, and make the counter
state which kind of zero it is: a plan that genuinely ran no build and a counter that
matched nothing must not both render as `build_count: 0`. Pair the count with the
population it was computed over, as the other analyze-logs figures already do.

## Evidence

- `analyze-logs` → `build_count: 0` for this plan
- script-cost rollup, same run → `pyproject_build`, 84 calls, 4,122,990 ms, 48% of script time
- corroborating seam: `1169fb5b` / finding `34fe2d` fixed the identical outer-consumer
  re-parse for the daemon-routed executed-test count
- observed by the retrospective and independently by the orchestrator

## Recurrence — 2026-09-02 (domain-over-provision)

Third observation, and it confirms the daemon-routing hypothesis in the Root cause section.

`analyze-logs` emitted `build_time.build_count: 0` and `total_build_seconds: 0.0`. The same run's `script_cost_rollup` ranks `plan-marshall:build-pyproject:pyproject_build` **first** with **72 calls** and **7,231,000 ms** — **74.3%** of all script time in the plan, and by a wide margin its single largest cost line.

The discriminator is now directly observable. Every build on this plan was daemon-routed: the work log carries paired `build-server submit queued: job_id=… mechanism=daemon_longpoll` / `build-server wait result: … mechanism=daemon_longpoll` lines for each one, plus a `[BUILD-SERVER] resolved build (requested=auto, resolved=routed, …)` line. Not one build executed inline. `build_count: 0` against 72 daemon-routed calls is therefore consistent with the hypothesis that the counter matches only the direct-execution emission shape.

Consequence for this plan's retrospective: the plan-efficiency aspect rendered `total_build_seconds: unavailable` per its own absent-is-not-zero rule, so the confident zero did not propagate — but the build-minimality facet again had no population, for the third plan running.

## Recurrence — 2026-09-03 (plan-150-close-the-namespace-conversion, PR #1383)

Fourth observation — and it **partially refutes the 2026-09-03 recurrence above**, so the
root cause stated in this lesson should not be treated as settled.

That recurrence concluded "daemon-routed builds write no change-ledger row, so the oracle
sees none of it." This run contradicts the no-row half directly: a `manage-change-ledger
query --kind build` returns 99 rows, **27 of them dated 2026-09-02**, and every one of the 27
carries `plan_id: NO_PLAN`. The rows were written. What was dropped is the plan attribution
ON the row, not the row itself. Zero of the 27 name
`plan-150-close-the-namespace-conversion`, whose own `script-execution.log` records 175
`plan-marshall:build-pyproject:pyproject_build` invocations totalling 9,489,980 ms — 71.5% of
all script time the plan spent.

So there are two candidate mechanisms in play and the evidence now separates them: rows may
be missing on some paths, but on this path the rows exist and the attribution is lost at
write time. The plan points at the worktree-vs-main resolution seam — it ran with
`use_worktree: true`, and an older row in the same ledger records
`worktree_resolution_failed` with `manage-status get-worktree-path returned non-success:
error='file_not_found' message='status.json not found'`.

The remedy this adds to the Proposed action above: resolve and stamp the running plan's id at
the ledger **write** site rather than defaulting to `NO_PLAN`, and make an unresolvable plan
id an explicit recorded state. A build row whose plan could not be determined must say so, so
a downstream `build_count: 0` can be told apart from "this plan's builds were mis-filed" —
the same which-kind-of-zero discipline this lesson already asks of the counter, applied one
layer earlier.

Folded here by the orchestrator (`test-quality` epic) from inbox message
`plan-150-close-the-namespace-conversion-001.md` rather than raised as a new lesson.

## Recurrence — 2026-09-04 (domain-glob-seeding, PR #1406)

Fifth observation, and the **first non-zero `build_count`** — which is more informative than
another zero, because it separates the two candidate mechanisms once more.

`analyze-logs` reported `build_time: {build_count: 1, suspect_count: 1, error: 1,
total_build_seconds: 0.0}`. The same fragment's `script_cost_rollup` ranks
`plan-marshall:build-pyproject:pyproject_build` **first** with **60 calls** and **4,077,340 ms
— 51.2%** of all script time.

So one row was written, and it was written with a duration of `0` and status `error`. This is
not the "no rows at all" shape, and it is not the "rows written under `NO_PLAN`" shape either:
a row exists, it is attributed to this plan, and its measurement is empty. Because
`suspect_count == build_count == 1`, the plan-efficiency aspect had to render
`total_build_seconds` as a **floor of `0.0`** — technically correct per the suspect-zero rule,
and useless: it is a floor of zero over a plan that demonstrably spent about 68 minutes
building.

**The routing condition is inverted from the earlier recurrences, and that is the finding.**
Every prior observation was on a daemon-routed run. On this plan the daemon was unreachable for
its entire duration and **every build fell back to in-process** — `script-execution.log`
records `[BUILD-SERVER] resolved build (requested=auto, resolved=in_process, reason=unreachable,
… mechanism=in_process_fallback)`. So the ledger under-counts on the **direct-execution** path
too, at a rate of 1 row per 60 builds. The daemon-routing hypothesis in the Root cause section
above is therefore, at best, one of several paths that lose rows — it cannot be the whole
explanation, because the non-daemon path loses 59 of 60.

Adds to the Proposed action: whatever writes the ledger row must be on the **common** path,
below the routing choice, so a row is written identically whether the build was daemon-routed,
in-process by choice, or in-process by fallback. A per-mechanism counter published beside
`build_count` would have made all five of these observations self-diagnosing.

## Recurrence — 2026-09-06 (every-test-runs-and-the-suite-does-not-slow-down, PR #1426)

Sixth observation. `analyze-logs` again reported `build_time: {build_count: 0,
total_build_seconds: 0.0, suspect_count: 0}` while the same fragment's `script_cost_rollup`
ranks `pyproject_build` **first** with **89 calls** and **10,100,140 ms — 56.8%** of all
script time. `total_build_seconds` rendered `unavailable` per the absent-is-not-zero rule, so
the confident zero again did not propagate; the build-minimality facet again had no
population.

This run was queried against the ledger directly rather than reasoned about, and the result
separates the two mechanisms **on one plan** — which none of the five earlier observations
did:

- `manage-change-ledger query --kind build` returns 172 rows. **Zero** name this plan.
- **17** rows carry a `2026-09-05` timestamp — the day the plan made most of its 89 build
  calls — and **all 17** carry `plan_id: NO_PLAN`. This is the plan-150 attribution-loss
  shape, reproduced verbatim.
- **Zero** rows carry a `2026-09-06` timestamp, although a whole-tree build demonstrably ran
  that morning: the plan directory holds `build-results/default/python-2026-09-06-081206.log`
  at 7,130,379 bytes, and the three loop-back fix tasks each recorded "Whole-tree verify
  green: compile, lint, test; 24620 tests" that day.

So on a single plan the ledger lost attribution on one day and lost the rows entirely on the
next. Even taking the 17 as this plan's, 17 rows against 89 calls is a 5:1 under-count before
attribution is considered at all — consistent with the `domain-glob-seeding` observation of
1 row per 60 builds, and inconsistent with any explanation resting on a single routing path.

The remedy already stated stands and is reinforced: write the row on the common path below
the routing choice, stamp the resolved plan id at the write site, and make an unresolvable
plan id an explicit recorded state rather than a `NO_PLAN` default. Add one thing: publish
the row count beside the call count the script log already carries, so a 17-against-89
discrepancy is visible from the ledger itself instead of only from a retrospective that
happens to cross-check.

## Recurrence — 2026-09-13, plan implement-plan-165-close-orphan-defects (epic test-quality)

Second measured occurrence, and it **confirms the daemon-routing hypothesis above**.
Build count read `0` again while the same plan's `script-execution.log` recorded **59**
`pyproject_build` calls totalling 5,940,020 ms — 43.6% of all script time and again the
single largest cost line. Every one of the 59 resolved through
`[BUILD-SERVER] resolved build (requested=auto, resolved=routed, mechanism=daemon_longpoll)`,
so the discriminator this lesson named as "testable by counting the same log both ways"
is now observed rather than suspected: the daemon-routed path writes no change-ledger
build row.

The consumer chain is also now known to be honest about it — `plan_efficiency` rendered
`total_build_seconds: unavailable` (not `0`) on the `build_count == 0` rule, so the
absent measurement was not reported as an instant build. The defect is upstream of that
rendering: the oracle sees nothing to render.

Consequence worth stating plainly: build cost is unmeasurable for every plan that takes
the fast path, i.e. increasingly all of them.
