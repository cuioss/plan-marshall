# finalize-step-sync-baseline rebase changes the worktree's discoverable script set but does not regenerate the phase-5-generated per-tree executor, so clean-env dispatch fails script-notation resolution until the executor is regenerated

## Context

During phase-6-finalize of the `detach-long-running-builds` plan, the
`finalize-step-sync-baseline` step rebased the plan worktree onto `origin/main`.
That rebase was **non-noop**: it pulled in PR #864, which introduced a new
`automatic-review` skill (bot-review modularized out of the old inline
`automated-review` step) — i.e. the rebase added a new skill directory with its
own `scripts/`.

Immediately afterward, clean-environment dispatch of `manage-tasks` and
`manage-findings` failed (`test_dispatch_resolves_without_pythonpath` ×2 in
`test_dispatch_clean_env.py`): the executor could not resolve those script
notations without a `PYTHONPATH` fallback.

## The defect

The per-tree executor (`.plan/execute-script.py`) is **derived state** generated
once at the phase-5 move-in (ADR-002: each worktree gets its own generated
executor when the plan directory moves into the worktree). Its embedded
`SCRIPTS = { ... }` notation→path mapping and its `_MARKETPLACE_SCRIPT_DIRS`
discovery roots are a **snapshot of the marketplace script set at generation
time**.

`finalize-step-sync-baseline` rebases the worktree onto `origin/main` at finalize
start, which can change the marketplace surface — add/remove skills, add/remove
`scripts/` directories, change notation→path mappings. But the rebase does **not**
re-derive the worktree executor. So after a non-noop rebase that changes the
discoverable script set, the worktree executor is stale: it lacks the newly-merged
skill's script directory, and clean-env dispatch (no `PYTHONPATH` fallback) fails
script-notation resolution.

Symptom signature:

- `finalize-step-sync-baseline` performed a **non-noop** rebase onto `origin/main`.
- The rebase pulled in a merge that **changed the marketplace script set** (new
  skill `scripts/` dir, renamed/moved script, changed notation mapping).
- A subsequent finalize dispatch (or its clean-env resolution test) fails to
  resolve a `manage-*` script notation without a `PYTHONPATH` fallback.
- Regenerating the worktree executor makes the notation resolvable again.

## Root cause

The post-rebase re-resolution contract (shipped in plan-10 / PR #855, keyed on the
`advances_main_via_rebase` fact) re-resolves **step workflow DOCS** from the rebased
worktree, but it does **not** cover the **executor**. The worktree executor is a
separate piece of phase-5-generated derived state whose script-set snapshot goes
stale the moment the rebase changes the discoverable marketplace scripts, and
nothing in the sync-baseline / re-resolution path re-derives it.

This is the same *family* as:

- `2026-06-23-09-001` — stale **host plugin cache** after a skill rename
  (`skill_load_failure` until post-merge sync). Different object (host cache vs
  per-tree executor), different trigger (plan's own rename vs sync-baseline rebase),
  different failure surface (skill loading vs script-notation dispatch resolution).
- `2026-06-21-01-001` — frozen composed-at-outline **manifest** references a removed
  step's doc (`validate-loadable` fails). Different object (manifest vs executor),
  different remedy (recompose manifest vs regenerate executor).

Following the precedent that 09-001 itself sets (same family, different failure
surface → separate lesson), this is a distinct third derived-state object: the
per-tree executor.

## How to apply

- **Regenerate the worktree executor after a non-noop sync-baseline rebase.** When
  `finalize-step-sync-baseline` (or any mid-finalize step that advances the worktree
  via rebase) performs a rebase that changes the discoverable script set, re-derive
  the worktree executor before the next dispatch:

  ```bash
  python3 .plan/execute-script.py \
    plan-marshall:tools-script-executor:generate_executor generate \
    --marketplace-root {worktree_path}
  ```

- **Treat a clean-env script-notation resolution failure (a `manage-*` notation that
  resolves only with a `PYTHONPATH` fallback) immediately after sync-baseline as the
  signature of this gap** — the executor is stale, not the notation wrong. The fix is
  regenerate-worktree-executor, not restoring a `PYTHONPATH` fallback.

- **Durable remediation:** extend the post-rebase re-resolution contract so it covers
  the executor, not only the step workflow docs — `finalize-step-sync-baseline` (or
  the dispatcher, on observing a non-noop rebase that changed the discoverable script
  set) should regenerate the worktree executor as part of the same re-resolution pass
  that re-resolves the step docs.

## Impact

Without the executor regeneration, any finalize run whose sync-baseline rebase pulls
in a marketplace change to the script set (a common occurrence on an active meta-project
`main`) leaves the worktree executor unable to resolve the newly-merged notations, and
every subsequent clean-env dispatch in that finalize run fails until the executor is
manually regenerated. Scope: meta-project (plan-marshall self-development), where a
finalize rebase routinely changes the in-tree marketplace script set.
