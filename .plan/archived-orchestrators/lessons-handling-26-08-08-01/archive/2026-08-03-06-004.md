# A plan whose deliverable the lifecycle consumes at a phase it has already passed is not self-exercising - say so in the outline

## Observation

`PLAN-CIS-028` reordered the finalize post-run-review steps to run **after** the merge gate. It
could not exercise that fix: its **own execution manifest was composed at outline time with the old
order**, so its own post-run-review steps — including the lessons-capture that reported this — still
ran *before* the merge gate. The fix is correct and landed; it is simply **unobservable from inside
the plan that shipped it**.

This is structural, not an oversight, and it is now the third recorded member of one family:

| Instance | Mechanism | Effect |
|---|---|---|
| `PLAN-10` | plugin cache syncs at step 19, retrospective runs at 17 | the fixed component is not the one that runs |
| `PLAN-CIS-028` | `execution.toon` composed at outline time | the new ordering is never exercised |
| `PLAN-CIS-028` (again) | `.plan/execute-script.py` resolves scripts from the plugin cache, which syncs after the retrospective | the **old code runs and emits a false verdict** |

⛔ The third is the loudest: `check-artifact-consistency.py`'s shipped fix replaces a confident
`Recall 0%` with `inconclusive`, and the plan's own retrospective still emitted
`affected_files_recall, fail, Recall 0%` — because the cached copy that executed predates the merge.
A stale-cache execution is **not a benign delay; it is a wrong answer with a confident
presentation**, and nothing in the report discloses which copy produced it.

⚠ **A trap this lesson exists to prevent, recorded because it was walked into while filing it**: the
mechanism above was briefly judged refuted by reading the step `order:` values on **post-merge
`main`** and finding the retrospective sorted after the cache sync. That reading was of the order the
plan **installed**, not the order it **ran** — which is this lesson's own subject, one level up. ⇒
**When diagnosing a run, read the order from the run's execution manifest or its step log, never from
the tree the run produced.**

## Rule

- When a plan's deliverable modifies **phase-6 step ordering, step selection, step frontmatter, or
  any component the finalize pipeline itself consumes**, state explicitly in the outline that the
  change is **not self-exercising**, and name the observation point: the *next* plan composed after
  the merge.
- **Do not accept the plan's own green finalize as evidence the fix works.** That green was produced
  by the pre-change manifest and, for script-backed steps, by the pre-merge cached code.
- The verification that counts is either **(a)** a derivation-level test over the composed manifest
  — preferred, and what `PLAN-CIS-028` did ship — or **(b)** an explicit post-merge observation on
  the following plan, recorded as owed residue when (a) cannot cover it.
- A step that consumes a component the same plan modified should **record the resolved provenance**
  (cache version vs merged HEAD) in its output, so a reader can tell which copy produced the verdict.

## Impact

`manage-execution-manifest` (snapshot-at-outline semantics), `phase-3-outline` (the
self-exercisability call-out), `phase-6-finalize` step ordering, `plan-retrospective` (every
script-backed aspect), and every future plan touching finalize order, the plugin-cache path, or
executor regeneration.
