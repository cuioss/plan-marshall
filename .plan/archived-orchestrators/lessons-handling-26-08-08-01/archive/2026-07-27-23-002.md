# A wrong [DISPATCH] line is retracted by a second [DISPATCH]-tagged prose line, so the audit population carries a known-false record no detector can filter

`dispatch-logging.md` specifies an emission contract but no retraction contract.
When an emitted line is wrong, the only available repair is to write another
line — which is itself tagged `[DISPATCH]`.

## Observed

During the finalize of `finalize-dispatch-audit-integrity` (PR #1026), the plan
whose entire purpose was to make the `[DISPATCH]` log trustworthy:

```text
20:09:14Z [DISPATCH] target=execution-context-level-3 level=level-3
          role=post-run-review workflow=…/lessons-capture.md
20:09:27Z [DISPATCH] CORRECTION of the immediately preceding line which
          mis-stated the level: target=execution-context-level-4 level=level-4
          role=post-run-review workflow=…/lessons-capture.md
```

Both lines are still in `work.log`. Both carry the `[DISPATCH]` tag.

## Consequences for the detector this plan shipped

1. **Over-count.** A tag-filtered count reports 12 dispatches for a finalize that
   performed 11.
2. **Wrong value on first match.** A consumer resolving `lessons-capture` to its
   dispatched level reads `level-3`. The actual envelope was `level-4`.
3. **No filter is possible.** "CORRECTION of the immediately preceding line" is
   free prose. There is no field, no tag variant, and no id linking the retraction
   to its target, so a structured consumer cannot drop either line.

The acceptance evidence for the plan's own D1 was a `[DISPATCH]` line count. That
count was reported as 10 and is defensible at the timestamp it was taken, but the
same log ends the phase carrying a record known to be false.

## Root cause

The `level` field is transcribed by the model from a value the resolver already
computed. Any hand-transcribed field can diverge from its source; this one did,
within the same run that fused the emit to the spawn.

## Guidance

- **Emit the line from the component that owns the value.** Have the level
  resolver return the formatted `[DISPATCH]` line, not a value for the caller to
  re-type into a message string. The fused emit-to-spawn fix removed the
  *omission* failure mode and left the *transcription* failure mode untouched.
- **An append-only audit log needs a retraction shape, not a retraction
  convention.** A structured `retracts=<hash_id>` field on the superseding line —
  or a distinct tag — lets a detector reconstruct the true population. Prose
  beside the record is invisible to every consumer that is not a human reading
  sequentially.
- **This is the third instance of the same archetype in one run.** Finding
  `59dcbe`'s cross-reference to a nonexistent finding id was corrected only in
  `decision.log`; `adr-propose`'s `lane=off` manifest presence was flagged only in
  `decision.log`. In all three cases the wrong record still stands and the
  correction lives somewhere a consumer will not look. When you catch yourself
  writing a correction *next to* a record, correct the record.
