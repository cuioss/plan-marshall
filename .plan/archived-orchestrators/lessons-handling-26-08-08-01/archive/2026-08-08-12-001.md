# A pytest COLLECTION ERROR reports failed=0 and build_status=SUCCESS through the parse verb, so an entire un-executed test file reads as green — only exit_code and the raw log dissent

## Observed

During phase-5-execute of `absent-names-two-states-with-opposite-remedies` (TASK-005), a
`module-tests plan-marshall` run produced this apparent state:

| Surface | Reported |
|---------|----------|
| Wrapper TOON `tests:` block | `passed: 15068`, **`failed: 0`**, `skipped: 2` |
| `pyproject_build parse --format json` | **`build_status: "SUCCESS"`**, `total_issues: 0`, `tests_failed: 0` |
| `pyproject_build parse --failures-detail` | `total_failures: 0`, `root_causes: 0` |
| Wrapper TOON `status` / `exit_code` | **`error` / `1`** |
| Raw pytest log, final line | `15068 passed, 2 skipped, **1 error** in 219.25s` |

A newly-added test file — `test/plan-marshall/tools-integration-ci/test_not_triggered_passthrough.py`
— had a `SyntaxError` (prose accidentally left outside its module docstring, tripping on a U+2014
em-dash). pytest could not COLLECT it, so **every test in that file silently did not run**, and the
one surface that named the problem was `short test summary info: ERROR <path>`.

Three of the four structured surfaces called this green. `build_status: "SUCCESS"` is the most
misleading of them: it is emitted while a whole file's worth of assertions never executed.

## Root cause

pytest distinguishes three outcomes, and the wrapper's summary models only two:

- **failure** — a test ran and its assertion failed (`failed: N`).
- **error** — a test or file never ran (collection error, fixture error, import error).
- **pass/skip**.

The `tests:` block carries `passed` / `failed` / `skipped` and **no `errors` key**, so a collection
error is invisible in it. The `parse` verb's `build_status` derivation likewise keys off failure
markers, so it reports `SUCCESS`. The **only** honest signals are the process `exit_code` (pytest
exits 1 on an error even with zero failures) and the raw log's `short test summary info` block.

This is a strictly worse shape than the already-documented "build wrapper exits 0 on failure"
problem, because it is *silent in the opposite direction*: there is no failing test to notice, and the
number that looks like coverage (15068 passed) actually **went up** relative to earlier runs while
coverage went DOWN.

## Why the usual defences did not catch it

- **"Read the TOON `status`/`errors[]`, not the exit code"** — followed, and it still misled: `status`
  was `error` but `errors[]` said *"Build failed but no structured errors were parsed"*, i.e. the
  wrapper knew something failed and could not say what.
- **Test-count comparison** — actively misleading. The count rose (15031 → 15068) because other new
  tests in the same task DID run. A rising count is not evidence that the file you just wrote ran.
- **`--failures-detail`** — returns `total_failures: 0`, because there is no failure to detail.

## Remedy

1. **Trust `exit_code != 0` over every green field.** When the wrapper reports
   `status: error` with *"no structured errors were parsed"*, the correct next action is to read the
   raw log's tail for `short test summary info` — NOT to re-parse, and NOT to conclude the run was
   fine because `failed: 0`.
2. **Run the module_testing diff-assertion guard — it is the countermeasure for exactly this.**
   `assert_test_identifiers run --identifiers-file … --log …` compares the identifiers the task WROTE
   against the log. On the broken run it would have reported every identifier in the un-collected file
   as `missing`; after the fix it reported `passed: true, found_count: 50, missing_count: 0`. This is
   the guard's whole reason for existing ("a structural guardrail against silently-skipped tests") and
   this incident is its canonical trigger. Do not skip it because the suite "looks green".
3. **Tool-layer fix (we own the wrapper): surface the error count.** Add `errors: N` to the parsed
   `tests:` block and make `build_status` resolve to `FAILURE` when `errors > 0`, so a collection
   error cannot present as `SUCCESS`. Pair it with a test whose fixture is a file that fails to
   collect, asserting the parse reports non-SUCCESS — the population being "outcomes pytest can
   report", not just pass/fail.
