# Chain-tail predicate tests plan-global dependents, not deliverable completion

# Chain-tail predicate tests plan-global dependents, not deliverable completion

## Context

`phase-5-execute` Step 10 introduces itself as firing "at the **per-deliverable chain-tail point** — the moment all tasks for the just-completed deliverable are done", and Step 10a states that the phase-5 envelope is "the SOLE owner of every per-deliverable commit". The predicate it actually specifies is a different question:

> **Chain-tail predicate**: Does any other pending/in-progress task have `depends_on` pointing to the just-completed task?
> - **YES** → a downstream task still needs to run → this is NOT the chain tail → skip both the commit and the focused build.

On this plan, deliverables 1 through 5 each carried exactly one task, and deliverable 6 declared `depends: "1, 2, 3, 4, 5"`. So at the moment each of TASK-1..5 completed — which is precisely when its deliverable was done — TASK-6 was pending and depended on it, the predicate answered YES, and both the commit and the focused build were skipped. Deliverable 7 (`depends: "6"`) and deliverable 8 (`depends: "7"`) chain the same way. The predicate was false at every real per-deliverable boundary in the plan.

No per-deliverable commit fired. All eight deliverables were instead settled by the orchestrator's boundary-settlement path at the `5-execute → 6-finalize` transition — the path Step 10a explicitly designates "the RECOVERY for that refusal, not the norm".

## Root cause

The predicate asks "does anything depend on ME?", which is a question about the plan's terminal task. The prose asks "is MY DELIVERABLE finished?", which is a question about the deliverable's own task set. The two coincide only when no later deliverable depends on an earlier one — that is, only on a plan whose deliverables are fully independent. Any `depends:` edge between deliverables, which is the ordinary way to express a survey-then-audit-then-repair structure, makes the predicate false at every boundary except the plan's last.

The YES-branch gloss is where the substitution hides: "a downstream task still needs to run → this is NOT the chain tail" silently changes the subject from *this deliverable's* chain tail to *the plan's*.

## Proposed action

Scope the predicate to the deliverable. Replace the plan-global reverse-dependency test with:

> Does any other pending/in-progress task **carrying the same `deliverable` index** remain?

That is the question the surrounding prose already asks, it is computable from the same `manage-tasks` data the current test reads, and it is unaffected by cross-deliverable `depends_on` edges. Where a downstream deliverable's dependency must still gate the *focused build*, gate the build on it separately — the commit obligation is owner-independent per Step 10a's own argument, and the build already skips when no buildable module is present.

## Impact

Three losses, all silent. Per-deliverable commits collapse into one settlement pass, so the commit granularity the design promises is not delivered and a bisect over a multi-deliverable plan cannot land between deliverables. The focused per-deliverable build never runs, so a defect introduced in deliverable 1 is not caught until the end-of-phase sweep. And the recovery path runs on every structured plan, which means the `worktree_dirty_at_boundary` refusal it exists to answer is the normal case rather than the exception — a recovery that always fires stops being a signal.

Fix tasks make it worse: TASK-9 through TASK-12 were appended under deliverable 7 after TASK-8 had already completed, so even the plan-terminal reading of the predicate was invalidated retroactively.

## Evidence

- `manage-tasks list`: 12 tasks; deliverables 1-5 carry exactly one task each; TASK-9..12 appended under deliverable 7 after TASK-8 completed
- `solution_outline.md` deliverable metadata: deliverable 6 `depends: "1, 2, 3, 4, 5"`, deliverable 7 `depends: "6"`, deliverable 8 `depends: "7"`
- `phase-5-execute/SKILL.md` Step 10 — the predicate text and its YES-branch gloss
- `phase-5-execute/SKILL.md` Step 10a — "the RECOVERY for that refusal, not the norm", describing the path that in fact settled all eight deliverables
