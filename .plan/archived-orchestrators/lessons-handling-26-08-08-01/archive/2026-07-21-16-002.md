# Deliverables mutating the same symbols need an explicit dependency edge — one outline pass shipped a missing D1<->D3 edge, a misclassified touched-skill, an undercounted touched-skill list, and an under-scoped count-prose criterion

A solution outline whose deliverables mutate a shared symbol set within the
same source file must declare the resulting dependency edge explicitly, or the
Q-Gate is the only backstop — and one outline pass in this plan (PR #964, the
terminal-title-refresh-cadence run) shipped four distinct completeness gaps in
a single Design-notes authoring pass, all raised and resolved in-run via an
operator-directed corrective outline pass.

## What happened

The outline for `terminal-title-refresh-cadence` split the fix across three
deliverables touching `claude_runtime.py`. Deliverable 1 (D1) and Deliverable 3
(D3) both mutated the same two symbols — `_DISPLAY_RENDER_ENTRIES` and
`_install_terminal_title_hooks` — yet D1 declared `depends: none`. D1's own
success criterion ("eight rows total") was an anchor that was only true in the
window BEFORE D3 deleted a row from `_DISPLAY_RENDER_ENTRIES`; once D3 landed,
D1's criterion as originally worded no longer matched the post-D3 state.
Sequencing D1 before D3 without an explicit edge meant nothing enforced that
D1's criterion be re-checked (or reworded) against D3's mutation.

Three further completeness gaps surfaced in the same Q-Gate pass:

- A deliverable's Design notes classified only ONE of the two skills it
  actually touched.
- A deliverable's declared touched-skills count undercounted the true count
  (three claimed, four actual).
- A count-prose sweep criterion was under-scoped: it did not require an
  absolute target, only an increment — which mattered here because the
  platform-runtime operation-count prose was ALREADY drifted before this plan
  (two files said 21 while sibling files said 22), so an increment-only
  criterion would have preserved the pre-existing inconsistency instead of
  correcting it.

All five findings (3 error, 2 warning) were raised by the phase-3-outline
Q-Gate and resolved within the same run via a corrective outline pass — no
shipped defect, but a full extra outline iteration was spent recovering from
gaps that a more careful first-pass authoring could have avoided.

## The generalizable rule

When authoring deliverable Design notes for an outline that splits related
work across multiple deliverables touching the SAME file:

1. **Symbol-mutation dependency edges are not optional.** If two deliverables
   both mutate the same symbol (a function, a module-level constant/registry
   like `_DISPLAY_RENDER_ENTRIES`, a hook-installation call), the
   later-mutating deliverable's Design notes MUST declare a `depends:` edge on
   the earlier one — even when the deliverables are conceptually independent
   features. The dependency exists at the SYMBOL level, not the feature level.
2. **A success criterion anchored to a mutable shared symbol's current shape
   (a row count, an entry count, a key list) must be re-verified against every
   LATER deliverable that also mutates that symbol**, or worded to survive the
   later mutation (e.g. "N rows after D3's removal" rather than a bare "N rows
   total" written before D3 exists).
3. **Touched-skills classification and count must be exhaustive**, not
   approximate — walk every file a deliverable's diff touches and classify
   every skill boundary crossed, not just the primary one.
4. **A count-prose sweep criterion must assert an absolute target, not a bare
   increment**, whenever the pre-existing prose corpus might already be
   inconsistent (siblings disagreeing on a count is itself evidence the
   corpus was already drifted) — an increment-only criterion propagates
   existing drift instead of correcting it.

## Why it slipped

Design-notes authoring is a single-pass, per-deliverable narrative exercise;
nothing structurally forces an author to cross-check a deliverable's declared
symbols/dependencies against sibling deliverables' symbol lists in the same
outline. The phase-3-outline Q-Gate caught all five findings, so the pipeline
worked as designed — but the corrective pass cost a full outline iteration
that a pre-Q-Gate self-check (enumerate every symbol each deliverable in the
outline mutates, and diff for overlaps before finalizing `depends:` edges)
would have avoided.

## Impact

Advisory-only cost this run (Q-Gate caught it before phase-4-plan), but the
Q-Gate's success depends on findings being correctly attributable to a
specific deliverable/edge — a missing dependency edge that Q-Gate does NOT
catch (e.g. two deliverables mutating a symbol that isn't itself scanned by
the check) would ship a genuinely broken execution order. Authoring outlines
with an explicit per-deliverable "symbols touched" enumeration, cross-checked
for overlap before finalizing dependency edges, is the durable fix.

## Recurrence — 2026-07-22 (consumer-upgrade-cache-freshness)

Same defect class, but this recurrence shows the corrective rule from this
lesson (declare the `depends:` edge) is NECESSARY but not SUFFICIENT. D1
(fail-closed cache-freshness gate) and D2 (union-keep cache-retention sweep)
both mutate `marshall-steward/scripts/upgrade.py`'s Stage 1/Stage 3
composition for the consumer project kind, and D2 correctly declared
`depends: "1"` — the sequencing edge this lesson prescribes was present from
the first draft. Despite that, the two deliverables' Design notes still
stated CONTRADICTORY facts about the meta-vs-consumer stage matrix: one
deliverable's narrative described the matrix one way, the sibling deliverable
restated an inconsistent version of the same matrix, and the phase-3-outline
Q-Gate flagged the contradiction as an error-severity finding, resolved in
the same corrective pass.

Generalization — new facet: a `depends:` edge fixes ORDERING (deliverable B
runs after deliverable A) but does nothing to force the two deliverables'
PROSE claims about a shared mechanism to agree. When two deliverables in the
same outline each narrate a variant (here: meta project vs consumer project)
of the same underlying structure (a stage matrix, a state machine, a schema),
authoring their Design notes as independent narratives — even with a correct
dependency edge between them — leaves the actual restated facts unchecked
against each other. The corrective step is additional to declaring the edge:
after drafting Design notes for deliverables that share a mutated structure,
diff their prose restatements of that structure against each other (and
against the refine-time-verified ground truth, when one exists) before
finalizing the outline, not just verify the edge exists.

## Recurrence — 2026-07-22 (plan-39-manifest-tier-truthful-stamp)

Third occurrence, and the first one that reproduces rules 3 and 4 of this
lesson's generalizable rule **verbatim, in the same single deliverable** —
which is what promotes those two rules from "observed once" to a confirmed
recurring authoring failure rather than an artifact of the original run.

Both findings landed on D2 of the manifest-execution-tier-stamp outline, and
both were raised by the phase-3-outline Q-Gate and resolved in the same run:

- **Rule 3 recurrence (error, architecture-mismatch).** D2's Design-notes
  block classified only **2 of the 5** skills its own `Affected files` list
  touched. Note the ratio is worse than the original occurrence (1 of 2, and
  3-claimed-vs-4-actual): the miss rate grows with the size of the affected
  set, because the author classifies the skills that are *salient to the
  deliverable's narrative* and never walks the affected-files list back to a
  skill boundary per entry. The declared `Affected files` list was itself
  complete — the defect is purely the un-walked mapping from that list to the
  touched-skills classification.
- **Rule 4 recurrence (warning, scope-criterion under-coverage).** D2's
  success criterion enumerated exactly **2 sites** for an inverted
  "per_task is the safe floor" phrasing it committed to rewriting, but a
  **third live instance** existed at `phase-5-execute/SKILL.md:222` — on the
  *same line* as a clause D2 had already committed to rewriting. This is the
  sharpest available form of the rule-4 failure: the missed site was not in
  some distant file the author could plausibly not have known about, it was
  co-located with text the criterion already named. An enumerated site list
  written from recall — even recall of a file the author is actively editing —
  under-counts.

Generalization — new facet (the mechanical-enumeration rule): rules 3 and 4
both describe an author enumerating a SET (skills touched, sites to sweep) by
recall while narrating, and both recurrences under-count. The durable
corrective is not "be more careful", it is to **derive each declared set
mechanically from its own source of truth before finalizing the deliverable**:

- Touched-skills = walk the deliverable's own `Affected files` list and map
  each entry to its owning skill (`architecture which-module --path P`), then
  dedup. Never author the skill list independently of the file list.
- Sweep-site criteria = run the actual content search for the target phrasing
  and enumerate the hits, then write the criterion against that count. A site
  list that was never produced by a search is an estimate, not a criterion —
  and if the search cannot be run (see the sibling coverage-gap lesson on
  denied search tooling), the criterion must say the set is unverified rather
  than assert a number.

Both facets are cheap pre-Q-Gate self-checks on artifacts the outline already
contains; the cost of skipping them has now been a corrective outline
iteration on three separate plans.
