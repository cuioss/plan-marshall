# First-match selection over an evidence set manufactures the negative verdict the predicate was meant to detect

## Evidence anchor

PR #1477 (plan-pr-046), CodeRabbit finding `45ee84` — Major,
`workflow-integration-github/scripts/github_re_review.py:767`.

## What happened

`_match_bot_comment()` returned the **first** eligible comment, and `await_fresh_review()` then
derived `head_sha_verified` from that one record alone. So when a bot had published several eligible
comments, an earlier comment naming no commit SHA **hid** a later comment naming the current HEAD, and
the envelope published `head_sha_verified: false`.

The consequence is not cosmetic: a spurious `head_sha_verified: false` is what the sibling review arm's
own docstring calls "a manufactured decline — the one failure on this path that blocks a merge". The
selection strategy fabricated the exact negative the predicate exists to detect truthfully.

Note the shape of the escape: a first-match implementation **passes the favourable comment ordering by
accident**, so single-ordering test coverage is green over a broken selector. TASK-013's fix therefore
had to add regression coverage for *both* comment orders.

## The rule

When a boolean verdict is derived from **one record selected out of a set of matching records**, the
selector must prefer a record that can **satisfy** the predicate, not the first record that passes the
eligibility filter. Eligibility and evidential sufficiency are two different tests, and collapsing them
into one `next(...)` makes the verdict depend on arrival order.

Structural form of the bug:

```text
record  = first(r for r in records if eligible(r))     # WRONG when verdict = predicate(record)
verdict = predicate(record)
```

Correct form: select over `eligible(r) and predicate(r)` first, falling back to any eligible record
only to report the negative.

## Test obligation that travels with it

A selector of this shape MUST be covered with **both** orderings of the input set. One ordering is not
a test of a selector — it is one assertion that happens to hold. This is the same "N passing checks of
a pure function is one assertion repeated N times" trap in a different costume.

## Where else to sweep

Any site deriving a verdict from `_match_*` / `find_first` / `next(...)` over a comment, review, check
run, or commit list, where the verdict then gates a merge or a re-review.
