# execution_tier routing generalizes compile/test-compile to an unregistered verify step, breaking compose

## Context

While running `phase-4-plan` for `runnable-slice-keys-on-the-floor-not-the-measurement`, `manage-execution-manifest compose` failed with `status: error, error: unresolvable_step, step_id: "verify:compile"`.

The `execution_tier` Routing pass (`decision-rules.md` § "execution_tier Routing") maps an orchestrator-tier task verification command to a phase-5 step ID: `quality-gate -> verify:quality-gate`, `verify`/`module-tests -> verify:module-tests`, `coverage -> verify:coverage`, and "every other parseable verb generalizing to the bare `verify:{verb}` step". `architecture derive-verification`'s own `build_class -> verification command` table (`resolve-command.md`) legitimately emits two additional build classes for production/test changes: `compile` (production role) and the `test-compile` companion of `module-tests` (test role). Neither `compile` nor `test-compile` has a registered `ext-point-build-verify-step` implementor (`canonical_verify.md` declares only `canonicals: [quality-gate, module-tests, coverage]`), so when either is orchestrator-tier, the routing pass generalizes it to a bare `verify:compile` / `verify:test-compile` step ID that a later structural gate (`unresolvable_step`) then rejects as unresolvable, because no implementor declares that canonical.

This is currently unreachable for Maven/Gradle/npm (300s floor keeps `compile`/`test-compile` per_task), but is reliably triggered for ANY plan-marshall Python-domain implementation or module-testing task authored while `PYTEST_OUTER_FLOOR_SECONDS = 600` still tiers every pyprojectx canonical `orchestrator` — i.e. exactly the pre-fix state this very plan (`runnable-slice-keys-on-the-floor-not-the-measurement`) exists to correct. Phase-4-plan cannot mutate production code to fix `manage-execution-manifest` from inside its own planning pass, so the workaround applied here was to stamp each task's `verification.commands` with only the registered-canonical derived command (`module-tests`), dropping the `compile` / `test-compile` companion rows, matching what both deliverables' own `Verification:` field already stated verbatim.

## Resolution / Recommendation

`manage-execution-manifest`'s `execution_tier` routing generalization ("every other parseable verb generalizing to the bare `verify:{verb}` step") should either:
1. Register `compile` and `test-compile` as additional canonicals on `canonical_verify.md` (or a sibling implementor) so a generalized `verify:compile` / `verify:test-compile` step resolves cleanly, or
2. Recognize that `compile` and `test-compile` are always accompanied by a registered sibling command from the SAME `build_class` group (`compile` has no sibling; `test-compile` always co-occurs with `module-tests`) and either fold the unregistered verb's routing into its sibling's step ID, or drop the unroutable verb from the per-task list without erroring (since the accompanying registered command / phase-level candidate already exercises the same underlying suite).

Until one of these lands, any planner authoring `verification.commands` from `architecture derive-verification`'s raw output for a plan-marshall Python-domain task should drop `compile` / `test-compile` rows and rely on the registered `module-tests` / `quality-gate` / `verify` / `coverage` commands, which is the workaround this plan applied.
