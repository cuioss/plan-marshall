# Counts and lists restated by hand in prose went stale in the same change that altered the set

## What happened

Plan plan-25-integration-test-evidence (PR #408). The same defect class was found five times, by three different checks:

- 0f5e14 (self-review): `doc/development/README.adoc` still said "twenty-six-file descriptor surface" after the plan raised it to twenty-eight.
- 897c9c (self-review): a comment in `benchmarks/pom.xml` said "Both properties ... both goals ... Both stay ordered LAST" after a third execution was added below it.
- 55836d (CodeRabbit review body): `benchmarks/README.adoc` goal counts said twelve declared goals; thirteen are declared, twelve produce a CI result.
- 9cdc1e (CodeRabbit inline): the host-port table in `integration-test-topology.adoc` repeated the suites' port assignments by hand.
- b10ff7 / 223af6 (self-review): "no limit-shaped key lives outside this surface" was false on disk twice, the second time in the sentence written to fix the first.

## What the plan put in place

For the host-port table: the table is a tagged block read at runtime by `OneOffGatewayContainersTest`; it must list exactly the ports the sources declare as `APPLICATION_PORT`, each once, with the assigning class (commit a5c505f4). The triage recorded one rule for both this table and the descriptor inventory: hand-written list plus build-time contract test (decision log 07efbb).

## Rule

- When a change adds or removes a member of a set, search for every restatement of the set's size or membership (number words included: "both", "twelve", "twenty-six") in the same change.
- A list in documentation that mirrors a set defined in code gets a contract test, or is not written as a closed list.
- Do not write absence claims ("no X exists outside Y") in documentation unless a test asserts them. When such a sentence is found false, delete it rather than qualify it.
