# Ranking/scoring selection needs a deterministic tie-break, and gate-trigger state must be cleared when its driving aspect is dropped — two functional-correctness bugs in-house verify missed, only the review bot caught

## Context

In the `routing-v2-recipe-match` plan, the plan's own phase-5 verification
(module-tests + quality-gate + the deliverable verification sweep) passed clean,
yet the CodeRabbit PR review caught **two Major functional-correctness bugs** the
in-house gates missed. Both are reusable defect classes worth recording
independently of the specific recipe-match code.

## Bug A — non-deterministic selection in scoring/ranking code

The recipe auto-route picked the highest-scoring skill, but the tie-break for
**equal scores** was non-deterministic: two recipes with identical blended
scores could be selected in different order across runs, so auto-route could
route the same request to different skills on different invocations.

Unit tests passed because they asserted on the *score*, not on the *selected
identity under a tie*, and the iteration order happened to be stable within a
single test process. The non-determinism only manifests across processes / input
orderings — exactly what a single deterministic-seed test run cannot surface.

**Rule**: any code that *selects one element from many by a score/rank* must
have a **total, deterministic tie-break** (e.g. break ties by a stable
secondary key such as the candidate's id/name), and must have a test that
asserts the *selected identity* under an equal-score tie — not only that the
top score is correct. "Pick the max" is under-specified whenever two maxima can
exist.

## Bug B — gate-trigger state not cleared when its driving aspect is dropped

The plan dropped an aspect from a flow, but the residual `verification_steps`
list for that aspect was left **non-empty**. A downstream gate keys off
"verification_steps is non-empty" to decide whether to re-trigger the quality
gate, so the dropped aspect's stale residue **re-triggered the quality gate**
that should no longer have run.

**Rule**: when a feature/aspect is removed, audit every piece of *state that
other code reads as a trigger condition* and clear it as part of the removal —
a non-empty list, a set flag, or a registered hook left behind after its owner
is dropped becomes a phantom trigger. Removal is not just "stop producing"; it
is "also retract the trigger state you already produced."

## Cross-cutting lesson

The plan's own verification (build + module-tests + scoped quality-gate +
deliverable sweep) is a **structural** gate — it confirms the code compiles,
types check, lints clean, and tests pass. It does **not** reason about
*functional correctness under tie/edge inputs* or about *residual trigger state
after a removal*. Those are precisely the gaps adversarial review bots fill (cf.
the recurring "only the PR bot caught it" lesson cluster). When a change touches
**selection-by-score** or **removes an aspect that other code keyed off of**,
add a targeted positive test for the edge — do not rely on the structural gate
to surface it.

## Recurrence — 2026-06-24 (dynamic-finalize-step-discovery) — Bug C: omitted filter predicate, negative case never tested

A third functional-correctness defect class in the same family, on the
finalize-step frontmatter-discovery plan (PR #775). The plan replaced the
hardcoded finalize-step registry with frontmatter discovery; the discovery seed
was supposed to include only **built-in** steps that are `default_on`. The seed
code omitted the `source == 'built-in'` filter, so **non-built-in `default_on`
steps leaked into the seed**. The plan's own phase-5 verification (module-tests +
quality-gate + deliverable sweep) passed clean; the leak was caught only by the
**external CodeRabbit review** (8 comments surfaced the load-bearing latent
defect).

**Why every in-house gate missed it**: the test fixtures all carried
`source == 'built-in'`, so every step in the test corpus satisfied the (missing)
predicate trivially. With no fixture in the *excluded* class, the omitted filter
produced identical output to a correct filter on the happy-path corpus — a
green-on-the-positive-case result that says nothing about the negative case. This
is the exact shape of `2026-06-21-00-001` ("a test covering only the member where
the names coincide cannot detect the diverging member") generalized to a filter
predicate: a filter's correctness is only observable when the corpus contains at
least one element the filter must EXCLUDE.

**Rule (Bug C)**: when code adds or relies on a filter predicate that selects a
subset (`x for x in xs if pred(x)`), the test corpus MUST contain at least one
element for which `pred` is **false** — otherwise an omitted or wrong predicate is
indistinguishable from the correct one. Assert on the *excluded* set, not only on
the *included* set. A missing-filter bug is a no-signal bug under a
single-class fixture, exactly like a silent-degrade config read: the structural
gate stays green because the wrong code and the right code agree on the
all-positive corpus.

This widens the cross-cutting lesson's "add a targeted positive test for the edge"
guidance with a concrete third trigger: alongside **selection-by-score** (Bug A)
and **removes-an-aspect-other-code-keyed-off (Bug B)**, **introduces-or-depends-on-
a-filter-predicate** (Bug C) is a change shape where the structural gate gives
false confidence and a negative-case test is the only in-house defence. Recorded
here as a recurrence (not a new lesson) because it shares the same component,
the same "in-house verify missed, only the review bot caught a
functional-correctness bug" root cause, and the same cross-cutting corrective rule.
