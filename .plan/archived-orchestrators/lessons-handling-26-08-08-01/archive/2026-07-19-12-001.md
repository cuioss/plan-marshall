# Adding an archived/frozen-store read fallback must be matched by an explicit archived-state guard on every sibling mutation verb and by output-contract reconciliation

A read verb that gains an "archived / frozen store" read fallback opens a
new state — the store location resolves, but the record it points at is
immutable — and every sibling mutation path plus the documented output
contract must be audited for that state in the same change. On PR #937
(the orchestrator `archive` verb), four review-bot findings all traced to
the same omission: the new `archived-orchestrators/` read fallback
(`get_log_path(allow_archived=...)`, and the extended `status` / `resume` /
on-query store scan) was added, but the write-side and the docs were not
brought into agreement with the frozen state.

## Recurrence signature

Four independent defects, one root cause. All in-house gates were green;
only the PR bot caught every one:

1. **Read fallback leaks into a write.** `cmd_orchestrator_metadata`
   accepted `--get` and `--set` together. The shared fetch fell back to an
   archived read and then entered the write branch, mutating the *active*
   orchestrator tree for an archived-only epic instead of refusing. Fix:
   an explicit `--get`/`--set` mutual-exclusion guard that rejects before
   resolving status or entering either branch.
2. **Strict active-path write defeats the idempotent repeat.** The archive
   workflow's Step 3 issued a strict active-path `manage-logging --store
   orchestrator` write after the tree had already moved, returning
   `file_not_found` and never reaching the `orchestrator archive`
   idempotent `already_archived: true` path. Fix: detect the
   already-archived result and branch before the strict active-path log
   write.
3. **Read-only workflow continues into writes.** `resume.md` documented
   archived resume as read-only, yet the workflow fell through into file /
   status / log writes the archived-store contract forbids. Fix: an
   explicit archived/closed early-return that reports the frozen record and
   STOPs before the mutating steps, with the sibling standard
   (`orchestration-model.md`) stating the read-only guarantee.
4. **Output contract drifts from the implementation.** The workflow doc
   documented `archived_to` as a relative `archived-orchestrators/{slug}`
   value and omitted `display_detail`, while `cmd_archive` returns
   `archived_to = str(dest)` (the absolute main-anchored path). Fix:
   reconcile the doc to the schema the code actually returns (locked in by
   the tests).

## Rule

When you add an archived / frozen / read-only-store read fallback to any
read verb, in the same change:

- **Guard every mutation-capable sibling verb and workflow** with an
  explicit archived-state check (mutual-exclusion on get/set, early-return
  / refusal on write) so a read fallback can never flow into a write
  against the active tree. The read path resolving from the frozen store is
  the load-bearing new behavior — the write paths are where it silently
  goes wrong.
- **Keep the documented idempotent-repeat path reachable**: a strict
  active-path write placed before the idempotent branch defeats the
  documented "safe to re-run" contract once the tree has moved.
- **Reconcile every output-contract doc to the schema the code actually
  returns** (field names, absolute-vs-relative path form, presence of
  `display_detail`) — tests pin the real schema, so a paraphrased doc
  contract is drift the PR bot will flag.

## Impact

The whole class is invisible to in-house gates (quality-gate, module-tests,
plugin-doctor) because each verb passes in isolation; only cross-verb /
doc-vs-code review surfaces the missed frozen-state handling. Treat the
introduction of any read-only-store fallback as a whole-surface sweep of
its sibling mutation verbs and output contracts, not a single-verb edit.
