# manage-adr scan omits the duplicate population from its success payload, so a duplicate-ADR gate cannot pass on its own evidence

## What happened

A pre-merge gate in API Sheriff PR #350 had to decide whether `doc/adr/` carries duplicate ADR numbers.
`manage-adr scan`'s SUCCESS payload omits `duplicate_count`, `duplicate_numbers` and `duplicate_paths`
entirely, so the gate had no field to read a verdict from. `origin/main` did in fact carry two ADR-0053
files at that moment (one from PR #346, one renamed into place by PR #348), so the gate's subject was
real and the gate still could not see it. It was waived by operator decision.

## Why it matters

A gate whose evidence field does not exist cannot pass on its own evidence — it can only be waived or
blindly trusted. Both outcomes are worse than no gate: a waiver normalises skipping it, and a blind pass
reports a duplicate-free corpus that was never checked. The duplicate this gate existed to catch reached
`main` and is still there.

## Suggested corrective rule

`manage-adr scan` must publish the duplicate population in its success payload — a count, the colliding
numbers, and the paths per number — so an absent duplicate reads as a MEASURED zero rather than as a
missing field. Per ADR-019's own rule, a checked-and-clean result and an unobservable one must be
distinguishable.
