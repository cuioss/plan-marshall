# A placeholder-bearing constraint-bounded doc string must be length-checked against the placeholder's worst-case expansion, not its literal form

A documented string literal that carries a `{placeholder}` and is governed by
a length/char-class constraint declared in its own document must be validated
against the placeholder's *worst-case substituted form*, not its literal
authored form. The literal reads as compliant; the constraint is only violated
once the placeholder is expanded to its real runtime value.

## Recurrence signature

This plan inserted a `mark-step-done` call into phase-6-finalize SKILL.md item
7a whose `--display-detail` string was authored as:

```
"proceeded unreviewed per operator (head {head_sha})"
```

That literal is 51 characters and reads as well under the document's own
≤80-char `display_detail` limit (SKILL.md line ~229). But `{head_sha}`
expands to a 40-character git SHA at runtime, so the materialized string is
`38 + 40 + 1 = 81` characters — one over the documented ceiling. Every
in-house gate passed (plugin-doctor scoped quality-gate, pre-submission
self-review, the outline-review Q-Gate); only the PR review bot (Gemini, PR
#750) did the substitution arithmetic and flagged the overflow. The fix
shortened the prefix to `"proceeded unreviewed (head {head_sha})"` —
`38 + 40 + 1 = 79`, under the limit.

## Defect class

This is the placeholder-expansion-length blind spot, distinct from the
already-covered "advertised-form help string" and "same-document ordinal
reference" self-review candidate classes:

- The deterministic `ext-self-review-plan-marshall` surface enumerates many
  candidate shapes (regexes, user-facing strings, advertised-form help
  strings, same-document ordinals), but none of them *expand a `{placeholder}`
  to its worst-case real value and re-measure the result against a
  same-document length/char-class constraint*.
- The constraint and the violating literal live in the **same document**, so
  there is no producer/consumer drift to detect — the literal simply lies to
  a static reader because the binding length cost is hidden inside the
  placeholder.

## Corrective rule (do X, not Y)

When authoring or reviewing a documented string literal that (a) contains a
`{placeholder}` AND (b) is governed by a length or character-class constraint
stated in the same document:

1. Identify the placeholder's worst-case substituted value. For known
   fixed-width tokens this is exact: a git SHA is 40 chars, a short SHA is 7,
   an ISO-8601 UTC timestamp is 20, a `phase-N-name` token its longest member,
   etc.
2. Substitute the worst case and re-measure the materialized string against
   the declared constraint (char count for a length limit; the char set for
   an ASCII/charset limit).
3. Author the literal so the *expanded* form satisfies the constraint — budget
   the fixed-width placeholder cost against the ceiling up front, leaving the
   prose prefix only the remaining characters.

Do NOT eyeball the literal's authored length and assume compliance — the
placeholder hides the binding cost, and the literal-vs-expanded gap is exactly
where the overflow lives.

## Why in-house gates miss it

The same "all in-house gates clean, only the PR bot caught it" family as
lessons 2026-06-21-21-001, 2026-06-22-11-001, and 2026-06-21-12-001/002: a
defect whose detection requires a small computation (here, substitute-and-
measure) that no deterministic candidate-surfacing rule performs. The general
mitigation is to add the worst-case-expansion length check to the
constraint-bounded-placeholder-string candidate surface so the arithmetic runs
in-house rather than relying on the PR reviewer to do it.
