# A doc-authored /plan-marshall hand-off command string must be validated against Action Resolution's actual parameter surface -- an omitted task= silently resolves to action=list

## The defect

This plan (D3/D4 in `orchestration-model.md`/`orchestrate.md`/`decompose.md`)
authored an emit contract for the orchestrator's proactive hand-off: the
standing next-step suggestion the orchestrator emits at the end of a landing
analysis. One authored form of that emitted command string was:

```
/plan-marshall Execute the staged plan spec at {path}
```

This carries no `task=` parameter. Per the `/plan-marshall` command's own
Action Resolution rules, a command string with no recognizable `task=`
argument resolves to rule 6 — the fallback — which is `action=list`, NOT
"execute the plan at this path." The doc authored a command string intended to
trigger execution, but the string itself, read through the target command's
actual parameter surface, does something else entirely.

Caught by pre-submission self-review, not by phase-3-outline or the Q-Gate —
neither of those surfaces re-parses an authored command string against the
target command's real argument grammar; they check the surrounding prose and
structure, not the string's own routability.

## The generalizable rule

**When a doc authors a COMMAND STRING meant to be handed to a slash-command or
CLI entry point, that string must be validated against the target's actual
parameter/argument surface before it ships** — not just proofread as prose.
Authoring an emit contract is not the same activity as authoring narrative
text: the string has an executable meaning determined by the target's parser
(here, `/plan-marshall`'s Action Resolution rule table), and an author who
knows the *intended* effect can still produce a string whose *actual* parse*
differs, because the intended meaning lives in the author's head while the
parser only sees the literal tokens.

## Where this recurs

Any doc that emits a ready-to-run command for another agent/process to
consume — an orchestrator's "next" suggestion, a plan-spec hand-off pointer, a
finalize step's remediation instruction — carries this same risk whenever the
command targets a multi-mode entry point (one whose resolved action depends on
which flags/positional tokens are present, not just which subcommand is
named). The fix is procedural: after authoring such a string, trace it through
the target's actual resolution rules (or, better, construct it from a template
the target's own contract doc defines) rather than trusting that "it reads
like an execute command" is the same as "it resolves to execute."
