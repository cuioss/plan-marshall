# Pre-merge re-fetch double-files an in-place-edited bot summary as a new pending finding

A review bot edits its summary comment in place on each push. The pre-merge barrier re-fetch keys the comment on (`comment_id`, `edit_term`) — the identity triple (`bot_kind`, `comment_id`, `edit_term`) in `github_pr.py:897` — so a new edit term files a second pending pr-comment finding even when the verdict did not change ("no issues") and the first copy was already resolved `accepted`. The duplicate blocked the merge until hand-resolved.

## Solution

When a re-fetched comment shares a `comment_id` with an already-resolved finding, carry the prior resolution forward if the bot's verdict did not change. At minimum, auto-accept an edited issue_comment summary from a configured review bot that reports no issues, rather than filing it as a fresh pending finding.

## Impact

Any review bot with one edited-per-push summary re-blocks the merge gate after every push — pure friction that also trains operators to skim pr-comment findings.
