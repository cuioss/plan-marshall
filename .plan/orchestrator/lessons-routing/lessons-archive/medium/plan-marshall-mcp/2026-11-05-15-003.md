# PR stays mergeable while finalize re-runs its pre-merge reviews after a rebase

## What happened

Plan `question-loop-run-follow-up-measurement` resumed finalize on 2026-11-05. The branch had been rebased (head
8b9fb22), and finalize was running its pre-merge reviews again: a functional review delta round and then a full
closing round. While that was in progress, PR #114 was merged from the operator account (61daf53, about 15:15Z). The
required checks were green and nothing on the PR showed that a review was still running.

The closing functional review then reported a blocking finding: the run command named `pm.experiment.harnesses` where
the code reads `pm.experiment.hosts`. Because the PR had already merged, the fix had to go forward in PR #118. The
other pre-merge steps (code-review, pre-push-quality-gate, ci-verify, automatic-review, sonar-roundtrip) were not run
again for the rebased head. The decision log records this (WARNING 373cd4).

## Improvement

While finalize is re-running review verdicts after a rebase, the PR should show that it is not ready, so that a merge
outside the plan cannot get ahead of the reviews. Options:

- Convert the PR to draft, or add a blocking label or status, when the re-review loop starts. Restore it only when the
  merge authorization for the current HEAD is recorded.
- At finalize re-entry, check whether the PR was merged during the review loop, as branch-cleanup did here. Report the
  steps that were skipped as an explicit gap, not as done.

Until that exists: the operator should not merge a PR while its plan's finalize is between a rebase and its review
closure, even under a standing merge authorisation.
