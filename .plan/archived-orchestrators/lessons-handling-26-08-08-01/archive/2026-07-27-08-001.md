# Self-review must enumerate every relational case a new guard/scanner/boundary-check's own condition implies, not only the case that motivated it

## Covered portion — do not re-derive

The original narrow finding recorded here — self-review had no lens for a newly-added
guard's own *key-derivation* function collapsing two distinct, documented-as-reachable
inputs onto the same identity key (prefix-collision / naming-convention-collision) — is
now covered by the `predicate-over-parsed-structure` (scan-versus-anchor) candidate list
in `pm-plugin-development:ext-self-review-plan-marshall`, decided and regression-tested
against the original #1013 worked example. See
`marketplace/bundles/pm-plugin-development/skills/ext-self-review-plan-marshall/standards/unreachable-guard-detection.md`
for the full decision record, the rejected alternative framings, and the discriminator for
when this class of check can and cannot see a defect.

## Weaker, related evidence — still open (same originating plan, folded in rather than filed separately)

The plan's own regression test for the fix
(`test_all_legs_agree_all_marked`) asserted only that the three
version-selection legs agreed with each other, never that the agreed-upon
value was the *correct* one. A test shaped this way cannot fail in the
direction that matters most for a resolver-agreement bug: all three legs
regressing to the same wrong answer together still passes. This is the same
underlying gap as the guard-vacuity gap above — verifying *consistency*
without verifying *correctness against the documented ground truth* — just
manifesting in the test suite instead of in production code. Any future
"eliminate a disagreement between N legs" fix should pin at least one
assertion against the independently-known-correct value, not only
cross-leg equality. No self-review lens covers this yet.

## Recurrence — 2026-07-28 (orchestrator-inbox-pickup) — still open

A second, structurally distinct instance of the same evasion pattern, this
time surviving the reviewer's own EXPLICIT scrutiny rather than a blind spot
in the checklist. Plan `orchestrator-inbox-pickup` used a `_section()` helper
(extracts the body under a markdown heading) that stopped scanning only at a
heading of the SAME level as its target — so a target `###` section, followed
later by a `####` sub-heading and then a `##` sibling section, ran all the way
to end-of-file instead of stopping at the `##` boundary.

During self-review, this exact function was inspected and explicitly reasoned
about: the reviewer verified the `####`-nesting case (a deeper heading does not
terminate the section) and concluded the guard was correct. The `##`-boundary
case — a shallower sibling heading terminating the section early — was never
checked, and that is exactly the case that was wrong. The finding was caught
by an external reviewer, not by the self-review pass that had already looked
directly at this code.

**This is a different shape from the covered portion above.** It is a
**boundary-scanning** function with no key-derivation/identity at all: a loop
that terminates on a match condition (`heading level == target level`) is
vacuous for every input where the correct termination condition is broader
(`heading level <= target level`) — and an examiner who tests only the
motivating asymmetric case (deeper nesting) and calls the guard cleared has
not tested the function, only confirmed the one case that prompted the
inspection. The `predicate-over-parsed-structure` detector that covers the
key-derivation case above is scoped to identity-key derivation and does not
fire on this boundary-comparison shape.

## Rule — still open

For ANY newly-added or newly-modified guard, scanner, or boundary-check
function — not only key-derivation/classification functions — self-review
must enumerate the FULL set of relational cases the function's own condition
implies (e.g., for a level/threshold comparison: less-than, equal-to, AND
greater-than against the target, not just the one direction the originating
bug involved) before clearing it. Explicitly having examined and reasoned
about a function is not evidence it was tested against every direction of its
own comparison — "I looked at this and traced one case" and "I verified every
case this function's logic distinguishes" are different claims, and
self-review must make the latter one before returning CLEAN. No detector for
this broader class exists yet.
