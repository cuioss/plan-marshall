# scope_creep_check is structurally dead: plan_creation_sha has a consumer but no producer

The scope-creep guard could not run on any of the three fix tasks in plan
`remove-suspicious-path-blocklist`. It returned `could_not_look` / `no_baseline_sha` every
time, because `references.json` carries no `plan_creation_sha`.

This is not a per-plan gap. The field has a documented consumer and **no producer
anywhere in the bundle**, so the guard is dead for every plan.

## The evidence

`references.json` for this plan:

```text
['branch', 'base_branch', 'scope_estimate', 'domains', 'track',
 'affected_files', 'read_intent_files']
```

No `plan_creation_sha`. A bundle-wide search for the field finds exactly two sites, both
of them readers:

```text
phase-5-execute/scripts/scope_creep_check.py:205   base_sha = refs.get('plan_creation_sha')
phase-5-execute/SKILL.md:576                       (prose describing the read)
```

Nothing in `phase-1-init`, `manage-references`, or any other skill ever writes it.
`manage-references` has a generic `set` verb that *could* write it, but no workflow step
calls it with that key.

## Why this is dangerous rather than merely useless

`scope_creep_check.py` handles the missing baseline gracefully — it returns a
"no diff was computed" shape rather than crashing. That graceful degradation is what hides
the failure: the guard reports an **absent measurement**, and an absent measurement reads
at a glance like a clean one. Every plan for the lifetime of this defect has run with
scope-creep detection silently switched off while appearing to have it.

This is the same failure shape the marketplace's own store-resolution work exists to
abolish: a zero that does not say which kind of zero it is. `list-stalled` distinguishes
`plans_root_state: present` + `scanned_plan_count: 0` from `plans_root_state: missing`;
`manage-findings` distinguishes `findings_store_state: missing` from `plan_absent`. The
scope-creep guard has the same problem and has not had the same treatment applied.

## Rules

1. **A field with a consumer and no producer is a broken feature, not a missing nicety.**
   When adding a reader for a persisted field, add the writer in the same change, or the
   guard ships permanently disabled. A grep for the field name returning only readers is
   the detection signal.
2. **An absent measurement must never be reported in the same shape as a clean one.** A
   guard that cannot look should say so in a form the caller has to branch on — the
   discriminator pattern already established across `manage-findings` and
   `manage-lessons`. `could_not_look` exists in the return; what is missing is any caller
   treating it as different from a pass.
3. **When a guard has never fired in any plan, suspect the guard before concluding the
   codebase is clean.** Zero scope-creep detections across a whole corpus is a claim about
   the detector at least as much as a claim about the plans.

## Fix direction

The natural producer is `phase-1-init`, at the point the plan's branch is created: record
`git rev-parse HEAD` into `references.plan_creation_sha` via
`manage-references set`. Any plan created before that fix keeps returning the absent
measurement, so the caller-side branch in rule 2 is needed regardless.

## Recurrence — 2026-09-08, epic `quality-report-remediation`

**Third independent observation, and still not self-correcting.** Plan `plan-06-forwarded-trust-model` (PR #214, `6e1a19c`) recorded `no_baseline_sha` on all 20 of its tasks. Scope was verified by hand instead. Three plans in one epic, no mitigation applied between any of them. Verbatim report follows.


On every single task of this plan, `scope_creep_check` returned
`could_not_look` / `no_baseline_sha`: the plan's `references.json` carried no
`plan_creation_sha`, so the guard had no baseline to diff the worktree against and
declined to answer. Scope was verified by hand for the whole run instead.

The reporting behaviour is correct — an absent measurement was reported as absent,
never as a pass — but the outcome is that a guard which exists specifically to catch
unnoticed scope drift ran zero times across an entire plan, in a run that (per the
sibling lessons) *did* contain two scope breaches. The guard was structurally unable
to see the exact class of defect it exists for.

The general shape: **a guard whose precondition is populated at plan-creation time,
and which degrades to `could_not_look` when that precondition is missing, can be
inert for 100% of a run without a single error surfacing.** Nothing aggregates
`could_not_look` across tasks, so N consecutive non-answers read as N benign lines
rather than as one loud "this control is switched off".

## Solution

- Capture `plan_creation_sha` into `references.json` at plan creation (phase 1), and
  treat its absence at first use as a plan-setup defect to repair, not merely a
  reason the check abstains.
- When a guard cannot look, allow a backfill: resolve the baseline from the plan's
  first commit / branch merge-base rather than abstaining, so a missing field
  degrades to a slightly weaker baseline instead of to no baseline.
- Aggregate `could_not_look` outcomes across a phase and escalate once the count of
  consecutive non-answers hits a threshold (or simply reaches the end of the phase
  with zero answers). A control that never answered should end the phase with a
  visible warning, not silence.

## Impact

Applies to any precondition-dependent check that degrades to a non-answer. The
failure mode is total silent disablement — the worst kind, because the run looks
exactly like a run where the check passed every time.
