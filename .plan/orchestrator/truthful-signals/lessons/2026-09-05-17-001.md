# declared_set_closure structurally excludes profile=verification tasks from its projection population

## Context

Deliverable 1 of plan `one-format-several-implementations-that-disagree` is a "gate" deliverable
authored with a single `verification` profile (correctly — it performs pure investigation/census
work, not production code changes). It also declares a write target under `mutation_scope`
(`work/toon-emitter-census.toon`, the census artifact the task must produce).

Running `manage-tasks qgate-mechanical-checks` flagged a `declared_set_closure` (`projection`) gap:
"deliverable 1 declares 'work/toon-emitter-census.toon' as a write but no task targets it" — even
after the task's step 2 was explicitly corrected to target that exact path with `write-new` intent.

## Root Cause

`_qgate_closure.py::check_declared_set_closure` skips every task whose `profile == "verification"`
before building the `tasks_by_deliverable` population (`if (task.get('profile') or '').strip() ==
_VERIFICATION_PROFILE: continue`). A verification-profile task's steps are therefore **never**
examined by the projection closure, regardless of what those steps target. A deliverable that is
(a) legitimately single-profile `verification` and (b) also declares a real write in
`mutation_scope` (the common shape for a census/gate/investigation deliverable that must persist an
artifact) will **always** trip this finding, and no task-side fix can silence it — the check cannot
see any verification-profile task's steps by construction.

## Resolution Approach

Do not try to "fix" this by adding steps to the verification task (it will not be recognized) or by
removing the artifact path from the deliverable's declaration (that would misrepresent real,
load-bearing behavior). Instead:

1. Still add the write step to the verification task for traceability/step-tracking (it drives
   `current_step` progression and documents intent even though the closure check cannot see it).
2. Disposition the resulting `declared_set_closure` finding as `taken_into_account` with a detail
   naming the checker's verification-profile carve-out explicitly, so the disposition is legible to
   a later reader rather than looking like an unaddressed gap.
3. Do NOT re-run `qgate-mechanical-checks` after resolving — a re-run reopens the finding to
   `pending` again (a known separate defect: re-running qgate checks reverts accepted findings), so
   confirming the resolution by re-running the check is self-defeating.

## Generalization

Any future plan that authors a `verification`-profile gate/census/investigation deliverable which
also writes a `work/` (or other) artifact via `mutation_scope` will hit this exact finding. This is
a structural property of the mechanical checker, not a planning mistake — recognize the shape early
and apply the same `taken_into_account` disposition rather than iterating on task steps.
