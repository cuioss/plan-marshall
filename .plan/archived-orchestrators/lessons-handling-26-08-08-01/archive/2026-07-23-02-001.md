# A telemetry field promised in a documented command-return contract must be populated in the return dict, not only routed to a side-effect record sink

When a doc's output contract promises a field in a command's **returned**
value, the implementation must place that field in the returned dict/TOON.
Routing the value only into a side-effect sink (a logging/telemetry record,
a metric emit) does NOT satisfy a *return* contract — the consumer that reads
the command result still cannot see it.

## Context

PLAN-42 (`waiting-standard-usage-observability`, PR #988) added observability
for the waiting-standard mechanism selection. It:

- added `record_wait_mechanism()` (a telemetry side-effect sink in
  `tools-integration-ci/scripts/ci_base.py`), and
- updated `plan-marshall/workflow/await-long-running.md` to document that
  `cmd_ci_wait` returns a `mechanism` field in its result TOON so the
  orchestrator can reconcile which mechanism actually ran.

Both `cmd_ci_wait` implementations
(`workflow-integration-github/scripts/_github_ci.py`,
`workflow-integration-gitlab/scripts/gitlab_ops.py`) computed `mechanism` and
passed it to `record_wait_mechanism()` — but returned their completion and
deadline dicts **without** `mechanism`. The documented *return* contract was
therefore satisfied only by the *side-effect* path; a consumer reading the
command result got nothing. The telemetry contract test
(`test_ci_wait_mechanism_record.py`) compounded it by covering only 2 of the 3
mechanisms (`watch_tail`, `poll_fallback`) and omitting `seed_only`.

## Root cause

Two mechanically-identical implementations (GitHub + GitLab) each diverged the
same way, and the divergence was invisible to every in-house gate:

- No unit/contract test asserted the returned dict carried `mechanism`, so
  quality-gate + module-tests stayed green.
- The doc was authored alongside the code in the same plan, so the
  documented-but-unimplemented return field looked internally consistent.
- The value existed (it reached the record sink), which masks the gap from a
  casual read — "the field is computed" is not "the field is returned".

Only the CodeRabbit PR bot caught it (finding `f48bfa`), fixed in-run by
TASK-006 (return-field) + TASK-007 (seed_only contract test). This is the
recurring "in-house gates green, only the PR bot caught it" slipped-then-caught
class, specialized to a return-vs-side-effect contract split.

## Corrective action

When a plan adds a telemetry/observability field:

1. If a doc's contract says the field is **returned**, add it to *every*
   return path of *every* handler (success AND deadline/error payloads), not
   only to the record sink.
2. Add a contract test that asserts the field is present in the returned value
   — one case **per enumerated value** of the field (here: one per mechanism,
   `watch_tail` / `poll_fallback` / `seed_only`), so a telemetry path cannot
   regress unnoticed.
3. When two parallel implementations share a contract (GitHub + GitLab
   `cmd_ci_wait`), apply the change and the assertion to both — a mechanical
   twin is exactly where a one-sided fix hides.
4. Distinguish "computed / logged" from "returned" during self-review: a field
   flowing into a side-effect sink does not discharge a *return*-shaped
   contract clause.

## Impact

Affects any command whose documented output contract names a field the
consumer reads back from the result (not the logs). The failure is silent
under in-house gates because no test asserts the return shape and the value is
present in a side channel. The fix is cheap; the detection gap is the
expensive part — close it with a per-value return-contract test.
