# argument-naming enforcement is opt-in: a script absent from the Canonical Forms table escapes CANONICAL_FORMS_DRIFT entirely, so manage-change-ledger ships a Rule-5-forbidden 'query' read verb

At 6-finalize a call to `manage-change-ledger read --kind build --limit 3` was rejected
with `exit_code: 2` — the script's verb set is `{worktree-sha, append, classify-outcome,
query}`, so the collection read is spelled `query`, not `read`/`list`. The agent-side half
of that rejection is already covered by lesson `2026-07-15-18-001`. This lesson records the
**script-side** half, which is a real defect we own and which no in-house gate can currently
see.

## The script violates a rule the standard states explicitly

`persona-plan-marshall-agent/standards/argument-naming.md` § "Rule 5 — List-verb
canonicalization" is unambiguous:

> Canonical verb: `list` … Domain-qualified verbs (`tasks-by-domain`, `tasks-by-profile`) and
> operation-specific synonyms (**`query` for a collection read**) are drift — rename them to
> `list` plus a filter flag.

`manage-change-ledger query` is exactly that shape — a collection read whose filter dimensions
are already expressed as flags:

```text
usage: manage-change-ledger.py query [-h] [--kind {build,change,job}] [--exit-code EXIT_CODE]
```

It is the literal example the rule forbids, already carrying the `list`-plus-filter-flags
structure the rule prescribes. Only the verb name is wrong.

## Why no gate caught it — the enforcement surface is opt-in

`argument-naming.md` § Enforcement lists four `ARGUMENT_NAMING_*` plugin-doctor rules. Map each
against this defect:

| Rule | What it scans | Would it catch `query`? |
|---|---|---|
| `ARGUMENT_NAMING_NOTATION_INVALID` | 3-part notations in docs vs the executor `SCRIPTS` mapping | No — the notation is valid |
| `ARGUMENT_NAMING_SUBCOMMAND_UNKNOWN` | subcommands named in **docs** vs the script's `subparsers.choices` | No — it validates docs against argparse, and argparse genuinely declares `query`. A doc that correctly documents a badly-named verb passes |
| `ARGUMENT_NAMING_FLAG_UNKNOWN` | `--flag` tokens in docs vs the matched subparser | No — flag-level only |
| `ARGUMENT_NAMING_CANONICAL_FORMS_DRIFT` | "cross-checks **every row above** against the live argparse declarations" | **No — `manage-change-ledger` has no row.** The check is table-driven, so a script that was never added to the Canonical Forms table is never cross-checked |

The gap is structural, not a bug in any one rule: three of the four rules validate **documentation
against the script**, and the fourth validates **the script against the table**. Nothing validates
**the script against the rules** (Rule 2 `read`/`get`/`exists`, Rule 5 `list`). A script therefore
escapes Rule 2 and Rule 5 entirely by the simple act of never being added to the table — and being
absent from the table is the default state for every new script.

This is the same archetype as the recurring vacuous-guard family (cf. `2026-07-23-01-002`, a gate
that `continue`s past items lacking the very key it enforces): the guard's population is defined by
the same artifact whose absence is the defect.

## Cost, measured

Rule 5's own rationale predicts this cost precisely: "an LLM pattern-matching from one `manage-*`
script to another guesses the verb … producing silent `exit_code: 2` argparse rejections." The
corpus quantification in `2026-07-15-18-001` measured **237 argparse rejections across 52 notations
in 38 of 115 plans**. Every un-tabled script is an unbounded contributor to that number, and the
naming drift that produces the wrong guess is invisible to CI.

## Corrective action (do X, not Y)

- **Do** rename `manage-change-ledger query` to `list`, keeping `--kind` / `--exit-code` as the
  filter flags Rule 5 prescribes. Accept `query` as an additive argparse alias if any call site
  still spells it, exactly as Rule 2 does for the three accepted read-verb aliases.
- **Do** add a `manage-change-ledger` block to the Canonical Forms table in the same change, so
  `ARGUMENT_NAMING_CANONICAL_FORMS_DRIFT` starts covering it.
- **Do** close the structural gap rather than only this instance: make the table's coverage
  **mandatory rather than opt-in** — a new rule (e.g. `ARGUMENT_NAMING_CANONICAL_FORMS_INCOMPLETE`)
  that enumerates every script under `skills/manage-*/scripts/` and fails when one has no Canonical
  Forms rows, and/or a rule that checks each declared subcommand name directly against the Rule 2 /
  Rule 5 verb vocabulary. Without this, the next un-tabled script repeats the defect silently.
- **Do not** treat the rejection as purely an agent-improvisation instance and file it only against
  `2026-07-15-18-001`. When the agent's guess matches the documented house convention and the
  *script* is the party that diverged, the fix belongs at the tool layer.

## Scope check before acting

`query` may not be the only Rule-2/Rule-5 divergence hiding in un-tabled scripts. Enumerate the
subcommand names of every `manage-*` script and diff them against the Rule 2 (`read`/`get`/`exists`)
and Rule 5 (`list`) vocabulary before deciding the size of the rename; the same sweep produces the
missing table rows as a by-product.
