# Doc prose for an async-wait config knob mis-described the completion condition (acknowledged vs submitted); all in-house gates clean, only the PR bot caught it

## Context

The plan `seed-re-review-timeout-config-knobs` (PR #748) was a documentation- and
config-seeding-only change: it added two re-review-timeout knobs
(`re_review_await_timeout_seconds: 600`, `re_review_on_timeout: ask`) to the
`default:automated-review` step block of `.plan/marshal.json` across three repos, and
documented all five re-review knobs (the two new + three pre-existing PR #742 knobs)
in `doc/user/configuration.adoc` and
`marketplace/bundles/plan-marshall/skills/manage-config/standards/data-model.md`.

No code shipped — the author was documenting, second-hand, the behavior of the
re-review mechanism built by PRs #742/#745 (whose live implementation lives in
`workflow-integration-github/scripts/github_re_review.py` and
`phase-6-finalize/standards/automated-review.md`).

## Signature

Two `gemini-code-assist` inline comments on PR #748 (findings `1c1ffe` on
`data-model.md:509` and `7adf65` on `configuration.adoc:216`, both medium-priority)
caught the same defect in both doc sites, caught-and-fixed in-run (slipped, then
caught — the highest-value lesson class):

> The description states the timeout is for the re-review to be "acknowledged by the
> bot". However, according to `github_re_review.py` and `automated-review.md`, the
> system actually polls and waits for a **completed/submitted** review (matching the
> HEAD SHA and post-dating the trigger time), not just an acknowledgement.

The author's prose described the async-wait completion condition with an imprecise
verb — "acknowledged by the bot" — that the implementation does not honor. The matcher
(`await_fresh_review`) waits for a review whose `submittedAt` post-dates the trigger
AND whose reviewed commit SHA matches HEAD: a *submitted/completed* review, not a mere
acknowledgement. The fix replaced "acknowledged by the bot" with "submitted by the bot"
in both files (two rows in `data-model.md`, two occurrences in `configuration.adoc`).

## Root cause

When documenting a config knob (or any parameter) that fronts an **asynchronous
wait / poll** behavior, the author paraphrased the completion condition the code
actually waits on with a looser, plausible-sounding verb. "Acknowledged" reads
naturally for a timeout-on-a-bot-interaction knob, but the gate's actual termination
condition is narrower and load-bearing: a *submitted/completed review matching HEAD*.
The doc and the implementation diverged semantically — the prose described a weaker
event (acknowledgement) than the one the code enforces (submission matching HEAD).

This is the **doc-accuracy specialization** of the standing "in-house gates check
structure, not domain correctness" family. The plan passed every in-house gate clean
— `plugin-doctor` quality-gate clean (1 skill gated), pre-submission self-review clean
(0 candidates examined), CI all green — because none of those gates reads documentation
prose against the implementation it describes. Only the adversarial PR bot, which had
the matcher source in view, caught that the documented completion condition was wrong.

This is distinct from the doc-contract-drift family (`2026-06-21-12-003`): that family
is about *coverage* — under-enumerating a subset of the doc sites / config members /
write sites that must change in lock-step. Here NO site was omitted (both doc sites
were correctly in `affected_files` and edited); the defect is the *semantic accuracy
of the description at sites that WERE covered*. Coverage was complete; correctness was
not.

## How to apply

- **Describe the actual completion condition, not a looser paraphrase.** When
  documenting a knob/param that fronts an async wait, poll, retry, or gate, state the
  exact event the code terminates on. For a re-review/await gate that is "a submitted
  review matching HEAD", not "acknowledged"; for a CI wait it is "all required checks
  reach a terminal conclusion", not "CI finishes"; etc. The narrowest accurate verb
  is the right one — a looser verb implies a weaker guarantee than the code provides.

- **When documenting second-hand behavior, read the implementation before writing the
  prose.** A documentation-only plan that describes code it did not write is the
  highest-risk case for this defect — the author has no edit-time feedback from the
  code. Open the matcher/poll function and the owning workflow doc
  (here `github_re_review.py` + `automated-review.md`) and quote the actual
  termination condition rather than inferring it from the knob's name.

- **Treat a clean in-house-gate run on a documentation change as necessary-but-not-
  sufficient when the doc describes behavior.** No in-house gate (plugin-doctor,
  pre-submission self-review, CI) reads doc prose against the implementation it
  describes — that semantic divergence is exactly what the adversarial PR bot reads
  for. Where a doc deliverable's value IS the accuracy of a behavioral description,
  budget for the PR-bot round trip or pre-empt it by cross-checking the prose against
  the source at authoring time.

## Impact

Both occurrences were caught and fixed in-run before merge, so nothing inaccurate
shipped. Had it shipped, every operator reading the `re_review_on_timeout` /
`re_review_await_timeout_seconds` documentation would have formed a wrong mental model
of when the timeout fires — believing a bot acknowledgement satisfies the gate when in
fact only a submitted review matching HEAD does. For a policy knob whose `ask` /
`proceed` / `defer` branches gate whether an *unreviewed* HEAD is merged, an inaccurate
description of the await condition is a meaningful correctness gap in operator-facing
docs.
