# The router-flag placement hint fires only when the flag exists, staying silent on the undeclared case

## Context

`input_validation.py` (surfaced through the executor template and `script-shared`'s
`argparse_surface.py`) emits a corrective note when a router-consumed flag is placed after the
verb. It worked exactly as designed on plan `misconfigured-reviewer-name-reads-missing-review`:

> `21:07:52Z` — `ci.py: error: unrecognized arguments: --plan-id …`
> `note: --plan-id is a top-level flag and belongs BEFORE the subcommand (verb), not after it.
> The flag exists — it is only in the wrong position. Move it ahead of the verb, e.g.
> `… ci --plan-id X pr comments --pr-number 1392`.`

Ten minutes later the caller made the **mirror-image** mistake against a different script:

> `21:17:55Z` — `github_pr.py: error: unrecognized arguments: --plan-id …`

`github_pr` declares no `--plan-id` anywhere — not on the router, not on any subcommand. The
error was bare. No note fired, because the note's precondition is that the flag exists
somewhere in the surface and is merely misplaced.

The `--plan-id` family accounted for **4 of this plan's 26 script failures** across
`ci` (3) and `github_pr` (1), inside a 16-minute window, with the corrective note landing in
the middle of them.

## Root cause

The hint is keyed on "this flag is declared on the router but was found after the verb", so it
covers one of two failure shapes. The other shape — "this flag is not declared on this script
at all" — gets argparse's bare `unrecognized arguments`, and it is the shape that needs the
*louder* message, because the remedy is the opposite one: **drop the flag**, not move it. A
caller who has just been told "the flag exists, move it earlier" and then hits a bare rejection
on a neighbouring script has been primed toward exactly the wrong fix.

`plan-marshall:persona-plan-marshall-agent` § "Never invent script subcommands" already
enumerates five canonical argparse-rejection recurrence signatures, including this family in
both directions. The runtime hint implements one direction of it.

## Proposed action

1. Extend the rejection handler: when an unrecognized flag is **absent from the whole argparse
   surface** of the target script, emit a note saying so and naming the flag set the script
   does declare — the same shape the existing "use a declared flag for X: [...]" path already
   produces for other flags.
2. Distinguish the two notes clearly in wording. The existing one says "the flag exists — it is
   only in the wrong position"; the new one must say the flag does not exist on this script,
   because those prescribe opposite moves.
3. `github_pr` specifically: it takes plan context implicitly and declares no `--plan-id`. If
   that is deliberate, the note should say so; a caller cannot tell an intentional omission
   from an oversight from a bare argparse line.
