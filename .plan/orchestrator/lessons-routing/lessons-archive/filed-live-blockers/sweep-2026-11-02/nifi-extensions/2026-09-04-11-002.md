## What happened

`LogSanitizer`'s `CONTROL_CHARS` pattern used Java's `\p{Cntrl}`. Outside Unicode mode that class matches only the ASCII
range `[\x00-\x1F\x7F]`, so C1 controls — notably U+009B (CSI) — passed through `forLog()` untouched. The class's own
Javadoc claimed complete control-character coverage, and its test corpus contained no C1 case, so both the implementation
and its documentation asserted a guarantee the regex did not provide.

Fix applied: `\p{javaISOControl}` in place of `\p{Cntrl}` (which covers NEL, leaving only U+2028/U+2029 needing the
explicit carve-out), plus a U+009B test case and a corrected Javadoc claim.

## Candidate rule (for orchestrator judgement)

Two reusable observations, both wider than this file:

1. **Regex character-class semantics are a security boundary.** In Java, `\p{Cntrl}` is ASCII-scoped by default and
   `\p{javaISOControl}` is the correct class for "every ISO control character". A sanitizer that names a POSIX class
   without checking its Unicode scope silently under-matches.
2. **A security guarantee stated in Javadoc must have a negative test for its stated boundary.** The Javadoc asserted
   full coverage; the tests exercised only ASCII controls. The claim and its evidence were never reconciled — which is
   the same "closure claim without re-checking the declaring source" failure the agent-behaviour rules name for prose
   enumerations, here appearing in production Javadoc.

Possible dispositions: fold (1) into the Java security standard's input-validation/secure-logging section; fold (2) into
the JUnit/coverage standard as "a documented security boundary needs a test at the boundary, not inside it".

## Why this is cross-plan

Both observations are language-level and codebase-independent: any plan writing or reviewing a character-filtering
sanitizer in Java can reproduce the exact defect.
