= Cloud-run quality analysis: `truthful-signals`
:toc: left
:toclevels: 3
:sectnums:

Analysis of the 47 plans from the `truthful-signals` epic that were exported to
`doc/plans/truthful-signals/` and executed as standalone cloud runs, against the 10 most recent
plans executed locally through the full plan-marshall lifecycle.

[IMPORTANT]
====
**Measured at repository HEAD `5e9c0865d`, 2026-08-22.** Every figure here is point-in-time and
re-derivable from the ingested corpus at `.plan/local/orchestrator/truthful-signals/cloud-runs/`.

This document carries a measurement instant, which the project documentation standard otherwise
forbids. The deviation is deliberate and is the subject of the analysis itself: a comparative
measurement without its instant is exactly the untruthful signal this epic exists to remove. The
gap counts below moved by 90 between the audit that produced them and this analysis.
====

== Scope, populations, and how each number was derived

Three populations. Every count in this report rides with the population it was computed over.

[cols="1,1,4",options="header"]
|===
| Population | n | Derivation

| Cloud plans | 47 | Directories under the ingested `cloud-runs/` tree, each holding `plan.md`, `report-01.md`, `verification.md`, `gaps.md`. 44 original (`030`–`460`, no `400`) plus 3 audit-derived (`500`/`510`/`520`).
| Cloud deliverables | 256 | Distinct `D<n>` rows in each run's `verification.md` deliverable-by-deliverable table.
| Cloud gaps | 308 | `## G<n>` sections in each `gaps.md`, excluding each file's `## Refuted during adversarial review` section.
| Local plans | 10 | Every plan in `.plan/local/archived-plans/` — the complete local archive, not a sample.
| Local deliverables | 46 | `### <n>.` headings under `## Deliverables` in each `solution_outline.md`.
| Local findings | 203 | `qgate` + `pr-comment` entries in each plan's `artifacts/findings/*.jsonl`.
|===

[WARNING]
====
**The two defect counts are not the same measurement and must not be subtracted.**

The cloud gaps were found by an *independent post-hoc audit* (PR #1298) run over plans that had
already merged — 44 verification agents plus 44 adversarial re-review agents, with mutation
testing. The local findings were raised by each plan's *own in-run gates* and resolved before
merge. One measures what escaped; the other measures what was caught.

**No equivalent post-hoc audit has ever been run over the local plans**, so this report cannot
state a local escape rate. That asymmetry is the single largest confound here and is not
resolved by any number below.

== Why so many gaps? The taxonomy answers it

[IMPORTANT]
====
**The gap count is substantially a function of what the verification call ASKED FOR.**

`verification.md` and `gaps.md` were not produced by the plan runs. They come from a separate,
operator-issued verification pass whose brief asks for a *thorough review of all code and
documentation in the repository*, explicitly covering: correctness and edge cases; hidden traps and
false security; whether the security posture fails closed; whether tests are real content tests
rather than coverage tests; whether generators and positive/negative cases are used correctly; and
whether documentation — both Javadoc and AsciiDoc — is sensibly structured and matches the code.

**Read the taxonomy below against that checklist and the correspondence is close to exact.** The
dominant kinds are documentation accuracy, incomplete sweeps, and vacuous tests — which are the
prompt's own headings. A verification call that asked a narrower question would return a smaller
number over the same plans.

⇒ **`308` is the yield of one particular review question, not a lane-quality constant.** Comparing it
to any figure produced by a different question is invalid, and this report does not do so.

⛔ **Two findings are NOT prompt artifacts and survive this caveat intact**, because they are measured
against the plans' own claims rather than against an external checklist:

* the **21.1% deliverable fidelity failure rate** — the plan said it did something and the tree disagreed;
* the **57.1% CodeRabbit resolution rate** — findings an independent reviewer raised and the run never resolved.

Those two carry the verdict. The raw gap count does not.
====

[#_codeRabbit_the_reviewer_signal]
== CodeRabbit: the reviewer signal

Review findings are an independent measurement of plan quality — a reviewer that had to raise a
finding is a defect the plan shipped into review. Measured per PR from `ci pr comments`, counting
inline comments authored by `coderabbitai` that carry a `cr-comment:v1` fingerprint (the marker that
distinguishes an originating finding from CodeRabbit's own auto-generated replies).

[NOTE]
====
**The classifier was validated against an independent measurement.** For PR #1134 it returns 10
findings; the `review-retrospective` step run separately over the same PR reported *10 actionable*
(of 13 raw, 3 meta). The two agree exactly.
====

[cols="4,2,2",options="header"]
|===
| | Cloud lane | Local plan-marshall

| PRs | 47 | 10
| CodeRabbit **reviewed** | 16 (34%) | 6 (60%)
| CodeRabbit **declined** (quota) | 31 | 4
| Findings raised | 84 | 47
| Findings per reviewed PR | 5.2 | 7.8
| Findings **resolved** | 48 (**57.1%**) | 47 (**100%**)
| PRs with findings and **zero** resolved | 6 | 0
|===

=== The resolution rate is the discriminator

**Local plans resolved 47 of 47 CodeRabbit findings — 100%. Cloud plans resolved 48 of 84 — 57.1%.**

6 cloud PRs received CodeRabbit findings and resolved **none of them**: `090`, `130`, `180`, `250`, `300`, `390` — 34 findings left on the table.

This is the cleanest evidence in the report for outcome 1. The local lane has a *findings pipeline*
— `automatic-review` files each comment as a `pr-comment` finding, a unified triage dispositions
every one, and the blocking-finding invariant refuses the phase transition while any actionable
finding is still `pending`. **A local plan structurally cannot merge with an unresolved review
finding.** The cloud lane reads comments and relies on the run to act on them, so 43% simply were
not acted on.

=== Why coverage was low in BOTH lanes — and what that does to the argument

Every decline sampled, in both lanes, carries the identical notice:

[quote]
____
Review limit reached — `@cuioss-oliver`, you've reached your PR review limit, so we couldn't start
this review.
____

This is an **account-level quota**, not a `skip-bot-review` label and not a lane decision. It affects
both lanes: the local lane also lost 4 of 10 PRs to it.

[IMPORTANT]
====
**A second-order effect worth naming.** The cloud lane pushed 47 PRs through review in a short
window. That volume is itself a plausible driver of the quota exhaustion that then degraded review
for *everything* in the same period — including the local plans, 4 of which were declined.

So the reviewer dimension splits in two: **coverage** is environmental and shared (outcome 3), while
**resolution of what the reviewer did find** is entirely a lane property (outcomes 1 and 2). Only
the second explains the gap corpus.
====

== Cost

=== A cloud plan is billed THREE times, not once

Token spend on a cloud-lane plan lands in three separate places, and only the middle one is what
"running a plan" usually means:

[cols="1,3,3",options="header"]
|===
| # | Expenditure | Produces

| 1 | **Authoring** the plan | the `plan.md` staged under `doc/plans/{epic}/` — one `author-cloud-plan` pass
| 2 | **Running** the plan | the branch, the PR, the merge, and `report-01.md`
| 3 | **Verifying** the plan | `verification.md` + `gaps.md` — a separate operator-issued review call
|===

A local plan-marshall plan carries the equivalent of all three *inside one lifecycle*: outline and
plan phases author it, phase-5 executes it, and phase-6's gates plus `plan-retrospective` verify it —
all inside the single `metrics.md` total.

[WARNING]
====
**The 2–4% figure cannot be attributed across these three buckets from this corpus.** No cloud run
published a token figure, so the split between authoring, running and verifying is **unmeasured**. If
2–4% covers only bucket 2, the true cloud cost per plan is higher than this report's headline
comparison implies — possibly materially.

What is certain is directional: the local lane's 1–2% is a *single, fully-measured* number covering
all three functions, while the cloud lane's 2–4% is an *unattributed* number covering at least one of
them.
====


[IMPORTANT]
====
**The cloud lane cannot measure its own cost.** The epic audit's own § Cost section reads
*"Tokens: not available to the agent in this session"*, and no cloud run in this corpus published
a token or billing figure. Every cost number below is therefore the operator's observation, not a
measurement the lane produced.

This is itself a finding: a lane that cannot report its own consumption cannot be cost-optimised,
and cannot be compared on any basis except an external one.
====

[cols="3,2,2",options="header"]
|===
| | Cloud plan | Local plan-marshall plan

| Cost per plan (operator observation) | **2–4%** of weekly limit | **1–2%** of weekly limit
| Measured tokens per plan | not produced | 6,200,361
| Measured billing-weighted per plan | not produced | 93,085,693
| Self-measurement | none | full per-phase breakdown in `metrics.md`
|===

At the operator's figures, the 47 cloud plans in this corpus consumed roughly **94–188% of a
weekly limit** — the equivalent of **47–94 local plans**. What that bought is recorded above:
308 gaps, of which **218 are still open**, and a 21% deliverable fidelity failure rate.

=== What a measured local plan actually costs

`PLAN-TRUTH-074`, finalized during this analysis, was measured end-to-end by its own
`plan-retrospective`:

* **5,432,972 tokens** — and the retrospective labels this a *floor* (`n=5/6` phases), rather than
  publishing it as a total.
* **3.4x its own error anchor** for a `single_module` + `feature` plan (1.6M).
* **`6-finalize` alone was 59.2%** of the spend, against 16.8% for `5-execute`.

The last figure is the one worth carrying: on a local plan, *finalizing* costs three and a half times
what *implementing* costs. The gates are not free, and this report's argument that they are worth it
should be read against that price, not around it.

[NOTE]
====
**The local lane's measurement is not clean either — and it says so.** The same retrospective reported
that the change-ledger recorded **0 build rows while 144 `pyproject_build` calls ran** (62.4% of script
wall time), and that all 25 dispatch-boundary rows carry their four context-load columns unpopulated,
so `billing_weighted_total` is 0 over a population of 0 and the `Billing (cost)` column is empty for
every phase.

That is a real defect, and it is recorded here rather than omitted because it cuts against this
report's own thesis. The distinction that survives it: the local lane **measures, publishes a
population, and flags its own holes**; the cloud lane produces no figure at all. A wrong number with a
declared population is auditable. An absent one is not.
====

== Adjudication of the three candidate explanations

=== 1. plan-marshall shows its benefit — *SUPPORTED, and it is mostly a machinery argument*

The local lane runs gates the cloud lane structurally does not have. Enumerated from the
phase-6-finalize manifest of the local plans in this corpus:

[cols="3,3",options="header"]
|===
| Local gate | Cloud-lane equivalent

| `pre-push-quality-gate` — per-bundle + whole-tree build and tests | conditional `./pw verify`, skipped entirely on a docs-only footprint
| `pre-submission-self-review` — structural sweep over ext-point-derived candidates | none
| `automatic-review` + unified triage + findings pipeline | review bots only, no triage pipeline
| Q-Gate findings captured and blocked at **every** phase boundary | none
| `phase_handshake` invariants incl. blocking-finding gate | none
| `finalize-step-simplify`, `finalize-step-security-audit` | none
| `plan-retrospective` + `review-retrospective` | none
| Per-phase metrics, token and billing accounting | none
|===

The evidence is direct: the local plans surfaced **4.41 defects per deliverable and closed them
before merge**; the cloud plans shipped **1.20 gaps per deliverable that an external audit had to
find afterwards**. The gates are the difference, and the cloud lane declares most of them out of
scope by construction.

[WARNING]
====
**Do not over-claim this.** The comparison is confounded — see the warning in § Scope. No post-hoc
audit has been run over the local plans, so their escape rate is *unknown*, not zero. The honest
claim is: **the local lane demonstrably catches more before merge**, not that it ships fewer bugs.
====

=== 2. `cloud-plan-lane` / `author-cloud-plan` is faulty — *SUPPORTED, with named mechanisms*

Five contract-level defects are evidenced in this corpus, each with a measured consequence:

**(a) The run report is self-assessed.** The same agent that does the work writes the report that
attests to it, with no independent pass. Consequence: **51 of 308 gaps (16.6%) are corrections to
the runs' own reports.** Three reports were internally self-contradictory (`060` and `310` said
`_pending_` on a merged PR; `500` said "PR not yet opened" against PR #1320; `450` denied opening a
PR in five cells while describing it in five others).

**(b) Derived figures are taken before the review cycle closes.** The review cycle widens the diff.
Measured: `520` had two files added by CodeRabbit after its counts were taken, making three separate
report figures one low; `500` omitted a *production* file from its § Collateral for the same reason;
`510` used a floating `origin/main` endpoint three sections after its own § Build gate corrects that
exact defect. The contract does not require a final re-derivation.

**(c) The build gate skips on a docs-only footprint.** `git diff --name-only -- '*.py'` returning
zero files skips the build. Legitimate for the audit's own docs-only diff, but it means a
markdown-only plan ships with **no gate at all** — and 56.8% of this corpus's gaps are prose defects.

**(d) The lane assumes affordances a fresh clone does not have.** Three plans had a GATE deliverable
that could not be opened from a cloud clone — `230/D0` (archived CI manifests), `440/D4` (a real
finalize to measure), `030/D0` (the ruleset API returns `403`). Those three are precisely why `230`
and `440` carry `partially-implemented`. `.plan/` state is git-ignored and therefore absent.

**(e) Nothing governs many agents in one working tree.** The audit run itself hit this: agents
mutation-testing concurrently could snapshot a file another had already mutated and "restore" it to
a corrupted state, and two agents wrote scratch files into the repository. Found and closed
*during* the run; the contract still carries no rule.

=== 3. A general Claude Code issue — *WEAKLY SUPPORTED, and mostly external-service limits*

What is genuinely environmental rather than contractual:

* **Review-bot coverage was degraded on essentially every PR** — 1-of-3 or 2-of-3 throughout.
  `coderabbitai` rate-limited on a rolling window, `sourcery-ai` on a weekly quota and, on large
  diffs, on a hard **150,000 diff-character ceiling** that no wait clears.
* **Squash merges make per-commit claims uncheckable.** Every run report cites pre-squash SHAs that
  resolve to nothing in a clone, so no "seen to fail pre-fix" assertion in this corpus is verifiable.
* **Verification base commits vanish.** Four `verification.md` headers cite base commits absent from
  the clone.

[NOTE]
====
**Cross-lane control: the review *coverage* shortfall is not cloud-specific.** Every CodeRabbit
decline sampled in *both* lanes carries the same account-quota notice, and the local lane lost 4 of
its 10 PRs to it. `PLAN-TRUTH-074`, a local plan finalized during this analysis, recorded 1-of-3
coverage across the whole bot roster — `cuioss-review-bot` and `sourcery-ai` were both unmeasurable.

Coverage is therefore environmental and shared, which **removes it as an explanation for the gap
count**. What is *not* shared is what happens to a finding once raised: local **100%** resolved,
cloud **57.1%**. See xref:_codeRabbit_the_reviewer_signal[the reviewer section].
====

None of these explains the gap count. They explain why *review* was thin, not why the *plans*
shipped incomplete sweeps and vacuous guards.

== Verdict

[IMPORTANT]
====
**Outcomes 1 and 2, jointly — and they are the same finding seen from two sides.**

The cloud lane is not defective in the sense of being broken; it is defective in the sense of being
**thin**. It deliberately gives up the in-run verification machinery that produces plan-marshall's
quality — and then has to buy that verification back as a **separate, separately-billed third call**,
which is where all 308 gaps came from.

The verdict does **not** rest on the raw gap count, which is a function of what that verification call
asked for (see § Why so many gaps). It rests on the two measurements taken against the plans' *own
claims*: a **21.1% deliverable fidelity failure rate** — claimed done, tree disagreed — and a
**57.1% CodeRabbit resolution rate** against the local lane's 100%.

The corpus's own best evidence for this reading is that the three *remediation* plans — which ran in
the same cloud lane — closed 90 gaps and **filed 25 new ones**, two of them `high`. The lane does not
self-correct; it re-introduces its own defect class at each pass.

**The cost picture is worse than the headline.** A cloud plan is billed three times — authoring,
running, verifying — against a local plan's single fully-measured lifecycle total. The 2–4%
observation cannot be attributed across those three, so the real multiple over the local lane's 1–2%
is unknown and is bounded below, not above, by 2x.

**The reviewer signal is the sharpest single discriminator in this report.** Of the CodeRabbit findings
raised against each lane, the local lane resolved **47 of 47 (100%)** and the cloud lane **48 of 84
(57.1%)**, with six cloud PRs resolving *none* of what they were given. That is not a quality-of-work
difference — it is the presence or absence of a findings pipeline. A local plan structurally cannot
merge while an actionable finding is `pending`; a cloud plan can, and 36 findings did.
====

== What the cloud lane is genuinely good at

Recorded so the verdict is not read as "never use it":

* **Breadth under parallelism.** 44 plans executed and then 44 verified plus 44 adversarially
  re-reviewed — 99 agents in one session. No local lane does that.
* **Mechanically-derived figures survive.** In `500`, *every* census figure re-derived exactly
  (152/81/71/69, the 43/18/2/7/1 split, 46/21, 29 rows) while five narrative sections went stale.
  **Derivation held; assertion did not.**
* **The adversarial second pass works.** It refuted 11 gap sets' supporting clauses, corrected
  verdicts in both directions, and caught defects in the *fixes being proposed*.
* **`320` and `520` are genuine successes** — 10 of 10 and 29 of 30 upstream gaps closed, the latter
  verified by execution rather than reading.

== Recommendations

Ordered by measured value.

1. **Do not run implementation plans in the cloud lane without a verification gate.** Reserve it for
   breadth work — audits, sweeps, verification fan-outs — where its parallelism is the point.
2. **Add a mandatory final re-derivation step** after the review cycle closes. This single change
   addresses mechanism (b) and a large share of the 51 report-correction gaps.
3. **Give the lane a blocking findings gate.** This is the highest-value single change: 36 CodeRabbit
   findings were raised and never resolved because nothing refused the merge. The local equivalent is
   the `pending_findings_blocking_count` invariant.
4. **Stop self-assessing the run report**, or stop treating it as evidence. An independent pass over
   the report — not the work — would have caught all three self-contradictory reports.
5. **Make the docs-only build-gate skip explicit as a coverage gap**, not a pass. It should read
   *could not look*, never *clean* — the epic's own namesake rule.
6. **Give the lane a cost measurement.** It currently cannot report its own consumption at all.
7. **Add a concurrent-working-tree rule** to § Step 6: dirty-check before mutating, scratch in
   `$TMPDIR`. The audit hit this and fixed it in-flight; the contract still does not carry it.
8. **Route `.plan/`-dependent gates to a local run.** Three plans failed a gate for this reason; the
   staged `PLAN-TRUTH-097` now carries that constraint explicitly.
