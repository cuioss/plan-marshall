# Profile-standards recipe over an already-compliant codebase degenerates to a near-no-op

When the `refactor-to-profile-standards` recipe is run over a codebase
that is already standards-compliant (typically because a prior OpenRewrite
cleanup or an earlier compliance pass already landed), the per-package
refactoring deliverables degenerate into verified no-ops and the recipe's
net change collapses to noise-level edits. Recognise this shape early and
short-circuit it rather than paying the full per-package plan cost.

## Context

`plan-marshall:recipe-refactor-to-profile-standards` expands into one
deliverable per package, each tasked with bringing that package into
compliance with the configured profile standards. The recipe assumes the
target packages carry real, fixable divergence from the standards.

In the `recipe-refactor-to-profile-standards-2026-06-15-13` run against
`cui-jsf-test-basic`, the codebase had already been brought to compliance
by a prior OpenRewrite cleanup. The recipe still expanded to 15 package
deliverables and executed all of them. The outcome:

- **13 of 15** package deliverables were verified no-ops — the inspection
  confirmed the package already complied, and no edit was produced.
- The entire plan's **net diff was a single typo fix plus a whitespace
  change** — i.e. noise-level, not the substantive refactor the recipe
  exists to perform.

The plan was structurally healthy (it shipped green), but the effort/value
ratio was poor: a full multi-deliverable plan lifecycle produced essentially
nothing because there was nothing to refactor.

## The Pattern

A standards-enforcement recipe carries a hidden precondition: *the target
must actually diverge from the standards.* When that precondition is already
satisfied — because a deterministic tool (OpenRewrite) or an earlier plan
already enforced the same standards — the recipe does not fail, it simply
does redundant work. Every deliverable runs, inspects, confirms compliance,
and records a no-op. The cost is real (plan setup, per-package dispatch,
verification, finalize) while the value is ~zero.

This is distinct from a recipe that finds and fixes a small amount of
divergence: a 2-of-15 hit rate where the 2 hits are real refactors is a
good run. A 0-real-refactor run whose only net change is a typo is the
near-no-op signature.

## Takeaway

Before committing to a full per-package `refactor-to-profile-standards`
expansion, add (or rely on) a cheap pre-flight compliance probe over the
scope:

- If the same standards are already enforced deterministically (e.g. an
  OpenRewrite recipe in the build, or a recent compliance plan), treat the
  manual refactor recipe as **likely redundant** and confirm with the user
  before expanding the full plan — the manual pass duplicates what the
  deterministic tool already guarantees.
- Where a compliance probe is available, gate the recipe's deliverable
  expansion on it: skip packages the probe reports as already-compliant,
  so the recipe only allocates deliverables for packages with real
  divergence, instead of expanding one-per-package and discovering the
  no-ops only after dispatch.

The general rule: a standards-enforcement recipe should detect "the scope
is already compliant" as a first-class early-exit condition, not discover
it deliverable-by-deliverable after a full plan has been built and run.

## Recurrence — 2026-06-16 (recipe-refactor-to-profile-standards-module-testing)

A second run of the same recipe against the **same** `cui-jsf-test-basic`
codebase did NOT degenerate — and that sharpens the applicability boundary
of this lesson. This run targeted the `module_testing` profile over the
`test_packages` source set (the prior near-no-op run targeted production
scope, already flattened by OpenRewrite). The outcome was the opposite of a
no-op: a substantive 44-file, ~937-insertion / ~625-deletion refactor that
migrated legacy test classes to JUnit 5 (replacing `ConfigurableFacesTest` /
`@EnableJsfEnvironment`, adopting parameter resolution, adding `@DisplayName`
and assertion messages). The Gemini PR review confirmed it as a genuine
modernization with no actionable findings.

### Refinement of the rule

The near-no-op signature is NOT a property of the *recipe + codebase* pair —
it is a property of the **scope × profile cell**. The same codebase that is
already-compliant for one profile (production OpenRewrite-enforced standards)
can carry large, real divergence for a *different* profile/scope
(`module_testing` standards over the test tree, which OpenRewrite did not
touch). So the pre-flight compliance probe from the Takeaway must be run
**per scope-cell**, not once per codebase. "We already ran this recipe on
this repo and it was a no-op" is NOT sufficient evidence to short-circuit a
run that targets a different profile or a different source set — re-probe the
specific cell before declaring redundancy.
