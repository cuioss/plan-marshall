# test-integrity reports assertion_removed per file after a class split; make the comparison split-aware

## Problem

Deliverable 5 of plan-22 split the over-budget NonValidatingJwtParserJweTest (823 lines) into three flat sibling classes (369 / 245 / 256 lines; decision log TASK-7, 2026-11-05T12:04:57Z) with the same test methods and rows. The review_support test-integrity check compares assertions per file and reported `assertion_removed` for the original file: 75 assertions were flagged although 111 assertions were relocated into 118 across the three new classes (the difference is the leak-check strengthening of TASK-7). The functional review recorded the resulting weakened-test flag (F7) as blocking, and it could only be closed by a per-head operator override ("accepted by the operator as a false positive; to be closed by override at the final head", 13:53 and 14:36 entries). Every new head needs the override again.

(The 75 / 111 / 118 figures were reported by the finalize orchestrator for this step; the decision log confirms the split, the F7 flag and the per-head override.)

## Solution

Make the comparison split-aware: when a file disappears or shrinks and new files appear in the same change, compare the assertion multiset (or count) of the removed side against the union of the added sibling files, and report `assertion_removed` only for the net loss. A moved-test heuristic keyed on the test method name (the plan prefixed colliding names with a group name) would be enough for the common case.

Until then, a plan that splits a test class should expect the flag, record the relocation counts in the decision log when splitting, and prepare the operator override.

## Impact

False weakened-test findings block finalize and cost an operator interaction at every HEAD advance; they also train reviewers to wave the finding class through, which hides a real weakening.
