# orchestrator inbox detect cannot be called for a plan with no source_id, which is every description-sourced plan

## Problem

`phase-6-finalize` SKILL.md § Step 3 item 4b.a0 resolves the orchestration verdict once per finalize run, and four steps consume it (`default:lessons-capture`, `plan-marshall:plan-retrospective`, `default:finalize-step-preference-emitter`, `default:emit-landing`). The documented procedure is two calls:

```bash
manage-plan-documents request read --plan-id {plan_id} --section source_id
orchestrator inbox detect --source-id "{source_id}"
```

For a **description-sourced** plan the first call returns `status: error, error: section_not_found` — `request.md` has no `source_id` section at all, because `phase-1-init` Step 5.1 writes `--source-id` only for the traceable sources (`lesson`, `issue`, `recipe`) and explicitly omits it for `description`.

The second call then cannot be made. `inbox detect` declares `--source-id` as **required with no `nargs='?'` / `const=''`**, and the generated executor strips empty-string arguments before argparse sees them (`script_args = [a for a in script_args if a]`), so `--source-id ""` arrives as a bare flag and argparse rejects it:

```text
orchestrator inbox detect: error: argument --source-id: expected one argument
```

Exit 2. Observed on plan `pre-push-gate-mutation-coherence`.

## Why it matters

`description` is the **default and most common plan source** — every `/plan-marshall task="..."` invocation produces one. So the documented a0 procedure is unrunnable on the majority of plans, at a step that four consumers depend on.

The failure is loud (exit 2) rather than silent, which is the good case. But the workflow prescribes no handling for it: item 4b.a0 documents the `unrecognised_id` WARNING branch and the three other `detection` tokens, and says nothing about the source_id being **absent**. An orchestrator following it literally is stuck; one improvising may guess a verdict, and guessing `orchestrated: true` would route lesson-shaped output to an epic inbox that does not exist.

The structural answer is unambiguous — an orchestrated plan is by definition one whose `source_id` is an orchestrator plan-spec pointer, so no `source_id` means `orchestrated: false` — but that reasoning currently has to be reconstructed at each call site rather than being what the verb returns.

## Directive

1. **Give `--source-id` `nargs='?'` with `const=''`**, matching the sibling flags elsewhere in the codebase that must survive the executor's empty-argument stripping, and have the verb return `orchestrated: false` with a `detection` token for the absent case. A distinct token (`no_source_id`) is better than reusing `not_orchestrator_pointer`: the latter says a pointer was read and did not match, which is a different observation from no pointer existing.
2. **Or**, if the verb should keep a required argument, amend item 4b.a0 to branch on the `section_not_found` return **before** the detect call, and state the `orchestrated: false` verdict there. This is cheaper but leaves each consumer's correctness resting on prose.
3. Either way, **regression test**: a description-sourced plan must reach a resolved orchestration verdict without an argparse rejection.

## Relationship to the sibling lesson

This is the same archetype as `2026-09-08-22-003` (`review_completeness check --measured-diff-size` rejecting its documented invocation on the common path): a flag that cannot accept the empty value the normal path produces, on a surface the executor strips empties from. Two independent instances in one run suggests the empty-argument contract is under-applied across the script surface generally — a sweep for required-or-non-`nargs` flags whose producers can legitimately emit nothing would be worth more than either point fix.
