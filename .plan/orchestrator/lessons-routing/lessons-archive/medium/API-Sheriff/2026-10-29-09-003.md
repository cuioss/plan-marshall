# Rebasing over a docs split can silently orphan the branch's edits to the moved content: search the new tree for the branch's wording after the rebase

Source: PLAN-V02-50 (#532), candidate lesson 007; extends the finalize-main-drift memory.

## Observation

While the plan was in flight, `main` split `doc/architecture.adoc` into `doc/architecture/` (#533). Rebasing onto it moved the content the branch had edited. A clean or trivially resolved rebase does not show that the branch's edits ended up in the file that now owns the section; an edit can be dropped, or left in a stub.

## Rule

- Before the rebase, check `HEAD..origin/main` for file moves or splits that touch any document the branch edits.
- After the rebase, search the new tree for the branch's new wording and confirm it is in the file that now owns the section. Re-apply it there if it was dropped.
- Re-check `xref:` links and anchors that pointed at the old single file.

## Apply

Every long-running plan whose finalize rebases over a documentation restructure. The orchestrator also applies it when a staged spec names a path a split has since moved (V02-07, V02-48 named `doc/architecture.adoc`).
