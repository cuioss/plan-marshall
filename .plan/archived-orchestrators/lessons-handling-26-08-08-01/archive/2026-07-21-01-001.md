# Analysis/inventory report deliverables ship structural and quantitative claims unverified against the codebase and internally inconsistent across the report set, only PR review bots caught the drift

A whole-project, analysis-only plan (deliverable = a set of written
`doc/analysis/*.md` reports: a redundancy report, a fixture/bootstrapping
inventory, a unification proposal, and a remediation map) passed every
in-house gate and shipped a PR whose report bodies carried five distinct
structural/quantitative inaccuracies. None were caught by the plan's own
verification — all five were surfaced by the PR review bots (CodeRabbit +
gemini-code-assist) after push and fixed in loop-back cycle 1.

The common root cause: report claims were **asserted from the author's
working memory / a single indirect signal, not re-verified against ground
truth**, and the multi-document report set was **not cross-checked for
internal consistency**. An analysis deliverable's value IS its factual
accuracy — an unverified count or an inconsistent path is a defect exactly
as a wrong line of code is.

## The five recurrence instances (all one class)

1. **Wrong count.** The `collect_ignore` prose said "four" smoke tests where
   the actual on-disk set was seven concrete files across four categories
   (`discover_modules` had 2, not 1). The reviewer's own suggested "six" also
   undercounted — proving the number was never derived by counting the real
   files.
2. **Absence inferred, not verified.** A bullet claimed `test/adapters/` was
   absent based solely on `git ls-files` returning no match. That command
   proves only that no *tracked* file matches the pattern, not that the
   directory is absent from the filesystem. Absence must be proven by a
   direct filesystem check, or the claim must be narrowed to "no tracked
   `test/adapters/*` files".
3. **Path prefixes inconsistent / nonexistent.** One report cluster used a
   `test/plan-marshall/` prefix and left one side of a mirror pair with no
   prefix at all, while sibling clusters used fully-qualified on-disk paths.
   The prefix must match the actual on-disk directory layout and be applied
   uniformly across every cluster and both sides of every mirror pair.
4. **Cross-document scope misalignment.** A remediation unit (M4 in the
   unification proposal) named only the JaCoCo coverage locations, but the
   sibling document's Cluster D enumerated additional coverage surfaces
   (`build-npm/test_js_coverage.py`, `extension-api/test_coverage_parse.py`,
   `pm-dev-frontend-cui/coverage`). A claim spanning two report documents
   (proposal ↔ remediation-map) must name the same surface set in both, or
   explicitly scope-limit and enumerate the excluded surfaces.
5. **Symbol name not the exported one.** A migration contract referenced a
   private `_HAPPY` table where the actual exported symbol other sections
   already cited is `HAPPY_VALUES`. Any symbol named in a migration/consumer
   contract must be the real exported identifier, verified against the
   source, not a plausible private-looking name.

## The rule — do X instead of Y

When authoring an analysis/inventory/design report whose deliverable is the
written document itself, run a **ground-truth + cross-document consistency
self-verification pass before submission**:

- **Every count** — re-derive it by enumerating the real files/symbols at
  authoring time; never carry a number from memory or from a single earlier
  draft.
- **Every absence assertion** — prove it with a direct filesystem check
  (or narrow the wording to exactly what the evidence supports, e.g. "no
  tracked X" for a `git ls-files`-based observation).
- **Every path** — match the actual on-disk directory layout and apply the
  prefix uniformly across all clusters and both sides of every mirror pair.
- **Every symbol name** — cite the exported identifier verified against the
  source, not a private-looking guess.
- **Every claim that spans more than one report document** — the surface set,
  scope, and naming must agree across all documents, or the narrower document
  must explicitly enumerate what it excludes.

Treat the report set as a mutually-consistent whole and grep the reports for
each pinned number, path prefix, and symbol name to confirm one canonical
value is used everywhere. In-house gates (plugin-doctor, quality-gate) do not
read analysis-report prose for factual accuracy, so this self-verification
pass is the only pre-push safety net — the PR review bots are the backstop,
not the gate.

## Recurrence — 2026-07-21 (refactor-test-suite-pytest-standards) — broadens scope to downstream consumption

Second observation, and a scope broadening: the SAME defect class recurred,
but this time the inaccuracy was caught by a **downstream consumer**, not
the author's own self-review, and not a PR bot. This plan consumed
`.plan/local/orchestrator/test-suite-quality/analysis/test-suite-remediation-map.md`
(part of the same report set this lesson already covers) as its authoritative
remediation work list. Four of its factual claims were refuted at execute
time by on-disk verification:

1. **RU-4** claimed four build backends share an identical coverage fixture;
   `build-pyproject`'s is Cobertura (coverage.py) while gradle/maven's are
   JaCoCo — a 4-way dedup was structurally impossible.
2. **RU-7** claimed a `discover_modules` integration tier covers assertions
   the unit tier duplicates; that tier contains ZERO pytest test functions
   and depends on external non-repo clones.
3. **RU-1** undercounted the `_pm_input_validation_fixtures` importer set
   (map/outline said 14, disk said 18 live imports across 20 modules
   including one cross-bundle) — the miss would have broken pytest
   COLLECTION, not just tests.
4. **RU-2/D3** called seven files "near-identical mirrors"; one carried four
   unique behavioural assertions that a blind delete would have silently
   dropped.

**Scope broadening — the rule now covers consumption, not only authoring.**
The original rule above ("run a ground-truth + cross-document consistency
self-verification pass before submission") only binds the *author* at
submission time. This recurrence proves the same unverified-claim defect
survives an author's self-review and a PR-bot review and still reaches a
**later, independent plan** that treats the document as ground truth. The
rule is broadened:

- **Every factual claim in an analysis/remediation-map artifact is a
  HYPOTHESIS, not ground truth — for every consumer, not only the author.**
  A downstream plan that uses an analysis document as its work list MUST
  re-derive each claim (counts, fixture-identity claims, "near-identical"
  assertions, dependency/coverage claims) against the live filesystem before
  acting on it, exactly as the authoring self-verification pass does.
- A consolidation/deletion/dedup deliverable in particular must re-derive its
  own file set and its own equivalence claims rather than trusting a count or
  a "these are duplicates" assertion carried over from the source document.
- Catching this class of defect at execute time (a stopped delete/dedup) is
  strictly cheaper than catching it at PR-review time (a shipped-then-fixed
  defect) — treat every consumed analysis artifact as pre-review, regardless
  of whether it already went through its own review cycle.
