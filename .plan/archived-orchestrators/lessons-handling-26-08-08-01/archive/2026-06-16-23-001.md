# JVM build-error classifier tags compilation errors / test failures as [deprecation_warning] — mis-categorization in the shared build pattern set

# JVM build-error classifier tags compilation errors / test failures as [deprecation_warning] — mis-categorization in the shared build pattern set

**Context:** nifi-extensions archived-plan audit (2026-06-16). The quality-chain
check surfaced build findings whose titles carry an obviously-wrong category tag.

## Symptom

Across multiple nifi plans, `artifacts/findings/build-error.jsonl` entries tag
genuine **compilation errors** and **test failures** with the `[deprecation_warning]`
category, e.g.:

- `Build error [deprecation_warning]: COMPILATION ERROR :`
- `Build error [deprecation_warning]: Symbol: Klasse TestJwtIssuerConfigService`
  (a "cannot find symbol" compilation error — not a deprecation)
- `Build error [deprecation_warning]: Ort: Klasse RestApiGatewayProcessorTest`

A missing-symbol compilation error is not a deprecation. The category is mis-assigned.

## Where it lives

The JVM build-output category patterns are in the shared classifier:

- `marketplace/bundles/plan-marshall/skills/script-shared/scripts/build/_build_jvm_patterns.py`
  (the `deprecation_warning` pattern list — line ~52).
- `marketplace/bundles/plan-marshall/skills/script-shared/scripts/build/_warnings_classify.py`
  (`ALWAYS_FIXABLE_TYPES` lists `compilation_error` and `deprecation_warning` as
  SEPARATE types — so the distinction exists and the classifier should preserve it).

So the categories `compilation_error` and `deprecation_warning` are both defined;
the bug is that compilation-error / test-failure lines are being bucketed under
`deprecation_warning`.

## Open question to confirm at fix time

Determine the exact mechanism before fixing — three candidates:
1. **Pattern over-match** — a `deprecation_warning` regex matches lines it should not
   (most likely; fix the pattern specificity / ordering so `compilation_error` wins).
2. **Coarse build-level default** — the classifier stamps every line of a failed
   build with one dominant/first category rather than classifying per line.
3. **`-Werror` / fail-on-warning** — a deprecation warning was *promoted* to a
   compilation error by the build config; if so the tag is arguably a root-cause
   pointer, NOT a mis-classification (the missing-symbol example above argues
   against this being the whole story).

## How to apply

- Treat a build finding whose `[category]` contradicts its body text (e.g.
  `[deprecation_warning]` on `COMPILATION ERROR` / `cannot find symbol` /
  `Tests run: … Failures:`) as the signature.
- Fix in the shared JVM pattern set (`_build_jvm_patterns.py` / `_warnings_classify.py`)
  with a per-line classification test; add a unit test asserting a `COMPILATION
  ERROR` line classifies as `compilation_error`, not `deprecation_warning`.
