# Recording a known fail-open as a documented gap instead of closing it hands the close to the reviewer — twice

## Evidence anchor

- Self-review Q-Gate finding `f0869c` (6-finalize, round 8): the marker-shape sweep claimed
  "population-derived over the live registry" while its SHAPE axis was a hardcoded triple.
- CodeRabbit `0f4db5` (PR #1477 round 1, Minor): the BOT axis of the same sweep is a hardcoded tuple.
- CodeRabbit `d9e200` (PR #1477 round 2, Minor): the SHAPE axis — explicitly "the residual half of a
  finding already accepted earlier in this PR".

## What happened

The plan's own pre-submission self-review found the defect first (`f0869c`) and chose the *documenting*
remedy: the docstring was rewritten to "name the fail-open blind spot for an off-vocabulary key and
name the accessor that closing it would require". The gap was recorded as known and left open.

CodeRabbit then billed two separate review rounds for the same gap — round 1 for the bot axis, round 2
for the shape axis that the first fix left behind. Round 2's own words: the bot population was derived
in TASK-012, "but the `(issue_comment, review_body, inline)` tuple still bounds WHAT is swept, so a
marker declared on any other publish shape passes unseen and the test title claim quietly stops holding".

Both CodeRabbit comments cite this project's OWN corpus learning back at it: *"For every set-guarding
detector, derive the population from its authoritative source at build time or runtime."*

## The rule

When a self-review finds that a guard's claimed population is not the population it actually sweeps,
**rewriting the claim to match the narrower reality is not a resolution — it is a deferral**. The
honest-docstring remedy is correct only when closing the gap is genuinely out of the plan's scope AND
nothing downstream depends on the guard's coverage. Here the guard's coverage was the plan's subject.

Test to apply: if the remedy is "document the gap", ask *who closes it and when*. If the answer is
"a reviewer, on this same PR", close it now — the review round is more expensive than the fix,
especially under a 1-review/hour rate window.

## Second-order point

A guard with more than one axis (bot x shape, key x value, type x name) is derived only when **every**
axis is derived. Deriving one axis and hardcoding the other produces a guard that reads as
population-derived and is not — which is worse than an obviously hardcoded one, because the claim
suppresses the next reader's suspicion.
