## Objective

Every Claude harness sync writes a new plugin-cache version directory and regenerates the executor, but never touches Claude Code's plugin registry (`~/.claude/plugins/installed_plugins.json`). The registry keeps naming the previous version, so a session loads skill and workflow text from an older version than the scripts the executor runs, and Claude Code's own collector marks the freshly synced directory `.orphaned_at`. Nothing reports this: the sync says `success`, the orchestrator's restart check reports `registry_parity: not_available`, and the only repair is an operator script kept outside the repository that must be re-run after every landing. This plan makes the gap a red signal at sync time and at the restart check, brings the repair into the repository as an explicit operator-visible step, and makes every document that tells the operator what to do afterwards say the same thing. Carries forward truthful-signals PLAN-TRUTH-154 D7 and D8.

## Deliverables

1. **The sync reports the registry gap.** After the Claude leg of `marketplace/targets/sync.py` has synced, it reads the registry and adds a `registry_parity` block to the Claude result: one row per `*@plan-marshall` registry entry (every scope) with the bundle, the entry's `installPath` version, its `version` field, the version just synced, and whether the synced directory carries `.orphaned_at`; plus one verdict, `in_parity` / `behind` / `unreadable`. `behind` is a red outcome of the run (non-zero exit and a non-`success` Claude row), unless the repin of deliverable 3 ran in the same invocation and closed it. `unreadable` (registry absent, not JSON, no `*@plan-marshall` entry) is reported as its own state and is never folded into `in_parity`. `--dry-run` reports the verdict and writes nothing. Done when: a test under `test/sync-harnesses/` builds a fixture home with a registry in the live shape pinned one version behind the synced tree and asserts `behind`, the named versions and a non-zero exit; a second fixture with matching versions asserts `in_parity` and exit 0; a third with no registry asserts `unreadable`.

2. **One reader that can read the live registry and the live executor.** The existing detector `_plugin_pin_trap.py` returns "unreadable" for both stores on a real machine: its registry reader expects one object per plugin where the live file holds a list of entries under a `{bundle}@plan-marshall` key, and its executor regex expects one path segment between `cache/` and the version where the live layout has two (`cache/plan-marshall/{bundle}/{version}/`). Fix both adapters against fixtures in the live shapes, and have the sync observer of deliverable 1 and the restart-check arm of deliverable 4 use the same reading rules (the sync engine is stdlib-only and loaded by file location, so settle at outline whether it loads the detector module by path or the rules are stated once in a shared stdlib module). Done when: a test in `test/pm-plugin-development/plugin-doctor/test_plugin_pin_trap.py` feeds a registry with `"plugins": {"plan-marshall@plan-marshall": [{user-scope entry}, {project-scope entry}]}` and an executor whose paths read `.../cache/plan-marshall/plan-marshall/0.1.N/skills/...` and gets both versions back instead of `None`; the test fails at HEAD.

3. **The repin is a step in the repository, visible to the operator.** Add a repin entry point next to the cache sync (a `--repin` mode of the engine or a sibling script under `marketplace/targets/claude/`) that ports the mechanics of the out-of-repo script: dry run by default, `--apply` to write; remove `.orphaned_at` from each `{bundle}/{target-version}` directory first, then back the registry up once and rewrite `installPath`, `version`, `lastUpdated` (and `gitCommitSha` when the cache-root `dist-manifest.json` names a `source_sha`) on every `*@plan-marshall` entry whose bundle has that version directory, through a temp file and an atomic replace; never touch another marketplace's entries or `.in_use` files; finish with a gate that re-reads the registry and fails if any repinned entry is not at the target version. The sync skill and the finalize step invoke it as a named step with its own result line and its own token in the step's `display_detail`, never as a silent side effect of the rsync. Whether the step applies automatically or only reports the exact command is the first verify-first clause below; the default this spec recommends is opt-in apply (off unless the operator enabled it), with the dry-run report always printed. Done when: a fixture test proves the order of operations (an injected failure between the marker removal and the registry write leaves the registry untouched and a backup-free state), proves foreign-marketplace entries are byte-identical afterwards, and proves the dry run writes nothing; and a run of the finalize step against a fixture records a `pin` token in its detail.

4. **The restart check scores `registry_parity`.** `cleanup-restart-check` stops reporting `not_available` for this arm. It reads the three stores (registry `installPath` version per `*@plan-marshall` entry, executor `MARSHALL_VERSION`, newest cache version directory) and reports `ready` when they agree, `not_ready` when the registry is behind the executor (evidence names both versions and the repin command), and `indeterminate` when a store cannot be read or the plan-marshall marketplace is not installed through the registry at all. The arm joins the readiness floor. Done when: `test/plan-marshall/plan-orchestrator/test_orchestrator_restart_check.py` asserts all three verdicts from fixtures, asserts a `not_ready` parity row lowers the overall verdict, and no longer asserts `not_available` or the `PLAN-TRUTH-059` owner string; `plan-orchestrator/SKILL.md` describes the arm as scored.

5. **One statement of what to do after a sync.** Today three surfaces disagree: the sync skill says `/reload-plugins`, with a restart as fallback; the out-of-repo script says only a full restart re-seats skill bodies; the detector's remedy text says a restart does not fix the gap and that the registry must never be written. Replace them with one consistent sequence — sync, repin (explicit step), full restart — stated in `.claude/skills/sync-harnesses/SKILL.md` and its two sibling command files, `.claude/skills/finalize-step-sync-plugin-cache/SKILL.md`, `doc/developer/marketplace-build.adoc`, a new symptom row in `doc/developer/manual-sync-recovery.adoc` ("skill text is older than the scripts it calls"), and the `REMEDY_*` constants in `_plugin_pin_trap.py`. Done when: a test asserts the three sync command files carry the same post-sync instruction block, and no file in Expected Surface still tells the operator that `/reload-plugins` alone is sufficient after a Claude sync or that the registry must not be written by the repin step.
