# extract-chat-signal keeps 1 of 13 operator turns, starving every downstream aspect

## Context

`extract-chat-signal run --session-id 1a4a9135-...` resolved the transcript for plan `domain-glob-seeding` and reported:

```toon
raw_turn_count: 400
kept_raw_count: 1
operator_turn_count: 1
gate_decision_count: 2
reduced_bytes: 1113
dropped_turn_count: 399
no_signal: false
over_budget: false
```

The transcript actually holds **13** operator-authored turns (`"type":"user"` entries carrying no `toolUseResult` key; the other 146 user-type entries are tool-result envelopes). The reducer therefore recovered 1 of 13 — recall 0.08 — and reported that single turn as the whole operator population.

The one turn it kept was the phase-2-refine gate answer. Everything it dropped was the material the aspect exists to analyse:

- the operator's approval of an out-of-footprint scope addition (the `build.py` `cmd_quality_gate` fix, commit `4e85bef`);
- two continuation prompts issued after the orchestrator announced it would continue and then ended the turn, on a run configured `finalize_without_asking=true` / `loop_back_without_asking=true`.

Because `no_signal` is `false` and `over_budget` is `false`, the pre-pass routes to **Tier 1** — "feed `reduced_transcript` to the LLM analysis prompt" — so the aspect is handed 1,113 bytes and told the transcript is good. It is not the documented Tier 2 degradation path; there is no skip-reason token, and nothing downstream can tell an over-reduced transcript from a genuinely quiet run.

## Root cause

The reducer's keep predicate is tuned to structured decision markers (`operator-decision:` blocks, gate answers) rather than to operator authorship. A turn is kept because it matches a marker, not because a human wrote it. Free-prose operator input — an approval, a correction, a "why did you stop?" — matches no marker and is dropped with the 399 assistant/tool turns.

The failure is silent in the direction that matters: `operator_turn_count` is derived from the kept set, so it reports the reducer's own recall as if it were the transcript's content. A consumer reading `operator_turn_count: 1` concludes the operator intervened once.

## Proposed action

In `marketplace/bundles/plan-marshall/skills/plan-retrospective/scripts/extract-chat-signal.py`:

1. **Derive `operator_turn_count` from the raw transcript, not the kept set.** Count `"type":"user"` entries with no `toolUseResult` key before reduction. This is the population; the kept set is the sample.
2. **Publish the recall.** Emit `operator_turns_total` beside `operator_turns_kept`, so the fragment can state its own coverage instead of asserting a count it did not measure.
3. **Keep every operator-authored turn unconditionally.** They are the aspect's primary input and there were 13 of them here against a 2 MiB budget — the reduction has no need to drop any.
4. **Route a low-recall reduction to Tier 2.** When `operator_turns_kept < operator_turns_total`, the reduced transcript no longer supports a behavioural verdict: emit the fragment with the existing `transcript_too_large` / `transcript_unavailable` machinery extended by a third skip-reason token rather than presenting a starved transcript as Tier 1.

Point 2 alone would have made this defect self-reporting.

## Evidence

- aspect: chat_history_analysis — `reducer_coverage.recall: 0.08`, `genuine_operator_turns_in_transcript: 13`, `operator_turns_reported_by_reducer: 1`
- aspect: permission_prompt_analysis — `prompt_population: undetermined`; the aspect's only channel is this reduced transcript, so a permission prompt raised during the run could not have been seen
