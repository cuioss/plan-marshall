# A staged spec's measured-value table and its hard constraints are leads, not evidence

## What happened

PLAN-89 / PR #1044. The staged spec was **wrong twice**, and both errors were caught only because the
consuming phase verified the premises instead of building on them:

1. **A quoted measured value was stale.** The spec claimed `verify` ran at ~640 s. It is **learned at
   248 s**, so it resolves `per_task`, not `orchestrator` — and a downstream deliverable had to
   re-anchor on `coverage` instead.
2. **A hard constraint was unsatisfiable as written.** The spec required "never touch the floor", but
   at 630 the value **exceeded the harness cap**, so no tier derivation alone could satisfy it.

Neither error was sloppiness — both premises were plausible when written. The measured value had
simply **drifted since**, and the constraint's impossibility only appears when you compute against
the real cap.

## Solution

**Rule:** a number or a constraint written into a staged spec is a **lead**, not evidence. Two
consequences, both cheap:

- **A LEARNED value is a measurement that drifts.** Any spec quoting a learned timing, threshold or
  calibration owes a **re-read at outline**, before scoping on it. Quote the value *and* name the
  symbol that produces it, so the consuming phase can re-derive rather than trust.
- **A "never X" constraint must be checked for satisfiability against the real bounds**, not only for
  desirability. State the bound it must live within; if no value satisfies it, that is a
  **re-scope**, not an implementation problem to push downstream.

Label both under the Verify-First Contract: an inferred mechanism, an Expected Surface, **and every
derived count or measured value** are three independently-labelled claim classes.

## Impact

⭐ **This is the Verify-First Contract working exactly as designed** — the value of the contract is
visible precisely when a spec is wrong, and here it was wrong twice in one plan without either error
reaching the implementation.

The generalizable half: a spec's authority comes from its *provenance*, not its confidence. A number
in a table reads as settled fact; a constraint phrased as "never" reads as a boundary someone
checked. **Neither is true by default**, and the consuming phase — refine, or outline when refine did
not run — is where that gets established.
