# Add an orchestrator-tier-handoff carve-out to the B7 no-progress predicate

## Context

At 2026-08-24T19:52:19Z the B7 no-progress predicate matched on this plan's first execute dispatch return: `in_progress=1, completed_delta=0, tokens=395651`. It was not applied — but only because the orchestrator reasoned past it by hand and recorded why (decision `79ad38`):

> B7 no-progress predicate matched ... but NOT applied: the return is the documented orchestrator-tier build hand-off (reason=orchestrator_tier_build), which has a dedicated await-long-running handler prescribing run-builds-then-re-dispatch. B7 targets non-progressing checkpoint loops; this loop is blocked on orchestrator-owned work. Classified voluntary_checkpoint. **Gap: B7 has no carve-out for the orchestrator-tier handoff and will misfire on it whenever the first task exceeds 50K tokens.**

The hand-off itself is correct and documented: `architecture resolve` returned `execution_tier=orchestrator` for compile/quality-gate/module-tests on an unmeasured module, and the leaf is forbidden to run or background an orchestrator-tier build (decision `7d41e8`). The leaf did exactly the right thing, and the predicate that guards against stuck loops read it as stuck.

The same shape recurred: 3 of 5 execute dispatch rows are `voluntary_checkpoint`, tripping the separate >50% agent-initiated-re-dispatch threshold in `logging-gap-analysis` for the identical reason.

## Root cause

B7's predicate is `in_progress > 0 AND completed_delta == 0 AND tokens > threshold`. An orchestrator-tier build hand-off satisfies all three by construction: the leaf yields before completing its task precisely because it must not run the build, and the exploration leading up to that point can exceed the token threshold on a single task. The predicate has no access to the return's `reason=orchestrator_tier_build`, which is exactly the discriminator that distinguishes a blocked-on-orchestrator loop from a non-progressing one.

## Proposed action

Carve the orchestrator-tier hand-off out of B7 by reading the return's `reason`: when it is `orchestrator_tier_build`, route to the `await-long-running` handler and do not evaluate B7. The signal already exists on the return; B7 simply does not consult it.

Apply the same carve-out to the `logging-gap-analysis` >50% threshold, which already excludes `budget_yield` and `returned_with_findings` for the analogous reason — a `voluntary_checkpoint` whose recorded cause is the orchestrator-tier hand-off is not agent-initiated re-dispatch.

## Evidence

- decision `79ad38` — the run diagnosed and recorded the gap itself, including its recurrence condition
- decision `7d41e8` — the hand-off is documented behaviour, not a workaround
- decision `6bdd68` — a second, independent orchestrator-tier yield later in the same phase
- aspect: logging_gap_analysis — 3/5 (60%) execute rows tripped the sibling threshold for the same non-defect
