# Phase-5 execution-context doc-port deliverable shipped structurally-valid content that omitted the deliverable's enumerated required points and passed the scoped plugin-doctor quality-gate; only orchestrator content-verification against success criteria caught it

## Context

During plan `authoring-new-domain-knowledge-content-can-ship-a` (PR #725), phase-5
TASK-002 dispatched an `execution-context-level-4` executor to add a
`### Filesystem-Boundary I/O Guards` subsection to `pm-dev-python:python-core`
(`standards/python-core.md`). The deliverable's "Change per file" block enumerated
THREE required points, taken verbatim from the consolidated lesson 2026-06-17-11-001:

1. the glob/iterate `OSError` guard (`Path.glob`/`iterdir`/`rglob`, wrapped so the
   `try` encloses the consuming iteration, not just the call);
2. the `errors="replace"` text-read guard;
3. the `UnicodeDecodeError`-is-a-`ValueError` / `(OSError, ValueError)` catch-tuple rule.

The executor instead wrote a thematically-adjacent but DIFFERENT subsection: a
generic `open()`/`OSError` error-handling guide (validate → narrow-scope open →
handle, existence checks, `PermissionError` narrowing, exception chaining). It
covered NONE of the three enumerated points — the example used a plain
`encoding="utf-8"` with no `errors="replace"`, never mentioned glob iteration, and
never mentioned `UnicodeDecodeError` being a `ValueError`.

The scoped plugin-doctor `quality-gate` returned `status: pass, total_issues: 0` —
the content was structurally well-formed (correct nesting, no lesson-id-in-prose,
no historical prose). The executor returned `next_action: task_complete` with
`verification: passed`. The drift was caught ONLY because the orchestrator read the
actual written content against the deliverable's enumerated success criteria before
accepting the step. The orchestrator rewrote the subsection to cover all three
points and re-ran the gate (still clean).

## The anti-pattern

A phase-5 execution-context executor can satisfy a documentation-port deliverable
with content that is **structurally valid and on-topic but does not match the
deliverable's enumerated content requirements**. The scoped structural gate
(plugin-doctor `quality-gate`) certifies structure — nesting, frontmatter, prose
rules — and is silent on whether the prose actually says what the deliverable's
"Change per file" / "Success Criteria" block requires. The executor's own
`verification: passed` reflects that structural gate, not a content-vs-spec check.
This is the same gates-check-structure-not-X failure family as the plan's own
subject (lesson 2026-06-16-14-001), specialized to the execution loop: a doc-port
deliverable whose value IS its specific enumerated content is exactly where a
structural-only verification gives false confidence.

Symptoms:

- A doc-port / authoring deliverable enumerates specific required points (a list
  of rules, fields, or examples the new prose MUST contain).
- The executor writes well-formed, on-topic prose that omits or substitutes some
  of those enumerated points.
- The scoped quality-gate passes (structure is fine) and the executor returns
  `task_complete` / `verification: passed`.
- Only reading the written content against the deliverable's enumerated success
  criteria reveals the mismatch.

## How to apply

- **For doc-port / authoring deliverables with enumerated required points, the
  orchestrator (or a verification step) MUST content-verify the written prose
  against the "Change per file" / "Success Criteria" enumeration — a clean
  structural quality-gate is necessary but NOT sufficient.** Treat the executor's
  `verification: passed` as a structural pass only.
- **Cheap check**: grep the written file for each enumerated required token before
  accepting the step. Here, `errors="replace"`, `UnicodeDecodeError`, and
  `Path.glob`/iteration would each have been a one-line grep that exposed the gap.
- The fix is a content rewrite, not a structural one — so the verification that
  catches it must also be a content check, not a structural gate.

## Recurrence signature

- Phase-5 doc-port / authoring deliverable with an enumerated required-content list.
- Executor returns `task_complete` + `verification: passed`; scoped quality-gate `pass`.
- Written prose is structurally clean but omits/substitutes one or more enumerated points.
- Caught only by orchestrator content-verification against the deliverable's success criteria.

## Recurrence — 2026-07-14 (finalize-lane-materialization)

Two more instances of the same class — a leaf reporting its assigned surface
complete while leaving an **owned** surface un-swept — surfaced in PR #896. Both
generalize the lesson beyond "authoring prose omits enumerated content points" to
"a deliverable under-covers a surface it explicitly owns":

1. **Docs-retirement leaf skipped a file in its OWN `affected_files` list.** A D3
   docs-retirement leaf concluded that `manage-execution-manifest/SKILL.md` needed no
   edit, even though SKILL.md:574 still carried the retired "off honored-but-warning"
   phrasing the retirement was removing — and that file was in the deliverable's own
   `affected_files`. Concluding no-edit-needed by narrative, without grepping the
   assigned file for the retired token, is the same under-coverage of enumerated
   scope: here the enumerated unit is a FILE to edit, not a content point to include.

2. **A script return-field addition did not update the documented Output contract.**
   The `manage-config` `sync-defaults` return grew `materialized` /
   `materialized_count` fields, but the owning SKILL.md Output block was not updated
   to declare them. Adding a return field is a co-located contract change: the
   documented Output block is an owned surface the same edit must sweep.

Catching gate: unlike the original 2025 instance (caught by orchestrator
content-verification), both of these were caught by **pre-submission-self-review**
(findings e596e9 and 2b8fd6). Self-review's deterministic candidate surfaces
(retired-token / stale-phrasing sweep, and Output-contract-vs-body drift) are now a
catching gate for this under-coverage class — but the durable rule is unchanged:
a leaf's "done" is not evidence that every owned/enumerated surface (content points,
an assigned file edit, a documented Output block) was actually covered.
