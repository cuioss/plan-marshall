# compose wipes execution_log despite doc claiming it is untouched

`manifest-schema.md` and `manage-execution-manifest/SKILL.md` both state: "the
`compose`/`read`/`validate`/`validate-loadable` operations never read or write
it" (referring to `execution_log`). Observed on `plan-truth-157`: the manifest
had 1 `execution_log` row (`verify:quality-gate`, `executed`, unmeasured,
`2026-09-13T23:02:22Z`) before a recompose call (issued to pick up a
`marshal.json` `phase-5-execute.verification_steps` change made mid-execute).
Immediately after recompose, `refire-report` returned `execution_log_rows: 0`
— the row was gone.

`write_manifest` most likely serializes the composer's constructed body dict
wholesale, and that dict never carries an `execution_log` key, so writing it
silently drops whatever `execution_log` the file already had. The claim in
the docs is true of the composer's *read/decision* logic (it never consults
`execution_log` to decide anything) but false of the *write* side-effect.

## Directive

Fix `write_manifest`/`cmd_compose` to read the existing manifest's
`execution_log` (when present) and carry it forward unchanged into the
recomposed body, OR — if a recompose mid-execute is meant to be disallowed —
make `compose` refuse when `execution_log` is non-empty rather than silently
truncating it. Either way, correct the doc claim in `manifest-schema.md` §
"`execution_log[]`" and `manage-execution-manifest/SKILL.md`'s Enforcement
section to match whichever behavior is chosen.

## Recovery applied

Re-recorded the lost row via `record-step` with the same `step_id`/`phase`/
`outcome`, but the restored row's timestamp (`2026-09-14T07:05:26Z`) is NOT
the original (`record-step` has no timestamp override) — an honest but
imprecise repair.
