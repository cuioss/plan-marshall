= Code Intelligence
:nofooter:
:toc: left
:toclevels: 2

xref:../../README.md[Plan Marshall] » xref:README.adoc[Concepts]

"Which modules depend on which?" sounds like a question a tool that has already crawled the whole repository should be able to answer. For a long time Plan Marshall answered it with a Maven-shaped guess buried in a query handler, and returned an empty graph on every project that was not a Maven reactor — without ever mentioning that it had nothing to look with.

Code intelligence is the substrate underneath those questions: what Plan Marshall knows about the shape of a codebase, how much of it costs a subprocess, and — the part that turned out to matter most — how a caller can tell a real answer from a missing capability.

== The tier ladder

The substrate is built in tiers, cheapest first. Each tier is a strictly larger claim about the codebase, and each costs strictly more to produce, so they are worth naming separately rather than collapsing into "the architecture data".

[source,text]
----
┌───────────────────────────────────────────────────────────────┐
│ Tier 2 — symbol intelligence                    NOT BUILT     │
│   call graphs, symbol references, type relations              │
├───────────────────────────────────────────────────────────────┤
│ Tier 1 — module edges                    RESOLVER-DERIVED     │
│   which modules depend on which, with per-edge provenance     │
├───────────────────────────────────────────────────────────────┤
│ Tier 0 — the crawl                        SUBPROCESS-FREE     │
│   module set + per-module metadata + the file inventory,      │
│   read by the path, ownership, and content readers;           │
│   no edges at all                                             │
└───────────────────────────────────────────────────────────────┘
----

*Tier 0* is the crawl. It walks the filesystem, parses each build descriptor with the standard library, and yields the module set plus per-module metadata — coordinates, paths, packages, source counts, canonical commands — and, per module, the categorised file inventory. It deliberately invokes no build tool, so a fifty-module reactor crawls in fifty cheap reads rather than fifty JVM startups. Several readers sit on that one product without enlarging the claim it makes: `files` enumerates it, `find` globs its paths, `which-module` attributes a path back to its owner, and `search --content` scans the bodies of the files in it. What Tier 0 does not produce is a single edge: knowing that `core` and `api` both exist says nothing about whether one depends on the other.

*Tier 1* is the edge set — module-to-module dependency edges, each carrying the identity of whatever derived it. This is the tier the derivation-resolver seam ships, and it is what the `graph`, `path`, `neighbors`, and `impact` verbs traverse, plus the adjacency surfaces of `overview` and `module` / `info`.

*Tier 2* is symbol-level intelligence — call graphs, symbol references, type relations. It is not built. It appears on the ladder so the tiers read as a ladder rather than as a finished set, and so the gap between "Plan Marshall knows the module graph" and "Plan Marshall understands the code" stays explicit.

== The resolver seam

Edge derivation is an extension point rather than core logic, because there is no domain-neutral way to derive an edge. A Maven reactor derives edges from `groupId:artifactId` coordinates. A documentation tree derives them from cross-document references. A Python package derives them from import statements. Each of those is domain knowledge already owned by the bundle that understands that data, and none generalises to the others.

So core owns the merge, the provenance, and the traversal, and owns none of the derivation. A *derivation resolver* is a bundle-supplied implementor that answers exactly one question — which modules depend on which — by returning `(from, to)` module-name pairs plus notes describing anything it deliberately refused to answer.

=== Why a third axis

The seam is a third, independent axis rather than a face on an existing one. Plan Marshall already had two:

* *Axis-A* — skill loading. "What skills does this domain load?" Declared by `ExtensionBase`, subclassed by language and content domain bundles.
* *Axis-B* — the file-to-build map. "What build does a changed file trigger?" Declared by `BuildExtensionBase`, subclassed by build-system skills.

Those two hierarchies are deliberately disjoint — xref:../adr/004-The_file-to-build_contract_is_owned_by_build-system_extensions_not_languagecontent_domains.adoc[ADR-004] keeps them that way — and that disjointness is what forces a third axis. The Maven coordinate join belongs to `build-maven`, which subclasses `BuildExtensionBase` and not `ExtensionBase`, so a resolver hook on `ExtensionBase` would have been structurally unreachable from the one bundle that most needed it. Folding edge derivation into Axis-B instead would have been the mirror error: a future markdown resolver would have to masquerade as a build system to declare an edge.

`DerivationResolverBase` therefore inherits from neither and is inherited by neither. An implementor from either hierarchy opts in by multiple inheritance, which is the only shape reachable from both sides.

== N-resolver union

Several resolvers are active at once and the graph is the union of their edge sets. The union needs no conflict rule, because no conflict is expressible: an edge is an unweighted `(from, to)` boolean, so union is idempotent and commutative.

The nearest thing to a conflict is duplicate *identity*, not duplicate value. A markdown resolver deriving an edge from a cross-document reference and a Python resolver deriving the same module pair from an import statement have not disagreed — they have independently corroborated. That case collapses into one edge carrying both producer ids, which is also exactly what a caller needs in order to trust it.

[source,text]
----
   resolver: maven        resolver: markdown       resolver: python
        │                        │                        │
   (core → util)            (core → util)            (api → core)
        │                        │                        │
        └───────────┬────────────┘                        │
                    ▼                                     ▼
      ┌─────────────────────────────┐     ┌─────────────────────────────┐
      │ from: core                  │     │ from: api                   │
      │ to:   util                  │     │ to:   core                  │
      │ producers: [markdown,maven] │     │ producers: [python]         │
      └─────────────────────────────┘     └─────────────────────────────┘
                    corroborated                    single-sourced
----

== The provenance contract

Every edge names its producers and every response names the resolvers that ran. That buys one specific property, which is the reason the seam is shaped the way it is:

[cols="1,3"]
|===
| Response | Meaning

| `resolver_count: 0`, `edges: []`
| *No resolver ran.* The empty graph is an absence of capability, not a finding.

| `resolver_count: N`, `edges: []`
| *N resolvers ran and found nothing.* The empty graph is a real, positive answer.
|===

Those two states are indistinguishable without the count, and they warrant opposite reactions: the first means "install a resolver", the second means "there are genuinely no edges here". An unqualified empty list reports both as the second. This is the same fail-closed reporting discipline xref:../adr/009-Status_reporting_fails_closed_with_an_explicit_unknown_state.adoc[ADR-009] establishes and that the `find` and `which-module` verbs already apply through their `truncated` and `elided` flags — a confident-looking answer has to carry the evidence that makes it confident.

Two obligations follow. First, *every edge carries a non-empty `producers[]`* — including edges core adds itself, which is why a declared `internal_dependencies` entry is stamped `declared` and a virtual-sibling cross-link is stamped `sibling-cross-link`. No edge in any response is producer-less. Second, *every suppressed edge is reported*, through the `notes[]` half of a resolver's return.

The suppression channel exists because of a specific failure. A resolver keys its derivation on some identity — a Maven coordinate, a document path, a package name — and two modules can claim the same key. Resolving that by insertion order silently drops one module and every edge pointing at it, and which module survives depends on map iteration order: a non-deterministic answer presented as a confident one. A resolver facing an ambiguous key therefore emits no edge for it and reports the collision, so an ambiguous key stays distinguishable from an absent one.

== The Tier-0 companion: path attribution

Tier 0 yields the module set. It does not say which module owns an arbitrary path — and that second question is the one the change-footprint classifiers ask once per changed file, and the one `which-module` answers at its third resolution rung.

Path attribution is an extension point for the same reason edge derivation is: there is no domain-neutral way to derive it. The `plan-marshall` bundle knows that `.plan/**` and `.claude/skills/**` are its own, a documentation bundle knows what `doc/**` is, a build bundle knows which tree its production sources live in. Each is domain knowledge already owned by the bundle that understands that tree, so core owns the merge, the provenance, and the resolution order, and owns none of the claims. `PathAttributionBase` is a fourth axis for the same structural reason `DerivationResolverBase` is a third — the implementor population straddles both existing hierarchies, so an implementor from either opts in by multiple inheritance. Ownership is not build routing: Axis-D answers which module *owns* a path, Axis-B answers what build a changed file *triggers*, and neither table feeds the other.

The merge differs from the edge union in exactly one structural respect. A claim is a keyed mapping — the normalised path prefix is the identity, the claimed module is the value — so a value exists to disagree about and a conflict *is* expressible, where for an unweighted `(from, to)` boolean none was. Two attributors claiming the same prefix for different modules have genuinely contradicted, and the merge emits no claim for that prefix and reports the collision rather than letting discovery order pick a winner.

The provenance residue is the same one axis over:

[cols="1,3"]
|===
| Response | Meaning

| `attributor_count: 0`, `module: null`
| *No attributor ran.* The unattributed path is an absence of capability, not a finding.

| `attributor_count: N`, `module: null`
| *N attributors ran and none claimed this path.* The unattributed path is a real, positive answer.
|===

A `module: null` carrying a collision note is a third answer again — the ownership is disputed rather than merely unclaimed.

== The other Tier-0 reader: content search

Path attribution asks a question *about* the inventory. Content search asks a question about what is *inside* it: which files contain a given string. `search --content` is a second reader over the same Tier 0 product — it opens the files the crawl already enumerated and applies a regex to each body. That is worth being precise about, because "search the code" sounds like the tier above.

It is not. Tier 2 is symbol intelligence: knowing that this identifier is a function, that this call site invokes that definition, that this type flows into that parameter. Content search knows none of that — it knows that a sequence of characters appears in a file. A regex cannot distinguish a definition from a comment mentioning it, and does not claim to. The verb makes exactly the claim Tier 0 supports and no larger one, which is why it sits here rather than one rung up.

The provenance residue takes a third form, one axis over again. There is no producer set to name, because nothing was derived — so the discriminator is the *population*:

[cols="1,3"]
|===
| Response | Meaning

| `count: 0`, `files_scanned: 0`
| *Nothing was searched.* The empty result is an absence of population, not a finding.

| `count: 0`, `files_scanned: N`
| *N files were opened and none matched.* The empty result is a real, positive answer.
|===

That is the same shape as `resolver_count` and `attributor_count`: two states that are indistinguishable without the count, warranting opposite reactions, where an unqualified empty list reports both as the second. The companion field is `unreadable[]` — a file skipped because it could not be decoded or could not be read is named with its reason rather than quietly dropped from the denominator, which is the no-silent-suppression half of the same discipline.

=== Location and strength, never the lines

A hit reports where it is — `module`, `category`, `path` — and how strongly — `match_count`, the number of occurrences in that file. It deliberately carries no matching line text and no line numbers.

The reason is a cost asymmetry rather than a limitation. Returning line bodies makes the response size a function of the corpus's *match density*; returning files makes it a function of the corpus's *file count*. Those diverge badly at exactly the moment the sweep is most useful — a broad question over a large tree — and the divergent case is the one that would flood a caller's context, which is the resource this whole substrate exists to spend carefully.

`match_count` is what stands in for the lines. It is a ranking signal: it lets a caller sort the hit list and spend a `Read` on the two or three files that matter instead of on all of them. Sweep, rank, read a few.

=== Inventory scope is not tree scope

The honest limit here is the one a caller is most likely to over-read. The search covers the crawled inventory, which by construction excludes always-ignored directories (`.git`, `node_modules`, `target`, caches), dotfile trees outside the allowlist — `.claude/**` and `.github/**` among them — and anything a `.gitignore` rule removes, including `.plan/`.

So a `count: 0` over a large `files_scanned` is a trustworthy *"not in any inventoried file"*. It is not *"not in the tree"*, and the two are not interchangeable when the thing being looked for might live in a workflow file or a local setting. Untracked-but-not-ignored files are covered, though: the walk is gitignore-aware rather than driven by what git tracks, so the reader also works outside a git worktree.

== The honest limit

[CAUTION]
====
*The provenance contract makes an answer auditable; it does not make it correct.*

`resolver_count: 2` tells a caller that two resolvers ran and names them. It does not tell the caller that either one understood the project. A resolver that parses the wrong file, or matches on the wrong key, reports `status: ok` with an edge count and contributes a confidently-labelled wrong edge. Provenance narrows "why is this graph empty?" to a mechanical answer; it does not review the derivation.

The tier ladder has its own limit: Tier 1 stops at module granularity. "Module `api` depends on module `core`" is often too coarse to act on — the interesting question is usually which symbol, in which file. That is Tier 2, and Tier 2 is not built.

Finally, the seam derives edges only for module sets that Tier 0 discovered. A resolver cannot invent a node: the merge drops any pair whose endpoints are not both known module names. A dependency on something the crawl never found is not an edge, and is not reported as one.
====
