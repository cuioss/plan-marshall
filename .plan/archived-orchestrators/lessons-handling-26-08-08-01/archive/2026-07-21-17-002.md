# A newly-relied-upon script flag must be verified against the owning skill's contract doc, not just argparse -- implemented is not documented

A plan added new `session push-title-token --store orchestrator --slug {slug}` invocations
to four orchestrator workflow docs (`analyze.md`, `decompose.md`, `orchestrate.md`,
`lessons-handling.md`). The author verified the flags against the implementation —
`platform_runtime.py` argparse, which declares `--store` and `--slug` fully, including both
`invalid_argument` guards — and shipped the call-sites on that basis.

## Defect

Verification stopped at the implementation. The **governing contract** for the operation did
not document the flags at all:

- `plan-marshall:platform-runtime` SKILL.md § Operations table listed only `--plan-id` /
  `--icon` for `session push-title-token`.
- `platform-runtime/standards/contract.md` § `session push-title-token` → Arguments listed
  the same two flags.

Only the router's own module docstring mentioned `--store` / `--slug`. So a reader who did
the correct thing — consult the governing skill contract for a newly-relied-upon operation —
would conclude the new call-sites were passing **undocumented arguments**, and would have no
authority for the store-selector semantics. The plan simultaneously created N new consumers
of a flag while leaving the flag's contract surface empty.

Pre-submission self-review (`pm-plugin-development:ext-self-review-plan-marshall`, contract-
sources candidate class) caught it and it was fixed inline during finalize (Q-Gate finding
`c9df38`), so nothing shipped broken. The residue is the authoring discipline that let it
reach self-review at all.

## Root cause

"Implemented" was treated as equivalent to "documented". The argparse declaration is the
*mechanism*; the SKILL.md Operations table and `standards/contract.md` Arguments section are
the *contract*. A flag can be live in argparse for a long time — reachable, tested, even
used by one internal call-site — and still be absent from the contract, because nothing
forces the two into agreement when the flag is first added. The gap becomes visible only
when a change makes the flag load-bearing for external callers, and at that moment the
author is the last person positioned to notice it.

## Corrective action

When a change introduces a call-site that **newly relies** on a script argument, do not
verify the argument against argparse alone. Verify it against the owning skill's contract
surface and close any gap in the same change:

1. Resolve the owning skill of the script notation being invoked.
2. Check the argument appears in **both** contract surfaces where the skill maintains them:
   the SKILL.md Operations / Canonical-invocations row, and `standards/contract.md` (or the
   equivalent per-operation Arguments section).
3. If either omits it, transcribe the argument **verbatim from the argparse declaration** —
   name, choices, default, and every validation guard (e.g. the `invalid_argument` rejection
   paths) — into the contract, in the same commit as the new call-sites. Do not paraphrase
   from the module docstring; the docstring is not the contract either.
4. Treat "the flag is already implemented and another call-site already uses it" as *not*
   discharging the obligation. First external reliance is the trigger.

The inverse discipline for script authors: adding a flag to argparse is not complete until
the Operations table and the contract Arguments section carry it. Shipping a flag
contract-less defers the cost onto the first consumer.

## Relationship to existing corpus

Distinct from `2026-07-18-05-002` (contract-change prose mirrored across N locations — sweep
by stale phrasing): there the contract *changed* and stale copies survived. Here nothing
changed — the contract was silently incomplete from the moment the flag was added, and
adoption is what exposed it. A stale-phrase grep finds nothing, because there is no stale
phrase; the defect is an **absence**.

Distinct from `2026-07-15-18-001` (agents improvise non-existent `manage-*` subcommands —
consult Canonical invocations for the exact verb): there the invoked surface did not exist
and the contract was right. Here the invoked surface exists and the contract is wrong by
omission — so "consult the contract" would have *mis-informed* the reader. Both lessons
point at the same document; this one covers the direction where the document, not the
invocation, is at fault.

## Impact

Every `{bundle}:{skill}:{script}` operation whose flag surface is documented in two places
(SKILL.md Operations table + `standards/contract.md`) separately from its argparse
declaration — i.e. the whole marketplace script surface. The failure is silent: all in-house
gates pass, because the call-sites are correct and the script works. Only a contract-sources
structural self-review, or a human reading the contract, surfaces it.

A structural gate is the durable fix candidate: a plugin-doctor analyzer that diffs each
script's argparse flag set against the flags documented in the owning skill's Operations
table / contract Arguments sections would make this class impossible to ship rather than
relying on self-review to catch it per-plan.
