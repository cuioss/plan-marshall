# Lessons carrying YAML frontmatter are listable but unaddressable by every id-keyed verb

## What happened

The `finalize-step-lessons-housekeeping` step tried to retire lesson `2026-09-03-17-001` after this plan landed its prescribed fix. `manage-lessons remove` returned `error: not_found` for a lesson file that demonstrably exists on disk and appears in `manage-lessons list`.

Sweeping the corpus found the same signature on **10 of 78 active lessons**: `2026-09-03-02-001` through `02-009`, plus `17-001`.

## Root cause

Those files carry YAML `---` frontmatter instead of the corpus's `key=value` header. The list path tolerates the difference — it renders them with empty `component` and `category` — but every **id-addressed** verb (`get`, `read`, `remove`, `update`, `supersede`, `set-body`, `set-title`) misses them and reports `not_found`.

## Why it matters

These lessons are in a state with no exit. They can be listed but never retired, updated, or superseded, so they accumulate indefinitely and permanently overstate the size of the active corpus. Worse, the failure is silent in the direction that matters: a housekeeping pass that tries to retire one gets `not_found` and — correctly, per its own error handling — treats it as non-fatal and moves on. Nothing escalates, so the corpus quietly fills with entries that no automated pass can ever remove.

The immediate consequence in this run: a promotion landed without its paired retirement, leaving a documented rule and the lesson that motivated it both live. That is the benign version. The accumulating version is a corpus where the retire/supersede machinery no longer reaches a growing fraction of its own contents.

## How to apply

Two halves, and the second is the one that keeps it fixed:

- **Normalise the existing ten.** Rewrite their headers into the `key=value` form so the id-addressed verbs reach them, then the owed retirements can proceed.
- **Close the write path that produced them.** A `key=value` corpus that silently accepts YAML-frontmatter files is the actual defect — the ten did not arrive by hand-editing, they arrived because something wrote them that way (an agent using `Write` directly rather than `manage-lessons add` + `set-body`). Either teach the reader to accept both header forms, or make the corpus reject a malformed file at write time instead of accepting one that later reads as absent.

Prefer making `list` and the id-addressed verbs agree, whichever way that is settled: the present split — visible to one, invisible to the other — is what let this go unnoticed until a retirement failed.

## Detection

`manage-lessons list` renders an affected lesson with empty `component` and `category`; `manage-lessons get --lesson-id {id}` on the same id returns `not_found`. That disagreement is the signature.

Related: [[2026-09-03-17-001]] is the lesson whose retirement this blocked.

## Recurrence — 2026-09-04 (plan-145-publish-the-missing-parser-seams)

**The population is growing, which is the prediction this lesson made.**

A fresh `manage-lessons list` during this plan's retrospective returns 87 active
lessons, of which **12** render with empty `component` and `category` — the
documented signature. Up from 10 of 78 when this lesson was written.

The affected ids are the original nine `2026-09-03-02-001` … `02-009` plus
`2026-09-03-17-001`, and now also `2026-09-04-07-001` and `2026-09-04-07-002`.

Two observations:

1. **The write path is still open.** The two new members were created a day
   *after* this lesson was filed, so nothing yet rejects a malformed file at
   write time. That is the half this lesson called "the one that keeps it fixed".
2. **The share is roughly stable, so the absolute count grows with the corpus.**
   12.8% → 13.8% of active lessons are now unaddressable by every id-keyed verb.
   `finalize-step-lessons-housekeeping` ran three times on this plan and
   reported `0 rm, 0 promo, 0 adapt, 81 keep` each time — a clean-looking result
   that is silently unable to reach an eighth of what it is counting.

The corrective ordering follows from that: **close the write path first**, then
normalise. Normalising twelve files while the producer is still live buys one
clean sweep and no more.
