# Deployed plugin cache serves pre-fix frontmatter, so a shipped order/mutates_source fix never takes effect and the gate that would catch it is defeated too

The execution-manifest composer resolves each finalize step's `order` and
`mutates_source` by reading that step's standards-doc frontmatter from the tree
`Path(__file__)` lives in — which, at runtime, is the **deployed plugin cache**,
not the marketplace source tree. When the cache is stale for a bundle, the
composer silently composes against the OLD contract. Nothing errors: the sort
succeeds, the manifest is well-formed, and the ascending-order validator agrees,
because every one of them reads the same stale frontmatter.

## Observed

PR #990 (`b8581d952`, merged 2026-07-23) fixed two defects on
`phase-6-finalize/standards/finalize-step-preference-emitter.md`:

- `order: 80` → `order: 61`, so the step runs BEFORE the `branch-cleanup` (70)
  merge gate and its `architecture enrich` write can ride the plan's own PR.
- added `mutates_source: true`, so the dispatcher's commit instrumentation fires.

Three days later, a plan composed its manifest and got the **pre-fix** ordering
back:

```text
… lessons-capture(60), branch-cleanup(70), finalize-step-preference-emitter, …
```

Source tree at HEAD:

```text
order: 61
mutates_source: true
```

Deployed cache `plan-marshall/0.1.1194`:

```text
order: 80
(no mutates_source key)
```

Under the cache's `order: 80` the composer's output is *correctly* ascending
(70 → 80 → 81 → 85), so `_check_ascending_order` passes. The manifest is not
malformed; it is faithful to the wrong input.

## Why the guard did not fire

#990 also added `_analyze_mutates_source_order.py`, whose stated purpose is to
fail a step that is ordered at/after the merge gate and omits an explicit
`mutates_source` key — "an absent declaration is a compose-time failure rather
than a silent pass". That analyzer reads frontmatter too. The cache copy has no
`mutates_source` key **and** sits after the merge gate, which is exactly the
condition the analyzer exists to reject — but the analyzer's own bundle
(`pm-plugin-development`) was current while `plan-marshall` was stale, so the
rule never saw the file it was written for. The omission hole #990 closed in
source stayed open in the running system.

## The sharper finding

The cache was **internally inconsistent at one version string**. At
`0.1.1194`:

- `pm-plugin-development` DID carry #990's new analyzer.
- `plan-marshall` did NOT carry #990's frontmatter change.

So a bundle's version directory name is not a freshness oracle for that bundle's
content generation. Two bundles under the same version can be at different
commits, and a cross-bundle contract (analyzer in one bundle, subject in another)
can be half-applied with no signal.

## Impact

A `mutates_source: true` step scheduled after `branch-cleanup` writes tracked
source AFTER the PR is squash-merged and the feature branch is gone. The edit
cannot ride the PR, cannot be squashed into the landed commit, and surfaces later
as an unexplained dirty `main`. Here it stayed latent only because the step
no-op'd (1 disposition vs `preference_min_recurrence: 2`) — the ordering defect
was live, its trigger simply did not fire.

## Guidance

- Do not treat "the fix is merged to main" as "the fix is in effect". For any
  change to frontmatter that a **runtime resolver** reads (`order`,
  `mutates_source`, `lane`, `default_on`, `presets`, `implements`), the fix takes
  effect only after the plugin cache is re-synced. Verify against the cache copy,
  not the source copy.
- When a plan changes a frontmatter key that governs composition, re-read the
  DEPLOYED path (`~/.claude/plugins/cache/{marketplace}/{bundle}/{version}/…`)
  as the acceptance check.
- A structural analyzer and the files it governs must be verified at the same
  content generation. An analyzer that passes is only meaningful if its subject
  tree is as fresh as the analyzer.
- Suspect this class whenever a composed manifest contradicts the source-tree
  frontmatter: compare cache vs source before concluding the composer is buggy.
  The composer was correct here; its input was not.
