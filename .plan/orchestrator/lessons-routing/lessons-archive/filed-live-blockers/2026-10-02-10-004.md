# Diff scope-creep and task artifacts against the merge base

## Context

While the plan was paused for a red main, the feature branch was fast-forwarded onto the repaired main. From then on two phase-5 measurements attributed upstream files to the plan:

- The scope-creep guard counted 6 and then 16 "residual" paths over its threshold of 5. Every one came from upstream commits #1665-#1668; the plan had edited only its declared files.
- Closing TASK-1 emitted 14 `[ARTIFACT]` lines, of which 10 name files the plan never touched (`doc/antigravity/*`, `doc/developer/*`, `doc/user/*`, `test/plan-marshall/manage-config/test_config_defaults.py`).

## Root cause

Both diffs run from a fixed commit recorded before the branch moved: `plan_creation_sha..HEAD` for the guard and `task_start_sha..HEAD` for the artifact lines. Once main is merged or fast-forwarded into the branch, those ranges contain upstream history, so everything upstream changed reads as the plan's or the task's work.

## Proposed action

Compute both ranges from the merge base with the base branch (the plan's own contribution), or re-stamp the recorded start commits whenever the baseline is reconciled. Add a test where upstream commits land between the recorded commit and HEAD and assert they are counted for neither the guard nor the artifact lines.

- decision.log 2026-10-01T09:51:14Z (fast-forward 638e13906 to 427649eb2 with uncommitted plan files preserved)
- work.log 2026-10-01T10:03:38Z (TASK-1's 14 artifact lines)

## Recurrence — 2026-10-02 (unified-sync-all-harnesses)

### Context

Task artifact lines over-attributed again, through a second trigger that involves no upstream movement. The plan commits once per deliverable, so the second task of a deliverable starts on a working tree that still holds the first task's uncommitted changes. Its `[ARTIFACT]` lines then list both tasks' files:

- TASK-2 repeats all 10 of TASK-1's files, including `Deleted .claude/skills/sync-plugin-cache/scripts/sync.py`, which TASK-1 removed.
- TASK-4 repeats TASK-3's 6, TASK-6 repeats TASK-5's 2, TASK-8 repeats TASK-7's 24, TASK-10 repeats TASK-9's 3.

The work log holds 145 `[ARTIFACT]` lines for an 89-path footprint. The retrospective's population check (13 of 13 change-qualified tasks emitted a line) passes on these lines, so it cannot see the over-attribution.

### Root cause

Same family: the task's range starts at a commit that does not bound the task's own contribution. Here `task_start_sha` equals the sibling task's start commit, and the diff runs against the working tree.

The proposed action above does not cover this trigger. A merge-base range would attribute the whole branch to each task.

### Proposed addition

Bound a task's artifact diff by the working-tree state at task start (for example a tree hash or a path-and-hash snapshot taken when the task is marked in progress), not by a commit. Add a test with two tasks in one deliverable and no commit between them, and assert the second task's lines exclude the first task's files.

- work.log 14:54:10Z and 14:59:19Z (TASK-3, TASK-4), 15:05:02Z and 15:12:48Z (TASK-5, TASK-6), 15:33:19Z and 16:11:19Z (TASK-7, TASK-8), 16:17:20Z and 16:20:31Z (TASK-9, TASK-10).
