# A machine running several plan worktrees oversubscribes itself and manufactures timeout-shaped test failures

## Observation

During finalize of `misconfigured-reviewer-name-reads-missing-review` (PLAN-PR-044), the same
whole-tree `module-tests` suite produced four different outcomes on one unchanged tree, and
the variable was machine load, not code:

| Attempt | Load | Result |
|---|---|---|
| baseline (quiet) | ~8 | 23775 passed, 0 failed, **715s** |
| #1 | ~56 | 23770 passed, **5 failed** — all `pytest-timeout (>300s)`, zero assertions |
| #2 | ~106 | `status: timeout` at 1800s — **no verdict at all** |
| scoped (438s baseline) | ~105 | `status: timeout` at 1800s — **no verdict** |

Every failure was a wall-clock timeout inside heavy whole-marketplace plugin-doctor tests
(`run_quality_gate` / `ast.walk` / subprocess-select). The branch never touched
`pm-plugin-development` — `git log origin/main..HEAD` over it is empty.

The load came from concurrent plan worktrees running their own suites (up to four active
plans on one machine), each spawning ~10 pytest-xdist workers, plus IDE and OS background
work. Two separate observations also showed the daemon's timeout **not reaping the worker
tree**: orphaned xdist workers were still burning 20-24% CPU each ~15 minutes after their
job timed out, compounding the next run's contention.

## Why it matters

Three distinct costs, and the third is the dangerous one:

1. **Wall-clock.** ~80 minutes across three attempts, plus a waited-out drain window.
2. **A false failure signal.** Attempt #1 looks exactly like five real test failures. Only
   reading the failure *mode* (timeout, not assertion) and checking `git log` for provenance
   separated it from a genuine regression.
3. **Pressure toward a false green.** The available shortcuts — raise `pytest-timeout`,
   narrow the suite, or accept the triage path over an empty finding set — all produce a
   green that was never earned. A build that reports no verdict produces no findings, so
   routing it to `verification-feedback` sweeps an empty set and reports a clean pass.

## Directive

- **Never route a `timeout` / `killed` / `indeterminate` build into findings triage.** It
  produces no findings by design; the triage would report a clean sweep over nothing.
- **Read the failure mode before the failure count.** N timeouts is not N test failures.
  Establish provenance (`git log origin/main..HEAD` over the failing paths, plus a known
  green baseline) before treating any of it as branch-introduced.
- **Reap only your own worktree's orphans.** The daemon's timeout does not reap the xdist
  worker tree; `pkill -f "worktrees/{plan_id}/.venv"` is in bounds, another plan's is not.
- **Consider a machine-global build-queue slot across worktrees.** One shared slot would
  serialise sibling suites instead of letting four plans each spawn ten workers. The
  build-queue limiter already exists in `manage-locks`; it is the natural home.
- **When the budget is genuinely exhausted, degrade honestly.** Mark the gate `done` with a
  `display_detail` naming the un-gated arm (`module-tests UN-GATED (budget)`), log what IS
  and IS NOT established, and let remote CI — which runs uncontended — be the authority.
  Never re-run a third time hoping for a different machine.
