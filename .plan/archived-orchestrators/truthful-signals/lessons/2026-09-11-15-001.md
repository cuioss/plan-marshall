# Ask of every guard, test set and claim: what would have to change for this to go red — and did anything check it?

## The one question

Every rule below is the same question asked of a different artifact: **"what would have to be deleted or
changed for this to go red — and did anything actually check that?"** A guard, a test pair, a comment and
a verdict each assert that something is protected or established; each can be individually correct and
still protect nothing.

## 1. Review complementary tests as a SET, not individually

Two tests that split an input space (non-empty / empty, present / absent) can each be correct and jointly
blind: the assertion that pins the shared mechanism sits in neither, because each author assumed the other
covered it. Observed: a non-empty-body probe asserted only status and header, its zero-length companion
asserted `body=<none>` — deleting the body-rendering path left both green. The gap survived Q-Gate, the
outline, the structural self-review and the simplify pass; an automated PR reviewer caught it. **Per-item
review cannot see a set-level gap.** For every complementary pair ask: *if the mechanism both protect were
deleted, would either go red?* If not, add the missing assertion to the member whose fixture exercises it,
and say in its message why the companion does not cover it — so it is not later deleted as redundant.

## 2. Land the mechanical guard in the same change that removes the instances

Removing N instances of a defect class by hand leaves instance N+1 free to arrive. Observed: ten removed,
a guard landed over the objection that it was redundant, and the eleventh arrived within a day — copied
wholesale from a sibling service by an unrelated PR — and was caught only by the guard, at the merge-queue
boundary, after review and PR CI had passed. **"There are no instances left" is the argument that makes the
guard cheap, not redundant.** Weigh a guard against ingress paths (copy-paste from a sibling, a revert, a
stale branch, a new contributor), never against instance count.

## 3. A guard test that enforces a cross-module convention lands with the written convention

A test enforcing a convention that spans module boundaries converts a silent rule into a red test — but a
red test citing an undocumented rule tells the maintainer *that* they broke something, not *what*. "The test
is the documentation" does not hold across a module boundary: whoever trips it is by definition not working
in the module the test lives in. Land the written statement of the convention in the same change, in a
location the failure message points at.

## 4. A sentence naming a mechanism is a claim — open the mechanism before writing it

"Guarded by X", "enabling Y does Z", "safe because the shell does W", "every build stays green" are claims
that drift one way: the mechanism changes, the sentence does not — and a later reader who trusts it stops
looking, so a false guard-claim is strictly worse than none. Observed four times on one branch, caught by
review every time and by a test never. Naming a test file is not evidence; naming the assertion in it that
reads the guarded thing is. **Any sentence falsified by opening one file is written only after opening that
file** — or deleted.

## 5. Scope a verdict to the evidence that produced it

Evidence covering one form of a hypothesis retires that form, not the hypothesis: "contradicted for held
listeners; untested for accepted and client sockets" is the finding, "contradicted" is the overreach. And N
claims read off one observation are one observation and N−1 inferences. A `MEASURED` label does not check
scope — it raises the reader's confidence in the overreach. Before any conclusive verdict, enumerate the
hypothesis's forms, state which the evidence covered, and count observations against claims.
