# Promoting a filesystem-walking analyzer to a build-failing gate catches synthetic test fixtures that materialize analyzer-triggering files outside the sanctioned scan scope

When a deliverable flips a filesystem-walking lint rule from analyze-only to
build-failing (`quality-gate`), the rule that was previously advisory now
gates the build for *every* tree the walk reaches — including synthetic trees
that pre-existing test fixtures materialize on disk. A fixture that was
harmless while the rule only surfaced findings becomes a hard build failure
the moment the rule joins `quality-gate`.

## Evidence (hardening-sweep, TASK-006)

Deliverable 2 promoted the plugin-doctor agentfile-hygiene rules
(`agentfile-line-count-over-budget`, `agentfile-directory-tree-present`) from
analyze-surfaced-only into the `quality-gate` dispatch. Immediately after the
flip, the whole-tree quality-gate went red on a file the plan never touched:
the plugin-doctor test fixture `_clean_bundles` in
`test/pm-plugin-development/plugin-doctor/test_runner.py` builds a synthetic
bundle tree containing `CLAUDE.md` / `AGENTS.md`-shaped files. The
now-build-failing agentfile scan walked *into* that fixture tree — an
"agentfile scan escape" — and flagged the synthetic agentfiles as budget /
directory-tree violations. The fix (TASK-006) nested the fixture tree under
`marketplace/bundles/` so the scan's scope-resolution treated it correctly
instead of escaping into an unscoped location.

The defect was caught in-run by the phase-5 verification-feedback sweep (the
own quality-gate went red), so nothing shipped — but it was invisible until
the gate-flip landed, because the fixture had been inert under the prior
analyze-only mode.

## Root cause

A build-failing analyzer's blast radius is every path its walk reaches, not
just production source. Test fixtures that synthesize the exact artifact class
the analyzer keys on (agentfiles, here) are indistinguishable from real
violations once the analyzer gates. The fixture's placement — outside the
sanctioned, scope-excluded root the analyzer expects — is what turns it into a
false positive at the gate.

## Corrective action (do X, not Y)

- **Do**, before flipping any filesystem-walking analyzer to build-failing,
  sweep the test tree for fixtures that materialize the artifact class the
  analyzer keys on (files matching its glob / name pattern), and either nest
  them under the analyzer's sanctioned + scope-excluded root or add them to the
  analyzer's exclusion set. This is the same "sweep the mirror surface when you
  change the contract" discipline as the test-local-render-helper class
  (lesson 2026-07-14-16-001) and the mirror-contract-surface class
  (lesson 2026-06-29-16-001), applied to a scan-scope boundary.
- **Do not** flip the rule and rely on CI to surface the fixture escape after
  the fact — land the gate-flip only after the own-tree (fixtures included) is
  green under the newly-gating rule. The plan's own constraint ("do not flip on
  a dirty own-tree") is the right instinct; extend "own-tree" to include the
  synthetic trees that test fixtures build on disk.

## Impact

A gate-flip that looks self-contained (two rules move into `quality-gate`)
carries a hidden second-order dependency on every test fixture that trips the
scan. Missing it costs a red-gate loop-back and a fixup task; catching it up
front (fixture sweep as a sibling step of the flip) keeps the flip a one-shot
change.
