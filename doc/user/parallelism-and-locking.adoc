Operating Plan Marshall with several plans in flight at once. Concurrent plans contend for three shared resources — the merge-to-`main` boundary, the build machine, and a rate-limited review bot's window — and Plan Marshall serializes all three with cooperative, main-anchored locks. This page covers the settings you can tune (build concurrency, the PR-merge boundary, and the review-bot rate window), where the lock events are logged, and what to do when the build queue looks stuck. For how the locks work, see xref:../concepts/parallelism-and-locking.adoc[Concepts › Parallelism and Locking].

[#build-concurrency]
== Build-concurrency settings

Three settings govern build concurrency and stale-slot recovery, and they live in three different places — only one of them is `marshal.json`.

[cols="2,1,3,3", options="header"]
|===
| Setting | Default | Where it lives | Managed with

| `build.queue.max_slots` — the build-slot cap
| 5
| `~/.plan-marshall/marshalld/machine-config.json`, beside the daemon's `registry.json`. Machine-global; the home root is overridable via `PLAN_MARSHALL_HOME`.
| `manage_build_server config get` / `config set --max-slots N` / `config migrate`

| `upper_limit_seconds` — the stale-slot threshold
| 600 s (also the floor; ceiling 3600 s)
| A top-level field of `~/.plan-marshall/build-queue.json` — the queue state whose entries it governs. Machine-global.
| `build_queue limit get` / `limit set --value N`

| `build.queue.max_retries`
| 10
| `marshal.json`, under the top-level `build.queue` block.
| Edit the JSON directly
|===

Two of the three are *machine-global* — one value per host, shared by every checkout contending for the one machine-global `build-queue.json`. Both are applied to *every* repository's entries in that shared queue, so a per-repo copy is one two callers could hold different values of while competing for the same slots. Being host state, neither is git-tracked and neither is a `marshal.json` key. `max_retries` is the only per-repo one, and legitimately so: it bounds nothing but this caller's own re-poll loop.

[#build-slot-cap]
=== The build-slot cap

`max_slots` is the maximum number of builds that may run concurrently across every session on the host. A build that finds a free slot runs immediately; otherwise it is enqueued and promoted in FIFO order as slots free up.

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-build-server:manage_build_server config get
python3 .plan/execute-script.py plan-marshall:manage-build-server:manage_build_server config set --max-slots 8
----

`config get` takes no flags and writes nothing. `config set` takes `--max-slots` and nothing else; it is the unconditional writer, so it is also the only way to repair a machine-config file whose cap is unreadable or invalid. *No restart is needed* — a running daemon re-resolves the cap on every submit, so a `config set` takes effect on the next build submitted.

Do not hand-edit `machine-config.json`. `config set` and `config migrate` are its only writers, and they serialize on a guard file so a concurrent writer cannot slip between `migrate`'s "is the cap unset?" check and its write.

The cap is never reported as a bare number, because the value alone cannot tell a configured 5 from a fallback 5. Every report carries a `max_slots_source`, and a `max_slots_detail` whenever that source is not the nominal one:

[cols="1,3", options="header"]
|===
| `max_slots_source` | What it means

| `machine_config` | A positive integer is configured there. This is the nominal case, and the only one with nothing to explain.
| `default` | Neither the file nor the key is present. Nothing is configured, which is a perfectly normal state; the cap is 5.
| `invalid` | The key *is* present but holds something unusable — a non-integer, a boolean, or a non-positive number. The cap falls back to 5 and `max_slots_detail` names the offending value.
| `unreadable` | The file exists but could not be read or parsed. The cap falls back to 5 and `max_slots_detail` names the error.
|===

`invalid` and `unreadable` are deliberately kept distinct from `default`: the file exists and holds *something*, so a cap may well be configured and merely mistyped or unreachable — which is a different problem from having configured nothing. Repair either with `config set`.

`manage_build_server status` reports the cap the *running* daemon is applying, taken from its ping rather than resolved locally (a local resolve answers what a *fresh* daemon would apply — a different question). A daemon pinned to a copy predating the cap fields sends neither, and both then render `unknown` rather than a plausible substitute; a degraded source additionally gets a `max_slots_warning` naming the fallback being admitted against.

[#stale-slot-threshold]
=== The stale-slot threshold

`upper_limit_seconds` is the adaptive estimate of the longest real build, and xref:../concepts/parallelism-and-locking.adoc[the self-healing reaper] treats an active slot older than `2 ×` this value as dead. It is monotonic-up and clamped to `[600 s, 3600 s]`, so it grows toward the longest build observed but never ratchets past an hour.

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-locks:build_queue limit get
python3 .plan/execute-script.py plan-marshall:manage-locks:build_queue limit set --value 900
----

Neither verb takes a `--plan-id`: they read and write machine-global state that belongs to no plan. `limit set` takes `--value` and nothing else. A value below 600 is floored to 600 and one above 3600 is clamped to 3600 — the result reports both `requested` and the `value` actually stored, plus a `clamped` flag, so a clamp is never silent; a non-positive value is rejected outright.

CAUTION: `--value` belongs to `build_queue limit set`; `--max-slots` belongs to `manage_build_server config set`. They are different scripts managing different settings, and neither accepts the other's flag.

`limit get` distinguishes a configured 600 from the fallback: its `source` reads `queue_state` when the field is actually stored in the queue and `default_floor` when it is not, because the fallback *is* the floor and the number alone could not tell them apart.

[#per-repo-key-not-in-effect]
=== A leftover per-repo setting is reported, never honoured

Both machine-global settings once lived per-repository, so a repository may still carry a copy. A copy takes *no effect* — and rather than failing silently, Plan Marshall reports it:

* A `build.queue.max_slots` in this repository's `marshal.json` is read for the sole purpose of reporting it. `config get` returns it as `per_repo_max_slots: {value, in_effect: false}`, and *every* `build_queue acquire` carries a `per_repo_max_slots_not_in_effect` warning naming the repository path and its value, the cap actually in effect with its source, and the one-step fix. The warning repeats on every queued build on purpose: a once-off notice is one that whoever inherits the repository never saw.
* A `build.queue.upper_limit_seconds` in the main-anchored `run-configuration.json` is inert the same way. `build_queue limit get` reports it as `per_repo_value` with `in_effect: false`. The `manage-run-config build-queue-limit` verbs that used to manage it no longer exist.

To clear a leftover cap, migrate it:

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-build-server:manage_build_server config migrate
----

`config migrate` takes no flags. It copies the repository's value machine-wide *only when nothing is set there*, then removes the per-repo key. It writes the machine-global side first, deliberately: if the repository edit then fails, the recoverable state is "the value is machine-wide, the key is still present", which a re-run completes — whereas the reverse order would delete your only record of the value before it was stored anywhere.

[cols="1,1,3", options="header"]
|===
| `outcome` | `status` | What changed

| `nothing_to_migrate` | `success` | Nothing — this repository carries no per-repo key.
| `migrated` | `success` | Nothing was set machine-wide, so the value was copied there and the per-repo key removed.
| `removed_duplicate` | `success` | The machine-global side already held the *same* value, so only the per-repo key was removed; `machine-config.json` was left byte-identical.
| `refused` | `error` | *Nothing, on either side* — both files byte-identical. Every refusal reports `machine_config_modified: false` and `marshal_json_modified: false`.
| `partial` | `error` | The machine-global side is settled but the `marshal.json` edit did not commit. Re-run to converge via `removed_duplicate`.
|===

A refusal names one of six reasons. `values_differ` — the machine-global cap is set and differs from this repository's, and picking a winner is precisely what this verb declines to do, so it reports both values and both paths. `machine_config_invalid` and `machine_config_unreadable` — the machine-global file exists and is emphatically not "unset", so copying over it could discard a configured cap; repair it with `config set --max-slots N` first. `per_repo_value_invalid` — this repository's own value is not a positive integer, so copying it would install a broken cap machine-wide. `machine_config_write_failed` and `machine_config_unresolved` — the guarded write did not happen, or a concurrent writer won the race and the resulting state does not resolve to a configured cap, so the repository's key is never removed on the strength of a stale "unset".

`marshal.json` is git-tracked, so a `migrated` or `removed_duplicate` leaves your working tree dirty; each says so in its `detail`. Commit the edit. Only the one key is removed — `max_retries` and the `build.queue` block itself survive.

[#cap-disagreement]
=== Cap disagreement is reported, never reconciled

Because each process resolves the cap for itself while the queue is shared host-wide, two sessions can still admit against *different* caps — a daemon started before a `config set`, say, or a caller whose machine-config file became unreadable. Every queue entry is therefore stamped at admission with the cap it was admitted under, and each `acquire` compares its own cap against the existing stamps and reports a `cap_agreement` verdict: `agree`, `disagree`, or `unknown` (nothing disagreed, but at least one entry carried no usable stamp). The verdict always rides with the population it was computed over, so an `agree` over an empty queue is visible as such rather than reading like a clean bill of health. A `disagree` also emits one `cap-disagreement` `[LOCK]` event.

Reporting is the whole of it: the admitting caller applies its own cap, existing stamps are left as admitted, and neither value is picked as authoritative — which is why the report names no remedy command. Choosing a winner is what a per-caller cap over a shared queue cannot do correctly, and the fix is to stop having two: set the cap machine-wide with `config set`, and let the daemon pick it up on its next submit.

The queue-side result fields are tabled in full in the `manage-locks` skill contract, and the cap verbs in the `manage-build-server` one (see <<concept-crossover>>).

== PR merge and the merge boundary

The settings below govern how a plan crosses the shared merge-to-`main` boundary — the merge method, the post-CI auto-merge gate, the pre-merge rebase decision, the merge-mutex hold window, the fail-closed pre-merge review-completeness barrier, and the platform merge-queue opt-in. Concurrent plans serialize against exactly this boundary, so its settings live here with the other concurrency controls. They are step-owned params of the `default:branch-cleanup` finalize step, read/written with `manage-config plan phase-6-finalize step get/set --step-id default:branch-cleanup`.

[#merge-strategy]
=== PR merge strategy and auto-rebase

[cols="1,1,3", options="header"]
|===
| Config key | Default | What it controls

| `steps['default:branch-cleanup'].pr_merge_strategy` | `squash` | Step-owned param of `default:branch-cleanup`. The merge method the branch-cleanup step passes to `pr merge` — `squash`, `merge`, or `rebase`. Read/written via `step get` / `step set` (see xref:configuration.adoc#step-configuration[Configuration → Step configuration] § Step parameters).
| `steps['default:branch-cleanup'].final_merge_without_asking` | `true` | Step-owned param of `default:branch-cleanup`. Gates the post-CI auto-merge — `true` merges automatically once CI is green, under the cross-plan merge mutex; setting it `false` opts into being prompted before merging.
| `steps['default:branch-cleanup'].auto_rebase_threshold` | `no_overlap_only` | Step-owned param of `default:branch-cleanup`. Gates the pre-merge auto-rebase decision. `no_overlap_only` lets the auto-rebase proceed only when your branch and the base branch have not changed the same files; any file changed on both sides defers the decision to you.
| `steps['default:branch-cleanup'].merge_queue_wait_budget_seconds` | `1800` | Step-owned param of `default:branch-cleanup`. Bounds (in seconds, ~30 min) the FIFO merge-queue poll loop — caps how long branch-cleanup waits for its turn at the head of the merge queue before falling back to a last-resort prompt.
| `steps['default:branch-cleanup'].merge_hold_window` | `full_window_release_at_waits` | Step-owned param of `default:branch-cleanup`. Hold-scope mode for the merge mutex. `full_window_release_at_waits` acquires the lock before the first staleness-creating operation — the pre-merge force-push when `use_merge_queue` is `false`, the enqueue when it is `true` (that path performs no rebase) — and holds it through the CI gate, merge, and merge-CI-wait, releasing + FIFO-re-enqueueing at every operator-wait / loop-back boundary and re-validating after re-acquire. `pre_merge_only` is the legacy narrow hold (acquire only at the Pre-Merge Gate).
| `steps['default:branch-cleanup'].merge_hold_budget_seconds` | `3600` | Step-owned param of `default:branch-cleanup`. Bounds (in seconds, ~60 min) the maximum wall-clock the widened merge mutex may be held across the staleness window. Exceeding it during a legitimate wait releases + FIFO-re-enqueues the lock and escalates via a prompt, so a live-but-slow holder cannot monopolize the merge critical section.
| `steps['default:branch-cleanup'].use_merge_queue` | `false` | Step-owned param of `default:branch-cleanup`. Opt-in complement that routes the final merge through the platform merge queue (GitHub merge queue / GitLab merge train) instead of the immediate `pr safe-merge`, serializing a truly-external commit the session-scoped mutex cannot. Setting it `true` *also skips the pre-merge rebase and force-push entirely* — the queue rebases and re-tests against the latest base as its own authoritative gate, so performing one locally would duplicate that work and invalidate every quality verdict finalize already recorded against the pre-rebase HEAD. Default `false` because engaging the platform merge queue is a repo-level branch-protection change affecting all PR workflows.
| `steps['default:branch-cleanup'].pre_merge_comment_barrier` | `fail_into_loopback` | Step-owned param of `default:branch-cleanup`. Governs the fail-closed pre-merge review-completeness barrier that re-fetches bot comments immediately before merge/enqueue and blocks the merge on EITHER of two predicates: any still-unhandled comment (the final net for a comment posted after `plan-marshall:automatic-review` marked done), or any REQUIRED bot whose participation against the merge HEAD is unproven. The second predicate is not redundant — a bot that never reviewed publishes no comment, so an absent review is indistinguishable from a clean one to a pending-comment count alone. `fail_into_loopback` (default) loops back into the `plan-marshall:automatic-review` triage pipeline. `ask` stops instead and puts the decision to you, naming which comment is still unhandled or which required reviewer never reviewed the commit about to be merged, and offering three answers: *Re-triage now* (recommended) sends the blocking comments back through triage and holds the merge until they are handled; *Merge anyway with a recorded reason* merges and writes the reason you give into the plan's decision record, so the unhandled comment is on file rather than lost; *Defer merge* merges nothing now and leaves the PR for a later finalize run. The barrier gates BOTH the immediate `pr safe-merge` and the `use_merge_queue` merge-queue paths.
| `steps['default:branch-cleanup'].admin_merge_on_stuck_state` | `false` | Step-owned param of `default:branch-cleanup`. Gates the GitHub-only stuck-state `--admin` fallback inside `ci pr safe-merge` — `false` refuses the admin merge and surfaces the stuck PR to the operator; `true` permits `gh pr merge --admin` only when the PR stays `mergeable_state: blocked` past the poll timeout AND every active ruleset requirement is provably met. Orthogonal to `final_merge_without_asking` (which gates whether the merge is attempted at all).
| `steps['default:pre-submission-self-review'].drop_review_on_scope_gate` | `false` | Step-owned param of the on-by-default `default:pre-submission-self-review` step. Escape hatch for the manifest composer's scope-gating pre-filter. `false` keeps the bot-review invariant intact; `true` opts into additionally dropping `plan-marshall:automatic-review` on scope-gated plans.
|===

NOTE: All `default:branch-cleanup` step params — `pr_merge_strategy`, `final_merge_without_asking`, `auto_rebase_threshold`, `merge_queue_wait_budget_seconds`, `merge_hold_window`, `merge_hold_budget_seconds`, `use_merge_queue`, `pre_merge_comment_barrier`, and `admin_merge_on_stuck_state` — are nested under the `default:branch-cleanup` step in the `plan.phase-6-finalize.steps` keyed map, not flat phase-level fields. Read the whole param object in one call with `manage-config plan phase-6-finalize step get --step-id default:branch-cleanup`.

NOTE: The `pre_merge_comment_barrier` is the final safety net that makes leaving `re_review_on_loopback` off (its `false` default, see xref:configuration.adoc#automated-review[Configuration → Automated PR review]) safe: even when a loop-back fix commit is not re-reviewed by the bots, the barrier re-fetches and blocks on any unhandled comment before the merge. It is independent of the initial-wait settings (`review_bot_buffer_seconds`, `review_completion_poll_timeout_seconds`, and the rate-window await of <<rate-window-await>>): those bound how long the *initial* review wait polls, whereas the barrier is a distinct, always-on re-fetch at merge time — so a comment that lands after the initial wait (a late pass, or one posted once a bot's rate window reopens) is still caught.

[#merge-queue]
=== Platform merge queue (both providers)

The `use_merge_queue` opt-in (see the `default:branch-cleanup` param table above) routes the final merge through the *platform merge queue* so the platform re-tests-and-merges the PR against the latest base branch, serializing a truly-external commit (a manual `gh`/`glab` merge, a dependabot merge, a parallel remediation PR) that the session-scoped merge mutex cannot serialize on its own. It is supported on *both* providers:

* *GitHub* — the platform merge queue, configured as a `merge_queue` rule in a repository ruleset on the default branch. `pr merge-queue` engages it via `gh pr merge --auto`.
* *GitLab* — a *merge train* (a Premium/Ultimate-tier feature enabled per-project). `pr merge-queue` performs a real merge-train enqueue via `POST /projects/:id/merge_trains/merge_requests/:iid`.

Enabling it also changes what finalize does *before* the merge: the *local pre-merge rebase and force-push are skipped entirely*, and the pre-merge CI wait is downgraded to a single non-blocking snapshot. Both are redundant once a queue is in use — the platform rebases the branch onto the latest base, re-tests it, and refuses a still-red result — and performing them locally is not free. A rebase that actually replays rewrites every commit SHA on the branch, which invalidates every quality verdict finalize already recorded against the pre-rebase HEAD and makes the pipeline re-run those gates from scratch. With the queue enabled, finalize takes the branch as it stands, gates on a cheap CI snapshot, and enqueues.

==== Provisioning via `/marshall-steward`

Rather than hand-configuring the platform, use the steward's *Merge Queue* provisioning step (first-run wizard Step 13.5, or Configuration → Merge Queue in the maintenance menu). It follows a *probe → ask → configure-or-refuse* pattern and is idempotent (a re-run against an already-configured project surfaces nothing and mutates nothing):

. *Probe* the platform via `ci repo merge-queue probe`, which returns one of the shared eligibility discriminators: `eligible_configured`, `eligible_unconfigured`, `ineligible`, or `unsupported`.
. On `eligible_configured` — report and return silently; no change.
. On `eligible_unconfigured` — the repository can take a merge queue but has none, so the steward asks *once* whether to enable it, and says what each answer does. *Yes* (recommended) runs `ci repo merge-queue enable`, persists `use_merge_queue=true`, and from then on every plan's final merge is enqueued for the platform to rebase, re-test and merge — which also means finalize stops rebasing and force-pushing beforehand. *No* changes nothing on the repository, and plans keep merging directly under the session-scoped merge mutex.
. On `ineligible`/`unsupported` — refuse with an actionable message naming the remedy (GitLab tier / GitHub Administration-scope or org policy), never a stack trace.

Setting `use_merge_queue=true` directly (via `step set`) is *probe-validated at set time*: enabling it is rejected with an actionable both-remedies message when a live probe reports `ineligible`/`unsupported`. At finalize time, a merge-queue enqueue failure aborts branch-cleanup with an actionable error naming both remedies (disable `use_merge_queue`, or run the steward provisioning step) — it never silently falls back to an immediate merge.

==== Eligibility is always probed live

There is *no static per-provider capability flag* recording whether the merge queue is available — eligibility is *always* probed live against the actual repository/project state at set time and at provisioning time. The `required_status_checks` "require branches to be up to date before merging" branch-protection setting is left as an *operator choice* (recorded in the steward prompt), not forced by the provisioning step.

==== How each provider path is verified (fixture-vs-live)

The two provider paths are verified differently:

* *GitHub — fixture-tested verbs, live-eligible target.* The probe/enable verbs are unit-tested against API-shape-faithful fixtures (not the live `gh` CLI). GitHub merge queue is GA and this repository was confirmed eligible by a live platform probe, so — unlike GitLab — a real, accessible target exists: the steward provisioning exercises the verbs against the live GitHub API the first time it runs on this repo.
* *GitLab — fixture-verified only.* The GitLab merge-train probe/enable/enqueue path is verified against *API-shape-faithful fixtures only* (no live-GitLab-consumer verification is implied). The fixtures mirror the real Projects-API and merge-train response shapes so the handler logic is validated without a live GitLab instance.

[#rate-window-await]
== Review-bot rate window

A rate-limited review bot can answer a review request with a *refusal* instead of a review — CodeRabbit accepts roughly one review per hour, and its window then resets. When the refusing bot is a required one, finalize has no review verdict to proceed on, and the window it is waiting for is a shared resource: the claim co-tenants the merge-mutex store, so concurrent plans queue for the same window instead of each spending it. Whether finalize waits at all is governed by two step-owned params of `plan-marshall:automatic-review` — `review_rate_window_await`, which is off by default, and `review_rate_window_timeout_seconds`, which caps the wait at 3600 s.

*This repository arms the await.* `review_rate_window_await` is `true` here, so on a required bot's *awaitable* refusal finalize blocks for up to `review_rate_window_timeout_seconds` — 3600 s — waiting for the window to reopen, and escalates to the operator only once that budget is spent. A *structural* refusal is unaffected and never waits: the diff exceeds a ceiling the reviewer itself declares, so no reopening window would admit it, and the step escalates immediately. With the await left off, a detected refusal settles as ordinary and the step proceeds without waiting at all.

Read both params in one call:

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-config:manage-config plan phase-6-finalize step get --step-id plan-marshall:automatic-review
----

== The [LOCK] Log

Both locks emit `[LOCK]` lifecycle events — acquire, blocked, release, the reaper's stale-reclaim, and the build queue's cap-disagreement report — but they do *not* write to a plan's per-worktree work-log. Lock contention spans sessions, so the events go to a *single main-anchored global log* shared by every session, alongside Plan Marshall's other global logs under the main checkout's `.plan/`. Each line carries the lock id and, on contention, the holder and the waiter, so you can reconstruct who held what and for how long.

When two plans appear to serialize against each other — one waiting while another holds the merge mutex or a build slot — the main-anchored `[LOCK]` log is the place to look. Grep it for the waiting plan's id to find the `blocked` event and the `holder` it names.

== FAQ

=== No more builds are accepted / the queue appears stuck

When new builds stop being admitted, work through these steps in order:

1. *Inspect the `[LOCK]` events.* Open the main-anchored global lock log and find the active build ids and their `acquired` timestamps. A slot held far longer than a real build takes is the likely culprit; the `held` duration on a later `reaped-stale` event confirms it.

2. *Let the self-healing reaper clear it.* The reaper runs at the start of every acquire and every release, so the next queue operation auto-clears any active entry older than `2 ×` the adaptive <<stale-slot-threshold,`upper_limit_seconds`>> and emits a `reaped-stale` `[LOCK]` event. In most cases simply triggering another build (or releasing one) frees the wedged slot without any manual action. Read the current threshold — and the exact reclaim age derived from it — with `build_queue limit get`, which reports `reap_threshold_seconds` alongside the value.

3. *Edit `build-queue.json` as a last resort.* If a slot must be freed immediately and no queue operation is imminent, inspect the machine-global `~/.plan-marshall/build-queue.json` (the host-wide queue, overridable via `PLAN_MARSHALL_HOME`) to identify the stale active entry, then remove that entry from the `active` list. Do this only when you are certain the holding build is genuinely dead — removing a live build's entry lets a second build claim its slot.
