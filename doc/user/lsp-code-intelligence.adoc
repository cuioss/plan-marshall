`phase-5-execute` normally locates its work by reading files and edits them one `Edit` at a time. When you opt in, it can instead reach a warm language server for the two things a server does better: *locating* a symbol by coordinate (without reading the file that contains it) and applying a *verified multi-file rename* (one parser-checked patch instead of many hand-made edits).

[IMPORTANT]
====
*This is strictly opt-in, and an unconfigured project loses nothing.* If you configure no language server, execute behaves exactly as it does today — the same `Read` and `Edit` path, byte for byte. There is no default-on language server, and nothing changes for a project that never asks for one. The rest of this page is only relevant if you *want* the capability.
====

== What it gives you

[cols="1,3", options="header"]
|===
| Capability | What it does

| Locate by coordinate
| `definition`, `references`, `document-symbol`, and `workspace-symbol` return *coordinates, not file bodies* — so a leaf can find where a symbol is defined or used without reading the containing files.

| Verified rename
| A rename produces one `WorkspaceEdit` — a complete, parser-verified, multi-file patch. Its footprint is captured *from the edit itself*, it is applied, and diagnostics are re-run over exactly the touched files. A *worsened* diagnostic set fails the step and rolls the change back.

| Pre-build diagnostics
| `diagnose` surfaces unresolved imports, syntax errors, and type errors *ahead of* the build round-trip.
|===

[NOTE]
====
*Diagnostics supplement the quality gate — they do not replace it.* `diagnose` is a cheap pre-build signal for catching a broken edit early. It does not run the project's tests, linters, coverage, or full type-check, and a clean `diagnose` is *not* a green build. Always run the canonical build (`./pw verify`, or your project's resolved verify command) before treating a change as correct.
====

== Enabling it

The binding is *machine-local*, because a language server is locally-installed tooling that differs from machine to machine. It lives in the git-ignored run configuration, not in a version-controlled project file, so enabling it on your machine never changes execution for a teammate who has not.

Point a language at its installed server with the run-config `language-server` verb. For this repository's own Python surface, using https://github.com/microsoft/pyright[pyright]:

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-run-config:run_config language-server set \
  --language python --command '["pyright-langserver", "--stdio"]' --language-id python
----

`--command` is the server's argv as a JSON array. Read, list, and remove the binding with the sibling verbs:

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:manage-run-config:run_config language-server get --language python
python3 .plan/execute-script.py plan-marshall:manage-run-config:run_config language-server list
python3 .plan/execute-script.py plan-marshall:manage-run-config:run_config language-server remove --language python
----

`--disabled` on `set` keeps the binding on file but inactive — useful to turn the capability off without re-entering the command. The full schema is in the xref:../../marketplace/bundles/plan-marshall/skills/manage-run-config/standards/run-config-standard.md[run-configuration standard] § "Language-Servers Section".

== The three states you can always tell apart

The client never returns a bare empty result. Every response makes three situations distinguishable, so you can tell a *missing capability* from a *real answer*:

[cols="1,3", options="header"]
|===
| State | Meaning

| `not_configured`
| No server is configured (or it is disabled) for the language. The leaf falls back to `Read` / `Edit`. This is the state of every unconfigured project — and it costs nothing.

| `unreachable`
| A server is configured but did not start (wrong command, not installed). Carries a `reason`. The leaf falls back to `Read` / `Edit`, and the degradation is *reported*, not silent.

| `ok`
| A server ran. A result with `provider_count: 1` and an empty location list is then a *real* "found nothing" — genuinely no references, not a missing server.
|===

The `unreachable` state is why a broken configuration is a reported degradation rather than a silent one: you can tell "I never configured a server" from "the server I configured is broken", and act on each differently.

== The write side, and why it is safe

A `WorkspaceEdit` touching twenty files is a mutation nothing read. The rename path is built so that an edit nobody read is at minimum an edit the parser re-checked:

* the touched-file list is captured *from the edit*, never inferred from a later `git diff`;
* the edit is applied, then diagnostics are re-run over exactly those files;
* if the error count went *up*, the step *fails* and the change is *rolled back*.

So a rename that lands is one the language server produced and the parser re-verified; a rename that would have broken the parse never survives in the tree.
