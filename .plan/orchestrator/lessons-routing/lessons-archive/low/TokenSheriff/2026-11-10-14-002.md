# architecture --plan-id is a router flag and must precede the verb; a post-merge search through it silently scans nothing

## Problem

An executing agent ran a content search with the plan id appended after the verb:

```text
architecture search --content --pattern 'getRealm|realm\(\)|sanitiz' --plan-id jwks-key-ids-contract-pin
```

`architecture.py` declares `--plan-id` (and `--project-dir`) only at the top level. The call was rejected with `exit_code=2`, `error: misplaced_router_flag`, `flags: [--plan-id]`, and the script printed the corrected form: `architecture.py --plan-id jwks-key-ids-contract-pin search --content --pattern ...`. Two minutes earlier in the same envelope (08:45:03 and 08:45:05) the agent had issued two `architecture --plan-id ...` calls in the correct order, so the position was known but not applied consistently.

Source: script-failure cluster `plan-marshall:manage-architecture:architecture`, 1 occurrence, work-log hash `ad988d`, script-log hash `76e529`, 2026-11-10T08:48:01Z, phase 5-execute, finalize loop-back 1 while working on TASK-7.

## Solution

Place `--plan-id` and `--project-dir` before the verb: `architecture --plan-id P search --content --pattern X`, never after it. The script already gives a precise `misplaced_router_flag` hint, so the remaining fix is on the caller side: the canonical invocation the agent copies from should show the router flag before the verb.

## Side observation

After the plan worktree was removed, the same correctly ordered call returns `status: success` with `files_scanned: 0`. A post-merge search through `--plan-id` therefore silently scans nothing instead of failing. That is a fail-open read worth its own guard (an error or a warning when the resolved worktree is absent).
