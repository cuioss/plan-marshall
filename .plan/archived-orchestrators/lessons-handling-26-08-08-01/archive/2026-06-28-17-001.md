# Light-lane/documentation-only plans predictably trip the 4-plan Q-Gate assessment-coverage check because phase-3-outline produces zero CERTAIN_INCLUDE assessments by design — expected false-positive, resolve accepted

The phase-4-plan Q-Gate §2.2 assessment-coverage check requires every file
listed in a deliverable to be backed by a `CERTAIN_INCLUDE` assessment. But
phase-3-outline's **light lane** produces **zero** assessments by design — for a
bounded, documentation-only deliverable whose file changes are fully enumerated,
the light lane skips the formal scope-assessment pass entirely. The result is a
predictable, recurring false-positive: every light-lane / documentation-only plan
with an enumerated fix surface trips the §2.2 check with a "missing
CERTAIN_INCLUDE assessments for N files" finding, even though the fix surface is
already complete and correct.

This is the same genre of expected-Q-Gate-false-positive as lesson
`2026-06-21-11-001` (phase-2-refine `narrative_vs_code_validator` predictably
fires on lesson-conversion plans), but a different phase, validator, and root
cause: there the source narrative is stale-by-construction; here the assessment
baseline is empty-by-construction because the light lane never produced one.

## Root cause

The §2.2 assessment-coverage check assumes an assessment baseline exists, but it
is not **lane-aware**. The light lane legitimately produces no `CERTAIN_INCLUDE`
records, so there is nothing to back-fill — the "gap" the check reports is a
structural consequence of the chosen outline lane, not a real coverage hole. The
3-outline validator already suppresses this false-positive-flood class for its
own scope; the 4-plan Q-Gate re-raises the equivalent concern as a coverage gap
without the matching suppression.

## Recommended action

When a light-lane / documentation-only plan trips the §2.2 assessment-coverage
check:

- Triage the finding as the **expected false-positive** it is. Confirm the
  enumerated fix surface is complete and correct (a quick read of the
  deliverable's file list against the request scope), then resolve the finding
  `accepted` (or `taken_into_account`) with a reason that names the light-lane /
  zero-assessment-baseline cause. Do **not** spin up assessment agents to
  back-fill `CERTAIN_INCLUDE` records — there is no baseline to reconcile against
  and the work is pure ceremony.
- The durable fix is to make the §2.2 check **lane-aware**: skip (or downgrade to
  informational) the CERTAIN_INCLUDE-coverage requirement when phase-3-outline
  produced no assessment baseline, mirroring the suppression the 3-outline
  validator already applies. Until that lands, the disposition above is the
  standing answer.

## Evidence

Plan `fix-broken-relative-link-findings` (documentation-only, 14 enumerated
files, light-lane outline). The 4-plan Q-Gate raised
`Q-Gate: missing CERTAIN_INCLUDE assessments for 14 files in Deliverable 1`
(finding `7c1f35`). The user confirmed the 14-file fix surface complete/correct
at the 3-outline review gate; the finding was resolved `accepted` because
phase-3-outline produced zero CERTAIN_INCLUDE assessments by design, leaving no
baseline to back-fill.

## Recurrence (deep lane — scope broadened)

The same §2.2 false-positive also fires on **deep-lane, multi-module** plans, not
only light-lane / documentation-only ones. The trigger is not the lane *label*
but the **absence of a CERTAIN_INCLUDE baseline** — and a deep-lane outline can
legitimately have an empty baseline too.

Plan `arch-gate-build-command` (deep lane, multi_module, 7 deliverables across
plan-marshall / pm-dev-java / pm-dev-python / pm-dev-frontend). The 4-plan Q-Gate
raised `Q-Gate: No CERTAIN_INCLUDE assessments for any deliverable (7
deliverables, all write-replace files unassessed)` (finding `477cbd`). The
solution outline was authored with explicit per-deliverable **"Affected files:"**
lists rather than a file-by-file assessment pass, so the CERTAIN_INCLUDE corpus
was empty by design and the §2.2 cross-check was **vacuous, not failed** —
affected-file-set correctness was independently confirmed by §2.5 File Existence,
§2.3 False Positive, and §2.4 Architecture Constraints (all PASS). Resolved
`taken_into_account`; re-running phase-4-plan cannot synthesize assessments.

**Broadened disposition:** the standing answer above applies whenever
phase-3-outline produced **zero CERTAIN_INCLUDE assessments by design** — whether
that is a light-lane / doc-only plan OR a deep-lane plan that enumerated affected
files per deliverable instead of running a formal assessment pass. The durable
lane-aware fix should key off *baseline presence*, not the lane name.

## Recurrence — 2026-07-22 (arm-pytest-gates-remeasure-yardsticks) — a third disposition: file the assessments

Third occurrence, and the first where the standing "resolve accepted" answer was
**not** the right call. Plan `arm-pytest-gates-remeasure-yardsticks` (deep lane)
tripped the empty-baseline check at 3-outline (finding `1cf90a`, severity
`warning`). It was resolved `fixed` — the missing `CERTAIN_INCLUDE` assessments
were filed explicitly — rather than accepted.

The discriminator is **cheapness, not lane**: when the affected-file set is small
and already enumerated per deliverable, filing the assessments retroactively is a
few `manage-findings` calls and converts a *vacuous* evidence trail into a real
one. Accepting the finding leaves the §2.2 cross-check permanently unable to say
anything about the plan; filing the assessments makes it discriminating. The
"do not spin up assessment agents to back-fill" advice above is still correct for
its own case (large enumerated surfaces where the back-fill is pure ceremony, and
light-lane plans that never ran a discovery sweep at all) — but it is not the
universal answer.

**Refined disposition ladder**, applied in order:

1. Deep-lane plan with a *small* enumerated affected-file set → **file the
   assessments** (resolve `fixed`). A vacuous evidence trail is worth the few
   calls it costs to make real.
2. Light-lane / doc-only plan, or a large surface where the baseline is
   empty-by-construction and back-filling is ceremony → resolve
   `accepted` / `taken_into_account` naming the empty-baseline cause.

The durable lane-aware fix is unchanged: key the suppression off *baseline
presence*, and prefer downgrading to informational over hard-gating, so case 1
stays visible as a nudge rather than being silenced.
