# Scoped -Dtest=<package>.* matching zero classes fails the surefire build

A scoped per-package test verification that passes `-Dtest=<package>.*` to
the Maven Surefire plugin fails the **whole build** when the pattern matches
zero test classes — Surefire treats "no tests matched the specified pattern"
as a hard `MojoFailureException`, not a soft skip. The fix is to use a
class-name pattern (or the correct package glob) that actually resolves, or
to set `-Dsurefire.failIfNoSpecifiedTests=false` when an empty match is
acceptable.

## Context

During `recipe-refactor-to-profile-standards-module-testing` against
`cui-jsf-test-basic`, a per-package verification step invoked:

```bash
./mvnw test -Dtest=de.cuioss.test.jsf.junit5.*
```

Surefire's `-Dtest` selector is a **class-name** matcher, not a package
selector. The trailing `.*` after a package segment does not enumerate the
classes in `de.cuioss.test.jsf.junit5` — it is interpreted as a class-name
glob that resolves to nothing. The build failed with:

```
Failed to execute goal org.apache.maven.plugins:maven-surefire-plugin:3.5.5:test
(default-test) on project cui-jsf-test-basic:
No tests matching pattern "de.cuioss.test.jsf.junit5.*" were executed!
(Set -Dsurefire.failIfNoSpecifiedTests=false to ignore this error.)
```

The five `build-error` findings recorded for the run were this single
failure plus its four boilerplate continuation lines ("re-run with -e",
"re-run with -X", the Help URL, etc.) — one real defect, fanned out by the
log-line finding extractor. It auto-resolved on the next, unfiltered build.

## Root Cause

Surefire's `failIfNoSpecifiedTests` defaults to `true`. When a `-Dtest`
value is supplied, an empty match set is escalated to a build failure. The
operator's mental model ("`package.*` runs every test in the package") does
not match Surefire's selector grammar:

- `-Dtest=de.cuioss.test.jsf.junit5.*` → class-name glob, matches **zero**
  classes → build fails.
- `-Dtest='de.cuioss.test.jsf.junit5.**'` (double-star) → recurse into the
  package and subpackages → matches the classes.
- `-Dtest='de.cuioss.test.jsf.junit5.*Test'` → class-name glob ending in
  `Test` → matches the JUnit classes by convention.
- A fully-qualified class name (`...junit5.JsfSetupExtensionTest`) →
  matches exactly that class.

## Solution

When narrowing a verification to a package, prefer a pattern Surefire can
resolve — the double-star package glob or an explicit `*Test` class suffix —
and reserve the bare `package.*` form for nothing. If an empty match set is
a legitimate, expected outcome (e.g. a package that genuinely has no tests
yet), pass `-Dsurefire.failIfNoSpecifiedTests=false` so the empty match is a
skip rather than a hard failure.

## Impact

Applies to any scoped Maven test invocation that filters by `-Dtest`,
including per-package verification loops in profile-standards / module-testing
recipes that dispatch one test run per package. A single mis-shaped glob
turns a green per-package gate into a spurious red build. The failure is
self-clearing on the next unfiltered run, so it can masquerade as a flaky
build error rather than the deterministic selector-grammar mistake it is —
recognise the "No tests matching pattern ... were executed!" message as the
signature and fix the pattern, do not retry blindly.
