# Bot acknowledgment notices are filed as findings and block the gate until triaged, though comment-patterns.json exists to drop them

[SUPERSEDED]

This lesson was superseded by `2026-08-25-09-013`.

Reason: Duplicate I filed without first checking the corpus, which the standing guidance requires. 2026-08-25-09-013 covers the same defect and covers it better: it names the root cause (the content-aware layer is per-bot and only fires for a bot declaring contentless_review_markers / actionable_content_markers, so the fail-closed empty default that is right for a finding COUNT becomes a merge-blocking stall at the barrier), and it weighs two remedies, recommending that the BARRIER rather than the producer draw the distinction so the gate stops depending on an enumeration staying complete. My entry proposed only the weaker of those two. Carrying forward the delta my observation adds, so it is not lost with the stub: (1) two further phrasings observed on PR #1409 that reached the store as pending findings — 'GitHub couldn't provide a complete incremental comparison…' (the full-review fallback notice) and 'Already reviewed the last commit…' (the reply to a re-review trigger) — neither matching the approval-notice / 'Review finished' / 'Actionable comments posted: N' bodies already recorded there; (2) the cost compounds per re-review, since each loop-back that re-triggers a bot produces another acknowledgment, so a plan with several review cycles pays it repeatedly. Both strengthen the canonical lesson's case for the barrier-side remedy.
