# Documentation-only fix commits re-fire the whole head-dependent finalize cycle; add a fast path or batching

## Problem

The finalize pipeline re-fires every head-dependent step on each HEAD advance: security audit, functional review, code review, architecture refresh, verifiers, the pre-push quality gate, push, CI, bot review and Sonar. Plan-22's later fix commits were documentation-only (ADR, Javadoc and doc wording; tasks TASK-21 to TASK-28 are marked ADR-only or Javadoc-only in the decision log), yet each one went through the whole cycle. The decision log shows the cycle repeating from 15:04 (first push) through 22:38 (merge) with loop-backs at 15:54, 17:14, 18:08, 18:39, 20:28 and 21:12; the finalize orchestrator estimated about one hour per commit.

## Solution

Offer a documentation-only fast path in the finalize composer: when the delta since the last fully verified head touches only documentation and comment lines (no executable code, no test code, no build files), re-run only the steps whose result can change: doc/AsciiDoc validation, a delta functional review of the changed statements, push and CI. Skip the security audit, code-review full round, and bot re-review unless the delta touches a security-relevant file.

Alternative or complement: batch the findings of a round into one fix commit (already the practice) and defer the re-fire until the operator marks the batch complete, instead of re-firing on every commit of a multi-task fix wave.

## Impact

On a docs-and-tests plan the head-dependent cycle dominated the wall-clock time (finalize ran from 13:35 to 22:38 for a plan whose execute phase took about two hours). A fast path would cut the loop cost without weakening the gates for code changes.

## Recurrence (plan-25-epic-leftover-sweep, 2026-11-09)

Recurred on PR #883 of plan-25: every fix commit after the finalize gates invalidated the security audit, functional review, code review and pre-push gate, including wording-only commits (comments, plan text). Concrete mechanism proposed by the plan: no finalize step declares `verdict_inputs`; each head-dependent step should declare the inputs its verdict depends on (production sources, test sources, docs) and a new head should invalidate a verdict only when the diff since the verdict's head touches those inputs. The same cause made the functional review re-file a criterion the operator had already waived at a wording-only head (inbox messages 017 and 054 of plan-25).
