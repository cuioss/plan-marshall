# Sanitise every attacker-controlled field a parser returns and test each field against each property the requirement states

## Problem

The new RFC 6750 `insufficient_scope` challenge parser (`InsufficientScopeChallengeParser`, PR #888) passed `error_description` through `LogSanitizer.sanitize` (escape and length bound) but returned `realm` raw. Both values come from the untrusted `WWW-Authenticate` header of a resource server and can be up to the 8192-character header limit. `BearerChallengeParams.containsOtherControlCharacter` refuses only C0 controls and DEL, so U+0085 (NEL), U+2028 and U+2029 pass the guard and would have reached the caller through `getRealm()`. That contradicted threat entry `T-CHALLENGE-INJECTION`, which covers header injection through `WWW-Authenticate`.

The defect passed implementation, functional review and code review. CodeRabbit caught it after the PR was opened (pr-comment finding `6e3d28`, fixed by TASK-7, commit 44d5e01a), costing one finalize loop-back (iteration 1 of 5).

The fix then repeated the pattern one level down. The requirement states that `realm` and `error_description` MUST be escaped AND length-bounded. The tests covered escaping of `realm` (U+2028) and truncation of `error_description` (`shouldTruncateDescription`), but no test pinned truncation of `realm`. The bot flagged that gap on its second pass (finding `6ffcc9`, fixed by TASK-8, commit b6d413e9), costing a second loop-back (iteration 2 of 5) for a one-test commit and a full re-run of the head-dependent gates.

## Solution

1. When a parser returns several attacker-controlled fields from one header, apply the same sanitizer to EVERY returned string field. Do not sanitize only the field that is meant for display: any returned field may be logged or shown.
2. When a fix adds a field to a "MUST be X and Y" requirement, write the field x property test matrix explicitly in the same task (each field, each property, plus one Unicode line-separator case such as U+2028 per field), rather than copying only the test that motivated the fix.
3. Confirm each cell is real with a non-vacuity check: remove the sanitize call and see the test fail. TASK-8 did this; TASK-7 did not.

## Impact

Two review rounds and two re-runs of the head-dependent finalize gates for a defect that a field x property matrix written with the first fix would have closed. The same shape as lesson 2026-11-04-13-001 (a register row needs a wired test on every input path it names) applied to fields instead of paths.

## Recurrence: the thrown message is a sink too (plan-28-epic-cleanup-sweep, PLAN-28)

The same shape recurred one plan later in `DpopProofValidator`. The deliverable sanitised the DPoP proof log lines, but `rejectWith` still logged the raw proof `typ`, `alg` and `kty` at WARN (`DpopProofValidator.java:615`, Q-Gate finding d42731, found by the code review, TASK-019: sanitise the `rejectWith` log and its thrown message). CodeRabbit then found four more directly thrown DPoP rejections (thumbprint, jti replay, htm, htu) that formatted raw remote text into the exception message (review body 011567, TASK-020). A sanitisation sweep over a class that touches only the sites the request names left two follow-up loops in that run.

Rules added: (1) list every sink in the class before sweeping it: each LOGGER call AND each exception message built from remote input; (2) sanitise once at the single point that feeds both the log and the thrown message, as PLAN-28 finally did, rather than per call site; (3) pin the thrown message as well as the WARN text in tests; (4) a test oracle must mirror the full production predicate: `isEscaped` in `InsufficientScopeChallengeAttackDatabaseTest` did not cover the nine bidi controls `ErrorTextSanitizer` now escapes, so a regression of that part would have passed (finding 5da5d0, TASK-022 and TASK-024).
