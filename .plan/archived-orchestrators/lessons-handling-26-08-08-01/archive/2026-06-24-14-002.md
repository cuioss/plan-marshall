# A scoring-blend's max attainable score must be checked against the gating threshold it feeds at outline/plan time, or a gate becomes structurally unreachable

## Context

The `routing-v2-recipe-match` plan added a recipe-match scorer that blends
several weighted signals into a 0.0–1.0 confidence, and an auto-route gate that
fires when that confidence clears a threshold (`>= 0.7`). The keyword-overlap
signal — the dominant contributor for a free-form request that matches no other
signal — was capped at a **0.6 weight ceiling**.

The defect surfaced only while *authoring the tests*: for a free-form request
whose sole matching signal is keyword overlap, the maximum attainable blended
score is 0.6, which is **below** the 0.7 auto-route threshold. Auto-route was
therefore **structurally unreachable** for the exact request class it was
designed to serve. No input could ever trip the gate.

The fix (after escalating via `AskUserQuestion`) was to lower the auto-route
threshold so the gate becomes reachable for the keyword-only request class.

## Lesson

When a design blends weighted signals into a score and then **gates** on that
score, the gate's reachability is a function of two independently-authored
numbers: the **maximum attainable score** (the sum/blend of the per-signal
ceilings under the realistic best case for the target input class) and the
**gate threshold**. If `max_attainable_score < threshold` for the input class
the gate exists to serve, the gate is dead — it can never fire — and nothing in
the type system, the build, or the unit tests will flag it unless a test happens
to assert the gate fires for that class.

This is a latent design-correctness defect, not a coding bug: each number is
individually reasonable; only their *relationship* is wrong.

## How to apply

- At outline/plan time, whenever a design introduces a **scoring blend feeding a
  gate**, explicitly compute the maximum attainable score for each input class
  the gate is meant to serve and confirm it can clear the threshold. Treat
  `max_attainable_score >= threshold` (for at least the served input classes) as
  an outline-level invariant to state and check, the same way you would check a
  loop terminates.
- Be especially alert when one signal is capped *below* the threshold and is the
  *only* signal a whole input class can produce — that is the structural-
  unreachability trap. The per-signal ceiling and the gate threshold are usually
  authored in different places by different reasoning, so their incompatibility
  is invisible at each site.
- Add at least one test that asserts the gate **fires** for the input class it
  exists to serve (a positive-reachability test), not only tests that assert it
  stays closed below threshold.

## Recurrence — 2026-07-25 (repair-plan-retrospective-false-verdicts)

Same defect class — a construct prescribed at outline time that could never execute — but
the unreachability mechanism was **control-flow dominance**, not score-vs-threshold
arithmetic. This broadens the lesson from "scoring blends feeding a gate" to **any
prescribed branch or gate whose reachability at its prescribed insertion point was never
checked**.

Deliverable 3 of the plan prescribed a new branch in
`plan-retrospective/scripts/compile-report.py`, specifying its insertion point by position
in the surrounding function. As specified, that position sits **after an earlier
status-based early-return** that dominates it: on every input reaching the prescribed
location, the function has already returned. The branch would have shipped as dead code.
The phase-3-outline Q-Gate caught it (finding `787393`) and it was resolved
`taken_into_account` before phase-4-plan — the same favourable, early catch point as some
other recurrences, but the near-miss is instructive: the outline had specified *where* to
put the code without establishing that control flow reaches there.

The irony is worth recording: the plan's charter was removing vacuous/never-firing logic
from `plan-retrospective`, and its own outline prescribed a never-firing branch. A plan does
not get immunity from the defect archetype it exists to remove.

Generalization — new facet:

- **Reachability is an outline-time invariant for control flow, not only for scores.** When
  an outline prescribes inserting a branch, guard, or gate at a specific location in an
  existing function, read the code *between the function entry and that location* and
  confirm no early `return` / `raise` / `continue` / short-circuit dominates it for the
  input class the new branch exists to serve. State the reachability finding in the
  deliverable, the same way `max_attainable_score >= threshold` is stated for a scoring
  gate.
- **Specifying an insertion point by position is not the same as specifying it by
  precondition.** Prefer expressing the insertion point in terms of the state that must
  still be live at that point ("before the status early-return, while `report` is still
  unfiltered") over a positional instruction ("after the X block") — a positional
  instruction carries no reachability claim a reviewer can check.
- **The positive-reachability test rule already in this lesson applies unchanged**: add a
  test that drives an input which actually reaches and fires the new branch, not only tests
  that assert it stays inert.
