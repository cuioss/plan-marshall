# Dispatch manage-metrics reconcile-ledgers as a retrospective aspect

## Context

`manage-metrics reconcile-ledgers` exists, is documented, is read-only, and
reconciles the plan's two row ledgers (`execution.toon`'s `execution_log[]` and
each `work/metrics-dispatch-boundaries-{phase}.toon`) against each other and
against the per-phase aggregate. Run by hand against
`pre-push-gate-mutation-coherence` it returned **24 findings** over 32 union rows,
including:

- 3 × `row_absent_from_execution_log` totalling **603,578 dispatched tokens**
  (12.9% of the run's 4.68M) — dispatches that terminated and recorded their usage
  while no `record-step` row names them, so that spend is invisible to any
  `execution_log` sum.
- 17 × `row_absent_from_boundary_ledger`.
- 1 × `boundary_never_closed` for `6-finalize` (11 rows recorded, no `end_time`).
- 2 × `phase_re_entered` (`2-refine`, `3-outline`, both `close_count > 1`).

None of this reaches the compiled retrospective. `plan-retrospective/SKILL.md`'s
Step 3 aspect table has 16 rows and no `reconcile-ledgers` entry, so a report
produced by the documented workflow carries none of these findings. The
`plan-efficiency` aspect reads the same store's `totals_*` and reports a token
figure without any signal that two ledgers disagree about which dispatches
produced it.

## Root cause

A producer with no consumer. The verb was built and documented; wiring it into the
one workflow whose job is to read the plan's own instrumentation was not part of
the same change. This is the mirror image of lesson `2026-08-31-09-001` (a
`SECTION_SPEC` row with no producer) — here the producer exists and no section
consumes it.

## Proposed action

1. Add a deterministic script-backed row to `plan-retrospective/SKILL.md`'s Step 3
   table — key `ledger-reconciliation`, script
   `plan-marshall:manage-metrics:manage-metrics reconcile-ledgers`, run per the
   generic deterministic-aspect pattern.
2. Register the key in `scripts/retro_sections.py` (`SECTION_SPEC`) with a section
   heading, and add its `union_rows` / per-phase state fields to
   `ZERO_ATTRIBUTION_FIELDS` so a clean reconciliation states the population it
   reconciled rather than printing a bare zero.
3. Have `plan-efficiency` read the reconciliation's `row_absent_from_execution_log`
   token sum and qualify `totals.tokens` with it — a total that 12.9% of the
   measured spend is missing from one of its two ledgers should not render
   unqualified.

The verb takes `--plan-id` and an optional `--window-seconds`, performs zero
mutation, and already degrades honestly (`structurally_excluded` for phases the
execution log cannot hold, `not_evaluated` on an unreadable manifest), so wiring
it in adds a fact source and no new failure mode.

## Evidence

- aspect: logging_gap_analysis — ledger_reconciliation block: 24 findings, 603,578 tokens absent from the execution log
- `plan-retrospective/SKILL.md` § Step 3 — 16-row aspect table, no reconcile-ledgers row
- `manage-metrics/SKILL.md` § reconcile-ledgers — "Pure arithmetic — it reserves no judgement for itself"
