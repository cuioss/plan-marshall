# Capture the session id at finalize entry, not at retrospective order 995

## Context

Plan `plan-145-publish-the-missing-parser-seams` ran across two sessions. `status.metadata.session_ids` held only `a7a1ec30-faa9-4ebc-80a7-872ddaf2abcd` — the session that drove phases 1-5 — for the entire 6-finalize phase. The finalize session `b0bc0637-3a5f-4d62-8071-9b0d72eaf59f` was appended by `platform_runtime session capture` at **plan-retrospective Step 1**, which runs at `order: 995` — after every other finalize step had already completed.

Any finalize-phase consumer that resolves a transcript by session id therefore read a *different* session's transcript, or none at all. Two measured consequences on this run:

- `totals_billing_weighted_total: 0` with `totals_billing_weighted_total_population_count: 0` — the `Billing (cost)` column in `metrics.md` is empty for **all six phases**, so the cost-side view of a 5.36M-token plan is unavailable.
- `context_position_cost` reports `measured_rows: 0` of `total_rows: 24` and `position_multiple: unmeasured` — the four-field `message.usage` view was never attributed for any phase.

## Root cause

The session-capture seam is placed inside the retrospective workflow rather than at finalize entry. A plan that changes sessions mid-finalize — a session restart, or a resumed run — has an incomplete `session_ids` list for the whole window in which the finalize consumers run, and the list is only repaired by the very last analytical step, which is also opt-in and lane-prunable.

This is the writer-side mirror of lesson `2026-08-25-09-006` (fall back to `status.metadata.session_ids` when the forwarded id has no transcript). That fallback would **also** have failed here, because the list itself did not yet carry the right id — so the reader-side remedy is not sufficient on its own.

## Proposed action

Capture the active session id at **finalize entry** (phase-6-finalize Step 1, before any step dispatches), and re-capture on every session-restart resume, rather than at `plan-retrospective` Step 1. The capture is idempotent and cheap; the ordering is the whole defect.

Keep the retrospective's own capture as a backstop, but stop treating it as the primary write.

## Escalation — 2026-09-13, plan implement-plan-165-close-orphan-defects (epic test-quality)

This lesson asks for capture at **finalize entry**. A later run shows that is still too
late, and names the earlier boundary: `phase-1-init` logged
`session_id not captured at plan-init - phase-6-finalize will attempt a late session
capture before its hard-block abort`. The late capture DID succeed, so by this lesson's
own remedy the run was compliant — and every phase-1-to-4 window was still unmeasured,
because `manage-metrics enrich` attributes per-phase context-load by walking the session
transcript against recorded phase windows and had no anchor for the windows that elapsed
before the capture.

Measured consequence: all 18 dispatch-boundary rows across `4-plan`, `5-execute` and
`6-finalize` carried `unmeasured_columns: [input_tokens, output_tokens,
cache_read_input_tokens, cache_creation_input_tokens]`; `context_position_cost` read
`total_rows: 18, measured_rows: 0, position_multiple: unmeasured`; and `metrics.md`
rendered an empty Billing column for every phase with
`totals_billing_weighted_total_population_count: 0`.

So the remedy generalises one step earlier: capture at **plan-init**, not finalize entry.
Where the runtime genuinely cannot supply the id that early, make the consequence visible
at the point of loss — an entirely empty Billing column currently gives the reader no
indication that a missing session binding is the cause.
