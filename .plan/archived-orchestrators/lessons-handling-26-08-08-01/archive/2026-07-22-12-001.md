# Suppress repeated title-token work-log lines on unchanged token value

## Context

Retrospective of plan `propagate-parallel-plan-hardening`. The plan's `logs/work.log`
holds 265 entries. 88 of them (33 percent) are `[MANAGE-STATUS] Title token: ...`
lines emitted by `manage-status title-token set`:

- 60 consecutive byte-identical `Title token: lock-waiting` lines written at
  31-second intervals between 09:12 and 09:52 while `branch-cleanup` polled the
  merge queue.
- roughly 26 `Title token: build-busy` lines from the build-busy bracketing that
  wraps every long-running build/CI call.

Every one of the 60 `lock-waiting` lines carries the same dedup hash `5dbd97`, so
the dedup key is computed and written but never consulted to suppress a repeat.

The consequence is not cosmetic. `analyze-logs`, the retrospective's log aspects,
and any human reading the finalize narrative all have to page past a 60-line
identical block to find the two real phase-6 events that bracket it. On a plan with
a longer lock wait the ratio gets worse without bound, because the emission rate is
tied to the poll interval, not to anything that changed.

## Root cause

`title-token set` logs unconditionally at INFO on every call. A polling loop calls
it once per poll iteration with the same token value, so the number of log lines
scales with wait duration rather than with state changes. The title-token surface
is a display concern whose only interesting event is a transition
(`none -> lock-waiting`, `lock-waiting -> lock-owned`, `lock-owned -> cleared`);
steady-state re-assertions carry zero information.

## Proposed action

In `manage-status`'s `title-token set` path, compare the requested token against the
currently-persisted `title_token` before logging:

- token value changed — write the work-log line as today (this is the transition,
  and it is the line readers actually want).
- token value unchanged — perform the persist/push side effects as today but either
  skip the work-log emit entirely or drop it to DEBUG.

`title-token clear` already logs a distinguishable `Title token cleared (was: X)`
line and needs no change. The existing dedup hash can be reused as the comparison
key rather than adding new state.

Expected effect on the audited plan: 88 title-token lines collapse to roughly 8
transition lines, and work.log's signal density for phase 6 roughly triples.

## Evidence

- aspect: `logging_gap_analysis` — `LOG_NOISE` gap: 88 of 265 work-log entries
  (33 percent) are identical title-token lines, and every `lock-waiting` line
  carries the same dedup hash, so the dedup key is computed but never used to
  suppress a repeat.
- aspect: `log_analysis` — `counts.work_entries: 265`; `top_tags` peaks at
  `STATUS,44` while the untagged title-token lines outnumber every tagged category.
- source: `logs/work.log` lines 202-263 (the 60-line `lock-waiting` block) and
  lines 91-188 (the interleaved `build-busy` block).
