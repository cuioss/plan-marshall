# Hand-authored multi-line block-scalar TOON values leak as spurious top-level keys

## Context

While authoring `plan-efficiency` and `routing-decisions` retrospective fragments for
`build-decision-oracle-consolidation`, a `summary: |` YAML-style block-scalar with indented
continuation lines was written by hand into the fragment TOON file, then registered via
`collect-fragments add` and later consumed by `compile-report run`. The compiled report emerged
with 7 extra bogus `##` sections whose titles were title-cased fragments of the summary prose
(e.g. `"In Hindsight This Was The Right Call, Not Over Provisioning"`, `"Warning Line Recurs 4
Times In The Compose Log"`) sitting as siblings of the real aspect sections, and the `plan_efficiency`
JSON's own `summary` field was truncated to a quoted fragment of only the first line.

## Root cause

The TOON parser (`toon_parser.parse_toon`) does not support YAML-style `key: |` block-scalar
continuation. When a hand-authored fragment file uses that syntax, the parser reads only the
first line as the value for `summary` and then treats each subsequent indented continuation line
as an independent top-level `key: value` pair rather than folding it into the block. Because
`collect-fragments add` merges the parsed fragment dict directly under the aspect key in the
bundle without validating that the fragment's own top-level shape stayed exactly one key deep,
those spuriously-parsed continuation-line keys leak out as bundle-level siblings of the real
aspect keys. `compile-report`'s generic fallback render path (intended only for legitimate
domain-contributed aspects) then renders each leaked key as its own `##` section, since it cannot
distinguish a genuine aspect key from parser wreckage.

## Proposed action

Two independent hardenings, either sufficient alone:

1. `collect-fragments add` should validate that the parsed fragment is a single dict whose keys
   match the aspect's expected shape (or at minimum, reject/warn when the parsed fragment
   introduces unexpected keys at odd indentation depths) before merging it into the bundle.
2. Document in `ref-toon-format` (and cross-reference from every LLM-aspect reference doc under
   `plan-retrospective/references/`) that hand-authored fragment TOON files MUST NOT use
   multi-line block-scalar (`key: |`) syntax for prose fields — use a single-line quoted string
   instead. This is the practical workaround already in use and should be the documented
   authoring convention, not tribal knowledge.

## Evidence

- aspect: plan_efficiency — original `summary: |` fragment produced leaked top-level keys after
  a full init -> add -> finalize -> compile-report round trip; `compile-report`'s
  `sections_written` count was 21 instead of the expected 14 for a 13-aspect bundle.
- aspect: routing-decisions — `posture_verdict: |` (multi-line) produced the remaining leaked
  keys in the same run.
- Fix verified: rewriting both fields as single-line quoted strings and re-running
  init -> add(x13) -> finalize -> compile-report produced exactly 14 `sections_written` and 0
  `sections_omitted`, matching the 13-aspect + Executive-Summary expectation.
