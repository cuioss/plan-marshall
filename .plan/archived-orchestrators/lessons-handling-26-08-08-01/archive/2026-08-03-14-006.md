# Operator resume after a loop-back halt emits no step instrumentation at all

## Context

`content-search-seam` halted at `2026-08-03T11:30:58Z` when the finalize loop-back ceiling was breached, returning control to the operator. Work then resumed and four steps ran to completion: `branch-cleanup` (PR #1084 squash-merged via the queue), `project:finalize-step-deploy-target`, `project:finalize-step-sync-plugin-cache`, and `project:finalize-step-review-retrospective`.

All four carry terminal outcomes in `status.metadata.phase_steps["6-finalize"]`. None produced instrumentation:

| Channel | Last record before the halt | Records after |
|---------|------------------------------|---------------|
| `[DISPATCH]` work-log lines | 11:21:52Z (`automatic-review`) | 0 |
| `[STEP]` work-log lines | 09:38:03Z | 0 |
| `metrics-dispatch-boundaries-6-finalize.toon` | 11:30:48Z (17 rows) | 0 |
| `metrics-accumulator-6-finalize.toon` | 11:30:47Z (20 samples) | 0 |

Two of the four are provably dispatched despite the missing declaration: `project:finalize-step-review-retrospective` and `plan-marshall:plan-retrospective` each emitted their own `[STATUS] (plan-marshall:execution-context.X) Complete` line, which only an `execution-context` envelope produces. The envelopes ran; only their announcements are missing.

## Root cause

Step instrumentation lives in the orchestrator's normal step-iteration preamble. The operator-driven resume path re-enters finalize at a specific step without replaying that preamble, so every channel that the preamble owns stops at once. The failure is not four independent omissions but one skipped preamble.

`mark-step-done` is unaffected because it is called by the step itself, from inside the envelope. That is what makes the gap deceptive: `phase_steps` looks complete and healthy, so `phase_steps_complete` passes, while every channel that would let an auditor verify *how* those steps ran is empty.

## Consequences

1. The execution-context dispatch audit cannot distinguish "ran inline where dispatch was required" from "was dispatched but not announced". This retrospective had to fall back on the envelopes' own completion lines to resolve two of the four, and could resolve none of the other two.
2. Token accounting stops. The 6-finalize accumulator's last write is 11:30:47Z, so every post-halt step — including `branch-cleanup`, which drove a merge-queue merge, and both retrospective steps — contributes zero to the phase total. The phase figure is a floor whose shortfall is not merely unknown but unbounded.
3. `record-dispatch-boundary` termination causes stop, so the audit trail that exists to explain *why* a dispatch ended is blind across exactly the window where an abnormal halt occurred.

## Proposed action

1. Factor the step-iteration preamble (`[STEP] Executing`, `[DISPATCH]`, `record-dispatch-boundary`, `accumulate-agent-usage`) into a single entry point that every path into a step must go through, including resume. No step should be reachable except via that entry point.
2. Emit an explicit `[STATUS] Resuming finalize at step {step} after operator halt` line so the discontinuity is a recorded event rather than an inferred gap between timestamps.
3. Have the retrospective's dispatch audit treat a terminal `phase_steps` outcome with no instrumentation as a distinct `no_evidence` state, separate from `dispatch_coverage_violation` — asserting inline execution from missing evidence is itself an unqualified negative.
4. Add a test that resumes finalize mid-phase and asserts each subsequent step produced a `[DISPATCH]` line and a dispatch-boundary row.
