# Make merge-queue enqueue prove PR membership, not just the queue rule

## Context

PR #1480 was fully green — all 11 checks passing, GitHub reporting the PR mergeable, and both required reviewers (cuioss-review-bot, coderabbit) published against the exact head commit. It was nonetheless enqueued into the merge queue twice and sat through two complete 30-minute windows with nothing merging. The operator escalation identified the mechanism precisely: the enqueue call returns success on the strength of the branch's queue rule existing, not on this PR having actually joined the queue. The automation therefore could not distinguish a PR that had joined and was waiting from one that never entered at all, and burned a full hour of wall clock before a human noticed.

## Root cause

The enqueue operation's success return is unfalsifiable with respect to the thing the caller actually needs to know. It asserts a property of the branch (a queue rule is configured) and the caller reads it as a property of the PR (this PR is now queued). Those are different claims, and nothing downstream re-checks the second one, so a failure to join the queue is indistinguishable from a slow queue.

## Proposed action

After enqueueing, positively verify PR membership in the queue rather than trusting the enqueue return — query the merge-queue entry for the PR and confirm it resolves, and surface a distinct, actionable state when the PR is not found in the queue after the enqueue reported success. The waiting loop should treat "not in the queue" as a terminal condition requiring re-enqueue or escalation, not as an indistinguishable slow path that burns the full wait budget. At minimum, the enqueue return should carry what it actually verified so a caller cannot mistake the branch-rule check for a membership check.
