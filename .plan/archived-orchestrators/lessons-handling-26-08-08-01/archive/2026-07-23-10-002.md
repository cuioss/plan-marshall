# Fail-loud spec-pointer detection gated on file existence, not syntax, so a missing pointer silently fell through to plain-text handling

## Context

Caught by CodeRabbit during finalize on plan-41-phase-1-init-spec-ingestion — a
D3 defect that BOTH phase-3/4 Q-Gate AND pre-submission self-review missed.

## Symptom

The D2 file-pointer detection predicate that classifies a canonical
`implement {path}` request required the referenced file to EXIST before
treating the request as a file pointer. When the path was missing, detection
failed and the request silently fell through to the plain-text branch —
defeating D3's fail-loud intent entirely. A missing spec pointer produced a
quiet misclassification instead of a loud `spec_pointer_unreadable` failure.

## Root cause / archetype

A fail-closed/fail-loud predicate must classify by SYNTAX first, then check
existence as a separate, later step. Gating the classification itself on the
resource existing collapses the loud-failure path into a silent fallback.
This is the confident-signal-hides-a-caveat archetype (truthful-signals
epic): the absence of a loud error read as "no spec pointer" rather than
"spec pointer, but broken."

## Fix

TASK-006 reordered the check: classify a canonical `implement {path}` form
by SYNTAX alone, THEN separately check existence. A syntactically-valid but
missing pointer now routes to `spec_pointer_unreadable` instead of the
plain-text branch.

## Generalization

Any detector whose purpose is to gate a fail-loud path (existence-required
routing, format-required routing) must never make "resource exists" part of
the classification predicate itself — existence is a downstream validity
check, not a shape check. Apply this rule whenever adding a new fail-closed/
fail-loud detection boundary; a Q-Gate or self-review pass that only tests
the happy path (pointer exists) will not catch this class of defect — test
the missing-resource path explicitly.
