# Record a refuted review finding as rejected, not taken_into_account

## Context

The review retrospective for this plan corrected the reviewer false-positive rate to approximately
8.7% after discovering that two refuted CWE-78 claims had been recorded by the triage with
`resolution: taken_into_account` when both were in fact rejections. The claims were examined,
refuted as false positives, and then filed under the resolution that means the opposite.

`manage-findings` already carries the correct value. `rejected` exists precisely for a finding the
validity-verification stage refutes as a false positive, and like `fixed` and `accepted` it is
non-pending, so using it costs nothing at the gate. `taken_into_account` means the finding was
credited and folded into the work — an entirely different claim about the reviewer.

The damage is to measurement, not to the merge. Every downstream reviewer-quality figure is computed
from these resolutions, so mis-filing a rejection as an acceptance inflates the apparent accept rate
and deflates the measured false-positive rate. A reviewer that files bad findings looks better than
it is, and the corpus of evidence for tuning or dropping a reviewer is quietly corrupted. This plan
only caught it because the review retrospective re-derived the rate by hand.

## Root cause

`taken_into_account` reads, in ordinary English, as "I considered this" — which is true of a refuted
finding too. The vocabulary invites the wrong choice when the triage is deciding quickly, and nothing
downstream of the write distinguishes a refutation recorded as an acceptance from a genuine one.

## Proposed action

Two parts. First, make the triage path that refutes a finding write `rejected` rather than leaving
the resolution to free choice — a refutation has exactly one correct resolution and the code should
supply it. Second, state the distinction where the triage reads it: `taken_into_account` means the
finding was credited; `rejected` means it was refuted; the fact that both are non-pending is not a
licence to treat them as interchangeable.

## Evidence

- Review retrospective for PR #1447: corrected reviewer false-positive rate approximately 8.7%,
  reached by re-classifying two CWE-78 claims that the triage had recorded as
  `taken_into_account` when both were rejections.
- aspect: script_failure_analysis — the plan filed 3 review comments across 5 `automatic-review`
  firings; the resolution vocabulary is exercised on every one, so the mis-filing rate matters at
  small comment counts.
- Note for the orchestrator: the review retrospective also excluded the gate-delta comparison
  because the findings span four reviewed SHAs, so no single reviewed tree exists. That exclusion
  is correct and is recorded here only so it is not re-derived.
