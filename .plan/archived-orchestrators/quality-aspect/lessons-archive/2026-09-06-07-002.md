# Forward orchestration context resolved from source_id instead of a bare false

## Context

The `plan-marshall:plan-retrospective` finalize step was dispatched for plan `domain-post-plan-narrow` with `orchestrated: false` and `epic: ""` in its prompt body.

Both values are wrong. The plan's own `request.md` carries `source_id: .plan/orchestrator/operator-ux/plans/PLAN-03-domain-post-plan-narrow.md`, and the canonical detection seam returns the opposite verdict:

```text
orchestrator inbox detect --source-id ".plan/orchestrator/operator-ux/plans/PLAN-03-domain-post-plan-narrow.md"
  -> orchestrated: true, epic: operator-ux, detection: orchestrated
```

`plan-retrospective`'s Input Contract states that in finalize-step mode the dispatcher supplies `orchestrated` / `epic` and that the retrospective body MUST NOT recompute them. The retrospective therefore correctly honoured the forwarded `false` for its Step 5b branch — and routed every candidate lesson to the GLOBAL lessons store instead of the `operator-ux` epic inbox, which is the sink the orchestrator actually reads.

## Root cause

The must-not-recompute rule concentrates the resolution at a single point (`phase-6-finalize` Step 3 item 4b.a0) so that one run cannot disagree with itself. That is the right design, but it makes the single resolution point load-bearing with no downstream check: a leaf that is forbidden to recompute is also unable to notice it was handed a wrong value, so a defect there is silent by construction and lands as candidate lessons filed into the wrong corpus.

## Proposed action

1. At the finalize dispatcher's resolution point, resolve `orchestrated` / `epic` through the documented two-call seam — `manage-plan-documents request read --plan-id {plan_id} --section source_id`, then `orchestrator inbox detect --source-id "{source_id}"` — and forward the seam's verdict. A bare `false` must be the seam's answer, never a default.
2. Have the dispatcher record the resolution (source_id read, detect verdict) in the decision log, so the value a leaf is handed is auditable after the fact.
3. Keep the leaf's must-not-recompute rule as it is; the fix belongs at the producer.

## Evidence

- aspect: request_result_alignment — `orchestration_context_observation` block records `forwarded_orchestrated: false` against `detect_verdict: orchestrated` / `detect_epic: operator-ux`.
- The retrospective's own Step 5b honoured the forwarded value and recorded to the global store, which is what makes the defect's consequence concrete rather than theoretical.

## Recurrence — 2026-09-08 (sweep-preambles-shipped-accessors)

Second instance, identical in every structural respect, on a different epic.

The `plan-marshall:plan-retrospective` finalize step was dispatched with `orchestrated: false`
and `epic: ""`. The plan's `request.md` carries
`source_id: .plan/orchestrator/test-quality/plans/PLAN-135-sweep-the-preambles-the-shipped-accessors-can-now-reach.md`,
and the canonical seam returns the opposite verdict:

```text
orchestrator inbox detect --source-id ".plan/orchestrator/test-quality/plans/PLAN-135-sweep-the-preambles-the-shipped-accessors-can-now-reach.md"
  -> orchestrated: true, epic: test-quality, detection: orchestrated
```

The same `source_id` was visible to the run from its very first phase: phase-1-init's
planning-lane decision entry (`4f49cb`, 2026-09-07T15:50:41Z) records
`'plan_source': '.plan/orchestrator/test-quality/plans/PLAN-135-...'` in its signal set.
The value the dispatcher needed was in the decision log four hours before the retrospective fired.

### What this instance adds

The first instance noted that a leaf forbidden to recompute "is also unable to notice it was
handed a wrong value, so a defect there is silent by construction". This run shows the leaf CAN
notice, and what it costs to act on it. This retrospective verified the discrepancy against the
canonical seam, then still honoured the forwarded `false` — because the Input Contract's
must-not-recompute rule is unambiguous and a leaf substituting its own routing verdict would be
improvisation. Two high-confidence lessons (`2026-09-08-01-001`, `2026-09-08-01-002`) were
therefore filed into the GLOBAL store rather than the `test-quality` epic inbox, and the
discrepancy was returned to the orchestrator for re-routing.

So the defect is not silent by construction after all — it is silent by *contract*. That
strengthens proposed action 2 in particular: had the dispatcher recorded its resolution in the
decision log, the wrong value would have been auditable at the moment it was produced instead of
being reconstructed by the leaf that had to obey it.

Proposed actions 1-3 stand unchanged and remain unapplied.

## Recurrence — 2026-09-09 (close-the-runtime-slice-parametrization)

Third instance, same epic as the second, and the first one where the resolution point was not
merely wrong but **never executed at all**.

The dispatcher forwarded `orchestrated: false` / `epic: ""` to THREE consumers this run —
`plan-marshall:plan-retrospective`, `project:finalize-step-review-retrospective` and
`default:lessons-capture` — having never run item 4b.a0's two-call seam. The value was not a
mis-resolution; it was a default typed in place of a resolution. Run after the fact, the seam
answers as it did in both prior instances:

```text
orchestrator inbox detect --source-id ".plan/orchestrator/test-quality/plans/PLAN-155-close-the-runtime-slice-parametrization.md"
  -> orchestrated: true, epic: test-quality, detection: orchestrated
```

### What this instance adds

**The manifest itself contradicted the forwarded value, and nothing compared them.**
`default:emit-landing` is composed OUT of a non-orchestrated plan at compose time, yet it is
present in this plan's `phase_6.steps`. So the composer had already resolved this plan as
orchestrated and written that verdict into the manifest the dispatcher reads at Step 2 — while
the dispatcher forwarded the opposite. Two resolutions of the same fact existed in one run,
one of them derived and persisted, and no check reconciled them.

That is a cheaper guard than proposed action 2, and it composes with it: **the presence of
`emit-landing` in `phase_6.steps` is a persisted, machine-checkable claim that the plan is
orchestrated.** A dispatcher about to forward `orchestrated: false` on a manifest containing
that step is provably disagreeing with its own input and can fail loud on the spot, with no
extra call.

The consequence was the usual one: this run's lesson-shaped output — eight
`plan-retrospective` lessons plus two appended recurrences — went to the GLOBAL corpus instead
of the `test-quality` epic inbox.

Detection route differed too, and is worth recording. No leaf verified the seam this time. The
`lessons-capture` body noticed the *inconsistency* — its forwarded `orchestrated: false` against
Q-Gate finding `f504ea`, which describes the request as "an orchestrator-authored staged plan
spec" — and surfaced it as a flag it explicitly declined to verify, because the same
must-not-recompute rule forbids that body from re-issuing either call. The orchestrator then ran
the seam and confirmed it. So the second instance's finding holds and sharpens: a leaf can notice,
and a leaf that reports the discrepancy without resolving it is behaving correctly under the
contract.

Proposed actions 1-3 still stand and remain unapplied after three instances. Add:

4. Reconcile the forwarded verdict against the manifest before dispatching: when
   `default:emit-landing` is in `phase_6.steps`, `orchestrated: false` is a contradiction the
   dispatcher must not forward.
