# mark-step-done does not enforce the display_detail 80-char ASCII ceiling it documents

## Rule

`manage-status mark-step-done` accepts a `--display-detail` value that violates the
canonical ≤80-character ASCII constraint and returns `status: success`. The
constraint is documented but not enforced anywhere in the write path.

## Observation

Observed live in PLAN `shipped-guards-assume-the-meta-projects-own-layout`: an
87-character value was stored verbatim with no error.

The constraint is owned by `phase-6-finalize/standards/external-step-contract.md`
and is relied on by the finalize output renderer, so an over-long value is a real
contract breach that reaches a user-facing surface.

## Why this is load-bearing rather than theoretical

At least **three** dispatched agents in a single finalize independently discovered
that the documented Branch A `display_detail` template renders at 87 characters
with a non-ASCII em dash, and each hand-trimmed it to comply. The guard exists in
prose, and in each agent's diligence — nowhere in the write path. An agent that
did not check would have shipped the breach silently.

This is the vacuous-guard archetype at the enforcement layer: a documented
constraint with no enforcing check is indistinguishable, from the caller's side,
from no constraint at all.

## How to apply

Validate length and ASCII-ness in `_cmd_mark_step` and reject with a typed error —
the same way the verb already rejects a missing `--head-at-completion` on a
`head_dependent: true` step. That precedent is the argument: the verb already
demonstrates it can fail closed on a contract violation, so this is a gap in
coverage rather than a design choice.

Until then, treat the ceiling as caller-enforced and measure any placeholder-bearing
template against its **worst-case expansion**, never its literal form.
