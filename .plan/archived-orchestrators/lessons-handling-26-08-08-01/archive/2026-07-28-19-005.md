# plan-retrospective runs at step 17 — after branch-cleanup destroys its footprint input and before sync-plugin-cache makes the plan's own fixes live, so no plan can self-verify a finalize-pipeline fix

## Context

PLAN-10 (PR #1036, epic `test-suite-quality`). `plan-marshall:plan-retrospective` sits at
position **17** of 22 finalize steps. Two steps that determine whether it can measure anything
sit on the wrong side of it:

```
16  branch-cleanup                          <- removes the worktree (and the branch)
17  plan-marshall:plan-retrospective        <- runs HERE
18  project:finalize-step-deploy-target
19  project:finalize-step-sync-plugin-cache <- makes THIS plan's code live
```

One root cause, two independently-damaging symptoms. Both observed, neither hypothesised.

## Symptom A — runs BEFORE the cache sync, so it executes pre-fix code

The executor resolves scripts through the plugin cache. At retrospective time the cache
predated the merge. PLAN-10's D1 registered two `SECTION_SPEC` rows; the retrospective meant
to exercise them ran against the copy that lacks them:

```
$ collect-fragments add --aspect direct-gh-glab-usage
status: error
error: "Unregistered aspect key: 'direct-gh-glab-usage' … Valid aspect keys: [ …15 keys… ]"
```

Identical rejection for `execution-context-dispatch-audit`. Both fragments were produced and
both thrown away. Verified as a **staleness artefact, not a regression** — merged main carries
both rows; the cache copy's `SECTION_SPEC` ended at `permission-prompt-analysis`.

The general form is worse than the D1 instance: **a plan that fixes any finalize-time
component can never have that fix exercised by its own finalize run.** The same run showed it
for D3 — 16 steps recorded `outcome=done` against **7** `[STEP] Completed step:` lines in
`work.log`, a 9/16 (56 %) miss rate, i.e. exactly the pre-fix behaviour D3 closed. Every one of
that plan's four headline claims therefore rests on unit tests alone, while the finalize
pipeline reports green.

This is the deployment-staleness family (see `2026-07-27-08-004`, where the plugin cache
served pre-fix frontmatter and defeated the gate that would have caught it); what is new here
is that the **step ordering inside a single finalize run** guarantees it, with no cache-drift
required.

## Symptom B — runs AFTER worktree teardown, so coverage measures against nothing

**The `affected_files_*` half of this symptom is CLOSED.** `_resolve_footprint` now reports
*whether* it resolved, not merely what it resolved to, and both `affected_files_recall` and
`affected_files_exact_match` read that state through one named predicate: an unresolvable footprint
yields `inconclusive` with a named warning finding and **no percentage at all**, so a figure —
including `0%` — is emitted only from a footprint that genuinely resolved. Do not re-stage that
work, and do not re-file the "0% recall on an exact footprint" instance.

**The residue is the rest of the instrument.** `direct-gh-glab-usage` still returns `total: 0`
with `status: success` when its diff surface no longer exists — the identical
absence-coerced-into-a-signal shape, on an aspect the footprint predicate does not reach. Any other
aspect that derives a count or a ratio from a post-teardown surface has the same exposure and has
not been swept.

**A missing input reported as a zero score is a false negative wearing a number.** `0 findings`
is indistinguishable, to every downstream reader, from "measured and clean". This is a recurrence
of `2026-06-24-18-003` (a missing/unreadable input must be inconclusive, never coerced into a
signal value) — now inside the retrospective instrument itself.

## Corrective rule

**Two parts; the second is required even if the first is adopted.**

1. **The ordering half of this rule is SETTLED — do not act on it.** The retrospective already
   runs after `project:finalize-step-sync-plugin-cache` at the live ordering, and the second
   constraint ("before `branch-cleanup`") is now **forbidden**, not merely unmet:
   `plan-marshall:plan-retrospective` declares `post_run_review: true`, and a step carrying that
   fact MUST be ordered after the merge gate `default:branch-cleanup` — a derivation guard
   asserts it over the whole derived population. Moving the retrospective ahead of the gate would
   now fail that guard. The input-loss the old prescription tried to dodge by reordering is
   instead handled at the instrument (part 2): an input the gate destroyed is reported
   unmeasurable rather than measured.

   **The surviving obligation is the fallback clause.** Whenever the cache sync does not precede
   the retrospective on a given run — it is a project-local, `default_on: false` step, so it is
   absent from any run that does not register it — the retrospective must explicitly re-resolve
   its own script paths against the merged source rather than trusting the cache. That is still
   owed and is what keeps Symptom A live.
2. **A coverage aspect whose input is absent MUST report `unavailable`, never `0`.** Enacted for
   `check-artifact-consistency`'s `affected_files_*` pair (see Symptom B). Still owed for
   `direct-gh-glab-usage`'s diff surface and for every other aspect that derives a count or ratio
   from a surface the merge gate can destroy — derive that population rather than patching the one
   named aspect. The distinction between "clean" and "not measured" must survive into the report.

## Impact

Every plan that runs the opt-in retrospective. Symptom A additionally means **no plan can
self-verify a finalize-pipeline fix** for any step ordered ahead of the cache sync, which is
precisely the class of work this epic keeps producing. Symptom B's surviving half silently
understates coverage on every plan for the aspects still unswept, and the understatement is
largest for the plans that changed the most files.

## Recurrence — 2026-08-03 (content-search-seam)

PR #1084. Confirms both halves of Symptom B independently, on a plan whose worktree
`branch-cleanup` had already removed before the retrospective ran.

**The closed half held.** `check-artifact-consistency` returned exactly the prescribed shape —
no percentage was invented from an absent footprint:

```
affected_files_recall,inconclusive,"Plan footprint could not be resolved (no live worktree diff
  and no modified_files key) — recall is unmeasurable, not 0%"
affected_files_exact_match,inconclusive,"… the comparison substantiates no verdict"
```

Both emitted paired `warning` findings and `details.footprint_resolved: false`. Recorded as a
counterexample: the fix works. (The true figures, recovered here by hand from merge commit
`714130bdb`, are recall 1.00 and precision 1.00 over 37 files — so the aspect correctly declined
to guess even though the guess would have been right.)

**The residue reproduced verbatim, and is wider than one aspect.** Two aspects returned a
clean-looking zero from a surface that no longer exists:

```
aspect: direct-gh-glab-usage    status: success   counts.total: 0   findings[0]
aspect: wrapper-tangle          status: success   counts.total: 0   findings[0]
```

`wrapper-tangle` is a **domain-contributed** aspect (`pm-plugin-development`, merged after the
fixed table via `provides_retrospective_aspects()`), which sharpens part 2 of the corrective
rule: the unavailable-not-zero contract cannot be discharged by sweeping the built-in aspect
list, because domain bundles contribute post-teardown-surface aspects the core list does not
enumerate. The population to derive is *every registered aspect that reads a diff surface*,
including extension-point contributions, and the contract belongs at the extension point so a
new domain aspect inherits it rather than re-implementing it.

**Symptom A did not reproduce on this run.** `project:finalize-step-sync-plugin-cache` completed
at version 0.1.1291 before the retrospective dispatched, so the fallback clause was not
exercised. Absence of the symptom here is not evidence the fallback works — it was never
reached.
