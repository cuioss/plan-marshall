# Documentation-only deliverables need skills_by_profile.documentation, not .implementation (which does not exist for the documentation domain)

A `documentation`-domain module's architecture descriptor exposes
`skills_by_profile.documentation.*` — it has no `skills_by_profile.implementation`
key. When `phase-4-plan` allocates a task for a documentation-only deliverable
and looks up the module's skills under the generic `implementation` profile
(the default profile name used for code-change deliverables), the lookup
resolves to an empty list and the task is created with `skills: []` — silently
losing the documentation-specific skill set (`ref-asciidoc`, `ref-documentation`,
`ref-narrative-styles`, the documenter persona, `ref-code-quality`) the task
actually needed.

## Where it surfaced

Plan issue-426's `phase-4-plan` Q-Gate flagged: "Module documentation has empty
skills_by_profile.implementation -- task created with skills: []." caught at
planning time, before execution. TASK-005 (the documentation deliverable —
updating `doc/architecture/gateway.adoc` and
`doc/reference/configuration.adoc`) was corrected by switching the profile
key from `implementation` to `documentation`, which populated the task's
skills with `pm-documents:ref-asciidoc` / `ref-documentation` /
`ref-narrative-styles` plus the documenter persona and `ref-code-quality`.

## Root cause

Task-skill resolution defaulted to the `implementation` profile key
uniformly across deliverable types, without branching on whether the
deliverable is a documentation-only change. The `documentation` domain
module's descriptor never populates `skills_by_profile.implementation`
(there is no "implementation" concept for a docs-only module) — only
`skills_by_profile.documentation` is meaningful there. A profile lookup that
does not account for domain-specific profile-key naming silently degrades to
an empty skill set instead of erroring, which is what let the gap through to
the Q-Gate rather than failing loudly at allocation time.

## Fix applied

Corrected the task's profile key from `implementation` to `documentation`
before dispatch, so the task inherited the module's actual documentation
skill set.

## How to apply (generalizable)

When allocating a task for a deliverable whose domain is `documentation` (or
any other non-code domain with its own profile namespace), resolve skills
via that domain's own `skills_by_profile.{domain}` key — never default to
`skills_by_profile.implementation` for a domain that has no implementation
concept. Before dispatch, confirm the resolved `skills[]` list is non-empty
for the deliverable's actual profile; an empty `skills: []` on task creation
is itself the Q-Gate signal that the wrong profile key was queried — treat it
as a hard planning-time error to check, not something to defer to execution.
