# list resolves a worktree-resident plan that read then reports file_not_found

## Context

Running Gate 2 of the lesson-creation policy (the active-plan check) from the main checkout, `manage-status list` returned five active plans and **told me where each one lives**:

```text
plans[5]{id,current_phase,status,location}:
  NO_PLAN,unknown,in_progress,current
  domain-glob-seeding,6-finalize,in_progress,current
  every-module-counts-and-the-campaign-can-finish,6-finalize,in_progress,worktree
  plan-145-publish-the-missing-parser-seams,6-finalize,in_progress,current
  unreviewed-merge-gate-holes,6-finalize,in_progress,worktree
```

Reading either of the two `location: worktree` rows then failed:

```text
manage-status read --plan-id unreviewed-merge-gate-holes
-> status: error / error: file_not_found / message: status.json not found

manage-plan-documents request read --plan-id unreviewed-merge-gate-holes --section summary
-> status: error / error: document_not_found
```

So `list` can resolve the plan directory well enough to report its checkout, but `read` cannot reach it, and neither verb offers the cross-checkout opt-in that `manage-findings` already ships as `--any-checkout` (declared on `list`, `get`, `qgate list`, `assessment list`, `assessment get`).

## Root cause

`manage-status list` performs cross-checkout discovery (that is where `location` comes from), while `manage-status read` resolves cwd-relatively only. The two verbs disagree about the population they can see, so any workflow that **enumerates with `list` and then reads per plan** is structurally unable to complete for worktree-resident peers.

The blast radius is not cosmetic. On this run it blocked Gate 2 of the lesson-creation policy for 2 of 5 active plans, which forced one otherwise-high-confidence candidate ("Trigger-B bot selection never fired the blocking required bot") to be **held rather than filed** — because the unreadable plan `unreviewed-merge-gate-holes` plausibly covers that exact root cause, and the fail-closed rule forbids reporting a check that could not look as clean.

## Proposed action

1. Add `--any-checkout` to the read verbs of `manage-status` (`read`, `metadata`) and `manage-plan-documents` (`request read`), resolving through the existing `git-workflow locate-plan-checkout` seam — exactly the surface `manage-findings` already implements, including its read-only restriction so a cross-checkout read never grants write authority.
2. Until then, `manage-status read`'s `file_not_found` for an id that `list` reported with `location: worktree` should name the checkout that holds it, rather than reporting a bare not-found. `list` already knows the answer.
3. The lesson-creation policy's Gate 2 should state what a caller does when the active-plan population is only partially readable — the fail-closed disposition (hold the candidate, report the coverage gap) rather than filing on a partial scan.

- Direct reproduction, twice: `manage-status read` and `manage-plan-documents request read`, both `not_found` for an id `list` had just resolved
- Precedent for the remedy: `manage-findings` `--any-checkout` (five read verbs, read-only by construction)
