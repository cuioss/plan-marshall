# Shared test-helper module needs BOTH sys.path and mypy_path registration under explicit_package_bases

## Context

Observed during phase-4/5 of `refactor-test-suite-pytest-standards` while
consolidating scattered input-validation test fixtures into a single shared
module under `test/_shared/`. Moving the fixtures made them bare-importable
for pytest (pytest's own rootdir/conftest-based collection found them fine),
but broke `mypy` test-compile for every importer.

## The bug

The project's mypy configuration uses `explicit_package_bases`. Under that
mode, mypy derives a module's top-level dotted name purely from walking up
from the file's directory to the nearest ancestor that is NOT a valid Python
package-base candidate (no `__init__.py`, or a name mypy's crawl stops at —
a hyphen in the directory name is one such stop condition). `_shared` is a
syntactically valid Python identifier, so mypy's package-base crawl walked
straight past `test/_shared/` and named the module `test._shared.*` instead
of treating it as a bare top-level import target. All 19 bare importers
(`from _pm_input_validation_fixtures import ...`-style imports) failed
test-compile with `import-not-found`, even though `pytest` itself collected
and ran every test successfully — the two tools resolve import identity by
different mechanisms.

The pre-existing hyphenated `test/<bundle>/` directories (e.g.
`test/plan-marshall/`) never needed any special handling because a hyphen in
the directory name is NOT a valid Python identifier, so mypy's package-base
crawl stops there automatically and treats the hyphenated directory as the
package-base boundary. `test/_shared/` has no such stop signal.

## Root cause

A shared test-helper module reachable via `sys.path`/pytest's rootdir
insertion (bare-importable at test-run time) is a **completely separate
registration** from being reachable via mypy's `mypy_path` (a top-level
importable module at type-check time). Registering one does not register
the other. The failure mode is invisible until a test-compile / mypy pass
specifically runs against the moved module — a plain pytest run gives no
signal that mypy will fail.

## Corrective rule — do X instead of Y

- **Y (avoid):** relying on pytest's own import mechanics (rootdir insertion,
  conftest-based `sys.path` manipulation) as evidence that a shared
  test-helper package is fully wired for the whole toolchain. It only proves
  the pytest side.
- **X (do):** when introducing (or relocating fixtures into) a bare-import
  shared test-helper directory whose name is a valid Python identifier
  (no hyphen), explicitly add it to `mypy_path` in `pyproject.toml`
  alongside whatever makes it pytest-importable:

  ```toml
  [tool.mypy]
  mypy_path = ["test/_shared"]
  ```

  This makes `_shared` itself the package-base mypy anchors on, so
  `_pm_input_validation_fixtures` and its siblings resolve as top-level
  modules instead of `test._shared.*`.
- **Signature to recognize this defect class:** pytest collection/run is
  fully green, but a scoped mypy / test-compile pass on the SAME test files
  reports `import-not-found` for every importer of a shared helper module
  that was just moved or newly introduced under a bare (non-hyphenated)
  directory name.
- **General rule:** any new bare-importable shared test-helper directory
  under `explicit_package_bases` needs BOTH registrations — pytest-visible
  (rootdir/conftest) AND `mypy_path` — verified independently, because a
  hyphenated sibling directory's silence on this issue is not evidence the
  bare directory is exempt; the hyphen is precisely what exempted it.

## Scope

Applies to any Python project using mypy `explicit_package_bases` that
introduces or relocates a bare-identifier (non-hyphenated) shared
test-helper directory. Hyphenated `test/<bundle>/`-style directories are
unaffected because the hyphen itself stops mypy's package-base crawl.
