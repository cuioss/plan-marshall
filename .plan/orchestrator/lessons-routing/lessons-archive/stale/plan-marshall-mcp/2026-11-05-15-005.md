# foreign_pr_gate assumes a feature/{plan_id} branch in every foreign repository

Plan `question-loop-run-follow-up-measurement` (PR #114) could not be archived through the
pre-archive foreign-PR landing gate, although every foreign change it made had landed as
intended. `foreign_pr_gate check` returned `error: foreign_landing_indeterminate` and named two
unresolved rows:

- `plan-marshall-documentation`: the landing state "Could not resolve the tip SHA of branch
  'feature/question-loop-run-follow-up-measurement'". The docs change used the branch
  `docs/question-loop-follow-up-measurement` and landed as PR #144 (merged as 2071fbcc). The
  project's own rule names that branch shape, so the gate's `feature/{plan_id}` assumption
  can never match it.
- `plan-marshall-telemetry/question-loop-follow-up/README.md`: "repository root not resolvable".
  The evidence store is a pushed branch (`question-loop-follow-up`, bf129e2a) that by design
  never gets a PR, and the declared path names the branch as if it were a directory.

The gate fails closed and has no override. The operator archived over it, and the gap is in
the plan's decision log.

Proposed fix:

1. Classify a foreign repository on the branch its deliverable actually pushed, from the
   change ledger or the commit, instead of `feature/{plan_id}`.
2. Accept a merged PR found by head branch as `landed`.
3. Let a deliverable declare a PR-less landing form (an evidence-store branch) that the gate
   reads as `pushed_by_design`, not `pushed_no_pr`.
4. Add a recorded operator override, like `manage-status loop-back close`, so a
   mis-modelled repository does not force archiving past the gate by hand.
