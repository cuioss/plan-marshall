# Detector/parser test fixtures must mirror the post-normalization production data shape, or a boundary-anchored regex passes tests yet is dead in production

A line-start-anchored regex marker (`^…` under `re.MULTILINE`) in a PR-comment
detector was validated by a unit-test fixture that fed the detector RAW,
newline-bearing comment bodies. The test was green. In production, however,
`fetch_pr_comments_data` flattens every comment body — newlines are collapsed
to spaces — **before** the detector runs. The `^`/line-start anchor therefore
never matched a real comment: the marker was green-in-tests and dead-in-prod.
The fixture masked the defect because it presented the *pre-normalization*
data shape, not the shape the detector actually sees at runtime.

## Root cause

The test fixture and the production caller disagreed on the data shape at the
detector's input boundary. A parser/detector consumes whatever the upstream
normalization pipeline emits, not the "natural" raw form of the source. When a
fixture is hand-authored in the raw/convenience shape, any regex feature that
is sensitive to that difference — line anchors (`^`/`$`), `re.MULTILINE`,
whitespace classes, newline-vs-space boundaries — can pass the test while
being structurally incapable of firing in production. The green test provides
false assurance and the defect ships until an external reviewer notices the
marker can never trigger.

## Corrective action

- **Fixtures for a detector/parser MUST mirror the PRODUCTION data shape** —
  the post-normalization form the code actually receives — not a pre-normalization
  convenience shape. If production flattens newlines to spaces, the fixture
  must be a flattened, space-joined string.
- Prefer routing fixtures through the **same normalization function** the
  production caller uses (e.g. build the fixture by calling the real
  `fetch_*`/normalize helper, or a shared helper that applies the identical
  transform) so the fixture shape can never silently drift from production.
- When a detector relies on a boundary-sensitive regex feature (`^`, `$`,
  `re.MULTILINE`, newline/space distinctions), add an explicit assertion that
  the marker fires against a **normalized** input, and a negative assertion
  that documents the normalized shape — so the anchor's viability is tested,
  not just its syntax.

## Recurrence signature

Green unit test for a regex/string detector + external reviewer (PR bot, human)
reporting "this marker/branch can never match real input" → suspect a
fixture-shape vs production-shape mismatch at the input boundary. This is a
whole *class* of masked defects: any test whose fixture skips a normalization
the production path applies will over-report coverage for boundary-anchored
matching logic.
