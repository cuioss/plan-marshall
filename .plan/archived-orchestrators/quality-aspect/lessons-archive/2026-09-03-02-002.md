# ci pr view returns no body field, forcing a gh bypass on any PR-body edit flow

## Context

Plan-170 shipped a PR whose `## Intent` section had been truncated mid-sentence at the 1492/1500-char budget. Repairing it required reading the current PR body, editing the section, and writing the result back. The write half worked correctly through `ci pr edit`. The read half did not: `ci pr view` returns PR metadata but carries no `body` field, so there was no way to fetch the text being amended through the abstraction.

The run reached for `gh pr view 1385 --json body` directly, twice, and then self-reported it as a hard-rule violation (`decision.log` `34f7ec`).

## Root cause

The CI abstraction covers PR body *writes* but not PR body *reads*. That is not merely an omission of convenience: `CLAUDE.md` makes routing through the abstraction a hard rule with no exception, so an edit flow — which structurally must read what it amends — has no compliant path. The rule and the API disagree, and the agent is left choosing which to break.

The violation was self-reported rather than caught, and the retrospective's own `direct-gh-glab-usage` detector reported zero (see lesson 2026-09-03-02-001), so nothing would have surfaced it automatically.

## Proposed action

- Add a body-returning read to `plan-marshall:tools-integration-ci:ci` — either an `--include-body` flag on `pr view`, or a dedicated `pr body` verb. The GitHub provider already shells `gh pr view --json`, so the field is one key away; mirror it in the GitLab provider.
- Prefer returning the body on the existing verb behind a flag, so callers do not have to know which of two verbs to reach for.
- Once the verb exists, `pr_intent_section`'s edit path (see the sibling defect where `render` appends rather than replaces) can read-modify-write entirely inside the abstraction.
