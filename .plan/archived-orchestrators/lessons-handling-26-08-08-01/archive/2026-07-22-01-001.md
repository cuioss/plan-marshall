# A value read from a self-rewriting learned store is not ground truth — outline cited an adaptive timeout that was already stale at Q-Gate time

## Symptom

Phase-3-outline authored an Overview section headed as a **disk-verified ground truth table**. One row asserted that the outer deadline for the `module-tests` canonical command key was `232s`. The Root Cause narrative and a deliverable success criterion both repeated the `232-vs-300` figure as the load-bearing arithmetic of the defect being fixed.

The value HAD been read off disk. It was correct when read. By the time the 3-outline Q-Gate re-read the same key — the same session, hours later — it returned `216`. Nothing was wrong with either read.

## Root cause

The key lives in the adaptive/learned timeout store, which `timeout_set` rewrites after **every** build: a weighted average on success, a doubling on timeout. The value is therefore a *sample of a moving quantity*, not a fact about the codebase.

The failure is not "the outline did not verify its claim" — the usual outline defect. The outline DID verify it, against the genuine source of truth, and got the right answer. The failure is that **verification confers no durability when the source rewrites itself.** A disk read of a learned store has a shelf life of one build. Labelling that read "ground truth" and then reasoning from the literal number silently converts a volatile observation into a premise, and every downstream artifact that quotes the number — narrative, success criteria, doc prose, and worst of all test fixtures and code constants — inherits an expiry date nobody recorded.

Here the load-bearing inequality (`learned outer deadline < 300s pytest inner backstop`) still held at `216`, so no deliverable was invalidated. That is luck, not design: the store doubles on timeout, so a single timed-out run would have pushed the same key past `300` and inverted the very relation the plan existed to fix — while the outline still asserted `232`.

## Corrective action

1. **Classify every cited value by stability before writing it into an outline.** A value is STABLE if changing it requires a code edit (a named constant, a config literal, an ini setting). A value is VOLATILE if any runtime path writes it back (learned timeouts, duration estimates, recurrence counts, `last_seen` stamps, cached measurements). Only STABLE values may be presented as ground truth.
2. **State the inequality, never the sample.** Argue from the stable bounds that bracket the volatile value — in this plan: the `MIN_TIMEOUT` floor, the `PYTEST_OUTER_FLOOR_SECONDS` constant, and the pytest ini `timeout`. The claim "the learned deadline sits below the inner backstop" survives drift; the claim "the learned deadline is 232s" does not.
3. **Never encode a volatile value as a literal** in code, in a test fixture, or in documentation prose. A test that pins a learned figure fails on the next build for reasons unrelated to the behaviour under test. Where a test needs the value, stub the getter and treat the return as an arbitrary fixture, not as a disk-read figure.
4. **When a volatile observation must appear at all** (as motivating evidence), label it explicitly as a volatile sample, name the writer that rewrites it, and state that it may not be encoded anywhere. Do not put it in a table headed "verified".

## Recurrence signature

An outline that presents a numeric value as verified/ground-truth, where re-reading the same key later in the same plan returns a different number, and where no code changed in between. The tell at authoring time is simpler and catchable without a re-read: **the value's source has a writer.** If you can name a function that writes the key back (`timeout_set`, an estimate updater, a counter bump), the value is volatile and must not be quoted as a fact.

## Evidence

- Plan `build-timeout-truthful-status`, 3-outline Q-Gate finding `063d24` (`request_alignment`): "outline cites a volatile learned timeout 232s that is already stale on disk at 216s".
- Remediation resolved the finding by de-grounding the figure across all four narrative sites: the ground-truth table was replaced with a stability-annotated table carrying only the stable bounds plus an explicit volatile row; the defect was restated as an inequality; the `232`/`216` observations survive only as a labelled illustrative aside stating neither may be encoded; a deliverable success criterion was reworded to "no learned value whatever it drifts to"; and a new success criterion required the drift guard to hard-code no learned figure.
