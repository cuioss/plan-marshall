# Counterfactual/replay checks must treat a missing/unreadable input as inconclusive, never coerce it into a signal value

**Context:** `track-selection-accuracy-audit` plan (2026-06-24). The plan added a new `check_track_selection_accuracy()` retrospective check to `.claude/skills/audit-archived-plan-retrospectives/scripts/audit.py`. The check is a *counterfactual replay*: it reconstructs the "correct" planning track each archived plan would have routed to, by re-deriving the routing signals from the archived plan's realized inputs (one of which is `request_concrete`, re-derived from the plan's `request.md` via the S5 regex constants imported from `_cmd_planning_lane.py`), then compares that counterfactual against the track the plan actually ran.

## Symptom

CodeRabbit flagged a Major correctness bug (commit `873b23`) in the new check code: when the archived plan's `request.md` was **missing or unreadable**, the code path fed that absence straight into the S5 "vague request" branch, yielding `request_concrete = False`. A `False` here is a *real signal value* that pushes the counterfactual toward the deep/complex track. So a plan that had simply lost its `request.md` (or whose file was unreadable) could be reported as **UNDER-TRACKED** — a fabricated verdict driven by a missing input rather than by any realized signal. The check's own outline and unit tests covered the happy path and the populated-vs-vague cases, but **never the missing-input degradation case**, so nothing in-run caught it.

Two further robustness gaps in the same change were also caught by review rather than by our tests: a broad bare-`except`-style catch around the router import (swallowing real import errors), and docstring drift versus the actual behavior.

## Root cause

A counterfactual / replay check conflated two distinct conditions into one signal value:

- **"the input is present and says X"** — a real signal value (`request_concrete = False` because the request genuinely reads as vague).
- **"the input is absent / unreadable"** — *no signal at all*; the check cannot know what the request said.

The code mapped the second condition onto the first (`missing request.md → request_concrete = False → vague`). Once absence is coerced into a real signal value, that value flows into the verdict computation and produces a confident-but-fabricated verdict (here, UNDER-TRACKED) for what is actually an inconclusive case.

This is the inverse failure shape of "silent-degrade-to-default" config reads (lesson `2026-04-..` build-config require_wrapper): there, a missing key degraded to a benign default and produced *no* signal; here, a missing input degrades to a *positive, verdict-driving* signal and produces a *wrong* signal. Both share the lesson "missing input must not be silently mapped onto a valid value," but the replay-check case is more dangerous because the coerced value actively manufactures a false finding.

## How to apply

- **In any counterfactual/replay/audit check that re-derives signals from a stored input, treat a missing or unreadable input as INCONCLUSIVE — never as a signal value.** When the input the check depends on (a file, a metadata key, a referenced artifact) is absent or unreadable, the check must short-circuit to an explicit `inconclusive` / `skipped` / `insufficient-data` verdict and surface *why*, rather than feeding the absence into the signal-derivation path. A verdict is only valid when every input it depends on was actually read.
- **Distinguish absence from a real value at the read boundary.** Re-deriving `request_concrete` (or any signal) from `request.md` requires three-valued logic at the boundary: present-and-concrete, present-and-vague, and absent/unreadable. Collapsing the third state into either of the first two is the bug. Return a sentinel (e.g. `None`) for "could not read," and have the verdict computation propagate inconclusive rather than picking a default branch.
- **Test the missing-input degradation case explicitly.** The check's test matrix MUST include a case where the depended-on input is missing/unreadable, asserting the check emits inconclusive (not a confident verdict). Happy-path + populated-vs-vague coverage cannot detect coerced-absence; only a deliberate missing-input case can.
- **Don't catch broad on a re-derivation import.** Importing the routing helper (`evaluate_signals_pure` + S5 regex from `_cmd_planning_lane.py`) with a broad bare-except masks a real `ImportError`/`AttributeError` and turns a structural breakage into a silently-degraded check. Let import failures propagate (or catch the specific exception and surface it), so the check fails loud instead of silently producing wrong verdicts.

## Impact

Affects every audit/retrospective check that *replays* a routing or scoring decision against archived inputs — not just `check_track_selection_accuracy`. Any such check that reads a stored artifact and re-derives a signal from it can fabricate a verdict when the artifact is missing. The corrective rule (missing input → inconclusive, with an explicit missing-input test) generalizes to the whole counterfactual-check family in `audit-archived-plan-retrospectives` and to any future replay-style audit logic.

## Recurrence — 2026-07-09 (plan-11-audit-check-refresh)

The same audit.py input-robustness family recurred at the **I/O read boundary**, one step earlier than the signal-derivation coercion above. `gemini-code-assist` flagged **five** distinct real defects in `audit.py` where an archived-plan input read was **unguarded against `OSError` / malformed input** — the reads degrade (crash or silently mis-behave) when the archived plan's file is unreadable or its JSON/content is malformed, rather than short-circuiting the affected check to inconclusive. Phase-5 `module-tests` (pytest) passed over all five: the test matrix exercised the happy path and populated cases but **never drove the degradation path** (unreadable file, malformed JSON), so nothing in-house caught them — only the adversarial review bot did.

This **broadens the lesson from "missing input coerced into a signal value" to the whole read boundary**: in `audit-archived-plan-retrospectives`, every archived-plan input read (open/parse of `request.md`, `status.json`, metrics/findings artifacts) MUST be wrapped so `OSError` **and** malformed-content (`ValueError` / `JSONDecodeError`, remembering `UnicodeDecodeError` is a `ValueError`) both route the owning check to an explicit `inconclusive` / `skipped` verdict — never a bare read that propagates a crash or a coerced value into the verdict. This is the read-boundary sibling of the exception-set-symmetry rule (`2026-06-30-20-001`).

**Recurring test-coverage gap (the load-bearing part):** happy-path module-tests over archived-plan input structurally cannot surface these — a boundary guard's absence is invisible unless a test feeds an unreadable/malformed artifact. The audit-check test matrix MUST include, per check, an unreadable-file case and a malformed-content case asserting an inconclusive verdict; otherwise the unguarded boundary ships and only review catches it. Treat "review bot flags a missing OSError/JSON guard in `audit.py` that all in-house gates passed" as the recurring signature.
