# SecureRandom in native-image code: use a per-instance field, not static and not per-call

## Problem

In plan-05-jwe-ecdh-es, `JweDecryptor` (token-sheriff-validation, `validation/jwe/`) held a `private static final SecureRandom`. CI failed in the GraalVM native-image build: a `SecureRandom` instance created during image build-time class initialization gets baked into the image heap, and native-image rejects it. TASK-004 ("Fix native-image build: remove static SecureRandom from JweDecryptor") fixed it.

The obvious alternative, creating `new SecureRandom()` inside the method for each call, trips Sonar rule java:S2119 ("Save and re-use this Random").

## Rule

When a class in a module that ships into a Quarkus/GraalVM native image needs a `SecureRandom`:

- Do NOT use a `static` field. It is initialized at image build time and breaks the native build.
- Do NOT create one per call. That trips Sonar java:S2119.
- DO use a per-instance (non-static, `final`) field, created in the constructor or at the field declaration. It is created at runtime, reused across calls, and passes both the native build and Sonar.

## Detection

A local `./mvnw verify -Ppre-commit` does not catch this. Only the native-image CI job does. Check any new `static ... SecureRandom` (or other build-time-initialized entropy or crypto state) in token-sheriff-validation before pushing.
