# Fix every Sonar finding immediately: one throwing call per assertThrows lambda, and a write-time suppression where try-with-resources would block

## Problem

New JUnit tests in plan-03 (PR #833, `AccessTokenCacheTest`) drew two Sonar findings that were seen only in the post-push round-trip, which forced a loop-back from finalize to execute: `java:S5778` (more than one possibly-throwing call inside an `assertThrows` lambda) and `java:S2093` (try/finally on an executor where try-with-resources was expected).

## Solution

Fix every tool finding immediately, in the task that produced it, and write new tests so the finding cannot arise. Inside `assertThrows` lambdas keep exactly one call that can throw and build arguments and fixtures before the lambda. For an `ExecutorService` where try-with-resources would block (`close()` waits for termination, for example with a placeholder one-day scheduled task), keep `shutdownNow()` in `finally` and add `@SuppressWarnings("java:S2093")` with a one-line reason at write time. Suppression is the exception, in the rule's own correct syntax with a stated reason, never a way to defer the finding.

## Impact

A finding that is only fixed after the push costs a full loop-back through finalize, a new CI run and another review round.
