# Dependabot config: verify review-bot claims before stripping working config; scope every accepted-risk 'ignore' with 'versions'

When editing `.github/dependabot.yml`, local verification (lint + unit tests)
gives ZERO coverage of the Dependabot schema, so review bots become the only
gate — and one of them was wrong. On PR #362 the automated-review step acted on
two bot comments: one was a genuine improvement, the other was incorrect and
stripped valid, pre-existing configuration that had to be reverted.

## Pitfall 1 — do NOT blindly apply review-bot claims about config validity (`cooldown` IS supported)

A review bot (gemini-code-assist) claimed the `cooldown:` block was an
"unsupported" Dependabot key, and the automated-review step removed it from ALL
`updates:` entries — including the pre-existing maven entry that had carried
`cooldown` on `main` for a long time.

That claim was **false**. `cooldown` is a documented, supported Dependabot
version-update option (`default-days`, `semver-major-days`, `semver-minor-days`,
`semver-patch-days`). It was already present and working on `main` — Dependabot
was actively running update jobs against the repo, which it could not do if the
file failed to parse. Stripping it was a regression and had to be reverted.

Do: before applying a bot comment that REMOVES pre-existing, working
configuration, verify the claim against the actual tool docs/behavior. The
strongest tell here: the key was already on `main` and the tool was demonstrably
working with it. A bot asserting "X is unsupported" about config that is live and
functioning is the signal to verify, not to delete. Removing working config is
high-blast-radius — a malformed `dependabot.yml` silently disables ALL dependency
and security updates for every ecosystem in the file.

## Pitfall 2 — an `ignore` rule with only `dependency-name` suppresses everything

An `ignore` rule that lists only `dependency-name` (no `versions:` constraint)
acts as a blanket blacklist: it suppresses ALL future version updates AND
security advisories for that package, not just the one accepted-risk version
range. This is the opposite of the intent when the ignore documents a single
accepted advisory (here: GHSA-h67p-54hq-rp68 for js-yaml 3.x, accepted because
the only fix is a breaking babel-jest downgrade and js-yaml is dev/test-only).
This was the bot comment that WAS correct (coderabbitai) and worth applying.

Do: scope every risk-acceptance ignore to the affected range with `versions:`
so unrelated future high-severity advisories for the same package are still
surfaced. For the js-yaml case:

```yaml
ignore:
  # Accepted advisory GHSA-h67p-54hq-rp68 (js-yaml moderate DoS): only
  # reachable transitively via the jest dev toolchain; the sole fix is a
  # breaking babel-jest downgrade, so the advisory is accepted, not patched.
  - dependency-name: "js-yaml"
    versions:
      - ">=3.0.0 <4.0.0"
```

The `versions` value is an array of strings using the package manager's native
range syntax; a comma-separated single string also works, but the array form is
the recommended shape.

## Rule of thumb

`.github/dependabot.yml` is invisible to local lint/test/build, so review bots are
the gate — but they are not infallible. Treat REMOVING working config on bot
advice with extra skepticism (verify the key really is unsupported, especially
when it was already live on `main`), and always pair an accepted-risk `ignore`
with a `versions:` scope so the ignore is a surgical exception, not a blanket mute.
