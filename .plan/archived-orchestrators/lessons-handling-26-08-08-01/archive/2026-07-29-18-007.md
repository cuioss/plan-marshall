# A blind-spot-class request cannot be a scoping input - refine's fix-location hypotheses have no standing

## Observation

On `inventory-blind-spot` (PR #1056), phase-2-refine produced fix-location hypotheses that were
**0-for-3**:

1. A fix location. Wrong.
2. A second fix location. Wrong.
3. That the two inventories (`manage-architecture`'s file inventory and `pm-plugin-development`'s
   `enumerate_skill_files`) share **one** enumeration seam, so one fix serves both. Wrong — they are
   two independent enumerations answering two different questions, and unifying them would have shifted
   the plugin-doctor lint population by ~14 files, a finding-flood the module-tests gate would not have
   caught.

The plan landed correctly anyway, and the recorded reason is the operator's **init-time deep-lane
override** (`lane_escalated: true`, `escalation_trigger: premise`). The deep lane's codebase-wide
discovery measured the real population and settled all three hypotheses as wrong. On the light lane the
plan would have implemented hypothesis 1 or 2 against a 3-kind allowlist.

## Root cause

Refine reasons from the request text plus shallow lookups. For a **blind-spot-class** request — *"X is
not being seen"* — the request text is **by construction written by someone who cannot see X**. Its
named symptoms are a sample, and its implied fix locations are guesses about code the requester has not
read.

⛔ **Refine confidence measures agreement with the REQUEST, not with the CODEBASE.** This run recorded
98.5 confidence on premises that were entirely wrong.

## Rules

1. **A refine-time fix-location hypothesis is a search hint with no standing.** It must never enter the
   outline as a premise; discovery must be free to falsify it, and the outline should record the
   falsification explicitly.
2. **Blind-spot-class requests are a deep-lane trigger on premise.** The signature: the request asserts
   something is missing / not indexed / not seen / not detected, and names specific instances. The
   requester's visibility is the thing under question, so the request cannot be a reliable scoping
   input. Today the operator must supply this override by hand.
3. **"Two components ask the same question, so they must share a seam" is a hypothesis, not a fact.**
   Verify by reading both call sites **and both downstream consumers** before scoping a unification.
   Here the consumer that made unification wrong was two hops from the apparent duplication.

## Provenance

PR #1056. Outcome data supports automatic deep-lane routing for the blind-spot request shape.
