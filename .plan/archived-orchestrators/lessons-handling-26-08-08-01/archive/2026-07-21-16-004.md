# A dispatched execution-context agent can hit a stream-idle API stall mid-run — verify disk state before re-firing, then drive the step inline rather than blind-retry the dispatch

A dispatched `execution-context` agent can hit an API stream-idle stall mid-run
— the model connection hangs and the dispatch never returns a result, distinct
from the harness externally killing a `run_in_background` job (that failure
mode is covered separately). When this happens, the correct recovery is to
verify disk state FIRST, then drive the step inline — never blind-retry the
dispatch on the assumption that "it probably applied something before it
stalled."

## What happened

During this plan's finalize re-fire of `finalize-step-simplify`, a dispatched
`execution-context` leaf stalled mid-run on a stream-idle API condition. Before
taking any recovery action, the worktree was checked for a dirty tree and the
step's `mark-step-done` record was checked against the current HEAD. Both
showed the stalled agent had applied nothing: the worktree was clean and the
step record was still stamped at the prior HEAD. That verification proved it
was safe to drive the step inline rather than re-dispatch (which would have
risked a duplicate or half-applied mutation had the stall actually landed a
partial write) or silently treat the stall as a completed no-op.

## The generalizable rule

On any dispatched-agent stall or non-return (stream-idle, timeout, or an
ambiguous partial result):

1. **Do not blind-retry the dispatch.** A second dispatch on top of an unknown
   partial state can double-apply a mutation or race against a half-written
   file.
2. **Verify disk state before deciding the recovery path** — `git status`
   (clean vs dirty) plus the step's recorded `head_at_completion` /
   `mark-step-done` timestamp against the current HEAD are enough to establish
   whether the stalled agent applied anything.
3. **When verification proves nothing was applied**, drive the step inline in
   the current context instead of re-dispatching — this both completes the
   step and avoids paying for a second dispatch envelope that could stall
   again.
4. **When verification shows a partial mutation DID land**, treat it as a
   contaminated intermediate state: inspect what changed before deciding
   whether to complete, revert, or hand-fix — do not assume the partial state
   is either fully correct or fully absent.

## Why it happens

A stream-idle stall is an external harness/API condition, not a plan-marshall
defect — the same class of "unreachable root cause outside plan-marshall" as
the harness's external `run_in_background` job kills, but a DIFFERENT failure
mode (a live foreground dispatch's model stream hangs, vs. a backgrounded
process getting killed with zero output). Both share the same corrective
shape: never trust the ambiguous non-result at face value; re-establish ground
truth from disk before acting.

## Impact

Low cost when the disk-state check is run before reacting (this instance: one
inline step re-drive, no wasted re-dispatch, no duplicate mutation risk). The
risk this lesson guards against is the alternative — reflexively re-dispatching
or reflexively marking the step done-by-assumption — either of which could
compound into a duplicated or missed mutation on a step that actually matters
(a finalize step that touches source, e.g. `finalize-step-simplify`).

## Recurrence — 2026-07-22 (pyproject-routing-integration)

Second occurrence, this time on a **phase-5-execute** dispatch rather than a
finalize step, and it exercised the branch the original filing had only
described hypothetically: point 4, "verification shows a partial mutation DID
land."

**What happened.** A phase-5-execute dispatch was killed by a harness
stream-idle timeout mid-verification. Disk-state verification showed a
*split* state: TASK-001 was marked done and its source edits were present and
correct, but the workflow's Step 10a **commit obligation was unmet** — the
task's own record said complete while the artifact the step was contractually
required to produce (the commit) did not exist. The orchestrator settled the
outstanding commit itself, recorded a change-ledger entry for it, and then
re-dispatched with the resume context baked into the prompt.

**What this adds to the rule.** The original point 4 framed a partial landing
as "inspect what changed before deciding whether to complete, revert, or
hand-fix." This instance sharpens it in two ways:

1. **A step's completion RECORD and its completion OBLIGATIONS are separate
   surfaces, and a kill can split them.** Checking `git status` for a dirty
   tree and checking the step's `mark-step-done` record are not sufficient
   together — both looked consistent here (edits present, task marked done)
   while the *commit* the step owed was simply missing. When verifying disk
   state after a kill, enumerate the step's declared obligations (commit,
   ledger entry, artifact emission, status write) and check each one, rather
   than inferring completeness from the task record.

2. **Settle-then-resume beats revert-then-retry when the landed work is
   correct.** The recovery here was not to discard the partial state: the
   orchestrator *completed the missing obligation in its own context* and
   re-dispatched with the already-done work described in the prompt. This is
   the cheapest correct recovery for a split state whose landed half verifies
   clean, and it depends on the re-dispatch carrying resume context — a
   spawned agent cannot be resumed, so the answer must be baked into a fresh
   dispatch (see [[project_harness_agent_no_resume]]).

## Recurrence — 2026-07-26 (retire-gemini-registry-ground-pr-agent-standard)

Third occurrence, and the first to motivate a PREVENTIVE mitigation rather
than only a post-kill recovery procedure. A phase-4-plan dispatch ran for
roughly 20 minutes and was killed by a harness stream-idle timeout
immediately before its single terminal write — the entire batch of planned
tasks existed only in the dispatched agent's context and was lost in full (0
tasks on disk after the kill; the disk-state verification this lesson already
prescribes correctly detected nothing had landed). The re-dispatch succeeded
only after being instructed to persist incrementally (write each task to disk
as it is produced) rather than accumulating the whole task batch in context
and writing once at the end.

**Addition to the rule**: for any long-running dispatch that produces
multiple independent durable artifacts (tasks, findings, lesson entries,
etc.), front-loading durable writes — persisting each unit as soon as it is
produced instead of batching everything behind one terminal write — is a
preventive mitigation against exactly this failure mode, not just a recovery
step. A dispatch whose entire output rides on one final write has 100% of its
work at risk from a stream-idle kill at any point in the run; incremental
persistence bounds the loss to whatever was produced since the last write.
