# Plans under-scope the mirror contract surface (doc catalogues, cited-sibling docs, and count-pinning tests) of a code/registry change

Registering a new recipe in the marketplace touches more than the recipe SKILL.md and its `plugin.json`/`marketplace.json` registration. There is a human-facing doc-contract surface that the plan's outline routinely under-scopes, and the drift is only caught late — at the user's outline-review gate or in pre-submission self-review — rather than being planned in from the start.

## The two under-scoped doc contracts (recipe registration)

When a plan registers a new recipe, the deliverable outline MUST include edits to BOTH of these human-facing contracts, not just the machine registration:

1. **`doc/concepts/recipes.adoc`** — the prose catalogue of available recipes. A new recipe that is absent here is undiscoverable to a human reader even though it is wired in the registry. (This drift was caught by the user at the outline-review gate on the agentfile-hygiene-audit-recipe plan.)
2. **The owning plugin's `SKILL.md` `provides_recipes()` table** (e.g. `plan-marshall-plugin/SKILL.md`) — the per-bundle recipe inventory. A new recipe missing from this table desynchronizes the bundle's advertised surface from its actual registry. (This drift was caught only by pre-submission self-review on the same plan.)

## Recurrence signature

This is the recipe-registration instance of the broader "plans under-scope the doc-contract surface" pattern. The defect class: phase-3-outline enumerates the code/registration deliverables but omits the human-facing prose contracts that mirror them, so the drift surfaces downstream (review gate / self-review / PR bot) instead of being a planned deliverable.

## Corrective action

At phase-3-outline, for any plan that **registers, renames, or removes a recipe**, fold these into the deliverable set explicitly:

- An edit to `doc/concepts/recipes.adoc`.
- An edit to the owning plugin `SKILL.md`'s `provides_recipes()` table.

More generally: when a deliverable adds an entry to any machine-readable registry (recipe registry, ext-point Current Implementations table, canonicals list), grep the repo for the sibling human-facing prose catalogue that mirrors that registry and add the mirroring edit to the outline. Treat the prose catalogue as a first-class deliverable, not a Boy-Scout afterthought.

## Recurrence — 2026-07-06 (fix-execution-profile-posture-dialogue)

Same defect class, a new sibling surface: an operator-prompt migration in `phase-1-init`
edited the authoritative `phase-1-init/SKILL.md` plus `planning.md` and `agents.md`, but
MISSED three sibling standards docs that SKILL.md **cites as authoritative** and that
restate the same contract — `workflow.md`, `lesson-source-premise-check.md`, and
`plan-overwrite.md`. Pre-submission self-review caught the drift on iteration 2 as
same-document / contract-drift findings.

This broadens the lesson beyond the machine-registry → human-prose-catalogue mirror. The
under-scoped surface is not always a *prose catalogue* of a *machine registry*: it is any
**sibling doc that restates the same normative contract** and is bound to the doc you are
editing. When an authoritative `SKILL.md` (or any contract-owning doc) cites sibling
standards docs as authoritative, editing the contract in the owner obligates a matching
edit in every cited sibling that restates it — those cited docs are a first-class part of
the deliverable's doc-contract surface, not a Boy-Scout afterthought.

Corrective action generalized: at outline time, for any deliverable that changes a
**normative contract** in an authoritative doc, enumerate that doc's *cited authoritative
siblings* (follow its "see / cites as authoritative" cross-references) and fold the
lock-step edits to each restating sibling into the deliverable set. Grep the old
contract's wording across the sibling docs to find every co-changing site up front.

Same defect class, extended from the *doc*-contract surface to the *test*-contract
surface. D1 added three abstract methods to `platform-runtime/runtime_base.py`
(abstract-method count 18 → 21) plus three new session verbs, but the outline's
deliverable scoping missed two mirror surfaces that had to be fixed downstream:

1. **Test-contract**: `test_platform_runtime_base.py` pins the abstract-method COUNT as an
   assertion (`18` → had to become `21`). Adding abstract methods to a base class changes

2. **Doc-contract**: `platform-runtime/SKILL.md` + `standards/contract.md` document the

Generalization: the under-scoped mirror surface is not only prose that mirrors a registry
or a cited-sibling doc — it also includes **structural tests that pin a count or shape
derived from the code you are changing** (abstract-method-count assertions,
enum-membership tests, operation-count schemas, `__all__` / registry-size checks). At
outline time, when a deliverable adds or removes a member of a counted or enumerated set
(abstract methods, operations, enum variants, registry entries), grep for the test(s) AND
doc(s) that assert that set's count or membership, and fold the lock-step edits into that
deliverable's **test list** and **doc list** — treat both as first-class deliverables, not
Boy-Scout afterthoughts.

Same defect class, now the missed sibling surface lived **inside the same document**. A
marshall-steward maintenance bug (`architecture init --force` blanked every module's

Generalization: the under-scoped mirror surface is not always a *separate* sibling file
(prose catalogue, cited-authoritative-sibling doc, count-pinning test) — it can be a

the other. At outline (and at edit) time, when you touch any flag/subcommand/schema
description in a doc, grep *that same file* for every other block that restates the same
surface (Canonical-invocations blocks, scripts tables, reference rows) and fold the
matching edits into the deliverable — same-document siblings are first-class, not a
Boy-Scout afterthought.

   role.
4. Over-coverage mirror of the same defect: D5 listed `dispatch-logging.md` /

- **When a success criterion IS a whole-tree literal-token scan, DERIVE the affected-files

  grep that must seed the plan's affected-files list. Every file that grep hits is a
  first-class deliverable target, including diagram/render surfaces (`.svg`, ASCII call-graph
  boxes) where the token is embedded in rendered content.
- **The mirror surface extends ACROSS bundles.** A doc in another bundle that cites your
  changed component as an *exemplar* of a pattern is a first-class mirror-contract site. When
  you remove or rename the pattern instance, grep every bundle (not just the owning one) for
  citations of the changed token and fold the re-anchor edits into the outline. And sweep
  **completely, not representatively** — when a registry has N sibling rows (sub-key rows,
  enum variants), fix all N against the source-of-truth registry, not the one "representative"
  row.

surface.** When a deliverable adds or fixes behavior in one provider module
(`github_ops.py`, `github-impl.md`), its sibling provider module (`gitlab_ops.py`,

paired deliverable, not the "primary" provider with the sibling as a Boy-Scout afterthought.
The cost of not doing so is measured here: 6 self-review iterations and ~43% of finalize
tokens.

## Recurrence — 2026-07-11 (promote-self-review-default-finalize)

Same defect class, on another **finalize-step promotion** (`default:pre-submission-self-review`
promoted to a default step), and this recurrence sharpens the mirror surface for
**step-promotion/rename doc sweeps specifically**: the under-scoped sites were NOT prose id
references (those D5 correctly updated) but three *structured* restatements of the same
contract that a prose-only sweep skips. The plan's own pre-submission-self-review AND
CodeRabbit each caught siblings the D5 doc sweep missed:

1. **Example serialization in the wrong shape** — a fenced example of `steps` in
   `data-model.md` still used the **old array shape** when the contract is a keyed-map. Updating
   the prose that describes the id left a stale example serialization that contradicted the
   contract shape.
2. **Canonical-order / ordered-step lists with wrong ordinal position** — both a JSON example
   ordering AND a prose "Default steps" list in `data-model.md` either omitted the promoted step
   or placed it at the wrong position. A promotion changes an element's *membership and ordinal*
   in every ordered enumeration of the step set, not just its name.
3. **Stale flat-path config-field-list entry** — a knob that migrated from a flat path to a
   nested step-owned path still had a **flat-path field-list entry** in `configuration.adoc` and
   `decision-rules.md`. A field-list that enumerates config paths is a mirror of the config
   schema and must move the entry when the path moves.

Generalization — new facet, specific to **step-promotion/rename sweeps**: updating prose id
references is necessary but NOT sufficient. A step-promotion/rename doc sweep must also
enumerate and update, in lock-step:

- **Every example serialization** — every JSON/keyed-map/YAML fenced block that renders the
  changed structure. Verify the block matches the current contract *shape* (array vs keyed-map),
  not just the id text.
- **Every canonical-order / ordered-step list** — both machine (JSON example ordering) and prose
  ("Default steps" enumerations). A promotion changes the element's membership AND ordinal
  position; check position, not just presence.
- **Every config-field-list entry** — when a knob migrates from a flat path to a nested
  step-owned path, move its entry in every field-list that enumerates config paths
  (`configuration.adoc`, `decision-rules.md`), not just the prose that describes it.

At outline time for a promotion/rename: grep the OLD id, then separately audit every fenced
example block, every ordered-step list (for both membership and ordinal), and every
config-field-list for the moved/renamed element — the structured restatements are where a
prose-only sweep leaks.

tree — NOT scoped to the one test file the task author remembers. A task directive of the
form "remove/update existing assertions for {removed behavior}" is a red flag that the file
set was enumerated from memory; grep the removed token and fold every hit into the task's
test list as a first-class edit target before phase-5.

enumerates that operation's outcomes — not only the operation-count docs, and not only the
deliverable-named standards. Two sharpenings:

1. **The outcome-enumeration surface is wider than the plan's explicitly-named

   when the same change widens B's outcomes too. Sweep every operation whose outcome set the
   change touches, not just the one the deliverable centered on. The corrective rule already

   enumerations, and that sibling operations are independent members of that sweep.

## Recurrence — 2026-07-25 (repair-plan-retrospective-false-verdicts)

Same defect class, two facets, and the **latest catch point yet recorded** for this pattern:
one facet was caught by a PR review bot and the other by `lessons-housekeeping` — i.e. after
phase-5 had already shipped and after the pre-submission self-review had passed.

**Facet 1 — the doc enumerates an outcome the code CANNOT produce (over-enumeration).**
Every prior recurrence of the outcome-enumeration facet (2026-07-23) is *under*-enumeration:
the code gained an outcome the doc did not list. This one is the inverse. The
`plan-retrospective/references/artifact-consistency.md` example row advertised
`affected_files_recall,partial,...`, but `check_affected_files_recall` returns only
`pass` / `fail` / `skip` — `partial` is unreachable. Because the doc's own interpretation
rules downstream say "`partial` checks surface only when actionable", the phantom status did
not merely document nothing: it fed the consuming LLM a rule keyed on a status the pipeline
can never emit. CodeRabbit caught it on PR #998; no in-house gate did.

Generalization: **an outcome/status enumeration in a doc is a mirror contract in BOTH
directions.** Sweeping for outcomes the code emits but the doc omits is only half the check;
also verify that every status the doc names — especially inside example rows and worked
examples, which read as illustrative and therefore escape scrutiny — is actually producible
by the implementation. A doc-declared status the code cannot emit is worse than a missing
one, because downstream consumers (interpretation rules, routing tables, LLM instructions)
build logic on it.

**Facet 2 — aspect reference docs left declaring the PRE-FIX contract after phase-5 shipped.**
The plan changed behavior owned by two `plan-retrospective` aspect reference docs —
`references/routing-decision-verification.md` and `references/chat-history-analysis.md` — and
both still declared the old contract after execute completed. Neither the outline's
affected-files sweep, nor the phase-3-outline Q-Gate, nor the pre-submission self-review
caught them; `finalize-step-lessons-housekeeping` did, at the very end of finalize.

Generalization — new facet: in a skill whose behavior is *split across a SKILL.md plus a set
of per-aspect reference docs* (the `references/{aspect}.md` pattern used by
`plan-retrospective`, `manage-lessons`, and others), **each aspect reference doc is the
authoritative contract for its own aspect**, not supplementary prose. When a deliverable
changes the behavior of aspect X, `references/{X}.md` is a first-class mirror-contract target
with the same standing as the script that implements it. At outline time, map each changed
script/function to the aspect reference doc that documents it (the mapping is usually
name-for-name) and fold that doc into the same deliverable — do not rely on a
SKILL.md-centric sweep, which will not reach the per-aspect files.
