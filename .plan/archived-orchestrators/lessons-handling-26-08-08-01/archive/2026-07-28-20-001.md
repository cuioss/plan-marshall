# derive-verification's compile build_class has no phase-5 canonical route, so stamping it into a task's sole verification.commands fails manifest compose with unresolvable_step

## Context

Discovered during `phase-4-plan` task creation for plan `exploration-share-is-unmeasured` while stamping `verification.commands` (SKILL.md Step 6) for an `implementation`-profile task whose changed-artifact list contained production `.py` files but no test files (the paired `module_testing` task owns the test files instead — the standard 1:N split).

`architecture derive-verification` correctly classified the changed files and returned a single `compile` build_class row (`python3 .plan/execute-script.py plan-marshall:build-pyproject:pyproject_build run --command-args "compile plan-marshall"`), with `execution_tier: orchestrator` and `exceeds_bash_ceiling: true` (the `plan-marshall` bundle is large enough that even a `compile`-only pass exceeds the Bash ceiling).

Stamping this single command into the task's `verification.commands` and then running `manage-execution-manifest compose` failed with:

```
error: unresolvable_step
message: "phase_5 step `verify:compile` in marshal.json is unresolvable: step `verify:compile` names an unknown canonical `compile` — no ext-point-build-verify-step implementor (nor the composer canonical→role table) declares it"
```

Root cause: `_route_task_verification_commands` (manage-execution-manifest.py) promotes every `orchestrator`-tier task verification command out of the task and onto `phase_5.verification_steps`. The fast-path verb->step map (`_VERB_TO_PHASE_5_STEP` in `_manifest_rules.py`) covers only `quality-gate` / `verify` / `module-tests` / `coverage`. Any other verb (including the legitimate `compile` build_class that `architecture resolve`/`derive-verification` can emit) generalizes to a bare `verify:{verb}` step id — by design, per the docstring, which explicitly acknowledges this can fail the later resolvability gate. `_verify_canonicals_universe()` (in `_manifest_validation.py`) only recognizes `quality-gate` / `module-tests` / `coverage` / `integration-tests` / `e2e` (plus domain-appended `arch-gate`) — `compile` is not, and cannot become, a member without a code change.

This means: any implementation-only task in a large module (where `compile` alone exceeds the Bash ceiling and is force-routed to orchestrator tier) that derives ONLY a `compile` command will break `manage-execution-manifest compose` outright. Smaller modules never hit this because their `compile` classifies as `per_task` tier and stays inline, never touching the phase-5 routing path — which is likely why this had not surfaced before on a project the size of `plan-marshall` itself.

## Workaround applied (planning-time, no source touched)

phase-4-plan does not stamp a lone `compile` (or `test-compile`) command into `task.verification.commands` when the derived command's verb has no canonical phase-5 route. For an `implementation` task whose deliverable has a paired `module_testing` task, leave `verification.commands: []` on the implementation task (its production changes are transitively verified by the paired task's `module-tests` run over the same module) and keep ONLY the canonical `module-tests` command on the `module_testing` task, dropping any co-derived `test-compile` row.

## Suggested fix (source-level, out of scope for a planning-phase agent)

Either (a) add `compile` (and `test-compile`) to `_VERB_TO_PHASE_5_STEP` mapped to an appropriate existing canonical (likely `verify:module-tests`, since a compile-only check is subsumed by the module-tests run), or (b) have `derive-verification` never emit a standalone `compile` build_class for a task whose deliverable carries a paired `module_testing` task — defer entirely to that task's `module-tests` command, mirroring the workaround above at the deriver level so future planners don't have to rediscover this by hand.
