# A dispatched leaf without Grep/Glob reaches for Bash grep/find instead of the documented content-search fallback chain

## Observation

Two dispatched `execution-context` leaves reported briefly reaching for Bash `grep` for content
search before self-correcting to the sanctioned tools. The project's hard rule forbids Bash file
operations (`find`, `grep`, `cat`, `ls`) unconditionally and the enforcement hook blocks them, so
each attempt cost a rejected tool call and a recovery round-trip. Trigger: when `Grep`/`Glob` are
not granted to the subagent at runtime, the leaf's first instinct is the shell equivalent rather
than the documented fallback chain.

## Corrective

In a dispatched leaf, content search resolves in this order and never falls through to a shell:
1. `architecture search --content --pattern P` (module-attributed, inventory-scoped)
2. `architecture find --pattern P` for a PATH glob
3. `Grep` / `Glob` when granted
4. `Read` for scanning inside an already-known file
5. Report the coverage gap to the orchestrator for trees the inventory does not walk.

Bash `grep`/`find`/`git grep` are NOT step 5 — never a fallback, whether or not `Grep` was granted.

## Scope

Every dispatched `execution-context` leaf. If this recurs across plans, the remedy is likelier
prompt-level than knowledge-level — the envelope already documents the chain, so the recurrence
suggests the degradation branch needs to be more prominent at the point the leaf discovers `Grep`
is unavailable.
