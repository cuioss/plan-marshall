# Orchestrator cwd pin silently reverts to main checkout across background-job boundaries, producing an orphan plan directory with no self-correction escape hatch

# Orchestrator cwd pin silently reverts to main checkout across background-job boundaries, producing an orphan plan directory with no self-correction escape hatch

## Context

During this plan's phase-5+ execution, the orchestrator's pinned working
directory — the worktree at
`.plan/local/worktrees/{plan_id}` that every dispatched leaf and `git -C`
call is supposed to bind against — reverted to the main checkout across a
long background-job boundary (a build/verify call awaited across a wake-up
cycle). The revert was silent: no error, no log line naming the switch. The
next leaf dispatched after that boundary inherited the reverted cwd (main),
and a `manage-files` write for this plan created an ORPHAN plan directory on
main instead of the intended worktree path.

## Root cause

Two compounding facts:

1. **The pin is not re-asserted after a wait boundary.** Whatever session/
   process state carries the "active cwd" fact across a `run_in_background`
   await or a long synchronous Bash call does not survive that boundary
   reliably — the orchestrator's cwd silently reverts to the main checkout
   rather than staying pinned to the worktree, with nothing logging the
   reversion at the moment it happens.
2. **The scoped `manage-*` scripts have no self-correction escape hatch.**
   `manage-status`, `manage-findings`, and `manage-files` all resolve their
   plan directory relative to the process's current working directory —
   none of them accepts a `--project-dir` (or equivalent) override the way
   `tools-integration-ci` does. A leaf that discovers its cwd has drifted
   (by comparing `pwd` against `status.metadata.worktree_path`) has no way
   to correct the call itself; it can only refuse to proceed or re-`cd`
   before retrying.

## Detection

The drift is only visible by explicitly comparing the live process cwd
against the plan's own recorded intent:

```bash
pwd
python3 .plan/execute-script.py plan-marshall:manage-status:manage-status get-worktree-path --plan-id {plan_id}
```

A mismatch between `pwd` and the returned `worktree_path` (when
`worktree_state: materialized`) is the signal — nothing else surfaces it
proactively, and a `manage-files`/`manage-status`/`manage-findings` call made
from the wrong cwd succeeds silently, writing into (or reading from) the
wrong plan directory tree with no error.

## Corrective action

- **Before any dispatch that follows a long-running background-job
  boundary** (an `await-long-running` wake-up, a `run_in_background` result
  pickup), re-verify the active cwd against `get-worktree-path` and re-`cd`
  (or re-resolve via `git-workflow locate-plan-checkout`) BEFORE issuing the
  next `manage-*` call or `git -C` invocation. Do not assume a pin
  established earlier in the run is still in effect after such a boundary.
- **Do not trust a pin to persist across a wake-up cycle without
  verification.** The cheap `pwd` vs. `worktree_path` check above should be
  a standing habit at every post-wait resume point, not a one-off debugging
  step.
- **A leaf that detects the drift cannot self-correct through the affected
  scripts alone** — `manage-status`/`manage-findings`/`manage-files` have no
  `--project-dir` escape hatch (unlike `tools-integration-ci`, which does
  take an explicit repo/dir argument). The remedy available today is
  `git-workflow locate-plan-checkout` to re-resolve the correct path, followed
  by re-`cd`-ing (or re-dispatching with the corrected `WORKTREE` value) before
  retrying the call — there is no in-script recovery.
- **Owning fix (not yet done):** either make the cwd pin durable across
  background-job boundaries (survive the wake-up without silent reversion),
  or add a `--project-dir` override to `manage-status`/`manage-findings`/
  `manage-files` so a leaf that detects drift can self-correct in place
  instead of depending on a fragile ambient cwd.

## Impact

An orphaned plan directory on main is not merely cosmetic — it can hold
findings/status/task writes that the real (worktree-resident) plan directory
never sees, silently splitting the plan's state across two locations. Any
downstream read (status, findings, task list) against the wrong location
returns stale or empty results with no error, so the drift can propagate
several steps before anything looks wrong.
