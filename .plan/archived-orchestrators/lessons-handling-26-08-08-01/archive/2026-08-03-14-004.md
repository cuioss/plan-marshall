# RE_ENTRY_COVERAGE guard is vacuous at exactly the value it exists to catch

## Context

`references/logging-gap-analysis.md` specifies the RE_ENTRY_COVERAGE rule:

> **RE_ENTRY_COVERAGE** — **Precondition**: at least one `[STATUS] (plan-marshall:phase-5-execute) Re-entering execute phase` entry exists in `work.log` […]. When the precondition holds, cluster […] For each cluster after the first, expect exactly one `Re-entering` line. If `re_entry_count` […] does not match the number of `Re-entering` lines observed, emit a `warning`-severity finding. **Plans without any `Re-entering` line skip this rule entirely.**

The rule detects missing `Re-entering` lines, and its precondition is the presence of a `Re-entering` line. At zero lines — total absence, the worst possible value — the precondition fails and the rule skips.

Observed on `content-search-seam`:

- `work/metrics-dispatch-boundaries-5-execute.toon` records **3** dispatches: two `voluntary_checkpoint` (21:52:38Z, 22:37:36Z) and one `clean_exit_queue_empty` (22:44:37Z). Three dispatch clusters ⇒ **2** re-entries owed.
- `analyze-logs` reported `dispatch_clustering: {inferred_dispatches: 1, starting_markers: 1, re_entering_markers: 0}`.
- Findings emitted by the rule: **none**.

The facts needed to fire were present, computed, and printed in the same fragment. The rule declined to look at them.

## Root cause

The precondition and the detection target are the same signal. This is the general shape of a vacuous guard: *a check whose enabling condition is the presence of the thing whose absence it detects can never fire on total absence, only on partial absence.* It degrades exactly as the defect worsens, and is silent at the maximum.

The precondition was added for a legitimate reason — not to false-positive on plans predating the `Re-entering` instrumentation. But "this build predates the feature" and "this build has the feature and emitted nothing" are different states, and the precondition cannot tell them apart because it reads the same evidence for both.

## Proposed action

1. Re-key the precondition onto an **independent** capability signal — the presence of `work/metrics-dispatch-boundaries-{phase}.toon`, which is written by the same generation of the code and is not the thing being counted. Old plans lack the file and still skip; new plans with zero `Re-entering` lines now fire.
2. Derive the expectation from the dispatch-boundary row count (population-derived), not from the count of the marker being audited. `re_entry_count = rows - 1` is computable without reading a single `Re-entering` line.
3. Add a regression test whose fixture has N dispatch-boundary rows and **zero** `Re-entering` lines, asserting a finding is emitted. A fixture with one `Re-entering` line passes against the current defect and proves nothing.
4. Sweep the sibling precondition-guarded rules in the same document — OUTCOME_COVERAGE, ARTIFACT_EMISSION's new branch, VOLUNTARY_CHECKPOINT_POLLING — for the same shape. Each is guarded on the presence of the marker family it counts. OUTCOME_COVERAGE happened to pass cleanly here (7 tasks, 7 lines), so this run does not falsify them; it also does not clear them.

## The generalizable rule

A guard's precondition must be independent of its detection target. When the two coincide, the guard measures its own applicability rather than the property, and returns "not applicable" precisely when the property is most violated. Derive the expected count from a population the defect cannot shrink.
