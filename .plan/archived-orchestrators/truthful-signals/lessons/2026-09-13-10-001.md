# phase_handshake pending_findings_by_type undercounts against pending_findings_blocking_count

Observed while running plan architecture-store-query-truthfulness (PLAN-CIS-049): the phase-3-outline handshake row captured pending_findings_blocking_count=1 while its pending_findings_by_type breakdown showed all-zero, including triage=0. The pending item was real: qgate-2-refine.jsonl held hash 039658 (type=triage, resolution=pending). The two fields are documented as derived from the same population (pending_findings_blocking_count sums the pending count across the ACTIONABLE finding-type set named in pending_findings_by_type), so a non-zero blocking count with an all-zero by-type breakdown is an internal contradiction in the invariants module.

## Directive
When investigating a phase_handshake capture row where pending_findings_blocking_count is greater than zero but pending_findings_by_type sums to zero, do not conclude the population is inconsistent from a plan-scoped manage-findings list --resolution pending call alone -- that verb reads the plan-scoped general findings store, a DIFFERENT store from the phase-scoped Q-Gate findings (qgate-{phase}.jsonl, read via manage-findings qgate list --plan-id X --phase Y). Check every phase-scoped qgate store before concluding a discrepancy is a bug in the blocking-count computation itself. Separately, the invariants module pending_findings_by_type computation likely does not fold in phase-scoped Q-Gate findings the way pending_findings_blocking_count does -- worth a dedicated fix so the two fields cannot read different populations under the same capture call.
