# Architecture-resolved build duration estimates run ~5x stale and converge too slowly to be a trustworthy execution_tier routing input

## Symptom

During this plan's phase-5 measurement work, the architecture-resolved
canonical build commands carried `estimated_duration` values that were
roughly five times the measured wall-clock cost on the same worktree:

| Canonical command | Resolved estimate | Measured actual | Overshoot |
|-------------------|-------------------|-----------------|-----------|
| `module-tests`    | 670 s             | 137 s           | ~4.9x     |
| `coverage`        | 1451 s            | 267 s           | ~5.4x     |

The estimates DO adapt downward as observations accumulate — mid-plan they
had decayed to 576 s and 1233 s respectively — but the step size is small
relative to the gap, so several more full runs would be needed before the
estimate approaches the true cost.

## Root cause

The duration estimator is a slow-converging smoother over historical run
durations with no mechanism to discount stale observations quickly. Once an
estimate has been inflated (by an earlier slower machine state, a cold
cache, a whole-tree run misattributed to a scoped target, or a
harness-killed run counted at its timeout ceiling), it decays back toward
truth only asymptotically. There is no reset, no outlier rejection, and no
confidence signal on the estimate to tell a consumer how much to trust it.

## Impact — the estimate is a ROUTING input, not a cosmetic one

This is not merely a wrong number in a display. `estimated_duration` feeds
the `execution_tier` decision in the resolved canonical-command envelope:

- a short estimate yields `execution_tier: per_task`, so the dispatched leaf
  runs the build synchronously inside its own envelope with
  `timeout: bash_timeout_seconds * 1000`;
- a long estimate yields `execution_tier: orchestrator`, which forbids the
  leaf from running the command at all and forces a hand-off back to the
  main-context orchestrator.

A ~5x-inflated estimate therefore pushes commands over the orchestrator
threshold that would comfortably have completed inside the leaf. The
observable cost is a spurious dispatch round-trip: the leaf returns without
doing the work, the orchestrator re-dispatches or runs the build itself, and
the plan pays an extra envelope plus the orchestrator's serialized attention
for a job that measured 137 s. The inflation is also self-reinforcing in the
opposite direction from what you want — routing to the orchestrator tier
means fewer per-task observations of the true scoped cost.

## Corrective action

1. Make the estimator converge fast enough to be trusted, or stop treating it
   as authoritative for routing. Concretely: bound the estimate's staleness
   (e.g. weight recent observations far more heavily, or discard observations
   older than N runs), and reject outliers — in particular do not fold a
   timed-out or harness-killed run's ceiling value into the mean, since that
   is exactly the observation that inflates the estimate and then persists.
2. Emit a confidence/observation-count alongside `estimated_duration` in the
   resolved envelope so the tier decision can degrade gracefully: a
   low-confidence long estimate should NOT by itself force
   `execution_tier: orchestrator`.
3. Widen the hysteresis on the tier boundary rather than reading a single
   point estimate — a command that has recently measured well under the
   threshold should not flip to the orchestrator tier on one inflated
   resolution.
4. Independently of the estimator fix, record measured durations back into
   the architecture store on every run (including leaf-tier runs) so the
   convergence has data to work with.

## Recurrence signature

Any run where the architecture-resolved `estimated_duration` for a scoped
build target exceeds the measured wall-clock by more than ~2x, AND the
resolved `execution_tier` is `orchestrator` while the measured duration
would have fit comfortably inside a `per_task` leaf budget, is this defect.
The tell is an orchestrator hand-off for a build that finishes in a couple
of minutes.

## Recurrence — 2026-07-27 (refusal-recognizer-generalizes-phrasing) — INVERSE POLARITY, and it is the dangerous one

This lesson was filed for over-estimation and its recurrence signature above
describes only that direction. The same estimator failed in the opposite
direction on this plan, and the under-estimate is **strictly worse than the
over-estimate this lesson was filed for**.

**What happened.** `quality-gate` live-resolved `execution_tier: per_task` with
a stamp of ~170 s. The run took 273 s — a ~60% under-estimate. Because the tier
was `per_task`, the dispatched leaf ran it synchronously with
`timeout: bash_timeout_seconds * 1000`; the call blew through that budget and
the harness auto-moved it to background, producing the zero-byte-output kill
signature. A dispatched leaf cannot background result-bearing work (it is a
leaf, and the return path is synchronous), so there was no recovery inside the
envelope.

**Verified after the fact.** Re-resolving the same command post-run returns a
stamp that is *lower still*:

```text
architecture resolve --command quality-gate --module plan-marshall
  bash_timeout_seconds: 150
  execution_tier: per_task
  exceeds_bash_ceiling: false
```

150 s — below the 170 s that was already 60% short, **after** a 273 s
observation. Whatever the smoother did with that run, it did not move the
estimate toward it. This is direct evidence for corrective action (4): either
the over-running/backgrounded run was never recorded (the leaf died before it
could write back), or it was recorded and the smoother is dominated by faster
cached runs. Both readings say the same thing — the estimate is not converging
on the tail that matters.

**Why the inverse polarity is the severe direction.** The over-estimate case
this lesson documents costs *an extra dispatch round-trip*: the leaf declines,
the orchestrator re-runs, the work completes. The under-estimate case routes
work into a path that is **structurally incapable of completing it**. The leaf
cannot background, cannot extend its own budget, and returns nothing — the
build's outcome is unobservable, so the failure is not merely slow, it is
silent. An estimator that is wrong in the safe direction wastes an envelope; one
that is wrong in this direction destroys the result.

**Added corrective action — asymmetric margin at the tier boundary.** The two
error directions have asymmetric cost, so the tier decision must not treat them
symmetrically:

1. **Pad the `per_task` budget, not just the tier choice.** When routing
   `per_task`, set `bash_timeout_seconds` from an upper quantile of observed
   durations (or the stamp times a safety factor), never the central estimate.
   A `per_task` route whose budget equals the mean will be exceeded roughly half
   the time by construction.
2. **Never route `per_task` on a low-confidence short estimate.** The
   zero-measurement extreme of this is now closed: the runnable-slice-keys-
   on-the-floor plan made `execution_tier` fail closed to `orchestrator`
   whenever a command's run-config key has never been measured, uniformly
   across all four build engines, independent of what the floor-derived
   stamp alone would suggest. The residual gap this item still guards is a
   command that HAS been measured at least once (so it clears that gate) but
   whose single/noisy measurement is itself an under-estimate — exactly the
   170s-stamp/273s-actual case documented above. That command still routes
   `per_task` with no confidence/quantile margin; items 1 and 3 remain the
   open fix for it.
3. **Feed overrun observations back preferentially.** A run that exceeded its
   budget is the single most informative sample for this estimator and is
   precisely the sample most likely to be lost (the process was killed). Record
   the duration at kill time as a *lower bound* rather than discarding it.

**Extended recurrence signature.** Add the inverse case: any run where the
resolved `execution_tier` is `per_task` and the measured wall-clock exceeds
`bash_timeout_seconds`, is this defect. The tell is a dispatched build that
returns zero bytes of output after being auto-backgrounded by the harness —
which is easily misread as the unrelated harness-kill class, so check the
resolved stamp against the elapsed time before attributing it there.
