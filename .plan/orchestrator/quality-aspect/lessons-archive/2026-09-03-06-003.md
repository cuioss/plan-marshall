# Let should_emit render a fragment that declares it could not look

## Context

`compile-report.should_emit` gates conditional sections on `status in (None, 'success')`:

```python
# Accept only success-status fragments with meaningful content.
status = fragment.get('status')
if status not in (None, 'success'):
    return False
```

Immediately above it sits a by-name carve-out for one aspect, whose comment states the problem precisely: chat-history-analysis's Tier-2 graceful-skip fragment "carries `status: skipped` plus a `severity: warning` finding the reference explicitly requires to be visible in the compiled report — the status guard would drop it".

The sibling registry disagrees with the guard. `retro_sections.ZERO_DECLARED_UNMEASURED_STATUSES` is `frozenset({'not_evaluated', 'skipped'})`, documented as the statuses with which "a fragment DECLARES that it could not look, rather than reporting a zero it never measured". So `not_evaluated` is blessed as honest by the registry and accepted by `should_emit` on **no** aspect at all.

This retrospective hit it. `permission-prompt-analysis` genuinely could not evaluate its channel — the only transcript access available is `extract-chat-signal`'s reduction, which kept 6 of 1426 turns by an operator-turn predicate, and a permission prompt is a tool-call interruption rather than an operator turn. The fragment reported that honestly with `status: not_evaluated`, a populated `channel_state_reason`, and a `findings` entry. `compile-report` returned `status: warning` with `sections_dropped: ['Permission Prompt Analysis']`, and the report carried **no permission section at all** — which reads exactly like the silent clean-zero that lesson `2026-09-02-13-004` exists to prevent, one layer up in the renderer.

Controlled confirmation: re-emitting the identical fragment with `status: success` plus an `evaluation_state: not_evaluated` field, changing nothing else, produced `status: success` with `sections_dropped: []` and the section rendered.

## Root cause

Two modules own overlapping vocabulary and disagree. `retro_sections` declares which statuses are honest could-not-look declarations; `should_emit` hard-codes its own narrower accept-set and patches the gap per-aspect by name. The by-name carve-out fixed the one instance that was noticed instead of the class.

## Proposed action

Widen the guard to consult the registry it already imports:

```python
if status not in (None, 'success') and status not in ZERO_DECLARED_UNMEASURED_STATUSES:
    return False
```

`compile-report` already imports `ZERO_DECLARED_UNMEASURED_STATUSES` for `_names_checked_set`, so no new import is needed. Then delete the `chat-history-analysis` by-name carve-out, which the widened guard subsumes — leaving it in place would preserve the second source of truth this change removes. Do not add a `permission-prompt-analysis` carve-out; that would repeat the mistake a third time.

## Evidence

- `plan-retrospective/scripts/compile-report.py` `should_emit` — the status guard and the by-name carve-out above it
- `plan-retrospective/scripts/retro_sections.py` `ZERO_DECLARED_UNMEASURED_STATUSES` — the contradicting vocabulary
- First compile of this plan's report: `status: warning`, `sections_dropped: ['Permission Prompt Analysis']`
- Second compile, status-field change only: `status: success`, `sections_dropped: []`, section written
- Related: lesson `2026-09-02-13-004` (permission-prompt-analysis reports an unmeasured channel as a clean zero) — this is the same failure reached through the renderer rather than the producer

## Recurrence — 2026-09-06, plan `domain-post-plan-narrow` (PR #1422)

**Second instance, reproduced step for step including the controlled confirmation — the fix
proposed above is still unapplied.**

This retrospective's `permission-prompt-analysis` again could not evaluate its channel:
`extract-chat-signal` kept 5 of 1513 turns by the operator-turn predicate, and a permission
prompt is not an operator turn. The fragment was authored with `status: not_evaluated` — the
token the registry blesses — plus a populated `population` field and two `findings` entries.

`compile-report` returned `status: warning`, `sections_dropped: ['Permission Prompt Analysis']`,
and the report carried no permission section. Re-emitting the identical fragment with
`status: success` and the not-measured semantics moved into body fields (`channel_measured: false`,
`prompts_found: not_measured`) produced `status: success`, `sections_dropped: []`, and the section
rendered — the same one-field controlled confirmation the original recorded.

### What this instance adds

The workaround has a cost the first instance did not name: the only way to get the section into
the report is to state `status: success` over a channel that was never measured. The fragment
now has to carry a `status_caveat` field explaining that its own status word is weaker than the
truth, because the instrument would not render the true one. An aspect is being made to
soften its declaration to satisfy a renderer — which is the precise inversion of what the
`ZERO_DECLARED_UNMEASURED_STATUSES` vocabulary exists to enable.

Note also that this occurred on a plan whose entire subject was removing the class "a guard that
could not look must not read as a guard that looked and found nothing". The renderer forced that
exact softening on the retrospective auditing that plan.

The one-line widening in Proposed action remains correct and remains unapplied. Adding a
`permission-prompt-analysis` by-name carve-out is still the wrong fix, for the reason already
stated.

## Recurrence — 2026-09-08, plan `sweep-preambles-shipped-accessors` (PR #1446)

**Third instance, again reproduced with the one-field controlled confirmation. Still unapplied.**

Same aspect, same cause, different status token — which is what this instance adds.

`permission-prompt-analysis` could not evaluate its channel: `extract-chat-signal` kept 2 of
1007 turns (`operator_turn_count: 2`, `gate_decision_count: 2`), and a permission prompt lands
in the tool-result channel the reduction discards. The fragment was authored with
`status: skipped` plus a `reason` token and a `severity: warning` finding — the shape
`references/chat-history-analysis.md` explicitly specifies so that "a `warning` finding makes
the skip visible in the compiled report".

`compile-report` returned `status: warning` with `sections_dropped: ['Permission Prompt Analysis']`
and the report carried no permission section. Re-emitting with `status: success` plus
`channel_state: unmeasured` / `evaluated_population: 0` and an unchanged warning finding produced
`status: success`, `sections_dropped: []`, and the section rendered.

### What this instance adds

The first two instances used `not_evaluated`. This one used **`skipped`** — the *other* member of
`ZERO_DECLARED_UNMEASURED_STATUSES`, and the one the `chat-history-analysis` by-name carve-out
already accepts. So both members of the blessed vocabulary have now been observed being dropped,
and the carve-out is demonstrably per-aspect rather than per-status: the identical status word
renders for `chat-history-analysis` and is dropped for `permission-prompt-analysis` in the same
compile run.

That closes off any reading in which the guard is merely conservative about an unfamiliar token.
It is not the token it rejects; it is the aspect. The one-line widening
(`status not in ZERO_DECLARED_UNMEASURED_STATUSES`) plus deletion of the by-name carve-out is
still the correct fix, and is now supported by three instances across two distinct status values.
