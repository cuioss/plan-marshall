# A completeness sweep must derive its population from the claim, not one phrasing

## Context

Plan `pre-push-gate-mutation-coherence` flipped `pre-push-quality-gate`'s
`mutates_source` declaration, which made a paragraph asserting *"Two
`mutates_source: true` steps run BETWEEN the gates and review"* false wherever it
appeared. `pre-submission-self-review` correctly opened a sweep for that class and
found four sites. Commit `426982695` closed the sweep and recorded its own
completeness check in the commit message:

> Population re-derived independently over a 5429-file sweep with clean coverage
> (0 unreadable, no truncation, no elision): "those two steps" now returns count 0

The derivation genuinely ran, over the whole inventory, with clean coverage
fields. It was still wrong. That same commit's diff to
`marketplace/bundles/plan-marshall/skills/automatic-review/scripts/review_gate_delta.py`
fixed the module docstring and left the identical stale claim at **two further
sites in the same file**: the `_PROVENANCE` string constant (line ~169) and the
`--gate-head-sha` argparse help string (line ~575), the latter additionally
carrying the cardinal "two". CodeRabbit filed both as one Major (`da38dd`) about
30 minutes later, and its own comment anchored only one of the two — the fix at
`e488a7f8` had to sweep both.

## Root cause

The population predicate used for the re-derivation was a **literal phrase**
(`"those two steps"`), while the claim being retired was **semantic**: *this
paragraph enumerates the mutating steps between gate and review*. The two
surviving sites state the same claim in different words — `_PROVENANCE` writes
`'finalize-step-simplify (order 8) and finalize-step-security-audit (order 9)
mutate source after the gates'`, the help string writes `'two mutates_source
steps (finalize-step-simplify order 8, finalize-step-security-audit order 9)'` —
so neither matched the query. A `count: 0` over the wrong predicate is
indistinguishable from a `count: 0` over the right one, and the clean-coverage
fields (`unreadable: 0`, `truncated: false`, `elided: 0`) attest only that the
*search* was complete, never that the *predicate* was.

This is the known "derive completeness, never assert it" archetype at one turn
deeper: the derivation was performed and reported honestly, and the reported
number was still not evidence for the claim it was offered as evidence for.

## Proposed action

For any sweep that retires a semantic claim:

1. Derive the population from a **discriminating token of the subject**, not from
   the sentence being deleted. Here the right query is the step names
   (`finalize-step-security-audit`, `finalize-step-simplify` co-occurring) or the
   cardinal (`\btwo\b` near `mutates_source`) — not the prose the fix happened to
   author.
2. Run at least **two** independent queries with different phrasings and report
   the union; a single-query zero is a lower bound on the population, not a count.
3. When the sweep edits a file, **re-scan that file after the edit**. Two of the
   two misses here were inside the file the same commit had open, which is the
   cheapest possible place to catch them.
4. State in the completeness claim **which predicate was searched**, verbatim. The
   commit message above named the coverage of the search and not the query, so a
   reader could not evaluate whether the zero meant anything.
