## G1 — The input-table conformance scope is bound to an undocumented header string, so a Required row under any other header passes green

- **Kind:** vacuous-guard
- **Severity:** high
- **Where:** `test/plan-marshall/phase-6-finalize/test_step_prompt_fields_contract.py` — `_INPUT_TABLE_HEADER` (line 413) consumed by `_required_table_keys` (line 465: `if header[0].strip().strip('*').lower() == _INPUT_TABLE_HEADER`), which feeds `test_input_table_required_keys_equal_the_declaration`; the contract it implements is `marketplace/bundles/plan-marshall/skills/extension-api/standards/ext-point-finalize-step.md:140`
- **What is wrong:** the third assertion scope — the one `ext-point-finalize-step.md:140` calls *"the only direction that reaches a generic-template-dispatched step … so it is where the contract is actually held"* — reads a table **only** when its first header cell is the literal string `Prompt-body field`. That string is a repository convention, not a stated requirement: it appears in **no** normative document. `ext-point-finalize-step.md:128` says a step "states it in its own input table"; `:140` says "its prompt-body-field input table"; neither prescribes the header, and neither does `ext-point-execution-context-workflow.md`, `external-step-contract.md`, or `agents/execution-context.md`. Demonstrated with a matched positive/negative control pair whose **only** difference is the header text, on `phase-6-finalize/workflow/create-pr.md` (a step with no `requires_prompt_fields` declaration):
  - `| Field | Required | Description |` + `| \`ghost_field\` | Yes | … |` → the whole module runs **19 passed**, green.
  - `| Prompt-body field | Required | Description |` + the identical row → **RED**: `default:create-pr: declared=[] table=['ghost_field']`.

  Both files were restored byte-identically from a scratch snapshot; `git status --porcelain` clean afterwards.
- **Why it matters:** 260/G1's *Done when* reads *"injecting a `Required: Yes` non-contract prompt-body row into **any** finalize-step doc … turns a test red"*, and it does not. A step author who follows the contract's own words and heads the table `| Field |`, `| Input |` or `| Parameter |` gets an undeclared step-specific field that the dispatcher is never told to forward, with the guard reporting clean over a table it never opened. That is the "detector reports clean over an unexamined population" archetype this epic is named for, reintroduced inside the deliverable built to close an instance of it — the recurrence pattern `plan.md` § Notes warns about. No live instance exists today (only one of the 26 implementor docs carries a prompt-body-field table at all), so this is a latent vector rather than a current miss — which is exactly when it is cheapest to close.
- **Fix:** make the header an enforced contract rather than an unstated convention. Either (a) state the required header verbatim in `ext-point-finalize-step.md` § "Step-specific prompt-body fields" and add a guard asserting that every finalize-step doc containing a `Required`-column table under an `## Input`-shaped heading uses it — failing with the offending header; or (b) widen the discriminator to "a `Required`-column table whose first header cell is not a CLI parameter label", keeping the existing `| Parameter |` exclusion as the committed negative case, and add a synthetic positive for at least one alternative header. Either way, add a test asserting the guard fires on a non-convention header, so the discriminator itself is pinned the way `test_input_table_required_column_is_located_by_header_not_position` already pins the column lookup.
- **Done when:** a `Required: Yes` non-exempt prompt-body row added to any finalize-step doc turns a test in `test_step_prompt_fields_contract.py` red **regardless of the table's header text**, and a committed test asserts that with a non-`Prompt-body field` header.
- **Module/topic:** `plan-marshall:extension-api` / `plan-marshall:phase-6-finalize` — `requires_prompt_fields` input-table conformance scope

## G2 — `plan phase-6-finalize set --field <retired>` still returns `status: success` and persists a key nothing reads

- **Kind:** bug
- **Severity:** high
- **Where:** `marketplace/bundles/plan-marshall/skills/manage-config/scripts/_cmd_quality_phases.py` — `cmd_phase`, the `args.verb == 'set'` branch (the terminal `else: value = _coerce_value(args.value)` → `section[field] = value` → `save_config(config)` path, ~lines 405-425). Contrast the `get` branch at `:373-375`, which rejects an unknown field
- **What is wrong:** the `get` verb validates the field against the merged section and errors; the `set` verb has **no** membership check at all. Only three special cases validate (`per_deliverable_build`, `q_gate_validation`, and the `GATE_MODE_FIELDS` planning gates); every other field name falls through, is coerced, and is persisted. Executed against an isolated temp `PLAN_BASE_DIR` seeded from `get_default_config()`:
  - `set --field self_review --value never` → `{'status': 'success', …}` and `"self_review": "never"` written into the phase block;
  - `set --field plugin_doctor --value always` → `success`, persisted;
  - `set --field escalation_bogus --value banana` → `success`, persisted.

  And the asymmetry then **inverts**: after the write, `get --field self_review` returns `success, value: never`, so the operator's read-back confirms a key nothing consumes. (Before the write, the same `get` errors — confirmed against the repository's own config via the executor.)
- **Why it matters:** this is the half of 190/G6 that D4's own preamble diagnoses verbatim — *"The failure is asymmetric and both halves are bad … `set --field self_review --value never` returns `status: success` and persists a key nothing reads. That is a shipped false signal on the highest-risk gate the page describes"* — and D4's three items are all documentation edits plus the `set-lane` rejection. The gap's *Done when* is doc-scoped, so 190/G6 and 190/G7 are legitimately closed; but the live defect is neither fixed, nor excluded by § Out of scope, nor recorded in § Residue. Deleting the rows removes the *instruction* to send the false signal while leaving the signal itself intact for any operator with an older page, an older `marshal.json`, or a typo. The third case above shows the class is wider than the four retired gates: **any** misspelled field name is silently persisted into a git-tracked config file.
- **Fix:** give the `set` branch the same membership check the `get` branch has — reject a field absent from `{**defaults, **plan_config.get(phase_section, {})}` with an `error_exit` naming the phase and the accepted field list, and route a retired ceremony-gate name to its owning step's `lane` override (the string `step set --step-id <owning-step> --param lane` already exists as `_GENERIC_STEP_PARAM_ROUTE`'s shape in `_cmd_finalize_steps.py`). Add a test asserting `set --field self_review` errors and writes nothing, and a matched positive control asserting a real field still round-trips.
- **Done when:** `plan phase-6-finalize set --field self_review --value never` returns `status: error`, `marshal.json` is byte-unchanged after the call, and a committed test pins both halves.
- **Module/topic:** `plan-marshall:manage-config` — `plan phase-<N> set --field` unknown-field handling

## G3 — The wildcard-free glob guard's examined population can silently empty

- **Kind:** vacuous-guard
- **Severity:** medium
- **Where:** `test/plan-marshall/phase-6-finalize/test_verdict_currency.py` — `test_every_wildcard_free_declared_glob_names_a_tracked_path` (line 557); the companion that exists is `test_at_least_one_step_declares_a_verdict_input_surface` (line 449), which pins the *declaring* population, not the *examined* one
- **What is wrong:** the guard iterates `_declared_surfaces()` and skips every glob for which `_is_wildcard_free` is false. Today exactly one step declares `verdict_inputs` and all three of its globs are literal, so the guard examines three paths. Nothing asserts that number is non-zero. Demonstrated: replacing `project:finalize-step-era-stamp-fill`'s three literal globs with a single `'no/such/dir/*.py'` leaves the **entire** module green — **42 passed** — because the wildcard-bearing glob is exempt, the declaring-population guard is still satisfied, and the existence check then examines zero paths and reports clean. (Restored byte-identically; `git status` clean.)
- **Why it matters:** the surviving glob names nothing, so the verdict-currency classifier reads "the tree difference touches none of my surface", returns `preserved`, and the step SKIPs on a stale verdict — which is precisely the outcome 440/G1 exists to prevent, reached by a route the fix leaves open. The module's own convention is that every population-derived assertion carries an anti-vacuity companion (`test_at_least_one_step_declares_a_verdict_input_surface`, the `assert tracked` guard, `test_wildcard_free_discriminator_separates_a_literal_from_a_family`); this one assertion is the exception. Exempting wildcard-bearing globs is a deliberate and correct scope choice — publishing how many globs the exemption left unexamined is the missing half.
- **Fix:** count the wildcard-free globs the guard actually examined and assert the count is non-zero, with a message naming the declaring steps and how many of their globs were exempted — so a population that empties fails loudly instead of passing quietly. If a genuinely all-wildcard population is ever legitimate, make that an explicit, named allowance rather than a silent zero.
- **Done when:** rewriting every declared `verdict_inputs` glob to a wildcard-bearing form turns a test in `test_verdict_currency.py` red, and the message states how many wildcard-free globs were examined.
