# Validate new-module ITs in CI-isolation, not via full-reactor build

Re-homed from the TokenSheriff consumer store 2026-07-16 ([[feedback_manage_lessons_cwd_store_resolution]]).

**Context:** TokenSheriff PR #550 (OIDC client). The new client `*IT` files imported engine packages from `token-sheriff-client`, but the `token-sheriff-quarkus-integration-tests` pom only declared the Quarkus wrapper. Local `mvn install` + full-reactor test-compile MASKED the missing dependency (client classes were on the reactor/local-repo classpath), so agents reported "IT compiles". CI's **isolated** integration-tests job then failed with 33 compilation errors (`package de.cuioss.sheriff.token.client.* does not exist`).

**Why:** A full-reactor build resolves sibling-module classes transitively/through the reactor even when the pom does not declare the dependency the test code imports. CI runs the integration-tests job in isolation, so only declared dependencies are on the classpath.

**How to apply:** When a new module's tests import another new module's classes, declare a **direct** compile-scope dependency on exactly what you import. To reproduce CI locally, install the upstream modules (`install -DskipTests`) then run `clean test-compile -pl {it-module}` **without** `-am` — a green full-reactor build is NOT evidence the isolated CI job will compile.

## Recurrence — 2026-07-16 (fix-integration-build-npm-warnings)

The same CI-isolation dependency-drift class recurred on the **workflow side**: when PR #574 added client-module dependencies to the IT pom (the fix this lesson prescribes), the hardcoded `-pl` module list in the `install -DskipTests` step of `.github/workflows/integration-tests.yml` silently went stale — the newly-required upstream modules were not installed before the isolated IT job ran. Nothing gates the workflow's install list against the pom's dependency set, so they drift independently.

**Widened rule:** the isolated integration-tests CI job has TWO surfaces that must track the IT pom's dependency set — (1) the pom's own direct dependency declarations, and (2) the CI workflow's upstream `install -pl` module list. When adding a dependency to the IT pom, update the workflow install list in the same PR. Better: derive the install list mechanically (`install -pl {it-module} -am -DskipTests` so Maven computes the upstream closure) or add a CI check diffing the workflow's `-pl` list against the IT pom's reactor-internal dependencies.
