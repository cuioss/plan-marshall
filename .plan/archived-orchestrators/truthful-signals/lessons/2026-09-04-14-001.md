# Stale plugin-doctor help cache reports 344 false manage-invocation findings and reds module-tests

## Problem

`scan_manage_invocation` derives its accept-set from a recursive `--help` walk, memoised into a
content-hash-keyed on-disk cache under `.plan/temp/plugin-doctor-help-cache/` (the derivation lives
in `script-shared`'s `argparse_surface`). When that cache holds a degraded entry, the rule reports
the cached router-level flag set as if it were the script's whole surface, and every documented
subcommand flag becomes a finding.

Observed 2026-09-04 in the worktree for plan `apply-the-cloud-plan-lane-contract-amendments`:

- `doctor quality-gate` over the marketplace reported **344 findings**, all `manage-invocation-invalid`,
  all from `scan_manage_invocation`, every one naming the *same* four "registered" flags:
  `['audit-plan-id', 'help', 'plan-id', 'project-dir']` — the executor's router flags, not the
  target script's.
- The claim was false on inspection: `manage-tasks read --help` lists `--task-number` right there.
- `test_real_marketplace_quality_gate_has_zero_findings` consumes the gate, so `module-tests
  pm-plugin-development` went **red** (3140 passed, 1 failed) on a worktree with **zero commits ahead
  of origin/main and a clean tree** — a baseline that could not possibly have been broken by the plan.
- `run_config cleanup --target temp` (14221 files, 5.5 MB) cleared it. The same scoped gate that had
  reported 4 findings reported **0**; the full gate went 344 → **0**; `module-tests` went green at
  3141 tests.

## Why it matters

The failure mode is **uniform mass false-positives that read as a real regression**. Three properties
make it expensive:

1. It surfaces as a *test failure*, not as a doctor warning, so the reader's first hypothesis is
   "my change broke something" — but the tree was clean and unmodified.
2. The rule's own population/blind-spot columns were **empty** for `scan_manage_invocation`, so the
   report carried no signal that the accept-set had been derived from a degraded source. A rule whose
   verdict depends on a derived surface should publish whether that derivation succeeded.
3. The finding text is confidently specific ("registered: [...]"), which is exactly the
   confident-signal-hides-a-caveat shape — the four listed flags look like an answer, not like a
   fallback.

## Directive

- **Diagnostic**: when `scan_manage_invocation` reports many findings that all name the same short
  "registered" flag list, suspect the cache before the code. Clear it
  (`run_config cleanup --target temp`) and re-run scoped to one flagged file. A 4→0 swing on unchanged
  source is the confirmation.
- **Fix**: the derived-surface path should fail closed and say so — when the `--help` walk yields only
  the universal/router flags for a script that declares subparsers, that is an unresolved derivation,
  not an empty surface. Emit it as a coverage gap (or a blind-spot count) rather than as N findings.
  The module docstring already claims a "fail-closed-on-uncertainty invariant"; this run shows the
  invariant did not hold for the cached path.

## Evidence

- Gate before: `total_issues: 344`, all `rule_id: manage-invocation-invalid`.
- `manage-tasks read --help` → `--plan-id`, `--task-number` (the flag the rule called unregistered).
- `git status --porcelain` empty; `git log --oneline origin/main..HEAD` empty.
- Gate after cache clear: `total_issues: 0`, same 37 rules run.
- `module-tests pm-plugin-development` after clear: `status: success`, 3141 tests, 375s.

## Recurrence — 2026-09-05 (shipped-guards-assume-the-meta-projects-own-layout)

Same rule, same finding class, different counts — **173** whole-tree and **49** scoped, all
`scan_manage_invocation` / `manage-invocation-invalid`. It blocked the plan at
`pre-push-quality-gate` for roughly six hours (finding `cb3735`, operator-accepted, reported
to the `truthful-signals` epic).

Two things this recurrence adds, and the second contradicts this lesson's diagnostic.

**Provenance was PROVEN by control, not inferred.** The run ran the doctor against two
marketplace roots on byte-identical source: `<main>/marketplace` returned 0 findings,
`<worktree>/marketplace` returned 173. The branch touches none of the flagged files, and live
`--help` confirms the flagged flags exist (`manage-tasks batch-add --tasks-file` /
`--tasks-json`; `github_pr fetch_findings --required-bots` / `--optional-bots`). So the
differentiator is the **marketplace root**, not the source.

**The documented remedy did NOT work here, and three repairs were REFUTED.** This lesson's
Diagnostic says to clear the cache with `run_config cleanup --target temp` and expect a
swing to 0. On this run the gate had been green three times earlier in the session and turned
red only *after* a `run_config cleanup --target temp` swept 73,543 files and the plugin-doctor
dispatch regenerated the worktree executor — i.e. the sweep preceded the failure rather than
curing it. Recorded as do-not-retry in the resume anchor:

- `generate_executor generate`
- `generate_executor generate --force`
- `generate_executor generate --force` with `PM_SURFACE_BUDGET_SECONDS=1200`

All three returned `surfaces_derived=0 surfaces_reused=117 surfaces_not_derivable=45` —
surfaces reuse by script digest and nothing is re-attempted, so no regeneration path
re-derives them. Both executors were confirmed to contain the flags in `SCRIPT_SURFACES`, and
neither `.plan` nor `execute-script.py` is a symlink, so **executor content is not the
differentiator either.**

The Fix half of this lesson therefore becomes the whole remedy: the derived-surface path must
fail closed and report an unresolved derivation as a coverage gap rather than as N findings.
The cache-clear workaround is not reliable, and on this run it was the trigger.

dimensions rode the same invocation and are therefore also **un-gated** for that push.
