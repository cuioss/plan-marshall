# A plan hand-off can run twice: nothing detects a spec already in progress or shipped elsewhere

**Source signal:** kidicap-gateway-requirements inbox message `jwks-refresh-follow-ups-001` (finding, 2026-10-13).

## What happened

kidicap PLAN-28's hand-off command was run by two sessions. One shipped it as #437 (`82f2d7d8`). The second (`jwks-refresh-follow-ups`) got as far as execute task 5 on base `245e1928`, then execute's baseline check found 6 upstream commits touching its files, #437 among them. The operator closed it unmerged and archived it (`superseded_by_pr_437`). Its refine phase had also deferred deliverable 3 as "covered by a parallel task", a premise #437 contradicts (ADR-0063 A1).

## Why nothing caught it

- `next` emits a command; nothing records that a session has picked it up until the operator reports back, so the row can stay `staged` while the work is running.
- init's sibling check sees only local plans, not open or merged PRs or other sessions' worktrees.
- The orchestrator recorded the wrong `plan_marshall_plan_id` for the row (the duplicate's id), which hid the second run further.

## Candidate rule

Before emitting or starting a spec, check for: an open or merged PR whose branch or title names the spec's plan id or slug, an existing `landings/PLAN-NN.md`, and a live worktree for the same slug. Transition the row to `running` at emission, not on report-back, so a second `next` can see it.
