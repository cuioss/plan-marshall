# Search-tool denial to a dispatched leaf is non-deterministic within one session, so a coverage gap must be re-dispatched, never transferred into the plan success criterion

# Search-tool denial to a dispatched leaf is non-deterministic within one session, so a coverage gap must be re-dispatched, never transferred into the plan success criterion

The dispatched-leaf contract already anticipates that the harness may deny a
leaf its declared `Grep` / `Glob`, and it already prescribes the degrade path
(structured architecture queries first, `Read` inside an already-known file,
Bash `grep`/`find` blocked unconditionally) and the escape hatch (return the
coverage gap to the orchestrator rather than silently degrading to
spot-checks). See `ref-workflow-architecture/standards/agents.md` § "Leaf
cannot fire AskUserQuestion", the paragraph beginning "Its declared `Grep` /
`Glob` are legitimate search intent", and the mirrored
`agents/execution-context.md` § "Runtime tool availability for dispatched
leaves".

What the contract does NOT say — and what this run established — is that the
denial is **not a stable property of the session**. That omission is what
makes the documented escape hatch read as a dead end, and it is why this run
chose a mitigation the contract does not sanction.

## What happened

Plan `plan-39-manifest-tier-truthful-stamp` (PR #980). Within a single
session, four dispatched envelopes saw three different search-tool grants:

1. The phase-3-outline Q-Gate envelope was denied **both** `Grep` and `Glob`.
   Its content-sweep validators (2.12, 2.15) therefore ran at reduced
   breadth. It filed this as an info-severity coverage-gap finding (`5187da`).
2. The corrective re-dispatch of that same Q-Gate was **also** denied both —
   which is the observation that made the denial look deterministic, and
   which drove the mitigation choice below.
3. A later envelope in the same run **did** have `rg` available. It ran the
   sweep the first two envelopes could not, found 5 hits across 4 files, and
   confirmed all of them were already in scope — closing the gap at zero cost.
4. The `lessons-capture` envelope that recorded this lesson was denied `Grep`
   again (`Error: No such tool available: Grep`), while Bash `grep` was
   blocked by the file-operation hard rule's hook, exactly as the contract
   describes.

So: denied, denied, **granted**, denied — four envelopes, one session, no
change in the declared tool surface between them.

## The anti-pattern

Because envelopes 1 and 2 were both denied, the run concluded the capability
was simply unavailable and applied a mitigation the contract does not offer:
it **transferred the residual coverage risk into the plan's success
criterion** and resolved the finding `accepted`. The criterion then asserted a
sweep target the run had never actually enumerated.

That transfer is the defect, for two reasons:

- **It converts an unverified gap into a shipped promise.** A success
  criterion is a claim the plan commits to; a criterion whose site list was
  never produced by a search is an estimate wearing a criterion's clothes.
  Downstream (phase-4-plan, phase-5-execute, the finalize gates) treats it as
  verified because criteria are the thing they verify against — nothing
  re-opens the question.
- **It launders a capability failure into a scope decision.** The finding's
  resolution (`accepted`) records that the risk was *considered*, which reads
  as a deliberate scope judgment. It was not — it was a tool grant the run
  could not obtain, and the record no longer says so.

Envelope 3 is the proof the mitigation was unnecessary: the sweep was
runnable within the same session, and running it cost one dispatch.

## The rule

**A dispatched leaf that is denied its search tooling and cannot cover a
required sweep with structured queries + `Read` MUST return the coverage gap
to the orchestrator (the contract's existing escape hatch). The orchestrator
MUST then attempt to close it — not absorb it.**

The leaf closes the sweep itself first: `architecture search --content
--pattern P` is a script seam reached through the executor, so it is
available regardless of the harness tool grant. The ladder below now applies
only to the residual case — a sweep over a tree the inventory does not walk
(`.claude/**`, `.github/**`, gitignored paths).

Concretely, in orchestrator preference order:

1. **Re-dispatch the sweep in a fresh envelope.** The grant varies per
   envelope, so a second attempt is a real remedy and not a blind retry. This
   is a genuine exception to the blind-retry prohibition, because the failing
   input (the tool grant) is known to be re-sampled per dispatch — establish
   provenance by naming *the grant*, not the code, as the varying condition.
2. **Run the sweep in main context.** The orchestrator is not subject to the
   leaf's grant and can use `Grep`/`Glob` or the architecture inventory
   directly.
3. **Only if both fail:** record the gap explicitly as an unverified set —
   the criterion must say the enumeration is unverified rather than assert a
   count. Never silently promote an unenumerated set to a numeric criterion.

Correspondingly, a leaf must **not** self-resolve a search-denial coverage
gap as `accepted`; that resolution belongs to the orchestrator only after
steps 1 and 2 have been tried.

## Where the contract should change

`ref-workflow-architecture/standards/agents.md` (and its
`agents/execution-context.md` mirror) currently states the denial and the
degrade path but implies the denial is a fixed condition of the run. It
should add the non-determinism and the orchestrator's obligation:

- state that the `Grep`/`Glob` grant is re-sampled per dispatched envelope
  and MAY differ between envelopes in one session;
- state that a returned coverage gap obliges the orchestrator to attempt
  re-dispatch or a main-context sweep before accepting it;
- state that transferring an unclosed coverage gap into a plan success
  criterion is prohibited — an unverified set is recorded as unverified.

## Impact

No shipped defect on this plan: envelope 3's opportunistic sweep happened to
confirm the criterion's set was already complete. That is luck, not process —
had the sweep found an out-of-scope hit, the plan would have shipped a
criterion asserting a set it had never enumerated, and the miss would have
surfaced only at review or in production. The related outline lesson
(`2026-07-21-16-002`, rule 4 recurrence) is the same failure viewed from the
authoring side: that one under-counted a sweep set it *could* have searched;
this one asserts a sweep set it *could not*.

## Recurrence — 2026-07-22 (build-decision-oracle-consolidation, PR #985)

A `lessons-capture` envelope was denied the `Grep` tool and, per the hard
rule, treated Bash `grep`/`find` as unconditionally blocked by the
enforcement hook. It concluded — briefly — that NO whole-tree sweep was
possible in-envelope at all, which would have shipped an unswept ADR-007
obligation as an unverified gap rather than a closed one.

That conclusion was wrong on a narrower point than the original lesson's
"the grant is re-sampled per envelope": here the grant did **not** change.
The envelope did have a reachable in-envelope sweep and did not use it.

### Broadening — close the sweep in-envelope before returning a gap

The original escalation ladder (re-dispatch → main-context sweep → record as
unverified) assumes the denied envelope has no reachable search primitive at
all. That assumption no longer holds: `architecture search --content` is a
zero-cost rung **before** the ladder, reachable through the executor in the
same envelope. Only a sweep the inventory does not cover falls through to the
ladder. A leaf must not conflate "the `Grep` tool is denied" with "no sweep
is possible" — and must never substitute a Bash search binary, since `grep`,
`find`, `rg`, and git's `grep` subcommand are all hook-blocked.

## Recurrence — 2026-07-26 (retire-gemini-registry-ground-pr-agent-standard)

Confirms rung 2 of the escalation ladder ("run the sweep in main context") as
the working remedy when rung 1 (a non-blocked Bash search binary) is also
unavailable in-envelope. Two dispatched leaves in the same plan — a
q-gate content-sweep validator scoped to deliverable D1 and, separately, the
phase-5 execution leaf implementing D1 — both hit the denial (`Grep`/`Glob`
absent, Bash `grep`/`find` blocked by the hard-rule hook) on a deliverable
whose success criterion was "every hit in the survey scope is classified."
Both leaves correctly refused to fake the enumeration and returned the
coverage gap rather than substituting a spot-check — the behavior this
lesson's rule already prescribes, and worth reinforcing as the *correct*
response, not a failure. The orchestrator closed the gap both times by
writing a small ad-hoc scanner script under `.plan/temp/` and running it from
main context (rung 2), rather than re-dispatching (rung 1's zero-cost binary
rung was not applicable — the sweep needed content matching across many
files, and no non-blocked search binary was available either time) or
accepting an unverified criterion (rung 3). This occurrence exercises the
"neither the zero-cost binary rung nor re-dispatch closes it" branch and
validates that rung 2 (main-context sweep) remains a reliable, if costlier,
closure path — twice in the same plan.
