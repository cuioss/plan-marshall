# A new declarative key validated by a cross-cutting structural test in a DIFFERENT module is invisible to per-bundle module-tests; same-basename test files collide under pytest prepend import

A plan that adds a **new member to a declarative key/enum** (here: a `security`
profile category added to five bundles' `extension.py` files) is validated by a
**cross-cutting structural test that lives in a DIFFERENT module than the bundles
declaring the key**. Per-bundle `module-tests` ran green for every touched bundle, yet
the change was still broken — because the validator that enforces the allowlist
(`test_extension_implementations.py`, gating on `VALID_PROFILE_CATEGORIES`) lives in the
`plan-marshall` structural-validator test surface, not in any of the five touched
bundles. Only the **whole-repo `module-tests`** exercised it.

## Where it surfaced

Shipping `security-audit-finalize-step`, deliverable D3 added a `security` profile key to
five `extension.py` files (one per security-bearing bundle). The phase-5 executor ran
per-bundle `module-tests` for the touched bundles — all green. The defect set was caught
only by the whole-repo run:

1. **Allowlist in a foreign module.** The new `security` category was not added to
   `VALID_PROFILE_CATEGORIES`, so the structural validator
   `test_extension_implementations.py` (which is not part of any single bundle's
   module-tests) failed. The validator and the declaring bundles are in different
   modules, so per-bundle runs never executed it.
2. **Same-basename collision under pytest prepend import.** Four new test files shared a
   single basename. Per-bundle runs passed because each ran in isolation, but the
   whole-repo run, under pytest's default `prepend` import mode, collided the
   identically-named modules (`import file mismatch` / the second file shadowing the
   first), so tests silently did not all run as authored.
3. **Coverage hole in the declaring set.** One of the five security-bearing bundles
   (`java-cui`) declared the new profile but received no security-profile test at all —
   a per-bundle green run masked the missing coverage.

## Root cause

Phase-5 verification scope is keyed off the plan's touched bundles. A new member of a
declarative key has TWO blast radii the touched-bundle set cannot see:

- The **central structural validator / allowlist** that enforces the key's legal values
  lives in a different module (`plan-marshall`'s test surface). A new key member is only
  legal once registered there; per-bundle runs never load that validator.
- **New test files are global namespace citizens** under pytest's `prepend` import mode.
  Two test files anywhere in the repo that share a basename collide in the whole-repo
  run even though each per-bundle run is clean.

Symptom signature:

- A plan adds a new value to an enum/declarative-key in N bundles; `module-tests {bundle}`
  is green for all N.
- A structural validator in a *different* module enforces the key's allowlist
  (`VALID_*` set) and was not updated — caught only by whole-repo `module-tests`.
- New test files share a basename with an existing/sibling test file — `import file
  mismatch` only under the whole-repo prepend-import run.

## How to apply

- **Trigger on the change kind, not the file set.** When a deliverable adds a new member
  to a declarative key/enum (a profile category, a `VALID_*` allowlist member, a manifest
  step kind), grep the whole repo for the allowlist constant (`VALID_PROFILE_CATEGORIES`
  and siblings) and treat any hit in a foreign module as a mandate to run **whole-repo
  `module-tests`** (or the owning validator module's tests) at end-of-phase — never trust
  a per-bundle green sweep alone.
- **Register the key member in its central validator in the same deliverable.** Adding
  the key to the declaring bundles and adding it to the cross-cutting allowlist
  (`VALID_PROFILE_CATEGORIES`) are one atomic change; a deliverable that does the former
  without the latter is structurally incomplete.
- **New test files must have repo-unique basenames.** Under pytest `prepend` import mode,
  two same-basename test files collide in the whole-repo run. Name new test files with a
  module-qualifying prefix (or configure `importmode=importlib`) so they never shadow each
  other.
- **Verify every declaring bundle has its own test.** When a key is added to N bundles,
  confirm N tests exist — a green per-bundle run on a bundle with zero new tests is a
  false-confidence signal.

## Impact

Per-bundle `module-tests` is the correct cheap default for localized work, but it has a
structural blind spot for new declarative-key members: the enforcing validator and the
new test files both have whole-repo scope. The fix is whole-repo verification keyed on the
change kind (new enum/allowlist member), plus repo-unique test basenames — not abandoning
per-bundle scoping.
