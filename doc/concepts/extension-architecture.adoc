= Extension Architecture
:nofooter:
:toc: left
:toclevels: 2

xref:../../README.md[Plan Marshall] » xref:README.adoc[Concepts]

"How do I add a domain without forking the orchestrator?" is the plumbing question every successful workflow tool eventually has to answer. Plan Marshall's answer is that the core never decides what `Java` or `documentation` or `OCI containers` means — every domain-specific behaviour lives in a separate *bundle* that the core discovers, registers, and calls through a small, fixed set of extension points.

== The seam

The Plan Marshall core — the orchestrator, the six phase skills, the `execution-context` dispatcher, the `manage-*` services — owns the lifecycle. Bundles own the domain knowledge. They meet at a deliberately narrow contract: a handful of `ExtensionBase` hook methods, two declarative `implements:` markers on workflow / agent files, and one filesystem convention for discovery (every bundle ships a `skills/plan-marshall-plugin/extension.py` file at a hardcoded path). Once you know that seam, every domain bundle ships exactly the same way.

image::../resources/diagrams/extension-topology.svg[Extension topology — Plan Marshall core (orchestrator + phase skills + execution-context + manage-* + the extension-discovery scanner) on the left; the twelve named extension points (build, verify, triage, recipe, outline, provider, execution-context-workflow, dynamic-level-executor, self-review-surfacing, domain-verb, derivation-resolver, path-attribution) on the right with declaration mechanism and impl count annotations. All ten production bundles implement get_skill_domains; the other hooks are optional., align=center]

The required hook is `get_skill_domains()` — every bundle declares its domain identity and organises its skills by profile (`core`, `implementation`, `module_testing`, `integration_testing`, `quality`, `documentation`, `security`). Everything else is optional: the seam exposes twelve *domain-facing* extension points beyond that minimum — build, verify, triage, recipe, outline, provider, execution-context-workflow, dynamic-level-executor, self-review-surfacing, domain-verb, derivation-resolver, path-attribution — and a bundle fills in only the slots it actually needs. A frontend bundle might implement three; a documentation bundle might implement four. The unfilled hooks return the default no-op and the core uses its generic behaviour. (The full contract catalogue is larger — 17 `ext-point-*` documents in link:../../marketplace/bundles/plan-marshall/skills/extension-api/standards/[`extension-api/standards/`] — but the remaining five — `finalize-step`, `lane-element`, `domain-bundle`, `retrospective`, `build-verify-step` — are core-side wiring contracts, not slots a domain bundle typically fills.)

One of those twelve — *verify* — is a findings-pipeline stage rather than a domain-behaviour hook: a producer declares a `verification_profile`, and the findings it emits pass through an optional adversarial-refute pass that confirms each is a genuine defect before triage sees it (false positives close `rejected`). It runs BEFORE the `triage` extension point in the findings pipeline. The contract lives in xref:../../marketplace/bundles/plan-marshall/skills/extension-api/standards/ext-point-verify.md[`ext-point-verify.md`]; the pipeline placement is in xref:automatic-reviews.adoc[Concepts › Automatic Reviews]. It is NOT to be confused with `ext-point-build-verify-step`, the phase-5 build/verify *command* step (`quality-gate`, `module-tests`, `coverage`) — an unrelated concern.

Two of the twelve — *derivation-resolver* and *path-attribution* — are the newest, and the only ones whose opt-in is multiple inheritance rather than a hook method or an `implements:` marker. A resolver answers "which modules depend on which", contributing the `(from, to)` module pairs behind the `graph` / `path` / `neighbors` / `impact` query family. Edge derivation is an extension point because there is no domain-neutral way to derive it: a Maven reactor derives edges from coordinates, a documentation tree from cross-document references, a Python package from imports. Core owns the merge, the provenance, and the traversal; it owns none of the derivation. The substrate framing — the Tier 0/1/2 ladder this sits on, the N-resolver union, and the provenance property that keeps a zero-edge answer from reading as a finding — is in xref:code-intelligence.adoc[Concepts › Code Intelligence]; the contract is xref:../../marketplace/bundles/plan-marshall/skills/extension-api/standards/ext-point-derivation-resolver.md[`ext-point-derivation-resolver.md`]. *Path-attribution* is the younger of the two and answers the companion question — which module *owns* a given path — contributing the `(path_prefix, module_name)` claims behind `which-module`'s third resolution rung and behind the change-footprint classifiers; the ownership question is domain knowledge for the same reason edge derivation is, and the keyed-mapping merge that resolves it is in xref:code-intelligence.adoc[Concepts › Code Intelligence]. Its contract is xref:../../marketplace/bundles/plan-marshall/skills/extension-api/standards/ext-point-path-attribution.md[`ext-point-path-attribution.md`].

=== Four axes, deliberately disjoint

The twelve points hang off four independent hierarchies, and which hierarchy a hook belongs to is a real design decision rather than filing convenience:

* *Axis-A — skill loading.* "What skills does this domain load?" Declared by `ExtensionBase`, subclassed by language and content domain bundles (`pm-dev-python`, `pm-documents`).
* *Axis-B — the file-to-build map.* "What build does a changed file trigger?" Declared by `BuildExtensionBase`, subclassed by build-system skills (`build-maven`, `build-pyproject`).
* *Axis-C — module-edge derivation.* "Which modules depend on which?" Declared by `DerivationResolverBase`, subclassed by whichever bundle owns the relevant domain knowledge. The opt-in has a live example on each hierarchy: resolvers are registered from Axis-B build skills and from Axis-A domain bundles alike. Which bundle owns a given derivation follows from where the knowledge lives — Python-import edges, for instance, are language knowledge and belong to the Python domain bundle rather than to the Python build skill. The per-resolver roster is in xref:../../marketplace/bundles/plan-marshall/skills/extension-api/standards/ext-point-derivation-resolver.md[`ext-point-derivation-resolver.md`].
* *Axis-D — path attribution.* "Which module owns this path?" Declared by `PathAttributionBase`, subclassed by whichever bundle owns the tree being claimed (`plan-marshall-plugin` claims `.plan` and `.claude/skills`).

The four ABCs inherit from none of each other. Axis-A and Axis-B are kept disjoint by xref:../adr/004-The_file-to-build_contract_is_owned_by_build-system_extensions_not_languagecontent_domains.adoc[ADR-004] — a build system is not a language domain — and that disjointness is precisely what forced Axis-C to be a third axis instead of a face on either. `build-maven` subclasses `BuildExtensionBase` and not `ExtensionBase`, so a resolver hook on `ExtensionBase` would have been unreachable from the bundle that owns the Maven coordinate join; putting it on `BuildExtensionBase` would instead have forced the markdown and python resolvers — both Axis-A domain bundles — to masquerade as build systems. Axis-D lands on the same argument from the other direction: the bundles that know what they own straddle both hierarchies — `plan-marshall-plugin` and `pm-documents` sit on Axis-A, `build-pyproject` on Axis-B — so a claim hook on either ABC would have structurally excluded the other side, the containment failure xref:../adr/013-A_capability_spanning_both_extension_hierarchies_lives_in_a_sibling_ABC_not_a_face_on_either.adoc[ADR-013] names. An implementor from either hierarchy opts into Axis-C or Axis-D by multiple inheritance, which is the only shape reachable from both sides, and the shipped Axis-C roster now exercises both sides rather than only one.

The `security` profile is *resolution-only*: a bundle declares its focused per-domain security skills under `skills_by_profile.security`, and the proactive `finalize-step-security-audit` resolves them for each affected domain when it runs. Unlike the work profiles (`implementation`, `module_testing`, …), `security` is deliberately NOT auto-included in phase-4 task creation — it never spawns its own implementation tasks; it exists purely as a resolution axis the finalize-step gate reads (see xref:security.adoc[Concepts › Security]).

== Discovery

At install time the executor's `extension_discovery.py` scans every bundle under `marketplace/bundles/` (or the equivalent plugin-cache path) for the hardcoded discovery file. If it exists, the scanner imports it, instantiates the `Extension` class, and calls `get_skill_domains()` to learn the bundle's domain identity. The returned key is registered in `marshal.json` under `skill_domains.{key}`, with a `bundle` field added by `skill-domains configure` that reverse-maps from domain key to source bundle. Every subsequent hook is invoked through the same `Extension` instance whenever its host workflow needs it. The discovery is automatic — no manifest lookup, no per-bundle configuration, no registry to keep in sync.

== Identity, domain axis, compute: three orthogonal resolutions

The seam resolves three independent questions at dispatch time, and keeping their vocabulary distinct is load-bearing because each uses an overloaded word:

* **persona** — the *identity* a task is dispatched **as**. A persona (`implements: persona`) is a named, resolvable bundle of skills; xref:../../marketplace/bundles/plan-marshall/skills/manage-personas/SKILL.md[`manage-personas resolve`] flattens its composition DAG into the explicit `skills[]` the dispatcher carries. See xref:personas.adoc[Personas].
* **profile** — the *domain-specific resolution axis* (`implementation`, `module_testing`, `documentation`, `quality`, …). A profile is not an identity; it is the key the persona's `profiles:` frontmatter uses to pull `profile × domain` skills into the context. `get_skill_domains()` organises each bundle's skills by exactly this set of profiles.
* **role / level** — the *compute selection*: which model and effort level runs an LLM-judgement workflow. The xref:execution-context.adoc[execution-context] resolver maps a phase-scoped role to one of the level variants and dispatches it.

These three are orthogonal: a single dispatch resolves an identity (persona → `skills[]`), a domain axis (profile → domain skills), and a compute tier (role/level → agent variant) independently. "Role" in the compute sense (role/level) is deliberately never used for the identity sense — that is what *persona* names.

== Where this fits

Extension Architecture is the *plumbing* answer to "what is Plan Marshall." The xref:planning-workflow.adoc[Planning Workflow] is the *user-visible* answer. The twelve domain-facing extension points are the contact points between the two: every domain decision a plan makes — which build skill to dispatch (xref:build-management.adoc[Build Management]), which triage skill loads for a Sonar issue (xref:automatic-reviews.adoc[Automatic Reviews]), which skills enter the subagent context for a Java testing task (xref:skill-handling.adoc[Skill Handling]), which resolver derives the module graph and which attributor owns a changed path (xref:code-intelligence.adoc[Code Intelligence]) — flows through one of them.
