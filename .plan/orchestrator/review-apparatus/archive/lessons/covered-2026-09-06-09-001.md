title: pr wait-for-comments reported no reaction while two CodeRabbit refusals were already on the PR
content: "## Problem

On PR #1425 an explicit `@coderabbitai review` trigger was posted at 09:09:52Z. CodeRabbit reacted
twice within nine seconds:

- a NEW comment `IC_kwDOQ3xasM8AAAABS0v-wA`, `created_at 09:09:57Z` — *\"Action not completed — Review
  rate limited\"*;
- an IN-PLACE EDIT of the pre-existing notice `IC_kwDOQ3xasM8AAAABS0JWdw`, `created_at` still
  `07:00:17Z` but `updated_at` moved to `09:10:01Z`, its body now stating a fresh *\"53 minutes\"*
  countdown.

`ci pr wait-for-comments` ran for 189s across that period and returned:

```toon
timed_out: true
new_count: 0
movement_matched_bots[0]:
```

It reported **no reaction at all** while both reactions were already on the PR.

## Why both arms missed it

Two independent causes, and neither is a flake:

- **The movement arm never looked.** CodeRabbit's registry declares
  `participation_requires_update: false`, so in-place edits are outside what `movement_matched_bots`
  inspects. The edited notice is therefore invisible to that arm by configuration.
- **The count arm's baseline was already too late.** The new comment landed before the wait took its
  baseline, so the count went `6 → 6` and `new_count: 0` is arithmetically correct while being
  substantively false.

`rate_limited_bots[]` was the only structured field that flagged CodeRabbit at all, and it cannot
discriminate a fresh refusal from a stale one: it samples the newest comment without exposing its
timestamp. Only reading the comment BODY together with `updated_at` separates the two.

## Why it matters

A verdict of *\"no reaction\"* over a PR carrying two reactions is the archetype this epic tracks:
not-looking renders identically to looked-and-found-nothing. The operational consequence here was
concrete and nearly costly — a caller trusting `new_count: 0` concludes the bot is silent, and the
standing remedy for silence is to CLOSE the PR unmerged and reopen it. That is a destructive,
CI-re-running remedy applied on evidence that was simply not gathered, when the true state was an
ordinary quota refusal with a stated 53-minute ETA.

It also propagated a wrong inference: an earlier run concluded from the unchanged `created_at` that
the window had reopened at 07:59Z, when the in-place edit showed the real reset was ~10:03Z.

## Directive

Establish whether `wait-for-comments` can report a trustworthy negative at all for a bot declaring
`participation_requires_update: false`. If it cannot, it must say so rather than returning
`new_count: 0` — an arm that structurally cannot observe a class of reaction must not render its
silence as an observation.

Two specific gaps to settle:

- The baseline must be taken before the triggering action, or the return must publish the baseline
  it used so a caller can see that a reaction predating it was excluded by construction.
- `rate_limited_bots[]` should carry the sampled comment's `updated_at`, so a consumer can tell a
  refusal issued seconds ago from one issued two hours ago. Without it the field cannot support the
  wait-versus-trigger decision that callers actually make from it.

## Verification

Assert against a PR where a bot reacts ONLY by editing an existing comment: the verb must not report
that as no reaction. Add the matched negative — a PR where the bot genuinely did nothing — so the
test proves the two are distinguishable rather than that the detector merely fires. A test built only
on the new-comment path passes today and says nothing about either failure above."
